# 2. Semantics

This clause defines the semantic model of the Kurt machine: the δ model, the structure and the ordering of τ, reachability and indeterminacy, σ operations, the uniformity rule, the airside/landside boundary, and the classification of errors.

## 2.1 The δ model

An **operation** is an abstract semantic action defined by this specification.

An **instruction** is a Γ sequence that δ interprets as an operation.

An **evaluation** performs one operation. An evaluation yields a value where the operation it performs yields one.

An **execution context** performs a sequence of evaluations. A programme has at least one execution context, and finitely many. Every evaluation is performed by an execution context of the machine on which it takes place.

The **local state** of an execution context is what, with the programme, determines the operation the context performs next. It holds no part of τ. An execution context occupies one local state before each evaluation it performs, and the programme determines the one it occupies before the first, its **entry state**.

For an execution context and each local state of it, the programme determines either that the context performs no further operation, or one operation that it performs. Where it determines an operation, it determines the local state the context occupies thereafter from the operation, from what each read the operation performs yields, and from the signal the operation receives from the environment where it receives one. The evaluations of an execution context are those the programme so determines, beginning at its entry state.

An operation is **atomic** where δ completes it upon the objects it names alone, bringing each directly from its prior value to its resulting value. Operations are **transactional** where δ completes them as one.

An **execution** of a programme comprises, of each of its execution contexts, finitely many of the evaluations it performs, from the first. Of each such evaluation it comprises the value it yielded and the signal it received where there was one. It comprises also the following, as the subclause on the ordering of τ defines them:

&mdash; The settlement order of each cell.

&mdash; The write each execution context observes at each cell at each point.

&mdash; The rank of each write.

A **programme point** is a position in a programme at which an execution context that reaches it occupies a local state.

The **programme order** of an execution context is a strict total order over the evaluations it performs.

The **points** of an execution context are indexed by the non-negative integers. The τ operations an execution records of a context, as defined in the subclause on Γ and cells, are performed one at each successive point, beginning at the first. The local state an execution context occupies at a point is the one it occupies before the evaluation whose τ operation is performed there. Where one evaluation is earlier than another in the context’s programme order, each τ operation of the first is performed at an earlier point than each τ operation of the second.

The evaluations of the operands of an operator are earlier in programme order than the evaluation that performs the operation the operator denotes.

### Implementation defined

The **atomicity set** of a machine holds the pair of a size and an alignment where an access of that size, at an address aligned for that alignment, can be atomic. The set can be empty.

The **transactionality set** of a machine holds the pair of a size and an alignment where a load and a store upon an object of that size, at an address aligned for that alignment, can be transactional. The set can be empty, and is a subset of the atomicity set.

Both sets are implementation defined for each supported environment of the programme machine and of the translation machine.

### 2.1.1 Operand evaluation order

#### Static semantics

The **leading operand** of a binary operator is the operand that comes before the operator in the token sequence. The **following operand** is the operand that comes after the operator in the token sequence.

#### Dynamic semantics

For all binary operators, every evaluation of the leading operand is earlier in programme order than every evaluation of the following operand.

#### Design rationale (informative)

The operands of a binary operator are named by their position in the token sequence and not by a side. Which side of an operator an operand appears on depends on the direction in which the source text is displayed, and the language does not fix the direction.

#### Examples (informative)

```
// Evaluation in programme order
let mut i: si4 = 0;
let x = { i += 1; express i; } + { i += 1; express i; };
// Leading operand is evaluated first: i becomes 1, express 1.
// Following operand is evaluated next: i becomes 2, express 2.
// x = 1 + 2 = 3
```

## 2.2 The structure of τ

### 2.2.1 Γ and cells

The number of symbols of Γ is defined by the environment of the machine.

A **cell** is the least unit of storage of a machine; it holds one symbol of Γ.

A **Γ sequence** is a finite sequence of zero or more symbols of Γ.

A **bit** of a non-negative integer *v* at a non-negative position *k* is the value <span class="floor">⌊&thinsp;*v* / 2<sup>*k*</sup>&thinsp;⌋</span> mod 2 together with the position. The **weight** of position *k* is 2<sup>*k*</sup>. Where a rule names a number of bits, it names the bits at the positions less than that number.

The **cell width** of a machine is the least number of bits for which every symbol of Γ is less than two raised to it. *B*<sub>p</sub>, *B*<sub>x</sub>, and *B*<sub>c</sub> denote the cell widths of the programme machine, the translation machine, and the constant machine.

A **write** places one symbol at one cell, and a **read** yields one symbol from one cell. A write and a read are operations. A write names a cell and the symbol it places, and a read names a cell. A **τ operation** is a write or a read.

The **initial write** of a cell is the write that places there the symbol the initial storage of its machine pairs with the cell, as defined in the clause on general matters. No execution context performs it.

#### Implementation requirements

A conforming implementation exists only for an environment in which the number of symbols of Γ is a power of two greater than one.

A conforming implementation shall perform each τ operation at most once. It may introduce a τ operation at a cell into an execution context only where it establishes during translation that this context performs every τ operation at that cell.

### 2.2.2 Addresses and alignment

The cells of τ are numbered from zero to *A* &minus; 1, where *A* is the number of cells of τ; the number of a cell is its **address**. The cell **next to** a cell is the one whose address is greater by one; the cell next to the cell addressed by *A* &minus; 1 is the cell addressed by zero.

A **storage region** is an address *a* together with a number of cells *n* not greater than *A*. It comprises *n* cells in order. The first is the cell addressed by *a*, and each subsequent one is the cell next to the one before it. The **address of a storage region** is *a*, and the **offset** of a cell of the region is its position in that order, counting from zero.

An address is **aligned for** a non-negative integer where that integer is zero or divides the address.

#### Static semantics

`uaddr` is the type of an address. The size and value set of `uaddr` are defined in the clause on types. The forms a reference takes, and the information each carries beside an address, are defined in the clause on references and resource management.

#### Implementation requirements

An access the environment of its machine does not accept can cause indeterminate state, as defined in the subclause on indeterminate state. Which accesses it accepts is outside the scope of this specification. The implementation shall not use how a reference was obtained to determine whether the environment of its machine accepts an access through it, or to eliminate or reorder the access.

### 2.2.3 Types

#### Dynamic semantics

A **type** determines three properties: a **size**, an **alignment**, and an **interpretation**.

The size of a type, denoted `T'size`, is a non-negative integer not greater than *A*. The alignment of a type, denoted `T'align`, is a non-negative integer; an address is aligned for a type where it is aligned for `T'align`. The interpretation of a type maps each Γ sequence of length `T'size` to exactly one **value**; the values of the type are those it so gives, and the Γ sequences it maps to a value **represent** the value. The size, alignment, and interpretation of each type are defined in the clause on types.

### 2.2.4 Objects

An **object** is an address together with a type, for the period during which it exists. A reserved object exists from the reservation of its storage until its release, and objects of distinct reservations are distinct, as are objects that a type places as or within distinct fields or elements.

The storage region of an object is the one at its address of as many cells as the size of its type. Storage the implementation reserves for an object lies at an address aligned for its type, except where the layout rules of the clause on types place a constituent object at an address not so aligned.

An object is a **constituent object** of another where the type of the other places it within its layout, directly or within another it so places. The **outermost object** of an object is the reserved object, not itself a constituent object of a reserved object, of which it is a constituent object, or, where it is not a constituent object of a reserved object, the object itself.

Distinct reserved objects, neither of which is a constituent object, shall occupy disjoint cells while the storage of both is reserved. Such a violation, where not detected during translation, can cause indeterminate state.

Storage is **reserved** for an object and later **released**. The subclause on object lifetime defines, for each kind of reserved object, when each occurs. The **object lifetime** of an object begins when a store first makes it initialized, or, for an immortal object, when its storage is reserved; it ends when its storage is released.

At any point within its object lifetime, a reserved object is either **uninitialized** or **initialized**. Any other object is initialized. An object is initialized when its object lifetime begins. To **invalidate** an object is to make it, and each constituent object of it, uninitialized. A store into it, or into an object of which it is a constituent object, made without passing through a reference, makes it initialized.

A **store** places a value in an object, and a **load** obtains the value an object holds. A store and a load are operations. A store names an object, a type, and the value it places, and a load names an object and a type. Every evaluation that yields an object’s current value performs a load.

An **access** is a load, a store, or a load and a store performed as one. Each access is performed through a type. Where an access is performed through a reference, the type is the referent type of the reference and the address is the one the reference carries, and otherwise the type is the type of the object accessed and the address is that of its storage region.

A discriminant, a field, or an element that a type places within its layout, directly or within another it so places, is an **inner object** of an object accessed through that type. Where the object an access through a reference names is an inner object of the referent, the type is instead the type of that object. The address of such an access is instead the one the reference carries advanced by the offset at which the referent type so places that object. A referent type `[U]` places each of its elements at the offset its position, counting from zero, multiplied by `U'size`.

An access **reaches** the cells from its address, as many as the size of its type. Those cells form a storage region whose address is the address of the access.

**Initialization** is a store that begins the object lifetime of the object it stores into, or that transitions an object from uninitialized to initialized.

A **binding** is the association between an identifier or `self` and an object, introduced by a declaration. A binding persists for the object lifetime of its object. The declaration forms that introduce bindings are defined in the clause on declarations.

#### Dynamic semantics

Except where a rule states otherwise, a store performs a write at each cell of the storage region it reaches, placing at each the symbol at the corresponding position of a Γ sequence representing the value stored. Where more than one Γ sequence represents the value, the clause on types defines which of them is placed. A load performs a read at each cell of the storage region it reaches. Those reads yield a Γ sequence, ordered by cell. The value of the load is what the interpretation of its type gives that sequence. Which symbol a read yields is defined in the subclause on the ordering of τ. An access performs its τ operations at successive points of its execution context, its reads at earlier points than its writes.

A store, other than a store through an unmanaged reference, proceeds in two steps:

1. The existing value held by the target object is destroyed, if the object is initialized.
2. The writes of the new value take place at the target object.

#### Implementation requirements

A conforming implementation shall produce opaque code in which an object occupies its storage region from the reservation of its storage until its release, except where the implementation can resolve to that object every access that reaches the storage region.

#### Examples (informative)

The following are cases in which an implementation cannot resolve to an object every access that reaches its storage region:

&mdash; An external subroutine is invoked while the object exists.

&mdash; A reference to the object is stored in a `static` or `static mut` binding.

&mdash; A reference to the object is converted to `uaddr`.

&mdash; A reference to the object is used as the operand of a reinterpretation.

&mdash; A reference to the object appears as an operand in an `instruct` block.

### 2.2.5 Kurt standard alignment

#### Static semantics

**Kurt standard alignment** is the layout of every type and of every storage region the implementation reserves, except where a rule states otherwise.

Kurt standard alignment assigns to a finite sequence of types `T_0, T_1, ..., T_n` an offset for each, an alignment, and a size. Write *o*<sub>*i*</sub> for the offset of `T_i` and *a* for the alignment:

*o*<sub>0</sub> = 0

*o*<sub>*i*</sub> = <span class="ceil">⌈&thinsp;(*o*<sub>*i*&minus;1</sub> + `T_{i-1}'size`) / `T_i'align`&thinsp;⌉</span> × `T_i'align`

*a* = max(0, `T_i'align` over all *i*)

size = <span class="ceil">⌈&thinsp;max(0, *o*<sub>*i*</sub> + `T_i'size` over all *i*) / *a*&thinsp;⌉</span> × *a*

Where the divisor of one of these quotients is zero, the rounding leaves the dividend unchanged. Where the sequence is empty, the size and the alignment are both zero.

The additions and the roundings in these formulae are computed over the non-negative integers without wrapping.

A **padding cell** is a cell of the representation of a value of a composite type that lies outside the representation of every value that value holds or carries.

### 2.2.6 Object lifetime

A **scope** is a region of a source unit over which a name introduced within it is visible. A name is visible throughout the innermost scope containing its introduction, and outside it only so far as the visibility modifier defined in the clause on declarations permits. A block is a scope.

**Declaration order** is the order in which bindings appear in the token sequence. Where a single declaration introduces more than one binding, the declaration order of those bindings is the order of the binding identifiers within the pattern.

#### Dynamic semantics

A **reserved object** is an object for which a rule of this specification reserves storage, or a constituent object of such an object. Every reserved object other than a constituent object is exactly one of four kinds: an automatic object, a permanent object, a temporary object, or a resident object, as defined below. An automatic object or a permanent object is a **declared object**. An automatic object or a temporary object is a **mortal object**, and a permanent object or a resident object is an **immortal object**. A constituent object is a mortal object or an immortal object as the object of which it is a constituent object is, and its storage is reserved and released with the storage of that object.

An **automatic object** is the object of a binding other than a `static` binding. Its storage is reserved and released within the enclosing scope.

For the object of a subroutine parameter binding or of a variadic binding, storage is reserved at subroutine entry and the object is initialized by the invocation. For every other automatic object, storage is reserved at block entry.

A **temporary object** is an object, other than a declared object, a resident object, or a constituent object, that an evaluation produces. The value of a value expression is held by a temporary object that its evaluation produces. An evaluation that produces a temporary object stores into the object the value it holds. Storage for a temporary object is reserved where the object is produced and released when its object lifetime ends.

A **master** is any of the following:

&mdash; An evaluation of a block, of a statement, of a declaration, of an analysis root, or of an expression whose value selects a branch, an alternative, or a loop body.

&mdash; A round of an evaluation of a `while` expression, as the clause on statements and control flow defines.

&mdash; The body evaluation of a subroutine invocation together with its value return.

The **master of** a temporary object that holds the value of an expression is the innermost master that comprises the following evaluations:

&mdash; The evaluation of that expression.

&mdash; Each evaluation that, without passing through a reference, loads the temporary object or a constituent object of it, creates a reference designating either, or matches its value against a pattern.

&mdash; Each evaluation that does the same to the temporary object holding the value of an expression enclosing that expression, where that value is or holds a managed reference chained to the first temporary object or having an ancestor chained to it.

The object lifetime of a temporary object that holds the value of an expression ends where control leaves its master. Where an evaluation within its master initializes an automatic object, other than by an assignment expression, with a value that is or holds such a managed reference, the object lifetime ends instead immediately after the destruction of the last destroyed of those automatic objects, where that is later. The object lifetime of any other temporary object ends where control leaves the innermost of the following that comprises the evaluation that produces it: an evaluation of a block or of an analysis root, a round of an evaluation of a `while` expression, or the body evaluation of a subroutine invocation together with its value return.

A **permanent object** is the object of a `static` binding, or the object that a `static` declared as `?` introduces. Its storage is reserved before the execution of its machine begins, and never released.

A **resident object** is a reserved object, other than a permanent object or a constituent object, whose storage is reserved before the execution of its machine begins, or, for the crossed counterpart of a referent, where the referent crosses. Its storage is never released.

One object lifetime is **longer than** another where the other ends and it does not, or where both end and it ends the later. The two are **equal** otherwise.

A `break`, a `continue`, or an `express` exits, innermost first, each master and each scope between it and its target before control transfers.

When a scope exits, the automatic objects of the scope are destroyed in reverse declaration order, and immediately after the destruction of each, the temporary objects whose object lifetime ends there are destroyed in reverse order of production. The object of the variadic binding, if present, is destroyed after all block-local automatic objects and before the objects of the parameter bindings, which are destroyed in reverse declaration order.

Where control leaves a master, the temporary objects whose object lifetime ends there are destroyed in reverse order of production, before the automatic objects of the block the master evaluates, if any.

Where an object is destroyed, the value it holds is destroyed, as the clause on references and resource management requires.

#### Examples (informative)

```
fn example(a: si4, b: si4) -> si4 {
    // Declaration order: a, b, x, y
    let x = a + 1;
    let y = b + 2;
    return x + y;
}   // Destruction order: y, x, b, a
```

### 2.2.7 Automatic object layout

#### Dynamic semantics

Upon entry to a block, a storage region is reserved for the block. That region is its **layout region**. Within it, before any initializer is evaluated, storage is reserved in declaration order for all automatic objects belonging to the block. Kurt standard alignment, applied to the types of those objects in that order, gives the offset of each of those objects within the layout region and the alignment of the region.

Upon exit from a block, the storage reserved for it is released.

Upon subroutine entry, a layout region is reserved for the objects of the subroutine’s parameter bindings and of its variadic binding if any. The rule above, applied to the parameter bindings in declaration order followed by the variadic binding, determines the addresses of those objects within it. That region is released where control leaves the subroutine body, after those objects are destroyed.

#### Implementation requirements

A conforming implementation may use any physical storage mechanism to implement the **automatic object layout model**, which the dynamic semantics above define. Where any access the implementation cannot resolve to an object reaches storage within a layout region, every object in the region whose storage the access can reach shall occupy its storage region at the address the automatic object layout model gives it.

#### Implementation defined

The physical storage mechanism used to implement the automatic object layout model is implementation defined.

#### Examples (informative)

```
// Example 1: local binding layout in declaration order
fn pair_sum() -> si4 {
    let a: si4 = 3;
    let b: si4 = 4;
    let result = a + b;
    // Automatic object layout model (block entry):
    //   addr:  | a: si4  | b: si4  | result: si4 |
    //   cells: [ 0 ... 3 | 4 ... 7 | 8 ... 11    ]
    // result is the return operand but occupies its
    // declared position in the layout.
    return result;
}
// A conforming implementation may place result directly in
// the invoker’s storage (eliding the copy) if no access in the
// block that the implementation cannot resolve to an object
// can observe the difference.

// Example 2: an access through an unmanaged reference reaches
// a return-value object
fn example2() -> si4 {
    let arr: [si4; 3] = [0, 0, 0];
    let i: si4 = 0;
    // Automatic object layout model:
    //   addr:  | arr (12 cells) | i (4 cells) |

    airside {
        let p = arr.ptr as %mut si4;
        *(p + 3) = 5;
        // The store through p + 3 targets storage beyond arr’s
        // bounds. In the automatic object layout model, p + 3
        // targets the storage of i, so 5 is stored into i.
    }

    return i; // returns 5
}
// The conclusion follows from the automatic object layout model,
// so a conforming implementation may constant-fold the subroutine
// to `return 5;`. Neither arr nor i need occupy storage where the
// return value is the only effect the programme has.

// Example 3: dynamic index and range splitting
fn example3(n: uaddr) -> si4 {
    let .{ mut arr, i } = .{ [0~si4; 3], 0 };
    airside { *arr.xat_u(n) = 5; }
    return i;
}
// The layout fixes the relative positions of arr and i. Partition
// the execution-time cell offset n_cells = n * T'size, where T is
// the element type of arr:
//
//   Automatic object layout model (cells, relative to arr):
//     | arr: 12  | i: 4      |
//     [ 0 ... 11 | 12 ... 15 ]
//
//   n_cells ∈ {0 ... 8}:
//       within arr; unobservable store under the uniformity rule;
//       i remains 0
//
//   n_cells ∈ {9 ... 11}:
//       straddles arr and i; have i occupy its storage, return
//       the value a load of i reads from its cells
//
//   n_cells == 12:
//       targets i exactly; return 5
//
//   n_cells ∈ {13 ... 15}:
//       overlaps i and storage beyond the layout; preserve the store,
//       have i occupy its storage, return the value a load of i
//       reads from its cells
//
//   otherwise:
//       targets storage outside the layout; preserve the access
//
// Here T = si4, so n_cells is a multiple of 4: the straddling
// ranges are unreachable and the partition collapses to
//
//   n ∈ {0, 1, 2}: unobservable store, return 0
//   n == 3:         store hits i, return 5
//   otherwise:      store outside the layout, return 0
//
// A possible optimized form:
//
//     fn example3_opt(n: uaddr) -> si4 {
//         let s = n * si4'size;
//         if s == 12 { return 5; }
//         if s > 3 * si4'size {
//             *__ARR_BASE.add_si4(n) = 5;
//         }
//
//         return 0;
//     }
//
// __ARR_BASE denotes the address the automatic object layout model
// gives arr. The condition excludes the layout-interior stores that
// are unobservable.
```

### 2.2.8 Immortal object layout

#### Dynamic semantics

An access that reaches cells of more than one immortal object, and not only cells of one of them, can cause indeterminate state.

#### Implementation defined

The address at which the storage for an immortal object is reserved on the programme machine or the translation machine is implementation defined.

## 2.3 The ordering of τ

The **settlement order** of a cell is a total order upon the writes to that cell, the initial write first. A write **precedes** another at a cell when it is earlier in that cell’s settlement order, and **follows** it when it is later.

Each execution context, at each of its points and before performing the τ operation there, **observes** at each cell one write to that cell, its **observation** there at that point.

The execution records of each write a **rank**: zero for the initial write of a cell, a positive integer for every other.

### Dynamic semantics

A read observes the write its execution context observes at the cell it is of at its point, and yields the symbol that write placed there. A load observes at each cell it reaches the write its read there observes.

### 2.3.1 Observation and causation

#### Dynamic semantics

Of the writes to a cell that an execution context observes or performs, in the order of its points, or that a sequence of evaluations performs or its reads yield from, in its order, one observed or yielded from is **withdrawn** where it precedes one performed before it, or one observed, yielded from or performed after it precedes it.

An execution context **justifies** a write of rank *r* where it can perform, alone from its entry state, a sequence of evaluations that performs the context’s writes of rank not exceeding *r*, in which each read yields, from a write of rank less than *r* to the cell it is of, the symbol that write placed there, and in which no write a read yields from is withdrawn. Each evaluation of the sequence receives the signal the execution comprises of the context’s evaluation with as many evaluations before it, and otherwise none. A write the sequence performs is a write of the context where both place the same symbol at the same cell, each after as many such writes of its own.

A write is **caused** where no execution context performs it, or the one that performs it justifies it.

Every write is caused, and no observation is withdrawn.

An execution context observes its own write only from the point after it performs it.

A write is not outrun: where an execution context performs a write to a cell, each other execution context observes a write preceding it there at finitely many points.

### 2.3.2 Ordering properties

#### Dynamic semantics

Where a programme **relays** at a τ operation *o* from an operation *x*, every τ operation of the same kind performed before *x* is ordered before *o*. Where it **withholds** at *o* from *x*, every τ operation of the other kind performed before *x* is ordered before *o*.

A programme that relays at a read **relays loads**, and at a write **relays stores**; one that withholds at a read **withholds loads**, and at a write **withholds stores**. These four are the **ordering properties**.

An **ordering fence** is an operation that governs the order of the τ operations of the execution context that evaluates it, by where they are performed relative to it. A **translation ordering fence** governs the order in which the implementation arranges those operations, and an **execution ordering fence** the order in which the machine on which they are evaluated executes the instructions that perform them.

A programme relays or withholds at a τ operation from an execution ordering fence where that fence does so, and from the operation itself where the reference through which the access that performs it is performed does so. The **point** of an execution ordering fence is that of the first τ operation its execution context performs after it. The clause on references and resource management defines the forms of ordering fence and the references that relay or withhold.

Each write **conveys** at each cell one write to that cell, and at the cell it writes one that does not follow it.

Relaying constrains what is conveyed. Where a programme relays:

&mdash; Loads at a read *r* from *r* &mdash; what the write *r* observes conveys at a cell does not follow what *r*’s execution context observes there at the point after *r*.

&mdash; Loads at a read from an execution ordering fence *f* &mdash; what the write each read performed before *f* observes conveys at a cell does not follow what *f*’s execution context observes there at the point of *f*.

&mdash; Stores at a write *w* of an execution context *e* from an operation *x* &mdash; what *w* conveys at a cell does not precede what *e* observes there at the point of *x*, nor what any write *e* observes at or before that point conveys there.

### 2.3.3 Admissible executions

#### Dynamic semantics

A τ operation is **ordered before** another where at least one of the following holds:

&mdash; The first precedes the second.

&mdash; The first is the write the second, a read, observes.

&mdash; The first is a read, and the write it observes precedes the second.

&mdash; The rules upon relaying and withholding so require.

An execution of a programme is **admissible** where all of the following hold:

&mdash; The evaluations of each of its execution contexts are the first of those the programme determines.

&mdash; The rules upon observation and causation hold of it.

&mdash; Of the reads one atomic access performs at the cells another atomic access writes, either each observes a write preceding the write the latter performs there, or none does.

&mdash; Where a transactional access performs a write at a cell, the write its read there observes precedes that write, and no write follows the one and precedes the other.

&mdash; No τ operation is ordered before itself, directly or through further τ operations.

&mdash; There is an assignment, to each write at each cell, of the write it conveys there, under which the requirements upon relaying hold.

#### Design rationale (informative)

What a context observes at a cell is constrained by the rules above alone. An execution is therefore admissible in which each of two execution contexts observes at a cell a write the other performs at a later point of its own: an execution records what each context performed and observed, not one sequence they share. A programme obtains the observation of a write through the ordering properties.

#### Notes (informative)

By the rules upon observation and causation alone, of two writes of one execution context to one cell, the one performed at the earlier point precedes the other.

The following hold of every programme:

&mdash; For a programme that neither relays nor withholds anywhere, acyclicity and the conveying assignment constrain no execution further.

&mdash; Relaying or withholding at further τ operations admits no further execution.

&mdash; Where each write of a set is caused only if another write of the set has a lower rank, no ranks the execution can record satisfy the rule that every write is caused.

&mdash; The rule that every write is caused reads ranks only by comparing them: executions differing only in ranks that order the writes alike are alike admissible, and an execution’s finitely many writes have finitely many such orderings.

An execution is admissible whose settlement orders, ranks, observations and conveyed writes are read off one total order upon its τ operations and initial writes that places the initial writes first, the operations of each access consecutively and its reads before its writes, and the τ operations of each execution context in the order of its points. Each cell is settled as that order settles it, and each write ranked by its place in it, the initial writes at zero. An execution context observes at a cell the write there the order places last before the operation it performs at that point, or the last write there at a point where it performs none. Each write conveys at a cell the write to it the order places last before that write, or the initial write to it where the order places none there before it. A programme therefore has, for any number of evaluations chosen for each execution context, an admissible execution comprising that many of each context’s evaluations, or all of them where the context performs fewer.

Write ⟨*e*, *i*⟩ for the τ operation at point *i* of execution context *e*, ⊑<sub>*a*</sub> for precedence at cell *a* or equality, *Ω*<sub>*e*</sub><sup>*i*</sup>(*a*) for the observation of *e* at *a* at its point *i*, and *ρ*(*w*) for the rank of *w*. Write *V*(*w*, *b*) for the write *w* conveys at cell *b*, *Λ*<sub>*r*</sub>(*a*) for the writes to *a* of rank less than *r*, and *Θ*<sub>*e*</sub>(*r*) for the writes of *e* of rank not exceeding *r*. Write *Ψ*(*e*, *Λ*) for the sets *X* of writes such that *e* can perform a sequence of evaluations as the definition of justifying a write states, except that it performs every write of *X* and each read of a cell *a* yields from a write of *Λ*(*a*). The rule that every write is caused restates as *Θ*<sub>*e*</sub>(*ρ*(*w*)) ∈ *Ψ*(*e*, *Λ*<sub>*ρ*(*w*)</sub>) for every execution context *e* and every write *w* that *e* performs.

&mdash; relays stores at ⟨*e*, *i*⟩ from an operation whose point is *p*: for every *b*, *b*′ and *j* ≤ *p*, *Ω*<sub>*e*</sub><sup>*p*</sup>(*b*) ⊑<sub>*b*</sub> *V*(⟨*e*, *i*⟩, *b*) and *V*(*Ω*<sub>*e*</sub><sup>*j*</sup>(*b*′), *b*) ⊑<sub>*b*</sub> *V*(⟨*e*, *i*⟩, *b*)

## 2.4 Reachability and indeterminacy

Theorem. A Kurt machine with a partial transition function cannot exist.

Proof. Suppose, for contradiction, that a Kurt machine is permitted a partial transition function, so that some Kurt machine *K* = (*Q*, *Γ*, *Σ*, *δ*, *q*<sub>0</sub>) has dom(*δ*) = *D* ⊊ *C*, where *C* is the set of configurations, as defined in the clause on general matters. There exists a configuration *x* ∈ *C* \ *D*.

What *K* models is the computer, and by Axiom 1 the computer is a machine. A configuration is a state together with the signal the boundary holds, so *x* is a condition that machine can be in, and by Axiom 1 it is caused to act there.

The machine of Axiom 1 is a physical thing, and a physical thing does not pass into nothing: what it holds is conserved, and leaves it only across its boundary. The act therefore brings the machine to some condition. Which condition that is can be underspecified, but that there is one cannot. Apart from its boundary, the whole of the machine in that condition is a state of *Q*, and what the boundary then holds is a signal of *Σ* or the absence of one. That condition is therefore a member of *C*.

By the definition of the Kurt machine, *δ* is that act rather than an after-the-fact description of it. The configuration to which a machine at *c* passes is *δ*(*c*), so *δ* assigns *x* a member of *C*, contrary to *x* ∉ *D*.

∴ dom(*δ*) = *C*, and *δ* is total. Quod erat demonstrandum.

### Static semantics

A **trace** is a succession of programme points that an execution context can occupy, each immediately after the one before it.

An execution context **can occupy** a succession of programme points where it would occupy them in turn if all of the following held:

&mdash; It began at the first programme point of the innermost construct that encloses them among those the constraints of the subclause on control transfers and diverging expressions list.

&mdash; It evaluated no subroutine body that it invokes.

&mdash; It took each invocation that is not a diverging expression to return.

&mdash; It took each `xlat?` or `const?` conditional to select the branch it selects in an evaluation on the machine of that execution context.

&mdash; It continued after the evaluation of no diverging expression.

&mdash; It took each value that an expression yields to be any value of its type, except the values below.

The values excepted are the values of the following:

&mdash; A literal.

&mdash; A `cellbits` expression or a layout intrinsic applied to a closed type in an evaluation on the machine of that execution context.

&mdash; An identifier expression or a path expression in which no generic parameter occurs free and that names a `const` declaration or an associated constant whose expression is an analysis root.

&mdash; A `xlat` or `const` block.

Also excepted is the value of each of the following where the values of its constituent expressions, and of the default-value expressions of the fields it omits, are each excepted:

&mdash; A parenthesized expression.

&mdash; A negation, identity, or `!` expression.

&mdash; A bitwise, comparison, or logical expression.

&mdash; An arithmetic expression whose type satisfies `integer` or is a reference type.

&mdash; A composite, anonymous struct, array, or repeat construction.

A programme point is **reachable** where an execution context can occupy a succession of programme points that contains it. Every other programme point is **unreachable**. A programme point is **reachable from** a construct where it is reachable with the first programme point of that construct in place of that of the innermost construct named above. A construct is reachable, or reachable from a construct, where its first programme point is.

No operation at an unreachable programme point is a σ operation.

### 2.4.1 Indeterminate state

#### Dynamic semantics

An execution context is in an **indeterminate state** at a point where this specification, together with what the implementation determined in translating the programme, does not fix the transition its machine makes there.

#### Design rationale (informative)

Indeterminate state records the boundary of what the implementation determined. What lies beyond that boundary is determinate elsewhere. An environment documents facts of itself, and experiment upon an environment establishes further facts from the signals it supplies. Such a fact, joined to the rules this specification fixes, determines an outcome this specification alone does not. An execution context can reach an indeterminate state by acting upon one.

The rules that govern every other operation govern the operations around an indeterminate state unchanged. The implementation requirements upon σ operations leave a transformation no premise about such a state, and *δ* brings the machine to its successor by the theorem above.

#### Examples (informative)

```
fn indeterminate() -> uaddr {
    let x: uaddr = 10;
    airside {
        *(0x80_0000 as %mut uaddr) = 20;
    }

    return x;
}
```

Whether the environment accepts the store through `0x80_0000 as %mut uaddr` is outside the scope of this specification, and the store causes indeterminate state. A conforming implementation performs the store. Two translations that place `x` at different addresses can make `indeterminate` return different values: 10 where the store does not reach `x`, and 20 where it does.

```
const port: uaddr = 0xFE20_1000;

fn print(a: &[ui1]) {
    let .{ ptr, mut i } = .{ port as %volatile atomic mut ui4, 0 };

    while a.len > i {
        airside {
            while (*(ptr + 6) & (1 << 5)) != 0 {}
            *ptr = *(a.ptr + i) as ui4;
        }
    } and then { i += 1; }
}

extern fn main() -> ! {
    print("Hello, world!\n");
    loop {}
}
```

Whether the environment accepts the loads through `ptr + 6` and the stores through `ptr` is outside the scope of this specification, and each of them causes indeterminate state. The documentation of the environment fixes what each does: the bit at position 5 of the value a load yields is zero where the environment accepts a store, and each store it accepts causes the value of one cell of `Hello, world!\n` to cross the boundary between the machine and its environment.

```
// Search the addresses from first below last, at a stride of
// 0x1000, for one whose load yields 0x5AFE_C0DE.
airside fn probe(first: uaddr, last: uaddr) -> verdict[uaddr, void] {
    let mut base: uaddr = first;

    while base < last {
        let id = base as %volatile atomic ui4;
        if *id == 0x5AFE_C0DE { return verdict::Pass.{ base }; }
    } and then { base +|= 0x1000; }

    return verdict::Fail.{ void };
}
```

The load at `base` can yield any value, or can be an access the environment of the programme machine does not accept. Neither this specification nor the documentation of the environment fixes which. Where it yields `0x5AFE_C0DE`, the signal the load receives establishes that a load at the address `probe` returns in `verdict::Pass` yields that value. A later access to that address acts upon the fact.

```
struct chunk {
    ptr: %mut ui1,
    len: uaddr
} with destruct {
    release(self.ptr, self.len);
};

fn adopt(p: %chunk) -> chunk {
    return airside { express *p; };
}

fn hand_off(c: chunk) -> chunk {
    let taken = adopt(%c);
    airside { undrop(c); }
    return taken;
}

fn duplicate(c: chunk) -> chunk {
    return adopt(%c);
}
```

A load through an unmanaged reference yields a value to be copied, and the object `p` designates still holds its value.

`hand_off` leaves `c` uninitialized, and the destructor is invoked once upon the storage region. `duplicate` leaves `c` initialized, and both it and the value it returns hold a reference to that one region. Two destructors are invoked upon it, and the second passes to `release` the address of a region the first released. Neither this specification nor the documentation of the environment fixes what the second does, and it causes indeterminate state.

```
fn walk(depth: uaddr) -> uaddr {
    let scratch: [ui1; 4096] = [0; 4096];
    if depth == 0 { return scratch.len; }
    return walk(depth - 1) + scratch.len;
}
```

Each invocation reserves storage for its own `scratch`. Where the environment of the programme machine cannot supply that storage, execution exceeds a capacity limit of the environment, and this can cause indeterminate state: the storage so reserved can overlap that of another object, one that another execution context accesses included, and the stores that initialize `scratch` then reach it. Of the reservations and those stores, the indeterminate operations are those the implementation does not determine during translation, from the documentation of the environment or otherwise, to cause no indeterminate state.

## 2.5 σ operations

A **σ operation** is an operation that causes a value to cross the boundary between the machine and its environment, or that constrains the order in which such values cross.

### Static semantics

The σ operations are:

&mdash; Volatile access &mdash; any access performed through a reference carrying the `volatile` modifier.

&mdash; External subroutine invocation &mdash; any invocation of a subroutine whose definition the implementation does not determine to lie within the current translation unit.

&mdash; External subroutine return &mdash; any return of control to an invoker the implementation does not determine to lie within the current translation unit.

&mdash; External binding access &mdash; any access the implementation does not determine during translation to reach no cell of the object of a `static` binding declared in a `#dyn` namespace.

&mdash; Execution ordering fence &mdash; evaluation of an execution ordering fence.

&mdash; `instruct` block &mdash; any inline or global `instruct` block.

&mdash; **Indeterminate operation** &mdash; any operation the implementation does not determine during translation to cause no indeterminate state.

### Implementation requirements

A conforming implementation shall perform each σ operation exactly once, in the programme order of the execution context that performs it. It shall not widen a σ operation, nor coalesce one with any other operation, and it shall arrange no other operation within one. Where it performs a σ operation as more than one operation, the cells those operations reach shall be the cells that σ operation reaches, each reached by exactly one of those operations.

The implementation shall not move a τ operation across a σ operation.

The implementation shall not use what the environment does at a σ operation to eliminate or reorder an operation.

## 2.6 Uniformity rule

A conforming implementation may replace any sequence of operations with a different sequence, provided all of the following hold:

&mdash; Every σ operation is preserved and produces the same signal.

&mdash; The σ operations of each execution context stand in the programme order of that context.

&mdash; At each cell, the number of writes it performs does not exceed the number the replaced sequence performs there.

&mdash; Every execution it exhibits remains admissible under the subclause on the ordering of τ.

Where an indeterminate operation is present, executions that differ according to what the environment does at that operation are admissible.

### Design rationale (informative)

The uniformity rule is the sole source of an implementation’s freedom to transform a programme.

### Examples (informative)

```
extern fn dork(x: saddr) -> ui1 {
    if x == 0 { return 1; }
    else if x == 1 { return 0; }
    else if x == 2 { return 1; }
    else if x == 3 { return 0; }
    else if x == 4 { return 1; }
    else if x == 5 { return 0; }
    else if x == 6 { return 1; }
    else if x == 7 { return 0; }
    else if x == 8 { return 1; }
    else if x == 9 { return 0; }
    else { return 2; }
}

extern fn clever(x: saddr) -> ui1 {
    if 0 <= x and x < 10 {
        return (x & 1 == 0) as ui1;
    }

    return 2;
}
```

Both subroutines are `extern fn`. For every input, their σ operations are identical, stand in the same order, and produce the same signal, and a conforming implementation may translate either as the other.

## 2.7 The airside/landside boundary

### Static semantics

**Airside** is a lexically delimited region. An `airside` block, an `airside fn` body, and a global `instruct` block are airside.

**Landside** is the region outside every airside region.

An operation **requires airside** where this specification states that it does. Such an operation shall appear within an airside region. Every other requirement this specification imposes upon an operation holds within an airside region as it holds within a landside one.

## 2.8 Classification of errors

This specification classifies an error condition as a translation failure or as a trap.

### 2.8.1 Translation failure

#### Static semantics

A **translation failure** is source text the grammar of this specification does not permit, a violation of a requirement that this specification imposes on the programme, or any other condition this specification declares to be a translation failure. Exceeding a limit the implementation places upon the translation is a translation failure, and each such limit is implementation defined. A violation that this specification states can cause indeterminate state where not detected during translation is a translation failure only where so detected.

#### Implementation requirements

A conforming implementation shall reject any source unit whose translation incurs a translation failure and shall issue a **diagnostic**. No opaque code is produced.

An **advisory diagnostic** is a diagnostic issued for a construct this specification permits. It shall identify the construct, and a conforming implementation shall continue the translation after issuing one.

#### Implementation defined

What the diagnostic a translation failure requires reports, except where this specification requires otherwise, is implementation defined.

#### Examples (informative)

A type mismatch, a load of the source of a transfer made after the transfer without passing through a reference, a non-exhaustive `match`, and an unrecognized escape sequence are each a translation failure.

### 2.8.2 Trap

A **trap** is a determinate execution-time divergence. The mechanism by which `trap` operates is defined in the clause on statements and control flow.
