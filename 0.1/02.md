# §2. Semantics

This clause defines the semantic model of the Kurt machine: its operations, the structure and the ordering of τ, σ operations, the boundary between airside and landside, and the classification of errors.

## 2.1 The δ model

An **operation** is an abstract semantic action defined by this specification.

An **instruction** is a Γ sequence that δ interprets as an operation.

An **evaluation** performs one operation. An evaluation yields a value where the operation it performs yields one.

An **execution context** performs a sequence of evaluations. A programme has at least one execution context.

The **local state** of an execution context is what, with the programme, determines the operation the context performs next. It holds no part of τ. An execution context occupies one local state before each evaluation it performs, and the programme determines the one it occupies before the first, its **entry state**.

For an execution context and each local state of it, the programme determines either that the context performs no further operation, or one operation that it performs. Where it determines an operation, it determines the local state the context occupies thereafter from the operation, from what each read the operation performs yields, and from the signal the operation receives from the environment where it receives one. The evaluations of an execution context are those the programme so determines, beginning at its entry state.

An **execution** of a programme comprises, of each of its execution contexts, finitely many of the evaluations it performs, from the first. Of each such evaluation it comprises the value it yielded and the signal it received where there was one. It comprises also the following, as the subclause on the ordering of τ defines them:

— the settlement order of each cell.

— the write each execution context observes at each cell at each point.

— the rank of each write.

A **programme point** is a position in a programme at which an execution context that reaches it occupies a local state.

**Sequenced before** is a strict total order over the evaluations a single execution context performs.

The **programme order** of an execution context is the total order that sequenced before induces among its evaluations.

The **points** of an execution context are indexed by the non-negative integers. The τ operations an execution records of a context, as defined in the subclause on Γ and cells, are performed one at each successive point, beginning at the first. The local state an execution context occupies at a point is the one it occupies before the evaluation whose τ operation is performed there. Where one evaluation is earlier than another in the context’s programme order, each τ operation of the first is performed at an earlier point than each τ operation of the second.

An **operand expression** is an expression, other than the conditional initializer of a `while` expression, whose value is used by another expression. An expression that is not an operand expression is a **standalone expression**.

The evaluations of the operands of an operator are sequenced before the evaluation that performs the operation the operator denotes.

### 2.1.1 Operand evaluation order

#### Static semantics

The **leading operand** of a binary operator is the operand that comes before the operator in the token sequence. The **following operand** is the operand that comes after the operator in the token sequence.

#### Dynamic semantics

For all binary operators, every evaluation of the leading operand is sequenced before every evaluation of the following operand.

#### Design rationale (informative)

The operands of a binary operator are named by their position in the token sequence and not by a side. Which side of an operator an operand appears on depends on the direction in which the source text is displayed, and the language does not fix the direction.

#### Examples (informative)

```
// Fully sequenced evaluation
let mut i: si4 = 0;
let x = { i += 1; express i; } + { i += 1; express i; };
// Leading operand evaluates first: i becomes 1, express 1.
// Following operand evaluates next: i becomes 2, express 2.
// x = 1 + 2 = 3
```

## 2.2 The structure of τ

This subclause defines what τ comprises, the objects that occupy it, and the operations through which a programme reaches them.

### 2.2.1 Γ and cells

Γ is the set of symbols the storage of an environment holds, as defined in the clause on general matters. The number of symbols of Γ is defined by the environment.

A **cell** is the least unit of storage of an environment; it holds one symbol of Γ.

A **Γ sequence** is a finite sequence of zero or more symbols of Γ.

A **bit** of a non-negative integer *v* at a non-negative position *k* is the value <span class="floor">⌊&thinsp;*v* / 2<sup>*k*</sup>&thinsp;⌋</span> mod 2 together with the position. The **weight** of position *k* is 2<sup>*k*</sup>. Where a rule names a number of bits, it names the bits at the positions less than that number.

The **cell width** of an environment is the least number of bits for which every symbol of Γ is less than two raised to it.

A **write** places one symbol at one cell, and a **read** yields one symbol from one cell. A write and a read are operations. A write names a cell and the symbol it places, and a read names a cell. A **τ operation** is a write or a read. The writes and reads an access performs are defined in the subclause on objects, and the orders constrained among τ operations are defined in the subclause on the ordering of τ.

The **initial write** of a cell is the write that places there the symbol the programme’s initial storage pairs with the cell, as defined in the clause on general matters. No execution context performs it.

#### Implementation requirements

A conforming implementation exists only for an environment in which the number of symbols of Γ is a power of two greater than one.

A conforming implementation shall perform each τ operation at most once. It may introduce a τ operation at a cell into an execution context only where it establishes during translation that this context performs every τ operation at that cell.

#### Notes (informative)

The implementation may elide a τ operation, and may replace two τ operations upon one cell with one, wherever the uniformity rule permits.

### 2.2.2 The storage map, addresses, and alignment

The storage τ of the machine comprises the cells of its environment, and a storage map pairs each of them with the symbol it holds, as defined in the clause on general matters.

The cells of an environment are numbered from zero to *A* − 1, where *A* is the number of cells of the environment; the number of a cell is its **address**. The cell **next to** a cell is the one whose address is greater by one; the cell next to the cell addressed by *A* − 1 is the cell addressed by zero.

A **storage region** is an address *a* together with a number of cells *n* not greater than *A*. It comprises *n* cells in order. The first is the cell addressed by *a*, and each subsequent one is the cell next to the one before it. The **address of a storage region** is *a*, and the **offset** of a cell of the region is its position in that order, counting from zero.

An address is **aligned for** a non-negative integer where that integer is zero or divides the address.

#### Static semantics

`uaddr` is the type of an address; its values are the addresses. The size and value set of `uaddr` are defined in the clause on types. The forms a reference takes, and the information each carries beside an address, are defined in the clause on references and resource management.

#### Implementation requirements

An access the execution environment does not accept can cause indeterminate state, as defined in the subclause on indeterminate state. Which accesses it accepts is outside the scope of this specification. An access whose target lies outside the storage region of every object can cause indeterminate state. The implementation shall not use how a reference was obtained to determine whether the execution environment accepts an access through it, or to justify eliminating or reordering the access.

The implementation shall not assert that the storage of an object receives no store.

### 2.2.3 Types

#### Dynamic semantics

A **type** determines three properties: a **size**, an **alignment**, and an **interpretation**.

The size of a type, denoted `T'size`, is a non-negative integer not greater than *A*; the storage region of an object of the type has `T'size` cells. The alignment of a type, denoted `T'align`, is a non-negative integer; an address is aligned for a type where it is aligned for `T'align`. The interpretation of a type maps each Γ sequence of length `T'size` to exactly one **value**; the values of the type are those it so gives, and the Γ sequences it maps to a value **represent** the value. The concrete size, alignment, and interpretation of each type are defined in the clause on types.

### 2.2.4 Objects

An **object** is characterized by a type, a storage region, and an object lifetime.

An object’s type is fixed throughout its object lifetime.

The address of an object is the address of its storage region. An object’s address is stable from the reservation of its storage until its release. An object resides at an address aligned for its type, except where the layout rules of the clause on types place a constituent object at an address not so aligned.

An object that holds a value of a constituent of its type, as the clause on references and resource management defines constituents, is a **constituent object** of the object that holds the whole. A constituent object of a constituent object of an object is a constituent object of that object.

Distinct objects shall occupy disjoint cells while the storage of both is reserved, except where one is a constituent object of the other. Such a violation, where not detected during translation, can cause indeterminate state.

Storage is **reserved** for an object and later **released**. The subclause on object lifetime defines, for each category of object, when each occurs. The **object lifetime** of an object begins when a store first makes it initialized, or, for an object whose storage is reserved before execution begins, when execution begins; it ends when its storage is released.

At any point within its object lifetime, an object is either **uninitialized** or **initialized**. An object is initialized when its object lifetime begins. Its destruction, the transfer of the value it holds, or an `undestruct` upon it makes it uninitialized, and a further store makes it initialized again, as defined in the clause on references and resource management.

A **store** places a value in an object, and a **load** obtains the value an object holds. A store and a load are operations. A store names an object, a type, and the value it places, and a load names an object and a type. Every evaluation that yields an object’s current value performs a load.

An **access** is a load, a store, or a load and a store performed as one. Each access is performed through a type. Where an access is performed through a reference, the type is the referent type of the reference and the address is the one the reference carries. Otherwise the type is the type of the object accessed and the address is that of its storage region. The access **reaches** the cells from that address, as many as the size of that type. Those cells form a storage region whose address is the address of the access.

Two accesses **conflict** where they reach overlapping storage, at least one of them is a store, and the programme confers indivisibility upon at most one of them.

An **assignment** is an operation that stores a value into an object.

**Initialization** is an assignment that begins an object’s lifetime, or that transitions an object from uninitialized to initialized.

A **binding** is the association between an identifier and an object, introduced by a declaration. A binding persists for the object lifetime of its object. The declaration forms that introduce bindings are defined in the clause on declarations.

#### Dynamic semantics

A store performs a write at each cell of the storage region it reaches, placing at each the symbol at the corresponding position of a Γ sequence representing the value stored. Where more than one Γ sequence represents the value, the clause on types defines which of them is placed. A load performs a read at each cell of the storage region it reaches. Those reads yield a Γ sequence, ordered by cell. The value of the load is what the interpretation of its type gives that sequence. Which symbol a read yields is defined in the subclause on the ordering of τ.

#### Implementation requirements

A conforming implementation shall produce opaque code in which an object occupies its storage region from the reservation of its storage until its release, except where the implementation determines every access that reaches the storage region.

#### Examples (informative)

The following are cases in which an implementation does not determine every access that reaches an object’s storage region:

— The object crosses an external subroutine boundary.

— A reference to the object is stored in a `static` or `static mut` binding.

— A reference to the object is converted to `uaddr`.

— A reference to the object is used as the operand of `as!`.

— A reference to the object appears as an operand in an `asm` block.

### 2.2.5 Kurt standard alignment

#### Static semantics

**Kurt standard alignment** (KSA) is the layout of every type and of every storage region the implementation reserves, except where a rule states otherwise. Given identical parameters of the execution environment, the same sequence of types produces the same layout.

KSA assigns to a finite sequence of types `T_0, T_1, ..., T_n` an offset for each, an alignment, and a size. Write *o*<sub>*i*</sub> for the offset of `T_i` and *a* for the alignment:

*o*<sub>0</sub> = 0

*o*<sub>*i*</sub> = <span class="ceil">⌈&thinsp;(*o*<sub>*i*−1</sub> + `T_{i-1}'size`) / `T_i'align`&thinsp;⌉</span> × `T_i'align`

*a* = max(0, `T_i'align` over all *i*)

size = <span class="ceil">⌈&thinsp;max(0, *o*<sub>*i*</sub> + `T_i'size` over all *i*) / *a*&thinsp;⌉</span> × *a*

Where the divisor of one of these quotients is zero, the rounding leaves the dividend unchanged. Where the sequence is empty, the size and the alignment are both zero.

The additions and the roundings in these formulae are exact operations over the non-negative integers and do not wrap. Where every quantity they involve is determined at translation time, they are evaluated at translation time.

Cells that lie within the region so sized and within no `T_i` are **padding**.

### 2.2.6 Object lifetime

This subclause defines the categories of object lifetime, when the storage of an object of each is reserved and released, and the order in which objects are destroyed.

A **scope** is a region of a source unit over which a name introduced within it is visible. A name is visible throughout the innermost scope containing its introduction. A block is a scope.

**Declaration order** is the order in which bindings appear in the token sequence. Where a single declaration introduces more than one binding — as in a destructuring pattern — the declaration order of those bindings is the order of the binding identifiers within the pattern.

#### Dynamic semantics

A **binding object** is the object of a binding. A **temporary object** is produced during expression evaluation. Every object belongs to exactly one of two categories of object lifetime.

An object of the **automatic** object lifetime has its storage reserved and released within the enclosing scope.

For an automatic binding object of a subroutine parameter binding, storage is reserved at subroutine entry and the object is initialized by the argument store. For every other automatic binding object whose size is determined at translation time, storage is reserved at block entry. For one whose size is not so determined, the expressions its size depends upon are evaluated where the binding is declared, and storage is reserved there. Initialization occurs at each assignment to the binding that so transitions its object.

Storage for a temporary object is reserved where the object is produced and released when its object lifetime ends. The object lifetime of a temporary object produced in the initializer of a binding ends with that of the binding. The object lifetime of every other temporary object ends where control leaves the innermost standalone expression in which it is produced.

An object of the **permanent** object lifetime has its storage reserved before execution begins and never released. The object of a `static` or `static mut` binding has the permanent object lifetime, as does the object of a string literal and every object that occupies storage in the opaque code from a value evaluated at translation time.

One object lifetime is **longer than** another where the other ends and it does not, or where both end and it ends the later. The two are **equal** otherwise.

When a scope exits, the automatic objects belonging to the scope are destroyed in reverse declaration order; the temporary objects produced in the initializer of a binding are destroyed immediately after the binding, in reverse order of production. The variadic binding object, if present, is destroyed after all block-local binding objects and before the parameter binding objects, which are destroyed in reverse declaration order.

Where control leaves a standalone expression, the temporary objects whose object lifetime ends there are destroyed in reverse order of production.

Destroying an object executes its destructor, as the clause on references and resource management requires.

#### Examples (informative)

```
fn example(a: si4, b: si4) -> si4 {
    // Declaration order: a, b, x, y
    let x = a + 1;
    let y = b + 2;
    return x + y;
}   // Destruction order: y, x, b, a
```

### 2.2.7 Automatic object layout

#### Dynamic semantics

Upon entry to a block, a storage region is reserved for the block. That region is its **layout region**. Within it, before any initializer is evaluated, storage is reserved in declaration order for all automatic binding objects belonging to the block whose size is determined at translation time. Let *S* be a struct whose fields are those objects in that order. The layout region is aligned for *S*, and each binding object lies at the offset of its field in *S*. A binding object whose size is not determined at translation time is reserved where its binding is declared, at the least address aligned for its type that lies beyond every binding object already reserved in the block. The layout region extends to contain it, and is aligned for that object’s type where that alignment is greater than the alignment of *S*.

Upon exit from a block, the storage reserved for it is released.

Upon subroutine entry, a layout region is reserved for the subroutine’s parameter bindings and for its variadic binding if any, and the addresses of those binding objects are determined within it by the rule above, in declaration order.

For a refutable binding whose pattern does not match, the unmatched binding object’s storage is reserved as defined above and is released without destructor invocation when the `else` block causes the enclosing scope to exit.

#### Implementation requirements

A conforming implementation shall produce opaque code consistent with the layout model defined above. The implementation may use any physical storage mechanism provided all of the following hold:

— Occupancy — where an access the implementation cannot resolve to a specific object reaches storage within a block’s layout region, every object in the region whose storage the access can reach shall occupy its storage region at its layout-model address. The form of reference through which the access is performed, if any, does not bear upon this requirement.

— Transformation consistency — the σ operations are identical in order and signal to those of the layout model defined above.

#### Implementation defined

The physical storage mechanism used to implement automatic object layout is implementation defined.

#### Examples (informative)

```
// Example 1 — local binding layout in declaration order
fn pair_sum() -> si4 {
    let a: si4 = 3;
    let b: si4 = 4;
    let result = a + b;
    // Abstract layout (block entry):
    //   addr:  | a: si4  | b: si4  | result: si4 |
    //   cells: [ 0 ... 3 | 4 ... 7 | 8 ... 11    ]
    // result is the return operand but occupies its
    // declared position in the layout.
    return result;
}
// A conforming implementation may place result directly in
// the invoker’s storage (eliding the copy) if no arbitrary
// access in the block can observe the difference.

// Example 2 — arbitrary access reaches a return-value object
fn example2() -> si4 {
    let arr: [si4; 3] = [0, 0, 0];
    let i: si4 = 0;
    // Abstract layout:
    //   addr:  | arr (12 cells) | i (4 cells) |

    airside {
        let p = arr.ptr as %mut si4;
        *(p + 3) = 5;
        // The store through p + 3 targets storage beyond arr’s
        // bounds. In the abstract layout, p + 3 targets the
        // storage of i, so 5 is stored into i.
    }

    return i; // Kurt machine returns 5
}
// The conclusion follows entirely from the layout model, so a
// conforming implementation may constant-fold the subroutine to
// `return 5;`. Neither arr nor i need occupy storage where the
// return value is the only effect the programme has.

// Example 3 — dynamic index and range splitting
fn example3(n: uaddr) -> si4 {
    let .{ mut arr, i } = .{ [0~si4; 3], 0 };
    airside { *arr.xat_u(n) = 5; }
    return i;
}
// The layout fixes the relative positions of arr and i. Partition
// the execution-time cell offset n_cells = n * T'size, where T is
// the element type of arr:
//
//   Abstract layout (cells, relative to arr):
//     | arr: 12  | i: 4      |
//     [ 0 ... 11 | 12 ... 15 ]
//
//   n_cells ∈ {0 ... 8}:
//       within arr; unobservable store under the uniformity rule;
//       i remains 0
//
//   n_cells ∈ {9 ... 11}:
//       straddles arr and i; return value not predictable
//
//   n_cells == 12:
//       targets i exactly; return 5
//
//   n_cells ∈ {13 ... 15}:
//       overlaps i and storage beyond the layout; preserve the store,
//       have i occupy its storage, return value not predictable
//
//   otherwise:
//       targets storage outside the layout; preserve the access
//
// Here T = si4, so n_cells is a multiple of 4: the straddling
// ranges are unreachable and the partition collapses to
//
//   n ∈ {0, 1, 2}: unobservable store, return 0
//   n == 3:         store hits i, return 5
//   otherwise:      store outside the layout, return 0
//
// A possible optimized form:
//
//     fn example3_opt(n: uaddr) -> si4 {
//         if n == 3 { return 5; }
//         if n * si4'size > 3 * si4'size {
//             *__ARR_BASE.add_si4(n) = 5;
//         }
//
//         return 0;
//     }
//
// __ARR_BASE denotes the layout-model address of arr. The condition
// excludes the layout-interior stores that are unobservable.

// Example 4 — faithful access only, optimization permitted
fn make_buffer() -> [ui1; 4096] {
    let mut buf: [ui1; 4096] = [0; 4096];
    let mut i: uaddr = 0;

    while i < buf.len {
        airside {
            let p = (buf.ptr as uaddr + i * ui1'size) as %mut ui1;
            *p = (i & 0xFF) as ui1;
        }
    } then { i += 1; }

    return buf;
}
// Every access through an unmanaged reference targets an address within
// buf’s bounds, as established by the loop condition i < buf.len.
// The implementation may place buf directly in the invoker’s
// storage.
```

### 2.2.8 Permanent object layout

#### Dynamic semantics

Storage for a permanent object is reserved at an address aligned for its type. Which address is implementation defined. An access that reaches cells of more than one permanent object can cause indeterminate state.

## 2.3 The ordering of τ

This subclause defines what an execution context observes at each cell, the orders among τ operations that a programme can require, and the executions a conforming implementation can exhibit.

The **settlement order** of a cell is a total order upon the writes to that cell, of which the initial write is first. A write **precedes** another write at a cell when it is earlier in that cell’s settlement order, and **follows** it when it is later there.

Each execution context, at each of its points, **observes** at each cell one write to that cell. That write is the context’s **observation** at that cell at that point. A context observes at a point before performing the τ operation there.

The execution records of each write a **rank**: zero for the initial write of a cell, a positive integer for every other.

An execution context **justifies** a write of rank *r* where it can perform, alone from its entry state, a sequence of evaluations of which both of the following hold:

— the sequence performs the writes of the context of rank not exceeding *r*.

— each read in the sequence yields a symbol that a write of rank less than *r* placed at the cell the read is of.

### Dynamic semantics

A read observes the write its execution context observes at the cell it is of at the point of the read, and a load observes at each cell of the storage region it reaches the write the read it performs there observes. A read yields the symbol that the write it observes at the cell it is of placed there.

### 2.3.1 Observation and causation

#### Dynamic semantics

The rules upon observation and causation are:

— An execution context observes its own write only from the point after it performs it. Where an execution context performs a write to a cell, what it observes there at the point of the write precedes the write, and what it observes there at the next point does not precede it.

— An observation is not withdrawn. At each cell, the write an execution context observes at each successive point does not precede the write it observed at the previous point.

— Every write is caused. The execution context that performs a write justifies it.

— A write is not outrun. Where an execution context performs a write to a cell, each other execution context observes a write preceding it there at finitely many points.

### 2.3.2 Ordering properties

#### Dynamic semantics

Of two τ operations of one execution context performed at different points, the one at the later point **stands after** the one at the earlier point.

Where a programme **relays** at a τ operation, every τ operation of the same kind that it stands after is ordered before it.

Where a programme **withholds** at a τ operation, every τ operation of the other kind that it stands after is ordered before it.

A programme that relays at a read **relays loads**, and at a write **relays stores**; one that withholds at a read **withholds loads**, and at a write **withholds stores**. These four are the **ordering properties**.

An **ordering fence** is an operation that governs the order of the τ operations of the execution context that evaluates it, determined by where those operations are performed relative to it. A **translation ordering fence** governs the order in which the implementation arranges those operations. An **execution ordering fence** governs the order in which the environment executes the instructions that perform them.

A programme relays or withholds at a τ operation where an execution ordering fence does so, or where the reference through which the access that performs the operation is performed does so. The clause on references and resource management defines the forms of ordering fence and the references that relay or withhold.

Each write **conveys**, at each cell, one write to that cell. What it conveys is the observation it brings there to an execution context that observes it.

Relaying constrains what is conveyed:

— Where a programme relays loads at a read *r* observing a write *w*, what *w* conveys at a cell does not follow what *r*’s execution context observes there at the point after *r*.

— Where a programme relays stores at a write *w* performed by an execution context *e*, what *w* conveys at a cell does not precede the write *e* observes there at the point of *w*, nor what any write *e* observes at or before that point conveys there.

The clause on references and resource management confers **indivisibility** upon an access. Where an access carries it, then at each point of each execution context other than the one performing it, either no write the access performs follows what that context observes at the cell that write is to, or every one of them does. Where such an access performs both a read of a cell and a write to it, no write of another execution context both follows the write the read observes there and precedes the write the access performs there.

### 2.3.3 Admissible executions

#### Dynamic semantics

A τ operation is **ordered before** another where at least one of the following holds:

— the two are writes to one cell and the first precedes the second.

— the first is the write a read observes at the cell the read is of and the second is the read.

— the first is a read, the second is a write to the cell the read is of, and the write the read observes there precedes the second there.

— the rules upon relaying and withholding so require.

An execution of a programme is **admissible** where all of the following hold:

— the evaluations of each of its execution contexts are the first of those the programme determines.

— the rules under the subclause on observation and causation hold of it.

— every access the programme confers indivisibility upon meets the requirements upon indivisibility above.

— no τ operation is ordered before itself, directly or through further τ operations.

— there is an assignment, to each write at each cell, of the write it conveys there. Under that assignment the requirements above hold: the requirement upon relaying loads at every read where the programme relays loads, and the requirement upon relaying stores at every write where the programme relays stores.

#### Implementation requirements

A conforming implementation shall exhibit only admissible executions.

#### Design rationale (informative)

What a context observes at a cell is constrained by the rules above and by nothing else.

An execution is therefore admissible in which each of two execution contexts observes at a cell a write the other performs at a later point of its own. An execution records what each context performed and what each observed, and not one sequence they share. A programme obtains the observation of a write through the ordering properties above.

#### Notes (informative)

Of two writes of one execution context to one cell, the one performed at the earlier point precedes the other there, by the rules upon observation and causation alone.

The following hold whatever the programme:

— For a programme that neither relays nor withholds anywhere, exactly those executions are admissible whose evaluations are the first the programme determines and of which the rules under the subclause on observation and causation hold. Acyclicity and the conveying assignment constrain such a programme no further.

— Of two programmes that differ only in where they relay and withhold: where the first relays and withholds wherever the second does, every execution admissible of the first is admissible of the second.

— The orders constrained are those the rules above establish and those a programme asks for between two τ operations of a single execution context. No order between τ operations of different execution contexts arises that the rules above did not already establish.

— An execution is admissible whose settlement orders, ranks, observations and conveyed writes are read off one total order upon its τ operations and its initial writes that places the initial writes first, places consecutively the operations of each access the programme confers indivisibility upon, and contains the programme order of each of its execution contexts. Each cell is settled as that order settles it, and each write ranked by its place in it, the initial writes at zero. An execution context observes at a cell the write there the order places last before the operation it performs at that point, or the last write there at a point where it performs none. Each write conveys at a cell the write to it the order places last before that write. Every edge of ordered-before is then an edge of that order, so no τ operation is ordered before itself. A programme therefore has an admissible execution.

— Where each write of a set requires, to be caused, that another write of the set carry a strictly lower rank, no rank the execution can record satisfies the rule that every write is caused. The requirement descends and the ranks are non-negative integers. This holds of a set of any size, and of any shape of requirement among its writes.

— The rule that every write is caused reads a rank only through comparisons between ranks. Two executions differing only in ranks that order the writes alike are alike admissible. Since an execution records finitely many evaluations, and so finitely many writes, the ranks the rule distinguishes are the orderings of a finite set.

Write ⟨*e*, *i*⟩ for the τ operation at point *i* of execution context *e*, ⊑<sub>*a*</sub> for precedence at cell *a* or equality, and *Ω*<sub>*e*</sub><sup>*i*</sup>(*a*) for the write to *a* that *e* observes there at its point *i*.

Write *ρ*(*w*) for the rank the execution records of the write *w*, and *γ*(*w*) for the execution context that performs it.

Write *Λ*<sub>*r*</sub>(*a*) for the symbols a read of cell *a* may yield below rank *r*:

*Λ*<sub>*r*</sub>(*a*) = { *v* : a write to *a* of rank less than *r* placed *v* }

Write *Θ*<sub>*e*</sub>(*r*) for the writes of *e* whose rank does not exceed *r*. Write *Ψ*(*e*, *Λ*) for the sets *X* of writes such that, from the entry state of *e* and with no other execution context performing an operation, *e* can perform a sequence of evaluations that performs every write of *X* and in which each read of a cell *a* yields a symbol of *Λ*(*a*). The rule that every write is caused restates as *w* is performed ⟹ *Θ*<sub>*γ*(*w*)</sub>(*ρ*(*w*)) ∈ *Ψ*(*γ*(*w*), *Λ*<sub>*ρ*(*w*)</sub>).

The rank enters only through the comparisons *ρ*(*u*) &lt; *ρ*(*w*), which fixes *Λ*, and *ρ*(*u*) ≤ *ρ*(*w*), which fixes *Θ*. Where every write of a set has a write of that set at a strictly lower rank, no *ρ* satisfies the rule, the ranks being non-negative integers.

Writing *V*(*w*, *b*) for the write *w* conveys at cell *b*, the relaying is:

— relays stores at ⟨*e*, *i*⟩: for every *b*, *Ω*<sub>*e*</sub><sup>*i*</sup>(*b*) ⊑<sub>*b*</sub> *V*(⟨*e*, *i*⟩, *b*), and for every *b*, *b*′ and every *j* ≤ *i*, *V*(*Ω*<sub>*e*</sub><sup>*j*</sup>(*b*′), *b*) ⊑<sub>*b*</sub> *V*(⟨*e*, *i*⟩, *b*)

— relays loads at ⟨*e*, *i*⟩ reading *a*: for every *b*, *V*(*Ω*<sub>*e*</sub><sup>*i*</sup>(*a*), *b*) ⊑<sub>*b*</sub> *Ω*<sub>*e*</sub><sup>*i*+1</sup>(*b*)

## 2.4 Reachability and indeterminacy

Theorem. A Kurt machine with a partial transition function does not exist.

Proof. Suppose, for contradiction, that a Kurt machine *K* = (*Q*, *Γ*, *Σ*, *δ*, *q*<sub>0</sub>) exists whose transition function is partial: dom(*δ*) = *D* ⊊ *C*, where *C* is the set of configurations, as defined in the clause on general matters. There exists a configuration *x* ∈ *C* \ *D*.

Axiom 1 states the computer to be a machine. Two consequences of being one are used below.

— Substance. A machine is a thing and not a description of one. At every instant it has a whole, and that whole apart from its boundary is a state.

— Universality. Being caused to act by every condition is not a property a thing holds in part. A thing caused to act by some conditions and not by others is not a machine.

What *K* models is the computer, and by Axiom 1 the computer is a machine. A configuration is a state together with the signal the boundary holds, so *x* is a condition that machine can be in, and by Axiom 1 it is caused to act there.

By substance, the machine has a whole at the condition to which the act brings it; that whole apart from its boundary is a state of *Q*, and what the boundary then holds is a signal of *Σ* or the absence of one. That condition is therefore a member of *C*.

By the definition of the Kurt machine, *δ* is that succession rather than an after-the-fact description of it. The configuration to which a machine at *c* passes is *δ*(*c*). Since *x* ∉ *D*, *δ* assigns *x* no member of *C*, and the machine *K* describes passes from *x* to nothing — it is caused to act by the conditions of *D* and by no others.

By universality, *K* describes no machine, contrary to the supposition that *K* is a Kurt machine.

∴ dom(*δ*) = *C*, and *δ* is total. Quod erat demonstrandum.

### Static semantics

A programme point is **unreachable** where either of the following holds:

— on every path leading to it, a condition that is a translation-time constant excludes that path.

— it is the programme point that follows a control transfer or a diverging expression in programme order.

Translation-time constants are defined in the clause on expressions; control transfers and diverging expressions are defined in the clause on statements and control flow.

Every other programme point is **reachable**. Reachability is determined by translation-time evaluation alone. No σ operation is ascribed to an unreachable programme point, and the implementation may place there whatever operations its transformations permit, subject to the placement of an implicit `trap` that the clause on statements and control flow requires.

### Implementation requirements

The reachability of a programme point is independent of any value or state along paths to it that the implementation has not determined. A conforming implementation shall not assert otherwise in justifying a transformation.

### 2.4.1 Indeterminate state

#### Dynamic semantics

An execution context is in an **indeterminate state** at a point where this specification, together with what the implementation determined in translating the programme, does not fix the transition the Kurt machine makes there.

#### Design rationale (informative)

Indeterminate state records the boundary of what the implementation determined. What lies beyond that boundary is determinate elsewhere. An environment documents facts of itself, and experiment upon an environment establishes further facts from the signals it supplies. Such a fact, joined to the rules this specification fixes, determines an outcome this specification alone does not. An execution context can reach an indeterminate state by acting upon one.

The rules that govern every other operation govern the operations around an indeterminate state unchanged. The implementation requirements upon reachability and upon σ operations leave a transformation nothing to assert of such a state, and *δ* brings the machine to its successor by the theorem above.

#### Examples (informative)

```
fn indeterminate() -> uaddr {
    let x: uaddr = 10;
    airside {
        *(0x80_0000 as %mut uaddr) = 20;
    }

    return x;
}
```

The implementation does not determine whether the target of the store through `0x80_0000 as %mut uaddr` lies within the storage region of any object, and the store causes indeterminate state. A conforming implementation performs the store. Two translations that place `x` at different addresses can make `indeterminate` return different values: 10 where the store does not reach `x`, and 20 where it does.

```
const port: uaddr = 0xFE20_1000;

fn print(a: &[ui1]) {
    let .{ ptr, mut i } = .{ port as %volatile mut ui4, 0 };

    while a.len > i {
        airside {
            while (*(ptr + 6) & (1 << 5)) != 0 {}
            *ptr = *(a.ptr + i) as ui4;
        }
    } then { i += 1; }
}

extern fn main() -> ! {
    print("Hello, world!\n");
    loop {}
}
```

The loads through `ptr + 6` and the stores through `ptr` target storage outside the storage region of every object, and each of them causes indeterminate state. The documentation of the environment fixes what each does: the bit at position 5 of the value a load yields is zero where the environment accepts a store, and each store it accepts causes the value of one cell of `Hello, world!\n` to cross the boundary between the machine and its environment.

```
// Search the addresses from first below last, at a stride of
// 0x1000, for one whose load yields 0x5AFE_C0DE.
airside fn probe(first: uaddr, last: uaddr) -> verdict.[uaddr, void] {
    let mut base: uaddr = first;

    while base < last {
        let id = base as %volatile ui4;
        if *id == 0x5AFE_C0DE { return verdict::Pass(base); }
    } then { base +|= 0x1000; }

    return verdict::Fail(void);
}
```

The load at `base` can yield any value, or can be an access the execution environment does not accept. Neither this specification nor the documentation of the environment fixes which. Where it yields `0x5AFE_C0DE`, the signal the load receives establishes that a load at the address `probe` returns in `verdict::Pass` yields that value. A later access to that address acts upon the fact.

```
struct block {
    ptr: %mut ui1,
    len: uaddr
} with destruct {
    release(self.ptr, self.len);
};

fn adopt(p: %block) -> block {
    return airside { express *p; };
}

fn hand_off(b: block) -> block {
    let taken = adopt(%b);
    airside { undestruct(b); }
    return taken;
}

fn duplicate(b: block) -> block {
    return adopt(%b);
}
```

`adopt` transfers the value of the object `p` designates. A transfer invalidates the source binding, and `*p` names no binding. The object `p` designates holds the value still, and the destruction obligation upon it, as does the value `adopt` returns.

`hand_off` takes a value out of storage the programme manages itself and discharges the obligation the source holds. The destructor of the block executes once. `duplicate` leaves both `b` and the value it returns holding the obligation upon one storage region. Two destructors execute upon it, and the second passes to `release` the address of a region the first released. Neither this specification nor the documentation of the environment fixes what the second does, and it causes indeterminate state.

```
fn walk(depth: uaddr) -> uaddr {
    let scratch: [ui1; 4096] = [0; 4096];
    if depth == 0 { return scratch.len; }
    return walk(depth - 1) + scratch.len;
}
```

Each invocation reserves storage for its own `scratch`. Where the execution environment cannot supply that storage, execution exceeds a capacity limit of the environment and causes indeterminate state. The storage so reserved can overlap that of another object, one that another execution context accesses included, and the stores that initialize `scratch` then reach it.

## 2.5 σ operations

A **σ operation** is an operation that causes a value to cross the boundary between the machine and its environment, or that constrains the order in which such values cross.

### Static semantics

The σ operations are:

— Volatile access — any access performed through a reference carrying the `volatile` modifier.

— External subroutine invocation — any invocation of a subroutine whose definition is not available within the current translation unit.

— Execution ordering fence — evaluation of an execution ordering fence.

— `asm` block — any inline or global `asm` block.

An **indeterminate operation** is an operation the implementation does not prove during translation to cause no indeterminate state. Every indeterminate operation is a σ operation.

### Implementation requirements

A conforming implementation shall perform each σ operation exactly once, in the programme order of the execution context that performs it. It shall not split or widen a σ operation, nor coalesce one with any other operation.

The implementation shall not move a τ operation across a σ operation.

The implementation shall not assert what a σ operation reaches, or the result of performing it.

## 2.6 Uniformity rule

A conforming implementation may replace any sequence of operations with a different sequence, provided all of the following hold:

— every σ operation is preserved and produces the same signal.

— the σ operations of each execution context stand in the programme order of that context.

— at each cell, the number of writes it performs does not exceed the number the replaced sequence performs there.

— every execution it exhibits remains admissible under the subclause on the ordering of τ.

Every other operation constrains a conforming implementation only so far as it bears upon a τ operation or a σ operation.

Where an indeterminate operation is present, executions that differ according to what the environment does at that operation are admissible.

### Design rationale (informative)

The uniformity rule is the sole source of an implementation’s freedom to transform a programme. Within what it grants, the implementation is free.

### Examples (informative)

```
extern fn dork(x: saddr) -> ui1 {
    if x == 0 { return 1; }
    else if x == 1 { return 0; }
    else if x == 2 { return 1; }
    else if x == 3 { return 0; }
    else if x == 4 { return 1; }
    else if x == 5 { return 0; }
    else if x == 6 { return 1; }
    else if x == 7 { return 0; }
    else if x == 8 { return 1; }
    else if x == 9 { return 0; }
    else { return 2; }
}

extern fn clever(x: saddr) -> ui1 {
    if 0 <= x and x < 10 {
        return (x & 1 == 0) as ui1;
    }

    return 2;
}
```

Both subroutines are `extern fn`. The parameter `x` is a value received from Σ; the return value is a value emitted to Σ. For every input, both subroutines produce the same return value. The σ operations are identical in the same order, each producing the same signal. The two differ in nothing this specification constrains, and a conforming implementation may translate either as the other.

## 2.7 The airside/landside boundary

### Static semantics

**Airside** is a lexically delimited region. An `airside` block and an `airside fn` body are airside.

**Landside** is the region outside every `airside` block and every `airside fn` body.

An operation **requires airside** where the subclause that defines the operation states that it does. Such an operation shall appear within an airside region. Every other requirement this specification imposes upon an operation holds within an airside region as it holds within a landside one.

## 2.8 Classification of errors

This specification classifies an error condition as a translation failure or as a trap.

### 2.8.1 Translation failure

#### Static semantics

A **translation failure** is a violation, detected during translation, of a requirement that this specification imposes on the programme, or a condition that this specification declares to be a translation failure. A conforming implementation shall reject any source unit that contains a translation failure and shall issue a diagnostic that identifies the violated requirement or the declared condition. The programme is not translated and no opaque code is produced.

An **advisory diagnostic** is a diagnostic issued for a construct this specification permits. It shall identify the construct, and a conforming implementation shall continue the translation after issuing one.

#### Examples (informative)

A type mismatch, a use of an invalidated binding after transfer, a non-exhaustive `match`, and an unrecognized escape sequence are each a translation failure.

### 2.8.2 Trap

A **trap** is a determinate execution-time divergence. The mechanism by which `trap` operates is defined in the clause on statements and control flow.
