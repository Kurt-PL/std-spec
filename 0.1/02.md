# 2. Semantics

This clause defines the semantic model of the Kurt machine: the δ model, the structure and the ordering of τ, reachability and indeterminacy, σ operations, the uniformity rule, the airside/landside boundary, and the classification of errors.

## 2.1 The δ model

An **operation** is an action defined by this specification.

An **instruction** is a Γ sequence that *δ* interprets as an operation.

An **evaluation** performs one operation. An evaluation yields a value where the operation it performs yields one.

An **execution context** performs a sequence of evaluations. A programme has at least one execution context, and finitely many. Every evaluation is performed by an execution context of the machine on which it takes place.

The **local state** of an execution context is what, with the programme, determines the operation the context performs next. It holds no part of *τ*. An execution context occupies one local state before each evaluation it performs, and the programme determines the one it occupies before the first, its **entry state**.

For an execution context and each local state of it, the programme determines either that the context performs no further operation, or one operation that it performs. Where the programme determines an operation, it determines the local state the context occupies thereafter from the operation, from what each read the operation performs yields, and from the signal the operation receives from the environment where it receives one. The evaluations of an execution context are those the programme so determines, beginning at its entry state.

An operation is **atomic** where *δ* completes it upon the objects it names alone, bringing each directly from its prior value to its resulting value. Operations are **transactional** where *δ* completes them as one.

An **execution** of a programme comprises, of each of its execution contexts, finitely many of the evaluations it performs, from the first. Of each such evaluation it comprises the value it yielded and the signal it received where there was one. It comprises also the following, as §2.3 defines them:

&mdash; The settlement order of each cell.

&mdash; The write each read observes at each cell it reads.

&mdash; The order of happening.

&mdash; The reads each evaluation that happens counts on.

A **programme point** is a position in a programme at which an execution context that reaches it occupies a local state.

The **programme order** of an execution context is the order of the sequence of evaluations it performs.

The **τ points** of an execution context are the non-negative integers. (the τ points of an execution context are 0, 1, 2, …) The τ operations (§2.2.1) an execution records of a context *e* are those its evaluations perform, one at each successive τ point *i*, written ⟨*e*, *i*⟩, beginning at the first. (the τ operations recorded of *e* are ⟨*e*, 0⟩, ⟨*e*, 1⟩, …, each performed by an evaluation of *e*, ⟨*e*, *i*⟩ the one performed at τ point *i*) The local state an execution context occupies at a τ point is the one it occupies before the evaluation whose τ operation is performed there. (the local state *z*<sub>*e*</sub><sup>*i*</sup> of *e* at *i* is the one *e* occupies before the evaluation that performs ⟨*e*, *i*⟩) Where one evaluation is earlier than another in the context’s programme order, each τ operation of the first is performed at an earlier τ point than each τ operation of the second. (*x* earlier than *y* in the programme order of *e*, ⟨*e*, *i*⟩ a τ operation of *x* and ⟨*e*, *j*⟩ one of *y* ⇒ *i* &lt; *j*)

The evaluations of the operands of an operator are earlier in programme order than the evaluation that performs the operation the operator denotes.

### Implementation defined

The **atomicity set** of a machine holds each pair of a size and an alignment where an access of that size, at an address aligned for that alignment, can be atomic. The set can be empty.

The **transactionality set** of a machine holds each pair of a size and an alignment where a load and a store upon an object of that size, at an address aligned for that alignment, can be transactional. The set can be empty, and is a subset of the atomicity set.

Both sets are implementation defined for each supported environment of the programme machine and of the translation machine.

### 2.1.1 Operand evaluation order

#### Static semantics

The **leading operand** of a binary operator is the operand before it in the token sequence, and the **following operand** the operand after it.

#### Dynamic semantics

In each evaluation of a binary operator, the evaluation of the leading operand is earlier in programme order than that of the following operand.

#### Design rationale (informative)

The operands of a binary operator are named by their position in the token sequence and not by a side. Which side of an operator an operand appears on depends on the direction in which the source text is displayed, and the language does not fix the direction.

#### Examples (informative)

```
// Evaluation in programme order
let mut i: si4 = 0;
let x = { i += 1; express i; } + { i += 1; express i; };
// Leading operand is evaluated first: i becomes 1, express 1.
// Following operand is evaluated next: i becomes 2, express 2.
// x = 1 + 2 = 3
```

## 2.2 The structure of τ

### 2.2.1 Γ and cells

The number of symbols of *Γ* is defined by the environment of the machine.

A **cell** is the least unit of storage of a machine; it holds one symbol *γ* of *Γ*. (each cell holds one *γ* ∈ *Γ*)

A **Γ sequence** is a finite sequence of symbols of *Γ*. (a Γ sequence is a finite sequence (*γ*<sub>0</sub>, …, *γ*<sub>*n*&minus;1</sub>) with each *γ*<sub>*k*</sub> ∈ *Γ*)

A **bit** of a non-negative integer *v* at a non-negative position *k* is the value <span class="floor">⌊&thinsp;*v* / 2<sup>*k*</sup>&thinsp;⌋</span> mod 2 together with the position. The **weight** of position *k* is 2<sup>*k*</sup>. Where a rule names a number of bits, it names the bits at the positions less than that number.

The **cell width** of a machine is the least number of bits for which every symbol of *Γ* is less than two raised to it. (the cell width is the least *k* ≥ 0 with *γ* &lt; 2<sup>*k*</sup> for every *γ* ∈ *Γ*)

A **read** is an operation that names a storage region and yields a symbol from each of its cells, and a **write** is an operation that names a storage region and places a symbol at each of its cells. (a read names a storage region and yields one *γ* ∈ *Γ* from each of its cells *a*, and a write names a storage region and places one *γ* ∈ *Γ* at each of its cells *a*) A **τ operation** is a read or a write. (the τ operations are the reads and the writes)

The **initial write** *ι*<sub>*a*</sub> of a cell *a* is the write that places its initial symbol for the ordering of τ. (*ι*<sub>*a*</sub> is the write to *a* that places the initial symbol of *a*) No execution context performs it. (no execution context performs *ι*<sub>*a*</sub>) In execution after translation, that symbol is the one the initial storage of the machine pairs with the cell. (the symbol *ι*<sub>*a*</sub> places is the one the storage map of *q*<sub>0</sub> pairs with *a*) In a translation-time evaluation (§6.11), it is the one the cell holds when the evaluation begins. (the symbol *ι*<sub>*a*</sub> places is the one *a* holds when the evaluation begins)

#### Implementation requirements

A conforming implementation exists only for an environment in which the number of symbols of *Γ* is a power of two greater than one.

The implementation shall perform each τ operation at most once. (each τ operation is performed at most once) After the execution of a machine begins, the implementation shall perform at its cells no write other than one an evaluation performs. (each write the implementation performs at a cell after the execution begins is one an evaluation performs)

### 2.2.2 Addresses and alignment

The cells of *τ* are numbered from zero to *C* &minus; 1, where *C* is the number of cells of *τ*; the number of a cell is its **address**. The cell **next to** a cell is the one whose address is greater by one; the cell next to the cell addressed by *C* &minus; 1 is the cell addressed by zero.

A **storage region** is an address *β* together with a number of cells *n* not greater than *C*. It comprises *n* cells in order. The first is the cell addressed by *β*, and each subsequent one is the cell next to the one before it. The **address of a storage region** is *β*, and the **offset** of a cell of the region is its position in that order, counting from zero.

An address is **aligned for** a non-negative integer where that integer is zero or divides the address.

#### Static semantics

`uaddr` (§5.2, §5.3) is the type of an address. The forms a reference takes, and the information each carries beside an address, are defined in §8.2.

#### Dynamic semantics

An access the environment of its machine does not accept can cause indeterminate state (§2.4.1). Which accesses it accepts is outside the scope of this specification.

#### Implementation requirements

The implementation shall not use how a reference was obtained to determine whether the environment of its machine accepts an access through it, or to eliminate the access or reorder it in a different sequence (§2.6).

### 2.2.3 Types

#### Dynamic semantics

A **type** determines three properties: a **size**, an **alignment**, and an **interpretation**.

The size of a type (§5), denoted `T'size`, is a non-negative integer. The alignment of a type, denoted `T'align`, is a non-negative integer; an address is aligned for a type where it is aligned for `T'align`. The interpretation of a type maps each Γ sequence of length `T'size` to a **value**, and the Γ sequences it maps to a value **represent** the value. The values to which it maps a Γ sequence are the values of the type, and form the **value set** of the type.

### 2.2.4 Objects

An **object** is an address together with a type, for the period during which it exists. A reserved object (§2.2.6) exists from the reservation of its storage until its release, and objects of distinct reservations are distinct, as are objects that a type places as or within distinct fields or elements.

The **layout** of a type is its size, its alignment, and the offset at which it places each discriminant, field, and element.

The storage region of an object is the one at its address of as many cells as the size of its type.

An object is a **constituent object** of another where the type of the other places it, directly or within another it so places. Where an object is a constituent object of a reserved object that is not itself a constituent object of a reserved object, that reserved object is its **outermost object**. Any other object is its own outermost object.

Storage is **reserved** for an object and later **released** (§2.2.6). The **object lifetime** of an object begins when its storage is reserved and ends when its storage is released.

At any point within its object lifetime, a reserved object is either **uninitialized** or **initialized**. Any other object is initialized. A mortal object is uninitialized when its storage is reserved or released. An immortal object (§2.2.6) is initialized when its storage is reserved. To **invalidate** an object is to make it, and each constituent object of it, uninitialized. A store into it, or into an object of which it is a constituent object, made through no reference, makes it initialized.

A **load** is an operation that names an object and a type and yields the value the object holds, and a **store** is an operation that names an object, a type, and a value and places the value in the object. An object’s current value is yielded only by the evaluations of a load.

An **access** is a load or a store. An **atomic access** is an access that a rule states to be atomic. A **joint access** is a load and a store of one object that one rule defines together; that rule states where the store is performed and whether the two are transactional. Each access is performed through a type. Where an access is performed through a reference, the type is the referent type of the reference and the address is the one the reference carries. Otherwise the address is that of the storage region of the object accessed, and the type is the one that the rule defining the access names, or, where no rule names one, the type of the object accessed.

A discriminant, a field, or an element that a type places, directly or within another it so places, is an **inner object** of an object accessed through that type. Where the object an access through a reference names is an inner object of the referent, the type is instead the type of that object. The address of such an access is instead the one the reference carries advanced by the offset at which the referent type so places that object.

An access **spans** the cells from its address, as many as the size of its type. (an access of address *β* through a type `T` spans the cell addressed by *β* and each next one, `T'size` cells in all) Those cells form a storage region whose address is the address of the access. (those cells form the storage region of address *β* and of `T'size` cells)

A **binding** is the association between a name and an object. A binding persists for the object lifetime of its object. The constructs that introduce bindings are defined in §4.2, §4.3, §4.5, §4.11.3, §7.3, §7.3.1, §7.4, §7.5.1, and §8.8.

#### Dynamic semantics

A load reads each cell of the storage region it spans, by one read where the load is an atomic access and by one read at each cell otherwise. Those reads yield a Γ sequence, ordered by cell. The value of the load is the value to which the interpretation of its type maps that sequence. Which symbol a read yields is defined in §2.3.

Except where a rule states otherwise, a store places at each cell of the storage region it spans the symbol at the corresponding position of a Γ sequence representing the value stored, by one write where the store is an atomic access and by one write at each cell otherwise. Where more than one Γ sequence represents the value, §5.2 defines which of them is placed. §6.2.7 states where a store performs no write.

An access performs its τ operations at successive τ points of its execution context, its reads at earlier τ points than its writes. (the τ operations of an access of *e* are performed at the τ points *i* + *m* of *e* with 0 ≤ *m* &lt; *n*, for some *i* and *n*, each read at a lesser τ point than each write)

A store, other than a store through an unmanaged reference, proceeds in two steps:

1. The value the object the store names holds is destroyed, if that object is initialized.
2. The writes of the new value take place at that object.

#### Implementation requirements

Storage the implementation reserves for an object other than a constituent object shall lie at an address aligned for its type.

The implementation shall reserve storage such that distinct reserved objects, neither of which is a constituent object, occupy disjoint cells while the storage of both is reserved, except where the environment of its machine cannot supply that storage. Where it cannot, execution exceeds a capacity limit of the environment. Exceeding it can cause indeterminate state.

The implementation shall produce opaque code (§10.10) in which an object occupies its storage region from the reservation of its storage until its release, except where the implementation can resolve to that object every access that spans a cell of the storage region.

#### Examples (informative)

The following are cases in which an implementation cannot resolve to an object every access that spans a cell of its storage region:

&mdash; An external subroutine is invoked while the object exists.

&mdash; A reference to the object is stored in a permanent object.

&mdash; A reference to the object is converted to `uaddr`.

&mdash; A reference to the object is used as the operand of a reinterpretation.

&mdash; A reference to the object appears as an operand in an `instruct` block.

### 2.2.5 Kurt standard alignment

#### Static semantics

**Kurt standard alignment** assigns to a finite sequence of types `T_0, T_1, ..., T_{n-1}` a size, an alignment, and an offset for each. Write *ξ*<sub>*i*</sub> for the offset of `T_i` and *α* for the alignment:

*ξ*<sub>*i*</sub> = 0 where *i* = 0, and <span class="ceil">⌈&thinsp;(*ξ*<sub>*i*&minus;1</sub> + `T_{i-1}'size`) / `T_i'align`&thinsp;⌉</span> × `T_i'align` where *i* &gt; 0, for each *i* &lt; *n*

*α* = max(0, `T_i'align` over all *i*)

size = <span class="ceil">⌈&thinsp;max(0, *ξ*<sub>*i*</sub> + `T_i'size` over all *i*) / *α*&thinsp;⌉</span> × *α*

Where the divisor of one of these quotients is zero, the rounding leaves the dividend unchanged.

The additions and the roundings in these formulae are computed over the non-negative integers.

A **padding cell** is a cell of the representation of a value of a composite type that lies outside the representation of every value that value holds or carries.

### 2.2.6 Object lifetime

The **declaration order** of the following entities is the order in which they appear in the token sequence:

&mdash; The bindings of a scope.

&mdash; The fields of a type.

&mdash; The variants of a variant type (§4.6).

&mdash; The parameters, subject bounds (§9.4.2), and bound elements of a list.

&mdash; The items that an `impl` block or a protocol body declares.

A field without an identifier appears at its type. An object has the declaration order of its binding. The bindings that one declaration introduces are in the order of the binding identifiers within the pattern.

#### Dynamic semantics

A **reserved object** is an object for which a rule of this specification reserves storage, or a constituent object of such an object. Every reserved object other than a constituent object is exactly one of four kinds: an automatic object, a temporary object, a permanent object, or a resident object. An automatic object or a temporary object is a **mortal object**, and a permanent object or a resident object is an **immortal object**. An automatic object or a permanent object is a **declared object**. A constituent object is a mortal object or an immortal object as the object of which it is a constituent object is, and its storage is reserved and released with the storage of that object.

An **automatic object** is the object, other than a permanent object, of a binding or of a fixed parameter (§4.2) of a subroutine.

The object of a fixed parameter or of a variadic binding is initialized by the invocation. Where the invoked subroutine has no subroutine body, storage for that object is reserved upon entry to that subroutine, at the place that the invocation interface of that subroutine gives, and is released where control returns to the invoker. Such a subroutine loads that object after the invocation initializes it. Every automatic object other than the object of a fixed parameter or of a variadic binding **belongs** to the scope into which its binding is introduced.

A **temporary object** is an object, other than a declared object, a resident object, or a constituent object, that an evaluation produces. The value of a value expression is held by a temporary object that its evaluation produces, and the type of that object is the type of that expression. An evaluation that produces a temporary object stores a value into it. Storage for a temporary object is reserved where the object is produced and released when its object lifetime ends.

Where the implementation reserves storage in carrying out an evaluation, other than for an object this specification names, that evaluation produces a temporary object at that storage, of a type the implementation defines whose destructor is its default destructor. Each read or write the implementation performs at that object is a τ operation of the innermost evaluation the implementation is carrying out when it performs it. A write to such an object other than one the implementation performs at it can cause indeterminate state. (*o* a write to such an object *u*, and *o* not a write the implementation performs at *u* ⇒ *o* can cause indeterminate state)

A **master** is any of the following:

&mdash; An evaluation of a scope, of a statement, of a declaration, of an analysis root, of a filter clause (§7.4), or of an expression whose value selects a branch, an alternative, or a loop body.

&mdash; A lap (§7.5.1) of an evaluation of a `while` expression.

&mdash; The body evaluation of a subroutine invocation together with its value return.

The **master of** a temporary object that holds the value of an expression is the innermost master that comprises the following evaluations:

&mdash; The evaluation of that expression.

&mdash; Each evaluation that, through no reference, loads the temporary object or a constituent object of it, creates a reference designating either, or matches its value against a pattern.

&mdash; Each evaluation that does the same to the temporary object holding the value of an expression enclosing that expression, where that value is or holds a chained reference whose possible referents (§8.1.1) include the first temporary object or a constituent object of it.

The object lifetime of a temporary object that holds the value of an expression ends where control leaves its master. Where an evaluation within its master initializes an automatic object, other than by an assignment expression, with a value that is or holds a chained reference whose possible referents include that temporary object or a constituent object of it, and the last destroyed of the automatic objects so initialized is destroyed after control leaves the master, the object lifetime ends instead immediately after that destruction.

The object lifetime of any other temporary object ends where control leaves the innermost of the following that comprises the evaluation producing it:

&mdash; An evaluation of a scope, of a filter clause, or of an analysis root.

&mdash; A lap of an evaluation of a `while` expression.

&mdash; The body evaluation of a subroutine invocation together with its value return.

A **permanent object** is the object that a `static` declaration introduces. Its storage is reserved before the execution of its machine begins, or, where its declaration has an initializer, where the evaluation of its initializer block (§6.11) performed for its machine completes. Its storage is never released.

A **resident object** is a reserved object, other than a permanent object or a constituent object, whose storage is reserved before the execution of its machine begins, or, for the crossed counterpart of a referent, where the referent crosses (§6.11). Its storage is never released.

One object lifetime is **longer than** another where the other ends and it does not, or where both end and it ends the later. The two are **equal** otherwise.

A `break`, a `continue`, or an `express` exits, innermost first, each master and each scope between it and its target before control moves to the target.

Where control leaves a scope, the automatic objects belonging to the scope are destroyed in reverse declaration order, and immediately after the destruction of each, the temporary objects whose object lifetime ends there are destroyed in reverse order of production.

Where control leaves a subroutine body, after the automatic objects belonging to the scopes of the invocation are destroyed, the object of the variadic binding, if any, is destroyed, and then the objects of the fixed parameters, in reverse order of position.

Where control leaves a master, the temporary objects whose object lifetime ends there are destroyed in reverse order of production, before the automatic objects belonging to the scope the master evaluates, if any.

Where an initialized object is destroyed, the value it holds is destroyed, as §8.8.1 requires, and the object invalidated.

#### Examples (informative)

```
fn example(a: si4, b: si4) -> si4 {
    // Declaration order: x, y
    let x = a + 1;
    let y = b + 2;
    return x + y;
}   // Destruction order: y, x, b, a
```

### 2.2.7 Automatic object layout

#### Dynamic semantics

Upon entry to a scope, a storage region, its **layout region**, is reserved for the scope. Within it, before any initializer is evaluated, storage is reserved in declaration order for all automatic objects belonging to the scope. Kurt standard alignment, applied to the types of those objects in that order, assigns each of those objects its offset within the layout region and the region its alignment.

Where control leaves a scope, its layout region is released.

Upon entry to a subroutine body, a layout region is reserved for the objects of the fixed parameters of the subroutine and of its variadic binding, if present. The rule above, applied to the objects of those parameters in order of position, followed by the object of the variadic binding, assigns each of those objects its offset within the region and the region its alignment. That region is released where control leaves the subroutine body, after those objects are destroyed.

These rules are the **automatic object layout model**.

#### Implementation requirements

Where any access the implementation cannot resolve to an object spans a cell within a layout region, every object in the region whose storage includes a cell the access can span shall occupy its storage region at the offset within the layout region that the automatic object layout model assigns it.

#### Examples (informative)

```
// Example 1: local binding layout in declaration order
fn pair_sum() -> si4 {
    let a: si4 = 3;
    let b: si4 = 4;
    let result = a + b;
    // Automatic object layout model (block entry):
    //   addr:  | a: si4  | b: si4  | result: si4 |
    //   cells: [ 0 ... 3 | 4 ... 7 | 8 ... 11    ]
    // result is the return operand but occupies its
    // declared position in the layout.
    return result;
}
// The implementation may place result directly in
// the invoker’s storage (eliding the copy) if no access in the
// block that the implementation cannot resolve to an object
// can observe the difference.

// Example 2: an access through an unmanaged reference spans
// cells of a neighbouring automatic object
fn example2() -> si4 {
    let arr: [si4; 3] = [0, 0, 0];
    let i: si4 = 0;
    // Automatic object layout model:
    //   addr: | arr (12 cells) | i (4 cells) |

    airside {
        let p = arr.ptr as %mut si4;
        *(p + 3) = 5;
        // The store through p + 3 targets storage beyond arr’s
        // bounds. In the automatic object layout model, p + 3
        // targets the storage of i, so 5 is stored into i.
    }

    return i; // returns 5
}
// The conclusion follows from the automatic object layout model,
// so the implementation may constant-fold the subroutine
// to `return 5;`. Neither arr nor i need occupy storage where the
// return value is the only effect the programme has.

// Example 3: dynamic index and range splitting
fn example3(n: uaddr) -> si4 {
    let .{ mut arr, i } = .{ [0~si4; 3], 0 };
    airside { *(arr.ptr + n) = 5; }
    return i;
}
// The layout region fixes the relative positions of arr and i.
// Partition the execution-time cell offset n_cells = n * T'size,
// where T is the element type of arr:
//
//   Automatic object layout model (cells, relative to arr):
//     | arr: 12  | i: 4      |
//     [ 0 ... 11 | 12 ... 15 ]
//
//   n_cells ∈ {0 ... 8}:
//       within arr; unobservable store under the uniformity rule;
//       i remains 0
//
//   n_cells ∈ {9 ... 11}:
//       straddles arr and i; have i occupy its storage, return
//       the value a load of i reads from its cells
//
//   n_cells == 12:
//       targets i exactly; return 5
//
//   n_cells ∈ {13 ... 15}:
//       overlaps i and storage beyond the layout region; preserve
//       the store, have i occupy its storage, return the value a
//       load of i reads from its cells
//
//   otherwise:
//       targets storage outside the layout region; preserve the
//       access
//
// With T = si4, n_cells is a multiple of 4, the straddling
// ranges cannot occur, and the partition reduces to
//
//   n_cells ∈ {0, 4, 8}: unobservable store, return 0
//   n_cells == 12:       targets i, return 5
//   otherwise:           store outside the layout region, return 0;
//                        where the store spans storage the
//                        implementation reserves in carrying out
//                        an evaluation, the store can cause
//                        indeterminate state
//
// A possible optimized form:
//
//     fn example3_opt(n: uaddr) -> si4 {
//         let s = n * si4'size;
//         if s == 12 { return 5; }
//         if s > 3 * si4'size {
//             *(__ARR_BASE + n) = 5;
//         }
//
//         return 0;
//     }
//
// __ARR_BASE denotes a `%mut si4` that carries the address the
// automatic object layout model gives arr. The condition excludes
// the layout-interior stores that are unobservable.
```

### 2.2.8 Immortal object layout

#### Dynamic semantics

An access that spans cells of more than one immortal object, and not only cells of one of them, can cause indeterminate state.

#### Implementation defined

The address at which the storage for an immortal object is reserved on the programme machine or the translation machine is implementation defined.

## 2.3 The ordering of τ

The **settlement order** ⊏<sub>*a*</sub> of a cell *a* is a total order upon the writes to that cell, the initial write first, and a write **settles before** another at the cell when it is earlier in that order. (⊏<sub>*a*</sub> is a strict total order on the writes to *a*, with *ι*<sub>*a*</sub> ⊏<sub>*a*</sub> *w* for every other write *w* to *a*; *w* settles before *w*′ at *a* ⇔ *w* ⊏<sub>*a*</sub> *w*′)

The **order of happening** is the order in which the evaluations of the execution happen, each once. (the order of happening is a total order upon the evaluations of the execution, each taken once) An evaluation happens as a whole, except that a fence, which in this subclause is an execution ordering fence, happens component by component. (whole(*x*) ⇔ *x* is not a fence) An atomic access is one evaluation, and any other access is one evaluation for each read or write it performs, or one evaluation where it performs none. (an access *x* is one evaluation where *x* is an atomic access or performs no read and no write, and otherwise one evaluation for each read and each write *x* performs) The **next evaluation** of an execution context is the first in its programme order that the context has not reached. (next(*e*) at *T* is the first evaluation in the programme order of *e* that *e* has not reached at *T*) The context reaches its next evaluation when that evaluation happens, or at once where it has happened already. An evaluation is **early** where it happens while it is not the next evaluation of its context. (early(*x*) ⇔ *x* happens at a point *T* with *x* ≠ next(*e*) at *T*, *e* the context of *x*)

A read **observes**, at each cell it reads, one write to that cell: the initial write of the cell, or a write to the cell that has happened before the read happens. (a read of an execution context *e* at its τ point *i* observes at each cell *a* it reads one write to *a*, written *Ω*<sub>*e*</sub><sup>*i*</sup>(*a*), that is *ι*<sub>*a*</sub> or has happened before the read)

### Dynamic semantics

A read yields at each cell it reads the symbol that the write it observes there places at that cell. (a read by *e* at its τ point *i* yields at each cell *a* it reads the *γ* that *Ω*<sub>*e*</sub><sup>*i*</sup>(*a*) places at *a*) A load, and each evaluation that reads, observes at each cell it reads the write that its read of that cell observes. (a load or an evaluation of *e* observes at each cell *a* it reads *Ω*<sub>*e*</sub><sup>*i*</sup>(*a*), *i* the τ point of its read of *a*)

An execution is **admissible** where all of the following hold of it, in the terms that §2.3.1 and §2.3.3 define:

&mdash; No event is ordered before itself on a cell, through one or more steps. (¬(*p* ⊲<sub>*a*</sub><sup>+</sup> *p*) for every event *p* and every cell *a*)

&mdash; No event is ordered before itself across cells, through one or more steps. (¬(*p* ⊲<sup>+</sup> *p*) for every event *p*)

&mdash; An evaluation that happens as a whole is, under every valuation, its own claim when it happens early, and has the operation it happened with when its execution context reaches it. (whole(*x*) ⇒ ((early(*x*) ⇒ own<sub>*V*</sub>(*x*) at the point *x* happens, for every *V*) ∧ (op<sub>*V*</sub>(*x*) = op(*x*) for every *V* when *x* is reached)))

&mdash; An evaluation counted on observes, in each cell it is led in, the write its leader made there or, where its leader made none, the write its leader observed there, under every valuation when its execution context reaches it. (counted(*j*) ∧ led<sub>*V*</sub>(*j*, *a*) ⇒ the write *j* observes at *a* = the write leader<sub>*V*</sub>(*j*) made at *a*, or, where it made none there, the write it observed at *a*, for every *V* when *j* is reached)

### Examples (informative)

### 2.3.1 Causation and valuations

#### Dynamic semantics

The terms of this subclause are defined together.

An earlier evaluation *x* of an execution context is **tied** to a later evaluation *y* of it where any of the following holds, and an evaluation is tied to itself. In these conditions, the components of a fence take the place of the fence.

&mdash; Both access a common cell. (cells(*x*) ∩ cells(*y*) ≠ ∅, cells(*x*) the cells *x* accesses)

&mdash; Either is a `guard()`. (*x* is a `guard()` ∨ *y* is a `guard()`)

&mdash; One is a component with the kind pair (*k*<sub>1</sub>, *k*<sub>2</sub>), and the other an earlier evaluation of the kind *k*<sub>1</sub> or a later evaluation of the kind *k*<sub>2</sub>. (*y* a component with the kind pair (*k*<sub>1</sub>, *k*<sub>2</sub>) and *x* an evaluation of the kind *k*<sub>1</sub>, or *x* a component with the kind pair (*k*<sub>1</sub>, *k*<sub>2</sub>) and *y* an evaluation of the kind *k*<sub>2</sub>)

&mdash; Both are components with the same kind pair (§2.3.2). (*x* and *y* components with the same kind pair)

The **claim** of an evaluation *x* under a valuation *V* is the first evaluation, from the next evaluation of its execution context on, that occurs under *V*, is tied to *x*, and is not claimed under *V*. (claim<sub>*V*</sub>(*x*) at *T* = min{ *j* ≥ next(*e*) at *T* | occ<sub>*V*</sub>(*j*) ∧ tied(*j*, *x*) ∧ ¬(claimed<sub>*V*</sub>(*j*) at *T*) }, *e* the context of *x*) An evaluation is its own claim under *V* where its claim has, under *V*, the operation the evaluation happens with. (own<sub>*V*</sub>(*x*) at *T* ⇔ op<sub>*V*</sub>(claim<sub>*V*</sub>(*x*) at *T*) = op(*x*), op(*x*) the operation *x* happens with)

An evaluation is **claimed** under a valuation *V* after the point of the order of happening at which an evaluation that has it as its claim under *V* happens. (claimed<sub>*V*</sub>(*j*) at *T* ⇔ *j* = claim<sub>*V*</sub>(*x*) at *t*, for some *x* that happens at *t* &lt; *T*)

A **valuation** *V* of an execution context gives each evaluation that reads and that the context has still to reach a symbol in each cell it reads. Where an evaluation *x* has happened with one of them as its claim under *V*, that one has, in each cell, the symbol that the write *x* observed there places. Any other one counted on has, in each cell it is led in, the symbol of the leader in that cell. Each has any symbol in every other cell. (for each evaluation *j* that reads and that the context has still to reach at *T*, *V*(*j*, *a*) at *T* = the symbol that the write *x* observed at *a* places if *j* = claim<sub>*V*</sub>(*x*) at *t* for some *x* that happens at *t* &lt; *T*; else leadersym(leader<sub>*V*</sub>(*j*), *a*) if counted(*j*) at *T* ∧ led<sub>*V*</sub>(*j*, *a*); any symbol otherwise)

An evaluation that happens early **counts on** any set of evaluations of loads: the valuations considered for it give each of them, in each cell it is led in, the symbol of the leader in that cell, and each stays counted on from then on. (counted(*j*) at *T* ⇔ *j* is one of a set of evaluations of loads that an evaluation happening early at some *t* ≤ *T* counts on)

The evaluations that **occur under** a valuation are those the programme determines for the context from its first evaluation, each evaluation that reads yielding the value that the symbols it observed represent where the context has reached it, and the value that the symbols the valuation gives it represent otherwise. (occ<sub>*V*</sub>(*j*) ⇔ *j* occurs under *V*)

Under a valuation an evaluation has the operation the programme determines for it from those values. Two operations are the same where their kinds, cells, and operand values agree. (op<sub>*V*</sub>(*j*) = the kinds, the cells, and the operand values of the operation *j* has under *V*)

The **leader** of an evaluation under a valuation *V* is the last evaluation before it that occurs under *V* and is tied to it. (leader<sub>*V*</sub>(*j*) = max{ *b* &lt; *j* | occ<sub>*V*</sub>(*b*) ∧ tied(*b*, *j*) })

An evaluation of a load is **led in** each cell its leader accesses and it reads. (led<sub>*V*</sub>(*j*, *a*) ⇔ *j* is an evaluation of a load ∧ *a* ∈ cells(*j*) ∩ cells(leader<sub>*V*</sub>(*j*)))

The **symbol of the leader** in a cell is the symbol that the write the leader made there places or, where it made none, that the write it observed there places. (leadersym(*b*, *a*) = the symbol that the write *b* made at *a* places, or, where *b* made none at *a*, the symbol that the write *b* observed at *a* places)

### 2.3.2 Ordering properties

#### Dynamic semantics

A **kind pair** (*k*<sub>1</sub>, *k*<sub>2</sub>) relates an earlier evaluation of a kind *k*<sub>1</sub> to a later evaluation of a kind *k*<sub>2</sub>, where each kind is load or store. Each part of a joint access is of both kinds. A fence **relays loads** where it has the kind pair (load, load), **relays stores** where it has (store, store), **withholds loads** where it has (store, load), and **withholds stores** where it has (load, store). These four are the **ordering properties**. A fence other than `guard()` consists of one **component** for each ordering property it has, and `guard()` of one component with all four.

At each point of the order of happening, an execution context has these sets of writes, none of which contains an initial write:

&mdash; The writes it has **taken in** are those it has observed or made, and those its fences have added to them. (*P*)

&mdash; The writes **handed over** to it are those that the writes it has observed convey, other than the writes it has taken in. (*A*)

&mdash; Its **conveyed writes** are those its fences have added to them. A write **conveys** itself and the conveyed writes of its context at the time it happens. (*R*; conv(*w*) = {*w*} ∪ *R*, *R* that of the context of *w* when *w* happens)

&mdash; The writes it has made are its **own writes**. (*W*)

&mdash; The **published writes** are those in a set, common to all execution contexts, to which the fences of every context add. (*G*)

&mdash; Its **cell-sequenced writes** and its **globally sequenced writes** are the writes its fences have added to each. (*O*, *O*<sub>g</sub>)

A component has the effects of the ordering properties it has:

&mdash; Relaying loads takes in the writes handed over, and adds to the cell-sequenced writes the writes taken in, other than own writes not published. (*P* := *P* ∪ *A*; *O* := *O* ∪ (*P* &minus; (*W* &minus; *G*)))

&mdash; Relaying stores adds own writes to the conveyed writes. (*R* := *R* ∪ *W*)

&mdash; Withholding loads publishes own writes, then adds the published writes to the cell-sequenced writes and to the globally sequenced writes. (*G* := *G* ∪ *W*; then *O* := *O* ∪ *G*; *O*<sub>g</sub> := *O*<sub>g</sub> ∪ *G*)

&mdash; Withholding stores adds to the conveyed writes the writes taken in or handed over that are not own. (*R* := *R* ∪ ((*P* ∪ *A*) &minus; *W*))

A `guard()` has these effects, in this order:

1. It takes in the published writes and has the effects of relaying loads. (*P* := *P* ∪ *G* ∪ *A*; *O* := *O* ∪ (*P* &minus; (*W* &minus; *G*)))

2. It publishes every write taken in. (*G* := *G* ∪ *P*)

3. It has the effects of the other three ordering properties.

#### Examples (informative)

```
// Example 1: a payload and a flag. Every cell holds 0 at the start.
// d and flag are `static mut` objects of type ui4, and the code of
// each context lies within an airside region.

// context A
*&atomic mut d = 1;
guard.rs();
*&atomic mut flag = 1;
// context B
let f = *&atomic flag;
guard.rl();
let r = *&atomic d;
// f = 1 with r = 0 is excluded: the store to flag conveys the store
// to d; the load of flag hands the store to d over; the fence takes
// it in and orders it before the later load of d
// Without guard.rl() in B, f = 1 with r = 0 is admitted
```

### 2.3.3 Event order

#### Dynamic semantics

Each evaluation of an access is one **event**, with its τ operations.

An event *u* is **ordered after** writes as follows, in terms of the sets its execution context has just before *u* happens:

&mdash; On every cell, *u* is ordered after the globally sequenced writes and the writes it observes, other than own writes that are not cell-sequenced. (after<sub>all</sub>(*u*) = *O*<sub>g</sub> ∪ (obs(*u*) &minus; (*W* &minus; *O*)), obs(*u*) the writes *u* observes)

&mdash; An event *u* that reads is also ordered, on each cell it reads, after the cell-sequenced writes. (after<sub>*a*</sub>(*u*) = after<sub>all</sub>(*u*) ∪ *O* for an event *u* that reads *a*, and after<sub>*a*</sub>(*u*) = after<sub>all</sub>(*u*) otherwise)

An event *p* is ordered before a different event *q* on a cell *a*, written *p* ⊲<sub>*a*</sub> *q*, where at least one of the following holds of a τ operation *o* of *p* at *a* and a τ operation *o*′ of *q* at *a*:

&mdash; *o*, or the write *o* observes where *o* is a read, settles before *o*′. (*o* ⊏<sub>*a*</sub> *o*′, or *o* a read of *a* by *e* at τ point *i* and *Ω*<sub>*e*</sub><sup>*i*</sup>(*a*) ⊏<sub>*a*</sub> *o*′)

&mdash; *o* is the write that *o*′, a read, observes. (*o*′ a read of *a* by *e* at τ point *i*, and *o* = *Ω*<sub>*e*</sub><sup>*i*</sup>(*a*))

&mdash; *o* is a write, and *q* is ordered after *o* on *a*. (*o* ∈ after<sub>*a*</sub>(*q*))

&mdash; *p* and *q* are of one execution context, and *p* is the earlier in its programme order. (*p*, *q* of *e*, *p* earlier in the programme order of *e*)

An event *p* is ordered before a different event *q* **across cells**, written *p* ⊲ *q*, where at least one of the following holds:

&mdash; For some τ operation *o* of *p* and some τ operation *o*′ of *q* at one cell, *o*, or the write *o* observes where *o* is a read, settles before *o*′. (for some cell *a* and some *o* of *p* and *o*′ of *q* at *a*, *o* ⊏<sub>*a*</sub> *o*′, or *o* a read of *a* by *e* at τ point *i* and *Ω*<sub>*e*</sub><sup>*i*</sup>(*a*) ⊏<sub>*a*</sub> *o*′)

&mdash; *q* is ordered after a write of *p* on every cell. (*p* has a write in after<sub>all</sub>(*q*))

### 2.3.4 Joint accesses

#### Dynamic semantics

The load of a joint access is its **load part**, and its store, where it is performed, is its **store part**. Each part is an evaluation. The operands of the load part are the object and the type that its load names. The operands of the store part are the object, the type, and the value that its store names, and, where the joint access succeeds, every operand of the operation that performs the joint access. The store part happens after its load part, reads the cells its load part read, observing at each the write its load part observed there, and then writes.

The rule that defines a joint access may give it a **storing condition** on the value its load part observes. A joint access without one succeeds. A joint access with one fails where the value does not satisfy the condition, and succeeds or fails where the value satisfies it. That it succeeds or that it fails is its **outcome**. Where its rule permits, a joint access that fails may perform a store of the value its load part observed.

A valuation gives each joint access whose last part its execution context has still to reach an outcome that the value of its load part under the valuation permits. Under that valuation, the store part of such a joint access occurs where the joint access succeeds, or fails and performs a store of the value its load part observed. Under a valuation, a load part that has happened stands for the joint access whose load part is its claim under that valuation at the point at which it happened. An evaluation that happens early may count on an outcome where a load part has happened, has one value under every valuation considered for it, and every such valuation permits the outcome to the joint access that load part stands for under that valuation. Every later valuation then gives that outcome to the joint access that load part stands for under that later valuation.

#### Examples (informative)

```
// Two execution contexts, A and B, run side by side. Every cell
// holds 0 at the start. x and y are `static mut` objects of type ui4,
// and the code of each context lies within an airside region.

// Example 1: a joint access that fails
// context A
let r0 = *&atomic y;
let c = &atomic mut x >.< 9 then r0;
*&atomic mut x = 1;
// context B
let r1 = *&atomic x;
*&atomic mut y = r1;
// r0 = 1 with r1 = 1 is admitted: the load part observes 0, which
// permits the outcome that the joint access fails under every
// valuation, so the store to x counts on that outcome and happens
// early
```

## 2.4 Reachability and indeterminacy

Theorem. A Kurt machine with a partial transition function cannot exist.

Proof. Suppose, for contradiction, that a Kurt machine is permitted a partial transition function, so that some Kurt machine *K* = (*Q*, *Γ*, *Σ*, *δ*, *q*<sub>0</sub>) has dom(*δ*) = *D* ⊊ *Q* × *Σ*. There exists a pair (*q*, *σ*) ∈ (*Q* × *Σ*) &minus; *D*.

What *K* models is the computer, and by Axiom 1 the computer is a machine. A state of the machine, together with what the environment supplies at its boundary, is a condition that machine can be in, and every member of *Σ* can pass into it there. (*q*, *σ*) is therefore such a condition, and by Axiom 1 the machine is caused to act there.

The machine of Axiom 1 is a physical thing, and a physical thing does not pass into nothing: what it holds is conserved, and leaves it only across its boundary. The act therefore brings the machine to some state, and places at its boundary some signal or none. This specification can leave unspecified which these are, but not whether they exist. Apart from its boundary, the whole of the machine after the act is a state of *Q*, and what the act places at the boundary is a member of *Σ*, ε where it places none. The two are therefore a member of *Q* × *Σ*.

By Axiom 1 and the definition of the Kurt machine, the machine acts at (*q*, *σ*) under the same law as at every condition in *D*, and *δ* is that law as the machine embodies it rather than a description drawn afterwards from its acts in *D*. What the machine in state *q* comes to, and places at its boundary, where the environment supplies *σ* is *δ*(*q*, *σ*), so *δ* assigns (*q*, *σ*) a member of *Q* × *Σ*, contrary to (*q*, *σ*) ∉ *D*.

∴ dom(*δ*) = *Q* × *Σ*, and *δ* is total. Quod erat demonstrandum.

### Static semantics

A **trace** is a succession of programme points that an execution context can occupy, each immediately after the one before it. A trace has one **visit** to a programme point for each time it occupies that programme point.

An execution context **can occupy** a succession of programme points where it would occupy them in turn if each of the following held:

&mdash; It began at the first programme point of the innermost construct enclosing them that the constraints of §7.11 list.

&mdash; It took each value that an expression yields to be any value of its type.

&mdash; It took each `xlat?` or `arbit?` conditional to select the branch it selects in an evaluation on the machine of that execution context.

In that succession, at the programme point at which an invocation would pass control to the invoked subroutine, it passes to the programme point after that invocation. Where the subroutine that invocation invokes returns `!`, it instead occupies no further programme point.

A programme point is **reachable** where an execution context can occupy a succession of programme points that contains it. Every other programme point is **unreachable**. A programme point is **reachable from** a construct where it is reachable with the first programme point of that construct as the one at which the execution context begins. A construct is reachable, or reachable from a construct, where its first programme point is.

No operation at an unreachable programme point is a σ operation (§2.5).

### 2.4.1 Indeterminate state

#### Dynamic semantics

An execution context is in an **indeterminate state** at a programme point where this specification, together with what the implementation determined in translating the programme, does not fix the transition its machine makes there.

#### Design rationale (informative)

An environment documents facts of itself, and experiment upon an environment establishes further facts from the signals it supplies. Such a fact, joined to the rules this specification fixes, determines an outcome this specification alone does not. An execution context can reach an indeterminate state by acting upon one.

The operations around an indeterminate state follow the rules that every other operation follows. The implementation requirements upon σ operations leave a transformation no premise about such a state, and *δ* brings the machine to its successor state by the theorem above.

#### Examples (informative)

```
fn indeterminate() -> uaddr {
    let x: uaddr = 10;
    airside {
        *(0x80_0000 as %mut uaddr) = 20;
    }

    return x;
}
```

Whether the environment accepts the store through `0x80_0000 as %mut uaddr` is outside the scope of this specification, and the execution context is in an indeterminate state at the store. A conforming implementation performs the store. Where the environment accepts it, `indeterminate` returns 20 if the store spans a cell of `x`, and 10 otherwise. Where it does not, the store can, for example, diverge, or the environment can supply the storage and resume the programme.

```
const port: uaddr = 0xFE20_1000;

fn print(a: &[ui1]) {
    let .{ ptr, mut i } = .{ port as %volatile atomic mut ui4, 0 };

    while a.len > i {
        airside {
            while (*(ptr + 6) & (1 << 5)) != 0 {}
            *ptr = *(a.ptr + i) as ui4;
        }
    } and then { i += 1; }
}

extern fn main() -> ! {
    print("Hello, world!\n");
    loop {}
}
```

Whether the environment accepts the loads through `ptr + 6` and the stores through `ptr` is outside the scope of this specification, and the execution context is in an indeterminate state at each of them. Suppose the environment places at `port` a UART that conforms to the Arm PrimeCell UART (PL011) Technical Reference Manual, revision r1p5. The bit at position 5 of the value a load through `ptr + 6` yields is then the flag that is one while the transmit FIFO is full, so the inner loop waits until the UART can take a value, and the stores pass the values of the cells of `Hello, world!\n` to it one at a time. The terminal attached to the UART displays `Hello, world!`.

```
// Search the addresses from first below last, at a stride of
// 0x1000, for one whose load yields 0x5AFE_C0DE.
airside fn probe(first: uaddr, last: uaddr) -> verdict[uaddr, void] {
    let mut base: uaddr = first;

    while base < last {
        let id = base as %volatile atomic ui4;
        if *id == 0x5AFE_C0DE { return verdict::Pass.{ base }; }
    } and then { base +|= 0x1000; }

    return verdict::Fail.{ void };
}
```

The load at `base` can yield any value, or can be an access the environment of the programme machine does not accept. Neither this specification nor the documentation of the environment fixes which. `probe` is an experiment upon the environment: where a load yields `0x5AFE_C0DE`, it returns `base` in `verdict::Pass` on the basis of that fact.

```
struct chunk {
    ptr: %mut ui1,
    len: uaddr
} with destruct {
    release(self.ptr, self.len);
};

fn adopt(p: %chunk) -> chunk {
    return airside { express *p; };
}

fn hand_off(c: chunk) -> chunk {
    let taken = adopt(%c);
    airside { undrop(c); }
    return taken;
}

fn duplicate(c: chunk) -> chunk {
    return adopt(%c);
}
```

A load through an unmanaged reference copies the value of the object `p` designates, which still holds it.

`hand_off` leaves `c` uninitialized, and the destructor is invoked once upon the storage region. `duplicate` leaves `c` initialized, and both it and the value it returns hold a reference to that one region. Two destructors are invoked upon it, and the second passes to `release` the address of a region the first released. Neither this specification nor the documentation of the environment fixes what the second does, and the execution context is in an indeterminate state there. Depending on how the destructor is defined, the second can, for example, corrupt state the destructor relies on, detect such corruption and attempt recovery, or diverge.

```
fn walk(depth: uaddr) -> uaddr {
    let scratch: [ui1; 4096] = [0; 4096];
    if depth == 0 { return scratch.len; }
    return walk(depth - 1) + scratch.len;
}
```

Each invocation reserves storage for its own `scratch`. Where the environment of the programme machine cannot supply that storage, execution exceeds a capacity limit of the environment. Exceeding it can cause indeterminate state. The storage so reserved can then overlap that of another object, including one that another execution context accesses, and the stores that initialize `scratch` span a cell of it.

## 2.5 σ operations

A **σ operation** is an operation in which the environment of the machine takes part.

### Static semantics

The environment takes part in the following operations:

&mdash; Volatile access &mdash; any joint access, and any access not part of a joint access, performed through a reference carrying the `volatile` modifier.

&mdash; External subroutine invocation &mdash; any invocation of a subroutine whose definition the implementation does not determine to lie within the current translation unit.

&mdash; External subroutine return &mdash; any return of control to an invoker the implementation does not determine to lie within the current translation unit.

&mdash; External binding access &mdash; any joint access, and any access not part of a joint access, that the implementation does not determine during translation to span no cell of a permanent object declared in an `#extern` namespace.

&mdash; `instruct` block &mdash; any inline or global `instruct` block.

&mdash; **Indeterminate operation** &mdash; any operation the implementation does not determine during translation to cause no indeterminate state.

### Dynamic semantics

What the environment does with an operation after the implementation performs it is outside the scope of this specification.

### Implementation requirements

The implementation shall perform each σ operation, and each of its τ operations, exactly once. It shall not widen a σ operation, nor coalesce one with any other operation, and it shall arrange no other operation within one.

The implementation shall not use what the environment does at a σ operation to eliminate an operation or reorder one in a different sequence (§2.6).

## 2.6 Uniformity rule

The implementation may replace any sequence of operations with a different sequence, provided all of the following hold:

&mdash; For each execution it exhibits, some admissible execution of the programme has, of each execution context, the σ operations of that execution, each with the signal that originates from the machine at it.

&mdash; In the different sequence, the σ operations of each execution context stand in the programme order of that context.

&mdash; In the different sequence, no τ operation of an evaluation stands before a σ operation that precedes the evaluation in the programme order of the evaluation’s execution context, nor after one that follows it.

&mdash; Every execution it exhibits remains admissible under §2.3.

&mdash; Every requirement that this specification states under an Implementation requirements heading holds.

Where an indeterminate operation is present, the conditions above hold for each behaviour of the environment at that operation. (for every behaviour of the environment at the indeterminate operations, every execution *x*′ that the implementation exhibits under it is admissible, and some admissible execution *x* of the programme under it has, of each execution context, the σ operations of *x*′, in the programme order of that context, each with the signal that originates from the machine at it; in the different sequence, no τ operation of an evaluation stands before a σ operation that precedes the evaluation in the programme order of the evaluation’s execution context, nor after one that follows it; and every requirement stated under an Implementation requirements heading holds)

### Design rationale (informative)

The uniformity rule is the sole source of an implementation’s freedom to transform a programme.

### Examples (informative)

```
extern fn dork(x: saddr) -> ui1 {
    if x == 0 { return 1; }
    else if x == 1 { return 0; }
    else if x == 2 { return 1; }
    else if x == 3 { return 0; }
    else if x == 4 { return 1; }
    else if x == 5 { return 0; }
    else if x == 6 { return 1; }
    else if x == 7 { return 0; }
    else if x == 8 { return 1; }
    else if x == 9 { return 0; }
    else { return 2; }
}

extern fn clever(x: saddr) -> ui1 {
    if 0 <= x and x < 10 {
        return (x & 1 == 0) as ui1;
    }

    return 2;
}
```

Both subroutines are declared by external declarations. For every input, their σ operations are identical, stand in the same order, and the signals that originate from the machine at them are the same; the implementation may translate either as the other.

## 2.7 The airside/landside boundary

### Static semantics

An `airside` block, an `airside fn` body, and a global `instruct` block are each a lexically delimited **airside region**. **Airside** is the region within the airside regions.

**Landside** is the region outside every airside region.

An operation **requires airside** where this specification states that it does. Every other requirement this specification imposes upon an operation holds in airside as it holds in landside.

### Constraints

An operation that requires airside shall appear within an airside region.

## 2.8 Classification of errors

This specification classifies an error condition as a translation failure or as a trap.

### 2.8.1 Translation failure

#### Static semantics

A **translation failure** is the presence of source text the grammar of this specification does not permit, a violation of a requirement that this specification imposes on the programme, or any other condition this specification declares to be a translation failure. Exceeding a limit the implementation places upon the translation is a translation failure, and each such limit is implementation defined. Where this specification states that a violation can cause indeterminate state where not detected during translation, that violation is a translation failure only where so detected.

#### Implementation requirements

The implementation shall reject any source unit whose translation incurs a translation failure and shall issue a **diagnostic**. No opaque code is produced.

An **advisory diagnostic** is a diagnostic issued for a construct this specification permits. It shall identify the construct, and the implementation shall continue the translation after issuing one.

#### Implementation defined

Except where this specification requires otherwise, the content of the diagnostic a translation failure requires is implementation defined.

#### Examples (informative)

A type mismatch, a load of the source of a transfer, made after the transfer and through no reference, a non-exhaustive `match`, and an unrecognized string escape are each a translation failure.

### 2.8.2 Trap

A **trap** is a determinate execution-time divergence. `trap` is defined in §7.10.
