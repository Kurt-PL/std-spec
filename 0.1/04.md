# §4. Types

This clause defines the built-in types of the Kurt programming language: their classifications, representations, value sets, and properties.

The operators that act on these types are defined in the clause on expressions. The reference and derivation model is defined in the clause on references and resource management. The `with` keywords that attach semantic properties to declared types are defined in the clause on declarations.

## 4.1 Type classification

The meaning of a value is determined by the type of the expression used to access it. Types in Kurt are partitioned as follows.

**Built-in types** are types whose existence, representation, and operator semantics are defined normatively by this specification. Among them are the integer types, the floating radix point number types, and the reference types. The size and alignment of a built-in type follow from the parameters of the execution environment given below.

A declaration whose identifier is the name of a built-in type hides the built-in name within its scope.

`selftype` is a keyword that stands for a type rather than naming one. Where it is admissible, and which type it stands for there, are defined in the clause on protocols and implementations.

**Declared types** are types introduced by `struct`, `enum`, `contract`, and `type` alias declarations in the programme. Their declaration syntax is defined in the clause on declarations and in the clause on statements and control flow.

### Parameters of the execution environment

Every object occupies an integer number of cells, as defined in the clause on semantics; every address identifies a particular cell.

The following values are the only parameters of the execution environment in the Kurt type system. All other type widths and alignments are derived from these values:

### Implementation requirements

A conforming implementation shall know every built-in type directly; it shall not realize a built-in type by introducing a declaration or any other source text into the programme.

A conforming implementation shall document the values of all three parameters for each supported execution environment. The address width shall be sufficient to address the entire address space of the execution environment. The reference width shall be sufficient to hold a `%void` of the execution environment, including any additional information it carries in references.

## 4.2 Size and alignment

### Static semantics

For every type with non-zero size, `T'align` is a power of two and divides `T'size`; a type whose size is zero has alignment zero unless a `with` clause fixes its alignment otherwise.

For a type satisfying `numeric`, a reference type whose stored representation is a single address, and the subroutine pointer type, `T'align == T'size`, and the size derives from the type’s **bit width** *W*<sub>t</sub>:

`T'size` = 2<sup><span class="ceil">⌈&thinsp;log<sub>2</sub> <span class="ceil">⌈&thinsp;*W*<sub>t</sub> / `cellbits`&thinsp;⌉</span>&thinsp;⌉</span></sup>

Where `T'size` × `cellbits` is greater than *W*<sub>t</sub>, the interpretation of the type takes each value from *W*<sub>t</sub> bits alone, and maps 2<sup>`T'size` × `cellbits` − *W*<sub>t</sub></sup> Γ sequences to each value of the type. Which of them a store places is implementation defined.

For a type satisfying `numeric`, *W*<sub>t</sub> is the width defined in the subclause on integer types or the subclause on floating radix point number types. For a reference type whose stored representation is a single address, and for the subroutine pointer type, *W*<sub>t</sub> is the reference width.

The size and alignment of an array are defined in the subclause on array types; those of a tuple, struct, or enum, in the subclause on composite type representation.

### Design rationale (informative)

An alignment greater than a value requires is sound in every execution environment, and none requires more than the number of cells the value occupies. `T'align == T'size` is therefore sound everywhere without this specification determining the requirement of each environment; `pack(N)` relinquishes the resulting padding where the programme states its target’s requirement.

An integer type name denotes a power-of-two multiple of `cellbits`, and each floating radix point number type has a bit width that is a power of two, so <span class="ceil">⌈&thinsp;*W*<sub>t</sub> / `cellbits`&thinsp;⌉</span> is a power of two whenever `cellbits` divides *W*<sub>t</sub>. Rounding `T'size` up to a power of two keeps the alignment rule satisfied in every execution environment, including one whose `cellbits` does not divide *W*<sub>t</sub> — for example a floating radix point number type or an address-width integer under a `cellbits` that is not a power-of-two divisor of *W*<sub>t</sub>.

## 4.3 Integer types

### Static semantics

An integer type represents a finite subset of the mathematical integers.

An **unsigned** integer type uses pure binary encoding over all *W*<sub>t</sub> bits. The value of a *W*<sub>t</sub>-bit unsigned integer with bits *b*<sub>*W*<sub>t</sub>−1</sub>, …, *b*<sub>0</sub> is <span class="sum">Σ<sub>*k*=0</sub><sup>*W*<sub>t</sub>−1</sup></span> *b*<sub>*k*</sub> × 2<sup>*k*</sup>.

A **signed** integer type uses two’s complement encoding. The value of a *W*<sub>t</sub>-bit signed integer with bits *b*<sub>*W*<sub>t</sub>−1</sub>, …, *b*<sub>0</sub> is −*b*<sub>*W*<sub>t</sub>−1</sub> × 2<sup>*W*<sub>t</sub>−1</sup> + <span class="sum">Σ<sub>*k*=0</sub><sup>*W*<sub>t</sub>−2</sup></span> *b*<sub>*k*</sub> × 2<sup>*k*</sup>. Bit *W*<sub>t</sub>−1 is the **sign bit** — the position of greatest weight: when it is 1, the represented value is negative.

Bit-shift on signed integers is arithmetic shift: the descending shift replicates the sign bit into the vacated positions of greater weight.

### 4.3.1 Cell width of the environment

#### Syntax

```
cellbits_expr = "cellbits", [ '::', ( 'exec' | "xlat" ) ] ;
```

#### Static semantics

`cellbits` is a keyword that evaluates in expression contexts to a cell width, as defined in the clause on semantics. Under the rules for type inference, synthesis of a `cellbits` expression is undetermined. Its default type is `uaddr`. The widths of the `uiN` and `siN` types are derived from `cellbits`; those of `uaddr` and `saddr` are the address width.

`cellbits` admits two **qualified forms**.

`cellbits::exec` evaluates to the cell width of the execution environment. `cellbits::xlat` evaluates to the cell width of the translation environment. Each qualified form evaluates to the same value in every context.

The value of the unqualified `cellbits` depends on the context in which it is evaluated:

— Outside a `xlat` evaluation, `cellbits` evaluates to *B*<sub>e</sub>.

— Within a `xlat` evaluation, `cellbits` evaluates to the greater of *B*<sub>e</sub> and *B*<sub>x</sub>.

The value sets of the `uiN` and `siN` types are determined by the value to which the unqualified `cellbits` evaluates in the enclosing context. The behaviour of the unqualified `cellbits` within a `xlat` evaluation, and the conversion of values that cross the boundary of a translation-environment `asm` block, are defined in the clause on expressions.

#### Constraints

The value of a `cellbits` expression shall fit in the inferred type, as defined in the subclause on type inference and the inferred type `?`.

#### Implementation requirements

All address arithmetic, object sizes, and alignment computations applied to the opaque code shall be consistent with `cellbits::exec`.

#### Design rationale (informative)

The greater cell width makes every value of a cell-width-derived integer type representable in both environments. The qualified forms provide an environment-specific width independently of the evaluation context.

#### Value sets

For a type with bit width *W*<sub>t</sub>: the value set of an unsigned type is [0, 2<sup>*W*<sub>t</sub></sup> − 1]; the value set of a signed type is [−2<sup>*W*<sub>t</sub>−1</sup>, 2<sup>*W*<sub>t</sub>−1</sup> − 1], represented in two’s complement. A computation involving unsigned operands does not overflow; a result that cannot be represented by the resulting unsigned integer type is reduced modulo 2^W. Signed overflow wraps identically: the result is (mathematical result) mod 2^W, mapped to the signed value set by two’s complement interpretation.

#### Examples (informative)

Where `cellbits == 8`, `ui1` is 8-bit and `ui4` is 32-bit. Where `cellbits == 16`, `ui1` is 16-bit and `ui4` is 64-bit.

#### Notes (informative)

Saturating and widening operators are available as explicit alternatives to wrapping; they are defined in the clause on expressions.

## 4.4 Floating radix point number types

Arithmetic on a floating radix point number type conforms to ISO/IEC 60559:2020 where this clause does not state otherwise.

### Static semantics

A **floating radix point number type** divides its *W*<sub>t</sub> bits into three adjacent fields, from the position of greatest weight to the position of least weight: the **sign field**, of one bit; the **exponent field**; and the **significand field**. A value of such a type is a **floating radix point number**.

Such a type is named `fe{exponent_bits}s{significand_bits}`, where the numerals are the widths of the exponent field and the significand field, and *W*<sub>t</sub> is `1 + exponent_bits + significand_bits`. All floating radix point number types satisfy `numeric` but not `integer` or `primitive`.

### 4.4.3 Comparison

#### Dynamic semantics

The comparison operators `==`, `!=`, `<`, `>`, `<=`, `>=` on a floating radix point number type implement the ISO/IEC 60559:2020 total order predicate. Every floating radix point number is comparable with every other value of the same type.

The classes defined in the subclause on value classification are ordered, from least to greatest: NegQNN, NegSNN, NegInf, NegScl, NegZro, PosZro, PosScl, PosInf, PosSNN, PosQNN.

Within NegScl and PosScl, values are ordered by their numeric value. Within NegQNN and NegSNN, increasing payload orders earlier. Within PosSNN and PosQNN, increasing payload orders later.

`a == b` holds if and only if `a` and `b` occupy the same position in this order. `a != b` holds if and only if `a == b` does not hold. `a < b` holds if and only if `a` precedes `b` in this order. `a > b` holds if and only if `b` precedes `a`. `a <= b` holds if and only if `a < b` or `a == b`. `a >= b` holds if and only if `a > b` or `a == b`.

#### Implementation requirements

A conforming implementation shall produce comparison results consistent with the total order defined above. A comparison whose operand is a signalling NaN yields the result the order defines, as any other comparison does; the operand’s presence shall not alter control flow and shall not invoke `trap`.

### 4.4.4 NaN propagation

#### Dynamic semantics

A signalling NaN operand of `+`, `-`, `*`, `/`, or `%` is treated as a quiet NaN with the same sign and payload for the purpose of the rules below.

If exactly one operand of `+` or `-` is NaN, the result is a quiet NaN with payload 0 and the sign of the NaN operand, negated where the operator is `-` and the NaN is the following operand. If exactly one operand of `*`, `/`, or `%` is NaN, the result is a quiet NaN with payload 0 and the XOR of the two operands’ signs.

If both operands of `+` or `-` are NaN, the result is a quiet NaN with payload 0 and the sign of the leading operand. If both operands of `*`, `/`, or `%` are NaN, the result is a quiet NaN with payload 0 and the XOR of the two operands’ signs.

If neither operand is NaN and the operation produces NaN, as defined in the subclause on special operations, the result is a quiet NaN with payload 0. Its sign is determined by the same rule: the sign of the leading operand for `+` and `-`, and the XOR of the operands’ signs for `*`, `/`, and `%`.

Unary negation (`-`) on a NaN flips the sign bit; the kind and payload are preserved.

#### Implementation requirements

A conforming implementation shall produce a quiet NaN with payload 0 and the sign defined above from every operation defined in this subclause. The implementation shall not produce a signalling NaN as the result of any arithmetic operation. The implementation’s behaviour upon a signalling NaN operand, other than the arithmetic result, is implementation defined and may include invoking `trap`; absent such a behaviour, the operand’s presence shall not alter control flow.

### 4.4.5 Special operations

#### Dynamic semantics

— `0.0 / 0.0` yields NaN.

— `x / 0.0` where `x != 0.0` yields positive or negative infinity, depending on the sign of `x`.

— Overflow yields positive or negative infinity.

— Underflow yields zero or a subnormal value, depending on the magnitude.

#### Dynamic semantics

The rules for conversion between a floating radix point number type and an integer type by `as` are defined in the clause on expressions.

## 4.5 `void`

### Static semantics

`void` is the **unit type**. It has size zero and alignment zero. It contains exactly one value, written `void`. When a subroutine omits its return type, the return type is `void`.

## 4.6 Built-in contract type

### Static semantics

`verdict.[T, F]` is the built-in contract type, generic over a success payload type `T` and a failure payload type `F`.

`verdict.[T, F]` has exactly two variants. `Pass`, the success variant, holds a payload of type `T` and takes the discriminant value 1. `Fail`, the failure variant, holds a payload of type `F`, covers every other discriminant value, and bears the canonical value 0, as defined in the clause on declarations. The discriminant type is `ui1`. `verdict.[T, F]` is a contract type with the inverted pair `selftype.[F, T]`, as defined in the clause on statements and control flow; `!` applied to a value of `verdict.[T, F]` yields a value of `verdict.[F, T]`.

Contract types, which `if`, `?`, contract extraction, `and`, `or`, and `!` operate upon, are defined in the clause on statements and control flow.

### Examples (informative)

```
// The conventional truth-value vocabulary, declared in source
type bool = verdict.[void, void];
const true:  bool = verdict::Pass(void);
const false: bool = verdict::Fail(void);
```

### Notes (informative)

The set of discriminant values that `wild` covers for `verdict.[void, void]` depends on `cellbits::exec`: where `cellbits::exec == 8`, the covered set is `{0, 2, 3, ..., 255}`; where `cellbits::exec` takes a different value, the covered set is the value set of `ui1` minus the value `1`, scaled accordingly.

The definition of `verdict.[T, F]` is equivalent to the declaration:

```
contract verdict.[T, F] {
    Pass(T) = 1,
    Fail(F) = wild(0)
} with {
    inv -> selftype.[F, T],
    discrim(ui1)
}
```

## 4.7 Array types

`[T; N]` is an **array** whose length is fixed for the object lifetime of the object.

### Syntax

```
array_type = '[', ws, type, ws, ';', ws, expression, ws, ']' ;
```

### Static semantics

`[T; N]` is an array of `N` values of type `T`, where `N` is an expression of type `uaddr`. Where `N` is determined at translation time, so are `[T; N]'size` and every layout computation that depends on it. The layout is `N` contiguous values of `T` with no metadata: `[T; N]'size == N * T'size`. Where `N * T'size` is not zero, `[T; N]'align == T'align`.

The clause on references and resource management defines the implicit cast from a reference to `[T; N]` to the corresponding slice reference. It also defines the wide reference view that a `[T; N]` value and references to it expose, comprising the fields `.ptr` and `.len`.

Copy, transfer, and destruction semantics of `[T; N]` follow from `T`. An array literal `[e1, e2, ..., eN]` and a repeat literal `[expr; N]`, defined in the clause on expressions, are expressions of type `[T; N]`.

### Constraints

An array type `[T; N]` whose `N * T'size`, computed as an exact operation over the non-negative integers, exceeds the greatest value representable by `uaddr` shall not appear. Such a violation, where not detected during translation, can cause indeterminate state.

## 4.8 Tuple types

### Syntax

```
tuple_type = '.', ws, '{', ws, type, ws, { ',', ws, type, ws },
             [ ',', ws ], '}' ;
```

The `tuple_literal` production is defined in the clause on expressions.

### Static semantics

Tuples are built-in anonymous structs with positional fields. Both the literal form and the type form use `.{ ... }`. Tuples are the return type of widening arithmetic (`+@`): `a +@ b` returns `.{T, T}`.

Tuple fields are named by their zero-based index in declaration order. Field access uses the dot operator followed by the index literal: `.0`, `.1`, `.2`, …

### Constraints

A tuple field index shall be a non-negative integer literal within the range `[0, N)`, where `N` is the number of fields.

### Examples (informative)

```
// pair: .{si4, verdict.[void, void]}
let pair = .{ 42~si4, verdict.[void, void]::Pass(void) };
// triple: .{si4, fe11s52, verdict.[void, void]}
let triple = .{ 1~si4, 2.0~fe11s52,
                verdict.[void, void]::Fail(void) };
pair.0 // 42
pair.1 // verdict::Pass(void)
```

## 4.9 References

### Static semantics

A reference type is composed from a family and a sequence of modifiers. The families, the modifiers, the set of valid combinations, modifier placement, derivation rules, and atomic operations are defined in the clause on references and resource management.

The stored representation of a reference type whose referent type is neither `[U]` nor `dyn Protocol` is implementation defined. Storing a value of a reference type yields a Γ sequence that the interpretation maps to the value; which such Γ sequence is implementation defined.

## 4.10 Subroutine pointer types

### Syntax

```
subroutine_pointer_type = subroutine_ptr_header, ws,
                          subroutine_proto_param,
                          [ ws, subroutine_return ] ;

subroutine_ptr_header   = [ extern_clause, ws ], [ "variadic", ws ],
                          "fn", [ ws, generic_clause ] ;
```

The `subroutine_return` and `extern_clause` productions are defined in the clause on declarations.

### Static semantics

A subroutine pointer designates a subroutine. An expression naming a subroutine yields a value of the subroutine pointer type formed from the subroutine’s invocation interface, variadic status, generic parameters, parameter types, and return type. Its size is `(%void)'size`. The permitted conversions involving subroutine pointers are defined in the clause on expressions. The optional return-type position admits either a type or `!`; the latter indicates that a subroutine of this type does not return control to its invoker, with consequences defined in the subclause on control transfers and diverging expressions.

Parameter names in a subroutine pointer type follow the rules defined in the subclause on subroutine declarations.

A subroutine pointer type may carry an `extern` clause, a `variadic` keyword, and a `generic_clause` as prefixes. The `extern` clause selects the invocation interface; the `variadic` keyword selects the variadic variant of the interface. In type position, the `extern` clause denotes the invocation interface only. The preservation and name-stability effects that `extern` carries on subroutine declarations, as defined in the clause on declarations, do not apply to subroutine pointer types.

A subroutine pointer type with a `generic_clause` designates a subroutine whose signature is lowered according to the rules defined in the subclause on signature lowering for `extern` generic subroutines. At each invocation site through such a subroutine pointer, the invoker supplies the concrete type arguments and the corresponding bound descriptors as zone 3 parameters.

The invocation interface determines type identity. `extern` without a parenthesized identifier, `extern(native)`, and the absence of an `extern` clause all denote the `native` invocation interface, and the three spellings yield the same type.

Two subroutine pointer types are the same type where their invocation interface, their variadic status, and their generic parameters and bounds are the same.

### Examples (informative)

```
fn(si4) -> si4                // native (implicit)
extern fn(si4) -> si4         // native (explicit, identifier omitted)
extern(native) fn(si4) -> si4 // native (explicit, identifier present)
```

## 4.11 Composite type representation

This subclause applies Kurt standard alignment, defined in the clause on semantics, to composite types, and defines the clauses that depart from it.

### Syntax

```
repr_clause    = 'repr', ws, '(', ws, repr_arg, ws, ')' ;
repr_arg       = pack_scheme | identifier ;
pack_scheme    = 'pack', ws, '(', ws, integer_literal, ws, ')' ;
discrim_clause = 'discrim', ws, '(', ws, single_path, ws, ')' ;
align_clause   = 'align', ws, '(', ws, integer_literal, ws, ')' ;
```

### Static semantics

`repr` controls the layout of a composite type. On a struct, it governs the layout of the struct itself; on an enum, it governs the layout of the payload region. The argument names a layout scheme. A conforming implementation shall support at least the following schemes; additional identifiers are implementation defined.

— `pack(N)` — each field is placed at an alignment not greater than `N`.

— `native` — the native layout rules of the execution environment. The exact layout is implementation defined, but shall match the native invocation interface of the execution environment.

`discrim` controls the discriminant type of an enum. The argument is either a type satisfying `integer` or `void`. When the argument is `void`, the discriminant occupies zero cells.

### Constraints

At most one `repr(...)` may appear in a type’s `with` clause. At most one `discrim(...)` may appear in a type’s `with` clause. `discrim` shall appear only on `enum` and `contract` declarations. `repr` and `discrim` may be combined with each other and with `align(N)` in the same `with` clause.

In `pack(N)`, `N` shall be a power of two greater than zero.

`discrim(void)` shall appear only on an enum that declares at most one variant and that contains no `wild(V)` canonical value.

When the `discrim` argument satisfies `integer`, all discriminant values shall fit in the specified type.

### Implementation requirements

A conforming implementation shall support the `repr` schemes `pack` and `native` with the semantics defined above. The implementation shall document any additional `repr` identifiers it supports.

### 4.11.1 Composite type layout

#### Static semantics

The layout of a composite type is that which Kurt standard alignment, defined in the clause on semantics, gives the sequence of its field types. That sequence is:

— for a struct, its fields in declaration order;

— for a tuple, its fields in index order;

— for an enum or a contract type, the discriminant and the variant payload, as the subclause on automatic discriminant sizing defines.

Where `m_0, m_1, ..., m_n` are the fields of a composite type `S` in that order, `S'offset(m_i)` is the offset KSA assigns the field’s type, and `S'align` and `S'size` are the alignment and the size it assigns the sequence.

#### Padding semantics

Padding cells — whether implicit (inserted by KSA for alignment) or explicit (anonymous fields) — follow a two-phase model:

— At initialization — all padding cells are **zero-initialized**: a conforming implementation shall set every bit of every padding cell to zero when a struct value is constructed.

— After initialization — padding cells have the same load and store semantics as field storage.

Two struct values that differ only at padding cells hold the same field values. Their Γ sequences need not be identical.

#### Constraints

A struct type whose `S'size`, computed by the arithmetic above, exceeds the greatest value representable by `uaddr` shall not appear. Such a violation, where not detected during translation, can cause indeterminate state.

#### Design rationale (informative)

Every subsequent layout computation depends on `S'size`. Requiring its exact value to be representable by `uaddr` makes an oversized declaration a translation failure instead of admitting wrapped layout values.

### 4.11.2 Automatic discriminant sizing

#### Static semantics

These rules govern an enum and a contract type alike. The discriminant type is automatically determined by the declared variants:

— When the enum declares zero or one variants, no variant carries a `wild(V)` canonical value, no variant is assigned an explicit discriminant value, and `with discrim(T)` is not specified, the discriminant type is `void` and occupies zero cells. The enum then has exactly one discriminant value: the sole declared variant takes it where one is declared, and the implicit wild covers it where none is. The value-set requirement below does not apply to such an enum.

— Otherwise, where `with discrim(T)` is not specified, the smallest unsigned integer type that can represent all discriminant values is selected. If any discriminant value is negative, the smallest signed integer type is selected instead.

— If `with discrim(T)` is specified, the discriminant type is fixed to `T`.

The discriminant is placed at offset 0 of the enum representation. Each variant payload follows the discriminant, aligned to `payload_type'align`. The alignment of the enum is the greatest of the discriminant’s alignment and the alignments of all variant payloads. The total size of the enum is the least multiple of `enum'align` not less than the size of the discriminant plus the greatest of zero and the sizes of all variant payloads. Padding between the discriminant and payload, and trailing padding, follow KSA rules.

The automatically selected discriminant type shall have a value set, evaluated under `cellbits::exec`, that contains all discriminant values declared by the enum.

#### Examples (informative)

These examples apply where `cellbits::exec == 8`.

```
enum empty {}                               // 0 variants
                                            // -> void discriminant
enum unit { Only }                          // 1 variant
                                            // -> void discriminant
enum colour { Red, Green, Blue }            // 3 variants
                                            // -> ui1 discriminant
enum big_enum { ... }                       // 300 variants
                                            // -> ui2 discriminant
enum year_tag { Y2006 = 2006 }              // value 2006
                                            // -> ui2 discriminant
enum offset { Neg = -19700101 }             // negative
                                            // -> si4 discriminant
enum forced { A, B } with discrim(ui4);     // forced to ui4
enum error { A = -1972 } with discrim(ui1); // translation failure
enum bad { A, B } with discrim(void);       // translation failure
```

### 4.11.3 `with repr(pack(N))`

#### Static semantics

Under `with repr(pack(N))`, the alignment Kurt standard alignment uses for each field of the struct is the lesser of the field type’s alignment and `N`, in place of that alignment. An access to a field placed at an alignment less than that of its type can be performed by more than one instruction.

### 4.11.4 `with align(N)`

#### Static semantics

`with align(N)` sets the minimum alignment of a type to `N` cells. The alignment of a type that carries `align(N)` is the greater of `N` and the alignment the type would have were the clause absent, and the type’s size is rounded up to a multiple of the alignment.

#### Constraints

`N` shall be a power of two greater than zero.

#### Examples (informative)

```
struct packet {
    header: ui4,
    seq: ui4,
    payload: &[ui1]
} with {
    repr(pack(1)),
    align(4)
}
```

### 4.11.5 `with variadic`

#### Static semantics

A struct declared `with variadic` serves as the state object for variadic argument iteration. `with variadic` makes the type uncopyable, and the implementation supplies the destructor of the type.

#### Constraints

The size of a `with variadic` type shall equal the size of the native variadic state object of the execution environment.

A `with` clause shall not combine `variadic` with `repr` or `destruct`.

#### Implementation defined

The internal fields, the iteration interface, and the argument promotion rules of each `with variadic` type are implementation defined.

#### Examples (informative)

```
// AArch64 AAPCS64 — type definition
struct va_list {
    pub airside __stack:   %void,
    pub airside __gr_top:  %void,
    pub airside __vr_top:  %void,
    pub airside __gr_offs: si4,
    pub airside __vr_offs: si4,
} with variadic;

// AArch64 AAPCS64 — iteration impl
impl va_list {
    pub airside fn next_int.[T: integer]($self) -> T {
        if self.__gr_offs < 0 {
            let offs = self.__gr_offs;
            self.__gr_offs = offs + 8;
            if offs + 8 <= 0 {
                let addr = self.__gr_top as uaddr + offs as uaddr;
                return *(addr as %ui8) as T;
            }
        }

        let addr = self.__stack;
        self.__stack = ((addr as uaddr) + 8) as %void;
        return *(addr as %T);
    }

    pub airside fn copy(&self) -> selftype {
        return *(self as %selftype);
    }
}
```

## 4.12 Type inference and the inferred type `?`

### Syntax

```
inferred_type = '?' ;
```

### Static semantics

The token `?` in a type position is an **inferred type**. It is replaced by the resolved type for all subsequent analysis. A declaration whose type annotation is `?` is equivalent to the same declaration with the annotation omitted.

The type of a construct is determined by **synthesis** or by **checking**. Synthesis derives the type from the construct itself. Checking adopts an **expected type** supplied by a constraining construct — a type annotation, a parameter type, a return type, an operator’s typing relation, a use site of the binding, or the expected type of an enclosing expression.

If synthesis and checking both determine a type and agree, or if exactly one determines a type, the construct has the type. If neither determines a type, the construct has the default type defined for its form, and where its form defines none, the construct shall not appear. If they conflict, the construct shall not appear.

Where the following operand of a shift is undetermined, it is supplied `uiN` for a leading `uiN` or `siN`, and `uaddr` for a leading `uaddr` or `saddr`.

An omitted generic type argument is determined by unification of the synthesized argument types against the parameter types of the signature. A type argument not determined by unification shall be supplied explicitly.

### Constraints

An inferred type `?` shall not appear in a subroutine parameter type, a subroutine return type, a field type, an array element type, a tuple field type, or a type alias definition.

### Examples (informative)

```
let n = 42;      // neither synthesis nor checking — default saddr
let m: si4 = 42; // checking — literal takes si4

// checking propagates into the payload; F is fixed by the annotation
let v: verdict.[si4, si4] = verdict::Pass(42);

// unification: T resolved from the argument type, no explicit
// argument needed
let r = identity(m); // identity.[T](x: T) -> T  =>  T = si4

// T appears only in the return type — explicit argument mandatory
let d = default_value.[si4]();

// expected type propagates to both branches
let w: colour = if cond then colour::Red else colour::Green;

// operator operand — the unconstrained operand takes the type of
// the other operand
let big: uaddr = 4096;
let half = big / 2; // 2 takes uaddr
let ok = 100 < big; // 100 takes uaddr
let sh = big >> 4;  // 4 takes uaddr — primitive, same width

// the expected type reaches the shift through its leading operand
let mask: ui4 = 1 << 5; // 1 takes ui4; 5 takes ui4

// use-site resolution — i takes uaddr from a.len and a.ptr
fn f(a: &[ui1]) {
    let mut i = 0;           // default would be saddr
    while a.len > i {        // a.len is uaddr → i is uaddr
        consume(a.ptr + i);  // confirms uaddr
    } then { i += 1; }
}
```
