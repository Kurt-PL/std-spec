# 4. Types

This clause defines the built-in types of the Kurt programming language: their classifications, representations, value sets, and properties.

## 4.1 Type classification

### Syntax

```
type = single_path
     | array_type
     | anon_struct_type
     | ref_type
     | slice_reference
     | subroutine_pointer_type
     | protocol_type
     | inferred_type ;
```

`single_path` is defined in the clause on expressions. `ref_type` and `slice_reference` are defined in the clause on references and resource management. `protocol_type` is defined in the clause on protocols and implementations.

### Static semantics

The types of the Kurt programming language are partitioned as follows.

**Built-in types** are types whose existence, representation, and operator semantics are defined by this specification.

**Declared types** are types introduced by `struct`, `enum`, and `contract` declarations in the programme. Their declaration syntax is defined in the clause on declarations and in the clause on statements and control flow.

A declaration whose identifier is the name of a built-in type hides the built-in name within its scope.

### Implementation requirements

A conforming implementation shall not realize a built-in type by introducing a declaration or any other source text into the programme.

## 4.2 Size and alignment

### Static semantics

The following values are parameters of a machine in the Kurt type system:

<table>
<thead><tr><th>Parameter</th><th>Meaning</th><th>Constraint</th></tr></thead>
<tbody>
<tr><td>Cell width</td><td>Bits per cell</td><td>&gt; 0</td></tr>
<tr><td>Address width</td><td>Bit width of <code>uaddr</code> and <code>saddr</code></td><td>Defined by the environment of the machine</td></tr>
<tr><td>Reference width</td><td>Bit width of <code>%void</code> and of subroutine pointers</td><td>Defined by the environment of the machine; shall be at least the address width</td></tr>
</tbody>
</table>

For every type with non-zero size, `T'align` is a power of two and divides `T'size`. A type whose size is zero has alignment zero unless a `with` clause fixes its alignment.

For a closed type satisfying `numeric`, a reference type that is not wide, and a subroutine pointer type, `T'align == T'size`, and the size derives from the type’s **bit width** *W*<sub>t</sub>:

`T'size` = 2<sup><span class="ceil">⌈&thinsp;log<sub>2</sub> <span class="ceil">⌈&thinsp;*W*<sub>t</sub> / `cellbits`&thinsp;⌉</span>&thinsp;⌉</span></sup>

Where `T'size` × `cellbits` is greater than *W*<sub>t</sub>, the interpretation of the type takes each value from *W*<sub>t</sub> bits alone, and maps 2<sup>`T'size` × `cellbits` &minus; *W*<sub>t</sub></sup> Γ sequences to each value of the type.

For a closed type satisfying `numeric`, *W*<sub>t</sub> is the width defined in the subclause on integer types or the subclause on floating radix point number types. For a reference type that is not wide, and for a subroutine pointer type, *W*<sub>t</sub> is the reference width.

### Implementation requirements

A conforming implementation shall document the values of all three parameters for each supported environment of the programme machine and of the translation machine. The number of cells of the τ of each machine is two raised to its address width. The reference width shall be sufficient for a subroutine pointer to designate each subroutine of the programme in that environment.

### Implementation defined

Which of the Γ sequences that represent a value a store places, where `T'size` × `cellbits` is greater than the bit width of the type, is implementation defined.

### Design rationale (informative)

An alignment greater than a value requires is sound in every environment, and none requires more than the number of cells the value occupies. `T'align == T'size` is therefore sound everywhere without this specification determining the requirement of each environment. `pack(N)` relinquishes the resulting padding cells where the programme states its target’s requirement.

The suffix numeral of an integer type name denotes a power-of-two multiple of `cellbits`, and each floating radix point number type has a bit width that is a power of two, so <span class="ceil">⌈&thinsp;*W*<sub>t</sub> / `cellbits`&thinsp;⌉</span> is a power of two whenever `cellbits` divides *W*<sub>t</sub>. Rounding `T'size` up to a power of two keeps the alignment rule satisfied in every machine, including one whose cell width does not divide *W*<sub>t</sub> &mdash; for example a floating radix point number type or an address-width integer under a cell width that is not a power-of-two divisor of *W*<sub>t</sub>.

## 4.3 Integer types

### Static semantics

An **unsigned** integer type uses pure binary encoding. The value of a *W*<sub>t</sub>-bit unsigned integer with bits *b*<sub>*W*<sub>t</sub>&minus;1</sub>, …, *b*<sub>0</sub> is <span class="sum">Σ<sub>*k*=0</sub><sup>*W*<sub>t</sub>&minus;1</sup></span> *b*<sub>*k*</sub> × 2<sup>*k*</sup>.

A **signed** integer type uses two’s complement encoding. The value of a *W*<sub>t</sub>-bit signed integer with bits *b*<sub>*W*<sub>t</sub>&minus;1</sub>, …, *b*<sub>0</sub> is &minus;*b*<sub>*W*<sub>t</sub>&minus;1</sub> × 2<sup>*W*<sub>t</sub>&minus;1</sup> + <span class="sum">Σ<sub>*k*=0</sub><sup>*W*<sub>t</sub>&minus;2</sup></span> *b*<sub>*k*</sub> × 2<sup>*k*</sup>. Bit *W*<sub>t</sub>&minus;1 is the **sign bit**.

### 4.3.1 Cell width

#### Syntax

```
cellbits_expr = "cellbits", [ '::', ( 'prog' | "xlat" | "const" ) ] ;
```

#### Static semantics

Under the rules for type inference, synthesis of a `cellbits` expression is undetermined. Its default type is `uaddr`.

`cellbits` permits three **qualified forms**.

`cellbits::prog` evaluates to the cell width of the programme machine, `cellbits::xlat` to that of the translation machine, and `cellbits::const` to that of the constant machine.

The unqualified `cellbits` evaluates to the cell width of the machine on which the evaluation takes place.

The value sets of the integer types other than `uaddr` and `saddr` in an evaluation are determined by the value to which the unqualified `cellbits` evaluates in that evaluation.

#### Constraints

The value of a `cellbits` expression shall fit in its type.

#### Examples (informative)

Where `cellbits == 8`, `ui1` is 8-bit and `ui4` is 32-bit. Where `cellbits == 16`, `ui1` is 16-bit and `ui4` is 64-bit.

## 4.4 Floating radix point number types

Arithmetic on a floating radix point number type conforms to ISO/IEC 60559:2020 where this clause does not state otherwise.

A **floating radix point number type** divides its *W*<sub>t</sub> bits into three adjacent fields, from the position of greatest weight to the position of least weight: the **sign field**, of one bit; the **exponent field**; and the **significand field**. A value of such a type is a **floating radix point number**.

### 4.4.3 Comparison

#### Dynamic semantics

The comparison operators `==`, `!=`, `<`, `>`, `<=`, `>=` on a floating radix point number type compare by the order that the ISO/IEC 60559:2020 total order predicate defines. `a == b` holds if and only if `a` and `b` occupy the same position in this order. `a != b` holds if and only if `a == b` does not hold. `a < b` holds if and only if `a` precedes `b` in this order. `a > b` holds if and only if `b` precedes `a`. `a <= b` holds if and only if `a < b` or `a == b`. `a >= b` holds if and only if `a > b` or `a == b`.

### 4.4.4 NaN propagation

#### Dynamic semantics

A signalling NaN operand of `+`, `-`, `*`, `/`, or `%` is treated as a quiet NaN with the same sign for the purpose of the rules below.

Where `+`, `-`, `*`, `/`, or `%` yields NaN, the result is a quiet NaN with payload 0. For `*`, `/`, and `%` its sign is the XOR of the operands’ signs. For `+` and `-` its sign is that of the leading operand, except where the following operand alone is NaN. There it is the sign of the following operand, negated where the operator is `-`.

#### Implementation requirements

Where the implementation defines no behaviour upon a signalling NaN operand of an arithmetic operation, the operand’s presence shall alter no control flow.

The presence of a signalling NaN operand in a comparison or in a conversion by `as` shall alter no control flow and shall invoke no `trap`.

#### Implementation defined

The implementation’s behaviour upon a signalling NaN operand of an arithmetic operation, other than the arithmetic result, is implementation defined and may include invoking `trap`.

### 4.4.5 Special operations

#### Dynamic semantics

A result whose magnitude is too large or too small for the type, and the result of a division whose divisor is zero, follow ISO/IEC 60559:2020 under the rounding mode.

## 4.5 `void`

### Static semantics

`void` has size zero. It is in unit form, and its sole value is written `void`.

## 4.6 Built-in contract type

### Static semantics

`verdict[T, F]` is the built-in contract type, generic over a success payload type `T` and a failure payload type `F`.

`verdict[T, F]` has exactly two variants, each in unnamed-field form with one field. `Pass`, the success variant, has a field of type `T` and takes the discriminant value 1. `Fail`, the failure variant, has a field of type `F`, covers every other discriminant value, and bears the canonical value 0, as defined in the clause on declarations. The discriminant type is `ui1`. `verdict[T, F]` is a contract type with the inverted pair `verdict[F, T]`, as defined in the clause on statements and control flow.

### Examples (informative)

```
// The conventional truth-value vocabulary, declared in source
type bool = verdict[void, void];
const true:  bool = verdict::Pass.{ void };
const false: bool = verdict::Fail.{ void };
```

### Notes (informative)

The set of discriminant values that `wild` covers for `verdict[void, void]` is the value set of `ui1` less the value `1`.

The definition of `verdict[T, F]` is equivalent to the declaration:

```
contract verdict[T, F] {
    Pass { pub T } = 1,
    Fail { pub F } = wild(0)
} with {
    inv -> selftype[F, T],
    discrim(ui1),
    copyable
}
```

## 4.7 Array types

`[T; N]` is an **array** of length `N`.

### Syntax

```
array_type = '[', ws, type, ws, ';', ws, expression, ws, ']' ;
```

### Static semantics

`N` is an expression of type `uaddr`. The layout is `N` contiguous values of `T`, and `[T; N]'size == N * T'size`. Where `N * T'size` is not zero, `[T; N]'align == T'align`.

The clause on references and resource management defines the decay of a reference to `[T; N]` to the corresponding slice reference. It also defines the built-in fields `.ptr` and `.len` that a `[T; N]` value and references to it expose.

### Constraints

An array type `[T; N]` whose `N * T'size`, computed over the non-negative integers without wrapping, exceeds the greatest value representable by `uaddr` shall not appear. Such a violation, where not detected during translation, can cause indeterminate state.

## 4.8 Anonymous struct types

### Syntax

```
anon_struct_type = '.', ws, '{', ws, type, ws, { ',', ws, type, ws },
                   [ ',', ws ], '}' ;
```

### Static semantics

An **anonymous struct type** is a built-in type whose fields are named by their index in declaration order, counting from zero.

## 4.9 References

### Static semantics

A reference type is composed from a tribe and a sequence of modifiers. The tribes, the modifiers, the set of valid combinations, modifier placement, and derivation rules are defined in the clause on references and resource management.

The stored representation of a reference type whose referent type is `[U]` is defined in the clause on references and resource management, and of one whose referent type is a protocol type in the clause on protocols and implementations. For every other referent type the stored representation is one field of the reference width, and the subclause on size and alignment gives the size and the alignment.

### Implementation defined

What the field of a reference carries besides the address is implementation defined.

## 4.10 Subroutine pointer types

### Syntax

```
subroutine_pointer_type = subroutine_ptr_header, ws,
                          subroutine_proto_param,
                          [ ws, subroutine_return ],
                          [ ws, routes_clause ],
                          [ ws, with_single | ws, with_curly ] ;

subroutine_ptr_header   = [ extern_clause, ws ], [ "variadic", ws ],
                          [ "airside", ws ], "fn",
                          [ ws, generic_clause ] ;
```

The `subroutine_return` and `extern_clause` productions are defined in the clause on declarations.

### Static semantics

A subroutine pointer designates a subroutine. An expression naming a subroutine, or ending in a generic argument list after an expression, yields a value of the subroutine pointer type formed from the invocation interface, variadic status, airside status, generic parameters, parameter types, return type or `!`, subject bounds, and routes of the subroutine it names or of the instantiation. The permitted conversions involving subroutine pointers are defined in the clause on expressions. A subroutine of a type whose return is `!` does not return control to its invoker, with consequences defined in the subclause on control transfers and diverging expressions.

In a type, the `extern` clause names the invocation interface, the `variadic` keyword selects the variadic variant of that interface, and the `airside` keyword states that the subroutine is declared `airside` or within a `#dyn` block. The effects each prefix has upon a declaration, and the invocation interface of a subroutine that carries no `extern` clause, are defined in the clause on declarations.

A subroutine pointer type with a `generic_clause` or a subject bound designates a subroutine whose signature is lowered according to the rules defined in the subclause on signature lowering.

A `routes` clause or `with` clause belongs to the outermost subroutine declaration or subroutine pointer type whose return type it follows.

Two subroutine pointer types are the same type where they have the same routes and agree in each of the following:

&mdash; The invocation interface.

&mdash; The variadic status.

&mdash; The airside status.

&mdash; The generic parameters, and the bound elements of each, in order.

&mdash; The parameter types.

&mdash; The return type or `!`.

&mdash; The subject bounds, in order.

In this comparison, the generic parameters of the two at the same position are taken to be the same generic parameter where both are type parameters or both are dependence parameters of the same type.

### Constraints

The `with` clause of a subroutine pointer type shall contain only subject bounds. A subroutine pointer type in a type position shall be a closed type. An expression that ends in a generic argument list instantiating a subroutine, or that names an associated subroutine whose lowered signature carries a `selftype` level or the generic parameters of an enclosing declaration, shall appear only as the leading expression of a subroutine invocation.

### Design rationale (informative)

The type of a subroutine pointer alone fixes how the designated subroutine is invoked, and a generic parameter occurring free in that type would leave the invocation varying with a type argument that the subroutine has no means to receive.

### Examples (informative)

```
fn(si4) -> si4                // native (implicit)
extern fn(si4) -> si4         // native (explicit, identifier omitted)
extern(native) fn(si4) -> si4 // native (explicit, identifier present)
```

## 4.11 Composite type representation

### Syntax

```
repr_clause    = 'repr', ws, '(', ws, repr_arg, ws, ')' ;
repr_arg       = pack_scheme | identifier ;
pack_scheme    = 'pack', ws, '(', ws, integer_literal, ws, ')' ;
discrim_clause = 'discrim', ws, '(', ws, single_path, ws, ')' ;
align_clause   = 'align', ws, '(', ws, integer_literal, ws, ')' ;
```

### Static semantics

`repr` governs the placement of the fields of a struct, and of the fields of each variant of a variant type. The argument names a layout scheme:

&mdash; `pack(N)` &mdash; each field is placed at the alignment the subclause on `with repr(pack(N))` gives it.

&mdash; `native` &mdash; in an evaluation, the layout that the machine on which the evaluation takes place gives the type.

### Constraints

The `discrim` argument shall be a closed type satisfying `integer`, or `void`.

In `pack(N)`, `N` shall be a power of two greater than zero.

A `repr` identifier not among those the implementation documents shall not appear.

`discrim(void)` shall appear only on a variant type whose discriminant type would be `void` were the `with` clause absent.

Where the `discrim` argument satisfies `integer`, all discriminant values shall fit in the specified type.

### Implementation requirements

A conforming implementation shall support the `repr` schemes `pack` and `native`.

### Implementation defined

The layout `repr(native)` gives, and any further `repr` identifier and the layout it names, are implementation defined.

### 4.11.1 Composite type layout

#### Static semantics

The layout of a composite type is that which Kurt standard alignment, defined in the clause on semantics, gives a sequence of types. That sequence is:

&mdash; For a struct, the types of its fields in declaration order.

&mdash; For an anonymous struct type, the types of its fields in index order.

&mdash; For a variant type, its discriminant type, followed by the type that the subclause on automatic discriminant sizing defines for the fields of its variants.

A struct or an anonymous struct type places each of its fields, and a variant type its discriminant, at the offset Kurt standard alignment assigns the type at the same position in that sequence. For a composite type `S`, `S'align` and `S'size` are the alignment and the size Kurt standard alignment assigns that sequence.

After construction, a padding cell of a value has the load and store semantics that the type of the value gives every other cell of its representation.

Two values of one composite type that differ only at their padding cells hold and carry the same values.

#### Constraints

A composite type whose `S'size`, computed by the arithmetic above, exceeds the greatest value representable by `uaddr` shall not appear. Such a violation, where not detected during translation, can cause indeterminate state.

Determining the layout of a type shall not require, directly or indirectly, the layout of that type, nor, where that type is the type a generic declaration declares, the layout of a type that instantiates that declaration. For this rule:

&mdash; The layout of a composite type requires the layouts of its constituents and of the types of its fields, as the clause on references and resource management defines constituents.

&mdash; The layout of an array type requires the layout of its element type and what its length expression requires.

&mdash; An expression requires the layout of each type whose size, alignment, or offsets are used by an evaluation of a construct within the expression or within an expression its evaluation reaches.

&mdash; The layout of a reference type or of a subroutine pointer type requires nothing.

#### Implementation requirements

A conforming implementation shall set every bit of every padding cell to zero when a value of a composite type is constructed.

### 4.11.2 Automatic discriminant sizing

#### Static semantics

On each machine on which the declaration of a variant type is analysed, its **discriminant type** is determined by the first of the following that applies:

1. Where `with discrim(T)` is specified, the discriminant type is fixed to `T`.
2. Where the type declares zero or one variants, no variant carries a `wild(V)` canonical value, and no variant is assigned an explicit discriminant value, the discriminant type is `void`.
3. The unsigned integer type of least bit width that can represent all discriminant values under the cell width of that machine is selected. If any discriminant value is negative, the signed integer type of least bit width that can so represent them is selected instead. Of two such types of equal bit width, the one other than `uaddr` or `saddr` is selected.

A variant type whose discriminant type is `void` has exactly one discriminant value, and that value is zero. The sole declared variant takes it where one is declared, and the implicit wild variant covers it where none is.

The variant type places the fields of each variant where a struct of the same fields and the same `repr` places them, advanced by the offset Kurt standard alignment assigns the type that follows the discriminant type in the sequence the subclause on composite type layout gives the variant type. The alignment of that type is the greatest of zero and the alignments of those structs, and its size is the greatest of zero and the sizes of those structs, rounded up to a multiple of that alignment.

#### Constraints

A variant type whose discriminant values no integer type can represent under the cell width of a machine on which its declaration is analysed shall not appear.

#### Examples (informative)

These examples apply where `cellbits::prog == 8`.

```
// 1 variant → void discriminant
enum unit { only }
// 3 variants → ui1 discriminant
enum colour { red, green, blue }
// value 2006 → ui2 discriminant
enum year_tag { y2006 = 2006 }
// negative → si4 discriminant
enum offset { neg = -19700101 }
// forced to ui4
enum forced { lo, hi } with discrim(ui4);

// translation failure
// enum error { lo = -72 } with discrim(ui1);
// enum bad { lo, hi } with discrim(void);
```

### 4.11.3 `with repr(pack(N))`

#### Static semantics

Under `with repr(pack(N))`, the alignment Kurt standard alignment uses for each field whose placement `repr` governs is the lesser of the field type’s alignment and `N`.

### 4.11.4 `with align(N)`

#### Static semantics

The alignment of a type that carries `align(N)` is the greater of `N` and the alignment the type would have were the clause absent, and the type’s size is rounded up to a multiple of the alignment.

#### Constraints

`N` shall be a power of two greater than zero.

#### Examples (informative)

```
struct packet {
    header: ui4,
    seq: ui4,
    payload: &[ui1]
} with {
    repr(pack(1)),
    align(4)
}
```

### 4.11.5 `with variadic`

#### Static semantics

A struct declared `with variadic` serves as the state object for variadic argument iteration, and the implementation supplies the destructor of the type.

#### Constraints

The size of a `with variadic` type in an evaluation shall equal the size of the native variadic state object of the machine on which the evaluation takes place.

#### Implementation defined

For each machine, the layout of its native variadic state object, the means by which a `with variadic` type reaches the arguments it holds, and the conversions a variadic argument undergoes on it are implementation defined.

#### Examples (informative)

```
// AArch64 AAPCS64: type definition
struct va_list {
    pub airside __stack:   %void,
    pub airside __gr_top:  %void,
    pub airside __vr_top:  %void,
    pub airside __gr_offs: si4,
    pub airside __vr_offs: si4,
} with variadic;

// AArch64 AAPCS64: iteration impl
impl va_list {
    pub airside fn next_int[T: integer]($self) -> T {
        if self.__gr_offs < 0 {
            let offs = self.__gr_offs;
            self.__gr_offs = offs + 8;
            if offs + 8 <= 0 {
                let addr = self.__gr_top as uaddr + offs as uaddr;
                return *(addr as %ui8) as T;
            }
        }

        let addr = self.__stack;
        self.__stack = ((addr as uaddr) + 8) as %void;
        return *(addr as %T);
    }

    pub airside fn copy(&self) -> selftype {
        return *(self as %selftype);
    }
}
```

## 4.12 Type inference and the inferred type `?`

### Syntax

```
inferred_type = '?' ;
```

### Static semantics

The token `?` in a type position is an **inferred type**. It is replaced by the resolved type for the rest of semantic analysis. A declaration whose type annotation is `?` is equivalent to the same declaration with the annotation omitted. A declaration whose type annotation is omitted has the type the rules of this subclause determine for its initializer or expression.

The type of a construct is determined by **synthesis** or by **checking**. Synthesis derives the type from the construct itself. Checking adopts an **expected type** supplied by a constraining construct, which is one of the following:

&mdash; A type annotation.

&mdash; A parameter type.

&mdash; A return type.

&mdash; The type that an associated constant a protocol `impl` block provides shall bear.

&mdash; An operation.

&mdash; A use site of the name that the construct’s declaration introduces.

&mdash; The expected type of an enclosing expression.

&mdash; The matched type of a literal pattern or a range pattern, for the literal of each `literal_pat` that is or is within that pattern.

Where more than one constraining construct applies, checking determines the type on which those that determine one agree, and determines none where none of them determines one. Where those that determine a type do not all determine the same one, the construct shall not appear.

If synthesis and checking both determine a type and the one synthesis determines is assignable to the one checking determines, the construct has the one checking determines. If exactly one determines a type, the construct has that type. If neither determines a type, the construct has the default type defined for its form, and where its form defines none, the construct shall not appear. Otherwise, the construct shall not appear.

The **common type** of a set of expressions is the one type that each of them has, disregarding those that are control transfers or diverging expressions, as the clause on statements and control flow defines them. Where the set is not empty and each of them is so disregarded, the requirement of a common type is met, synthesis of that common type is undetermined, and its default type is `void`.

Where the rules of an operation, a cast included, admit exactly one type that an undetermined operand can have, given the types determined for its other operands and for its result, that type is the expected type of the operand.

An omitted generic type argument is determined by matching each parameter type of the signature against the synthesized type of its argument: where a type parameter stands at a position of the parameter type, the type at that position of the argument type, where the two types are of the same form at every enclosing position, determines it. Where more than one position determines a type argument, they shall determine the same one. A type argument that no parameter type so determines shall be supplied explicitly.

### Constraints

An inferred type `?` shall not appear in a subroutine parameter type, a subroutine return type, a field type, an array element type, or a type alias definition.

### Examples (informative)

```
let n = 42;      // neither synthesis nor checking: default saddr
let m: si4 = 42; // checking: literal takes si4

// checking propagates into the field. F is fixed by the annotation.
let v: verdict[si4, si4] = verdict::Pass.{ 42 };

// T determined by matching the parameter type, no explicit
// argument needed
let r = identity(m); // identity[T](x: T) -> T  →  T = si4

// T appears only in the return type: explicit argument mandatory
let d = default_value[si4]();

// expected type propagates to both branches
let w: colour = if cond then colour::red else colour::green;

// operator operand: the unconstrained operand takes the type of
// the other operand
let big: uaddr = 4096;
let half = big / 2; // 2 takes uaddr

// the expected type reaches both operands of the shift
// through its result
let mask: ui4 = 1 << 5; // 1 and 5 both take ui4

// use-site resolution: i takes uaddr from a.len and a.ptr
fn f(a: &[ui1]) {
    let mut i = 0;           // default would be saddr
    while a.len > i {        // a.len is uaddr → i is uaddr
        consume(a.ptr + i);  // confirms uaddr
    } and then { i += 1; }
}
```
