# §4. Types

This clause defines the built-in types of the Kurt programming language: their classifications, representations, value sets, and properties.

## 4.1 Type classification

### Syntax

```
type = single_path
     | "selftype"
     | array_type
     | tuple_type
     | ref_type
     | slice_reference
     | subroutine_pointer_type
     | protocol_object_type
     | inferred_type ;
```

`single_path` is defined in the clause on expressions. In a type position it names a built-in type, a declared type, or an instantiation of one. (e.g. `vec.[si4]`, `map.[&[ui1], vec.[vec.[si4]]]`.) `array_type`, `tuple_type`, `subroutine_pointer_type`, and `inferred_type` are defined below. `ref_type` and `slice_reference` are defined in the clause on references and resource management. `protocol_object_type` and `selftype` are defined in the clause on protocols and implementations.

### Static semantics

The types of the Kurt programming language are partitioned as follows.

**Built-in types** are types whose existence, representation, and operator semantics are defined normatively by this specification. Among them are the integer types, the floating radix point number types, and the reference types. The size and alignment of a built-in type follow from the parameters of the execution environment given in the subclause on size and alignment.

**Declared types** are types introduced by `struct`, `enum`, `contract`, and `type` alias declarations in the programme. Their declaration syntax is defined in the clause on declarations and in the clause on statements and control flow.

A declaration whose identifier is the name of a built-in type hides the built-in name within its scope.

### Implementation requirements

A conforming implementation shall know every built-in type directly. It shall not realize a built-in type by introducing a declaration or any other source text into the programme.

## 4.2 Size and alignment

### Static semantics

Every object occupies an integer number of cells, as defined in the clause on semantics. Every address identifies a particular cell.

The following values are the only parameters of the execution environment in the Kurt type system. All other type widths and alignments are derived from these values:

<table>
<thead><tr><th>Parameter</th><th>Meaning</th><th>Constraint</th></tr></thead>
<tbody>
<tr><td><code>cellbits</code></td><td>Bits per cell</td><td>&gt; 0</td></tr>
<tr><td>Address width</td><td>Bit width of <code>uaddr</code> and <code>saddr</code></td><td>Defined by the execution environment</td></tr>
<tr><td>Reference width</td><td>Bit width of <code>%void</code> and of subroutine pointers</td><td>Defined by the execution environment; shall be at least the address width</td></tr>
</tbody>
</table>

For every type with non-zero size, `T'align` is a power of two and divides `T'size`. A type whose size is zero has alignment zero unless a `with` clause fixes its alignment otherwise.

For a type satisfying `numeric`, a reference type that is not wide, and the subroutine pointer type, `T'align == T'size`, and the size derives from the type’s **bit width** *W*<sub>t</sub>:

`T'size` = 2<sup><span class="ceil">⌈&thinsp;log<sub>2</sub> <span class="ceil">⌈&thinsp;*W*<sub>t</sub> / `cellbits`&thinsp;⌉</span>&thinsp;⌉</span></sup>

Where `T'size` × `cellbits` is greater than *W*<sub>t</sub>, the interpretation of the type takes each value from *W*<sub>t</sub> bits alone, and maps 2<sup>`T'size` × `cellbits` − *W*<sub>t</sub></sup> Γ sequences to each value of the type. Which of them a store places is implementation defined.

For a type satisfying `numeric`, *W*<sub>t</sub> is the width defined in the subclause on integer types or the subclause on floating radix point number types. For a reference type that is not wide, and for the subroutine pointer type, *W*<sub>t</sub> is the reference width.

The size and alignment of an array are defined in the subclause on array types. The size and alignment of a tuple, a struct, or a variant type are defined in the subclause on composite type representation.

### Implementation requirements

A conforming implementation shall document the values of all three parameters for each supported execution environment. The address width shall be sufficient to address the entire address space of the execution environment.

### Design rationale (informative)

An alignment greater than a value requires is sound in every execution environment, and none requires more than the number of cells the value occupies. `T'align == T'size` is therefore sound everywhere without this specification determining the requirement of each environment. `pack(N)` relinquishes the resulting padding where the programme states its target’s requirement.

An integer type name denotes a power-of-two multiple of `cellbits`, and each floating radix point number type has a bit width that is a power of two, so <span class="ceil">⌈&thinsp;*W*<sub>t</sub> / `cellbits`&thinsp;⌉</span> is a power of two whenever `cellbits` divides *W*<sub>t</sub>. Rounding `T'size` up to a power of two keeps the alignment rule satisfied in every execution environment, including one whose `cellbits` does not divide *W*<sub>t</sub> — for example a floating radix point number type or an address-width integer under a `cellbits` that is not a power-of-two divisor of *W*<sub>t</sub>.

## 4.3 Integer types

### Static semantics

An integer type represents a finite subset of the mathematical integers.

An **unsigned** integer type uses pure binary encoding over all *W*<sub>t</sub> bits. The value of a *W*<sub>t</sub>-bit unsigned integer with bits *b*<sub>*W*<sub>t</sub>−1</sub>, …, *b*<sub>0</sub> is <span class="sum">Σ<sub>*k*=0</sub><sup>*W*<sub>t</sub>−1</sup></span> *b*<sub>*k*</sub> × 2<sup>*k*</sup>.

A **signed** integer type uses two’s complement encoding. The value of a *W*<sub>t</sub>-bit signed integer with bits *b*<sub>*W*<sub>t</sub>−1</sub>, …, *b*<sub>0</sub> is −*b*<sub>*W*<sub>t</sub>−1</sub> × 2<sup>*W*<sub>t</sub>−1</sup> + <span class="sum">Σ<sub>*k*=0</sub><sup>*W*<sub>t</sub>−2</sup></span> *b*<sub>*k*</sub> × 2<sup>*k*</sup>. Bit *W*<sub>t</sub>−1 is the **sign bit** — the position of greatest weight. Where it is 1, the represented value is negative.

Bit-shift on signed integers is arithmetic shift, and the descending shift replicates the sign bit into the vacated positions of greater weight.

### 4.3.1 Cell width of the environment

#### Syntax

```
cellbits_expr = "cellbits", [ '::', ( 'exec' | "xlat" ) ] ;
```

#### Static semantics

`cellbits` is a keyword that evaluates in expression contexts to a cell width, as defined in the clause on semantics. Under the rules for type inference, synthesis of a `cellbits` expression is undetermined. Its default type is `uaddr`.

`cellbits` permits two **qualified forms**.

`cellbits::exec` evaluates to the cell width of the execution environment. `cellbits::xlat` evaluates to the cell width of the translation environment. Each qualified form evaluates to the same value in every context.

The value of the unqualified `cellbits` depends on the environment the evaluation observes:

— In an evaluation that observes the execution environment, `cellbits` evaluates to *B*<sub>e</sub>.

— In an evaluation that observes the translation environment, `cellbits` evaluates to the greater of *B*<sub>e</sub> and *B*<sub>x</sub>.

The value sets of the `uiN` and `siN` types are determined by the value to which the unqualified `cellbits` evaluates in the environment the evaluation observes. The conversion of values that cross the boundary of a translation-environment `asm` block is defined in the clause on expressions.

#### Constraints

The value of a `cellbits` expression shall fit in the inferred type, as defined in the subclause on type inference and the inferred type `?`.

#### Implementation requirements

All address arithmetic, object sizes, and alignment computations applied to the opaque code shall be consistent with `cellbits::exec`.

#### Design rationale (informative)

The greater cell width makes every value of an integer type derived from the cell width representable in both environments. The qualified forms provide an environment-specific width independently of the environment the evaluation observes.

A computation involving unsigned operands does not overflow. A result that cannot be represented by the resulting unsigned integer type is reduced modulo 2<sup>*W*<sub>t</sub></sup>. A signed result that cannot be represented is reduced modulo 2<sup>*W*<sub>t</sub></sup> and mapped to the signed value set by two’s complement interpretation.

#### Examples (informative)

#### Notes (informative)

Saturating and widening operators are available as explicit alternatives to wrapping. They are defined in the clause on expressions.

## 4.4 Floating radix point number types

Arithmetic on a floating radix point number type conforms to ISO/IEC 60559:2020 where this clause does not state otherwise.

### Static semantics

A **floating radix point number type** divides its *W*<sub>t</sub> bits into three adjacent fields, from the position of greatest weight to the position of least weight: the **sign field**, of one bit; the **exponent field**; and the **significand field**. A value of such a type is a **floating radix point number**.

Such a type is named `fe{exponent_bits}s{significand_bits}`, where the numerals are the widths of the exponent field and the significand field, and *W*<sub>t</sub> is `1 + exponent_bits + significand_bits`. All floating radix point number types satisfy `numeric` but not `integer` or `primitive`.

### 4.4.1 Rounding

#### Implementation defined

The following are implementation defined:

— the rounding mode governing the operators, conversions, and other operations of this clause.

— whether an environment provides more than one such rounding mode.

— where it does, the means by which one is selected, the scope over which a selection remains in effect, and the set reachable by it.

A conforming implementation shall document these for each supported environment.

### 4.4.3 Comparison

#### Dynamic semantics

The comparison operators `==`, `!=`, `<`, `>`, `<=`, `>=` on a floating radix point number type implement the ISO/IEC 60559:2020 total order predicate. Every floating radix point number is comparable with every other value of the same type.

The classes defined in the subclause on value classification are ordered, from least to greatest: NegQNN, NegSNN, NegInf, NegScl, NegZro, PosZro, PosScl, PosInf, PosSNN, PosQNN.

Within NegScl and PosScl, values are ordered by their numeric value. Within NegQNN and NegSNN, a value with the greater payload is the lesser. Within PosSNN and PosQNN, a value with the greater payload is the greater.

`a == b` holds if and only if `a` and `b` occupy the same position in this order. `a != b` holds if and only if `a == b` does not hold. `a < b` holds if and only if `a` precedes `b` in this order. `a > b` holds if and only if `b` precedes `a`. `a <= b` holds if and only if `a < b` or `a == b`. `a >= b` holds if and only if `a > b` or `a == b`.

#### Implementation requirements

The presence of a signalling NaN operand in a comparison shall alter no control flow and shall invoke no `trap`.

### 4.4.4 NaN propagation

#### Dynamic semantics

A signalling NaN operand of `+`, `-`, `*`, `/`, or `%` is treated as a quiet NaN with the same sign for the purpose of the rules below.

Where `+`, `-`, `*`, `/`, or `%` yields NaN, whether because an operand is NaN or as the subclause on special operations defines, the result is a quiet NaN with payload 0. For `*`, `/`, and `%` its sign is the XOR of the operands’ signs. For `+` and `-` its sign is that of the leading operand, except where the following operand alone is NaN. There it is the sign of the following operand, negated where the operator is `-`.

#### Implementation requirements

Where the implementation documents no behaviour upon a signalling NaN operand of an arithmetic operation, the operand’s presence shall alter no control flow.

The presence of a signalling NaN operand in a conversion by `as` shall alter no control flow and shall invoke no `trap`.

#### Implementation defined

The implementation’s behaviour upon a signalling NaN operand of an arithmetic operation, other than the arithmetic result, is implementation defined and may include invoking `trap`.

### 4.4.5 Special operations

#### Dynamic semantics

— `0.0 / 0.0` yields NaN.

— `x / 0.0` where `x != 0.0` yields positive or negative infinity, depending on the sign of `x`.

— Overflow yields positive or negative infinity.

— Underflow yields zero or a subnormal value, depending on the magnitude.

## 4.5 `void`

### Static semantics

`void` has size zero. It contains exactly one value, written `void`.

## 4.6 Built-in contract type

### Static semantics

`verdict.[T, F]` is the built-in contract type, generic over a success payload type `T` and a failure payload type `F`.

`verdict.[T, F]` has exactly two variants. `Pass`, the success variant, holds a payload of type `T` and takes the discriminant value 1. `Fail`, the failure variant, holds a payload of type `F`, covers every other discriminant value, and bears the canonical value 0, as defined in the clause on declarations. The discriminant type is `ui1`. `verdict.[T, F]` is a contract type with the inverted pair `verdict.[F, T]`, as defined in the clause on statements and control flow.

### Examples (informative)

```
// The conventional truth-value vocabulary, declared in source
type bool = verdict.[void, void];
const true:  bool = verdict::Pass(void);
const false: bool = verdict::Fail(void);
```

### Notes (informative)

The set of discriminant values that `wild` covers for `verdict.[void, void]` is the value set of `ui1` less the value `1`.

The definition of `verdict.[T, F]` is equivalent to the declaration:

```
contract verdict.[T, F] {
    Pass(T) = 1,
    Fail(F) = wild(0)
} with {
    inv -> selftype.[F, T],
    discrim(ui1)
}
```

## 4.7 Array types

`[T; N]` is an **array** of length `N`. Every value of the type has that length.

### Syntax

```
array_type = '[', ws, type, ws, ';', ws, expression, ws, ']' ;
```

### Static semantics

`N` is an expression of type `uaddr`. Where `N` and `T'size` are determined at translation time, so are `[T; N]'size` and every layout computation that depends on it. The layout is `N` contiguous values of `T`, and `[T; N]'size == N * T'size`. Where `N * T'size` is not zero, `[T; N]'align == T'align`.

The clause on references and resource management defines the implicit cast from a reference to `[T; N]` to the corresponding slice reference. It also defines the built-in fields `.ptr` and `.len` that a `[T; N]` value and references to it expose.

Copy, transfer, and destruction semantics of `[T; N]` follow from `T`. An array literal `[e1, e2, ..., eN]` and a repeat literal `[expr; N]`, defined in the clause on expressions, are expressions of type `[T; N]`.

### Constraints

Every value `N` requires, other than the value of a dependence parameter, shall be determined at translation time.

An array type `[T; N]` whose `N * T'size`, computed as an exact operation over the non-negative integers, exceeds the greatest value representable by `uaddr` shall not appear. Such a violation, where not detected during translation, can cause indeterminate state.

## 4.8 Tuple types

### Syntax

```
tuple_type = '.', ws, '{', ws, type, ws, { ',', ws, type, ws },
             [ ',', ws ], '}' ;
```

The `tuple_literal` production is defined in the clause on expressions.

### Static semantics

Tuples are built-in anonymous structs with positional fields.

Tuple fields are named by their index in declaration order, counting from zero. Field access uses the dot operator followed by the index literal: `.0`, `.1`, `.2`, …

### Constraints

A tuple field index shall be a non-negative integer literal within the range `[0, N)`, where `N` is the number of fields.

### Examples (informative)

```
// pair: .{si4, verdict.[void, void]}
let pair = .{ 42~si4, verdict.[void, void]::Pass(void) };
// triple: .{si4, fe11s52, verdict.[void, void]}
let triple = .{ 1~si4, 2.0~fe11s52,
                verdict.[void, void]::Fail(void) };
pair.0 // 42
pair.1 // verdict::Pass(void)
```

## 4.9 References

### Static semantics

A reference type is composed from a tribe and a sequence of modifiers. The tribes, the modifiers, the set of valid combinations, modifier placement, derivation rules, and atomic operations are defined in the clause on references and resource management.

The stored representation of a reference type whose referent type is `[U]` is defined in the clause on references and resource management, and of one whose referent type is `dyn Protocol` in the clause on protocols and implementations. For every other referent type the stored representation is one field of the reference width, and the subclause on size and alignment gives the size and the alignment. What that field carries besides the address is implementation defined, and the implementation shall document it. Storing a value of a reference type yields a Γ sequence that the interpretation maps to the value. Which such Γ sequence is implementation defined.

## 4.10 Subroutine pointer types

### Syntax

```
subroutine_pointer_type = subroutine_ptr_header, ws,
                          subroutine_proto_param,
                          [ ws, subroutine_return ],
                          [ ws, with_single | ws, with_curly ] ;

subroutine_ptr_header   = [ extern_clause, ws ], [ "variadic", ws ],
                          [ "airside", ws ], "fn", [ ws, generic_clause ] ;
```

The `subroutine_return` and `extern_clause` productions are defined in the clause on declarations.

### Static semantics

A subroutine pointer designates a subroutine. An expression naming a subroutine yields a value of the subroutine pointer type formed from the subroutine’s invocation interface, variadic status, airside status, generic parameters, parameter types, return type, and subject bounds. Its size is `(%void)'size`. The permitted conversions involving subroutine pointers are defined in the clause on expressions. The optional return-type position permits either a type or `!`. A subroutine of a type written with `!` does not return control to its invoker, with consequences defined in the subclause on control transfers and diverging expressions.

Parameter names in a subroutine pointer type follow the rules defined in the subclause on subroutine declarations.

A subroutine pointer type may carry an `extern` clause, a `variadic` keyword, an `airside` keyword, and a `generic_clause` as prefixes. In a type, the `extern` clause names the invocation interface, the `variadic` keyword selects the variadic variant of that interface, and the `airside` keyword states that the subroutine is declared with the `airside` modifier or within a `#dyn` block. The effects each prefix has upon a declaration, and the invocation interface of a subroutine that carries no `extern` clause, are defined in the clause on declarations.

A subroutine pointer type with a `generic_clause` or a `with` clause designates a subroutine whose signature is lowered according to the rules defined in the subclause on signature lowering.

A `with` clause that follows the return type of a subroutine declaration or of a subroutine pointer type belongs to that declaration or type, never to a subroutine pointer type written as that return type.

Two subroutine pointer types are the same type where their invocation interface, their variadic status, their airside status, their generic parameters and the bound elements of each in order, their parameter types, their return types, and their subject bounds in order are the same.

### Constraints

The `with` clause of a subroutine pointer type shall contain only subject bounds. An expression that names an associated subroutine whose lowered signature carries a `selftype` level or the generic parameters of an enclosing declaration shall appear only as the leading expression of a subroutine invocation.

### Examples (informative)

```
fn(si4) -> si4                // native (implicit)
extern fn(si4) -> si4         // native (explicit, identifier omitted)
extern(native) fn(si4) -> si4 // native (explicit, identifier present)
```

## 4.11 Composite type representation

This subclause applies Kurt standard alignment to composite types and defines the `with` clauses that depart from it. Kurt standard alignment is defined in the clause on semantics.

### Syntax

```
repr_clause    = 'repr', ws, '(', ws, repr_arg, ws, ')' ;
repr_arg       = pack_scheme | identifier ;
pack_scheme    = 'pack', ws, '(', ws, integer_literal, ws, ')' ;
discrim_clause = 'discrim', ws, '(', ws, single_path, ws, ')' ;
align_clause   = 'align', ws, '(', ws, integer_literal, ws, ')' ;
```

### Static semantics

`repr` controls the layout of a composite type. On a struct, it governs the layout of the struct itself; on a variant type, it governs the layout of the payload region. The argument names a layout scheme:

— `pack(N)` — each field is placed at an alignment not greater than `N`.

— `native` — the native layout rules of the execution environment. The exact layout is implementation defined, but shall match the native invocation interface of the execution environment.

`discrim` controls the discriminant type of a variant type. The argument is either a type satisfying `integer` or `void`. When the argument is `void`, the discriminant occupies zero cells.

### Constraints

At most one `repr(...)` may appear in a type’s `with` clause. At most one `discrim(...)` may appear in a type’s `with` clause. `discrim` shall appear only on the declaration of a variant type. `repr` and `discrim` may be combined with each other and with `align(N)` in the same `with` clause.

In `pack(N)`, `N` shall be a power of two greater than zero.

`discrim(void)` shall appear only on a variant type whose discriminant type would be `void` were the `with` clause absent.

When the `discrim` argument satisfies `integer`, all discriminant values shall fit in the specified type.

### Implementation requirements

A conforming implementation shall support the `repr` schemes `pack` and `native` with the semantics defined above. The implementation shall document any additional `repr` identifiers it supports.

### 4.11.1 Composite type layout

#### Static semantics

The layout of a composite type is that which Kurt standard alignment, defined in the clause on semantics, gives the sequence of its field types. That sequence is:

— for a struct, its fields in declaration order.

— for a tuple, its fields in index order.

— for a variant type, the discriminant and the variant payload, as the subclause on automatic discriminant sizing defines.

Where `m_0, m_1, ..., m_n` are the fields of a composite type `S` in that order, `S'offset(m_i)` is the offset KSA assigns the field’s type, and `S'align` and `S'size` are the alignment and the size it assigns the sequence.

A **padding cell** is a cell of a composite type’s representation that no field of the type occupies, whether KSA inserted it for alignment or a `?` field declared it.

After construction, a padding cell carries the load and store semantics its type gives every other cell of the representation.

Two values of one composite type that differ only at padding cells hold the same field values. Their Γ sequences need not be identical.

#### Constraints

A composite type whose `S'size`, computed by the arithmetic above, exceeds the greatest value representable by `uaddr` shall not appear. Such a violation, where not detected during translation, can cause indeterminate state.

Determining the layout of a type shall not require, directly or indirectly, the layout of that type. For this rule, the layout of a composite type or of an array type requires the layouts of the types of its fields or its elements, and that of an array type requires in addition what its length expression requires; an expression requires what the rule of the clause on expressions upon what an evaluation requires reads it to require, and in addition the layout of each type to which a layout intrinsic is applied, within the expression or within an expression that reading reaches; and the layout of a reference type or of a subroutine pointer type requires nothing.

#### Implementation requirements

A conforming implementation shall set every bit of every padding cell to zero when a value of a composite type is constructed.

#### Design rationale (informative)

Every subsequent layout computation depends on `S'size`. Requiring its exact value to be representable by `uaddr` makes an oversized declaration a translation failure instead of permitting wrapped layout values.

### 4.11.2 Automatic discriminant sizing

#### Static semantics

The discriminant type of a variant type is automatically determined by its declared variants:

— When the type declares zero or one variants, no variant carries a `wild(V)` canonical value, no variant is assigned an explicit discriminant value, and `with discrim(T)` is not specified, the discriminant type is `void` and occupies zero cells.

— Otherwise, where `with discrim(T)` is not specified, the smallest unsigned integer type that can represent all discriminant values is selected. If any discriminant value is negative, the smallest signed integer type is selected instead.

— If `with discrim(T)` is specified, the discriminant type is fixed to `T`.

A variant type whose discriminant type is `void` has exactly one discriminant value, and that value is zero. The sole declared variant takes it where one is declared, and the implicit wild covers it where none is. The value-set requirement below does not apply to such a type.

The field sequence of a variant type is the discriminant followed by one payload, and Kurt standard alignment gives the layout of that sequence. The payload occupies as many cells as the largest variant payload of the type, and is aligned for the payload of greatest alignment. Where no variant of the type carries a payload, both are zero.

The automatically selected discriminant type shall have a value set, evaluated under `cellbits::exec`, that contains all discriminant values the variant type declares.

#### Examples (informative)

These examples apply where `cellbits::exec == 8`.

```
// 0 variants → void discriminant
enum empty {}
// 1 variant → void discriminant
enum unit { only }
// 3 variants → ui1 discriminant
enum colour { red, green, blue }
// 300 variants → ui2 discriminant
enum big_enum { ... }
// value 2006 → ui2 discriminant
enum year_tag { y2006 = 2006 }
// negative → si4 discriminant
enum offset { neg = -19700101 }
// forced to ui4
enum forced { lo, hi } with discrim(ui4);

// translation failure
// enum error { lo = -72 } with discrim(ui1);
// enum bad { lo, hi } with discrim(void);
```

### 4.11.3 `with repr(pack(N))`

#### Static semantics

Under `with repr(pack(N))`, the alignment Kurt standard alignment uses for each field of the struct is the lesser of the field type’s alignment and `N`, in place of that alignment. An access to an object placed at an alignment less than that of its type can be performed by more than one instruction.

### 4.11.4 `with align(N)`

#### Static semantics

`with align(N)` sets the minimum alignment of a type to `N` cells. The alignment of a type that carries `align(N)` is the greater of `N` and the alignment the type would have were the clause absent, and the type’s size is rounded up to a multiple of the alignment.

#### Constraints

`N` shall be a power of two greater than zero.

#### Examples (informative)

```
struct packet {
    header: ui4,
    seq: ui4,
    payload: &[ui1]
} with {
    repr(pack(1)),
    align(4)
}
```

### 4.11.5 `with variadic`

#### Static semantics

A struct declared `with variadic` serves as the state object for variadic argument iteration. `with variadic` makes the type uncopyable, and the implementation supplies the destructor of the type.

#### Constraints

The size of a `with variadic` type shall equal the size of the native variadic state object of the execution environment.

A `with` clause shall not combine `variadic` with `repr` or `destruct`.

#### Implementation defined

The internal fields, the iteration interface, and the argument promotion rules of each `with variadic` type are implementation defined.

#### Examples (informative)

```
// AArch64 AAPCS64 — type definition
struct va_list {
    pub airside __stack:   %void,
    pub airside __gr_top:  %void,
    pub airside __vr_top:  %void,
    pub airside __gr_offs: si4,
    pub airside __vr_offs: si4,
} with variadic;

// AArch64 AAPCS64 — iteration impl
impl va_list {
    pub airside fn next_int.[T: integer]($self) -> T {
        if self.__gr_offs < 0 {
            let offs = self.__gr_offs;
            self.__gr_offs = offs + 8;
            if offs + 8 <= 0 {
                let addr = self.__gr_top as uaddr + offs as uaddr;
                return *(addr as %ui8) as T;
            }
        }

        let addr = self.__stack;
        self.__stack = ((addr as uaddr) + 8) as %void;
        return *(addr as %T);
    }

    pub airside fn copy(&self) -> selftype {
        return *(self as %selftype);
    }
}
```

## 4.12 Type inference and the inferred type `?`

### Syntax

```
inferred_type = '?' ;
```

### Static semantics

The token `?` in a type position is an **inferred type**. It is replaced by the resolved type for all subsequent analysis. A declaration whose type annotation is `?` is equivalent to the same declaration with the annotation omitted.

The type of a construct is determined by **synthesis** or by **checking**. Synthesis derives the type from the construct itself. Checking adopts an **expected type** supplied by a constraining construct — a type annotation, a parameter type, a return type, an operation, a use site of the binding, or the expected type of an enclosing expression.

If synthesis and checking both determine a type and agree, or if exactly one determines a type, the construct has the type. If neither determines a type, the construct has the default type defined for its form, and where its form defines none, the construct shall not appear. If they conflict, the construct shall not appear.

The **common type** of a set of expressions is the one type that each of them has, disregarding those that are control transfers or diverging expressions. Control transfers and diverging expressions are defined in the clause on statements and control flow.

Where the rules of an operation, a cast included, admit exactly one type that an undetermined operand can have, given the types determined for its other operands and for its result, that type is the expected type of the operand.

An omitted generic type argument is determined by unification of the synthesized argument types against the parameter types of the signature. A type argument not determined by unification shall be supplied explicitly.

### Constraints

An inferred type `?` shall not appear in a subroutine parameter type, a subroutine return type, a field type, an array element type, a tuple field type, or a type alias definition.

### Examples (informative)

```
let n = 42;      // neither synthesis nor checking — default saddr
let m: si4 = 42; // checking — literal takes si4

// checking propagates into the payload. F is fixed by the annotation.
let v: verdict.[si4, si4] = verdict::Pass(42);

// unification: T resolved from the argument type, no explicit
// argument needed
let r = identity(m); // identity.[T](x: T) -> T  →  T = si4

// T appears only in the return type — explicit argument mandatory
let d = default_value.[si4]();

// expected type propagates to both branches
let w: colour = if cond then colour::red else colour::green;

// operator operand — the unconstrained operand takes the type of
// the other operand
let big: uaddr = 4096;
let half = big / 2; // 2 takes uaddr
let ok = 100 < big; // 100 takes uaddr
let sh = big >> 4;  // 4 takes uaddr

// the expected type reaches both operands of the shift through its result
let mask: ui4 = 1 << 5; // 1 and 5 both take ui4

// use-site resolution — i takes uaddr from a.len and a.ptr
fn f(a: &[ui1]) {
    let mut i = 0;           // default would be saddr
    while a.len > i {        // a.len is uaddr → i is uaddr
        consume(a.ptr + i);  // confirms uaddr
    } then { i += 1; }
}
```
