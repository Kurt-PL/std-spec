# 4. Declarations

This clause defines the declarations of the Kurt programming language: subroutines, bindings and constants, composite types, `struct` and `enum` declarations, type aliases, generics, patterns, `with` clauses, visibility, global `instruct` blocks, the decorations an item may carry, and the extent and duplication of names.

## 4.1 Items

A **declaration** introduces a name. A **definition** does so and determines the contents of what it names.

A construct **uses** the following declarations, layouts, and parts of definitions:

&mdash; The declaration of each binding and each item that it names.

&mdash; The layout of each type such that a rule that defines the evaluation of the construct refers to the size, the alignment, or an offset of that type.

&mdash; The body of each subroutine that it names, and, where it is a method invocation, the body of the subroutine that it resolves to.

&mdash; The initializer block of each `const` declaration and `static` binding that it names, and the expression of each implanted constant that it names.

&mdash; The default-value expression of each field that it omits.

&mdash; The destructor of the type of each object for which it reserves storage, and the destructor of each constituent of that type.

The **descriptors of a construct** are the following:

&mdash; Each descriptor that the value of the construct holds, where the construct decays a value to a reference to a protocol type.

&mdash; The descriptor that the construct emits, where it is a `T'bound(X)` expression.

&mdash; Each descriptor that the construct supplies for a generic parameter or a subject bound, where it is an invocation.

For each of its descriptors, a construct **uses through a descriptor** the body of each subroutine that the descriptor designates, the expression of each implanted constant for which the descriptor has a field, and the destructor of the type that the descriptor describes.

### Syntax

```
item            = { item_decoration, ws }, ( global_item | local_item ) ;

item_decoration = annotation
                | symbol_directive
                | inline_directive
                | no_inline_directive ;

global_item     = module_decl
                | impl_block
                | protocol_decl
                | global_instruct ;

local_item      = subroutine_def
                | const_decl
                | static_decl
                | struct_decl
                | enum_decl
                | contract_decl
                | type_alias_decl
                | use_decl
                | add_decl
                | path_decl
                | dyn_decl
                | trap_handler_decl ;
```

A `global_item` appears in a source unit or in a module body. A **local item** appears in a source unit, in a module body, or in a block. An item introduces its names into the top-level namespace of the source unit, into the module, or into the block in which it directly appears. The names of a `use_decl` or an `add_decl` are those it introduces, and the name of any other item is the one its identifier gives it. The source unit, its top-level namespace, and the module body are defined in the clause on programme structure and translation, and the block in the clause on statements and control flow.

An **item decoration** stands upon an item.

`module_decl`, `add_decl`, `path_decl`, and `dyn_decl` are defined in the clause on programme structure and translation. `impl_block` and `protocol_decl` are defined in the clause on protocols and implantations. `contract_decl` and `trap_handler_decl` are defined in the clause on statements and control flow. Every other item is defined in this clause.

### Constraints

An item decoration other than an annotation shall stand at most once upon what it decorates.

A local item that appears in a block shall not name a binding that is introduced outside the item and whose object is an automatic object. No generic parameter of a declaration, a subroutine pointer type, or an `impl` block within which such an item lies shall occur free in a type or an expression within that item.

## 4.2 Subroutine declarations

### Syntax

```
(* Shared productions *)
extern_clause     = "extern", [ ws, '(', ws, identifier, ws, ')' ] ;
variadic_clause   = "variadic", ws, '(', ws, identifier, ws, ':', ws,
                    type, ws, ')' ;
subroutine_return = '->', ws, ( type | '!' ) ;
fn_head           = [ "airside", ws ], "fn" ;

subroutine_sig_tail = [ ws, subroutine_return ], [ ws, routes_clause ],
                      [ ws, with_single | ws, with_curly ] ;

(* Headers *)
subroutine_def_header   = [ "pub", ws ], [ extern_clause, ws ],
                          [ variadic_clause, ws ], fn_head, ws,
                          identifier, [ ws, generic_clause ] ;

subroutine_proto_header = [ "pub", ws ], [ extern_clause, ws ],
                          [ "variadic", ws ], fn_head, ws, identifier,
                          [ ws, generic_clause ] ;

(* Parameter lists *)
subroutine_def_param   = '(', ws, [ parameter_list ], ws, ')' ;
subroutine_proto_param = '(', ws, [ proto_parameter_list ], ws, ')' ;

parameter_list = parameter, ws, { ',', ws, parameter, ws },
                 [ ',', ws ] ;
parameter      = [ "mut", ws ], identifier, ws, ':', ws, type ;

proto_parameter_list = proto_parameter, ws,
                       { ',', ws, proto_parameter, ws }, [ ',', ws ] ;
proto_parameter      = [ "mut", ws ], [ identifier, ws, ':', ws ],
                       type ;

(* Definition form: parameter names mandatory *)
subroutine_def = subroutine_def_header, ws, subroutine_def_param,
                 subroutine_sig_tail, ws, block ;
```

The `generic_clause` production is defined in the subclause on generic declarations.

### Static semantics

A subroutine definition introduces a named subroutine and supplies its operations. A subroutine definition, the definition of an implanted subroutine, a subroutine prototype, and a subroutine pointer type each introduce parameters, the self parameter and the variadic binding included. They introduce them into the part of the construct from the parameter list to its end. Each of those parameters other than the variadic binding is a **fixed parameter**. So is the self parameter that a `destruct` keyword introduces. Every subroutine has an invocation interface. It is `native` unless an `extern` clause names another, as the subclause on external declaration defines.

A **subroutine prototype** states the name, the parameters, and the return type of a subroutine. It appears only in a `#dyn` block, as defined in the clause on programme structure and translation, or in a protocol body, as defined in the clause on protocols and implantations.

A subroutine declaration or a subroutine pointer type that omits `-> T` is the same declaration or type with `-> void`.

`mut` on a parameter applies to the parameter binding alone.

### Dynamic semantics

When a subroutine is invoked, execution proceeds as follows:

1. Argument evaluation &mdash; each argument expression is evaluated in the order defined in the subclause on subroutine invocation.
2. Body evaluation &mdash; the body is evaluated.
3. Value return &mdash; the return value is copied or transferred to the invoker.
4. Local destruction &mdash; control exits, innermost first, each master and each scope of the invocation that it has not exited, as the clause on semantics defines.

### Constraints

Where a subroutine definition or the definition of an implanted subroutine declares `-> !`, or declares a return type other than `void`, the programme point at the end of its body shall be unreachable.

### Examples (informative)

```
fn add(a: si4, b: si4) -> si4 { return a + b; }
fn diverge() -> ! { trap(); }
fn unit() { } // returns void

// mut parameter: the parameter binding is multi-assignment
fn zero_and_sum(mut buf: [si4; 4]) -> si4 {
    let mut total: si4 = 0;
    let mut i = 0;

    while i < 4 {
        total += *buf.at(i);
        *buf.at_xcl(i) = 0;
    } and then { i += 1; }

    return total;
}

// Direct recursion
fn factorial(n: uaddr) -> uaddr {
    return if n == 0 then 1 else n * factorial(n - 1);
}
```

### 4.2.1 `airside fn`

#### Static semantics

An invocation of an `airside fn`, or through a subroutine pointer whose type carries the `airside` keyword, requires airside.

### 4.2.2 External declaration

#### Static semantics

A declaration that carries `extern` is an **external declaration**. The `extern` clause has the following effects upon the declaration:

&mdash; Name stability &mdash; the external name of a declaration that does not declare an implanted subroutine is the declaration’s identifier, except where a `#symbol` directive upon it supplies another.

&mdash; Invocation interface &mdash; for subroutine declarations, the parenthesized identifier selects the invocation interface. `native` denotes the native invocation interface of the machine on which an invocation of the subroutine takes place.

A declaration carries an **external name** where it carries `#symbol`, where it appears in a `#dyn` block, or where it carries `extern` and does not declare an implanted subroutine.

A definition that carries no external name has an implementation-defined name in the opaque code.

#### Constraints

A parenthesized invocation interface identifier shall not appear on an `extern static` declaration. The identifier of an `extern` clause shall name an invocation interface that the implementation documents.

#### Implementation requirements

The implementation shall apply no name transformation to the external name of an external declaration.

The implementation shall retain in the opaque code an item that is analysed on the programme machine and that lies outside every `#dyn` namespace, in a form invocable or accessible from outside the translation unit, where any of the following holds:

&mdash; The declaration that introduces it carries an external name.

&mdash; The item is a subroutine and an expression names it other than to name the invoked subroutine of an invocation.

&mdash; A descriptor the implementation emits designates it.

#### Implementation defined

How an external name is represented in the opaque code is implementation defined.

#### Examples (informative)

```
pub extern fn init() { ... }
pub extern(native) fn init2() { ... } // equivalent to above
pub extern(efi) fn efi_entry(handle: uaddr, table: %ui1)
    -> uaddr { ... }

// extern without pub: kept in opaque code, private to the module
extern fn internal_hook() { ... }

// internal: implementation-defined name
fn helper(x: si4) -> si4 { ... }

pub extern static version: ui4 = 1;
extern static mut hw_state: ui4 = 0; // preserved but private
```

### 4.2.3 Variadic subroutines

A variadic subroutine accepts a variable number of arguments after its fixed parameters.

#### Static semantics

A subroutine declared with a `variadic` clause, and a subroutine prototype declared with the `variadic` keyword, use the variadic variant of their invocation interface. The identifier of a `variadic` clause names the **variadic binding** of the subroutine. The type of that binding is the type that the clause names.

#### Dynamic semantics

Upon entry, the invocation initializes the object of the variadic binding as the variadic variant of the invocation interface requires.

#### Constraints

The type named in the `variadic` clause shall satisfy `variadic`.

#### Examples (informative)

```
// Forwarding subroutine
variadic(args: va_list) fn my_printf(fmt: %ui1) -> si4 {
    return my_vprintf(fmt, args);
}

// Iteration within airside
variadic(args: va_list) fn sum_ints(count: si4) -> si4 {
    let mut total: si4 = 0;
    let mut i: si4 = 0;

    while i < count {
        airside { total += args.next_int[si4](); }
    } and then { i += 1; }

    return total;
}

// Indirect invocation through a variadic subroutine pointer
let f: extern variadic fn(%ui1) -> si4 = my_printf;
f(fmt, width, name);
```

## 4.3 Binding declarations

### Syntax

```
let_decl = "let", ws, pattern_body, [ ws, ':', ws, type ],
           [ ws, '=', ws, expression ],
           [ ws, else_bind, ws, block ], ws, ';' ;

else_bind = "else", [ ws, '.', ws, ident_pat ] ;
```

The pattern forms and their refutability are defined in the subclause on patterns and destructuring.

### Static semantics

A `let` declaration introduces the bindings its pattern introduces into the block in which it appears.

The **`else` branch** of a construct is the construct that follows its `else` keyword and, where one is present, the `ident_pat` after that keyword. The `ident_pat` of an `else_bind` introduces its name into that branch. On entry to the `else` branch, the `ident_pat` is matched against the following value, and the type of its name is the type of that value:

&mdash; In a `let` declaration, an `if let` expression, or a `while` expression of the `while let` form &mdash; the value that the pattern did not match.

&mdash; In any other construct &mdash; the failure payload of the value that selects the `else` branch.

A binding is a **multi-assignment binding** where `mut`, other than as a `ref_modifier`, precedes the token by which it is introduced, with no identifier between them, or where a `variadic_clause` introduces it. Every other binding is a **single-assignment binding**. The object of a multi-assignment binding may be stored into through that binding any number of times.

Binding a value to a binding initializes its object. An initialization of a binding’s object that the construct introducing the binding performs is a store into the object through that binding, and so is one that the invocation performs for a fixed parameter or a variadic binding. For a fixed parameter or a variadic binding, the invocation performs that initialization once, on entry to the invoked subroutine: where that subroutine has a subroutine body, at the first programme point of that body. Every initialization performed on entry to a scope is performed at the first programme point of that scope.

A **trace from the reservation** of a binding’s object is a trace that occupies its starting programme point only at its start, and that starts at the following programme point:

&mdash; For the object of a fixed parameter or a variadic binding &mdash; the first programme point of the subroutine body.

&mdash; For any other automatic object &mdash; the first programme point of the scope to which the object belongs.

A binding’s object is **definitely initialized** at a programme point where it is initialized when its storage is reserved, or where every trace from the reservation of the object to that programme point contains a store that makes it initialized.

### Constraints

The binding’s object shall be loaded, a managed reference to it created, and, through the binding, a constituent object of it stored into, only at a programme point at which it is definitely initialized. Such a violation through a reference, where not detected during translation, can cause indeterminate state.

The object of a single-assignment binding shall be stored into through that binding at most once in each trace from the reservation of its object.

A declaration that omits both the type annotation and the initializer shall not appear.

### Examples (informative)

```
let x: si4 = 42;     // single-assignment, initialized at declaration
let y = x + 1;       // single-assignment, type inferred
let mut counter = 0; // multi-assignment, initialized at declaration
counter += 1;        // OK: counter is mut

// Deferred initialization: single-assignment
let result: si4;
if condition {
    result = compute_a();
} else {
    result = compute_b();
}
print(result); // OK: every trace to here assigns result
// result = 0; // translation failure: result is single-assignment

// Deferred initialization: multi-assignment
let mut buf: [ui1; 4096];
buf = [0; 4096];
airside { dma_fill(%buf, 4096); }
print(buf); // OK: buf was initialized by the assignment above

// Diverging branch: its trace reaches no programme point after the if
let z: si4;
if runtime_condition {
    z = compute();
} else {
    trap();
}
print(z); // OK: the only trace to here assigns z

// translation failure: a trace omits the assignment
// let x: si4;
// if runtime_condition {
//     x = 1;
// }
// print(x); // the else trace reaches here and assigns nothing

// translation failure: managed reference to a binding
// that is not definitely initialized
// let a: si4;
// let r = &a;
```

### 4.3.1 The `else` clause on refutable patterns

#### Dynamic semantics

1. The initializer expression is evaluated.
2. The result is matched against the pattern.
3. If the pattern matches, the objects of the bindings the pattern introduces are initialized and execution continues after the declaration.
4. If the pattern does not match, the `else` branch is evaluated.

#### Constraints

Where its pattern is refutable, a `let` declaration shall include an initializer and an `else` clause; otherwise it shall include no `else` clause.

The `else` branch shall be a jump or a diverging expression.

#### Examples (informative)

```
// Irrefutable patterns: else is forbidden
let .{ x, y } = get_point(); // OK
// translation failure: irrefutable
// let .{ x, y } = get_point() else { return; };

// Refutable patterns: else is mandatory
// OK: diverge
let verdict::Pass.{ n } = try_parse() else { return; };
// OK: diverge with binding
let verdict::Pass.{ m } = try_parse() else.fail {
    log(fail); return;
};

// translation failure: no else
// let verdict::Pass.{ x } = try_parse();
```

## 4.4 Translation-time constants

A `const` declaration introduces a translation-time constant.

### Syntax

```
const_decl = [ "pub", ws ], "const", ws, ( identifier | '?' ), ws,
             [ ':', ws, type, ws ], '=', ws, expression, ws, ';' ;
```

### Static semantics

The initializer is evaluated in the initializer block of the declaration, as the clause on expressions defines.

A `const` declaration is analysed also on the programme machine.

A `const` declared as `?` introduces no name, and `pub` upon it has no effect.

### Constraints

A store to a field of the value a `const` declaration introduces shall not appear, regardless of the field’s modifiers.

### Examples (informative)

```
const max_size: uaddr = 1024;
const tau: fe11s52 = 6.283185307179586476925286766559;
// type inferred from the initializer
const limit = 1024~ui4;
// subroutine invoked at translation time
const crc_table: [ui4; 256] = make_lut();
```

## 4.5 Global bindings

A `static` declaration introduces a permanent object, as defined in the clause on semantics, and, other than where declared as `?`, a binding whose object is that permanent object.

### Syntax

```
static_decl = [ "pub", ws ], [ "extern", ws ], "static", ws,
              [ "mut", ws ], ( identifier | '?' ), ws,
              [ ':', ws, type, ws ], '=', ws, expression, ws, ';' ;
```

### Static semantics

A `static` declared as `?` introduces no name. A `#symbol` directive upon it gives it its external name. `pub` upon it has no effect.

An object expression designating the object of a single-assignment `static` binding is storable at no programme point.

### Dynamic semantics

The initializer is evaluated in the initializer block of the declaration, as the clause on expressions defines. The permanent object holds, when execution begins and when each translation-time evaluation that awaits the evaluation of that block begins, the value that the initializer block yields.

### Constraints

An identifier expression or a path expression that names a `static mut` binding requires airside.

### Examples (informative)

```
static config: app_config = default_config();
static mut counter: uaddr = 0;
// type inferred from the initializer
static limit = 4096~uaddr;

fn increment() {
    airside { counter += 1; } // airside required for static mut access
}

// Field mutability via mut field
struct tally {
    mut value: ui4
}

static shared_counter: tally = tally.{ .value = 0 };
// shared_counter is `static` (not `static mut`), but the `mut` field
// permits airside stores through &shared_counter.
```

## 4.6 Composite types

A **composite type** is a struct type, an anonymous struct type, or a variant type.

A **variant type** is a type whose value holds one of a set of named variants and a discriminant that records which. An `enum` declaration introduces a variant type, and so does a `contract` declaration, as defined in the clause on statements and control flow. Such a declaration introduces the names of the variants it declares into the namespace of that type.

### Syntax

```
composite_form   = '{', ws, ( anon_field_list | named_field_list ), ws,
                   '}' ;

anon_field_list  = anon_field, ws, { ',', ws, anon_field, ws },
                   [ ',', ws ] ;
anon_field       = field_modifiers, type, [ ws, '=', ws, expression ] ;

named_field_list = named_field, ws, { ',', ws, named_field, ws },
                   [ ',', ws ] ;
named_field      = field_modifiers, identifier, ws, ':', ws, type,
                   [ ws, '=', ws, expression ]
                 | '?', ws, ':', ws, type ;

field_modifiers  = { field_modifier, ws } ;
field_modifier   = "pub" | "airside" | "mut" ;
```

### Static semantics

A struct type, and each variant of a variant type, takes one of three forms:

&mdash; **Unit form** &mdash; it has no composite form.

&mdash; **Unnamed-field form** &mdash; its composite form matches `anon_field_list`.

&mdash; **Named-field form** &mdash; its composite form matches `named_field_list`.

An anonymous struct type is in unnamed-field form.

### Constraints

The path of a composite construction or of a composite pattern shall denote a variant, or a type in unit form, unnamed-field form, or named-field form. Curly brackets shall follow that path only where the type or variant it denotes is in unnamed-field or named-field form. They shall enclose a `field_init_list` or a `field_pat_list` only where that type or variant is in named-field form, and an `expression_list` or an `unnamed_pat_list` only where it is in unnamed-field form.

A field name shall be unique within a named-field composite type. `?` fields are exempt from uniqueness.

A composite construction whose path denotes a type or variant with an `airside` field requires airside.

A field that the declaration of a composite type declares without `pub` shall be designated, other than by an ignore pattern, only within the namespace that declares the composite type.

Every field that this specification gives a built-in type is `pub`.

### 4.6.1 Field modifiers

#### Static semantics

A **modifier** is a keyword written with a type, a field, or a declaration that qualifies how it is accessed or where it may be named. The modifiers of a reference type, the field modifiers, and the visibility modifier are defined where those constructs are defined.

The field modifiers `airside` and `mut` have the following effects:

&mdash; `airside` requires airside of every load from and every store to the field, and of the creation of a reference to the field or to a constituent object of it.

&mdash; `mut` gives the field **field mutability**. The field may be stored to through a reference or a binding that itself permits no store. Such a store requires airside, and so does the creation of a store-permitting reference to the field or to a constituent object of it.

#### Constraints

A field declaration that repeats a modifier shall not appear.

### 4.6.2 `?` fields

#### Static semantics

A **`?` field** declares padding cells within a struct type or variant in named-field form.

### 4.6.3 Default-value expressions

#### Static semantics

A field may carry a default-value expression of the form `= expr`. Where a composite construction omits that field, the construction initializes the field with the value of that expression.

## 4.7 Struct declarations

A struct declaration introduces a named composite type.

### Syntax

```
struct_decl = [ "pub", ws ], "struct", ws, identifier,
              [ ws, generic_clause ],
              ( [ ws, with_single ], ws, ';'
              | ws, with_curly
              | ws, composite_form,
                [ ws, with_single, ws, ';' | ws, with_curly ] ) ;
```

### Examples (informative)

```
// Unit form
struct empty_t;

struct point { x: si4, y: si4 }

struct origin_point {
    x: si4 = 0,
    y: si4 = 0
}

struct example {
    // private, the binding kind governs stores
    a: si4,
    // public,  the binding kind governs stores
    pub b: si4,
    // private, field mutability
    mut c: si4,
    // public,  field mutability
    pub mut d: si4,
    // private, airside-only access
    airside e: si4,
    // public,  airside-only access
    pub airside f: si4,
    // private, airside-only access, field mutability
    airside mut g: si4,
    // public,  airside-only access, field mutability
    pub airside mut h: si4
}

struct network_header {
    version: ui1,
    ?: ui1,
    length: ui2,
    ?: [ui1; 4],
    payload_offset: ui4
}
```

## 4.8 Enum declarations

### Syntax

```
enum_decl = [ "pub", ws ], "enum", ws, identifier,
            [ ws, generic_clause ], ws, '{', ws,
            [ variant_list ], ws, '}',
            [ ws, with_single, ws, ';' | ws, with_curly ] ;

variant_list  = variant, ws, { ',', ws, variant, ws }, [ ',', ws ] ;
variant       = identifier, [ ws, composite_form ],
                [ ws, '=', ws, variant_value ] ;

variant_value = discrim_value
              | "wild", [ ws, '(', ws, discrim_value, ws, ')' ] ;

discrim_value = [ sign, ws ], integer_literal ;
```

### Static semantics

`wild` declares that the designated variant covers all discriminant values that no other variant covers.

A `discrim_value` denotes, as an integer, the value of its integer literal, or, where it carries a `sign`, the value that `sign` yields as a unary negation or a unary identity whose operand is that literal. That literal takes no type from inference: without a type suffix, it and its negation are integers.

`wild(V)` declares a **canonical value** for the wild variant, where `V` is a `discrim_value`. A construction of the wild variant stores `V` as the discriminant. (e.g. `verdict::Fail.{ payload }` stores `V` as the discriminant.) The canonical value also governs discriminant extraction via `as`, as defined in the clause on expressions.

The rules of this subclause apply to every variant type.

A variant type that declares no `wild` variant has an **implicit wild variant**. It is assigned no discriminant value of its own. It covers all discriminant values of the type’s discriminant type that no declared variant covers.

A value of a variant type that declares no `wild` variant may be constructed by the expression `TypeName::wild`, as defined in the subclause on wild construction in the clause on expressions.

A variant declared without an explicit discriminant value is assigned its discriminant value by the **automatic discriminant assignment**. A `wild` variant without a canonical value counts as lacking an explicit discriminant value. In declaration order, each variant that lacks one is assigned the least non-negative integer that is neither an explicitly specified discriminant value within the type, counting each `wild(V)` canonical value among them, nor the discriminant value assigned to an earlier variant.

Where `wild` is written without a canonical value, a construction of the wild variant stores as the discriminant the value the automatic discriminant assignment assigns that variant.

### Constraints

A type shall have at most one `wild` variant.

Each explicitly specified discriminant value within a variant type, counting each `wild(V)` canonical value among them, shall be distinct from every other.

### Examples (informative)

```
// Variants in unit form only
enum colour { red, green, blue }

// Variant in unnamed-field form: single positional field
enum packet { data { &[ui1] }, ack, error = wild }

// Variants in unnamed-field form: multiple positional fields
enum shape {
    circle { fe11s52 },                 // radius: .0
    rect { fe11s52, fe11s52 },          // width: .0, height: .1
    triangle { fe8s23, fe8s23, fe8s23 } // sides: .0, .1, .2
}

// Variants in named-field form
enum event {
    key_press { key: ui4, modifiers: ui1 },
    mouse_move { x: si2, y: si2 },
    quit
}

// Mixed
enum message {
    ping,
    data { ui1, [ui1; 32] },          // positional: kind + payload
    error { code: ui4, msg: &[ui1] }, // named fields
    unknown = wild
}

// Accessing the fields of variants in unnamed-field form
let s: shape = shape::rect.{ 3.0, 4.0 };
match s {
    let shape::rect.{ w, h }        -> area(w, h);
    let shape::circle.{ r }         -> area_circle(r);
    let shape::triangle.{ a, b, c } -> area_triangle(a, b, c);
    wild                            -> 0.0;
}

// Accessing the fields of variants in named-field form
let e: event = event::key_press.{ .key = 65~ui4, .modifiers = 0~ui1 };
match e {
    let event::key_press.{ .key, .modifiers } ->
        handle_key(key, modifiers);
    let event::mouse_move.{ .x, .y }          -> handle_mouse(x, y);
    event::quit                               -> quit();
    wild                                      -> ignore();
}
```

## 4.9 Type aliases

A type alias introduces a new name for an existing type.

### Syntax

```
type_alias_decl = [ "pub", ws ], "type", ws, identifier,
                  [ ws, generic_clause ], ws, '=', ws, type, ws, ';' ;
```

### Static semantics

At every use site, a type alias is replaced by its aliased type, with the generic arguments supplied there substituted for the parameters it declares.

### Constraints

A generic alias that declares a generic parameter not appearing in the aliased type shall not appear.

### Examples (informative)

```
type byte        = ui1;
type index       = uaddr;
type pair[A, B]  = .{A, B};
type matrix[T]   = [[T; 4]; 4];

pub type seconds = ui4;

// No conversion at any use site
let b: byte = 42~ui1;
let c: ui1  = b;
fn takes_ui1(x: ui1) {}
takes_ui1(b);

// Protocol bounds resolve on the aliased type
fn show[T: fmt](x: T) { ... }
show(b); // OK: an implantation of fmt for ui1 exists

// Generic argument identity
let p1: pair[byte, si4] = .{ 1~ui1, 2 };
let p2: pair[ui1,  si4] = p1; // same type

// A struct declaration introduces a distinct type
struct seconds2 { val: ui4 }
```

## 4.10 Generic declarations

A declaration that carries one or more generic parameters, and that declares a type, a type alias, a subroutine, or a protocol, is a **generic declaration**. Each generic parameter is a type parameter or a dependence parameter.

### Syntax

```
generic_clause   = '[', ws, generic_item, ws,
                   { ',', ws, generic_item, ws }, [ ',', ws ], ']' ;
generic_item     = type_param | dependence_param ;
type_param       = identifier, [ ws, ':', ws, bound ] ;
dependence_param = "let", ws, identifier, ws, ':', ws, type ;
bound            = bound_elem, ws, { '+', ws, bound_elem, ws } ;
bound_elem       = builtin_bound | single_path ;

generic_args     = '[', ws, generic_arg, ws,
                   { ',', ws, generic_arg, ws }, [ ',', ws ], ']' ;
generic_arg      = type | expression ;
```

### Static semantics

A **generic argument list** follows the name of a generic declaration, or an expression whose type is a subroutine pointer type with a `generic_clause`. Its arguments correspond in order to the generic parameters of that declaration or of that `generic_clause`. Each generic parameter resolves to the argument it corresponds to. An argument is a `type` where the parameter corresponding to it is a type parameter, and an `expression` or an `inferred_type` where the parameter corresponding to it is a dependence parameter. An argument to which a type parameter resolves is a **type argument**.

An **instantiation** of a generic declaration is the type or protocol obtained by resolving each of its generic parameters to an argument. A generic declaration of a type, a type alias, or a protocol has one instantiation for each resolution of its generic parameters in which each argument satisfies every bound element declared upon the parameter that resolves to it. A path denotes one of them only together with its generic arguments. The types that a generic declaration of a type introduces are its instantiations.

Generic parameters are introduced into the declaration or subroutine pointer type that declares them. An `impl(...)` parameter list introduces generic parameters into its `impl` block, as defined in the clause on protocols and implantations.

A generic parameter **occurs free** in a type or an expression where, other than within a part of that type or expression of which it is a generic parameter, any of the following holds:

&mdash; It occurs there.

&mdash; It occurs free in a type that a `selftype` there stands for.

&mdash; It occurs free in the type of an expression that is, or lies within, that type or expression.

A type in which a generic parameter occurs free is an **open type**, and any other type is a **closed type**.

A **type parameter** is, in semantic analysis, a distinct open type, and, in each evaluation, denotes its type argument. An **eligible resolution** of generic parameters resolves each type parameter to a closed type that satisfies every built-in bound that its bound names or that a protocol its bound names entails. An open type satisfies a built-in bound `X` if and only if, in every programme and every machine, it satisfies `X` under every eligible resolution of its generic parameters.

A **dependence parameter** declares a value upon which the types within the declaration may depend. The argument supplied for it is a **dependence argument**. A dependence parameter may appear wherever a value expression of the same type may appear. (e.g. an array length, or the type or expression of a subsequent parameter or field.)

Two instantiations of the same generic declaration are the same type if and only if all type arguments are the same types and all dependence arguments yield the same value.

The **element type** of an array type `[T; N]` is `T`, and that of a slice reference is the type its brackets enclose.

Each of the following is an instantiation of a built-in generic declaration. The clause on types defines these types, except that the clause on references and resource management defines slice references and the tribes and modifiers of reference types, and the clause on protocols and implantations defines protocol types.

&mdash; An array type `[T; N]` &mdash; of the built-in generic declaration whose generic parameters are a type parameter for `T` and a dependence parameter of type `uaddr` for `N`, in that order.

&mdash; An anonymous struct type &mdash; of a built-in generic declaration with one type parameter per field, in field order.

&mdash; A slice reference &mdash; of the built-in generic declaration particular to its tribe and modifiers, with one type parameter for its element type.

&mdash; Every other reference type &mdash; of another built-in generic declaration particular to its tribe and modifiers, with one type parameter for its referent type.

&mdash; A subroutine pointer type that carries no `generic_clause` &mdash; of a built-in generic declaration with one type parameter per parameter type, in order, followed by one for its return type where that is not `!`. Two such types are instantiations of the same declaration if and only if they agree in each of the following:

&nbsp;&nbsp;&mdash; The number of parameters.

&nbsp;&nbsp;&mdash; The routes.

&nbsp;&nbsp;&mdash; The invocation interface.

&nbsp;&nbsp;&mdash; The variadic status.

&nbsp;&nbsp;&mdash; The airside status.

&nbsp;&nbsp;&mdash; The subject bounds, in order.

&nbsp;&nbsp;&mdash; Whether they return `!`.

&mdash; `verdict[T, F]` &mdash; of the built-in generic declaration with a type parameter for `T` and one for `F`, in that order.

&mdash; A protocol type &mdash; of a built-in generic declaration particular to its protocol, with the generic parameters of that protocol.

A type satisfies a declared protocol `X` if and only if an implantation of `X` for it is witnessed, as the clause on protocols and implantations defines witnessed implantations.

### Constraints

Where a generic argument list is written, the number of arguments it supplies shall equal the number of parameters in the declaration, or, where it follows an expression whose type is a subroutine pointer type, in the `generic_clause` of that type.

A dependence argument, or the expression of an implanted constant, in which a generic parameter occurs free shall be an identifier expression that names a dependence parameter, or an inferred type found to be such an identifier expression.

The path of a bound element shall denote a protocol. Each type argument shall satisfy every bound element declared upon the parameter that resolves to it.

A field expression whose receiver has, after reference transparency, a type parameter as its type shall not appear.

Each generic parameter that occurs free in an open type shall be a generic parameter of a declaration or subroutine pointer type within which the open type appears.

The type of a dependence parameter shall be a closed type, shall be copyable, and shall neither be a reference type nor contain one as a constituent.

The type of a dependence argument shall be assignable to the type of its dependence parameter.

An operation between two instantiations whose dependence arguments yield different values shall not appear. Such a violation, where not detected during translation, can cause indeterminate state.

### Examples (informative)

```
struct pair[A, B] {
    first:  A,
    second: B
}

contract option[T] {
    some { T },
    none { void } = wild
}

struct arc[T] {
    ptr: %T,
    mut ref_count: &atomic mut ui4
}

// Instantiation
let p: pair[si4, verdict[void, void]] =
    pair.{ .first = 42, .second = verdict::Pass.{ void } };
let x: option[si4] = option::some.{ 7 };

// Explicit generic arguments: required when type cannot be inferred
fn default_value[T: defaulted]() -> T {
    return (T impl defaulted)::default();
}

let val = default_value[si4]();

// Inline bound
fn max[T: primitive](a: T, b: T) -> T {
    return if a > b then a else b;
}

// Dependence parameters
struct ring[T, let capacity: uaddr] {
    data: [T; capacity],
    head: uaddr
}

let r: ring[fe11s52, 12] = ...;
```

### 4.10.1 Generic dispatch

#### Static semantics

A generic subroutine accesses type-specific properties through a bound descriptor passed to it at each invocation site, or through the generic argument vector of a type descriptor passed to it. A **bound descriptor** is a descriptor of a kind that `T'bound(X)` emits, as defined in the clause on expressions.

The invoker supplies a type descriptor for each type argument:

&mdash; Where the type argument is, in semantic analysis, a closed type, the descriptor `T'bound(type)` emits.

&mdash; Where it is otherwise a type parameter, the descriptor the invoker received for that type parameter, or the descriptor it reaches for that parameter through generic argument vectors from a type descriptor it received.

&mdash; Where it is otherwise an open type, a type descriptor the invoker assembles. Its size and alignment follow from the layout rules applied to its arguments, and its field 2 designates the same subroutine for every instantiation of the generic declaration the type instantiates. Each type descriptor so assembled, and the generic argument vector it designates, is a temporary object that the invocation produces.

An assembled type descriptor is supplied, or held in a generic argument vector, only for a type parameter whose bound names no declared protocol. For every other type parameter, and for the subject of every subject bound, the type descriptor that the invoker supplies, or that a generic argument vector holds, is the one that accompanies the protocol descriptor supplied for that parameter or subject. Those two descriptors are immortal objects. Each descriptor that an invocation receives exists until control leaves the body evaluation of that invocation.

### 4.10.2 Signature lowering

The signature of a generic subroutine, or of a subroutine whose `with` clause holds a subject bound, is lowered. The lowered signature is divided into three zones, in the following order.

The lowered signature has the invocation interface and the variadic status of the signature it lowers, and every parameter of its three zones is a fixed parameter.

The return type of the lowered signature is `void`. The result is passed back through the zone 1 parameter.

#### Zone 1

The first parameter is `%mut void`, designating storage the invoker reserves for an object of the source-level return type, or of `void` where the subroutine returns `!`. A type parameter within that type takes its size and its alignment from that parameter’s type descriptor.

#### Zone 2

The source-level parameters follow, in declaration order. A parameter whose type is an open type is lowered to `%void`, and the argument is passed as an unmanaged reference to storage holding the source-level value. A parameter whose type is a closed type is lowered to that type.

#### Zone 3

The descriptors and dependence parameters stand in levels, in the following order:

1. `selftype`, where it is a type parameter of the signature as the clause on protocols and implantations defines.
2. The generic parameters of the subroutine itself.
3. The subject bounds of its `with` clause.
4. The generic parameters of the enclosing declaration.

The enclosing declaration is the `protocol` declaration for a subroutine that a protocol body declares or that a protocol implantation provides, and the `impl(...)` parameter list for a subroutine that an inherent implantation provides. Within each level, parameters and subject bounds appear in declaration order.

For each type parameter, the `type` descriptor reference is emitted as `%void`, followed by one `%void` for each bound element of its bound, in the order of its bound. For each subject bound, the `type` descriptor reference of its subject is emitted as `%void`, followed by the descriptor reference of its protocol as `%void`. The descriptor each element designates is defined in the subclause on bound descriptor emission. For each dependence parameter, one parameter of its type is emitted.

#### Dynamic semantics

An invocation can cause indeterminate state where its zone 3 holds references that do not designate the descriptors that, under an eligible resolution of the generic parameters its levels hold, the subclause on generic dispatch and zone 3 calls for.

#### Design rationale (informative)

The lowered signature is a single symbol composed of closed types and `%void`s. The resulting symbol is invocable across `#dyn` boundaries without source.

#### Examples (informative)

```
extern fn process[T: ord + clone](x: &T) { ... }
// lowers to:
// fn process(
//     out:     %mut void,   // zone 1
//     x:       %void,       // zone 2
//     T_type:  %void,       // zone 3: T'bound(type)
//     T_ord:   %void,       // zone 3: T'bound(ord)
//     T_clone: %void        // zone 3: T'bound(clone)
// ) -> void

extern fn merge[
    T: ord, U: clone
](arr: $[T], default: U, count: si4) { ... }
// lowers to:
// fn merge(
//     out:     %mut void,   // zone 1
//     arr:     %void,       // zone 2
//     default: %void,       // zone 2
//     count:   si4,         // zone 2: closed
//     T_type:  %void,       // zone 3: T'bound(type)
//     T_ord:   %void,       // zone 3: T'bound(ord)
//     U_type:  %void,       // zone 3: U'bound(type)
//     U_clone: %void        // zone 3: U'bound(clone)
// ) -> void

extern fn fill[
    T: numeric, let N: uaddr
](buf: $[T; N]) { ... }
// lowers to:
// fn fill(
//     out:       %mut void, // zone 1
//     buf:       %void,     // zone 2
//     T_type:    %void,     // zone 3: T'bound(type)
//     T_numeric: %void,     // zone 3: T'bound(numeric)
//     N:         uaddr      // zone 3: dependence
// ) -> void

extern fn identity[T](x: T) -> T { return x; }
// lowers to:
// fn identity(
//     out:    %mut void,   // zone 1
//     x:      %void,       // zone 2
//     T_type: %void        // zone 3: T'bound(type)
// ) -> void
```

Usage through `#dyn`:

```
#dyn libsort {
    fn sort(out: %mut void, arr: %void,
        t_type: %void, t_ord: %void);
}

pub fn sort[T: ord](arr: $[T]) {
    airside {
        let mut dummy: void = void;
        let t_type = contract T'bound(type) else trap();
        let t_ord  = contract T'bound(ord)  else trap();

        libsort::sort(%mut dummy, %arr as! %void, t_type, t_ord);
    }
}

// At the invocation:
sort[si4](my_array);
```

## 4.11 Patterns and destructuring

The value a pattern is applied to is the **matched value**, its type is the **matched type**, and the object that holds it is the **matched object**.

### Syntax

```
pattern        = [ "let", ws ], pattern_body ;
pattern_body   = literal_pat | ident_pat | ignore_pat | wild_pat
               | composite_pat | anon_pat
               | slice_pat | string_pat | range_pat
               | binding_pat | or_pat ;

literal_pat    = [ sign, ws ], ( integer_literal | float_literal )
               | char_literal ;
ident_pat      = [ "mut", ws ], identifier ;
ignore_pat     = '?' ;
wild_pat       = "wild", [ ws, '(', ws, identifier, ws, ')' ] ;
composite_pat  = single_path,
                 [ ws, '.', ws, '{', ws,
                   [ field_pat_list | unnamed_pat_list ], ws,
                   '}' ] ;
anon_pat       = '.', ws, '{', ws, unnamed_pat_list, ws, '}' ;

field_pat_list = field_pat, ws, { ',', ws, field_pat, ws },
                 [ ',', ws, [ '...' ] ] ;
field_pat      = [ "let", ws ], [ "mut", ws ],
                 [ identifier, ws, '=', ws ],
                 '.', ws, identifier,
                 [ ws, '@', ws, pattern ] ;

unnamed_pat_list = pattern, ws,
                   { ',', ws, pattern, ws }, [ ',', ws ] ;

slice_pat      = '[', ws,
                 [ element_pat, ws, { ',', ws, element_pat, ws },
                   [ ',', ws ] ], ']' ;
element_pat    = pattern | '...' ;
string_pat     = string_literal | raw_string_literal ;
range_pat      = literal_pat, ws, ( '..' | '..=' ), ws, literal_pat ;
binding_pat    = ident_pat, ws, '@', ws, pattern ;
or_pat         = pattern_body, ws, '|', ws, pattern_body ;
```

### 4.11.1 Pattern forms

#### Static semantics

Where a `literal_pat` carries a `sign`, that `sign` is a unary negation or a unary identity whose operand is the literal that follows it, and the `literal_pat` denotes the value that operation yields. Otherwise the `literal_pat` denotes the value of its literal. A literal within a pattern is yielded by each evaluation that tests the pattern.

&mdash; **Literal pattern** &mdash; `p` matches a value `v` where `v == p` holds.

&mdash; **Identifier pattern** &mdash; an identifier, optionally preceded by `mut`, binds the matched value to a name at the matched type. Within a `pattern`, an identifier pattern that no `let` governs is a composite pattern.

&mdash; **Ignore pattern** &mdash; matches every value of the matched type and introduces no binding.

&mdash; **`wild` pattern** &mdash; matches a value that no declared variant of the matched type covers, and yields a reference to the cells of the matched object. That reference has type `&[ui1]`, and carries `volatile`, `atomic`, and `guard` where the reference nearest the matched object carries them. For the rules of the clause on references and resource management, it is created as from an object expression. That object expression designates the matched object, taken from the expression whose value is matched. The bare form `wild` discards it. The form `wild(`*name*`)` binds it to *name*.

&mdash; **Composite pattern** &mdash; matches a value of the type or variant its path denotes where each pattern it applies to a field of that value matches.

&mdash; **Anonymous struct pattern** (`.{ }`) &mdash; matches a value of an anonymous struct type where each pattern it lists matches the field at its position.

&mdash; **Slice pattern** &mdash; matches an array by element-wise comparison. The rules governing it are defined in the clause on statements and control flow.

&mdash; **String literal pattern** &mdash; syntactic shorthand for a fixed-length slice pattern, as the clause on statements and control flow defines it, whose elements are the `ui1` values of the string literal, as the mapping defined in the subclause on string literals gives them. A raw string literal pattern follows the same rules. (e.g. with an 8-bit cell and a literal encoding that assigns each character of the basic source character set the value that ISO/IEC 646:1991 (International Reference Version) assigns it, `"abc"` as a pattern is identical to `[0x61, 0x62, 0x63]`.)

&mdash; **Range pattern** &mdash; `a..=b` matches a value `v` where `a <= v` and `v <= b` hold, and `a..b` matches one where `a <= v` and `v < b` hold.

&mdash; **Binding pattern** (`@`) &mdash; `name @ sub_pattern` applies both `name` and `sub_pattern` to the matched value, and matches where both match.

&mdash; **Or-pattern** &mdash; `p | q` matches where its **leading pattern** `p` or its **following pattern** `q` matches.

A `let` **governs** the `pattern_body` or `field_pat` it precedes and every pattern and `field_pat` within it. An identifier pattern that a `let` governs binds, whether or not a name of its spelling is directly visible there.

Where a `let`, or the `pattern` that follows an `@`, belongs, in different derivations of a source unit, to patterns that comprise different tokens, it belongs to the one that comprises the most tokens.

Where the matched type of a literal, range, `wild`, composite, anonymous struct, slice, or string literal pattern is a reference type, the pattern applies reference transparency, as the clause on expressions defines it, to the matched value: the matched type of the pattern is instead the referent type, and its matched object the referent. The pattern matches a value of the reference type where it so matches the value the referent holds.

Matching that reaches a portion through an unmanaged reference requires airside.

#### Dynamic semantics

A **portion** is the matched object itself, a discriminant, a field, or an element, whether held by value or reached through a reference. A reference through which reference transparency reaches a matched object is also a portion.

A matching applies the patterns of a construct, and the `ident_pat` of its `else_bind`, to one of the following:

&mdash; The value that the subclause defining that construct states to be matched, or to which it applies those patterns.

&mdash; A payload of that value.

A matching begins after the evaluation that yields that value. It ends where the objects of the bindings that receive values from it are initialized or, where none does, at its last comparison. Where that evaluation yields the current value of an object, the matching performs, at its start, the one load of that object that obtains that value.

Where that subclause states the value to be matched against no pattern, the matching compares the discriminant of the value, and then applies the `ident_pat` after `->` of that construct, where it has one, to the success payload of a value of the success variant.

Where a matching first reaches a referent that reference transparency makes a matched object, it performs one load of that referent, through the reference whose value an earlier load of the matching obtained. Every comparison of a matching, and every binding of it that binds a portion, obtains the value of that portion from the value that evaluation yields and from the loads of such referents. The matching performs no other load.

A pattern compares its portions in leading-to-following order and stops at the first comparison that fails, except that the failure of the leading pattern of an or-pattern moves on to its following pattern.

#### Constraints

The leading pattern and the following pattern of an or-pattern shall bind the same names with the same types and the same binding kind.

An `ident_pat` or `field_pat` that carries `mut`, and a `field_pat` that carries an identifier before `=`, shall bind a name.

A pattern that matches no value of the matched type under any eligible resolution of the generic parameters that occur free in that type shall not appear.

The path of a composite pattern shall denote the matched type or a variant of it.

A string literal pattern shall appear only where the element type of the matched type is `ui1`.

### 4.11.2 Struct destructuring

#### Static semantics

A **destructuring pattern** is a composite pattern other than its path alone, or an anonymous struct pattern.

A **named-field destructuring** is a destructuring pattern whose path denotes a type or variant in named-field form. In it, a `field_pat` designates a field by `.field_name`. Where a `let` governs it, the form `.field_name` binds the field value to `field_name`, and the form `binding_name = .field_name` binds it to `binding_name`. A following `@ sub_pattern` applies the sub-pattern to the field value.

`...` at the end of the field list matches the fields the pattern does not mention, without binding them.

An **unnamed-field destructuring** is a destructuring pattern whose path denotes a type or variant in unnamed-field form, or an anonymous struct pattern. Each pattern its `unnamed_pat_list` lists designates the field at its position, counting in declaration order, and is applied to that field.

#### Constraints

Every field of a named-field destructuring, other than a `?` field, shall be mentioned unless the pattern ends with `...`.

The `unnamed_pat_list` of an unnamed-field destructuring shall list as many patterns as the matched type or variant has fields.

A destructuring pattern shall not be applied, directly or through a reference, to a value of a type that declares `with destruct`.

#### Examples (informative)

```
// Struct in named-field form
struct point { x: si4, y: si4 }
let point.{ .x, .y } = get_point();       // all fields
let point.{ px = .x, ... } = get_point(); // y ignored
let point.{ origin = .x @ 0, oy = .y } = get_point() else {
    return; // x bound to origin, constrained to 0
};

// Enum with a variant in named-field form
match e {
    // fields other than key ignored
    let event::key_press.{ .key, ... } -> handle(key);
    event::quit                       -> quit();
    wild                              -> ignore();
}

// Anonymous struct destructuring
let .{ a, b } = get_pair(); // all fields, positional order
// let .{ a, ... } = get_pair();
// translation failure: ... not permitted
```

### 4.11.3 Pattern bindings

#### Static semantics

A pattern binding holds the value of the portion its identifier pattern or `field_pat` binds, copied or transferred into it as the clause on references and resource management defines.

A pattern introduces one binding for each of the following that it contains, counting, of each or-pattern within it, its leading pattern alone: an identifier pattern or `field_pat` that a `let` governs, and a `wild_pat` that carries an identifier. In the following pattern of each such or-pattern, each of these binds its name to the binding that name has in its leading pattern.

#### Examples (informative)

```
let struct_t.{ .a, mut .b, .c } = get_structure();
// a and c are single-assignment, b is multi-assignment
b += 1; // OK: b is mut
// a += 1; // translation failure: a is single-assignment

let .{ x, mut y, z } = get_triple();
y += 1; // OK: y is mut

// Per-binding mut with refutable patterns
let verdict::Pass.{ .{ p, mut q } } = try_get_pair() else { return; };
q += 1; // OK: q is mut
```

### 4.11.4 Refutability

#### Static semantics

A pattern is **irrefutable** where it matches every value of the matched type, and **refutable** otherwise.

A slice pattern is irrefutable where each of its element patterns is irrefutable and the pattern matches every length that a value of the matched type can have under some eligible resolution of the generic parameters that occur free in that type, and refutable otherwise. A rest pattern, as the clause on statements and control flow defines it, is irrefutable. Which lengths a slice pattern matches is defined in the subclause on slice and string literal patterns.

## 4.12 `with` clauses

A `with` clause attaches properties to a declaration or to a subroutine pointer type.

### Syntax

```
with_single  = "with", ws, with_item ;
with_curly   = "with", ws, '{', ws, with_item, ws,
               { ',', ws, with_item, ws }, [ ',', ws ], '}' ;
with_item    = destruct_clause | inv_clause | repr_clause
             | discrim_clause | align_clause | "variadic" | "copyable"
             | subject_bound ;
```

### Static semantics

Each word is defined in the clause where it is introduced:

&mdash; `destruct` &mdash; supplies the destructor of the type (clause on references and resource management).

&mdash; `inv` &mdash; declares the inverted pair of a contract type (clause on statements and control flow).

&mdash; `repr` &mdash; controls representation (clause on types).

&mdash; `discrim` &mdash; sets the discriminant type of a variant type (clause on types).

&mdash; `align` &mdash; sets minimum alignment (clause on types).

&mdash; `variadic` &mdash; declares a variadic state type (clause on types).

&mdash; `copyable` &mdash; makes the type copyable where each of its constituents is (clause on references and resource management).

&mdash; `impl` &mdash; requires an implantation of a protocol for a type (clause on protocols and implantations).

### Constraints

Within a clause enclosed by curly brackets, each word other than `impl` shall appear at most once. A `with` word shall appear only on the declaration kinds and type kinds for which it is defined.

A `with` clause shall not combine `variadic` with `repr`, `destruct`, or `copyable`, nor `copyable` with `destruct`.

### Examples (informative)

```
// with_single form
struct handle { fd: si4 } with destruct { close(self.fd); };

// with_curly form
struct packet {
    header: ui4,
    payload: &[ui1]
} with {
    repr(pack(1)),
    align(4)
}
```

## 4.13 Visibility and name introduction

A **named item** is a variant, an implanted constant, an implanted subroutine, or a declaration that introduces a name.

### 4.13.1 Visibility modifier

#### Static semantics

A declaration marked `pub` is visible outside the namespace that declares it. A variant is visible wherever the declaration that declares it is visible. Where a declaration introduces a namespace identifier, `pub` upon it applies to every one it introduces, and the visibility of the declarations within the namespace is governed by `pub` upon those declarations independently. Namespaces, and the visibility a path requires at each of its segments, are defined in the clause on programme structure and translation.

### 4.13.2 Unqualified name introduction

#### Syntax

```
use_decl = [ "pub", ws ], "use", ws, use_tree, ws, ';' ;
use_tree = single_path, [ ws, "as", ws, identifier ]
         | path_prefix, '*'
         | path_prefix, '{', ws, use_tree, ws,
           { ',', ws, use_tree, ws }, [ ',', ws ], '}' ;
```

#### Static semantics

Each `use_tree` selects one or more named items and introduces names for them. Each name that a `use_tree` introduces stands, where it appears, for the path by which that `use_tree` selects the item named. Each identifier of that path is resolved as at the `use_decl`. For a child that a `use_tree` ending in `*` selects, that path is the `path_prefix` followed by the name of the child.

A `use_tree` consisting of a `single_path` selects the item denoted by the path. Its introduced name is the identifier of its `as` clause where one is present, and otherwise the identifier of the final segment of its path.

In a `use_tree` enclosed by curly brackets, the `path_prefix` preceding `{` is prepended to the path or `path_prefix` of each `use_tree` within.

A `use_tree` ending in `*` selects the children of the namespace that the last segment of its `path_prefix` reaches that are visible where the `use_decl` appears.

The visibility modifier of a `use_decl` applies to every name introduced by the declaration.

#### Constraints

&mdash; Each path selecting an item shall denote a named item.

&mdash; The last segment of each `path_prefix` preceding `{` or `*` shall reach a namespace, and, in a `use_tree` that no other `use_tree` contains, such a `path_prefix` shall not be empty.

&mdash; A `use_tree` shall contain no generic argument list.

&mdash; In a `use_tree` that consists of a `single_path` without an `as` clause, the final segment of its path shall be an `identifier`.

&mdash; Each item selected by a `pub use` declaration shall be visible outside the namespace that encloses the `pub use` declaration.

#### Examples (informative)

```
use math::sqrt;
let r = sqrt(2.0); // unqualified access

use io::{ read, write, close }; // multi-import

use collections::map as dictionary;

#add "bool.kr" as booleans;
use booleans::*;

pub use root::{
    branch::leaf,
    nested::{
        item as renamed,
        children::*
    }
};

use colour::red;
use colour::{ green, blue };
// red, green, blue can be used without the colour:: prefix.

let c = red;   // equivalent to colour::red

// Implanted constant
use si4::max;  // imports the implanted constant si4::max
let m = max;   // equivalent to si4::max

// Implanted subroutine
use vec::new;  // imports the implanted subroutine vec::new
let v: vec[si4] = new(); // equivalent to vec[si4]::new()
```

## 4.14 Global `instruct` blocks

A **global `instruct` block** is an `instruct` block that is a `global_instruct`. It embeds instructions into the opaque code. Inline `instruct` blocks are defined in the clause on expressions.

### Syntax

```
global_instruct = "instruct", ws, instruct_body ;
```

### Static semantics

The `instruct_body` production is defined in the clause on expressions, and where an `instruct` block ends in the clause on lexical structure.

Within a global `instruct` block, an inline expression (`'(expr)`) is the only form that injects a translation-time value into the instruction text.

A global `instruct` block may define external symbols through implementation-defined directives. A symbol so defined is resolved in the same manner as a symbol produced by an `extern` declaration.

### Implementation defined

The set of supported environments of the programme machine for global `instruct` blocks is implementation defined.

### Examples (informative)

```
const stack_size: uaddr = 4096 * 4;

instruct {
    .section .bss
    .align 16
    stack_bottom:
        .skip '( stack_size )
    stack_top:
}

instruct {
    .global _start
    _start:
        call main
}
```

## 4.15 `#inline` and `#no_inline`

The `#inline` and `#no_inline` directives annotate the definition of a subroutine.

### Syntax

```
inline_directive    = '#inline' ;
no_inline_directive = '#no_inline' ;
```

### Constraints

`#inline` and `#no_inline` shall stand only upon a subroutine definition or the definition of an implanted subroutine, and shall not both stand upon the same one.

### Implementation requirements

Where `#inline` is applied, the implementation should substitute the body of the annotated subroutine at each of its invocation sites.

Where `#no_inline` is applied, the instructions into which the body of the annotated subroutine is translated shall stand in the opaque code at most once, in a form invocable through the invocation interface of that subroutine. Each evaluation, in execution after translation, of an invocation of the subroutine shall invoke those instructions through that interface, and control shall be able to return from their execution into the instructions of the invoker, whether or not the subroutine declares `-> !`. Where every invocation of the subroutine lies within an evaluation root, within an analysis root of the translation machine, or within a leading branch of a `xlat?` or `arbit?` conditional, the subroutine stands in the opaque code where the subclause on external declaration retains it.

### Design rationale (informative)

Failure to honour `#inline` affects performance alone. A programme can depend on a subroutine remaining a discrete symbol in the opaque code, and on the instructions of its body being executed at one place. Disregarding `#no_inline` can therefore cause malfunction that no diagnostic can detect.

### Examples (informative)

```
#inline
fn fast_abs(x: si4) -> si4 {
    return if x < 0 then -x else x;
}

#no_inline
fn cold_path(err: error_code) -> ! {
    log_error(err);
    trap();
}

// #no_inline on a hook point: external tools may patch this symbol
#no_inline
extern fn trace_entry(id: ui4) {
    // body may be empty.
}

impl counter {
    #inline
    pub fn get(&self) -> uaddr { return self.val; }
}
```

## 4.16 Symbol identification

The `#symbol` directive sets the external name of a declaration to an identification string.

### Syntax

```
symbol_directive = '#symbol', ws, string_literal ;
```

### Static semantics

Where `#symbol` is present, the external name is the content of its string literal.

### Constraints

`#symbol` shall stand only upon a subroutine definition, the definition of an implanted subroutine, a `static` declaration, or a `dyn_subroutine`.

Distinct external symbols the opaque code of a translation unit contains shall have distinct external names.

### Implementation defined

What the string literal means is implementation defined for each supported environment of the programme machine and of the translation machine.

### Examples (informative)

```
// The Kurt subroutine kurt_compress is exported as “compress”
#symbol "compress"
extern fn kurt_compress(src: &[ui1], dst: $[ui1])
    -> verdict[uaddr, void] {
    ...
}

// The Kurt static is exported as “global_state”
#symbol "global_state"
extern static mut state: app_state = default();

// #symbol shall not stand upon a constant
// #symbol "limit"
// const limit: ui4 = 64; // translation failure
```

## 4.17 Annotations

An annotation attaches implementation-specific information to an item.

### Syntax

```
annotation         = '#[', annotation_content, ']#' ;
annotation_content = ? implementation defined ? ;
```

### Constraints

A `#[` without a matching `]#` shall not appear.

### Implementation requirements

The implementation may assign meaning to an annotation it recognizes. The meaning it assigns shall leave unchanged both the behaviour this specification defines for the programme and which source units the implementation rejects.

### Implementation defined

The structure and the meaning of the content between `#[` and `]#` are implementation defined.

### Examples (informative)

```
#[hot]#
fn dispatch(op: ui1) -> si4 { ... }

#[cold]#
fn report_failure(code: si4) { ... }

#[section ".boot"]#
airside fn reset_vector() { ... }
```

## 4.18 Name extent and duplication

### Static semantics

The **extent** of a name is the part of the source text into which it is introduced, or, for a name that the source text does not introduce, the **outermost extent**, which encloses every source unit. Two names are compared, by the rules of this subclause, only where the same position can refer to either.

A name is **in force** at each position of its extent other than the positions before the end of the `let` declaration that introduces it and the positions within the `use` declaration that introduces it.

The namespace that **declares** a name is the innermost namespace that encloses the declaration introducing it.

A name in force at a position is **hidden** there by each other name of the same spelling that is in force there and that is in force at a proper subset of the positions at which the first is in force. A name is **directly visible** where it is in force and not hidden. Within a `module`, a name whose extent is a namespace that encloses that `module` hides no name and is not directly visible. A name is **visible** where it is in force, throughout the namespace that declares it, and elsewhere so far as the visibility modifier permits.

Each of the following resolves to the name of its spelling that it can refer to and that is directly visible where it appears:

&mdash; A label name.

&mdash; The `self` of an identifier expression.

&mdash; An `identifier` that is the first segment of a path.

&mdash; The identifier that leads a source path.

For `impl` blocks, the uniqueness of protocol implantations and the resolution of item name overlap are defined in the clause on protocols and implantations.

### Constraints

Two names introduced into one scope, one namespace, the outermost extent, or one other part of the source text shall not share a spelling.

A position that resolves as this subclause defines shall appear only where exactly one name of its spelling that it can refer to is directly visible.

The resolution of a name, the type a type alias denotes, and the value of a constant or of the initializer of a `static` binding shall not depend on itself, directly or through other names. Each of them depends on a name where it needs the resolution of that name, the type that name denotes, or the value of the object or the constant that name designates.

### Examples (informative)

```
// Hiding in an inner scope: distinct binding, may share a name
let x: si4 = 1;
{
    // hides outer x: distinct binding, different type
    let x: fe11s52 = 2.0;
    use_float(x); // x is fe11s52 here
}                 // inner x destroyed, outer x directly visible again
use_int(x);       // x is si4 here, value 1

// Duplicate in the same scope: translation failure
// let y = 1;
// let y = 2; // translation failure: y already declared in this scope
```
