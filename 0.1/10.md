# 10. Programme structure and translation

This clause defines programme composition from source units, interaction with opaque code translated beforehand, and conditional translation. Opaque code production and translation unit boundaries are also defined here.

## 10.1 Source units

A **source unit** is the unit of Kurt source text submitted to the implementation for translation. The `source_unit` production is the start symbol of the grammar of this specification.

### Syntax

```
source_unit = ws, { item, ws } ;
```

## 10.2 Source processing order

Translation of a Kurt source unit proceeds in a fixed sequence of stages. Each stage operates on the output of the preceding stage. An implementation need not perform these stages, or the phases within them, as discrete passes. The opaque code and the diagnostics it produces shall be those it would produce if it did.

1. Source processing &mdash; the source unit undergoes source decoding, line ending recognition, the lexical strip, and tokenization, as defined in the clause on lexical structure. The result is an ordered sequence of tokens.
2. `#add` collection and path resolution &mdash; all `#add` declarations in the current source unit are collected. Each referenced source unit undergoes stages 1 and 2 independently. The `#add` dependency graph is constructed. It is a directed graph over the source units, and permits cycles. Duplicate inclusions are resolved as defined in the subclause on source path resolution. `#dyn` declarations are collected.
3. Declaration collection &mdash; all source units reachable via `#add` are traversed and all declarations are collected.
4. Body analysis &mdash; the declarations, subroutine bodies, and initializers of the translation unit are analysed for type correctness; this analysis is **semantic analysis**. Every translation-time evaluation is performed. This stage operates on the whole translation unit at once.
5. Opaque code emission &mdash; the implementation produces the opaque code corresponding to the translation unit.

## 10.3 Source path resolution

A **source path** is the content, after escape resolution, of the string literal of an `#add` or `#path` declaration. A source path that no identifier leads is resolved by the environment of the translation machine. A source path may be led by an identifier (`prefix::"path"`), which resolves to a prefix as defined in the subclause on path prefix declaration.

### Constraints

A source path shall identify a source unit.

### Implementation requirements

Where the same source unit is imported by `#add` more than once &mdash; directly or transitively &mdash; the implementation shall include that source unit in the translation unit once.

### Implementation defined

The mechanism by which the environment of the translation machine resolves a source path to a source unit is implementation defined.

## 10.4 Source-level import

`#add` imports a source unit into the current source unit. It does so under the namespace it introduces.

### Syntax

```
add_decl    = '#add', ws, [ "pub", ws ],
              ( path_form | block_form ), ws, ';' ;
path_form   = [ identifier, ws, '::', ws ], string_literal, ws,
              "as", ws, identifier ;
block_form  = [ identifier, ws, '::', ws ], '{', ws, path_entry, ws,
              { ',', ws, path_entry, ws }, [ ',', ws ], '}' ;
path_entry  = string_literal, ws, "as", ws, identifier ;
```

### Examples (informative)

```
#add "stack.kr" as stack;
#add std::"core.kr" as core;
#add std::{"core.kr" as kcore, "alloc.kr" as alloc, "host.kr" as host};
#add pub {"stack.kr" as pstack, "queue.kr" as queue};
```

## 10.5 External symbol declaration

`#dyn` introduces a namespace of external symbol declarations.

### Syntax

```
dyn_decl       = '#dyn', ws, [ "xlat", ws ], [ "pub", ws ],
                 identifier, ws, '{', ws, { dyn_item, ws }, '}' ;

dyn_item       = { item_prefix, ws }, ( dyn_subroutine | dyn_static ) ;

dyn_subroutine = subroutine_proto_header, ws, subroutine_proto_param,
                 subroutine_sig_tail, ws, ';' ;

dyn_static     = [ "pub", ws ], "static", ws, [ "mut", ws ], identifier,
                 ws, ':', ws, type, ws, ';' ;
```

### Static semantics

A `#dyn` namespace declares external symbols of the environment of the programme machine; a `#dyn xlat` namespace declares external symbols of the environment of the translation machine. Every operation on a symbol declared in a `#dyn xlat` namespace is evaluated at translation time.

A `fn` or `static` declaration within the block of a `#dyn` declaration introduces its name into the namespace that declaration introduces. The external name by which such a declaration is resolved is its identifier, except where a `#symbol` directive upon it supplies another, as the clause on declarations defines.

A `dyn_static` declaration is a `static` declaration that has no initializer. The storage of the object of the binding it introduces is reserved outside the programme.

A subroutine declared in a `#dyn` block is an `airside fn`.

A `dyn_subroutine` with the `variadic` keyword declares that the external subroutine uses the variadic variant of its invocation interface.

### Dynamic semantics

A symbol of the environment of the programme machine that the resolution does not identify uniquely can cause indeterminate state.

### Constraints

An identifier expression or a path expression that names a `static` binding declared in a `#dyn` block requires airside.

A translation-time evaluation shall not invoke a subroutine, or access a `static` binding, declared in a `#dyn` namespace without `xlat`.

A symbol of the environment of the translation machine that the resolution does not identify uniquely is a translation failure.

### Implementation defined

The mechanism by which an external symbol is resolved is implementation defined, in the environment of the translation machine and in that of the programme machine alike.

### Examples (informative)

Pattern 1 &mdash; fully source-local. Neither the namespace nor the symbol is public. The `pub` Kurt wrapper is all an importer sees.

```
#dyn libz {
    fn compress(
        dest: %mut ui1, dest_len: %mut uaddr,
        source: %ui1, source_len: uaddr
    ) -> si4;
}

pub fn compress(src: &[ui1], dst: $[ui1]) -> verdict[uaddr, void] {
    let mut dst_len: uaddr = dst.len;

    let ret = airside {
        express libz::compress(
            dst.ptr, %mut dst_len, src.ptr, src.len
        );
    };

    return if ret == 0 then verdict::Pass.{ dst_len }
        else verdict::Fail.{ void };
}
```

Pattern 2 &mdash; explicit invocation interface.

```
#dyn efi {
    extern(efi) fn entry(handle: uaddr, table: %ui1) -> uaddr;
    fn helper(x: si4) -> si4; // native invocation interface
}
```

Pattern 3 &mdash; external name differs from Kurt name.

```
#dyn weird {
    #symbol "__weird_internal_v2"
    fn compress_weird(x: si4) -> si4;
}
```

Pattern 4 &mdash; static binding import.

```
#dyn libc {
    static errno: si4;
    #symbol "optarg"
    static mut opt_arg: %ui1;
}
```

Pattern 5 &mdash; fully public. Both namespace and symbol are public. Importers can invoke the foreign subroutine directly, subject to the airside requirement at each invocation site.

```
#dyn pub libfast {
    pub fn fast_op(x: si4) -> si4;
}
```

Pattern 6 &mdash; namespace of the environment of the translation machine.

```
#dyn xlat host {
    fn getenv(name: %ui1) -> %ui1;
}
```

Pattern 7 &mdash; variadic declaration.

```
#dyn libc {
    variadic fn printf(fmt: %ui1) -> si4;

    #symbol "sprintf"
    variadic fn kurt_sprintf(buf: %mut ui1, fmt: %ui1) -> si4;

    fn vprintf(fmt: %ui1, args: va_list) -> si4;
}

// Kurt-side subroutine with variadic binding
variadic(args: va_list) fn printf(fmt: %ui1) -> si4 {
    return airside { express libc::vprintf(fmt, args); };
}
```

## 10.6 Path prefix declaration

A **prefix** is a name that stands for a source path and that may lead the source path of an `#add` declaration. `#path` declares one that stands for its own source path.

### Syntax

```
path_decl = '#path', ws, [ "pub", ws ], string_literal, ws, "as", ws,
            identifier, ws, ';' ;
```

### Static semantics

The environment of the translation machine may supply prefixes by a mechanism outside the source text.

An `#add` whose source path is led by an identifier is resolved relative to the source path for which the prefix that identifier resolves to stands, as the clause on declarations defines that resolution.

### Constraints

The name to which the identifier that leads a source path resolves shall be a prefix, and nothing that any other position resolves to or reaches shall be a prefix.

### Implementation defined

The mechanism by which the environment of the translation machine supplies a prefix outside the source text is implementation defined.

### Examples (informative)

```
#path "/usr/lib/kurt/vendor" as vend;
#add vend::"zlib/lib.kr" as zlib;
// under POSIX resolution rules this names
// /usr/lib/kurt/vendor/zlib/lib.kr. How a prefix and a source path
// combine is part of source path resolution.

#path "/usr/lib/kurt/std" as std;
#add std::"posix.kr" as posix;

// A prefix may follow the #add it leads. A second declaration
// of vend in this source unit would be a translation failure.
#add vend24::"zlib/lib.kr" as old;
#path "vendor/2024" as vend24;
```

## 10.7 Namespaces and `module`

`module` declares a namespace within a source unit.

### Syntax

```
module_decl = [ "pub", ws ], "module", ws, identifier, ws, '{',
              ws, { item, ws }, '}' ;
```

`super` and `srcroot` are alternatives of the `path_segment` production, defined in the clause on expressions.

### Static semantics

A `module`, a `#dyn` declaration, and each `as` identifier of a `#add` declaration introduce a namespace identifier.

Each of the following is a namespace:

&mdash; The **top-level namespace** of a source unit.

&mdash; A `module`.

&mdash; A type.

&mdash; A generic declaration of a type or of a type alias.

&mdash; A protocol implantation.

&mdash; The namespace a `#add` or `#dyn` declaration introduces.

Each namespace that encloses part of the source text, other than a top-level namespace, has as its **parent** the namespace that encloses it. The **children** of a namespace other than that of a protocol implantation or of a generic declaration of a type or of a type alias are the names introduced into it and the following:

&mdash; For the namespace a `#add` declaration introduces &mdash; the names introduced into the top-level namespace of the source unit it adds.

&mdash; For the namespace of a type &mdash; the implanted items to which the clause on protocols and implantations resolves a path from that namespace.

The children of the namespace of a generic declaration of a type or of a type alias are the names that are children of the namespace of every instantiation of that declaration and whose variant or implanted item one declaration introduces in each. Each such child denotes that variant or implanted item.

The children of the namespace of a protocol implantation are the implanted items to which the clause on protocols and implantations resolves a path from it.

Each of the following encloses no part of the source text:

&mdash; The namespace of a type.

&mdash; The namespace of a generic declaration of a type or of a type alias.

&mdash; The namespace of a protocol implantation.

&mdash; The namespace a `#add` declaration introduces.

A path reaches its segments in path order. Before its first segment, a path has reached the innermost namespace that encloses it. Each segment reaches the following from what the path has reached before it:

&mdash; An `identifier` segment reaches, as the first segment, what the name it resolves to denotes, as the clause on declarations defines. Otherwise it reaches what the child of that name denotes. Outside a `use_tree`, where what the path has reached before it is the namespace of a generic declaration of a type or of a type alias, the segment reaches what the child of the name that its `identifier` resolves to denotes in the namespace of an instantiation of that declaration.

&mdash; A `super` segment reaches the parent of the namespace reached.

&mdash; A `srcroot` segment reaches the top-level namespace of the source unit in which the path appears.

&mdash; A `selftype` segment reaches the type that `selftype` stands for.

&mdash; A qualified segment `(T impl Protocol)` reaches the namespace of the implantation of `Protocol` for `T`.

The path denotes what its final segment reaches.

### Constraints

At each `identifier` segment of a path, what it reaches shall be declared or shall be a type, and shall be visible at the point where the path appears.

Each segment of a path other than the final shall reach a namespace.

Where a `super` segment appears, the namespace the path has reached before it shall have a parent.

### Design rationale (informative)

`super` is meaningful only within the strict tree formed by `module` nesting. The `#add` dependency graph between source units can form an arbitrary directed graph, including cycles. No unique enclosing source unit exists, so `super` at the top level of a source unit names nothing. `srcroot` is unaffected, naming a fixed point within the current source unit regardless of how the source unit is reached.

### Examples (informative)

```
pub module io {
    pub fn read(fd: si4, buf: $[ui1]) -> saddr { ... }
    pub fn write(fd: si4, buf: &[ui1]) -> saddr { ... }
    fn internal_helper() { ... }
}

fn main() {
    let n = io::read(0, buf);
}
```

```
fn do_thing() { ... }

pub module foo {
    pub fn bar() {
        super::do_thing();
    }

    module nested {
        fn baz() {
            super::bar();
            super::super::do_thing();
            srcroot::do_thing();
        }
    }
}
```

```
module internal {
    pub fn helper() { ... }
}
// internal::helper is accessible in this source unit only.

pub module api {
    pub fn entry() { ... }
    fn detail() { ... }
}
// Importers can invoke api::entry but not api::detail.
```

## 10.8 Flag declaration

A **flag** is a name whose existence is determined at translation time.

### Syntax

```
flag_decl   = '#flag', ws, '(', ws, identifier, ws, ')' ;
unflag_decl = '#unflag', ws, '(', ws, identifier, ws, ')' ;
```

### Static semantics

`#flag` makes the flag it names exist, and `#unflag` makes it not exist, from the point where the directive appears to the end of the source unit in which it appears.

The environment of the translation machine may supply flags by a mechanism outside the source text. Such a flag is treated as if `#flag` naming it appeared before the first line of each source unit in the translation unit.

### Implementation defined

The mechanism by which the environment of the translation machine supplies a flag outside the source text, and the flags it supplies, are implementation defined.

### Examples (informative)

```
#flag(debug)
#flag(embedded)

// included if verbose exists
#flag_if(verbose) fn verbose_init() { ... } ##

#unflag(verbose)

// excluded
#flag_if(verbose) fn verbose_cleanup() { ... } ##

#flag(verbose) // verbose is back on

// included
#flag_if(verbose) fn verbose_shutdown() { ... } ##
```

## 10.9 Conditional translation

`#flag_if(expr)` conditionally includes a region of source text based on a flag expression.

### Syntax

```
flag_if_chain = flag_if_branch,
                { flag_else_if_branch },
                [ flag_else_branch ],
                [ '#flag_endif', { hs }, nl ] ;

flag_if_branch      = '#flag_if', ws, '(', ws, flag_expr, ws, ')',
                      ( line_body | block_body ) ;
flag_else_if_branch = '#flag_else_if', ws, '(', ws, flag_expr, ws, ')',
                      ( line_body | block_body ) ;
flag_else_branch    = '#flag_else', ( line_body | block_body ) ;

line_body  = ? inline source text ?, { hs },
             ( '#' | '##' ), { hs }, nl ;
block_body = { hs }, nl, ? source text ? ;

flag_expr = identifier
          | '!', ws, flag_expr
          | flag_expr, ws, "and", ws, flag_expr
          | flag_expr, ws, "xor", ws, flag_expr
          | flag_expr, ws, "or",  ws, flag_expr
          | '(', ws, flag_expr, ws, ')' ;
```

### Static semantics

A flag name **holds** if and only if the flag exists. `!`, `and`, `xor`, and `or` combine flag expressions by negation, conjunction, exclusive disjunction, and disjunction respectively. `!` binds most tightly, then `and`, then `xor`, then `or`. Each binary operator is leading-to-following associative.

A `#flag_if` directive begins a **chain**, and the matching `#flag_endif` or `##` terminator ends it. The `#flag_else_if` and `#flag_else` directives of a chain are those it contains that no chain within it contains. Each directive of a chain, with the source text it guards, is a **branch** of that chain.

The **terminator** of a branch is located on the line its directive stands on, the whitespace at the end of that line set aside. Where the last two characters that remain are `##`, they are the terminator. Otherwise, where the last character is `#`, it is the terminator. Otherwise the line carries no terminator.

Where the line a branch’s directive stands on carries a terminator, the branch is a **line branch**: its directive and its guarded text stand on that one line, and the guarded text runs from the end of the directive to the terminator. A `#` terminator ends the branch and leaves the chain open to a further branch. Where that line carries no terminator, the branch is a **block branch**: its guarded source text begins on the next line, and the chain continues only at a `#flag_else_if`, a `#flag_else`, or a `#flag_endif`.

The **included branch** of a chain is the first branch whose flag expression holds. A `#flag_else` is the included branch where no branch before it is included.

### Constraints

The constraints defined in this subclause apply to every `#flag_`-prefixed directive and every line-branch terminator, whether or not the enclosing branch is the included one. No constraint applies to source text of a branch that is not the included branch and that is neither a `#flag_`-prefixed directive nor a line-branch terminator.

A `#flag_`-prefixed directive shall be the first non-whitespace sequence on its line. The following shall not appear:

&mdash; A block-branch directive, or a `#flag_endif`, followed on its line by any character other than whitespace.

&mdash; An included line branch whose guarded text opens a literal, a comment, or an `instruct` block that does not close before the terminator.

&mdash; `#flag_endif` in a chain whose last branch is a line branch.

&mdash; A chain whose last branch is a line branch terminated by `#` rather than `##`.

&mdash; A chain whose last branch is a block branch and that has no `#flag_endif`.

&mdash; A `#flag_endif` that ends no chain, or a `#flag_else_if` or `#flag_else` that no chain contains.

&mdash; `#flag_else_if` after `#flag_else`, or duplicate `#flag_else` within the same chain.

### Examples (informative)

```
// Block branches
#flag_if(linux)
    fn epoll_create() -> si4 { ... }
    fn epoll_wait() -> si4 { ... }
#flag_endif

// Line branches
#flag_if(windows) let sep = '\\'; #
#flag_else let sep = '/'; ##

// Mixed: line and block branches in one chain
#flag_if(fast_path) return cached; #
#flag_else
    let result = compute(data);
    cache_store(result);
    return result;
#flag_endif

// Nested (block branches only)
#flag_if(linux)
    #flag_if(x86)
        fn sse_stuff() -> si4 { ... }
    #flag_else
        fn generic_simd() -> si4 { ... }
    #flag_endif
    fn common_linux() -> si4 { ... }
#flag_endif

// Inside a subroutine body
fn process(data: &[ui1]) -> verdict[void, error] {
    #flag_if(debug)
        log_entry(data);
    #flag_endif
    let result = transform(data)?;
    #flag_if(debug) log_exit(result); ##
    return verdict::Pass.{ void };
}

// An excluded branch is not tokenized, so its text need not be valid.
// The terminator ends the line branch. The `#` within does not.
#flag_if(impossible) ab"#@mx???H4& ##
```

## 10.10 Translation output

A translation of a Kurt source unit that incurs no translation failure produces **opaque code**: the instructions into which the unit is translated, together with what the resolution of external symbols requires.

The implementation may produce an interface source. An **interface source** is a Kurt source text that describes the `pub`-visible interface of the translated unit. It contains a `#dyn` declaration referencing the opaque code and re-declares the `pub`-visible subroutine signatures, type declarations, and constants. It is an ordinary source unit and may be imported via `#add` by other source units.

### Implementation requirements

The opaque code shall refer to no external symbol other than one that it defines or that a `#dyn` declaration of the programme declares, except where the instruction text of an `instruct` block carries the reference.

### Implementation defined

The arrangement of the opaque code is implementation defined. The mechanism by which an interface source is generated, and whether it is generated automatically or on request, is implementation defined.

### 10.10.1 Invocation interface

#### Static semantics

An **invocation interface** is the set of conventions by which an invoker and an invoked subroutine agree upon the placement of the arguments and of the returned value, and upon the state each preserves across the invocation.

#### Dynamic semantics

Each of the following invocations can cause indeterminate state:

&mdash; One performed through an invocation interface other than the invocation interface of the invoked subroutine.

&mdash; One performed through a subroutine pointer type whose number of fixed parameters differs from that of the invoked subroutine.

&mdash; One that stores the value of an argument through a type whose size is greater than the size of the type of the fixed parameter of the invoked subroutine at the position of the parameter to which that argument corresponds.

#### Implementation defined

The invocation interfaces, the identifier that selects each, and the one `native` denotes are implementation defined for each supported environment of each machine.

### 10.10.2 Translation unit definition

A **translation unit** consists of a root source unit together with the `#add` dependency graph reachable from it.

Within a translation unit, a type is the type its declaration introduces. A type one translation unit declares and a type another declares are the same type where their declarations agree in everything this specification determines from them, other than the identifiers they introduce. For this comparison, an identifier that names a declaration stands for the declaration it names, corresponding generic parameters are taken to be the same, and any two declarations already under comparison are taken to be the same. Two protocol declarations are the same where they are congruent, as the clause on protocols and implantations defines congruence.
