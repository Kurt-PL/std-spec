# §10. Programme structure and translation

This clause defines programme composition from source units, interaction with opaque code translated beforehand, and conditional translation. Opaque code production and translation unit boundaries are also defined here. The evaluation semantics of `xlat` blocks are defined in the clause on expressions.

## 10.1 Source units

A **source unit** is the unit of Kurt source text submitted to a conforming implementation for translation. The `source_unit` production is the start symbol of the grammar of this specification.

### Syntax

```
source_unit = ws, { item, ws } ;
```

A **source path** is a string literal appearing as the argument to `#add` or `#path`. A source path without a prefix is resolved by the translation environment. A source path may carry a prefix (`prefix::"path"`), which is declared as defined in the subclause on path prefix declaration.

## 10.2 Source processing order and name resolution

Translation of a Kurt source unit proceeds in a fixed sequence of stages. Each stage operates on the output of the preceding stage. An implementation need not perform these stages, or the phases within them, as discrete passes. It shall produce results as if it did.

1. Source processing — the source unit undergoes source decoding, line ending recognition, the lexical strip, and tokenization, as defined in the clause on lexical structure. The result is an ordered sequence of tokens.
2. `#add` collection and path resolution — all `#add` declarations in the current source unit are collected. Each referenced source unit undergoes stages 1 and 2 independently. The `#add` dependency graph is constructed. It is a directed graph over the source units, and permits cycles. Duplicate inclusions are resolved as defined in the subclause on source path resolution. `#dyn` declarations are collected.
3. Declaration collection — all source units reachable via `#add` are traversed and all declarations are collected. Subroutine bodies and initializers are analysed at the stage that follows.
4. Body analysis — after all declarations are collected, subroutine bodies and initializers are analysed for type correctness, and every evaluation that takes place in translation-time evaluation is performed. This stage operates on the whole translation unit at once. All `pub` declarations from all `#add`-reachable source units are collected before it begins, whatever the shape of the `#add` graph. Which of them are visible is determined by the visibility rules of the subclause on source-level import.
5. Opaque code emission — the implementation produces the opaque code corresponding to the translation unit.

Translation time encompasses all five stages above. Execution time begins when the opaque code commences execution in the execution environment and ends when the programme terminates.

## 10.3 Source path resolution

### Constraints

A source path that does not identify a source unit is a translation failure.

### Implementation requirements

If the same source unit is `#add`-ed more than once — directly or transitively — the implementation shall process it exactly once.

### Implementation defined

The mechanism by which the translation environment resolves a source path to a source unit is implementation defined.

## 10.4 Source-level import

`#add` imports a source unit into the current translation. It makes the `pub`-visible declarations of the referenced source unit available under a qualified namespace name.

### Syntax

```
add_decl    = '#add', ws, [ "pub", ws ],
              ( path_form | block_form ), ws, ';' ;
path_form   = [ identifier, ws, '::', ws ], '\"', source_path, '\"',
              ws, "as", ws, identifier ;
block_form  = [ identifier, ws, '::', ws ], '{', ws, path_entry, ws,
              { ',', ws, path_entry, ws }, [ ',', ws ], '}' ;
path_entry  = '\"', source_path, '\"', ws, "as", ws, identifier ;
source_path = ? a character sequence that the translation
                environment resolves to a source unit ? ;
```

### Static semantics

The `as` identifier introduces a namespace identifier into the enclosing scope.

Visibility of individual declarations within the imported source unit is governed by `pub` on those declarations independently.

### Examples (informative)

```
#add "stack" as stack;
#add std::"core" as core;
#add std::{"core" as core, "alloc" as alloc, "host" as host};
#add pub {"stack" as stack, "queue" as queue};
```

## 10.5 External symbol declaration

`#dyn` introduces a namespace of external symbol declarations. All declarations within a `#dyn` block are implicitly airside.

### Syntax

```
dyn_decl       = '#dyn', ws, [ "xlat", ws ], [ "pub", ws ],
                 identifier, ws, '{', ws, { dyn_item, ws }, '}' ;

dyn_item       = { item_prefix, ws }, ( dyn_subroutine | dyn_static ) ;

dyn_subroutine = subroutine_proto_header, ws, subroutine_proto_param,
                 [ ws, subroutine_return ], ws, ';' ;

dyn_static     = [ "pub", ws ], "static", ws, [ "mut", ws ], identifier,
                 ws, ':', ws, type, ws, ';' ;
```

### Static semantics

A `#dyn` namespace declares external symbols of the execution environment; a `#dyn xlat` namespace declares external symbols of the translation environment. Every operation on a symbol declared in a `#dyn xlat` namespace is evaluated at translation time wherever it appears. Only the resulting value is incorporated into the opaque code.

The identifier establishes a namespace and is declared in the enclosing scope. A `fn` or `static` declaration within the block is declared in that namespace. The external name by which such a declaration is resolved is its identifier, except where a `#symbol` directive upon it supplies another, as the clause on declarations defines.

A `dyn_static` declaration introduces a reference to an external global binding. `static` without `mut` permits load access only. `static mut` permits load and store access. The access a `dyn_static` permits is determined by its own declaration, whatever its type. The storage it designates is reserved outside the programme, and the object it designates has the permanent object lifetime, as defined in the clause on semantics.

A `dyn_subroutine` with the `variadic` keyword declares that the external subroutine uses the variadic variant of its invocation interface. The binding that captures the variadic arguments is declared on the Kurt-side subroutine, as defined in the subclause on variadic subroutines.

An external generic subroutine is declared by its lowered signature, as defined in the subclause on signature lowering.

A value passed to a symbol of a `#dyn xlat` namespace, or yielded by one, crosses the boundary of the translation environment’s own code, and the subclause on `asm` in `xlat` converts it. Where the result then reaches an evaluation that observes the execution environment, it crosses by the rules of the subclause on cross-environment value validity.

### Constraints

Invoking a subroutine declared in a `#dyn` block, accessing a `static` binding declared therein, or creating a reference to the object of such a binding or to a constituent object of that object, requires airside.

An invocation of a subroutine, or an access to a `static` binding, declared in a `#dyn` namespace without `xlat` shall not be reached by translation-time evaluation.

### Implementation requirements

The mechanism by which an external symbol is resolved is implementation defined, in the translation environment and in the execution environment alike. A symbol of the translation environment that the resolution does not identify uniquely is a translation failure.

The invocation interface for a subroutine imported via `#dyn` without an `extern` clause is the `native` interface of the namespace’s environment. When an `extern` clause is present, the invocation interface is determined by the parenthesized identifier, following the same rules as the `extern` prefix on subroutine declarations defined in the clause on declarations.

### Examples (informative)

Pattern 1 — fully source-local. Neither the namespace nor the symbol is public. The `pub` Kurt wrapper is all an importer sees.

```
#dyn libz {
    fn compress(
        dest: %mut ui1, dest_len: %mut uaddr,
        source: %ui1, source_len: uaddr
    ) -> si4;
}

pub fn compress(src: &[ui1], dst: $[ui1]) -> verdict.[uaddr, void] {
    let mut dst_len: uaddr = airside { express dst.len; };

    let ret = airside {
        express libz::compress(
            dst.ptr, %mut dst_len, src.ptr, src.len
        );
    };

    return if ret == 0 then verdict::Pass(dst_len)
        else verdict::Fail(void);
}
```

Pattern 2 — explicit invocation interface.

```
#dyn efi {
    extern(efi) fn entry(handle: uaddr, table: %ui1) -> uaddr;
    fn helper(x: si4) -> si4;  // native invocation interface
}
```

Pattern 3 — external name differs from Kurt name.

```
#dyn weird {
    #symbol "__weird_internal_v2"
    fn compress_weird(x: si4) -> si4;
}
```

Pattern 4 — static binding import.

```
#dyn libc {
    static errno: si4;
    #symbol "optarg"
    static mut opt_arg: %ui1;
}
```

Pattern 5 — fully public. Both namespace and symbol are public. Importers may invoke the foreign subroutine directly, subject to the airside requirement at each invocation site.

```
#dyn pub libfast {
    pub fn fast_op(x: si4) -> si4;
}
// Importers can invoke libfast::fast_op directly, within airside.
```

Pattern 6 — namespace of the translation environment. A `#dyn xlat` namespace declares symbols that exist only in the translation environment.

```
#dyn xlat host {
    fn getenv(name: %ui1) -> %ui1;
}
// host::getenv is evaluated at translation time wherever it
// appears. An invocation in execution code is folded to its
// resulting value. Its arguments are translation-time
// constants.
```

Pattern 7 — variadic declaration.

```
#dyn libc {
    variadic fn printf(fmt: %ui1) -> si4;

    #symbol "sprintf"
    variadic fn kurt_sprintf(buf: %mut ui1, fmt: %ui1) -> si4;
}

// Kurt-side subroutine with variadic binding
variadic(args: va_list) fn printf(fmt: %ui1) -> si4 {
    return airside { express libc::printf(fmt, args); };
}
```

Pattern 8 — generic declaration.

```
#dyn libsort {
    pub fn sort(
        out: %mut void, arr: %void, T_type: %void, T_ord: %void
    );
}

pub fn sort.[T: ord](arr: $[T]) {
    airside {
        let mut dummy: void = void;

        let type_bound = contract T'bound(type) else trap();
        let ord_bound = contract T'bound(ord) else trap();

        libsort::sort(
            %mut dummy,
            %arr as! %void,
            type_bound,
            ord_bound,
        );
    }
}
```

## 10.6 Path prefix declaration

`#path` declares a prefix that may lead the source paths of the `#add` declarations that follow it in the source unit in which it appears.

### Syntax

```
path_decl = '#path', ws, '\"', source_path, '\"', ws, "as", ws,
            identifier, ws, ';' ;
```

### Static semantics

The source path of a `#path` declaration is resolved as defined in the subclause on source path resolution.

The translation environment may supply prefixes by a mechanism outside the source text. Such a prefix is treated as if the corresponding `#path` declaration appeared before the first line of each source unit in the translation unit. The mechanism is implementation defined.

An `#add` whose source path carries a prefix is resolved relative to the source path of the last `#path` declaration of the prefix preceding the `#add` in the same source unit.

### Constraints

An `#add` whose source path carries a prefix that no `#path` declaration preceding it in the same source unit declares is a translation failure.

### Examples (informative)

```
#path "/usr/lib/kurt/vendor" as vend;
#add vend::"zlib/lib" as zlib;
// under POSIX resolution rules this names
// /usr/lib/kurt/vendor/zlib/lib. How a prefix and a source path
// combine is part of source path resolution.

#path "/usr/lib/kurt/std" as std;
#add std::"posix.kr" as posix;

#path "vendor/2024" as vend;  // a later declaration of vend. From
#add vend::"zlib/lib" as old; // here on, vend is this one.
```

## 10.7 Inline namespace

`module` declares a namespace scope within a source unit.

### Syntax

```
module_decl = [ "pub", ws ], "module", ws, identifier, ws, '{',
              ws, { item, ws }, '}' ;
```

`super` and `srcroot` are alternatives of the `path_segment` production defined in the clause on expressions.

### Static semantics

A `module` introduces a namespace identifier within its enclosing scope.

`pub` on the `module` keyword applies to the namespace identifier the `module` introduces, as the clause on declarations defines the visibility modifier.

A namespace is a scope: the top-level scope of a source unit, a block, a `module`, a type, or the namespace a `#add` or `#dyn` declaration introduces. A `module`, a type, and a namespace a `#add` or `#dyn` declaration introduces are **named** namespaces. The namespaces of a source unit form a tree in which a namespace is a child of the one that encloses it, and the top-level scope encloses every other. The children of a namespace are also the names it declares, together with the associated items and the variants of a type, as the clause on protocols and implementations and the clause on types define them.

The **root** of a path is its `path_root`, as the clause on expressions defines that production.

— An `identifier` root reaches what the name resolution of the clause on expressions resolves that name to.

— A `super` root reaches the parent of the innermost named namespace that encloses the path.

— A `srcroot` root reaches the top-level scope of the source unit.

— A qualified path root reaches the namespace the clause on expressions assigns it.

Each segment after the root moves once through the tree, in path order.

— An `identifier` segment moves to the child of that name.

— A `super` segment moves to the parent of the namespace that the root or the preceding segment reached.

The path denotes what its final segment reaches. Two paths that reach the same namespace denote the same declaration.

During declaration collection, the implementation collects declarations inside modules as part of the enclosing source unit’s declaration set, recording their qualified paths.

### Constraints

At the root of a path and at each segment, what it reaches shall be declared or shall name a built-in type, and shall be visible at the point where the path appears.

A `super` root or segment shall move from a namespace that has a parent. `srcroot` shall appear only as the root of a path.

A reference to a name outside the enclosing module shall use a path that reaches it.

A `module` shall not be the target of `#add`.

A `module` with the same name as another declaration in the same scope shall not appear.

### Design rationale (informative)

`super` is meaningful only within the strict tree formed by `module` nesting. The `#add` dependency graph between source units can form an arbitrary directed graph, including cycles. No unique enclosing source unit exists, so `super` at the top level of a source unit names nothing. `srcroot` is unaffected, naming a fixed point within the current source unit regardless of how the source unit is reached.

### Examples (informative)

```
pub module io {
    pub fn read(fd: si4, buf: $[ui1]) -> saddr { ... }
    pub fn write(fd: si4, buf: &[ui1]) -> saddr { ... }
    fn internal_helper() { ... }
}

fn main() {
    let n = io::read(0, buf);
}
```

```
fn do_thing() { ... }

pub module foo {
    pub fn bar() {
        super::do_thing();
    }

    module nested {
        fn baz() {
            super::bar();
            super::super::do_thing();
            srcroot::do_thing();
        }
    }
}
```

```
module internal {
    pub fn helper() { ... }
}
// internal::helper is accessible in this source unit only.

pub module api {
    pub fn entry() { ... }
    fn detail() { ... }
}
// Importers can invoke api::entry but not api::detail.
```

```
pub struct str { buf: &[ui1], len: uaddr }

pub module stdin {
    pub fn read_line() -> verdict.[str, io_error] { ... }
    pub fn read_all() -> verdict.[str, io_error] { ... }
}

pub module stdout {
    pub fn print(s: &str) { ... }
    pub fn println(s: &str) { ... }
}

pub module stderr {
    pub fn eprint(s: &str) { ... }
    pub fn eprintln(s: &str) { ... }
}
```

## 10.8 Flag declaration

A **flag** is a name that, at translation time, either exists or does not exist.

### Syntax

```
flag_decl   = '#flag', ws, '(', ws, identifier, ws, ')' ;
unflag_decl = '#unflag', ws, '(', ws, identifier, ws, ')' ;
```

### Static semantics

Flags can be introduced from two sources: source-level (`#flag(name)`) and the implementation-defined external mechanism.

Flags are evaluated in **source order**. `#flag` and `#unflag` take effect at the point where they appear, for the remainder of the source unit in which they appear. `#flag` upon a set flag, and `#unflag` upon an unset flag, have no effect.

Flags introduced by the external mechanism are treated as if `#flag` appeared before the first line of each source unit in the translation unit.

### Examples (informative)

```
#flag(debug)
#flag(embedded)

// included if trace is set
#flag_if(trace) fn traced_init() { ... } ##

#unflag(trace)

// excluded
#flag_if(trace) fn traced_cleanup() { ... } ##

#flag(trace) // trace is back on

// included
#flag_if(trace) fn traced_shutdown() { ... } ##
```

## 10.9 Conditional translation

`#flag_if(expr)` conditionally includes a region of source text based on a flag expression. Where the expression does not hold, the enclosed source text is excluded from translation.

### Syntax

```
flag_if_chain = flag_if_branch,
                { flag_else_if_branch },
                [ flag_else_branch ],
                [ '#flag_endif', { hs }, nl ] ;

flag_if_branch      = '#flag_if', ws, '(', ws, flag_expr, ws, ')',
                      ( line_body | block_body ) ;
flag_else_if_branch = '#flag_else_if', ws, '(', ws, flag_expr, ws, ')',
                      ( line_body | block_body ) ;
flag_else_branch    = '#flag_else', ( line_body | block_body ) ;

line_body  = ? inline source text ?, { hs },
             ( '#' | '##' ), { hs }, nl ;
block_body = { hs }, nl, ? source text ? ;

flag_expr = identifier
          | '!', ws, flag_expr
          | flag_expr, ws, "and", ws, flag_expr
          | flag_expr, ws, "xor", ws, flag_expr
          | flag_expr, ws, "or",  ws, flag_expr
          | '(', ws, flag_expr, ws, ')' ;
```

### Static semantics

A flag expression **holds** or does not hold. A flag name holds if and only if the flag exists. `!`, `and`, `xor`, and `or` combine flag expressions by negation, conjunction, exclusive disjunction, and disjunction respectively. `!` binds most tightly, then `and`, then `xor`, then `or`. Each binary operator is leading-to-following associative.

The **terminator** of a branch is located on the line its directive stands on, the whitespace at the end of that line set aside. Where the last two characters that remain are `##`, they are the terminator. Otherwise, where the last character is `#`, it is the terminator. Otherwise the line carries no terminator.

Where the line a branch’s directive stands on carries a terminator, the branch is a **line branch**: its directive and its guarded text stand on that one line, and the guarded text runs from the end of the directive to the terminator. A `#` terminator ends the branch and leaves the chain open to a further branch; a `##` terminator ends the branch and the chain. Where that line carries no terminator, the branch is a **block branch**: its guarded source text begins on the next line, and the chain continues only at a `#flag_else_if`, a `#flag_else`, or a `#flag_endif`.

Block branches may be nested. Chains may appear at any level.

Branch evaluation proceeds in source order. The **included branch** of a chain is the first branch whose flag expression holds. A `#flag_else` is the included branch where no branch before it is included.

### Constraints

A `#flag_`-prefixed directive shall be the first non-whitespace sequence on its line. The following shall not appear:

— A block-branch directive, or a `#flag_endif`, followed on its line by any character other than whitespace.

— An included line branch whose guarded text opens a literal, a comment, or an `asm` block that does not close before the terminator.

— `#flag_endif` in a chain whose last branch is a line branch.

— A chain whose last branch is a line branch terminated by `#` rather than `##`.

— Absence of `#flag_endif` from a chain whose last branch is a block branch.

— Unmatched `#flag_endif`, `#flag_else_if`, or `#flag_else` without a preceding `#flag_if` at the same depth.

— `#flag_else_if` after `#flag_else`, or duplicate `#flag_else` within the same chain.

### Implementation requirements

Inactive source text shall not be present in the opaque code.

All constraints defined in this subclause activate at the point at which the scanner recognizes a `#flag_`-prefixed directive, whether or not the enclosing branch is active. No constraint applies to source text of an inactive branch that is neither a `#flag_`-prefixed directive nor a line-branch terminator. Every constraint of this specification applies to the source text of an active branch.

### Examples (informative)

```
// Block branches
#flag_if(linux)
    fn epoll_create() -> si4 { ... }
    fn epoll_wait() -> si4 { ... }
#flag_endif

// Line branches
#flag_if(windows) let sep = '\\'; #
#flag_else let sep = '/'; ##

// Mixed — line and block branches in one chain
#flag_if(fast_path) return cached; #
#flag_else
    let result = compute(data);
    cache_store(result);
    return result;
#flag_endif

// Nested (block branches only)
#flag_if(linux)
    #flag_if(x86)
        fn sse_stuff() -> si4 { ... }
    #flag_else
        fn generic_simd() -> si4 { ... }
    #flag_endif
    fn common_linux() -> si4 { ... }
#flag_endif

// Inside a subroutine body
fn process(data: &[ui1]) -> verdict.[void, error] {
    #flag_if(debug)
        log_entry(data);
    #flag_endif
    let result = transform(data)?;
    #flag_if(debug) log_exit(result); ##
    return verdict::Pass(void);
}

// An excluded branch is not tokenized, so its text need not be valid.
// The terminator ends the line branch. The `#` within does not.
#flag_if(impossible) ab"#@mx???H4& ##
```

## 10.10 Translation output

A conforming translation of a Kurt source unit produces **opaque code**: the instructions into which the unit is translated, together with what the resolution of external symbols requires. The mechanism by which separate opaque codes are combined is outside the scope of this specification.

An opaque code may be one that this translation produces, one supplied via `#dyn`, or one produced by another translation system.

A conforming implementation may additionally produce an **interface source** — a Kurt source text that describes the `pub`-visible interface of the translated unit. An interface source contains a `#dyn` declaration referencing the opaque code and re-declares the `pub`-visible subroutine signatures, type declarations, and constants. It is an ordinary source unit and may be imported via `#add` by other source units.

### Implementation defined

The arrangement of the opaque code is implementation defined. The mechanism by which an interface source is generated, and whether it is generated automatically or on request, is implementation defined.

### 10.10.1 Invocation interface

#### Static semantics

An **invocation interface** is the set of conventions by which an invoker and an invoked subroutine agree upon the placement of the arguments and of the returned value, and upon the state each preserves across the invocation. The invocation interfaces an execution environment provides, and the identifier that selects each, are implementation defined.

#### Dynamic semantics

An invocation performed through an invocation interface other than the invocation interface of the invoked subroutine can cause indeterminate state.

#### Implementation requirements

The implementation shall document the invocation interface that `native` denotes for each supported execution environment. The invocation interface selection for `extern` subroutines is defined in the clause on declarations.

#### Examples (informative)

```
struct z_stream {
    next_in: %ui1,
    avail_in: ui4,
    total_in: uaddr,
    next_out: %mut ui1,
    avail_out: ui4,
    total_out: uaddr
} with repr(native);
```

### 10.10.2 Translation unit definition

A **translation unit** consists of a root source unit together with the entire `#add` dependency graph reachable from it. Opaque code bound via `#dyn` is not part of the translation unit.

A type one translation unit declares and a type another declares are the same type where their declarations are of the same kind and correspond: their generic parameters in order, by kind and, for dependence parameters, by type; the items of their `with` clauses; the fields of a struct in declaration order; and the variants of an enum in declaration order, corresponding variants bearing the same discriminant value and corresponding payloads. Corresponding types are compared by this rule; corresponding generic parameters, and the two declarations under comparison, are taken to be the same. Names are not compared. Two protocol declarations so read declare the same protocol object type where they are congruent, as the clause on protocols and implementations defines congruence.
