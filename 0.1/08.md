# §8. References and resource management

This clause defines the reference system: families, modifiers, the derivation tree, object lifetime, and the copy and transfer of values.

A **reference** is a value that designates an object. The **referent** of a reference is the object that the reference designates. Every reference has a referent type, denoted by the reference type’s tail. (e.g. `&T`, `$T`, `%T`.) The forms a reference can take are defined in the subclause on reference modifiers below.

## 8.1 Reference modifiers

### Syntax

```
ref_type     = ref_base, type ;
ref_base     = ref_family, ws, { ref_modifier, ws } ;

ref_family   = '%' | '&' | '$' ;
ref_modifier = "volatile" | "mut" | "atomic" | "guard" ;
```

The character that leads a reference type is its **family**; the **modifiers** that follow adjust how the referent is accessed.

### Static semantics

#### Families

— **Shared reference** (`&`) — multiple shared references to the same object can coexist (subject to the derivation tree). Managed.

— **Exclusive reference** (`$`) — while an exclusive reference to an object is held, the Kurt source text creates no reference to the object outside its derivation subtree, as defined in the subclause on the derivation tree. An exclusive reference is inherently storable; no `mut` modifier may appear after `$`. Managed.

— **Unmanaged reference** (`%`) — carries no lifetime and does not participate in the derivation tree.

#### Modifiers

— **Volatile access** (`volatile`) — every access through a volatile reference is a σ operation.

— **Store permission** (`mut`) — a shared or unmanaged reference carrying `mut` permits stores through the reference; one without it permits loads alone. The combinable forms are a shared mutable reference and an unmanaged mutable reference, the latter participating in no derivation tree.

— **Unordered atomic access** (`atomic`) — an access is **atomic** where the programme carries indivisibility upon it, as defined in the clause on semantics, and where it reaches no cell outside the object it accesses. The access carries no ordering guarantee relative to other operations on storage. Ordering is established by surrounding `guard(load)` / `guard(store)` fences, defined later in this clause.

— **Fully ordered atomic access** (`guard`) — the orders such an access carries are defined later in this clause.

#### Mutual exclusivity

— `atomic` and `guard` are mutually exclusive. A reference type that stacks the two shall not appear.

— `$` is exclusive and therefore inherently storable. Writing `mut`, `atomic`, or `guard` after `$` shall not appear.

#### Copyable and uncopyable references

An exclusive reference, in every form, is uncopyable. Its values follow transfer semantics, as defined in the subclause on copy and transfer semantics. Its destructor is a subroutine with no operation.

A reference whose family is `&` or `%`, in every modifier form, is copyable.

### Design rationale (informative)

Were an exclusive reference copyable, `let a: $si4 = $x; let b = a;` would produce two mutually underived exclusive references to one object. Transfer moves rather than duplicates the exclusivity claim. The claim is translation-time bookkeeping and carries no execution-time footprint.

The reference system — families and the derivation tree — prevents unintended behaviour through translation-time bookkeeping. It records how one reference is derived from another, and it reports of no reference, of any family and any modifier form, which storage an access through it reaches. Which storage two references reach in common is therefore established by the object model of the clause on semantics, and by nothing the reference system carries. Effects the bookkeeping does not see are constrained by none of it; instructions within `asm`, subroutines imported through `#dyn`, and other execution originating outside the programme’s Kurt source text are among them.

```
#dyn io {
    variadic fn printf(%ui1) -> si4;
}

fn poke(x: &saddr) {
    airside { asm { str '(1), ['(x)] } }
}

pub airside fn reflicate.[T](a: $T) -> .{ $T, $T } {
    let raw: %T = a as %T;
    return .{ raw as $T, raw as $T };
}

fn main() -> ui1 {
    let mut x: saddr = 0;
    poke(&x);                                // x holds 1
    airside { io::printf("%d\n\0".ptr, x); } // prints 1

    let .{ p, q } = reflicate.[saddr]($x);
    swap.[saddr](p, q);                      // both designate x
    *p = 2;
    *q = 3;
    airside { io::printf("%d\n\0".ptr, x); } // prints 3
    return 0;
}
```

The programme violates no rule of this specification. `poke` performs a store no reference form admits; `reflicate` produces, without leaving the Kurt source text, the arrangement the uncopyable rule of `$` keeps that text from writing. The bookkeeping establishes that the source text writes neither — not that neither occurs.

### 8.1.1 Modifier placement

#### Static semantics

The family and the referent type occupy fixed positions: the family appears first and the referent type appears last, as fixed by the `ref_type` production.

The modifiers that appear between the family and the referent type may be written in any order; the type is unchanged by their arrangement.

#### Constraints

A reference type that repeats a modifier shall not appear.

#### Notes (informative)

This specification writes the modifiers in the order `family [ volatile ] [ atomic | guard ] [ mut ] T` throughout its own prose and examples.

#### Notes (informative)

A shared reference permits stores only where it carries `mut`. An exclusive reference declares exclusive intent within the derivation tree; a shared mutable reference makes no such declaration, and multiple shared mutable references to the same object can coexist. The declaration is bookkeeping over the references the Kurt source text creates, and no form of it reports which storage an access reaches.

An unmanaged reference carries no lifetime; the `mut` modifier on an unmanaged reference records only that stores are permitted.

An unmanaged reference carrying `atomic` or `guard` provides, in every modifier form, the atomicity of its landside counterpart, with one additional concession: because unmanaged references can be derived from addresses computed at execution time, the alignment guarantee that KSA provides for automatic and permanent objects can fail to hold. Alignment semantics for atomic accesses are defined later in this clause; the unmanaged forms inherit those semantics unchanged.

### 8.1.3 Reference representation

#### Static semantics

Where the execution environment treats references as plain integers, a reference and `uaddr` are the same width. Where the execution environment carries additional information in references, a reference can be wider than `uaddr`.

A reference whose referent type is `[U]` or `dyn Protocol` is a **wide reference**. It carries an address together with the further information needed to describe the referent: the length for `[U]`, and for `dyn Protocol` the descriptor references the clause on protocols and implementations defines. Every reference form may designate such a referent. `uaddr` cannot represent a wide reference.

A load of a wide reference yields each cell independently, as defined in the clause on semantics. Where the loading execution context observes, at the cells of the reference, writes that no one access performed, the load yields an address and further information that no one access determined together. An access through the resulting reference reaches storage the address and the further information do not jointly describe, and can cause indeterminate state.

### 8.1.4 Reference casting

Casts between reference types, and between a reference type and `uaddr`, are written with `as`. All reference casts preserve the referent type `T` — changing `T` requires `as!`, which requires airside.

A cast is governed by four conversions: the **family conversion**, which determines the family of the result, and the `volatile`, store permission, and atomicity **modifier conversions**, which determine how the result is accessed.

#### Static semantics

A reference cast is admitted only where the family conversion and each of the three modifier conversions independently admits it. The family conversion is determined first: it fixes the region the cast requires and determines whether the modifier conversions are constrained. The three modifier conversions are independent of one another and are determined in any order.

In the family conversion, each cell gives the region a conversion requires, where the column is the source family and the row is the target:

Where the source family is `$`, `mut`, `atomic`, and `guard` do not appear upon the source, and the store permission and atomicity conversions do not apply.

The three modifier conversions apply where the source is a managed reference, whose modifiers protect derivation tree invariants. A cast whose source is an unmanaged reference admits every modifier conversion, `volatile` included, and requires airside.

A reference conversion may also be expressed by **dereference-and-re-reference** (**reref**): dereferencing the source reference and immediately taking a new reference with the desired family and modifiers. The expression `family [modifiers] *expr`, where `expr` has a reference type, dereferences `expr` to obtain the referent and then creates a new reference to the same storage with the specified family and modifiers. The result is a re-derivation: the new reference becomes a child node of the source reference in the derivation tree, exactly as if the source reference had been rebound via `as`.

The same conversion rules that govern `as` casts apply equally to reref.

#### Constraints

A cast whose family conversion, or any of whose modifier conversions, is independently prohibited shall not appear.

A reref that `as` would prohibit shall not appear. A reref that would require airside under `as` also requires airside.

#### Examples (informative)

```
// Family casts admitted landside
let shared: &T = exclusive as &T;       // $T → &T: no exclusivity, no store
let raw: %T = shared as %T;             // &T → %T: no lifetime
let addr: uaddr = raw as uaddr;         // %T → uaddr: no reference
let direct: uaddr = exclusive as uaddr; // $T → uaddr
let raw2: %T = addr as %T;              // uaddr → %T: no lifetime

// Family casts requiring airside
let managed: &T = airside { express raw2 as &T; }; // %T → &T
let excl: $T = airside { express raw2 as $T; };    // %T → $T

// Prohibited family casts
// addr as &T;    — translation failure: uaddr reaches %T alone
// shared as $T;  — translation failure: &T → $T
// smut as $T;    — translation failure: &mut T → $T

// Modifier casts
let vol: &volatile T = shared as &volatile T;     // &T → &volatile T
let guarded: &guard T = atomic_ref as &guard T;   // &atomic T → &guard T
let unord: &atomic T = guarded as &atomic T;      // &guard T → &atomic T
let atomic_view: &atomic T = shared as &atomic T; // &T → &atomic T
let atomic_store: &atomic mut T = mut_ref as &atomic mut T;
//   &mut T → &atomic mut T
let load_only: &atomic T = atomic_store as &atomic T;
//   &atomic mut T → &atomic T
// vol as &T;              — translation failure: &volatile T → &T
// atomic_store as &mut T; — translation failure: &atomic mut T → &mut T
// shared as &mut T;       — translation failure: &T → &mut T

// Combined: family + modifier in one cast
let raw_from_excl: %T = exclusive as %T;          // $T → %T
let vol_raw: %volatile T = shared as %volatile T; // &T → %volatile T

// Reref: family conversion
let excl: $T = ...;
let shared: &T = &*excl; // $T → &T (equivalent to: excl as &T)

// Reref: modifier addition
let p: %ui4 = ...;
airside {
    let vp: %volatile ui4 = %volatile *p; // add volatile
    let ap: %atomic ui4 = %atomic *p;     // add atomic
}

// Reref: to a managed reference (airside)
let raw_ref: %T = ...;
let managed: &T = airside { express &*raw_ref; }; // %T → &T
let excl2: $T = airside { express $*raw_ref; };   // %T → $T
```

#### Design rationale (informative)

A managed reference held outside the derivation subtree contradicts the exclusivity that `$T` asserts; the cast to `$T` from a managed reference is therefore a translation failure whatever modifiers the source carries.

An access performed without atomicity upon an object that another execution context accesses atomically is a conflicting access; atomicity is therefore retained within the managed families. A programme that requires a form without it casts to `%` first, where the region is airside.

A cast to a form without `volatile` would permit the implementation to transform accesses this specification requires it to perform.

The store permission conversion admits no cast to `mut` because a reference that carries it can be created only from a binding that permits stores; a cast that conferred it would issue store permission upon an object whose binding withholds it.

### 8.1.5 Slice references

A **slice reference** describes a contiguous run of elements of type `T` whose count is determined at execution time.

#### Syntax

```
slice_reference = ref_family, ws, { ref_modifier, ws },
                  '[', ws, type, ws, ']' ;
```

#### Static semantics

A `slice_reference` is a single, primitive grammatical production. The bracketed form `[T]` occurs only within it: it denotes the referent through the enclosing family and modifiers. A value of a slice reference type is a wide reference. Its further information is the length; the address and the length are exposed through the wide reference view defined below.

In any position where the slice reference is expected, a reference to the array `[T; N]` is implicitly cast to the corresponding slice reference. That is the slice reference whose family, modifiers, and element type match.

#### Wide reference view

An array is characterized by a reference and a length. A `[T; N]` value and a slice reference both expose them as built-in fields:

```
pub mut ptr // unmanaged reference to the first element; its modifiers
            // are derived from the enclosing reference (see below)
pub mut len: uaddr // length
```

The fields are `pub mut`. How `.ptr` and `.len` are accessed depends on whether the array is held as a value or through a slice reference.

When `.ptr` or `.len` is accessed on an array value — a non-reference binding of type `[T; N]` — the access is a **projection**: the implementation computes the result from the object’s address and its length without creating a separate object. For `[T; N]`, `.ptr` is the address of the first element, and `.len` is the length, which is fixed for the object lifetime of the object. Neither field occupies storage within the array value itself. A projection is not a storable object expression. Storing to a projection is a translation failure.

When a slice reference is created, the implementation creates an object of the stored representation defined below, and that object occupies its storage region, as defined in the clause on semantics. From that point onward, `.ptr` and `.len` are fields of the stored representation: they occupy cells of the object’s storage region, participate in the reference’s modifier semantics, and are storable subject to the `mut` field rules and the binding’s mutability.

#### Examples (informative)

```
let arr: [si4; 3] = [10, 20, 30];
arr.ptr; // %si4 — address of first element
arr.len; // 3
// arr.ptr = ...; — translation failure: a projection is not storable

let r: &[si4] = &arr; // &[si4; 3] implicitly casts to &[si4]
r.ptr; // OK — load always permitted
// r.ptr = ...; — translation failure: single-assignment binding, landside
// OK — airside store:
airside { r.ptr = 0x4000_1000~uaddr as %si4; }

let mut s: &[si4] = &arr;
s.len = 2~uaddr; // OK — mut binding, landside
```

#### Design rationale (informative)

A slice appears only as the referent of a reference. It is therefore described as a property of a reference rather than as a type of its own. This leaves `dyn Protocol` as the only unsized form, so `T'size` requires no special case for unsized types.

The fields are `pub mut` because constructing an array reference from an arbitrary address and length requires stores to `.ptr` and `.len`.

The family of the enclosing reference collapses to the unmanaged family on `.ptr` because unmanaged reference arithmetic advances `.ptr` to neighbouring elements. Retaining a managed family would attach a derivation-tree node to every load; retaining the exclusive family would issue mutually underived exclusive references to the same referent. The modifiers `mut`, `atomic`, `guard`, and `volatile` are inherited because they govern access to the underlying storage. In particular, losing `volatile` would permit caching or reordering where every access is required to be a σ operation.

## 8.2 Derivation tree

### Static semantics

All managed references to a given object form a **tree**. Deriving a new reference from an existing reference is a **re-derivation**. The new reference becomes a child node of the original. An access that reaches the object by other means stands outside the tree, and the tree reports nothing of it.

A **use** of a reference is an access through it, a re-derivation from it, or an assignment of it to an object. A reference is **live** at a programme point where some path of reachable programme points, as defined in the clause on semantics, leads from that point to a use of it. Liveness is determined by the paths of the programme alone.

### Constraints

An access through an exclusive reference shall not appear at a programme point at which a managed reference derived from it is live.

A managed reference to an object shall not be created at a programme point at which an exclusive reference to that object is live, unless it is derived from that exclusive reference.

An exclusive reference to an object shall not be created at a programme point at which a managed reference to that object that is not derived from it is live.

### Examples (informative)

```
root ($T)
  +- child1 (&T)     // re-derivation as shared load-only
  +- child2 (&mut T) // re-derivation as shared load/store
  +- child3 ($T)     // re-derivation as exclusive
       +- grandchild (&T)
```

### Design rationale (informative)

The constraints above are stated over liveness because liveness is settled by the paths of the programme, and the tree exists to be settled during translation. A reference ceases to constrain at its last use rather than at the end of the scope that holds it.

### 8.2.1 Modifiers and the tree

#### Static semantics

— `mut` — multiple shared mutable references to the same object can coexist.

— `volatile` — volatile-modified references participate in the derivation tree as their non-volatile counterparts do. Volatile accesses are σ operations, as defined in the clause on semantics.

— `atomic` / `guard` — an atomic reference whose family is `&` participates in the derivation tree, in every modifier form, as a shared reference does.

### 8.2.2 Unmanaged references

#### Static semantics

When a managed reference is converted to an unmanaged reference, the resulting reference is detached from the tree.

## 8.3 Lifetime propagation

Object lifetime categories and their order are defined in the clause on semantics. This subclause defines the object lifetime a managed reference carries and the constraints upon where such a reference may be placed.

### Static semantics

A managed reference carries the object lifetime of its referent.

The object lifetime carried by a composite-type instance is the shortest of those carried by its reference-typed fields. A composite-type instance with no reference-typed field carries no object lifetime.

The object lifetime carried by the managed reference a subroutine returns is the shortest of those carried by its parameters. Where no parameter of a subroutine carries an object lifetime, the managed reference it returns carries the permanent object lifetime.

### Constraints

Using a binding after the object lifetime of its object has ended, or after a transfer, `destruct()`, or `undestruct()` has made its object uninitialized, shall not appear. Such a violation, where not detected during translation, can cause indeterminate state.

A managed reference stored into an object whose object lifetime is longer than the object lifetime the reference carries shall not appear. A subroutine that returns a managed reference to an object whose object lifetime ends when the subroutine returns shall not appear.

The object lifetime of a composite-type instance shall be shorter than or equal to the object lifetime carried by each of its reference-typed fields.

These constraints govern managed references. An access through an unmanaged reference is governed by the clause on semantics.

### Examples (informative)

```
// Single reference parameter — the result carries its lifetime
fn passthrough(data: &[ui1]) -> &[ui1] {
    return data;
}

// Self parameter — the result carries the shortest of self and key
fn find(&self, key: &[ui1]) -> &[ui1] { ... }

// No reference parameter — the result carries the permanent lifetime
fn greeting() -> &[ui1] {
    return "permanent";
}

// Struct — the instance carries the shortest of its field lifetimes
struct view {
    header: &[ui1],
    body: &[ui1]
}

// Enum — implicit constraints on variant payloads
enum token {
    Referenced { &[ui1] },
    Owned { [ui1; 64] }
}
// token instance lifetime <= Referenced variant’s &[ui1] lifetime

// Tuple — implicit constraints
let pair: .{ &[ui1], uaddr } = .{ &data, 0 };
// pair lifetime <= &[ui1] field’s lifetime
```

## 8.4 Atomic references

### 8.4.1 Two ordering levels

#### Dynamic semantics

— **Unordered atomic reference** — an `atomic` reference confers indivisibility upon every access performed through it, and confers no ordering property. Ordering is established by surrounding `guard()` fences.

— **Fully ordered atomic reference** — a `guard` reference confers indivisibility upon every access performed through it. It relays and withholds at every read of a load so performed and at every write of a store so performed. Indivisibility and the four ordering properties are defined in the subclause on ordering properties.

#### Examples (informative)

```
// A fence adjoins the access it orders. `(load)` orders loads
// among themselves; `(store)` orders stores among themselves.
// Both hold later stores until earlier loads have yielded.

let v = *&atomic x;   // no fence — no ordering

let v = *&atomic flag;
guard(load);          // later loads yield after this one

guard(store);         // earlier stores are seen before this one
*&atomic mut flag = 1;

guard(store);
*&atomic mut ctr += 1;
guard(load);

guard();              // orders both, and withholds loads besides
let w = *&atomic ctr;

*&guard mut ctr += 1; // all of the above, in one access
```

### 8.4.2 Permitted operations

<table>
<thead><tr><th>Operation</th><th>Syntax</th><th>Semantics</th></tr></thead>
<tbody>
<tr><td>Atomic load</td><td><code>*r</code></td><td>Load the current value. <code>r</code> is an atomic reference in any form. The access is atomic.</td></tr>
<tr><td>Atomic store</td><td><code>*r = 42</code></td><td>Store a value. <code>r</code> is an atomic reference carrying <code>mut</code>, in any form. The access is atomic.</td></tr>
<tr><td>Atomic compound assignment</td><td><code>*r += 1</code></td><td>Apply the binary operation and store the result (<code>+=</code>, <code>-=</code>, <code>&amp;=</code>, <code>|=</code>, <code>^=</code>). <code>r</code> is an atomic reference carrying <code>mut</code>, in any form. The load and the store are one access, and it is atomic.</td></tr>
</tbody>
</table>

#### Dynamic semantics

KSA places every automatic and permanent object at an address aligned for its type. If the target address is not aligned for the referent type, the consequences are determined by the execution environment:

— where the execution environment supports atomic operations at a misaligned address natively, all accesses are atomic, including compound assignment and compare-and-swap;

— where it does not support them, the access can cause indeterminate state.

#### Constraints

— `T` shall satisfy `atomic`, as defined in the clause on protocols and implementations.

— A store through an atomic reference created from a field access is a store, a compound assignment, or a compare-and-swap (`>.<`). Such a store shall not appear unless the field carries the `mut` field modifier defined in the clause on declarations, or the access path begins with `$self` or with a `mut` binding of the containing value.

#### Examples (informative)

```
struct counters {
    mut hits: ui4, // mut — atomic store always permitted
    misses: ui4    // not mut — atomic store through &self shall
                   // not appear
}

impl counters {
    fn record_hit(&self) {
        *(&atomic mut self.hits) += 1; // OK — hits is mut
    }

    fn record_miss(&self) {
        *(&atomic mut self.misses) += 1;
        // translation failure — misses is not mut
    }

    fn read_misses(&self) -> ui4 {
        return *(&atomic self.misses); // OK — load, no mut required
    }
}
```

### 8.4.3 Ordering fences

Kurt provides two ordering fences, distinguished by the scope of the ordering guarantee. Each has three forms: a load form written `(load)`, a store form written `(store)`, and an empty form that carries both together with a further guarantee. The two fences are:

— Translation ordering fence (`volatile()`) — constrains the implementation’s reordering during translation.

— Execution ordering fence (`guard()`) — binds the implementation and the environment alike.

#### Syntax

```
volatile_fence = "volatile", ws, '(', ws,
                 [ ( 'load' | 'store' ), ws ], ')', ws, ';' ;
guard_fence    = "guard",    ws, '(', ws,
                 [ ( 'load' | 'store' ), ws ], ')', ws, ';' ;
```

#### Dynamic semantics

An execution ordering fence relays and withholds at τ operations its execution context performs after it, as defined in the subclause on ordering properties. A fence reaches no operation that another fence of the same form separates from it.

— Load form (`(load)`) — a `guard(load)` relays at every read, and withholds at every write, its execution context performs after it.

— Store form (`(store)`) — a `guard(store)` relays and withholds at every write its execution context performs after it.

— Empty form — a `guard()` relays and withholds at every τ operation its execution context performs after it.

A translation ordering fence binds the implementation alone: across the point at which it appears, the implementation shall not reorder the operations at which the execution ordering fence of the same form relays or withholds.

The complete fence matrix is:

<table>
<thead><tr><th></th><th><code>(load)</code> (loads)</th><th><code>(store)</code> (stores)</th><th>empty (both)</th></tr></thead>
<tbody>
<tr><td><code>volatile()</code> (implementation)</td><td><code>volatile(load)</code></td><td><code>volatile(store)</code></td><td><code>volatile()</code></td></tr>
<tr><td><code>guard()</code> (environment)</td><td><code>guard(load)</code></td><td><code>guard(store)</code></td><td><code>guard()</code></td></tr>
</tbody>
</table>

A `guard(load)` orders the reads and writes it reaches after every read its execution context performed before it; a `guard(store)` orders the writes it reaches after every read and every write so performed; a `guard()` orders every operation it reaches after every operation so performed. The `volatile` fence of each form binds the implementation alone, and the `guard` fence of that form binds the environment as well.

#### Implementation requirements

A conforming implementation shall not reject a conforming programme solely because a `(load)` fence and a `(store)` fence appear at different nesting depths or in different branches. Each fence is a standalone operation; the implementation evaluates it at the point where it appears in programme order.

All six fence forms are σ operations.

#### Examples (informative)

```
// A fence adjoins the access it orders: .load follows the load
// it orders, .store precedes the store it orders.

// translation ordering fence: signal handler synchronization
// (single execution context)
let seen = *&atomic flag;
volatile(load);
volatile(store);
*&atomic mut flag = 1;

// translation ordering fence: fully ordered (single-core interrupt handler)
volatile();
*&atomic mut ready = 1;

// execution ordering fence: load and store forms (multi-core)
let val = *&atomic data;
guard(load);
// ... use val ...
guard(store);
*&atomic mut result = computed;

// execution ordering fence: fully ordered (multi-core, empty form)
guard();

// Asymmetric execution fencing: `guard(store)` precedes the
// compare-and-swap; `guard(load)` follows it.
loop {
    guard(store);
    match &atomic mut ctr >.< expected then new {
        verdict::Pass(old)    -> { guard(load); break; };
        verdict::Fail(actual) -> { expected = actual; };
    }
}
```

The asymmetry in the pattern costs nothing to arrange. Only a write relays stores, and a compare-and-swap that finds the values unequal performs no write; the `guard(store)` preceding it therefore reaches the store of the successful attempt alone. The read of a compare-and-swap is performed on either outcome, so the `guard(load)` following it orders every operation the context performs afterwards against that read, which is what the pattern needs.

## 8.5 References below the managed level

Kurt distinguishes two levels below managed references: unmanaged references and `uaddr`.

### 8.5.1 Address as integer

`uaddr` is an unsigned integer type whose width equals the native address width of the execution environment. It carries no reference semantics. Arithmetic on unmanaged references is defined in the subclause on reference arithmetic.

### 8.5.2 Unmanaged reference

An unmanaged reference differs from `uaddr` in that it carries derivation history, and in the representation defined in the subclause on reference representation.

Kurt tracks the derivation history of references for derivation tree construction, not as a criterion of acceptance; whether the execution environment accepts an access is defined in the clause on semantics. `uaddr` is a plain integer. An unmanaged reference carries derivation history and can differ in size where the execution environment carries additional information in references. It can also differ in shape by being a wide reference.

Converting between an unmanaged reference and `uaddr` is defined by `as` casts and is landside — the cast itself is not a σ operation and requires no special privilege.

#### Examples (informative)

```
// %T → uaddr: extract the address
// (discards metadata if wide; landside)
let addr: uaddr = ptr as uaddr;

// uaddr → %T: assert that this address holds a valid T (landside)
let ptr: %T = addr as %T;

// dereferencing requires airside
airside { *ptr = value; }
```

### 8.5.3 The three-level hierarchy

<table>
<thead><tr><th>Form</th><th>Properties</th></tr></thead>
<tbody>
<tr><td><code>uaddr</code></td><td>integer; no reference semantics; no size or type information</td></tr>
<tr><td><code>%T</code></td><td>unmanaged reference; no derivation tree; no lifetime; may be wider than <code>uaddr</code>; may be a wide reference</td></tr>
<tr><td><code>&amp;T</code> / <code>$T</code></td><td>managed reference; derivation tree; lifetime tracked</td></tr>
</tbody>
</table>

The cast from a managed reference to an unmanaged reference is a landside cast (discards lifetime and derivation tree membership). The cast from an unmanaged reference to `uaddr`, and the cast from `uaddr` to an unmanaged reference, are both landside casts, as defined in the clause on reference casting and the subclause on addresses. No `airside` block is required for the cast itself.

### 8.5.4 Unmanaged reference arithmetic

The `+`, `-`, `+=`, and `-=` operators accept a leading operand of unmanaged reference type and a following operand of type `uaddr`. The result type is the type of the leading operand, with all modifiers preserved.

#### Static semantics

The leading operand is an unmanaged reference type, with any combination of modifiers. The following operand is of type `uaddr`.

#### Dynamic semantics

The effective cell offset is the following operand multiplied by `T'size`, where the multiplication wraps. The result is the address of the leading operand’s referent advanced by the offset for `+`, and set back by it for `-`. Both the multiplication and the address computation follow the wrapping semantics defined in the clause on expressions.

The result is an unmanaged reference to the computed address. The result inherits the derivation history of the leading operand.

The compound assignment forms `+=` and `-=` are permitted on a `mut` binding of unmanaged reference type with a following operand of type `uaddr`. The semantics follow from the corresponding binary operator and the compound assignment rules defined in the clause on expressions.

#### Constraints

The referent type `T` shall be a sized type; when `T` is unsized, the expression shall not appear.

#### Implementation requirements

A conforming implementation should issue a diagnostic when `T'size` is zero.

#### Examples (informative)

```
let base: %si4 = arr.ptr;
let third: %si4 = base + 2; // 2 * si4'size cells forwards
let prev: %si4 = third - 1; // 1 * si4'size cells backwards

let mut cursor: %si4 = arr.ptr;
cursor += 1; // advance one element
cursor -= 1; // retreat one element

let vp: %volatile mut ui4 = mmio_base;
let next_reg: %volatile mut ui4 = vp + 1; // modifiers preserved

// Cell-level arithmetic: cast to %ui1
let cell_ptr: %ui1 = base as %ui1;
let offset: %ui1 = cell_ptr + 16; // 16 cells forwards
```

## 8.6 Compare-and-swap operator

### Syntax

```
cas_expr = expression, ws, '>.<', ws, expression, ws, "then", ws,
           expression ;
```

The compare-and-swap operator requires an atomic reference target; all type, size, and alignment constraints follow from the target type as defined above. It returns `verdict.[T, T]` — the built-in contract type with both payloads of type `T`. `verdict::Pass(old_value)` is the success variant; `verdict::Fail(actual_value)` is the failure variant.

### Dynamic semantics

The operation compares the value at the target against `expected`. Where the two are not equal, it leaves the target unchanged and returns the failure variant containing the actual value. Where they are equal, it either replaces the value with `new` and returns the success variant containing the previous value, or leaves the target unchanged and returns the failure variant containing `expected`. The load and the store are one access, and it is atomic.

### Constraints

— The target shall be an atomic reference carrying `mut`. All type, size, and alignment constraints are inherited from the target type, as defined in the clause on permitted operations on atomic references.

### Examples (informative)

```
let guard_ref = &guard mut ctr;
let x = guard_ref >.< expected then new;
// x: verdict.[uaddr, uaddr]
```

```
// Unordered CAS with asymmetric fencing: `guard(store)`
// precedes the operation, `guard(load)` follows it
let mut expected = *&guard ctr;
loop {
    guard(store);
    match &atomic mut ctr >.< expected then new {
        verdict::Pass(old)    -> { guard(load); break; };
        verdict::Fail(actual) -> { expected = actual; };
    }
}

// Fully ordered CAS — no fences needed
let result = &guard mut ctr >.< expected then new;
if result -> old {
    // CAS succeeded
} else.actual {
    expected = actual;
}

// Replacement whenever the target holds any value other than a
// sentinel. SENTINEL and real_value are integer constants.
let slot_ref = &guard mut slot;
loop {
    let cur = *slot_ref;
    if cur == SENTINEL { break; }
    match slot_ref >.< cur then real_value {
        verdict::Pass(old) -> { process(old); break; };
        verdict::Fail(?)   -> { };
    }
}
```

In the first loop, a failure whose payload equals `expected` leaves `expected` unchanged, and the operation is repeated. A loop of this shape therefore replaces the value whenever the values are equal.

## 8.7 Copy and transfer semantics

The **constituents** of a type are the types of the values a value of the type holds: for an array, its element type; for a tuple, its element types; for a `struct`, the types of its fields; for an `enum` or a contract type, the types of its variant payloads. A reference has no constituents.

A type is **uncopyable** where a constituent of the type is uncopyable, or where this specification otherwise states the type to be uncopyable. A type that is not uncopyable is **copyable**.

### Constraints

A `struct`, `enum`, or `contract` declaration shall declare `with destruct` where a constituent of the type it declares is uncopyable under every choice of type argument.

### 8.7.1 Copy

A **copy** performs a read at each cell of the source storage and a write of the symbol so yielded at the corresponding cell of the destination storage. The source storage is unmodified. The source and destination are independent after the operation.

Copy applies to binding initialization, subroutine parameter passing, `return` expressions, and assignment of copyable types.

### 8.7.2 Transfer

#### Dynamic semantics

A **transfer** is a copy followed by the invalidation of the source binding. The destruction obligation the source binding held passes to the destination binding, and the source binding holds none thereafter.

Transfer applies to binding initialization, subroutine parameter passing, `return` expressions, and assignment of uncopyable types.

#### Constraints

The source binding of a transfer shall not be accessed after the transfer.

## 8.8 Assignment semantics

The assignment expression is defined in the clause on expressions. This subclause defines the operations performed when a load or store is executed through a reference.

### Dynamic semantics

#### Managed references

An access to a copyable type through a managed reference is a copy.

A store of an uncopyable type through a managed reference proceeds in the two steps defined in the clause on expressions.

#### Unmanaged references

An access through an unmanaged reference is a copy. The source storage is unmodified. The resulting value of a load carries an independent destruction obligation.

### Constraints

An uncopyable type shall not be loaded through a managed reference.

### Examples (informative)

```
// managed — !destruct: copy
let r: &si4 = &x;
let v = *r;  // copy

// managed — destruct store: destruct target, then transfer
*$handle_ref = open("c.bin");

// unmanaged — always copy
airside {
    let val = *(%*src);      // copy, independent obligation
    *(%mut dst) = new_value; // copy, existing value not destroyed
}

// swap via unmanaged references
pub airside fn swap.[T](a: $T, b: $T) {
    let mut tmp: T = uninit;
    *(%mut tmp) = *(%*a);
    *(%mut *a)  = *(%*b);
    *(%mut *b)  = *(%tmp);
    undestruct(tmp);
}
```

## 8.9 Destructors

### Syntax

```
destruct_clause = "destruct", [ ws, block ] ;
```

### Static semantics

`with destruct` makes the type uncopyable.

Every type has a **destructor**: the block of its `with destruct` clause where the clause carries one, the subroutine this specification otherwise supplies for the type where it supplies one, and a subroutine with no operation in every other case. The implementation invokes the destructor of a type when a value of the type goes out of scope.

Within a `with destruct` block, `self` is an exclusive reference to the object being destroyed — equivalent to `$selftype`. The destruct block may load and store fields through `self`, and may invoke methods that take `$self` or `&self`. The destruct block does not hold the object’s destruction obligation.

### Dynamic semantics

The destructor of an object executes immediately before its storage is released. The fields of a composite type are destroyed in reverse declaration order.

A conforming implementation shall guarantee that the destructor of every value is executed exactly once, except in the circumstances below, in which it shall not execute:

— The evaluation of a diverging expression, as defined in the clause on statements and control flow.

— `undestruct`.

— `as!`.

— A `static` binding, as defined in the clause on declarations.

### 8.9.1 Composite destruction

#### Static semantics

Destroying a value destroys its constituents. The destructor supplied by `with destruct`, where one is declared, executes before the destructors of the constituents.

The order for each composite form is:

— Struct — the destructors of the fields execute in the field destruction order defined above.

— Enum and contract type — the destructor of the active variant’s payload executes. A variant that holds no payload contributes no destructor invocation.

— Array — the destructor of each element executes in reverse index order.

#### Examples (informative)

```
struct buffer {
    data: %ui1,
    len: uaddr
} with destruct {
    // self: $buffer
    dealloc(self.data, self.len);
};

struct parser {
    buf: buffer, // buffer is uncopyable
    pos: uaddr
} with destruct;
// parser shall declare with destruct because buf is uncopyable.
// It is uncopyable; its values follow transfer semantics.

let p1 = parser { .buf = alloc_buffer(1024), .pos = 0 };
let p2 = p1; // transfer: p1 is invalidated
// p1.pos;   // translation failure — p1 was transferred

// When p2 goes out of scope:
//   1. p2.buf.destruct block executes (dealloc)
//   2. p2.pos requires no destruction

enum resource {
    File(file_handle), // file_handle is uncopyable
    None
} with destruct;
// resource shall declare with destruct because file_handle is
// uncopyable. Destroying a resource value invokes the active
// variant’s payload destructor: File(h) destroys h, None nothing.
```

### 8.9.2 Explicit early destruction

#### Syntax

```
destruct_invocation = "destruct", ws, '(', ws, expression, ws, ')' ;
```

#### Dynamic semantics

`destruct(expr)` consumes the value yielded by `expr`, executes its destructor immediately, and returns `void`. The original binding is invalidated and the object becomes uninitialized, subject to the constraint in the subclause on lifetime propagation.

#### Examples (informative)

```
{
    let handle = open_file("data.bin");
    process(&handle);
    destruct(handle); // destructor runs here, not at scope exit
    do_unrelated_work();
}
```

### 8.9.3 Destructor suppression

#### Syntax

```
undestruct_expr = "undestruct", ws, '(', ws, expression, ws, ')' ;
```

#### Dynamic semantics

`undestruct(expr)` consumes the value yielded by `expr` and returns `void`. The `with destruct` block does not execute. The original binding is invalidated and the object becomes uninitialized, subject to the constraint in the subclause on lifetime propagation.

#### Constraints

Invoking `undestruct` requires airside.

#### Examples (informative)

```
airside { undestruct(existing_handle); }
// existing_handle is consumed. Destructor does not run.
```
