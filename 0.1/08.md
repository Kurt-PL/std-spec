# 8. References and resource management

This clause defines the reference system: tribes, modifiers, the derivation chain, routes, reference forms, the propagation of object lifetime, atomic references and ordering fences, unmanaged reference arithmetic, the compare-and-swap operator, the copy and transfer of values, assignment, and destructors.

A **reference** is a value that designates an object. The **referent** of a reference is the object that the reference designates. Every reference has a referent type, denoted by the reference type’s tail. (e.g. `&T`, `$T`, `%T`.) The forms a reference can take are enumerated in the subclause on reference type enumeration below.

## 8.1 Reference properties

### Syntax

```
ref_type     = ref_base, type ;
ref_base     = ref_tribe, ws, { ref_modifier, ws } ;

ref_tribe    = '%' | '&' | '$' ;
ref_modifier = "volatile" | "mut" | "atomic" | "guard" ;
```

The character that leads a reference type is its **tribe**. The **modifiers** that follow adjust how the referent is accessed.

### Static semantics

#### Tribes

— **Shared reference** (`&`) — a managed reference that the derivation chain treats as shared.

— **Exclusive reference** (`$`) — a managed reference that the derivation chain treats as exclusive.

— **Unmanaged reference** (`%`) — a reference that carries no object lifetime and participates in no derivation chain.

A reference whose tribe is `&` or `$` is a **managed reference**.

#### Modifiers

— **Volatile access** (`volatile`) — every access through a volatile reference is a σ operation.

— **Store permission** (`mut`) — a shared or unmanaged reference carrying `mut` permits stores through the reference, and one without it permits loads alone. An access through a shared mutable reference requires airside, unless the reference carries `atomic` or `guard`.

— **Unordered atomic access** (`atomic`) — a reference carrying `atomic` confers no ordering property.

— **Fully ordered atomic access** (`guard`) — a reference carrying `guard` relays and withholds, as the subclause on atomic references defines.

#### Copyable and uncopyable references

An exclusive reference is uncopyable.

A reference whose tribe is `&` or `%` is copyable.

### Constraints

— A reference type that stacks `atomic` and `guard` shall not appear, whether written or formed by an expression.

— A reference type whose tribe is `$` and that carries `mut`, `atomic`, or `guard` shall not appear, whether written or formed by an expression.

— The type of a `const` declaration, of an associated constant, of a `static` binding, and of a `const` or `xlat` block shall neither be nor have as a constituent an exclusive reference type.

For a type, an expression, or a block item within the scope of a type parameter, the static semantics and the constraints of this clause hold under every choice of type argument for each type parameter in scope that satisfies each built-in bound that the bound upon that type parameter names or a protocol it names entails.

### Design rationale (informative)

Were an exclusive reference copyable, `let a: $si4 = $x; let b = a;` would produce two mutually underived exclusive references to one object. Transfer moves rather than duplicates the exclusivity claim.

The reference system — tribes and the derivation chain — is translation-time bookkeeping. It records how one reference is derived from another, and it records nothing about storage. Which cells an access reaches, and whether two accesses reach a cell in common, are settled by the object model of the clause on semantics. Effects the bookkeeping does not see are constrained by none of it. Instructions within an `instruct` block, subroutines imported through `#dyn`, and other execution originating outside the programme’s Kurt source text are among them.

```
#dyn io {
    variadic fn printf(%ui1) -> si4;
}

fn poke(x: &saddr) {
    airside { instruct { str '(1), ['p] } with { in('p) = x; } }
}

pub fn reflicate[T](a: %T) -> .{ $T, $T } {
    airside {
        return .{ a as $T, a as $T };
    }
}

fn main() -> ui1 {
    let mut x: saddr = 0;
    poke(&x);                                // x holds 1
    airside { io::printf("%d\n\0".ptr, x); } // prints 1

    let .{ p, q } = reflicate[saddr](%x);    // both designate x
    *p = 2;
    *q = 3;
    airside { io::printf("%d\n\0".ptr, x); } // prints 3
    return 0;
}
```

The programme violates no rule of this specification. `poke` performs a store no reference form permits; `reflicate` produces, without leaving the Kurt source text, the arrangement the uncopyable rule of `$` keeps that text from writing. The bookkeeping establishes that the source text writes neither — not that neither occurs.

### 8.1.1 Derivation chain

#### Static semantics

Managed references form **derivation chains**. Creating a managed reference, whether that creation is explicit or implicit, chains it as follows, and an invocation chains so, as a new reference, each managed reference that its return value is or holds.

— From a reference, the new reference is chained to that reference where it is a managed reference, and to nothing where it is an unmanaged reference.

— From an object expression that reaches its object through a reference, the new reference is chained to the reference nearest the object where that reference is a managed reference, and to nothing where it is an unmanaged reference.

— From an object expression that reaches its object without passing through a reference, the new reference is chained to the object the expression names before its first field access.

— From an invocation whose return value is or holds it, the new reference is chained to each managed reference that, on that invocation, is at a layer that a source denotes of a route of the invoked subroutine whose target is `return`, as the subclause on routes defines layers. Where the new reference is exclusive, it is not chained to one that permits no store and through which the per-field store permission permits none. It is chained to nothing where there is none or where a source of such a route is `static`.

— From any other value expression, the new reference is chained to the temporary object holding that value.

— Otherwise the new reference is chained to nothing.

Where the new reference is chained to a reference, the creation, or the invocation, is **reference chaining**.

For the rules of this subclause, an access whose object expression, or, for a load that matching performs, the expression whose value it matches, reaches its object without passing through a reference is taken to be an access through a managed reference created from that expression at the programme point immediately before the access and pending there. That reference is a shared reference where the access is a load and an exclusive reference otherwise.

On an invocation, a parameter **lends** each managed reference at each of its layers.

For the rules of this subclause and of the subclause on routes, a managed reference chained to more than one reference, or to a reference and to nothing, is taken to be several references, one chained alone to each reference to which it is chained and, where it is chained to nothing as well, one chained to nothing. For those rules, a reference chained to such a managed reference is taken to be chained to each of the several.

The **descent** of a managed reference is the field accesses that designate, from the object it is chained to or from the referent of the reference it is chained to, the object the object expression it is created from names, innermost first, preceded by the descent of the reference it is chained to. Where the reference is created from no object expression or is chained to nothing, the field accesses of its descent are none, and where it is chained to no reference, nothing precedes them.

A managed reference is a **descendant** of the reference to which it is chained and of every ancestor of that reference, and each of those is an **ancestor** of it.

Two managed references **meet** where one object or managed reference is such that each of them either is chained to it or has an ancestor chained to it, and one descent is a prefix of the other, equality included.

A reference is **pending** at a programme point where some trace contains that point and, after that point, an access through it, reference chaining from it, an invocation on which a parameter lends it, or a store of it into an object, with no creation of the reference, and no invocation whose return value is or holds it, between them.

Where the traces of the programme do not settle which managed reference the object of a binding, or a constituent object of it, holds at a programme point, the rules of this clause hold of the following managed references, and of no other:

— Each managed reference that a store on some trace containing that point, whether it names that object or an object of which that object is a constituent object, places into that object before that point.

— Where the binding is the binding of a parameter, each managed reference that object holds at subroutine entry.

#### Constraints

An access through an exclusive reference, or an invocation on which a parameter lends it, shall not appear at a programme point at which a descendant of it is pending where, of the following, one is a prefix of the other, equality included:

— The descent of that descendant after the descent of the exclusive reference.

— The field accesses that designate, from the referent, the object the access names, or, where none does, the least object so designated within which it lies.

For an invocation, the object the access names is taken to be the referent.

At a programme point at which an exclusive reference is pending, every other managed reference that is pending at the point and that meets it shall be an ancestor or a descendant of it.

Every managed reference that a parameter lends on an invocation and that meets an exclusive reference that a parameter lends on that invocation shall be that exclusive reference.

#### Design rationale (informative)

The first two constraints above are stated over what is pending because that is settled by the traces of the programme, and the derivation chain exists to be settled during translation. A reference therefore ceases to constrain where it is no longer pending, which may fall before the end of the scope that holds it.

#### Examples (informative)

```
the object of s (pair)      // descent []
  +- first ($pair)          // descent []
  |    +- next1 (&pair)     // descent []
  |    +- next2 (&mut pair) // descent []
  |    +- next3 ($pair)     // descent []
  |         +- further (&pair)
  +- side ($si4)            // created from $s.f — descent [f]
```

The diagram gives chaining and descent, not what is pending. `next1` and `next2` may be pending together; neither may be pending where `next3` is, and `next3` and `further` may be pending together. `first` and `side` are chained to the same object, and `[]` is a prefix of `[f]`, so they meet. Neither is an ancestor or a descendant of the other, so they may not be pending together.

```
fn id(r: &si4) -> &si4 { return r; }

struct holder {
    val: &si4
}

impl holder {
    fn get(&self) -> &si4 { return self.val; }
}

let mut x: si4 = 1;
let e: $si4 = $x;
let r = id(&*e);             // chained to the argument
// *e = 2;                   — translation failure: r is pending
let v = *r;

let mut y: si4 = 2;
let g: $si4 = $y;
let h = holder.{ .val = &*g };
let s = h.get();             // chained to &h and to the
                             // reference h.val holds
// *g = 3;                   — translation failure: s is pending
let u = *s;
```

### 8.1.2 Routes

#### Syntax

```
routes_clause = "routes", ws, '(', ws, route, ws,
                { ',', ws, route, ws }, [ ',', ws ], ')' ;

route         = route_source, { ws, '+', ws, route_source }, ws,
                '->', ws, route_target ;
route_source  = "static" | route_path ;
route_target  = "return" | "static" | route_path ;
route_path    = { '*', ws }, [ '...', ws ],
                ( identifier | "self" | dec_literal ) ;
```

The `dec_literal` production is defined in the clause on lexical structure.

#### Static semantics

Each `route` in a `routes` clause is a **route** of the declaration or type that carries it. Each `route_source` of a route is a **source** of it, and its `route_target` is its **target**.

A `route_path` that carries *k* `*` denotes layer *k* of a parameter, and, where it carries `...`, each layer of that parameter deeper than layer *k* as well. The parameter is the one its identifier names, the self parameter where it carries `self`, or the one whose position is the digit value of its `dec_literal`, counting from zero in declaration order, the self parameter included. `static` denotes no layer.

A subroutine declaration or subroutine pointer type that carries no `routes` clause has one route, whose target is `return` and whose sources denote every layer of every parameter and include `static`.

Two subroutine declarations or subroutine pointer types have the **same routes** where, for `return`, for `static`, and for each layer of each parameter, the sources of the routes whose target is or denotes it denote the same layers in the one as in the other and include `static` in both or in neither. For this comparison, a layer of a parameter is taken to be the same as that layer of the parameter at the same position.

On an invocation, the managed references at **layer** 0 of a parameter are those that the value the invocation copies or transfers into the parameter binding is or holds. Those at layer *k* + 1 are those that the value the referent of one at layer *k* holds is or holds, the referent being taken to hold as well each managed reference that the invocation stores into it. No other managed reference is at a layer of that parameter.

For the rules of this subclause, of the subclause on the derivation chain, and of the subclause on lifetime propagation, a subroutine that uses the variadic variant of its invocation interface, and a subroutine pointer type that carries `variadic`, are taken to have one further parameter, whose position follows that of the last fixed parameter. An invocation is taken to copy or transfer into the binding of that parameter a value that holds the values of the arguments beyond the fixed parameters, and that binding is the variadic binding where there is one.

For the rules of this subclause, of the subclause on the derivation chain, and of the subclause on lifetime propagation, an invocation stores, through each managed reference that is at layer *k* of a parameter and that permits, or through which the per-field store permission permits, a store to its referent or to a constituent object of it:

— For each managed reference at a layer of that parameter deeper than layer *k*, other than one this invocation stores, and for each at a layer that a source denotes of a route of the invoked subroutine whose target denotes layer *k* + 1 of that parameter, a new reference of its type chained to it.

— Where a source of such a route is `static`, a managed reference chained to nothing of each managed reference type that is, or is a constituent of, the referent type of that reference at layer *k*.

Each of these is stored by a store that names the referent. Where, on some trace containing a programme point, such a store is the last before that point to place a managed reference into the object of a binding or a constituent object of it, the rules of those subclauses hold, for the managed reference that object holds at that point, of the following managed references, and of no other:

— Each managed reference that a store on some trace containing that point, whether it names that object or an object of which that object is a constituent object, places into that object before that point.

— Where the binding is the binding of a parameter, each managed reference that object holds at subroutine entry.

For the rules of those subclauses, an invocation also stores each managed reference at a layer that a source denotes of a route of the invoked subroutine whose target is `static`, by a store that names, without passing through a reference, an object of the permanent object lifetime. Each managed reference so stored is pending at every programme point that some trace contains after the invocation.

Within the body of a subroutine, for the rules of this subclause, the value of the binding of a parameter at subroutine entry is taken to be or hold managed references that **come from** layer 0 of that parameter. For those rules, a load within the body through a managed reference that comes from layer *k* of a parameter is taken to yield a value that is or holds managed references that come from layer *k* + 1 of that parameter. For the rules of this subclause, an invocation within the body is taken to perform a load through each managed reference at a layer of a parameter of the invoked subroutine. A managed reference comes from each layer these give it and each layer from which an ancestor of it comes, and from no other. For the rules of this subclause, a construct is within the body of the innermost subroutine whose body contains it, and of no other subroutine.

#### Constraints

Within the body of a subroutine, for each managed reference that the value the subroutine returns is or holds:

— Each layer from which it comes shall be one that a source denotes of a route of the subroutine whose target is `return`.

— Where it comes from none, such a route shall have a `static` source.

— Neither it nor an ancestor of it shall be chained to an object of the automatic object lifetime.

Within the body of a subroutine, where the reference nearest the object a store names is a managed reference and comes from layer *k* of a parameter, for each managed reference that the store places:

— Each layer from which it comes shall be a layer of that parameter deeper than layer *k* or one that a source denotes of a route of the subroutine whose target denotes layer *k* + 1 of that parameter.

— Neither it nor an ancestor of it shall be chained to an object of the automatic object lifetime.

Within the body of a subroutine, a route of the subroutine whose target denotes layer *k* + 1 of a parameter shall have a `static` source where a store satisfies both of the following:

— The reference nearest the object it names is a managed reference and comes from layer *k* of that parameter.

— A managed reference that it places comes from no layer and is exclusive, carries `mut`, or has a referent type that is a protocol type or is, or has as a constituent, a managed reference type or a type with a field that has per-field store permission.

Within the body of a subroutine, for each managed reference that a store of either kind below places, each layer from which it comes shall be one that a source denotes of a route of the subroutine whose target is `static`, and neither it nor an ancestor of it shall be chained to an object of the automatic object lifetime:

— A store that names, without passing through a reference, an object of the permanent object lifetime.

— A store where the reference nearest the object it names is a managed reference, comes from no layer of a parameter, and neither it nor an ancestor of it is chained to an object of the automatic object lifetime.

None of the constraints of this subclause applies to a managed reference that is, or has an ancestor that is, created from an unmanaged reference or from an object expression in which the reference nearest the object is an unmanaged reference, or that a load through an unmanaged reference or through such a reference yields. None of them applies either to a store whose reference nearest the object is such a reference.

A `route_path` shall denote a layer of a parameter of the declaration or type that carries it. The target of a route shall be `return`, `static`, or a `route_path` that carries a `*`.

#### Examples (informative)

```
struct slot {
    h: &[ui1]
}

fn set(s: $slot, x: &[ui1]) routes(x -> *s) {
    s.h = x;
}

// fn put(s: $slot, x: &[ui1]) { s.h = x; }
// — translation failure: no route to *s

struct words {
    s: &[&[ui1]]
}

impl words {
    fn next($self) -> &[ui1] routes(**self + static -> return) {
        let [..., w] = self.s else { return ""; };
        self.s.len -= 1;
        return w;
    }
}

enum link {
    end,
    more { &mut node }
}

struct node {
    val: si4,
    rest: link
}

impl node {
    fn append(&mut self, n: &mut node) routes(n -> *...self) {
        let mut cur: &mut node = self;
        airside {
            while let link::more.{ r } = cur.rest { cur = r; }
            cur.rest = link::more.{ n };
        }
    }
}

// routes(n -> *self) in its place
// — translation failure: cur comes from
// every layer of self

let mut sl = slot.{ .h = "" };
{
    let t: [ui1; 2] = [1, 2];
    // set($sl, &t); — sl outlives t: not permitted
}

let f: fn($slot, &[ui1]) routes(1 -> *0) = set;
// let p: fn($slot, &[ui1]) = set;
// — translation failure: routes differ
f($sl, "ok");

let list: [&[ui1]; 2] = ["a", "b"];
let mut it = words.{ .s = &list };
let a = it.next(); // chained to the references list holds
let b = it.next(); // a is not chained to $it
print(a);
print(b);
```

### 8.1.3 Modifier placement

#### Static semantics

The modifiers that appear between the tribe and the referent type may be written in any order, and their order does not bear upon the identity of the type.

#### Constraints

A reference type that repeats a modifier shall not appear, whether written or formed by an expression.

### 8.2.2 Reference representation

#### Static semantics

A reference whose referent type is `[U]` or a protocol type is a **wide reference**. It carries an address together with the further information needed to describe the referent. For `[U]` that information is the length. For a protocol type it is the pair of descriptor references that the clause on protocols and implementations defines. Every reference form may designate such a referent. `uaddr` cannot represent a wide reference.

A load of a wide reference yields each cell independently, as defined in the clause on semantics. Where the loading execution context observes, at the cells of the reference, writes that no one access performed, the load yields an address and further information that no one access determined together. An access through the resulting reference reaches storage the address and the further information do not jointly describe, and can cause indeterminate state.

### 8.2.3 Reference casting

Casts between reference types are written with `as`. A **re-reference** `tribe [modifiers] *expr`, where `expr` has a reference type, dereferences `expr` and creates a new reference to the same storage with the specified tribe and modifiers. The cast between a reference and `uaddr` is defined in the subclause that follows.

A cast and a re-reference are each governed by four conversions: the **tribe conversion**, which determines the tribe of the result, and the `volatile`, store permission, and atomicity **modifier conversions**.

<thead><tr><th>to \ from</th><th>(none)</th><th><code>atomic</code></th><th><code>guard</code></th></tr></thead>
<tbody>
<tr><td>(none)</td><td>—</td><td>Translation failure</td><td>Translation failure</td></tr>
<tr><td><code>atomic</code></td><td>Landside</td><td>—</td><td>Landside</td></tr>
<tr><td><code>guard</code></td><td>Landside</td><td>Landside</td><td>—</td></tr>
</tbody>
</table>

Each table above states the source tribes it governs. The remaining sources depart from them:

— The store permission and atomicity conversions do not apply to an exclusive reference.

— A modifier conversion the tables mark a translation failure is permitted upon an unmanaged reference and requires airside. Every other cell applies unchanged.

#### Dynamic semantics

The result of a cast expression between reference types has the address and the further information of the source.

#### Constraints

A cast or a re-reference whose tribe conversion, or any of whose modifier conversions, is not permitted shall not appear.

Where the target type of a cast expression without `!` is a managed reference type, its referent type shall be the referent type of the source.

The source and the target of a cast expression without `!` between reference types shall both be slice references, both be references to a protocol type, or both be neither. Where both are references to a protocol type, their referent types shall be the same.

#### Design rationale (informative)

A managed reference that is neither an ancestor nor a descendant of an exclusive reference contradicts the exclusivity that the exclusive reference asserts. The cast to an exclusive reference from a managed reference is therefore a translation failure.

An access performed without atomicity upon an object that another execution context accesses atomically conflicts with it. Atomicity is therefore retained within the managed tribes. A programme that requires a form without it casts to `%` first, where the region is airside.

A cast to a form without `volatile` would permit the implementation to transform accesses this specification requires it to perform.

The store permission conversion permits no cast to `mut` because a reference that carries it can be created only from a binding that permits stores. A cast that conferred it would issue store permission upon an object whose binding withholds it.

#### Examples (informative)

```
// Tribe casts permitted on landside
let shared: &T = exclusive as &T; // $T → &T: no exclusivity, no store
let uman: %T = shared as %T;      // &T → %T: no object lifetime

// Tribe casts requiring airside
let managed: &T = airside { express uman as &T; }; // %T → &T
let excl: $T = airside { express uman as $T; };    // %T → $T

// Prohibited tribe casts
// shared as $T;  — translation failure: &T → $T

// Modifier casts

// &T → &volatile T
let vol: &volatile T = shared as &volatile T;
// &atomic T → &guard T
let guarded: &guard T = atomic_ref as &guard T;
// &guard T → &atomic T
let unord: &atomic T = guarded as &atomic T;
// &T → &atomic T
let atomic_view: &atomic T = shared as &atomic T;
// &mut T → &atomic mut T
let atomic_store: &atomic mut T = mut_ref as &atomic mut T;
// &atomic mut T → &atomic T
let load_only: &atomic T = atomic_store as &atomic T;

// vol as &T;              — translation failure: &volatile T → &T
// atomic_store as &mut T; — translation failure: &atomic mut T → &mut T
// shared as &mut T;       — translation failure: &T → &mut T

// Combined: tribe + modifier in one cast
let uman_from_excl: %T = exclusive as %T;          // $T → %T
let vol_uman: %volatile T = shared as %volatile T; // &T → %volatile T

// Re-reference: tribe conversion
let shared2: &T = &*excl; // $T → &T (equivalent to: excl as &T)

// Re-reference: modifier addition
let p: %ui4 = ...;
airside {
    let vp: %volatile ui4 = %volatile *p; // add volatile
    let ap: %atomic ui4 = %atomic *p;     // add atomic
}
```

### 8.2.4 Conversion between a reference and `uaddr`

#### Static semantics

A reference and a `uaddr` are converted into one another with `as`. Neither the tribe conversion nor any modifier conversion applies to such a cast.

A cast from a reference of any tribe to `uaddr` yields the address the reference carries.

#### Constraints

The source of a cast to a managed reference type shall be a reference type. A cast from `uaddr` to a wide reference shall not appear.

#### Implementation defined

What a cast from `uaddr` to an unmanaged reference type gives the reference besides the address is implementation defined.

#### Examples (informative)

```
let addr: uaddr = uman as uaddr;        // %T → uaddr: no reference
let direct: uaddr = exclusive as uaddr; // $T → uaddr
let uman2: %T = addr as %T;             // uaddr → %T

// addr as &T; — translation failure: uaddr reaches %T alone
```

### 8.2.5 Slice references

A **slice reference** describes a contiguous run of elements of type `T` whose count is determined at execution time.

#### Syntax

```
slice_reference = ref_tribe, ws, { ref_modifier, ws },
                  '[', ws, type, ws, ']' ;
```

#### Static semantics

The bracketed form `[T]` occurs only within the `slice_reference` production, and denotes the referent through the enclosing tribe and modifiers.

In any position where the slice reference is expected, the receiver of `.ptr` and of `.len` included, a reference to the array `[T; N]` is implicitly cast to the corresponding slice reference. That is the slice reference whose tribe, modifiers, and element type match, whose `.ptr` is the address of the array, and whose `.len` is `N`. For `.ptr` and `.len`, the cast takes place before reference transparency applies.

A `[T; N]` value and a slice reference both expose the address of the first element and the length as built-in fields:

<table>
<thead><tr><th>Field</th><th>Type</th><th>Content</th></tr></thead>
<tbody>
<tr><td><code>pub mut ptr</code></td><td>as below</td><td>An unmanaged reference to the first element.</td></tr>
<tr><td><code>pub mut len</code></td><td><code>uaddr</code></td><td>The length.</td></tr>
</tbody>
</table>

When `.ptr` or `.len` is accessed on an array value, the access is a **projection**, and the implementation computes the result from the object’s address and its length without creating a separate object. `.ptr` is then the address of the first element, and its projection creates a reference to that element; `.len` is `N`.

When a slice reference is created, the implementation creates an object of the stored representation defined below, and that object occupies its storage region, as defined in the clause on semantics. From that point onward, `.ptr` and `.len` are fields of the stored representation. They occupy cells of the object’s storage region, participate in the reference’s modifier semantics, and are storable subject to the `mut` field rules and the binding’s mutability.

The stored representation of a slice reference is two fields in this order:

<table>
<thead><tr><th>Field</th><th>Content</th></tr></thead>
<tbody>
<tr><td><code>ptr</code></td><td>unmanaged reference (reference width)</td></tr>
<tr><td><code>len</code></td><td><code>uaddr</code> (address width)</td></tr>
</tbody>
</table>

Kurt standard alignment gives the offset of each field, and the size and the alignment of the reference, from the types of those fields in that order.

The type of `.ptr` is an unmanaged reference. Where `.ptr` is a field of a slice reference, the modifiers `mut`, `atomic`, `guard`, and `volatile`, where present on that reference, are inherited unchanged, and the exclusive tribe contributes `mut`. (e.g. `.ptr` of `&volatile guard mut [T]` is `%volatile guard mut T`, and of `$[T]` is `%mut T`.) For a projection, `.ptr` carries `volatile`, `atomic`, and `guard` where the reference nearest the array carries them, and `mut` where the object expression that designates the array is storable at the point of the projection.

#### Design rationale (informative)

The fields are `pub mut` because constructing a slice reference from an arbitrary address and length requires stores to `.ptr` and `.len`.

The tribe of the enclosing reference collapses to the unmanaged tribe on `.ptr` because unmanaged reference arithmetic advances `.ptr` to neighbouring elements. Retaining a managed tribe would extend a derivation chain at every load; retaining the exclusive tribe would issue mutually underived exclusive references to the same referent. The modifiers `mut`, `atomic`, `guard`, and `volatile` are inherited because they govern access to the underlying storage. In particular, losing `volatile` would permit caching or reordering where every access is required to be a σ operation.

#### Examples (informative)

```
let arr: [si4; 3] = [10, 20, 30];
arr.ptr; // %si4 — address of first element
arr.len; // 3
// arr.ptr = ...; — translation failure: a projection is not storable

let r: &[si4] = &arr; // &[si4; 3] implicitly casts to &[si4]
r.ptr; // OK — load always permitted
// r.ptr = ...; — translation failure on landside:
// single-assignment binding
// OK — airside store:
airside { r.ptr = 0x4000_1000~uaddr as %si4; }

let mut s: &[si4] = &arr;
s.len = 2~uaddr; // OK — mut binding
```

## 8.3 Lifetime propagation

Object lifetime categories and their order are defined in the clause on semantics.

### Static semantics

A managed reference carries the object lifetime of the object to which it is chained, or, where it is chained to references, the shortest of the object lifetimes those references carry. One chained to nothing carries the permanent object lifetime.

The object lifetime a value of any other type carries is the shortest of those carried by the values it holds, as the subclause on copy and transfer semantics defines the constituents of a type. A value holding none that carries an object lifetime carries none itself.

### Constraints

Using a binding after the object lifetime of its object has ended shall not appear. Such a violation, where not detected during translation, can cause indeterminate state.

A managed reference stored into an object whose object lifetime is longer than the object lifetime the reference carries shall not appear. A subroutine that returns a managed reference to an object whose object lifetime ends when the subroutine returns shall not appear. Either violation, where not detected during translation, can cause indeterminate state.

### Examples (informative)

```
// Single reference parameter — the result carries what data carries
fn passthrough(data: &[ui1]) -> &[ui1] {
    return data;
}

// Self parameter — the result carries the shortest of self and key
fn find(&self, key: &[ui1]) -> &[ui1] { ... }

// No parameter — the result carries the permanent object lifetime
fn greeting() -> &[ui1] {
    return "permanent";
}

// Struct — the instance carries the shortest object lifetime
// its fields carry
struct view {
    header: &[ui1],
    body: &[ui1]
}
```

## 8.4 Atomic references

### 8.4.1 Two ordering levels

#### Dynamic semantics

A `guard` reference relays and withholds at every read of a load performed through it and at every write of a store so performed, as the clause on semantics defines those properties.

#### Examples (informative)

```
let v = *&atomic x;   // no fence — no ordering

let old = *&atomic ctr;

// atomicity and ordering together, in one access
let once = &guard mut ctr >.< old then old + 1;
```

### 8.4.2 Permitted operations

#### Dynamic semantics

A reference carrying `atomic` or `guard` is an **atomic reference**. An atomic reference `r` permits the load `*r`. One carrying `mut` permits also the store `*r = v` and the compare-and-swap defined in the subclause on the compare-and-swap operator.

Where the atomicity set the evaluation takes holds a pair whose size is that of the referent type and for whose alignment the target address is aligned, every access through the reference is atomic. Otherwise the access can cause indeterminate state.

#### Constraints

— The referent type of a reference type that carries `atomic` or `guard` shall satisfy `atomic`, as defined in the clause on protocols and implementations.

— A reference type that carries `atomic` or `guard` and whose referent type is a type parameter shall appear, whether written or formed by an expression, only where the bound upon that type parameter names `atomic` or names a protocol that entails `atomic`.

— An access through an atomic reference shall be performed by one of the expressions the dynamic semantics above permit.

— A store or a compare-and-swap through an atomic reference created from a field access shall appear only where that field access is storable.

#### Examples (informative)

```
struct counters {
    // mut — atomic store permitted
    mut hits: ui4,
    // not mut — atomic store through &self not permitted
    misses: ui4
}

impl counters {
    fn record_hit(&self, seen: ui4) {
        // OK — hits is mut; the store-permitting reference
        // requires airside
        airside { &atomic mut self.hits >.< seen then seen + 1; }
    }

    fn record_miss(&self, seen: ui4) {
        // &atomic mut self.misses >.< seen then seen + 1;
        // translation failure — misses is not mut
    }

    fn read_misses(&self) -> ui4 {
        return *(&atomic self.misses); // OK — load, no mut required
    }
}
```

### 8.4.3 Ordering fences

Each of the two ordering fences has three forms: a load form written `(load)`, a store form written `(store)`, and an empty form written `()` that orders every τ operation. The two fences are:

— The translation ordering fence is written `volatile()`.

— The execution ordering fence is written `guard()`.

#### Syntax

```
volatile_fence = "volatile", ws, '(', ws,
                 [ ( 'load' | 'store' ), ws ], ')' ;
guard_fence    = "guard",    ws, '(', ws,
                 [ ( 'load' | 'store' ), ws ], ')' ;
```

#### Static semantics

A fence is an expression whose value is `void`.

#### Dynamic semantics

An execution ordering fence relays and withholds at τ operations its execution context performs after it, as defined in the subclause on ordering properties.

— Load form (`(load)`) — a `guard(load)` relays at every read, and withholds at every write, its execution context performs after it.

— Store form (`(store)`) — a `guard(store)` relays and withholds at every write its execution context performs after it.

— Empty form — a `guard()` relays and withholds at every τ operation its execution context performs after it.

A translation ordering fence relays and withholds at no τ operation. The implementation shall arrange the τ operations of the execution context that evaluates it so that the orders an execution ordering fence of the same form establishes among them hold of the arrangement.

#### Examples (informative)

```
// A fence adjoins the access it orders: `(load)` follows the load
// it orders, `(store)` precedes the store it orders.

// translation ordering fence: signal handler synchronization
// (single execution context)
let seen = *&atomic flag;
volatile(load);
volatile(store);
*&atomic mut flag = 1;

// translation ordering fence: fully ordered
// (single-core interrupt handler)
volatile();
*&atomic mut ready = 1;

// execution ordering fence: load and store forms (multi-core)
let val = *&atomic data;
guard(load);
// ... use val ...
guard(store);
*&atomic mut result = computed;

// execution ordering fence: fully ordered (multi-core, empty form)
guard();
```

## 8.5 Unmanaged reference arithmetic

The `+`, `-`, `+=`, and `-=` operators accept a leading operand of unmanaged reference type and a following operand of type `uaddr`. The result type is the type of the leading operand, with all modifiers preserved.

### Dynamic semantics

The cell offset is the following operand multiplied by `T'size`, where `T` is the referent type, or `U` where the referent type is `[U]`. The result is the address of the leading operand’s referent advanced by the offset for `+`, and set back by it for `-`. Both the multiplication and the address computation follow the wrapping semantics defined in the clause on expressions.

The result is an unmanaged reference to the computed address. Where the leading operand is a wide reference, the result carries the same further information.

### Implementation requirements

A conforming implementation should issue an advisory diagnostic when `T'size` is zero.

### Examples (informative)

```
let base: %si4 = arr.ptr;
let third: %si4 = base + 2; // 2 * si4'size cells forwards
let prev: %si4 = third - 1; // 1 * si4'size cells backwards

let mut cursor: %si4 = arr.ptr;
cursor += 1; // advance one element
cursor -= 1; // retreat one element

let vp: %volatile atomic mut ui4 = mmio_base;
let next_reg: %volatile atomic mut ui4 = vp + 1; // modifiers preserved

// Cell-level arithmetic: cast to %ui1
let cell_ptr: %ui1 = base as %ui1;
let offset: %ui1 = cell_ptr + 16; // 16 cells forwards
```

## 8.6 Compare-and-swap operator

### Syntax

```
cas_expr = expression, ws, '>.<', ws, expression, ws, "then", ws,
           expression ;
```

### Static semantics

The compare-and-swap operator has the result type `verdict[T, T]`, the built-in contract type with both payloads of the target’s referent type `T`.

### Dynamic semantics

In `target >.< expected then new`, the three operands are evaluated in that order, and each is evaluated before the next begins. The operation compares the value at the target against `expected`. Where the two are not equal, it leaves the target unchanged and yields the failure variant containing the actual value. Where they are equal, it either replaces the value with `new` and yields the success variant containing the previous value, or leaves the target unchanged and yields the failure variant containing `expected`. The load and the store are performed as one access. Where the transactionality set the evaluation takes holds a pair whose size is that of the referent type and for whose alignment the target address is aligned, that access is transactional. Otherwise the access can cause indeterminate state.

### Constraints

The target shall be an atomic reference carrying `mut`, and `expected` and `new` shall be of its referent type. The referent type shall satisfy `transact`, as defined in the clause on protocols and implementations.

### Implementation defined

The conditions under which the operation leaves the target unchanged where the value at the target equals `expected` are implementation defined.

### Examples (informative)

```
// Unordered CAS with asymmetric fencing: `guard(store)`
// precedes the operation, `guard(load)` follows it
let mut expected = *&guard ctr;
loop {
    guard(store);
    match &atomic mut ctr >.< expected then new {
        let verdict::Pass(old)    -> { guard(load); break; };
        let verdict::Fail(actual) -> { expected = actual; };
    }
}

// Fully ordered CAS — no fences needed
let result = &guard mut ctr >.< expected then new;
if result -> old {
    // CAS succeeded
} else.actual {
    expected = actual;
}

// Replacement whenever the target holds any value other than a
// sentinel. Both sentinel and real_value are integer constants.
let slot_ref = &guard mut slot;
loop {
    let cur = *slot_ref;
    if cur == sentinel { break; }
    match slot_ref >.< cur then real_value {
        let verdict::Pass(old) -> { process(old); break; };
        verdict::Fail(?)       -> { };
    }
}
```

In the first loop, a failure whose payload equals `expected` leaves `expected` unchanged, and the operation is repeated.

## 8.7 Copy and transfer semantics

A value held by a value that another value holds is held by that other value. The **constituents** of a type are the types of the values a value of the type holds. The constituents of a variant type are the types of all its variant payloads. A reference has no constituents.

A type is **uncopyable** where a constituent of the type is uncopyable, or where this specification otherwise states the type to be uncopyable. A constructed type is **copyable** where each of its constituents is copyable and this specification does not otherwise state it to be uncopyable. In semantic analysis, a type parameter is copyable where it satisfies `copyable`, and neither classification applies to it otherwise.

The **destruction obligation** upon a value is the requirement that the value be destroyed. The object or the binding that holds the value holds that obligation, and the subclause on destructors fixes when the value is destroyed.

Wherever an operation yields a value that an object or a binding holds, the value is copied where its type is copyable and transferred where its type is uncopyable. A reference whose value is used only to designate its referent, to create a reference from it, or as the operand of a cast other than `as!` is neither copied nor transferred.

### Constraints

A declaration that introduces a composite type shall declare `with destruct` where a constituent of the type it declares is uncopyable under every choice of type argument.

### 8.7.1 Copy

A **copy** performs a read at each cell of the source storage and a write of the symbol so yielded at the corresponding cell of the destination storage.

### 8.7.2 Transfer

#### Dynamic semantics

A **transfer** is a copy followed by the invalidation of the source. The destruction obligation the source held passes to the destination, and the source holds none thereafter.

## 8.8 Assignment semantics

The assignment expression is defined in the clause on expressions.

### Dynamic semantics

#### Managed references

An access to a copyable type through a managed reference is a copy.

A store of an uncopyable type through a managed reference proceeds in the two steps defined in the clause on expressions.

#### Unmanaged references

An access through an unmanaged reference is a copy.

### Constraints

An uncopyable type shall be loaded through a managed reference only where the load yields a reference whose value is used only to designate its referent or to create a reference from it. Where that use stores through the reference or creates a reference that permits stores, the object expression that yields the reference shall be storable.

### Examples (informative)

```
// managed — copyable: copy
let r: &si4 = &x;
let v = *r;  // copy

// managed — uncopyable store: destruct target, then transfer
*$handle_ref = open("c.bin");

// unmanaged — always copy
airside {
    let val = *(%*src);      // copy, independent obligation
    *(%mut dst) = new_value; // copy, existing value not destroyed
}

// swap via unmanaged references
pub airside fn swap[T](a: $T, b: $T) routes(*b -> *a, *a -> *b) {
    let mut tmp: T = uninit;
    *(%mut tmp) = *(%*a);
    *(%mut *a)  = *(%*b);
    *(%mut *b)  = *(%tmp);
    undestruct(tmp);
}
```

## 8.9 Destructors

### Syntax

```
destruct_clause = "destruct", [ ws, block ] ;
```

### Static semantics

`with destruct` makes the type uncopyable.

Every type has a **destructor**: the block of its `with destruct` clause where the clause carries one, the subroutine this specification otherwise supplies for the type where it supplies one, and a subroutine with no operation in every other case.

Within a `with destruct` block, `self` is an exclusive reference to the object being destroyed. For the rules of this clause and of the subclause on routes, the block is the body of a subroutine whose one parameter is `self` and that carries no `routes` clause. The `with destruct` block does not hold the destruction obligation upon the value the object holds.

### Dynamic semantics

The value an object holds is destroyed at an evaluation of `destruct` upon the object, as the subclause on explicit early destruction defines. It is destroyed also immediately before that object’s storage is released, and upon a store into the object other than through an unmanaged reference, as the clause on expressions defines that store, each if and only if the object is initialized there.

No value is destroyed other than as the rules above call for.

### 8.9.1 Composite destruction

#### Static semantics

Destroying the value an object holds invokes the destructor of its type, and then destroys the value each initialized constituent object of that object holds.

The order for each composite form is:

— Struct — the values the fields hold are destroyed in reverse declaration order.

— Variant type — the payload of the variant the discriminant matches is destroyed.

— Array — the value each element holds is destroyed in reverse index order.

#### Examples (informative)

```
struct buffer {
    data: %ui1,
    len: uaddr
} with destruct {
    // self: $buffer
    release(self.data, self.len);
};

struct parser {
    buf: buffer, // buffer is uncopyable
    pos: uaddr
} with destruct;
// parser needs with destruct because buf is uncopyable.

let p1 = parser.{ .buf = alloc_buffer(1024), .pos = 0 };
let p2 = p1; // transfer: p1 is invalidated
// p1.pos;   // translation failure — p1 was transferred

// When p2 goes out of scope:
//   1. destroying p2.pos performs no operation
//   2. destroying p2.buf invokes buffer’s destructor (release)

enum resource {
    file(file_handle), // file_handle is uncopyable
    none
} with destruct;
// resource needs with destruct because file_handle is uncopyable.
// Destroying a resource value destroys the payload of the variant
// the discriminant matches: file(h) destroys h, none nothing.
```

### 8.9.2 Explicit early destruction

#### Syntax

```
destruct_invocation = "destruct", ws, '(', ws, expression, ws, ')' ;
```

#### Dynamic semantics

`destruct(expr)` has the result type `void`. The value yielded by `expr` is destroyed immediately. The object or the binding that held the value is invalidated and the object becomes uninitialized.

#### Constraints

After a transfer or an evaluation of `destruct` or `undestruct`, the following hold at each programme point that some trace contains after that invalidation, with no store into the object that it invalidates, or into an object of which that object is a constituent object, between them:

— The object that it invalidates, every constituent object of it, and every object of which it is a constituent object shall not be loaded or have a managed reference to it created.

— No constituent object of the object that it invalidates shall be stored into.

The source of a transfer, and the object `destruct` or `undestruct` invalidates, shall not be the object of a `static` binding, or a constituent object of that object or of an object whose type’s `with destruct` clause carries a block.

#### Examples (informative)

```
{
    let handle = open_file("data.bin");
    process(&handle);
    destruct(handle); // destructor is invoked here, not at scope exit
    do_unrelated_work();
}
```

### 8.9.3 Destructor suppression

#### Syntax

```
undestruct_expr = "undestruct", ws, '(', ws, expression, ws, ')' ;
```

#### Dynamic semantics

`undestruct(expr)` has the result type `void`. The value yielded by `expr` is not destroyed. The object or the binding that held the value is invalidated and the object becomes uninitialized.

#### Constraints

An `undestruct` expression requires airside.

#### Examples (informative)

```
airside { undestruct(existing_handle); }
// existing_handle is invalidated. The destructor is not invoked.
```
