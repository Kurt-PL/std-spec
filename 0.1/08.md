# 8. References and resource management

This clause defines the reference system: tribes, modifiers, the derivation chain, routes, reference forms, the propagation of object lifetime, atomic references and ordering fences, unmanaged reference arithmetic, the compare-and-swap operator, the copy and transfer of values, and destructors.

A **reference** is a value that designates an object. The **referent** of a reference is the object that the reference designates. Every reference has a referent type. That of a slice reference is defined in the subclause on slice references, and that of any other reference is the type the tail of its reference type denotes. (e.g. `&T`, `$T`, `%T`.)

## 8.1 Reference properties

### Syntax

```
ref_type     = ref_base, type ;
ref_base     = ref_tribe, ws, { ref_modifier, ws } ;

ref_tribe    = '%' | '&' | '$' ;
ref_modifier = "volatile" | "mut" | "atomic" | "guard" ;
```

The character that leads a reference type is its **tribe**. The modifiers that follow govern how the referent is accessed.

### Static semantics

#### Tribes

&mdash; **Shared reference** (`&`) &mdash; a managed reference that the derivation chain treats as shared.

&mdash; **Exclusive reference** (`$`) &mdash; a managed reference that the derivation chain treats as exclusive.

&mdash; **Unmanaged reference** (`%`) &mdash; a reference that carries no object lifetime and participates in no derivation chain.

A reference whose tribe is `&` or `$` is a **managed reference**.

#### Modifiers

&mdash; Volatile access (`volatile`) &mdash; every access through a reference carrying `volatile` is a σ operation.

&mdash; **Store permission** (`mut`) &mdash; a shared or unmanaged reference carrying `mut` permits stores through the reference, and one without it permits loads alone. An access through a shared reference carrying `mut` requires airside, unless the reference carries `atomic` or `guard`.

&mdash; Unordered atomic access (`atomic`) &mdash; every access through a reference carrying `atomic` is atomic, as the subclause on atomic references defines.

&mdash; Fully ordered atomic access (`guard`) &mdash; a reference carrying `guard` relays and withholds, as the subclause on atomic references defines.

#### Uncopyable references

An exclusive reference is uncopyable.

### Constraints

Each constraint of this clause upon a reference type applies alike to one that is written and to one that an expression forms.

&mdash; A reference type that stacks `atomic` and `guard` shall not appear.

&mdash; A reference type whose tribe is `$` and that carries `mut`, `atomic`, or `guard` shall not appear.

&mdash; The type of a `const` declaration, of an implanted constant, and of a `const` block shall be copyable. The type of a `static` declaration shall neither be nor have as a constituent an exclusive reference type.

For a type, an expression, or a block item, the static semantics and the constraints of this clause hold under every eligible resolution of the type parameters that occur free in it or in a type or an expression within it.

### Design rationale (informative)

Were an exclusive reference copyable, `let a: $si4 = $x; let b = a;` would produce two mutually underived exclusive references to one object.

The reference system &mdash; tribes and the derivation chain &mdash; records, during translation, how one reference is derived from another, and records nothing about storage. Which cells an access spans, and whether two accesses span a cell in common, are settled by the object model of the clause on semantics. No rule of the reference system constrains an effect that it does not record. Instructions within an `instruct` block, subroutines imported through `#dyn`, and other execution originating outside the programme’s Kurt source text have such effects.

```
#dyn io {
    variadic fn printf(%ui1) -> si4;
}

fn poke(x: &saddr) {
    airside { instruct { str '(1), ['p] } with { in('p) = x; } }
}

pub fn reflicate[T](a: %T) -> .{ $T, $T } {
    airside {
        return .{ a as $T, a as $T };
    }
}

fn main() -> ui1 {
    let mut x: saddr = 0;
    poke(&x);                                // x holds 1
    airside { io::printf("%d\n\0".ptr, x); } // prints 1

    let .{ p, q } = reflicate[saddr](%x);    // both designate x
    *p = 2;
    *q = 3;
    airside { io::printf("%d\n\0".ptr, x); } // prints 3
    return 0;
}
```

The programme violates no rule of this specification. `poke` performs a store no reference form permits; `reflicate` produces, without leaving the Kurt source text, the arrangement the uncopyable rule of `$` prevents that text from writing. The reference system establishes that the source text writes neither &mdash; not that neither occurs.

### 8.1.1 Derivation chain

#### Static semantics

The rules of this subclause, of the subclause on routes, and of the subclause on lifetime propagation are the **chain rules**. For the chain rules, the traces of the programme are taken one at a time. On a trace, a programme point is taken to be one visit to it, and each creation, each invocation that chains a new reference, and each construct whose value crosses yields, at each visit, references distinct from those it yields at every other visit. Each constraint of the chain rules shall be met on every trace.

Managed references form **derivation chains**. A cast whose target is a managed reference type, and a decay, each create the reference they yield. Creating a managed reference, whether that creation is explicit or implicit, chains it as follows. An invocation chains so, as a new reference, each managed reference that its return value is or holds.

&mdash; From a reference, the new reference is chained to that reference where it is a managed reference, and to nothing where it is an unmanaged reference.

&mdash; From an object expression that reaches its object through a reference, the new reference is chained to the reference nearest the object where that reference is a managed reference, and to nothing where it is an unmanaged reference.

&mdash; From an object expression that reaches its object without passing through a reference, the new reference is chained to the object the expression names before its first field expression.

&mdash; From an invocation whose return value is or holds it, the new reference is chained to each managed reference that, on that invocation, is at a layer the invoked subroutine routes to `return`, as the subclause on routes defines layers. Where the new reference is exclusive, it is not chained to one that permits no store and through which the field mutability permits none. It is chained to nothing where there is none or where the invoked subroutine routes `static` to `return`.

&mdash; From any other value expression, the new reference is chained to the temporary object holding that value.

&mdash; Otherwise the new reference is chained to nothing.

In place of the rules above, a construct whose value crosses chains each managed reference that its value is or holds as a new reference. Where the referent of that reference does not cross, the new reference is chained to the object of the `static` binding that holds the referent; otherwise it is chained to nothing.

Where the new reference is chained to a reference, the creation, or the invocation, is **reference chaining**.

For the rules of this subclause, the expression of an access is its object expression, or, for a load that a matching performs, the expression whose value that matching matches. An access whose expression reaches its object without passing through a reference is taken, for those rules, to be an access through a managed reference created from that expression at the programme point immediately before the access and pending there. That reference is a shared reference where the access is a load and an exclusive reference otherwise.

On an invocation, a parameter **lends** each managed reference at each of its layers.

For the rules of this subclause and of the subclause on routes, a managed reference chained to more than one reference, or to a reference and to nothing, is taken to be several references, one chained alone to each reference to which it is chained and, where it is chained to nothing as well, one chained to nothing. For those rules, a reference chained to such a managed reference is taken to be chained to each of the several.

The **descent** of a managed reference is the descent of the reference it is chained to, followed by its own field expressions. Its own field expressions, innermost first, are the field expressions from the object it is chained to, or from the referent of the reference it is chained to, that designate the object the following gives, or, where none does, the least object so designated within which that object lies:

&mdash; For a reference created from an object expression, the object that expression names.

&mdash; For a reference that a crossing chains to the object of a `static` binding, its referent.

A reference chained to nothing, and any other reference created from no object expression, has no own field expressions. Where a reference is chained to no reference, nothing precedes its own field expressions.

A managed reference is a **descendant** of the reference to which it is chained and of every ancestor of that reference, and each of those is an **ancestor** of it.

Two managed references **meet** where one object or managed reference is such that each of them either is chained to it or has an ancestor chained to it, and one descent begins with the other, equality included.

A reference is **pending** at a programme point where the trace has, after it, one of the following, with no creation, invocation, or construct that yields the reference between them:

&mdash; An access through the reference.

&mdash; Reference chaining from it.

&mdash; An invocation on which a parameter lends it.

&mdash; A store of it into an object.

On a trace, an object of a managed reference type that is the object of a binding, or a constituent object of that object, holds at a programme point each managed reference placed into it at the last programme point before that one at which a store places a managed reference into it, whether that store names that object or an object of which that object is a constituent object. Where an invocation performs those stores, as the subclause on routes defines, the object holds as well each managed reference it held before them. Where there is no such store and the binding is the binding of a parameter, the object holds each managed reference it holds at subroutine entry.

#### Constraints

An access through an exclusive reference, or an invocation on which a parameter lends it, shall not appear at a programme point at which a descendant of it is pending where, of the following, one begins with the other, equality included:

&mdash; The descent of that descendant after the descent of the exclusive reference.

&mdash; The field expressions that designate, from the referent, the object the access names, or, where none does, the least object so designated within which it lies.

For an invocation, the object the access names is taken to be the referent.

At a programme point at which an exclusive reference is pending, every other managed reference that is pending at the programme point and that meets it shall be an ancestor or a descendant of it.

Every managed reference that a parameter lends on an invocation and that meets an exclusive reference that a parameter lends on that invocation shall be that exclusive reference.

#### Design rationale (informative)

The constraints above on an access and on pending references are stated over what is pending because that is settled by each trace of the programme, and the derivation chain exists to be settled during translation. A reference therefore ceases to constrain where it is no longer pending, which may fall before the end of the scope that holds it.

#### Examples (informative)

```
the object of s (pair)      // descent []
  +- first ($pair)          // descent []
  |    +- next1 (&pair)     // descent []
  |    +- next2 (&mut pair) // descent []
  |    +- next3 ($pair)     // descent []
  |         +- further (&pair)
  +- side ($si4)            // created from $s.f, descent [f]
```

The diagram gives chaining and descent, not what is pending. `next1` and `next2` may be pending together; neither may be pending where `next3` is, and `next3` and `further` may be pending together. `first` and `side` are chained to the same object, and `[f]` begins with `[]`, so they meet. Neither is an ancestor or a descendant of the other, so they may not be pending together.

```
fn id(r: &si4) -> &si4 { return r; }

struct holder {
    val: &si4
}

impl holder {
    fn get(&self) -> &si4 { return self.val; }
}

let mut x: si4 = 1;
let e: $si4 = $x;
let r = id(&*e);             // chained to the argument
// *e = 2;                   // translation failure: r is pending
let v = *r;

let mut y: si4 = 2;
let g: $si4 = $y;
let h = holder.{ .val = &*g };
let s = h.get();             // chained to &h and to the
                             // reference h.val holds
// *g = 3;                   // translation failure: s is pending
let u = *s;
```

### 8.1.2 Routes

#### Syntax

```
routes_clause = "routes", ws, '(', ws, route, ws,
                { ',', ws, route, ws }, [ ',', ws ], ')' ;

route         = route_source, { ws, '+', ws, route_source }, ws,
                '->', ws, route_target ;
route_source  = "static" | route_path ;
route_target  = "return" | "static" | route_path ;
route_path    = { '*', ws }, [ '...', ws ],
                ( identifier | "self" | dec_literal ) ;
```

The `dec_literal` production is defined in the clause on lexical structure.

#### Static semantics

Each `route` in a `routes` clause is a **route** of the declaration or type that carries it. Each `route_source` of a route is a source of it, and its `route_target` is its target.

A `route_path` that carries *k* `*` denotes layer *k* of a parameter, and, where it carries `...`, each layer of that parameter deeper than layer *k* as well. The parameter is the one its identifier names, the self parameter where it carries `self`, or the one whose position is the digit value of its `dec_literal`, counting from zero in declaration order, the self parameter included. `static` denotes no layer.

A subroutine declaration or subroutine pointer type that carries no `routes` clause has one route, whose target is `return` and whose sources denote every layer of every parameter and include `static`.

A subroutine declaration or subroutine pointer type **routes** each layer that a source of one of its routes denotes, and `static` where it is such a source, to the target of that route and to each layer that target denotes.

Two subroutine declarations or subroutine pointer types have the **same routes** where, for `return`, for `static`, and for each layer of each parameter, the one routes the same layers to it as the other, and both or neither route `static` to it. For this comparison, a layer of a parameter is taken to be the same as that layer of the parameter at the same position.

On an invocation, the managed references at **layer** 0 of a parameter are those that the value the invocation stores into the object of the parameter is or holds. Those at layer *k* + 1 are those that the value held by the referent of a managed reference at layer *k* is or holds. For this, the referent is taken to hold as well each managed reference that the invocation stores into it. No other managed reference is at a layer of that parameter.

For the chain rules, a subroutine that uses the variadic variant of its invocation interface, and a subroutine pointer type that carries `variadic`, are taken to have one further parameter, whose position follows that of the last fixed parameter. An invocation is taken to store into the object of that parameter a value that holds the values of the arguments beyond the fixed parameters, and that object is the object of the variadic binding where there is one.

For the chain rules, an invocation stores, through each managed reference that is at layer *k* of a parameter and that permits, or through which the field mutability permits, a store to its referent or to a constituent object of it:

&mdash; For each managed reference at a layer of that parameter deeper than layer *k*, other than one this invocation stores, and for each at a layer the invoked subroutine routes to layer *k* + 1 of that parameter, a new reference of its type chained to it.

&mdash; Where the invoked subroutine routes `static` to layer *k* + 1 of that parameter, a managed reference chained to nothing of each managed reference type that is, or is a constituent of, the referent type of that reference at layer *k*.

Each of these is stored by a store that names the referent.

For the chain rules, an invocation also stores each managed reference at a layer the invoked subroutine routes to `static`, by a store that names, without passing through a reference, a permanent object or a constituent object of one. Each managed reference so stored is pending at every programme point after the invocation.

For the rules of this subclause, a construct is within the body of the innermost subroutine whose body contains it, and of no other subroutine. Within the body of a subroutine, for those rules:

&mdash; The value of the binding of a parameter at subroutine entry is taken to be or hold managed references that **come from** layer 0 of that parameter.

&mdash; A load within the body through a managed reference that comes from layer *k* of a parameter is taken to yield a value that is or holds managed references that come from layer *k* + 1 of that parameter.

&mdash; An invocation within the body is taken to perform a load through each managed reference at a layer of a parameter of the invoked subroutine.

A managed reference comes from each layer these give it and each layer from which an ancestor of it comes, and from no other.

#### Constraints

Within the body of a subroutine, for each managed reference that the value the subroutine returns is or holds:

&mdash; Each layer from which it comes shall be one the subroutine routes to `return`.

&mdash; Where it comes from none, the subroutine shall route `static` to `return`.

&mdash; Neither it nor an ancestor of it shall be chained to a mortal object.

Within the body of a subroutine, where the reference nearest the object a store names is a managed reference and comes from layer *k* of a parameter, for each managed reference that the store places:

&mdash; Each layer from which it comes shall be a layer of that parameter deeper than layer *k* or one the subroutine routes to layer *k* + 1 of that parameter.

&mdash; Neither it nor an ancestor of it shall be chained to a mortal object.

Within the body of a subroutine, the subroutine shall route `static` to layer *k* + 1 of a parameter where a store satisfies both of the following:

&mdash; The reference nearest the object it names is a managed reference and comes from layer *k* of that parameter.

&mdash; A managed reference that it places comes from no layer. That reference is exclusive, carries `mut`, or has a referent type that is a protocol type or is, or has as a constituent, a managed reference type or a type with a field that has field mutability.

Within the body of a subroutine, for each managed reference that a store of either kind below places, each layer from which it comes shall be one the subroutine routes to `static`, and neither it nor an ancestor of it shall be chained to a mortal object:

&mdash; A store that names, without passing through a reference, a permanent object or a constituent object of one.

&mdash; A store where the reference nearest the object it names is a managed reference, comes from no layer of a parameter, and neither it nor an ancestor of it is chained to a mortal object.

None of the constraints of this subclause applies to the following:

&mdash; A managed reference that is, or has an ancestor that is, created from an unmanaged reference or from an object expression in which the reference nearest the object is an unmanaged reference.

&mdash; A managed reference that a load yields through an unmanaged reference or through a reference the item above names.

&mdash; A store whose reference nearest the object is a reference either item above names.

A `route_path` shall denote a layer of a parameter of the declaration or type that carries it. The target of a route shall be `return`, `static`, or a `route_path` that carries a `*`.

#### Examples (informative)

```
struct slot {
    h: &[ui1]
}

fn set(s: $slot, x: &[ui1]) routes(x -> *s) {
    s.h = x;
}

// fn put(s: $slot, x: &[ui1]) { s.h = x; }
// translation failure: no route to *s

struct words {
    s: &[&[ui1]]
}

impl words {
    fn next($self) -> &[ui1] routes(**self + static -> return) {
        let [..., w] = self.s else { return ""; };
        self.s.len -= 1;
        return w;
    }
}

enum link {
    end,
    more { &mut node }
} with copyable;

struct node {
    val: si4,
    rest: link
}

impl node {
    fn append(&mut self, n: &mut node) routes(n -> *...self) {
        let mut cur: &mut node = self;
        airside {
            while let link::more.{ r } = cur.rest { cur = r; }
            cur.rest = link::more.{ n };
        }
    }
}

// With routes(n -> *self) in its place on append,
// translation failure: cur comes from every layer of self

let mut sl = slot.{ .h = "" };
{
    let t: [ui1; 2] = [1, 2];
    // set($sl, &t); // translation failure: sl outlives t
}

let f: fn($slot, &[ui1]) routes(1 -> *0) = set;
// let p: fn($slot, &[ui1]) = set;
// translation failure: routes differ
f($sl, "ok");

let list: [&[ui1]; 2] = ["a", "b"];
let mut it = words.{ .s = &list };
let a = it.next(); // chained to the references list holds
let b = it.next(); // a is not chained to $it
print(a);
print(b);
```

### 8.1.3 Modifier placement

#### Static semantics

A reference type is the same type whatever the order in which its modifiers are written.

#### Constraints

A reference type that repeats a modifier shall not appear.

### 8.2.2 Reference representation

#### Static semantics

A slice reference, or a reference to a protocol type, is a **wide reference**. It carries an address together with the **further information** needed to describe the referent. For a slice reference that information is the length. For a reference to a protocol type it is the pair of descriptor references that the clause on protocols and implantations defines. The referent of a reference to a protocol type is the object of its **erased type**, the type whose type descriptor `.tyd` designates, at the address `.ptr` carries.

#### Constraints

An expression that has the referent type of a wide reference shall be the operand of a reference creation.

### 8.2.3 Reference casting

Casts between reference types are written with `as`. A **re-reference** `tribe [modifiers] *expr`, where `expr` has a reference type, converts the reference that `expr` yields to a reference with the specified tribe and modifiers, and performs no access.

A cast and a re-reference each apply four conversions: the **tribe conversion**, which determines the tribe of the result, and the `volatile`, store permission, and atomicity **modifier conversions**.

#### Static semantics

A reference cast or a re-reference requires airside where its tribe conversion or any of its modifier conversions requires airside, and requires none where its target type is the type of its source.

An exclusive reference is taken, in these tables, to carry `mut`. Where the source is an unmanaged reference, a modifier conversion the tables mark a translation failure is permitted and requires airside.

A reference decays to each other reference type that has the same referent type and to which a cast from it is permitted and requires no airside. The decay yields the result of that cast.

#### Dynamic semantics

The result of a cast between reference types, and that of a re-reference, has the address and the further information of the reference it converts.

#### Constraints

A cast or a re-reference whose tribe conversion, or any of whose modifier conversions, is not permitted shall not appear.

Where the target type of a cast is a managed reference type, its referent type shall be the referent type of the source.

The source and the target of a cast between reference types shall both be slice references, both be references to a protocol type, or both be neither. Where both are references to a protocol type, their referent types shall be the same.

#### Design rationale (informative)

A managed reference that is neither an ancestor nor a descendant of an exclusive reference would be pending beside it, contrary to the constraints of the subclause on the derivation chain. The cast to an exclusive reference from a managed reference is therefore a translation failure.

An access performed without atomicity upon an object that another execution context accesses atomically conflicts with it. Atomicity is therefore retained within the managed tribes. A programme that requires a form without it casts to `%` first, where the region is airside.

A cast from a managed reference to a form without `volatile` would permit the implementation to transform accesses this specification requires it to perform.

The store permission conversion permits no cast to `mut` from a shared reference without `mut`, because a reference that carries `mut` can be created only from a binding that permits stores. Such a cast would confer store permission on an object whose binding withholds it.

#### Examples (informative)

```
// Tribe casts permitted on landside
let shared: &T = exclusive as &T; // $T → &T: no exclusivity, no store
let uman: %T = shared as %T;      // &T → %T: no object lifetime

// Tribe casts requiring airside
let managed: &T = airside { express uman as &T; }; // %T → &T
let excl: $T = airside { express uman as $T; };    // %T → $T

// Prohibited tribe casts
// shared as $T; // translation failure: &T → $T

// Modifier casts

// &T → &volatile T
let vol: &volatile T = shared as &volatile T;
// &atomic T → &guard T
let guarded: &guard T = atomic_ref as &guard T;
// &guard T → &atomic T
let unord: &atomic T = guarded as &atomic T;
// &T → &atomic T
let atomic_view: &atomic T = shared as &atomic T;
// &mut T → &atomic mut T
let atomic_store: &atomic mut T = mut_ref as &atomic mut T;
// &atomic mut T → &atomic T
let load_only: &atomic T = atomic_store as &atomic T;

// translation failures:
// vol as &T;              // &volatile T → &T
// atomic_store as &mut T; // &atomic mut T → &mut T
// shared as &mut T;       // &T → &mut T

// Combined: tribe + modifier in one cast
let uman_from_excl: %T = exclusive as %T;          // $T → %T
let vol_uman: %volatile T = shared as %volatile T; // &T → %volatile T

// Re-reference: tribe conversion
let shared2: &T = &*excl; // $T → &T (equivalent to: excl as &T)

// Re-reference: modifier addition
let p: %ui4 = ...;
airside {
    let vp: %volatile ui4 = %volatile *p; // add volatile
    let ap: %atomic ui4 = %atomic *p;     // add atomic
}
```

### 8.2.4 Conversion between a reference and `uaddr`

#### Static semantics

A reference and a `uaddr` are converted into one another with `as`. Neither the tribe conversion nor any modifier conversion applies to such a cast.

A cast from a reference to `uaddr` yields the address the reference carries.

#### Constraints

The source of a cast to a managed reference type shall be a reference type. A cast from `uaddr` to a wide reference shall not appear.

#### Implementation defined

What a cast from `uaddr` to an unmanaged reference type gives the reference besides the address is implementation defined.

#### Examples (informative)

```
let addr: uaddr = uman as uaddr;        // %T → uaddr: no reference
let direct: uaddr = exclusive as uaddr; // $T → uaddr
let uman2: %T = addr as %T;             // uaddr → %T

// addr as &T; // translation failure: uaddr reaches %T alone
```

### 8.2.5 Slice references

A **slice reference** describes a contiguous run of elements of the type its brackets enclose, whose count is determined at execution time.

#### Syntax

```
slice_reference = ref_tribe, ws, { ref_modifier, ws },
                  '[', ws, type, ws, ']' ;
```

#### Static semantics

The referent type of a slice reference is the array type of its element type whose length is the length the reference carries. In semantic analysis, the referent type of a slice reference is the same as that of each slice reference with the same element type, and as no other type. The values of the referent type of a slice reference are the values of the array types of its element type, of every length. A reference whose referent type is that of a slice reference is a slice reference with the same element type.

A reference to the array `[T; N]` decays to the corresponding slice reference. That is the slice reference whose tribe, modifiers, and element type match, whose `.ptr` is the address of the array, and whose `.len` is `N`.

A `[T; N]` value and a slice reference both expose the address of the first element and the length as built-in fields:

<table>
<thead><tr><th>Field</th><th>Type</th><th>Content</th></tr></thead>
<tbody>
<tr><td><code>mut ptr</code></td><td>as below</td><td>An unmanaged reference to the first element.</td></tr>
<tr><td><code>mut len</code></td><td><code>uaddr</code></td><td>The length.</td></tr>
</tbody>
</table>

When `.ptr` or `.len` is applied to an array value, the field expression is a **projection**. `.ptr` is then the address of the first element, and its projection creates a reference to that element; `.len` is `N`.

A slice reference has the stored representation defined below, and `.ptr` and `.len` of a slice reference object are the fields of that representation. They have field mutability.

The stored representation of a slice reference is two fields in this order:

<table>
<thead><tr><th>Field</th><th>Content</th></tr></thead>
<tbody>
<tr><td><code>ptr</code></td><td>unmanaged reference (reference width)</td></tr>
<tr><td><code>len</code></td><td><code>uaddr</code> (address width)</td></tr>
</tbody>
</table>

Kurt standard alignment gives the offset of each field, and the size and the alignment of the reference, from the types of those fields in that order.

The type of `.ptr` is an unmanaged reference. Where `.ptr` is a field of a slice reference, the modifiers `mut`, `atomic`, `guard`, and `volatile`, where present on that reference, are inherited unchanged, and the exclusive tribe contributes `mut`. (e.g. `.ptr` of `&volatile guard mut [T]` is `%volatile guard mut T`, and of `$[T]` is `%mut T`.)

For a projection, `.ptr` carries `volatile`, `atomic`, and `guard` where an access to the array through the receiver of the projection is performed through a reference that carries them, and `mut` where a store to the array through the receiver of the projection is permitted at the programme point of the projection.

#### Design rationale (informative)

The fields are `mut` because constructing a slice reference from an arbitrary address and length requires stores to `.ptr` and `.len`.

The tribe of the enclosing reference collapses to the unmanaged tribe on `.ptr` because unmanaged reference arithmetic advances `.ptr` to neighbouring elements. Retaining a managed tribe would extend a derivation chain at every load; retaining the exclusive tribe would issue mutually underived exclusive references to the same referent. The modifiers `mut`, `atomic`, `guard`, and `volatile` are inherited because they govern access to the underlying storage.

#### Examples (informative)

```
let arr: [si4; 3] = [10, 20, 30];
arr.ptr;              // %si4: address of first element
arr.len;              // 3
// arr.ptr = ...;     // translation failure: a projection is a value

let r: &[si4] = &arr; // &[si4; 3] decays to &[si4]
r.ptr;                // OK: load always permitted
// r.ptr = ...;       // translation failure on landside:
                      // single-assignment binding
// OK as an airside store:
airside { r.ptr = 0x4000_1000 as %si4; }

let mut s: &[si4] = &arr;
s.len = 2~uaddr;      // OK: mut binding
```

## 8.3 Lifetime propagation

### Static semantics

A managed reference carries the object lifetime of the object to which it is chained, or, where it is chained to references, the shortest of the object lifetimes those references carry. One chained to nothing carries the object lifetime of an immortal object.

The object lifetime a value of any other type carries is the shortest of those carried by the values it holds, as the subclause on copy and transfer semantics defines holding. A value holding none that carries an object lifetime carries none itself.

### Constraints

Using a binding after the object lifetime of its object has ended shall not appear. Such a violation, where not detected during translation, can cause indeterminate state.

A managed reference stored into an object whose object lifetime is longer than the object lifetime the reference carries shall not appear. A subroutine that returns a managed reference to an object whose object lifetime ends when the subroutine returns shall not appear. Either violation, where not detected during translation, can cause indeterminate state.

### Examples (informative)

```
// Single reference parameter: the result carries what data carries
fn passthrough(data: &[ui1]) -> &[ui1] {
    return data;
}

// Self parameter: the result carries the shortest of self and key
fn find(&self, key: &[ui1]) -> &[ui1] { ... }

// No parameter: the result carries the object lifetime of an
// immortal object
fn greeting() -> &[ui1] {
    return "hello";
}

// Struct: the instance carries the shortest object lifetime
// its fields carry
struct view {
    header: &[ui1],
    body: &[ui1]
}
```

## 8.4 Atomic references

### 8.4.1 Relaying and withholding by `guard`

#### Dynamic semantics

A `guard` reference relays and withholds loads and stores at the τ operations of each access performed through it, as the clause on semantics defines those properties.

#### Examples (informative)

```
let v = *&atomic x; // no fence: no ordering

let old = *&atomic ctr;

// atomicity and ordering together, in one access
let once = &guard mut ctr >.< old then old + 1;
```

### 8.4.2 Permitted operations

#### Static semantics

A reference carrying `atomic` or `guard` is an **atomic reference**. An atomic reference `r` permits the load `*r`. One carrying `mut` permits also the store `*r = v` and the compare-and-swap defined in the subclause on the compare-and-swap operator.

#### Dynamic semantics

Where the atomicity set the evaluation takes holds a pair whose size is that of the referent type of an atomic reference and for whose alignment the target address is aligned, every access through that reference is atomic. Otherwise such an access can cause indeterminate state.

#### Constraints

&mdash; Where a reference type carries `atomic` or `guard`, its referent type shall satisfy `atomic` where that reference type is not a slice reference, and so shall the element type of its referent type where that referent type is an array type.

&mdash; An access through an atomic reference shall be performed by one of the expressions the static semantics above permit.

&mdash; A store or a compare-and-swap through an atomic reference created from a field expression shall appear only where that field expression is storable.

#### Examples (informative)

```
struct counters {
    // mut: atomic store permitted
    mut hits: ui4,
    // not mut: atomic store through &self not permitted
    misses: ui4
}

impl counters {
    fn record_hit(&self, seen: ui4) {
        // OK: hits is mut; the store-permitting reference
        // requires airside
        airside { &atomic mut self.hits >.< seen then seen + 1; }
    }

    fn record_miss(&self, seen: ui4) {
        // &atomic mut self.misses >.< seen then seen + 1;
        // translation failure: misses is not mut
    }

    fn read_misses(&self) -> ui4 {
        return *(&atomic self.misses); // OK: load, no mut required
    }
}
```

### 8.4.3 Ordering fences

Each of the two ordering fences has three forms: a load form written `.load()`, a store form written `.store()`, and an empty form written `()`. The two fences are:

&mdash; The translation ordering fence is written `volatile`.

&mdash; The execution ordering fence is written `guard`.

#### Syntax

```
volatile_fence = "volatile", fence_form ;
guard_fence    = "guard",    fence_form ;
fence_form     = [ ws, '.', ws, ( 'load' | 'store' ) ],
                 ws, '(', ws, ')' ;
```

#### Static semantics

A fence is an expression whose value is `void`.

#### Dynamic semantics

An execution ordering fence relays and withholds at the τ operations its execution context performs after it, as defined in the subclause on ordering properties:

&mdash; Load form (`.load()`) &mdash; a `guard.load()` relays loads and withholds stores.

&mdash; Store form (`.store()`) &mdash; a `guard.store()` relays and withholds stores.

&mdash; Empty form &mdash; a `guard()` relays and withholds loads and stores.

A translation ordering fence relays and withholds at no τ operation.

#### Implementation requirements

Where, at an evaluation of a translation ordering fence, an execution ordering fence of the same form would order one τ operation of its execution context before another, the implementation shall not perform the second before the first. Of the τ operations so ordered, the implementation shall perform, at each cell, the last before that evaluation and the first after it.

#### Examples (informative)

```
// A fence adjoins the access it orders: `.load()` follows the load
// it orders, `.store()` precedes the store it orders.

// translation ordering fence: load and store forms
// (one execution context)
let seen = *&atomic flag;
volatile.load();
volatile.store();
*&atomic mut flag = 1;

// translation ordering fence: empty form
// (one execution context)
volatile();
*&atomic mut ready = 1;

// execution ordering fence: load and store forms
// (several execution contexts)
let val = *&atomic data;
guard.load();
// ... use val ...
guard.store();
*&atomic mut result = computed;

// execution ordering fence: empty form
// (several execution contexts)
guard();
```

## 8.5 Unmanaged reference arithmetic

### Static semantics

Where the synthesized type of the leading operand of `+` or `-` is an unmanaged reference type, the result type is the type of the leading operand.

### Dynamic semantics

The cell offset is the following operand multiplied by `T'size`, where `T` is the referent type, or the element type where the leading operand is a slice reference. The result carries the address that the leading operand carries, advanced by the offset for `+` and set back by it for `-`. Both the multiplication and the address computation follow the wrapping semantics defined in the clause on expressions.

Where the leading operand is a wide reference, the result carries the same further information.

### Implementation requirements

The implementation should issue an advisory diagnostic when `T'size` is zero.

### Examples (informative)

```
let base: %si4 = arr.ptr;
let third: %si4 = base + 2; // 2 * si4'size cells forwards
let prev: %si4 = third - 1; // 1 * si4'size cells backwards

let mut cursor: %si4 = arr.ptr;
cursor += 1; // advance one element
cursor -= 1; // retreat one element

let vp: %volatile atomic mut ui4 = mmio_base;
let next_reg: %volatile atomic mut ui4 = vp + 1; // modifiers preserved

// Cell-level arithmetic: cast to %ui1
let cell_ptr: %ui1 = base as %ui1;
let offset: %ui1 = cell_ptr + 16; // 16 cells forwards
```

## 8.6 Compare-and-swap operator

### Syntax

```
cas_expr = expression, ws, '>.<', ws, expression, ws, "then", ws,
           expression ;
```

### Static semantics

The compare-and-swap operator has the result type `verdict[T, T]`, where `T` is the referent type of the target.

### Dynamic semantics

In `target >.< expected then new`, the three operands are evaluated in that order.

The operation compares the value at the target against `expected`. Where the two are not equal, it leaves the target unchanged and yields the failure variant containing the actual value. Where they are equal, it either replaces the value with `new` and yields the success variant containing the previous value, or leaves the target unchanged and yields the failure variant containing `expected`.

The operation performs one access: a load and a store where it replaces the value, and, where it leaves the target unchanged, a load alone or a load and a store of the value loaded. Where the transactionality set the evaluation takes holds a pair whose size is that of the referent type and for whose alignment the target address is aligned, that access is transactional. Otherwise the access can cause indeterminate state.

### Constraints

The target shall be an atomic reference carrying `mut`, and `expected` and `new` shall be of its referent type. The referent type shall satisfy `transact`, as defined in the clause on protocols and implantations.

### Implementation defined

The conditions under which the operation leaves the target unchanged where the value at the target equals `expected` are implementation defined.

Whether the operation stores the value it loads where it leaves the target unchanged is implementation defined.

### Examples (informative)

```
// Unordered CAS with asymmetric fencing: `guard.store()`
// precedes the operation, `guard.load()` follows it
let mut expected = *&guard ctr;
loop {
    guard.store();
    match &atomic mut ctr >.< expected then new {
        let verdict::Pass.{ old }    -> { guard.load(); break; };
        let verdict::Fail.{ actual } -> { expected = actual; };
    }
}

// Fully ordered CAS: no fences needed
let result = &guard mut ctr >.< expected then new;
if result -> old {
    // CAS succeeded
} else.actual {
    expected = actual;
}

// Replacement whenever the target holds any value other than a
// sentinel. Both sentinel and real_value are integer constants.
let slot_ref = &guard mut slot;
loop {
    let cur = *slot_ref;
    if cur == sentinel { break; }
    match slot_ref >.< cur then real_value {
        let verdict::Pass.{ old } -> { process(old); break; };
        verdict::Fail             -> { };
    }
}
```

## 8.7 Copy and transfer semantics

A value of a struct type or of an anonymous struct type holds the value of each of its fields other than a `?` field, and a value of an array type the value of each of its elements. A value of a variant type holds its discriminant and the value of each field, other than a `?` field, of the variant it holds. A value held by a value that another value holds is held by that other value.

The **constituents** of a type are the types of the values a value of the type holds. The constituents of a variant type are its discriminant type and the types of the fields, other than `?` fields, of all its variants. A reference has no constituents.

A built-in type or a composite type whose declaration carries `with copyable` is **copyable** where each of its constituents is copyable, unless this specification states it to be **uncopyable**. Any other composite type is uncopyable. A type with an uncopyable constituent is uncopyable. In semantic analysis, a type parameter is copyable where it satisfies `copyable`, and neither classification applies to it otherwise.

A reference whose value is used only to designate its referent, to create a reference from it, or as the operand of a cast or of a decay is neither copied nor transferred.

### Dynamic semantics

A **copy** of a value that a load yields performs, at each cell of the destination storage, a write of the symbol that load read at the corresponding cell of the storage region of the object it names.

A load, other than through an unmanaged reference, of a value of an uncopyable type **transfers** that value where it yields it, and any other load yields a value to be copied.

A matching **takes** each portion bound by a binding that receives a value from that matching. It also takes each payload that the subclause defining its construct states to be, or to be held by, the value of the construct or a value the enclosing subroutine returns. A load that a matching performs yields the value of each portion that the matching takes, where the matching takes it, and yields no other value. To each value so yielded, the definitions of a copy and of a transfer in this subclause apply as to a load of that portion through the reference, if any, through which that load is performed.

The object that a transferring load names is the source of that transfer. The transfer invalidates its source. Then, where the outermost object of the source is still initialized, the value that outermost object holds is destroyed, as the subclause on composite destruction defines, and the outermost object is invalidated. The transfers of one matching invalidate all their sources before any such destruction.

### Constraints

The type of each field of a declaration that carries `with copyable` shall be copyable where the type argument for each type parameter of the declaration is copyable.

On each trace, from the invalidation of the outermost object of the source of a transfer up to and including the next store into that outermost object made without passing through a reference, the following apply to that outermost object at each access other than through an unmanaged reference and at each creation of a managed reference:

&mdash; Neither it nor any constituent object of it shall be loaded or have a managed reference to it created.

&mdash; No constituent object of it shall be stored into.

Such a violation through a reference, where not detected during translation, can cause indeterminate state.

The sources of the transfers of one matching shall be distinct objects, none of which is a constituent object of another.

No source of a transfer shall be an immortal object, or a constituent object of an object of a type whose destructor is a `with destruct` block or one the implementation supplies.

A load through a managed reference shall transfer no value. Where such a load yields a reference of an uncopyable type and that reference is used to store through it or to create a reference that permits stores, the object expression that yields it shall be storable.

### Examples (informative)

```
// managed, copyable: copy
let r: &si4 = &x;
let v = *r; // copy

// managed, uncopyable store: transfer; the existing value
// is destroyed before the write
*$handle_ref = open("c.bin");

// unmanaged: a load copies, a store destroys nothing
airside {
    let val = *(%*src);      // copy, destroyed independently
    *(%mut dst) = new_value; // existing value not destroyed
}

// swap via unmanaged references
pub airside fn swap[T](a: $T, b: $T) routes(*b -> *a, *a -> *b) {
    let mut tmp: T = uninit;
    *(%mut tmp) = *(%*a);
    *(%mut *a)  = *(%*b);
    *(%mut *b)  = *(%tmp);
    undrop(tmp);
}
```

## 8.8 Destructors

### Syntax

```
destruct_clause = 'destruct', ws, block ;
```

### Static semantics

Every type has a **destructor**: the block of the `with destruct` clause where its declaration carries one, the subroutine the implementation supplies for the type where this specification states that it supplies one, and otherwise a subroutine with no operation.

Within a `with destruct` block, `self` is an exclusive reference to the object being destroyed. The block is the body of a subroutine whose one declared parameter is a self parameter that the `destruct` keyword introduces into the block, whose return type is `void`, and that carries no `routes` clause. Its invocation also receives the type descriptor of the type, as the subroutine that field 2 of that descriptor designates receives it.

### Dynamic semantics

No value is destroyed other than as a rule of this specification calls for.

### Examples (informative)

```
// x is destroyed where the body ends
fn drop[T](x: T) {}

// A store through an unmanaged reference destroys nothing and
// leaves sink uninitialized: x, where its type is uncopyable,
// is transferred to it, and neither is destroyed where the body
// ends
airside fn undrop[T](x: T) {
    let mut sink: T;
    *(%mut sink) = x;
}

{
    let handle = open_file("data.bin");
    process(&handle);
    drop(handle); // destructor is invoked here, not at scope exit
    do_unrelated_work();
}

airside { undrop(existing_handle); }
// existing_handle is invalidated. The destructor is not invoked.
```

### 8.8.1 Composite destruction

#### Static semantics

Destroying the value an object holds invokes the destructor of its type, and then destroys the value held by each initialized constituent object that its type places directly and that the definition of holding names for that value, in this order:

&mdash; Struct or variant type &mdash; the values the fields hold are destroyed in reverse declaration order, and then, for a variant type, the value its discriminant holds.

&mdash; Anonymous struct type &mdash; the values the fields hold are destroyed in reverse index order.

&mdash; Array &mdash; the value each element holds is destroyed in reverse index order.

#### Examples (informative)

```
struct buffer {
    data: %ui1,
    len: uaddr
} with destruct {
    // self: $buffer
    release(self.data, self.len);
};

struct parser {
    buf: buffer,
    pos: uaddr
}

let p1 = parser.{ .buf = alloc_buffer(1024), .pos = 0 };
let p2 = p1; // transfer: p1 is invalidated
// p1.pos;   // translation failure: p1 was transferred

// When p2 goes out of scope:
//   1. destroying p2.pos performs no operation
//   2. destroying p2.buf invokes buffer’s destructor (release)

enum resource {
    file { file_handle },
    none
}
// Destroying a resource value destroys the fields of the variant
// the discriminant matches, and then the discriminant: file
// destroys its field first, none only the discriminant.
```
