# §5. Declarations

This clause defines the declarations of the Kurt programming language: subroutines, bindings, composite types, generics, patterns, `with` clauses, visibility, and the prefixes an item may carry.

## 5.1 Items

A **declaration** introduces a name into a scope. A **definition** does so and determines the contents of what it names.

### Syntax

```
item        = { item_prefix, ws }, ( global_item | local_item ) ;

item_prefix = annotation
            | symbol_directive
            | inline_directive
            | no_inline_directive ;

global_item = module_decl
            | impl_block
            | protocol_decl
            | global_asm ;

local_item  = subroutine_def
            | const_decl
            | static_decl
            | struct_decl
            | enum_decl
            | contract_decl
            | type_alias_decl
            | use_decl
            | add_decl
            | path_decl
            | dyn_decl
            | trap_handler_decl ;
```

A **global item** appears in a source unit or in a module body. A **local item** appears there and in a block as well. The block is defined in the clause on statements and control flow, and the source unit and the module body in the clause on programme structure and translation.

An **item prefix** stands upon an item. Item prefixes may stand in any order, and the subclause that defines each states what it may prefix.

`module_decl`, `add_decl`, `path_decl`, and `dyn_decl` are defined in the clause on programme structure and translation. `impl_block` and `protocol_decl` are defined in the clause on protocols and implementations. `contract_decl` and `trap_handler_decl` are defined in the clause on statements and control flow. Every other item is defined in this clause.

### Constraints

An item prefix other than an annotation shall stand at most once upon what it prefixes. An annotation may stand upon what it prefixes any number of times.

A local item that appears in a block shall not refer to a binding whose object has the automatic object lifetime, or to a generic parameter, that is declared outside the item, shall not name the `selftype` of an enclosing declaration, and shall not name, by its identifier alone and other than as the method of a method invocation, an item of an enclosing protocol or of a protocol that the bound list of an enclosing protocol names.

## 5.2 Subroutine declarations

A subroutine declaration introduces a named computation.

### Syntax

```
(* Shared productions *)
extern_clause     = "extern", [ ws, '(', ws, identifier, ws, ')' ] ;
variadic_clause   = "variadic", ws, '(', ws, identifier, ws, ':', ws,
                    type, ws, ')' ;
subroutine_return = '->', ws, ( type | '!' ) ;

(* Headers *)
subroutine_def_header   = [ "pub", ws ], [ extern_clause, ws ],
                          [ variadic_clause, ws ], [ "airside", ws ],
                          "fn", ws, identifier, [ ws, generic_clause ] ;

subroutine_proto_header = [ "pub", ws ], [ extern_clause, ws ],
                          [ "variadic", ws ], [ "airside", ws ],
                          "fn", ws, identifier, [ ws, generic_clause ] ;

(* Parameter lists *)
subroutine_def_param   = '(', ws, [ parameter_list ], ws, ')' ;
subroutine_proto_param = '(', ws, [ proto_parameter_list ], ws, ')' ;

parameter_list = parameter, ws, { ',', ws, parameter, ws },
                 [ ',', ws ] ;
parameter      = [ "mut", ws ], identifier, ws, ':', ws, type ;

proto_parameter_list = proto_parameter, ws,
                       { ',', ws, proto_parameter, ws }, [ ',', ws ] ;
proto_parameter      = [ "mut", ws ], [ identifier, ws, ':', ws ],
                       type ;

(* Definition form — parameter names mandatory *)
subroutine_def = subroutine_def_header, ws, subroutine_def_param,
                 [ ws, subroutine_return ],
                 [ ws, with_single | ws, with_curly ], ws, block ;

(* The header and parameter list without a body are used by the `#dyn`
   block, as defined in the clause on programme structure and
   translation. *)
```

The `generic_clause` production is defined in the subclause on generic declarations.

### Static semantics

A subroutine definition introduces a named subroutine into the enclosing scope and supplies its operations. Every subroutine has an invocation interface. It is `native` unless an `extern` clause names another, as the subclause on external declaration defines.

A **subroutine prototype** states the name, the parameters, and the return type of a subroutine. It appears only in a `#dyn` block, as defined in the clause on programme structure and translation, or in a protocol body, as defined in the clause on protocols and implementations. Parameter names are optional in a subroutine prototype, and a name that appears in one has no semantic effect.

If `-> T` is omitted, the return type is `void`.

A parameter without `mut` is a single-assignment binding. It may be loaded from, and an assignment to it within the subroutine body shall not appear. A parameter declared `mut` is a multi-assignment binding. It may be loaded from and assigned to, and exclusive references and shared mutable references may be created from it. In both cases, the argument value is copied or transferred into the parameter binding, as defined in the clause on references and resource management. `mut` on a parameter governs the parameter binding alone.

A subroutine may name itself, and two or more subroutines may name each other. Recursion is permitted to any depth the execution environment sustains.

### Dynamic semantics

When a subroutine is invoked, execution proceeds as follows:

1. Argument evaluation — each argument expression is evaluated in the order defined in the subclause on subroutine invocation. The resulting values are copied or transferred into the parameter bindings.
2. Subroutine body execution — the body executes. It can return early via `return`, diverge via `trap()`, or reach the closing curly bracket.
3. Value return — the return value is copied or transferred to the invoker.
4. Local destruction — the bindings of the invocation are destroyed in the order defined in the clause on semantics.

### Constraints

A subroutine parameter shall have a unique name within the parameter list.

Where a subroutine definition declares `-> !`, or declares a return type other than `void`, the programme point at the end of its body shall be unreachable. A subroutine declaring `-> !` shall not return control to its invoker. Reachability is defined in the clause on semantics.

### Examples (informative)

```
fn add(a: si4, b: si4) -> si4 { return a + b; }
fn diverge() -> ! { trap(); }
fn unit() { } // returns void

// extern subroutine — native invocation interface, symbol preserved
pub extern fn init() { ... }
pub extern(efi) fn efi_entry(handle: uaddr, table: %ui1)
    -> uaddr { ... }

// Argument evaluation order — a() runs before b(), b() before c()
foo(a(), b(), c());

// mut parameter — the parameter binding is multi-assignment
fn zero_and_sum(mut buf: [si4; 4]) -> si4 {
    let mut total: si4 = 0;
    let mut i = 0;

    while i < 4 {
        total += buf.at(i);
        *buf.at_mut(i) = 0;
    } then { i += 1; }

    return total;
}

// Direct recursion
fn factorial(n: uaddr) -> uaddr {
    return if n == 0 then 1 else n * factorial(n - 1);
}
```

### 5.2.1 `airside fn`

The `airside` modifier on a subroutine declaration specifies that the subroutine body is an airside region, as the clause on semantics defines airside.

#### Static semantics

An invocation to an `airside fn`, or through a subroutine pointer whose type carries the `airside` keyword, requires airside.

### 5.2.2 External declaration

#### Static semantics

A declaration prefixed with `extern` is an **external declaration**. The prefix has three effects upon the declaration:

— Preservation — where the declaration carries an external name, the implementation shall retain the item in an invocable or accessible form in the opaque code, accessible from outside the translation unit, whether or not it is referenced within the unit.

— Name stability — the external name is the declaration’s identifier, and the implementation shall apply no name transformation to it. How an external name is represented in the opaque code is implementation defined.

— Invocation interface — for subroutine declarations, the parenthesized identifier selects the invocation interface. `native` denotes the native invocation interface of the execution environment. Other identifier values are implementation defined. The implementation shall document the set of supported invocation interfaces for each execution environment.

A definition that carries neither `extern` nor `#symbol` has an implementation-defined name in the opaque code, and the implementation may eliminate the named item entirely where it determines that it is unreferenced.

#### Constraints

A parenthesized invocation interface identifier shall not appear on an `extern static` declaration. An identifier not among the invocation interfaces the implementation documents shall not appear.

#### Examples (informative)

```
pub extern fn init() { ... }
pub extern(native) fn init2() { ... } // equivalent to above
pub extern(efi) fn efi_entry(handle: uaddr, table: %ui1)
    -> uaddr { ... }

// extern without pub — kept in opaque code, private to the module
extern fn internal_hook() { ... }

#symbol "compress"
pub extern fn kurt_compress(src: &[ui1], dst: $[ui1])
    -> verdict.[uaddr, void] { ... }

// internal — implementation-defined name, may be eliminated
fn helper(x: si4) -> si4 { ... }

pub extern static version: ui4 = 1;
extern static mut hw_state: ui4 = 0; // preserved but private
```

### 5.2.3 Variadic subroutines

A variadic subroutine accepts a variable number of arguments after its fixed parameters. The variadic arguments are captured into a binding of a type satisfying `variadic`, as defined in the clause on protocols and implementations.

#### Static semantics

A subroutine declared with the `variadic` modifier uses the variadic variant of its invocation interface. The identifier names a `mut` binding whose type is the specified `with variadic` type.

#### Dynamic semantics

1. Entry — the implementation performs the argument capture that the variadic variant of the invocation interface requires, and initializes the binding’s object as the interface requires.
2. Exit — where the binding’s object is still initialized, the destructor the implementation supplies for the variadic type runs.

#### Constraints

The type named in the `variadic` modifier shall satisfy `variadic`.

#### Examples (informative)

```
// Forwarding subroutine
variadic(args: va_list) fn my_printf(fmt: %ui1) -> si4 {
    return my_vprintf(fmt, args);
}

// Iteration within airside
variadic(args: va_list) fn sum_ints(count: si4) -> si4 {
    let mut total: si4 = 0;
    let mut i: si4 = 0;

    while i < count {
        airside { total += args.next_int.[si4](); }
    } then { i += 1; }

    return total;
}

// Indirect invocation through a variadic subroutine pointer
let f: extern variadic fn(%ui1) -> si4 = my_printf;
f(fmt, width, name);
```

## 5.3 Binding declarations

A `let` declaration introduces one or more bindings within a scope. A binding associates a name with an object and determines whether the object may be assigned to after initialization.

### Syntax

```
let_decl = "let", ws, pattern, [ ws, ':', ws, type ],
           [ ws, '=', ws, expression ],
           [ ws, else_bind, ws, block ], ';' ;

else_bind = "else", [ ws, '.', ws, identifier ] ;
```

The pattern forms and their refutability are defined in the subclause on patterns and destructuring.

### Static semantics

The `mut` modifier on a pattern element determines the kind of the binding that element introduces, as defined in the subclause on per-binding assignment. A **single-assignment binding** permits its object to be assigned to at most once. A **multi-assignment binding** permits its object to be assigned to any number of times.

When an initializer is present, it constitutes the binding’s first assignment and the object is initialized at the point of declaration. When the initializer is omitted, the object lifetime of the binding’s object begins at the first assignment to it, as defined in the clause on semantics.

A binding’s object is **definitely initialized** at a programme point where every path of reachable programme points that reaches that point passes through the declaration of the binding and contains an assignment to the object after it. Reachable programme points are defined in the clause on semantics.

The storage of a binding a block declares is released at scope exit.

When the type annotation is omitted, the binding’s type is determined by the rules for type inference.

### Dynamic semantics

The storage of the binding’s object is reserved and released by the storage layout model defined in the clause on semantics.

### Constraints

The binding’s object shall be loaded, and a managed reference to it created, only at a programme point at which it is definitely initialized.

An assignment whose leading operand names a binding whose object has the automatic object lifetime shall follow the declaration of that binding in the token sequence. An assignment to a single-assignment binding shall appear only at a programme point at which the binding’s object is not definitely initialized.

A declaration that omits both the type annotation and the initializer shall not appear.

### Examples (informative)

```
let x: si4 = 42;     // single-assignment, initialized at declaration
let y = x + 1;       // single-assignment, type inferred
let mut counter = 0; // multi-assignment, initialized at declaration
counter += 1;        // OK — counter is mut

// Deferred initialization — single-assignment
let result: si4;
if condition {
    result = compute_a();
} else {
    result = compute_b();
}
print(result); // OK — every path to here assigns result
// result = 0; // translation failure — result is single-assignment

// Deferred initialization — multi-assignment
let mut buf: [ui1; 4096];
buf = [0; 4096];
airside { dma_fill(%buf, 4096); }
print(buf); // OK — buf was initialized by the assignment above

// Translation-time condition — the else path is unreachable
let val: si4;
if verdict.[void, void]::Pass(void) {
    val = 1;
}
print(val); // OK — no reachable path to here omits the assignment

// Diverging branch — the path through it reaches no point after the if
let z: si4;
if runtime_condition {
    z = compute();
} else {
    trap();
}
print(z); // OK — the only path of reachable points to here assigns z

// translation failure — a reachable path omits the assignment
// let x: si4;
// if runtime_condition {
//     x = 1;
// }
// print(x); // the else path reaches here and assigns nothing

// translation failure — one alternative assigns nothing
// let w: si4;
// match v {
//     a -> { w = init(); };
//     b -> {};
//     c -> { trap(); };
// }
// print(w); // the path through b reaches here and assigns nothing

// translation failure — managed reference to a binding
// that is not definitely initialized
// let a: si4;
// let r = &a;
```

### 5.3.1 The `else` clause on refutable patterns

A `let` declaration may use any pattern form defined in the subclause on patterns and destructuring. Whether a pattern is refutable is defined in the subclause on refutability.

#### Static semantics

When the `else` clause names a binding (`else.f`), the original value that failed to match is bound to `f` within the `else` block. The type of `f` is the type of the initializer expression — the complete, undestructured value.

#### Dynamic semantics

1. The initializer expression is evaluated.
2. The result is matched against the pattern.
3. If the pattern matches, all bound names are initialized and execution continues after the declaration.
4. If the pattern does not match, the `else` block executes. The `else` block is a control transfer or a diverging expression, and the enclosing scope exits.

#### Constraints

A `let` declaration shall include an `else` clause if and only if its pattern is refutable.

The `else` block shall be a control transfer or a diverging expression.

#### Examples (informative)

```
// Irrefutable patterns — else is FORBIDDEN
let .{ x, y } = get_point(); // OK
// translation failure — irrefutable
// let .{ x, y } = get_point() else { return; };

// Refutable patterns — else is MANDATORY
// OK — diverge
let verdict::Pass(x) = try_parse() else { return; };
// OK — diverge with binding
let verdict::Pass(x) = try_parse() else.fail {
    log(fail); return;
};

// translation failure — no else
// let verdict::Pass(x) = try_parse();
```

## 5.4 Translation-time constants

A `const` declaration introduces a named translation-time constant.

### Syntax

```
const_decl = [ "pub", ws ], "const", ws, ( identifier | '?' ), ws,
             [ ':', ws, type, ws ], '=', ws, expression, ';' ;
```

### Static semantics

The rule for an omitted type annotation is defined in the subclause on binding declarations. The initializer expression is evaluated at translation time, as defined in the clause on expressions. The resulting value is substituted at each use site.

A `const` declared as `?` introduces no name. Its initializer is evaluated as any other is. `pub` upon it has no effect.

### Constraints

The initializer establishes every field value. A store to a field after initialization shall not appear, regardless of the field’s modifiers.

### Examples (informative)

```
const max_size: uaddr = 1024;
const tau: fe11s52 = 6.283185307179586476925286766559;
// type inferred from the initializer
const limit = 1024~ui4;
// subroutine invoked at translation time
const crc_table: [ui4; 256] = make_lut();
```

## 5.5 Global bindings

A `static` declaration introduces a binding whose object has the permanent object lifetime, as defined in the clause on semantics. The initializer is evaluated at translation time. The object holds the resulting value when execution begins.

### Syntax

```
static_decl = [ "pub", ws ], [ "extern", ws ], "static", ws,
              [ "mut", ws ], ( identifier | '?' ), ws,
              [ ':', ws, type, ws ], '=', ws, expression, ';' ;
```

### Static semantics

The rule for an omitted type annotation is defined in the subclause on binding declarations.

A `static` declared as `?` introduces no name. Its storage is reserved as that of any other `static` is. A `#symbol` directive upon it gives the name by which the opaque code and symbol resolution identify it. `pub` upon it has no effect.

`static` without `mut` introduces a binding whose object may be loaded from any point in the programme. The binding is a single-assignment binding, and an object expression designating its object is storable at no programme point.

Where the type of a `static` binding contains `mut` fields — directly or transitively through fields held by value — those fields may be stored to, by the per-field store permission defined in the subclause on field modifiers. Such a store requires airside.

`static mut` introduces a binding whose object permits both loads and stores.

### Dynamic semantics

The implementation may arrange the initialized values in the opaque code in any order. The occupancy of referents in `static` initializers follows the rules defined in the clause on expressions. `with destruct` on a `static` binding’s type is permitted. No destructor executes for such a binding.

### Constraints

A load from or a store to a `static mut` binding, and the creation of a reference to its object or to a constituent object of that object, require airside.

### Examples (informative)

```
static config: app_config = default_config();
static mut counter: uaddr = 0;
// type inferred from the initializer
static limit = 4096~uaddr;

fn increment() {
    airside { counter += 1; } // airside required for static mut access
}

// External static — name is “version”, preserved unconditionally
pub extern static version: ui4 = 1;

// External static with identification specific
// to the execution environment
#symbol "global_state"
extern static mut global_state: app_state = default();

// Per-field store permission via mut field
struct atomic_counter {
    mut value: ui4  // mut field: airside stores always permitted
}

static shared_counter: atomic_counter = atomic_counter.{ .value = 0 };
// shared_counter is `static` (not `static mut`), but the `mut` field
// permits airside stores through &shared_counter.
```

## 5.6 Composite types

A **composite type** is a type composed of zero or more constituent fields.

A **variant type** is a composite type whose value holds one of a set of named variants, and carries a discriminant that records which. An `enum` declaration introduces a variant type, and so does a `contract` declaration, as defined in the clause on statements and control flow.

### Syntax

```
composite_form   = '{', ws, ( anon_field_list | named_field_list ), ws,
                   '}' ;

anon_field_list  = anon_field, ws, { ',', ws, anon_field, ws },
                   [ ',', ws ] ;
anon_field       = field_modifiers, type, [ ws, '=', ws, expression ] ;

named_field_list = named_field, ws, { ',', ws, named_field, ws },
                   [ ',', ws ] ;
named_field      = field_modifiers, identifier, ws, ':', ws, type,
                   [ ws, '=', ws, expression ]
                 | '?', ws, ':', ws, type ;

field_modifiers  = { field_modifier, ws } ;
field_modifier   = "pub" | "airside" | "mut" ;
```

### Static semantics

A struct type, and each variant of a variant type, takes one of three forms:

— **Unit form** — the type has no fields. Its size is zero. It contains exactly one value.

— **Unnamed-field form** — the type has one or more fields identified by position in declaration order.

— **Named-field form** — the type has one or more fields identified by name. Field access uses the dot operator followed by the field identifier.

A declaration or variant that omits the composite form is in unit form. One whose composite form matches `anon_field_list` is in unnamed-field form, and one whose composite form matches `named_field_list` is in named-field form.

### Constraints

Access to a `?` field shall not appear. A composite literal shall not name a `?` field. A destructuring pattern shall not bind a `?` field.

A field name shall be unique within a named-field composite type. `?` fields are exempt from uniqueness.

A composite literal that constructs a composite type with an `airside` field requires airside.

A non-`pub` field shall be named in a composite literal only within the namespace that declares the composite type.

### 5.6.1 Field modifiers

#### Static semantics

Three field modifiers exist: `pub`, `airside`, `mut`. They may be written in any order upon a field, and their effects hold together:

— `pub` makes the field visible outside the namespace that declares the containing type.

— `airside` requires airside of every load from and every store to the field, and of the creation of a reference to the field or to a constituent object of it.

— `mut` gives the field **per-field store permission**. The field may be stored to through a reference or a binding that itself permits no store. Such a store requires airside, and so does the creation of a store-permitting reference to the field or to a constituent object of it, in every modifier form.

Apart from what these modifiers give, whether a field is storable follows from the enclosing binding, as the clause on expressions defines field access.

The `mut` modifier has no effect upon a field of a `const` declaration’s value.

#### Constraints

A field declaration that repeats a modifier shall not appear.

### 5.6.2 `?` fields

#### Static semantics

A **`?` field** declares padding cells within a named-field composite type.

### 5.6.3 Default-value expressions

#### Static semantics

A field may carry a default-value expression of the form `= expr`. Where a composite literal omits the field, the field holds the value the expression yields.

## 5.7 Struct declarations

A struct declaration introduces a named composite type whose value is the product of its constituent fields. Each field occupies a distinct, typed storage region within the struct’s representation.

### Syntax

```
struct_decl = [ "pub", ws ], "struct", ws, identifier,
              [ ws, generic_clause ],
              ( [ ws, with_single ], ';'
              | ws, with_curly
              | ws, composite_form,
                [ ws, with_single, ';' | ws, with_curly ] ) ;
```

### Examples (informative)

```
// Unit form
struct empty_t;
let v = empty_t;

struct point { x: si4, y: si4 }

struct origin_point {
    x: si4 = 0,
    y: si4 = 0
}

struct example {
    // private, landside, the binding kind governs stores
    a: si4,
    // public,  landside
    pub b: si4,
    // private, landside, airside stores always permitted
    mut c: si4,
    // public,  landside, airside stores
    pub mut d: si4,
    // private, airside-only access
    airside e: si4,
    // public,  airside-only
    pub airside f: si4,
    // private, airside-only, airside stores
    airside mut g: si4,
    // public,  airside-only, airside stores
    pub airside mut h: si4
}

struct network_header {
    version: ui1,
    ?: ui1,
    length: ui2,
    ?: [ui1; 4],
    payload_offset: ui4
}

struct file_handle {
    fd: si4
} with destruct {
    close(self.fd); // self: $file_handle
};

struct packet {
    header: ui4,
    seq: ui4,
    payload: &[ui1]
} with {
    repr(pack(1)),
    align(4)
}
```

### Notes (informative)

Representation and alignment rules are defined in the clause on types. A struct may declare `with destruct` to supply a destructor. The destruction model is defined in the clause on references and resource management.

## 5.8 Enum declarations

An enum declaration introduces a named type with a fixed set of variants. Each variant may carry a payload.

### Syntax

```
enum_decl = [ "pub", ws ], "enum", ws, identifier,
            [ ws, generic_clause ], ws, '{', ws,
            [ variant_list ], ws, '}',
            [ ws, with_single, ';' | ws, with_curly ] ;

variant_list  = variant, ws, { ',', ws, variant, ws }, [ ',', ws ] ;
variant       = identifier, [ ws, composite_form ],
                [ ws, '=', ws, variant_value ] ;

variant_value = [ '-', ws ], integer_literal
              | "wild", [ ws, '(', ws, [ '-', ws ], integer_literal, ws,
                          ')' ] ;
```

Each variant is a composite type in one of the three forms:

— **Unit variant** — no composite form. The variant carries only its discriminant. Constructed by name alone.

— **Unnamed-field variant** — a composite form matching `anon_field_list`. Fields are accessed by their index in declaration order. Constructed with curly brackets.

— **Named-field variant** — a composite form matching `named_field_list`. Fields are accessed by name. Constructed with a literal enclosed by curly brackets.

### Static semantics

The implementation distinguishes unnamed-field variants from named-field variants by the form of the first field declaration within the composite form. If the first non-modifier token sequence matches `identifier ':'` or begins with `?`, the variant uses `named_field_list`. Otherwise, the first non-modifier token sequence is a type expression, and the variant uses `anon_field_list`.

`wild` declares that the designated variant covers all discriminant values not matched by any other variant, whether or not it declares a canonical value.

`wild(V)` declares a **canonical value** for the wild variant, where `V` is an integer literal, or `-` followed by one. When a value of the wild variant is created explicitly, the implementation shall store `V` as the discriminant. (e.g. `verdict::Fail(payload)` stores `V` as the discriminant.) The canonical value also governs discriminant extraction via `as`, as defined in the clause on expressions.

Where `wild` is written without a canonical value, the wild variant may still be constructed explicitly, and the construction stores as the discriminant the value the automatic discriminant assignment algorithm assigns that variant.

Matching a `wild` variant extracts as follows.

— Where a `wild` variant has no payload, matching it extracts nothing.

— Where a `wild` variant has a payload, the discriminant value is a wildcard, and the payload is extracted as the payload of any other variant is. (e.g. `Fail(F) = wild(0)` in `verdict`.)

The rules of this subclause govern every variant type.

A variant type that declares no `wild` variant has an **implicit wild**. The implicit wild has no payload and is assigned no discriminant value of its own. It covers all discriminant values of the type’s discriminant type that no declared variant matches. Where the discriminant type matches every such value to a declared variant, the implicit wild covers none.

A value of a variant type that declares no `wild` variant may be constructed by the expression `TypeName::wild`, as defined in the subclause on wild construction in the clause on expressions.

When a variant is declared without an explicit discriminant value, the implementation assigns a discriminant automatically using the following algorithm:

1. Collect the **occupied set** *S*, the union of all explicitly specified discriminant values and all `wild(V)` canonical values the type declares.
2. Initialize a **candidate counter** *d* to zero.
3. Traverse the variants in declaration order. A `wild` variant without a canonical value counts as lacking an explicit discriminant value. For each variant that lacks one, advance *d* to the smallest value ≥ *d* that is not in *S*, assign *d* as the variant’s discriminant value, add *d* to *S*, and set *d* to *d* + 1.

### Constraints

A type shall have at most one `wild` variant.

Each explicitly specified discriminant value within a variant type, counting each `wild(V)` canonical value among them, shall be distinct from every other.

A variant type for which the automatic discriminant assignment algorithm, defined above, finds no representable candidate value shall not appear.

### Examples (informative)

```
// Unit variants only
enum colour { red, green, blue }

// Unnamed-field variant — single positional field
enum packet { data { &[ui1] }, ack, error = wild }

// Unnamed-field variant — multiple positional fields
enum shape {
    circle { fe11s52 },                 // radius: .0
    rect { fe11s52, fe11s52 },          // width: .0, height: .1
    triangle { fe8s23, fe8s23, fe8s23 } // sides: .0, .1, .2
}

// Named-field variant
enum event {
    key_press { key: ui4, modifiers: ui1 },
    mouse_move { x: si2, y: si2 },
    quit
}

// Mixed
enum message {
    ping,
    data { ui1, [ui1; 32] },          // positional: kind + payload
    error { code: ui4, msg: &[ui1] }, // named fields
    unknown = wild
}

// Accessing unnamed-field variant fields
let s: shape = shape::rect.{ 3.0, 4.0 };
match s {
    let shape::rect.{ w, h }        -> area(w, h);
    let shape::circle.{ r }         -> area_circle(r);
    let shape::triangle.{ a, b, c } -> area_triangle(a, b, c);
    wild                            -> 0.0;
}

// Accessing named-field variant fields
let e: event = event::key_press.{ .key = 65~ui4, .modifiers = 0~ui1 };
match e {
    let event::key_press.{ .key, .modifiers } -> handle_key(key, modifiers);
    let event::mouse_move.{ .x, .y }          -> handle_mouse(x, y);
    event::quit                              -> quit();
    wild                                     -> ignore();
}
```

### Notes (informative)

How enums interact with `match` exhaustiveness is defined in the clause on statements and control flow. The layout of a variant type and automatic discriminant sizing are defined in the clause on types. The syntactic forms for constructing values of an enum type are defined in the clause on expressions.

A variant type may declare `with destruct` to supply a destructor. When a value of one is destroyed, the destructor of the active variant’s payload executes. The full destruction model is defined in the clause on references and resource management.

## 5.9 Type aliases

A type alias introduces a new name for an existing type.

### Syntax

```
type_alias_decl = [ "pub", ws ], "type", ws, identifier,
                  [ ws, generic_clause ], ws, '=', ws, type, ';' ;
```

### Static semantics

At every use site, a type alias is replaced unconditionally by its underlying type.

An `impl` block whose target is a type alias resolves against the underlying type. The duplicate-implementation rule defined in the clause on protocols and implementations applies to the resolved targets.

A generic alias `type A.[T, ...] = Expr` is expanded at each use site. The supplied type arguments are substituted for the declared parameters, and the resulting type then replaces the alias name. The expansion follows the same substitution rule as a non-generic alias.

### Constraints

A type alias that is directly or mutually recursive shall not appear. A generic alias that declares a generic parameter not appearing in the aliased type shall not appear.

### Examples (informative)

```
type byte        = ui1;
type index       = uaddr;
type pair.[A, B] = .{A, B};
type matrix.[T]  = [[T; 4]; 4];

pub type seconds = ui4;

// No conversion at any use site
let b: byte = 42~ui1;
let _: ui1  = b;
fn takes_ui1(x: ui1) {}
takes_ui1(b);

// Protocol bounds resolve on the underlying type
fn show.[T: fmt](x: T) { ... }
show(b); // OK — ui1 implements fmt

// Generic argument identity
let p1: pair.[byte, si4] = .{ 1~ui1, 2 };
let p2: pair.[ui1,  si4] = p1; // same type

// A struct declaration introduces a distinct type
struct seconds2 { val: ui4 }
```

## 5.10 Generic declarations

A generic declaration introduces a type or subroutine parameterized over one or more generic parameters — type parameters or dependence parameters. At each site that supplies arguments, the parameters are resolved to the arguments supplied.

### Syntax

```
generic_clause   = '.', ws, '[', ws, generic_item, ws,
                   { ',', ws, generic_item, ws }, [ ',', ws ], ']' ;
generic_item     = type_param | dependence_param ;
type_param       = identifier, [ ws, ':', ws, bound ] ;
dependence_param = "const", ws, identifier, ws, ':', ws, type ;
bound            = bound_elem, ws, { '+', ws, bound_elem, ws } ;
bound_elem       = builtin_bound | single_path ;

generic_args     = '.', ws, '[', ws, generic_arg, ws,
                   { ',', ws, generic_arg, ws }, [ ',', ws ], ']' ;
generic_arg      = type | expression ;
```

Generic subroutines use the same `generic_clause` syntax, placed between the subroutine name and the parameter list.

A **generic argument list** follows the name of the generic type or subroutine it instantiates. Its arguments correspond in order to the declared generic parameters. A type argument resolves a type parameter, and a dependence argument resolves a dependence parameter.

### Static semantics

Generic parameters are in scope for the entire declaration: the field list (for structs), the variant list (for enums), the parameter list and return type (for subroutines), and the `with` clause. An `impl` block that names the type introduces its own generic parameters, as defined in the clause on protocols and implementations.

A type in which a generic parameter remains unresolved is an **abstract type**. A type in which no generic parameter remains unresolved is a **concrete type**. **Instantiation** is the derivation of a concrete type from an abstract type by resolving each of its generic parameters to an argument.

A **type parameter** is a distinct abstract type at the declaration site. An **unconstrained parameter** is a type parameter whose bound has no element.

A **dependence parameter** declares a value upon which the types within the declaration may depend. The value supplied for it is a **dependence argument**. A dependence parameter may appear wherever a value expression of the same type may appear: in array lengths, and in the types and expressions of subsequent parameters and fields. Within the declaration that declares it, the value of a dependence parameter is determined at translation time where an argument resolves that dependence parameter for the construct whose analysis requires the value.

Two instantiations of the same generic declaration are the same type if and only if all type arguments are the same types and all dependence arguments are the same value.

An array type `[T; N]` is an instantiation of a built-in generic declaration whose generic parameters are a type parameter for `T` and a dependence parameter of type `uaddr` for `N`, in that order. A tuple type is an instantiation of a built-in generic declaration with one type parameter per field, in field order. A slice reference is an instantiation of a built-in generic declaration of its tribe and modifiers with one type parameter for its element type, and every other reference type is an instantiation of another built-in generic declaration of its tribe and modifiers with one type parameter for its referent type. A subroutine pointer type that carries no `generic_clause` is an instantiation of a built-in generic declaration particular to that type, with one type parameter per parameter type, in order, followed by one for its return type where that is not `!`. `verdict.[T, F]` is an instantiation of a built-in generic declaration with a type parameter for `T` and one for `F`, in that order. A protocol object type `dyn Protocol` is an instantiation of a built-in generic declaration particular to `Protocol`, with the generic parameters of `Protocol`.

A type argument that involves a generic parameter satisfies a declared protocol only where an implementation of that protocol for it is witnessed, as the clause on protocols and implementations defines witnessed implementations.

### Constraints

The number of arguments supplied shall equal the number of parameters in the declaration. Every value a dependence argument requires, other than the value of a dependence parameter, shall be determined at translation time.

The path of a bound element shall name a protocol. Each type argument shall satisfy every bound element declared upon the parameter it resolves.

A parameter identifier shall be unique within its parameter list. An inner parameter that hides an outer parameter of the same name shall not appear. A subroutine-level generic parameter hides any module-level type declaration of the same identifier.

An unconstrained parameter shall not be subjected to arithmetic, field access, or any operation requiring protocol or built-in bounds.

An abstract type shall appear only within the declaration that declares the generic parameter it leaves unresolved.

The type of a dependence parameter shall be a concrete type, shall be copyable, and shall neither be a reference type nor contain one as a constituent.

An operation between two instantiations whose dependence arguments differ shall not appear. Such a violation, where not detected during translation, can cause indeterminate state.

### Examples (informative)

```
struct pair.[A, B] {
    first:  A,
    second: B
}

contract option.[T] {
    some(T),
    none(void) = wild
};

struct arc.[T] {
    ptr: %T,
    mut ref_count: &atomic mut ui4
}

// Instantiation
let p: pair.[si4, verdict.[void, void]] =
    pair.{ .first = 42, .second = verdict::Pass(void) };
let x: option.[si4] = option::some(7);

// Explicit generic arguments — required when type cannot be inferred
fn default_value.[T: defaulted]() -> T {
    return (T as defaulted)::default();
}

let val = default_value.[si4]();

// Inline bound
fn max.[T: primitive](a: T, b: T) -> T {
    return if a > b then a else b;
}

// Dependence parameters
struct matrix.[T, const rows: uaddr, const cols: uaddr] {
    data: [T; rows * cols]
}

let m: matrix.[fe11s52, 3, 4] = ...;

fn zeros.[T: numeric, const N: uaddr]() -> [T; N] {
    return [0; N];
}
```

### 5.10.1 Generic dispatch

#### Static semantics

The type parameters of a generic subroutine are abstract within its body. The subroutine accesses type-specific properties through a bound descriptor passed to it at each invocation site, or through the generic argument vector of a type descriptor passed to it. The bound descriptor is obtained via `T'bound(X)`, as defined in the clause on expressions. A conforming implementation shall behave as though every generic subroutine receives and operates through a bound descriptor. It may generate a specialized copy for particular concrete type arguments within the same translation unit, provided every σ operation is preserved in the same order, each producing the same signal.

The invoker supplies a type descriptor for each type argument. Where the type argument is concrete, it supplies the descriptor `T'bound(type)` yields. Where the type argument is a type parameter of the invoker, it supplies the descriptor it received for that parameter. Where the type argument otherwise involves a generic parameter, the invoker **assembles** a type descriptor whose object lifetime ends when the invocation returns: its size and alignment follow from the layout rules applied to its arguments, and its field 2 designates the same subroutine for every instantiation of the generic declaration the type instantiates. An assembled type descriptor is supplied only for a type parameter whose bound names no declared protocol. For every other type parameter, and for the subject of every subject bound, the invoker supplies the type descriptor that accompanies the protocol descriptor it supplies with it.

A dependence argument is passed as a value of its type.

The type argument of each type parameter is determined from the subroutine’s arguments at the invocation site. Where a type argument is an inferred type `?`, the implementation resolves the corresponding type parameter by inference from the surrounding context. Where a type parameter appears solely in the return type, or where argument types yield contradictory constraints, the type argument shall be supplied explicitly. A dependence argument shall be supplied explicitly.

#### Constraints

The mapping from argument types to type parameters shall be exact and unambiguous.

### 5.10.2 Signature lowering

The signature of a generic subroutine is lowered to the execution environment’s invocation interface. The lowered signature is divided into three zones, always in the following order.

— **Zone 1** — the out-parameter. The first parameter is `%mut void`, pointing to storage the invoker reserves for the return value. The invoker determines the storage region by applying the layout rules of the clause on types to the source-level return type, taking the size and the alignment of each type parameter within it from that parameter’s type descriptor. A source-level return type of `void` has size zero, and the storage occupies zero cells.

— **Zone 2** — the source parameters. The source-level parameters follow, in declaration order. A parameter whose type involves a generic parameter is lowered to `%void`, and the argument is passed as an unmanaged reference to storage holding the source-level value. A parameter whose type involves none passes through unchanged.

— **Zone 3** — the descriptors and dependence parameters, in four levels, always in the following order: `selftype`, where it is a type parameter of the signature as the clause on protocols and implementations defines; the generic parameters of the subroutine itself; the subject bounds of its `with` clause; and the generic parameters of the enclosing declaration. The enclosing declaration is the `protocol` declaration for a subroutine that a protocol body declares or that a protocol implementation provides, and the `impl(...)` parameter list for a subroutine that an inherent implementation provides. Within each level, parameters and subject bounds appear in declaration order. For each type parameter, the `type` descriptor reference is emitted as `%void`, followed by one `%void` for each bound element of its bound, in the order of its bound. For each subject bound, the `type` descriptor reference of its subject is emitted as `%void`, followed by the descriptor reference of its protocol as `%void`. The descriptor each element designates is defined in the subclause on bound descriptor emission. An element that carries no fields designates an object of size zero. For each dependence parameter, one parameter of its type is emitted.

The return type of the lowered signature is `void`. The result is delivered through the zone 1 out-parameter.

The lowered signature is a single symbol composed of concrete types and `%void`s. The resulting symbol is invocable across `#dyn` boundaries without source.

#### Examples (informative)

```
extern fn sort.[T: ord](arr: $[T]) { ... }
// lowers to:
// fn sort(
//     out:    %mut void,   // zone 1
//     arr:    %void,       // zone 2
//     T_type: %void,       // zone 3: T'bound(type)
//     T_ord:  %void        // zone 3: T'bound(ord)
// ) -> void

extern fn add.[T: numeric](a: T, b: T) -> T { ... }
// lowers to:
// fn add(
//     out:       %mut void, // zone 1
//     a:         %void,     // zone 2
//     b:         %void,     // zone 2
//     T_type:    %void,     // zone 3: T'bound(type)
//     T_numeric: %void      // zone 3: T'bound(numeric)
// ) -> void

extern fn process.[T: ord + clone](x: &T) { ... }
// lowers to:
// fn process(
//     out:     %mut void,   // zone 1
//     x:       %void,       // zone 2
//     T_type:  %void,       // zone 3: T'bound(type)
//     T_ord:   %void,       // zone 3: T'bound(ord)
//     T_clone: %void        // zone 3: T'bound(clone)
// ) -> void

extern fn merge.[
    T: ord, U: clone
](arr: $[T], default: U, count: si4) { ... }
// lowers to:
// fn merge(
//     out:     %mut void,   // zone 1
//     arr:     %void,       // zone 2
//     default: %void,       // zone 2
//     count:   si4,         // zone 2: concrete
//     T_type:  %void,       // zone 3: T'bound(type)
//     T_ord:   %void,       // zone 3: T'bound(ord)
//     U_type:  %void,       // zone 3: U'bound(type)
//     U_clone: %void        // zone 3: U'bound(clone)
// ) -> void

extern fn fill.[
    T: numeric, const N: uaddr
](buf: $[T; N]) { ... }
// lowers to:
// fn fill(
//     out:       %mut void, // zone 1
//     buf:       %void,     // zone 2
//     T_type:    %void,     // zone 3: T'bound(type)
//     T_numeric: %void,     // zone 3: T'bound(numeric)
//     N:         uaddr,     // zone 3: dependence
// ) -> void

extern fn identity.[T](x: T) -> T { return x; }
// lowers to:
// fn identity(
//     out:    %mut void,   // zone 1
//     x:      %void,       // zone 2
//     T_type: %void,       // zone 3: T'bound(type)
// ) -> void
```

Usage through `#dyn`:

```
#dyn libsort {
    fn sort(out: %mut void, arr: %void,
        t_type: %void, t_ord: %void);
}

pub fn sort.[T: ord](arr: $[T]) {
    airside {
        let mut dummy: void = void;
        let t_type = contract T'bound(type) else trap();
        let t_ord  = contract T'bound(ord)  else trap();

        libsort::sort(%mut dummy, %arr as! %void, t_type, t_ord);
    }
}

// At the invocation:
sort.[si4](my_array);
```

### 5.10.3 `#dyn` boundary constraint

#### Constraints

A generic subroutine without `extern` shall not be exposed across `#dyn` boundaries. A `#dyn` block shall not declare a subroutine with unresolved generic parameters.

## 5.11 Patterns and destructuring

A pattern decomposes a value into its parts. Patterns appear in `let` declarations, `match` alternatives, and `if let` and `while let` conditions.

### Syntax

```
pattern        = [ "let", ws ], pattern_body ;
pattern_body   = literal_pat | ident_pat | ignore_pat | wild_pat
               | variant_pat | contract_pat | struct_pat | anon_pat
               | slice_pat | string_pat | range_pat
               | binding_pat | or_pat ;

literal_pat    = integer_literal | float_literal ;
ident_pat      = [ "mut", ws ], identifier ;
ignore_pat     = '?' ;
wild_pat       = "wild", [ ws, '(', ws, identifier, ws, ')' ] ;
variant_pat    = single_path, ws, '.', ws, '{', ws,
                 [ field_pat_list | unnamed_pat_list ], ws,
                 '}' | single_path ;
contract_pat   = single_path, ws, '(', ws, pattern, ws, ')' ;
struct_pat     = single_path, ws, '.', ws, '{', ws,
                 ( field_pat_list | unnamed_pat_list ), ws, '}' ;
anon_pat       = '.', ws, '{', ws, unnamed_pat_list, ws, '}' ;

field_pat_list = field_pat, ws, { ',', ws, field_pat, ws }, [ ',', ws ],
                 [ ws, '...' ] ;
field_pat      = [ "let", ws ], [ "mut", ws ], [ identifier, ws, '=', ws ],
                 '.', ws, identifier,
                 [ ws, '@', ws, pattern ] ;

unnamed_pat_list = unnamed_pat, ws,
                   { ',', ws, unnamed_pat, ws }, [ ',', ws ] ;
unnamed_pat      = ident_pat, [ ws, '@', ws, pattern ] ;

slice_pat      = '[', ws,
                 [ element_pat, ws, { ',', ws, element_pat, ws },
                   [ ',', ws ] ], ']' ;
element_pat    = pattern | '...' ;
string_pat     = string_literal | raw_string_literal ;
range_pat      = literal_pat, ws, ( '..' | '..=' ), ws, literal_pat ;
binding_pat    = ident_pat, ws, '@', ws, pattern ;
or_pat         = pattern, ws, '|', ws, pattern ;
```

### 5.11.1 Pattern forms

#### Static semantics

— **Literal pattern** — matches a value `v` where `v == literal` holds.

— **Identifier pattern** — an identifier, optionally preceded by `mut`, binds the matched value to a name at its original type. `mut` makes the binding a multi-assignment binding, as defined in the subclause on per-binding assignment. An identifier binds only where a `let` governs it, as this subclause defines below. An identifier that no `let` governs is a variant pattern.

— **Ignore pattern** — matches every value of the matched type and introduces no binding.

— **`wild` pattern** — matches a value that no declared variant of the matched type covers, and yields a reference to the cells of the matched object (`&[ui1]`). The bare form `wild` discards it. The form `wild(`*name*`)` binds it to *name*.

— **Variant pattern** — matches an enum variant. A unit variant is written as the path alone; a variant with payload is written with `.` and curly brackets.

— **Contract variant pattern** — matches a variant of a contract type, as defined in the clause on statements and control flow, and decomposes its payload by the enclosed pattern.

— **Struct pattern** — decomposes a struct value into its fields, written with `.` and curly brackets after the type name. The type name is mandatory. `...` at the end ignores remaining named fields. It is permitted only for named-field structs, not unnamed-field structs.

— **Anonymous struct pattern** (`.{ }`) — decomposes a tuple value into positional fields.

— **Slice pattern** — matches a slice or array by element-wise comparison. The rules governing it are defined in the clause on statements and control flow.

— **String literal pattern** — syntactic shorthand for a fixed-length slice pattern whose elements are the `ui1` values of the string literal, as defined by the mapping in the clause on lexical structure. A raw string literal pattern follows the same rules. The implementation expands the pattern into its Γ sequence during translation. (e.g. `"abc"` as a pattern is identical to `[0x61, 0x62, 0x63]`.)

— **Range pattern** — `a..=b` matches a value `v` where `a <= v` and `v <= b` hold, and `a..b` matches one where `a <= v` and `v < b` hold.

— **Binding pattern** (`@`) — `name @ sub_pattern` binds the matched value to `name` while testing against `sub_pattern`.

— **Or-pattern** — `p | q` matches if either alternative matches.

A `let` **governs** the pattern it precedes and every pattern within it. An identifier a `let` governs binds, whether or not the identifier names a declaration in scope. A `let` stands before a whole pattern, and before a single element of one. The `let` of a `let` declaration, of an `if let` condition, and of a `while let` condition governs the pattern that follows it.

#### Dynamic semantics

Matching loads a part of the matched value only where the pattern compares that part, or where that part is a reference through which the pattern reaches another part. The elements of a slice reference are reached through its `.ptr` field. A **part** is the matched object itself, a discriminant, a field, an element, or a payload, whether held by value or reached through a reference. A part reached through a reference is reached through the value of that reference that the load of the part holding it yielded. A pattern compares its parts in leading-to-following order and stops at the first comparison that fails, except that the failure of an alternative of an or-pattern moves on to its next alternative. Within one evaluation of a `match` expression or a `let` declaration, or of the condition of an `if let` or a `while let`, the first comparison of a part, or the first reach of another part through it, loads it, and every later comparison of that part or reach through it, in the same alternative or a later one, uses the value that load yielded.

#### Constraints

The alternatives of an or-pattern shall bind the same names with the same types and the same binding kind.

A `wild` pattern that matches no value shall not appear.

A string literal pattern shall appear only when the matched type is a slice reference, a reference to an array, or an array type, whose element type is `ui1`.

### 5.11.2 Struct destructuring

#### Static semantics

A struct pattern decomposes a value of a struct type or an enum variant with a struct payload. The type name, or the variant path, is mandatory.

In a **named-field destructuring**, a `field_pat` designates a field by `.field_name`. The form `.field_name` binds the field value to `field_name`. The form `binding_name = .field_name` binds it to `binding_name`. A following `@ sub_pattern` applies the sub-pattern to the field value.

`...` at the end of the field list causes fields not mentioned in the pattern to be ignored.

An **unnamed-field destructuring**, which applies to anonymous structs, unnamed-field structs, and unnamed-field variants, uses `unnamed_pat_list`. Fields are matched by position in declaration order. Each `unnamed_pat` introduces a binding or a sub-pattern for the field at its position.

#### Constraints

Every field of a named-field destructuring, other than a `?` field, shall be mentioned unless the pattern ends with `...`.

The bindings of an unnamed-field destructuring shall equal the fields of the type declaration in number and in order.

A destructuring pattern shall not be applied to a value of a type that declares `with destruct`, nor to a value of reference type. A destructuring pattern is one of: a struct pattern, an anonymous struct pattern (`.{ ... }`), or a variant pattern that destructures a payload.

#### Examples (informative)

```
// Named-field struct
struct point { x: si4, y: si4 }
let point.{ .x, .y } = get_point();  // all fields
let point.{ .x, ... } = get_point(); // y ignored
let point.{ origin = .x @ 0, .y } = get_point() else {
    return; // x bound to origin, constrained to 0
};

// Enum with named-field variant
enum event {
    key_press { key: ui4, modifiers: ui1 },
    quit
}

match e {
    let event::key_press.{ .key, ... } -> handle(key); // modifiers ignored
    event::quit                       -> quit();
    wild                              -> ignore();
}

// Anonymous struct (tuple) destructuring
let .{ a, b } = get_pair();      // all fields, positional order
// let .{ a, ... } = get_pair();
// translation failure — ... not permitted

// Enum with unnamed-field variant
match result {
    let verdict::Pass(val) -> accept(val);
    let verdict::Fail(err) -> handle(err);
}
```

### 5.11.3 Per-binding assignment

#### Static semantics

A pattern binding designates the matched component within the matched value. Where the binding carries `mut`, an assignment through it stores to that component.

A pattern introduces one binding for each identifier pattern and each field pattern it contains. A binding whose pattern element carries the `mut` modifier is a multi-assignment binding; a binding whose pattern element carries no `mut` modifier is a single-assignment binding. The kind of one binding is independent of the kind of every other binding the same pattern introduces.

#### Examples (informative)

```
let struct_t.{ .a, mut .b, .c } = get_structure();
// a and c are single-assignment, b is multi-assignment
b += 1; // OK — b is mut
// a += 1; — translation failure: a is single-assignment

let .{ x, mut y, z } = get_triple();
y += 1; // OK — y is mut

// Per-binding mut with refutable patterns
let verdict::Pass(.{ a, mut b }) = try_get_pair() else { return; };
b += 1; // OK — b is mut

// Every binding of a pattern carries its own mut
let verdict::Pass(.{ mut a, mut b }) = try_get_pair() else { return; };
a += 1; // OK
b += 1; // OK
```

### 5.11.4 Refutability

#### Static semantics

A pattern is **irrefutable** if it matches every possible value of the matched type. A pattern is **refutable** if there exists at least one value of the matched type that the pattern does not match.

The following patterns are irrefutable for any type:

— An identifier pattern, with or without `mut`.

— An ignore pattern.

The following patterns are irrefutable when their sub-components are irrefutable:

— An anonymous struct pattern in which every sub-pattern is irrefutable.

— A binding pattern `name @ sub` where `sub` is irrefutable.

— An or-pattern `p | q` where at least one of `p` or `q` is irrefutable.

The following patterns are always refutable:

— Literal patterns.

— Range patterns.

— String literal patterns.

— Contract variant patterns.

A struct pattern and a variant pattern are irrefutable where each of their sub-patterns is irrefutable and, where the path names a variant, that variant covers every value of the matched type, and refutable otherwise. A trailing `...` in a struct pattern does not affect its refutability.

A `wild` pattern is irrefutable where the matched type declares no variant, and refutable otherwise.

A slice pattern is irrefutable where each of its element patterns is irrefutable and the pattern matches every length a value of the matched type can have, and refutable otherwise. Where the matched type is a slice reference, an array type whose length involves a dependence parameter, or a reference to such an array, only a pattern that matches every length is irrefutable. A rest pattern is irrefutable. Which lengths a slice pattern matches is defined in the subclause on slice and string literal patterns.

## 5.12 `with` clauses

A `with` clause attaches behavioural properties to a declaration or to a subroutine pointer type. It appears after the core syntax of the declaration or type, and before the body where one is present.

### Syntax

```
with_single  = "with", ws, with_item ;
with_curly   = "with", ws, '{', ws, with_item, ws,
               { ',', ws, with_item, ws }, [ ',', ws ], '}' ;
with_item    = destruct_clause | inv_clause | repr_clause
             | discrim_clause | align_clause | "variadic"
             | subject_bound ;
```

### Static semantics

A `with` clause takes one of two forms:

— **Single-item form** (`with_single`) — `with word` or `with word(...)` or `with word { ... }`, attaching exactly one property. The form itself does not include a terminating semicolon. The grammar of the enclosing declaration or type determines whether a semicolon or body block follows.

— **Curly bracket form** (`with_curly`) — `with { k1, k2, ... }`, attaching one or more properties in a single clause. A trailing comma is permitted. The closing curly bracket terminates the clause.

`with` clauses are part of the declaration or type in which they appear and are evaluated at translation time. Each word is defined in the clause where it is introduced:

— `destruct` — attaches a destructor block (clause on references and resource management).

— `inv` — declares the inverted pair of a contract type (clause on statements and control flow).

— `repr` — controls representation (clause on types).

— `discrim` — sets the discriminant type of an enum (clause on types).

— `align` — sets minimum alignment (clause on types).

— `variadic` — declares a variadic state type (clause on types).

— `impl` — requires that a type implement a protocol (clause on protocols and implementations).

### Constraints

A declaration shall carry at most one `with` clause, using `with_curly` where it attaches more than one property. Within a clause enclosed by curly brackets, each word other than `impl` shall appear at most once. A `with` word shall appear only on the declaration kinds and type kinds for which it is defined.

### Examples (informative)

```
// with_single form
struct handle { fd: si4 } with destruct { close(self.fd); };

// with_curly form
struct packet {
    header: ui4,
    payload: &[ui1]
} with {
    repr(pack(1)),
    align(4)
}

// contract type with inverted pair
contract result.[T, F] {
    Pass(T) = 1,
    Fail(F) = wild(0)
} with {
    inv -> selftype.[F, T],
    discrim(ui1)
}
```

## 5.13 Visibility and name introduction

### 5.13.1 Visibility modifier

#### Static semantics

A declaration marked `pub` is visible outside the namespace that declares it. A declaration without `pub` is visible within that namespace alone. Namespaces, and the visibility a path requires at each of its segments, are defined in the clause on programme structure and translation. The declaration forms that permit `pub` state it in their own syntax.

### 5.13.2 Unqualified name introduction

#### Syntax

```
use_decl = [ "pub", ws ], "use", ws, use_tree, ws, ';' ;
use_tree = single_path, [ ws, "as", ws, identifier ]
         | single_path, ws, '::', ws, '*'
         | single_path, ws, '::', ws, '{', ws, use_tree, ws,
           { ',', ws, use_tree, ws }, [ ',', ws ], '}' ;
```

#### Static semantics

Each `use_tree` selects one or more named items and introduces names for them into the enclosing scope. Resolution of an introduced name yields the selected item. The introduced name is visible as the clause on semantics defines visibility.

A `use_tree` consisting of a `single_path` selects the item denoted by the path. Its introduced name is the final identifier of the path. When an `as` clause is present, the identifier of the clause is its introduced name.

In a `use_tree` enclosed by curly brackets, the path preceding `::{` is prepended to the path of each `use_tree` within. This rule applies recursively to each `use_tree` nested within another.

A `use_tree` ending in `::*` selects the accessible direct members of the namespace denoted by the preceding path.

The visibility modifier of a `use_decl` applies to every name introduced by the declaration.

#### Constraints

— Each path selecting an item shall resolve to a named item.

— Each path preceding `::{` or `::*` shall resolve to a namespace.

— Each introduced identifier shall differ from every other identifier declared or introduced in the enclosing scope, subject to the duplicate-declaration rules defined in the subclause on duplicate declarations.

— Each item selected by a `pub use` declaration shall be visible to importers of the source unit containing its declaration.

#### Examples (informative)

```
use math::sqrt;
let r = sqrt(2.0); // unqualified access

use io::{ read, write, close }; // multi-import

use collections::map as dictionary;

#add "bool.kr" as booleans;
use booleans::*;

pub use root::{
    branch::leaf,
    nested::{
        item as renamed,
        children::*
    }
};
```

### 5.13.3 Named items

#### Static semantics

A **named item** is an enum variant, an associated constant, an associated subroutine, or a declaration that introduces a name. A `use_tree` selects named items.

#### Examples (informative)

```
use colour::red;
use colour::{ green, blue };
// Red, Green, Blue may be used without the colour:: prefix.

let c = red; // equivalent to colour::red

// Associated constant
use si4::max; // imports the associated constant si4::max
let m = max;  // equivalent to si4::max

// Associated subroutine
use vec::new;  // imports the associated subroutine vec::new
let v = new(); // equivalent to vec::new()
```

## 5.14 Global `asm`

A **global `asm` block** is an `asm` block subordinate to no subroutine. It embeds execution environment instructions directly into the opaque code. A global `asm` block is a global item, as defined in the syntax of this clause. Inline `asm` is defined in the clause on expressions.

### Syntax

```
global_asm = "asm", ws, asm_body ;
```

### Static semantics

Global `asm` blocks are implicitly airside. The `asm_body` production, its two forms, and the rules that fix where the instruction text ends are defined in the clause on expressions.

A global `asm` block differs from inline `asm` in the following:

— A constraint clause shall not appear.

— An inline expression (`'(expr)`) is the only form that injects a translation-time value into the instruction text.

— The block may define external symbols through implementation-defined directives. A symbol so defined participates in external resolution in the same manner as a symbol produced by an `extern` declaration.

A global `asm` block is a σ operation.

### Implementation defined

The syntax of instruction text, implementation-defined directives, and the set of supported execution environments for global `asm` are implementation defined. A conforming implementation shall document the supported syntax of instruction text for each execution environment.

### Examples (informative)

```
const stack_size: uaddr = 4096 * 4;

asm {
    .section .bss
    .align 16
    stack_bottom:
        .skip '( stack_size )
    stack_top:
}

asm {
    .global _start
    _start:
        call main
}
```

## 5.15 `#inline` and `#no_inline`

The `#inline` and `#no_inline` directives control whether the implementation substitutes a subroutine’s body at each invocation site.

### Syntax

```
inline_directive    = '#inline' ;
no_inline_directive = '#no_inline' ;
```

Either directive is an item prefix, as defined in the syntax of this clause.

### Static semantics

Where `#inline` is applied, the implementation should replace each invocation of the annotated subroutine with a copy of its body at the invocation site. A conforming implementation shall not reject a programme solely because an `#inline` directive could not be honoured.

Where `#no_inline` is applied, the implementation shall not replace an invocation of the annotated subroutine with a copy of its body. Each invocation of the subroutine that the opaque code performs shall be emitted as an invocation instruction, and a subroutine the opaque code so invokes shall be emitted there as a discrete invocable entity. A subroutine the opaque code does not invoke is emitted where `extern` requires it, as defined in the subclause on external declaration.

### Constraints

`#inline` and `#no_inline` shall stand only upon a subroutine definition, and shall not both stand upon the same one.

### Design rationale (informative)

The circumstances in which an implementation declines `#inline` include a recursive invocation at the site, an indirect invocation, a code-size constraint of the execution environment, and a body unavailable in the current translation unit.

Failure to honour `#inline` affects performance alone. A programme can depend on a subroutine remaining a discrete symbol in the opaque code, and on the instructions of its body being executed at one place. Disregarding `#no_inline` can therefore cause malfunction that no diagnostic can detect.

### Examples (informative)

```
#inline
fn fast_abs(x: si4) -> si4 {
    return if x < 0 then -x else x;
}

#no_inline
fn cold_path(err: error_code) -> ! {
    log_error(err);
    trap();
}

// #no_inline on a hook point — external tools may patch this symbol
#no_inline
extern fn trace_entry(id: ui4) {
    // body may be empty. The symbol shall exist as an invocable entity.
}

impl counter {
    #inline
    pub fn get(&self) -> uaddr { return (*self).val; }
}
```

## 5.16 Symbol identification

The `#symbol` directive overrides the external name of a declaration with an identification string. A Kurt declaration is thereby identified, in the opaque code and at symbol resolution, by a name that differs from its Kurt identifier.

### Syntax

```
symbol_directive = '#symbol', ws, string_literal ;
```

The `#symbol` directive is an item prefix, as defined in the syntax of this clause. The content of the string literal is opaque to this specification and is passed through without transformation.

### Static semantics

Where `#symbol` is present, the implementation shall use the content of its string literal as the external name, in place of the name derived from the declaration’s identifier. Where the declaration introduces an item into the opaque code, `#symbol` confers Preservation upon it, as the subclause on external declaration defines that property.

### Constraints

`#symbol` shall stand only upon a subroutine definition, a `static` declaration, or a `dyn_item`.

Distinct external symbols of a translation unit shall bear distinct external names.

### Implementation defined

The interpretation of the string literal is implementation defined. A conforming implementation shall document how `#symbol` strings are interpreted for each supported environment.

### Examples (informative)

```
// The Kurt subroutine kurt_compress is exported as “compress”
#symbol "compress"
extern fn kurt_compress(src: &[ui1], dst: $[ui1])
    -> verdict.[uaddr, void] {
    ...
}

// The Kurt static is exported as “global_state”
#symbol "global_state"
extern static mut state: app_state = default();

// A constant has no external name for #symbol to override
// #symbol "limit"
// const limit: ui4 = 64; // translation failure
```

## 5.17 Informative annotations

An annotation attaches implementation-specific information to an item. This specification defines the syntax of an annotation and assigns it no meaning.

### Syntax

```
annotation         = '#[', annotation_content, ']#' ;
annotation_content = ? implementation defined ? ;
```

An annotation is an item prefix, as defined in the syntax of this clause. The content between `#[` and `]#` is a sequence of tokens whose structure and interpretation are implementation defined.

### Static semantics

A conforming implementation may assign meaning to an annotation it recognizes. The meaning it assigns shall leave unchanged both the behaviour this specification defines for the programme and which source units the implementation rejects. The implementation shall document the set of annotations it recognizes and the meaning it assigns to each.

Where the implementation assigns meaning to more than one annotation upon an item, it shall do so in source order. An annotation that the implementation does not recognize has no effect.

### Constraints

An unbalanced `#[` without a matching `]#` shall not appear.

### Examples (informative)

```
#[hot]#
fn dispatch(op: ui1) -> si4 { ... }

#[cold]#
fn report_failure(code: si4) { ... }

#[section ".boot"]#
airside fn reset_vector() { ... }
```

## 5.18 Duplicate declarations

This subclause governs the uniqueness of names within a scope and the interaction of declarations in nested scopes.

### Static semantics

A declaration in an inner scope **hides** a declaration of the same name in an outer scope. The inner declaration introduces a distinct named item. For the duration of the inner scope, the name denotes the inner item.

For `impl` blocks, the uniqueness of protocol implementations and the resolution of item name overlap are defined in the clause on protocols and implementations.

### Constraints

Within a single scope, a name shall be declared at most once. This rule applies to every declaration form that introduces a name into a scope, and to the associated items of an `impl` block alike. A `#path` declaration introduces a source path prefix rather than a name, as the clause on programme structure and translation defines.

### Examples (informative)

```
// Hiding in an inner scope — distinct binding, may share a name
let x: si4 = 1;
{
    // hides outer x — distinct binding, different type
    let x: fe11s52 = 2.0;
    use_float(x); // x is fe11s52 here
}                 // inner x destroyed, outer x visible again
use_int(x);       // x is si4 here, value 1

// Duplicate in the same scope — translation failure
// let y = 1;
// let y = 2; // translation failure: y already declared in this scope
```
