# §5. Declarations

A declaration associates a name with a subroutine, binding, type, or constant. A declaration determines the type, visibility, and, where applicable, the initial value of the named item.

The types that appear in declarations are defined in the clause on types. The expressions that initialize bindings are defined in the clause on expressions. The lexical rules governing identifiers and keywords are defined in the clause on lexical structure.

## 5.1 Subroutine declarations

A subroutine declaration introduces a named computation.

### Syntax

```
(* Shared productions *)
extern_clause     = "extern", [ ws, '(', ws, identifier, ws, ')' ] ;
variadic_clause   = "variadic", ws, '(', ws, identifier, ws, ':', ws,
                    type, ws, ')' ;
subroutine_return = '->', ws, ( type | '!' ) ;

(* Headers *)
subroutine_decl_header  = [ "pub", ws ], [ extern_clause, ws ],
                          [ variadic_clause, ws ], [ "airside", ws ],
                          "fn", ws, identifier, [ ws, generic_clause ] ;

subroutine_proto_header = [ "pub", ws ], [ extern_clause, ws ],
                          [ "variadic", ws ], [ "airside", ws ],
                          "fn", ws, identifier, [ ws, generic_clause ] ;

(* Parameter lists *)
subroutine_decl_param  = '(', ws, [ parameter_list ], ws, ')' ;
subroutine_proto_param = '(', ws, [ proto_parameter_list ], ws, ')' ;

parameter_list = parameter, ws, { ',', ws, parameter, ws },
                 [ ',', ws ] ;
parameter      = [ "mut", ws ], identifier, ws, ':', ws, type ;

proto_parameter_list = proto_parameter, ws,
                       { ',', ws, proto_parameter, ws }, [ ',', ws ] ;
proto_parameter      = [ "mut", ws ], [ identifier, ws, ':', ws ],
                       type ;

(* Declaration form — parameter names mandatory *)
subroutine_declaration = subroutine_decl_header, ws,
                         subroutine_decl_param,
                         [ ws, subroutine_return ],
                         [ ws, ( with_single | with_braced ) ], ws,
                         block ;

(* Prototype form — body omitted, parameter names optional *)
subroutine_prototype   = subroutine_proto_header, ws,
                         subroutine_proto_param,
                         [ ws, subroutine_return ],
                         [ ws, ( with_single | with_braced ) ], ';' ;
```

The `generic_clause` production is defined in the subclause on generic declarations.

### Static semantics

A subroutine declaration introduces a named subroutine into the enclosing scope. Each parameter has the form `name: Type` or `mut name: Type`. Parameters are separated by commas; a trailing comma is permitted.

A declaration that omits the body is a **prototype**: it declares the name, the parameters, and the return type of a subroutine, and supplies no operations. In a subroutine prototype, parameter names are optional. A parameter may be written as `type`, `mut type`, `name: type`, or `mut name: type`. A name that appears in a prototype has no semantic effect. Parameter names are mandatory in any declaration form that includes a body.

If `-> T` is omitted and no prototype in scope for the same name fixes a return type, the return type is `void`. A subroutine that at no point returns control to its invoker may declare `-> !`.

A parameter without `mut` is a single-assignment binding: it may be loaded from, an assignment to it within the subroutine body shall not appear, and only shared references may be created from it. A parameter declared `mut` is a multi-assignment binding: it may be loaded from and assigned to, and exclusive references and shared mutable references may additionally be created from it. In both cases, the argument value is copied or transferred into the parameter binding, as defined in the clause on references and resource management. `mut` on a parameter governs the parameter binding alone.

When a prototype exists in scope for the same name, the corresponding declaration form may elide any clause already fixed by the prototype.

A subroutine may name itself, and two or more subroutines may name each other. Recursion is permitted to any depth that the execution environment admits. Recursion within `xlat` blocks is subject to the evaluation limits defined in the clause on expressions.

### Dynamic semantics

When a subroutine is invoked, execution proceeds as follows:

1. Argument evaluation — each argument expression is evaluated in the order defined in the subclause on subroutine invocation. The resulting values are copied or transferred into the parameter bindings.
2. Subroutine body execution — the body executes. It can return early via `return`, diverge via `trap()`, or reach the closing brace.
3. Value return — the return value is copied or transferred to the invoker.
4. Local destruction — the bindings of the invocation are destroyed in the order defined in the clause on semantics.

### Constraints

A subroutine parameter shall have a unique name within the parameter list.

A `with` clause (`with_single` or `with_braced`) shall appear at most once.

A declaration form’s clauses that differ from a prototype already in scope for the same name shall not appear.

### Examples (informative)

```
fn add(a: si4, b: si4) -> si4 { return a + b; }
fn diverge() -> ! { trap(); }
fn unit() { } // returns void

// extern subroutine — native invocation interface, symbol preserved
pub extern fn init() { ... }
pub extern(efi) fn efi_entry(handle: uaddr, table: %ui1)
    -> uaddr { ... }

// Argument evaluation order — a() runs before b(), b() before c()
foo(a(), b(), c());

// mut parameter — the parameter binding is multi-assignment
fn zero_and_sum(mut buf: [si4; 4]) -> si4 {
    let mut total: si4 = 0;
    let mut i = 0;

    while i < 4 {
        total += buf.at(i);
        *buf.at_mut(i) = 0;
    } then { i += 1; }

    return total;
}

// Direct recursion
fn factorial(n: uaddr) -> uaddr {
    return if n == 0 then 1 else n * factorial(n - 1);
}
```

### 5.1.1 `airside fn`

The `airside` modifier on a subroutine declaration specifies that the subroutine body is an airside region. Within the body, every operation that requires airside is permitted.

#### Static semantics

<table>
<thead><tr><th>Declaration</th><th>Region</th><th>Permitted operations</th></tr></thead>
<tbody>
<tr><td><code>fn</code></td><td>Landside</td><td>Every operation apart from those that require airside</td></tr>
<tr><td><code>airside fn</code></td><td>Airside</td><td>Every operation</td></tr>
</tbody>
</table>

`airside fn` and `fn` are otherwise identical in syntax and semantics. `airside fn` may be `pub`. An invocation to an `airside fn` requires airside.

#### Notes (informative)

The `airside` block form is the corresponding mechanism for isolated airside operations within an otherwise landside subroutine. The block form is defined in the clause on expressions.

### 5.1.2 External declaration

The `extern` prefix on a subroutine or `static` declaration marks the named item as externally accessible and prevents its removal from the opaque code.

The `extern` clause appears before `fn` or `static`. When the parenthesized identifier is present, it names the invocation interface; when omitted, the invocation interface is `native`.

#### Static semantics

A declaration prefixed with `extern` is an **external declaration**. The prefix has three effects:

— Preservation — the implementation shall retain the named item in an invocable or accessible form in the opaque code, accessible from outside the translation unit, whether or not it is referenced within the unit.

— Name stability — the declaration’s identifier is used as the logical external name. The implementation shall not apply any name transformation to this identifier. How the logical external name is represented in the opaque code is implementation defined.

— Invocation interface — for subroutine declarations, the parenthesized identifier selects the invocation interface. `native` denotes the native invocation interface of the execution environment. Other identifier values are implementation defined; the implementation shall document the set of supported invocation interfaces for each execution environment.

When a `#symbol` directive is attached to the declaration, it overrides the logical external name with identification information of the execution environment. The directive is defined in the subclause on symbol identification.

A declaration without `extern` has an implementation-defined name in the opaque code. The implementation may derive the name by any scheme it chooses, and may eliminate the named item entirely if it determines that it is unreferenced.

#### Constraints

A parenthesized invocation interface identifier shall not appear on an `extern static` declaration. An identifier not among the invocation interfaces the implementation documents shall not appear.

#### Implementation defined

The scheme by which the name of a non-`extern` declaration is derived, the mechanism by which the logical external name is represented in the opaque code, and the set of invocation interface identifiers beyond `native` are implementation defined. A conforming implementation shall document each.

#### Examples (informative)

```
pub extern fn init() { ... }
pub extern(native) fn init2() { ... } // equivalent to above
pub extern(efi) fn efi_entry(handle: uaddr, table: %ui1)
    -> uaddr { ... }

// extern without pub — kept in opaque code, private to the module
extern fn internal_hook() { ... }

#symbol "compress"
pub extern fn kurt_compress(src: &[ui1], dst: $[ui1])
    -> verdict.[uaddr, void] { ... }

// internal — implementation-defined name, may be eliminated
fn helper(x: si4) -> si4 { ... }

pub extern static VERSION: ui4 = 1;
extern static mut HW_STATE: ui4 = 0; // preserved but private
```

### 5.1.3 Variadic subroutines

A variadic subroutine accepts a variable number of arguments after its fixed parameters. The variadic arguments are captured into a binding of a type satisfying `with variadic`, as defined in the clause on types.

The `variadic` clause is an optional modifier within `subroutine_decl_header`, positioned after `pub`/`extern` and before `airside`. The bare `variadic` keyword appears in `subroutine_proto_header`.

#### Static semantics

A subroutine declared with the `variadic` modifier uses the variadic invocation interface of the execution environment. The identifier names a `mut` binding whose type is the specified `with variadic` type. The binding is initialized by the implementation at subroutine entry and destroyed at subroutine exit by the implementation-generated destructor.

#### Dynamic semantics

1. Entry — the implementation performs the argument capture that the variadic invocation interface of the execution environment requires, and initializes the binding’s object as the interface requires.
2. Body execution — the binding is an ordinary `mut` binding; it may be loaded from, passed to other subroutines, or have methods invoked on it.
3. Exit — the implementation-generated destructor for the variadic type runs.

#### Constraints

The type named in the `variadic` modifier shall satisfy `with variadic`. The subroutine pointer type of a variadic subroutine includes the `variadic` keyword, as defined in the clause on types.

The `variadic` clause shall not contain the `mut` keyword before the identifier.

#### Examples (informative)

```
// Forwarding subroutine
variadic(args: va_list) fn my_printf(fmt: %ui1) -> si4 {
    return my_vprintf(fmt, args);
}

// Iteration within airside
variadic(args: va_list) fn sum_ints(count: si4) -> si4 {
    let mut total: si4 = 0;
    let mut i: si4 = 0;

    while i < count {
        airside { total += args.next_int.[si4](); }
    } then { i += 1; }

    return total;
}

// Indirect invocation through a variadic subroutine pointer
let f: extern variadic fn(%ui1) -> si4 = my_printf;
f(fmt, width, name);
```

## 5.2 Binding declarations

A `let` declaration introduces one or more bindings within a scope. A binding associates a name with an object and determines whether the object may be assigned to after initialization.

### Syntax

```
let_declaration = "let", ws, pattern, [ ws, ':', ws, type ],
                  [ ws, '=', ws, expression ],
                  [ ws, else_bind, ws, block ], ';' ;

else_bind       = "else", [ ws, '.', ws, identifier ] ;
```

The pattern forms and their refutability are defined in the subclause on patterns and destructuring.

### Static semantics

The `mut` modifier on a pattern element determines the kind of the binding that element introduces, as defined in the subclause on per-binding assignment. A **single-assignment binding** permits its object to be assigned to at most once. A **multi-assignment binding** permits its object to be assigned to any number of times.

When an initializer is present, it constitutes the binding’s first assignment and the object is initialized at the point of declaration. When the initializer is omitted, the object lifetime of the binding’s object begins at the first assignment to it, as defined in the clause on semantics.

The **initialization determination** for a binding at a programme point is the implementation’s establishment, from observations within the translation unit, that the binding’s object is initialized at the point. Whether an operation on the binding’s object is permitted or required at the point is determined by it.

Before the initialization determination has been established, the destructor of the binding’s type, if any, is not invoked at scope exit. After it has been established, the destructor of the binding’s type, if any, is invoked at scope exit.

The implementation may use any static analysis technique available to it to establish the initialization determination.

The status of a binding’s destruction obligation is determined by the assignment, transfer, and `undestruct` rules defined in the clause on references and resource management. Where control flow causes the obligation status to differ between branches at a scope exit point, the implementation shall either track the status at execution time and invoke or omit the destructor accordingly, or reject the programme with a translation failure.

When the type annotation is omitted, the binding’s type is determined by the rules for type inference.

### Dynamic semantics

When an initializer is present, the initializer expression is evaluated and the resulting value is stored into the binding’s object, which is thereby initialized. When an initializer is absent, the binding’s object is initialized at the first assignment to it. The storage of the binding’s object is reserved and released by the storage layout model defined in the clause on semantics.

### Constraints

Before the initialization determination has been established at a programme point, the binding’s object shall not be loaded and a managed reference to it shall not be created at the point.

An assignment to a single-assignment binding shall not appear where the initialization determination for the binding has been established at the programme point of the assignment.

A declaration that omits both the type annotation and the initializer shall not appear.

### Examples (informative)

```
let x: si4 = 42;     // single-assignment, initialized at declaration
let y = x + 1;       // single-assignment, type inferred
let mut counter = 0; // multi-assignment, initialized at declaration
counter += 1;        // OK — counter is mut

// Deferred initialization — single-assignment
let result: si4;
if condition {
    result = compute_a();
} else {
    result = compute_b();
}
use(result);   // OK — all paths proven to initialize result
// result = 0; // translation failure — result is single-assignment

// Deferred initialization — multi-assignment
let mut buf: [ui1; 4096];
buf = [0; 4096];
airside { dma_fill(%buf, 4096); }
use(buf); // OK — buf was initialized by the assignment above

// Constant propagation — implementation proves dead branch
let val: si4;
if verdict.[void, void]::Pass(void) {
    val = 1;
}
use(val); // OK — implementation proves the else path is unreachable

// translation failure — proof failure
let x: si4;
if runtime_condition {
    x = 1;
}
use(x); // implementation cannot prove x is initialized

// translation failure — managed reference to uninitialized binding
let a: si4;
let r = &a;
```

### 5.2.1 The `else` clause on refutable patterns

A `let` declaration may use any pattern form defined in the subclause on patterns and destructuring. Whether a pattern is refutable is defined in the subclause on refutability.

#### Static semantics

When the `else` clause names a binding (`else.f`), the original value that failed to match is bound to `f` within the `else` block. The type of `f` is the type of the initializer expression — the complete, undestructured value.

#### Dynamic semantics

1. The initializer expression is evaluated.
2. The result is matched against the pattern.
3. If the pattern matches, all bound names are initialized and execution continues after the declaration.
4. If the pattern does not match, the `else` block executes. The `else` block is a control transfer or a diverging expression, and the enclosing scope exits.

#### Constraints

A `let` declaration shall include an `else` clause if and only if its pattern is refutable.

The `else` block shall be a control transfer or a diverging expression.

#### Examples (informative)

```
// Irrefutable patterns — else is FORBIDDEN
let .{ x, y } = get_point(); // OK
// translation failure — irrefutable
let .{ x, y } = get_point() else { return; };

// Refutable patterns — else is MANDATORY
// OK — diverge
let verdict::Pass(x) = try_parse() else { return; };
// OK — diverge with binding
let verdict::Pass(x) = try_parse() else.fail {
    log(fail); return;
};

// translation failure — no else
let verdict::Pass(x) = try_parse();
```

## 5.3 Translation-time constants

A `const` declaration introduces a named translation-time constant. The initializer is evaluated at translation time; only the resulting value is incorporated into the opaque code.

### Syntax

```
const_declaration = [ "pub", ws ], "const", ws, identifier, ws,
                    [ ':', ws, type, ws ], '=', ws, expression, ';' ;
```

### Static semantics

The rule for an omitted type annotation is defined in the subclause on binding declarations. The initializer expression is evaluated at translation time, as defined in the clause on programme structure and translation. The resulting value is substituted at each use site.

### Constraints

A `const` initializer that cannot be evaluated at translation time shall not appear. The initializer establishes every field value; a store to a field after initialization shall not appear, regardless of the field’s modifiers.

### Examples (informative)

```
const MAX_SIZE: uaddr = 1024;
const TAU: fe11s52 = 6.283185307179586476925286766559;
// type inferred from the initializer
const LIMIT = 1024~ui4;
// subroutine invoked at translation time
const CRC_TABLE: [ui4; 256] = make_lut();
```

## 5.4 Global bindings

A `static` declaration introduces a binding whose object has the permanent object lifetime, as defined in the clause on semantics.

### Syntax

```
static_declaration = [ "pub", ws ], [ "extern", ws ], "static", ws,
                     [ "mut", ws ], identifier, ws,
                     [ ':', ws, type, ws ], '=', ws, expression, ';' ;
```

### Static semantics

The rule for an omitted type annotation is defined in the subclause on binding declarations.

`static` without `mut` introduces a binding whose object may be loaded from any point in the programme. Multiple execution contexts can load from the object without synchronization. The binding is a single-assignment binding: only a reference that permits no store may be created from it.

Where the type of a `static` binding contains `mut` fields — directly or transitively through fields held by value — those fields may be stored to, by the per-field store permission defined in the subclause on field modifiers. Such a store requires airside.

`static mut` introduces a binding whose object permits both loads and stores.

### Dynamic semantics

`static` bindings are initialized before any other Kurt-generated code executes. The implementation may arrange the initialized values in the opaque code in any order. The occupancy of referents in `static` initializers follows the rules defined in the clause on expressions. Their storage persists until the execution of the programme ends. `with destruct` on a `static` binding’s type is permitted — the type itself can have a destructor — but the destructor is never invoked.

### Constraints

A load from or a store to a `static mut` binding requires airside.

### Examples (informative)

```
static config: app_config = default_config();
static mut counter: uaddr = 0;
// type inferred from the initializer
static limit = 4096~uaddr;

fn increment() {
    airside { counter += 1; } // airside required for static mut access
}

// External static — name is “VERSION”, preserved unconditionally
pub extern static VERSION: ui4 = 1;

// External static with identification specific
// to the execution environment
#symbol "global_state"
extern static mut global_state: app_state = default();

// Per-field store permission via mut field
struct atomic_counter {
    mut value: ui4  // mut field: airside stores always permitted
}

static shared_counter: atomic_counter = atomic_counter { .value = 0 };
// shared_counter is `static` (not `static mut`), but the `mut` field
// permits airside stores through &shared_counter.
```

## 5.5 Composite types

A composite type is a type composed of zero or more constituent fields.

### Syntax

```
composite_form   = '{', ws, ( anon_field_list | named_field_list ), ws,
                   '}' ;

anon_field_list  = anon_field, ws, { ',', ws, anon_field, ws },
                   [ ',', ws ] ;
anon_field       = field_modifiers, type, [ ws, '=', ws, expression ] ;

named_field_list = named_field, ws, { ',', ws, named_field, ws },
                   [ ',', ws ] ;
named_field      = field_modifiers, identifier, ws, ':', ws, type,
                   [ ws, '=', ws, expression ]
                 | '?', ws, ':', ws, type ;

field_modifiers  = { field_modifier, ws } ;
field_modifier   = "pub" | "airside" | "mut" ;
```

### Static semantics

A composite type takes one of three forms:

— **Unit form** — the type has no fields. Its size is zero and its alignment is zero. It contains exactly one value.

— **Unnamed-field form** — the type has one or more fields identified by position in declaration order.

— **Named-field form** — the type has one or more fields identified by name. Field access uses the dot operator followed by the field identifier.

A declaration that omits the composite form is in unit form. A declaration whose composite form matches `anon_field_list` is in unnamed-field form. A declaration whose composite form matches `named_field_list` is in named-field form.

### Constraints

Access to a `?` field shall not occur. A composite literal shall not name a `?` field. A destructuring pattern shall not bind a `?` field. `?` fields are defined below.

A default-value expression shall be evaluable at translation time. A field without a default-value expression shall be initialized explicitly in every composite literal.

A composite type in unnamed-field form shall not contain `?` fields.

A field name shall be unique within a named-field composite type. `?` fields are exempt from uniqueness.

A composite literal that constructs a composite type with an `airside` field requires airside.

A non-`pub` field shall be named in a composite literal only within the module that declares the composite type.

### 5.5.1 Field modifiers

#### Static semantics

Three field modifiers exist: `pub`, `airside`, `mut`. They may be written in any order; the field’s meaning is unchanged by their arrangement.

The eight permitted combinations and their effects are:

— `field: T` — private, landside. Whether the field is storable follows from the enclosing binding.

— `pub field: T` — public, landside. Same store rules, visible to importers.

— `airside field: T` — private, airside-only. Every load and every store requires airside.

— `pub airside field: T` — public, airside-only. Every load and every store requires airside; the field is visible to importers.

— `mut field: T` — private, landside. Load is always permitted. Store through a `mut` binding is permitted; store through any other binding requires airside.

— `pub mut field: T` — public version of the above.

— `airside mut field: T` — private. Every load and every store requires airside, and store is permitted through every binding.

— `pub airside mut field: T` — public version of the above.

The `mut` modifier declares that a field carries **per-field store permission**: it may be stored to through a reference or a binding that itself permits no store, and such a store requires airside.

The `mut` modifier has no effect in a `const` context.

#### Constraints

A field declaration that repeats a modifier shall not appear.

### 5.5.2 `?` fields

#### Static semantics

A **`?` field** declares padding cells within a named-field composite type. A `?` field is zero-initialized at construction. Multiple `?` fields are permitted within a single composite type.

### 5.5.3 Default-value expressions

#### Static semantics

A field may carry a default-value expression of the form `= expr`. When a composite literal omits a field with a default-value expression, the expression is evaluated at the point of construction.

### 5.5.4 Padding semantics

#### Static semantics

Padding cells within a composite type follow the padding semantics defined in the clause on types.

## 5.6 Struct declarations

A struct declaration introduces a named composite type whose value is the product of its constituent fields. Each field occupies a distinct, typed storage region within the struct’s representation.

### Syntax

```
struct_declaration = [ "pub", ws ], "struct", ws, identifier,
                     [ ws, generic_clause ],
                     ( [ ws, with_single ], ';'
                     | ws, with_braced
                     | ws, composite_form,
                       [ ws, with_single, ';' | ws, with_braced ] ) ;
```

### Static semantics

A `struct` declaration introduces a named composite type. A struct whose declaration uses `;` is in unit form. A struct whose declaration uses a composite form is in unnamed-field or named-field form, determined by the composite form.

### Constraints

A `struct` declaration shall carry at most one `with` clause (`with_single` or `with_braced`).

### Examples (informative)

```
// Unit form
struct empty_t;
let v = empty_t;

struct point { x: si4, y: si4 }

struct origin_point {
    x: si4 = 0,
    y: si4 = 0
}

struct example {
    a: si4,                // private, landside — the binding
                           // kind governs stores
    pub b: si4,            // public,  landside — same
    mut c: si4,            // private, landside — airside stores
                           // always permitted
    pub mut d: si4,        // public,  landside — airside stores
                           // always permitted
    airside e: si4,        // private, airside-only access
    pub airside f: si4,    // public,  airside-only access
    airside mut g: si4,    // private, airside-only, airside
                           // stores always permitted
    pub airside mut h: si4 // public,  airside-only, airside
                           // stores always permitted
}

struct network_header {
    version: ui1,
    ?: ui1,
    length: ui2,
    ?: [ui1; 4],
    payload_offset: ui4
}

struct file_handle {
    fd: si4
} with destruct {
    close(self.fd); // self: $file_handle
};

struct packet {
    header: ui4,
    seq: ui4,
    payload: &[ui1]
} with {
    repr(pack(1)),
    align(4)
}
```

### Notes (informative)

Representation and alignment rules are defined in the clause on types. A struct may declare `with destruct` to supply a destructor that executes when the value goes out of scope. The destruction obligation, the copyability determination it governs, composite destruction, destruction order, explicit early destruction, and destructor suppression are defined in the clause on references and resource management.

## 5.7 Enum declarations

An enum declaration introduces a named type with a fixed set of variants. Each variant may carry a payload. At most one variant may be designated `wild`.

### Syntax

```
enum_declaration = [ "pub", ws ], "enum", ws, identifier,
                   [ ws, generic_clause ], ws, '{', ws,
                   [ variant_list ], ws, '}',
                   [ ws, with_single, ';' | ws, with_braced ] ;

variant_list     = variant, ws, { ',', ws, variant, ws }, [ ',', ws ] ;
variant          = identifier, [ ws, composite_form ],
                   [ ws, '=', ws, variant_value ] ;

variant_value    = integer_literal
                 | "wild", [ ws, '(', ws, integer_literal, ws, ')' ] ;
```

### Variant kinds

Each variant is a composite type in one of the three forms:

— **Unit variant** — no composite form. The variant carries only its discriminant. Constructed by name alone.

— **Unnamed-field variant** — a composite form matching `anon_field_list`. Fields are accessed by their index in declaration order. Constructed with braces.

— **Named-field variant** — a composite form matching `named_field_list`. Fields are accessed by name. Constructed with a brace literal.

### Static semantics

The implementation distinguishes unnamed-field variants from named-field variants by the form of the first field declaration within the composite form. If the first non-modifier token sequence matches `identifier ':'` or begins with `?`, the variant uses `named_field_list`. Otherwise, the first non-modifier token sequence is a type expression, and the variant uses `anon_field_list`.

An enum declares a set of named variants.

`wild` declares that the designated variant covers all discriminant values not matched by any other variant.

`wild(V)` declares a **canonical value** for the wild variant, where `V` is an integer literal. When a value of the wild variant is created explicitly, the implementation shall store `V` as the discriminant. (e.g. `verdict::Fail(payload)` stores `V` as the discriminant.) The canonical value also governs discriminant extraction via `as`, as defined in the clause on expressions.

Where `wild` is written without a canonical value, the wild variant may still be constructed explicitly. The discriminant value used for construction is the value assigned by the automatic discriminant assignment algorithm defined below, and an implementation may select a different value from the wild set.

The coverage of the wild variant is the same whether or not a canonical value is declared.

— Where a `wild` variant has no payload, matching it extracts nothing.

— Where a `wild` variant has a payload, the discriminant value is a wildcard, and the payload is extracted as the payload of any other variant is. (e.g. `Fail(F) = wild(0)` in `verdict`.)

An enum that declares no `wild` variant has an **implicit wild**. The implicit wild has no payload and is assigned no discriminant value of its own. It covers all discriminant values of the enum’s discriminant type that no declared variant matches; where the discriminant type matches every such value to a declared variant, the implicit wild covers none.

A value of an enum that declares no `wild` variant may be constructed by the expression `EnumType::wild`, as defined in the subclause on wild construction in the clause on expressions.

When a variant is declared without an explicit discriminant value, the implementation assigns a discriminant automatically using the following algorithm:

1. Collect the **occupied set** *S*: the union of all explicitly specified discriminant values and all `wild(V)` canonical values declared in the enum.
2. Initialize a **candidate counter** *d* to zero.
3. Traverse the variants in declaration order, without exception. A `wild` variant without a canonical value counts as lacking an explicit discriminant value. For each variant that lacks one: advance *d* to the smallest value ≥ *d* that is not in *S*; assign *d* as the variant’s discriminant value; add *d* to *S*; set *d* to *d* + 1.

### Constraints

A type shall have at most one `wild` variant.

Each explicitly specified discriminant value within an enum, counting each `wild(V)` canonical value among them, shall be distinct from every other.

A canonical value shall not collide with any explicit variant’s discriminant value.

An enum for which the automatic discriminant assignment algorithm, defined above, finds no representable candidate value shall not appear.

### Examples (informative)

```
// Unit variants only
enum colour { Red, Green, Blue }

// Tuple variant — single positional field
enum packet { Data { &[ui1] }, Ack, Error = wild }

// Tuple variant — multiple positional fields
enum shape {
    Circle { fe11s52 },                 // radius: .0
    Rect { fe11s52, fe11s52 },          // width: .0, height: .1
    Triangle { fe8s23, fe8s23, fe8s23 } // sides: .0, .1, .2
}

// Struct variant — named fields
enum event {
    KeyPress { key: ui4, modifiers: ui1 },
    MouseMove { x: si2, y: si2 },
    Quit
}

// Mixed
enum message {
    Ping,
    Data { ui1, [ui1; 32] },          // positional: kind + payload
    Error { code: ui4, msg: &[ui1] }, // named fields
    Unknown = wild
}

// Accessing positional variant fields
let s: shape = shape::Rect { 3.0, 4.0 };
match s {
    shape::Rect { w, h }        -> area(w, h);
    shape::Circle { r }         -> area_circle(r);
    shape::Triangle { a, b, c } -> area_triangle(a, b, c);
    wild                        -> 0.0;
}

// Accessing struct variant fields
let e: event = event::KeyPress { .key = 65~ui4, .modifiers = 0~ui1 };
match e {
    event::KeyPress { .key, .modifiers } -> handle_key(key, modifiers);
    event::MouseMove { .x, .y }          -> handle_mouse(x, y);
    event::Quit                          -> quit();
    wild                                 -> ignore();
}
```

### Notes (informative)

How enums interact with `match` exhaustiveness is defined in the clause on statements and control flow. Enum layout and automatic discriminant sizing are defined in the clause on types. The syntactic forms for constructing values of an enum type are defined in the clause on expressions.

An enum may declare `with destruct` to supply a destructor. When a value of the enum is destroyed, the destructor of the active variant’s payload executes. The full destruction model is defined in the clause on references and resource management.

## 5.8 Type aliases

A type alias introduces a new name for an existing type.

### Syntax

```
type_alias = [ "pub", ws ], "type", ws, identifier,
             [ ws, generic_clause ], ws, '=', ws, type, ';' ;
```

### Static semantics

At every use site, a type alias is replaced unconditionally by its underlying type.

An `impl` block whose target is a type alias resolves against the underlying type. The duplicate-implementation rule defined in the clause on protocols and implementations applies to the resolved targets.

A generic alias `type A.[T, ...] = Expr` is expanded at each use site: the supplied type arguments are substituted for the declared parameters, and the resulting type then replaces the alias name. The expansion follows the same substitution rule as a non-generic alias.

### Constraints

A type alias that is directly or mutually recursive shall not appear. A generic alias that declares a generic parameter not appearing in the aliased type shall not appear.

### Implementation defined

A conforming implementation may display either the alias name or the underlying type in diagnostic output. Built-in aliases shall be displayed by their alias name.

### Examples (informative)

```
type Byte        = ui1;
type Index       = uaddr;
type Pair.[A, B] = .{A, B};
type Matrix.[T]  = [[T; 4]; 4];

pub type Seconds = ui4;

// No conversion at any use site
let b: Byte = 42~ui1;
let _: ui1  = b;
fn takes_ui1(x: ui1) {}
takes_ui1(b);

// Protocol bounds resolve on the underlying type
fn show.[T: Fmt](x: T) { ... }
show(b); // OK — ui1 implements Fmt

// Generic argument identity
let p1: Pair.[Byte, si4] = .{ 1~ui1, 2 };
let p2: Pair.[ui1,  si4] = p1; // same type

// A struct declaration introduces a distinct type
struct Seconds2 { val: ui4 }
```

## 5.9 Generic declarations

A generic declaration introduces a type or subroutine parameterized over one or more generic parameters — type parameters or dependence parameters. At each site that supplies arguments, the parameters are resolved to the arguments supplied.

### Syntax

```
generic_clause   = '.[', ws, generic_item, ws,
                   { ',', ws, generic_item, ws }, [ ',', ws ], ']' ;
generic_item     = type_param | dependence_param ;
type_param       = identifier, [ ws, ':', ws, bound ] ;
dependence_param = "let", ws, identifier, ws, ':', ws, type ;
bound            = bound_elem, ws, { '+', ws, bound_elem, ws } ;
bound_elem       = builtin_bound | single_path ;

generic_args     = '.[', ws, generic_arg, ws,
                   { ',', ws, generic_arg, ws }, [ ',', ws ], ']' ;
generic_arg      = type | expression ;
```

Generic subroutines use the same `generic_clause` syntax, placed between the subroutine name and the parameter list.

A **generic argument list** appears at a use site of a generic declaration, following the name of the type or subroutine it instantiates, in a type position and in an expression position alike. Its arguments correspond to the declared generic parameters in order: a type argument resolves a type parameter; a dependence argument resolves a dependence parameter.

### Static semantics

Generic parameters are in scope for the entire declaration: the field list (for structs), the variant list (for enums), the parameter list and return type (for subroutines), the `with` clause, and any `impl` blocks that name the type.

A type in which a type parameter remains unresolved is an **abstract type**. A type in which no type parameter remains unresolved is a **concrete type**. **Instantiation** is the derivation of a concrete type from an abstract type by resolving each of its type parameters to a type argument.

A **type parameter** is a distinct abstract type at the declaration site. An **unconstrained parameter** `.[T]` is an opaque layout, restricted to operations agnostic to internal representation: assignment, parameter passing, and transfer.

A **dependence parameter** declares a value upon which the types within the declaration may depend. The value supplied for it is a **dependence argument**. A dependence parameter may appear wherever a binding of the same type may appear: in array lengths, and in the types and expressions of subsequent parameters and fields. A dependence parameter whose argument is determined at translation time may in addition appear wherever a `const` binding of the same type may appear.

Two instantiations of the same generic declaration are the same type if and only if all type arguments are the same types and all dependence arguments are the same value.

### Constraints

The number of arguments supplied shall equal the number of parameters in the declaration.

The path of a bound element shall name a protocol.

A parameter identifier shall be unique within its parameter list. An inner parameter that hides an outer parameter of the same name shall not occur. A subroutine-level generic parameter hides any module-level type declaration of the same identifier. A generic parameter that hides a generic parameter declared on an enclosing `impl` or `protocol` block shall not occur.

An unconstrained parameter `.[T]` shall not be subjected to arithmetic, field access, or any operation requiring protocol or intrinsic bounds.

An abstract type shall not appear in a position that requires a concrete type.

The type of a dependence parameter shall be copyable, and shall neither be a reference type nor contain one as a constituent.

An operation between two instantiations whose dependence arguments differ shall not appear. Such a violation, where not detected during translation, can cause indeterminate state.

### Examples (informative)

```
struct pair.[A, B] {
    first:  A,
    second: B
}

contract option.[T] {
    Some(T),
    None(void) = wild
};

struct arc.[T] {
    ptr: %T,
    mut ref_count: &atomic mut ui4
}

// Instantiation
let p: pair.[si4, verdict.[void, void]] =
    pair { .first = 42, .second = verdict::Pass(void) };
let x: option.[si4] = option::Some(7);

// Explicit generic arguments — required when type cannot be inferred
fn default_value.[T: Default]() -> T {
    return (T as Default)::default();
}

let val = default_value.[si4]();

// Inline bound
fn max.[T: primitive](a: T, b: T) -> T {
    return if a > b then a else b;
}

// Dependence parameters
struct matrix.[T, let rows: uaddr, let cols: uaddr] {
    data: [T; rows * cols]
}

let m: matrix.[fe11s52, 3, 4] = ...;

fn zeros.[T: numeric, let N: uaddr]() -> [T; N] {
    return [0; N];
}
```

### 5.9.1 Generic dispatch

#### Static semantics

The type parameters of a generic subroutine are abstract within its body. The subroutine accesses type-specific properties through a bound descriptor passed to it at each invocation site. The bound descriptor is obtained via `T'bound(X)`, as defined in the clause on expressions. This is the defining semantics: a conforming programme behaves as though every generic subroutine receives and operates through a bound descriptor. A conforming implementation may generate a specialized copy for particular concrete type arguments within the same translation unit, provided every σ operation is preserved in the same order, each producing the same signal.

A dependence argument is passed as a value of its type.

The concrete type of each type parameter is determined from the subroutine’s arguments at the invocation site. Where a type argument is an inferred type `?`, the implementation resolves the corresponding type parameter by inference from the surrounding context. Where a type parameter appears solely in the return type, or where argument types yield contradictory constraints, the type argument shall be supplied explicitly. A dependence argument shall be supplied explicitly.

#### Constraints

The mapping from argument types to type parameters shall be exact and unambiguous.

### 5.9.2 Signature lowering

The signature of a generic subroutine is lowered to the execution environment’s invocation interface. The lowered signature is divided into three zones, always in the following order.

— **Zone 1** — the out-parameter. The first parameter is `%void`, pointing to storage the invoker reserves for the return value. The invoker determines the storage region from the source-level return type: where the type involves a type parameter, from the `T'size` and `T'align` fields of the parameter’s type descriptor; where it is concrete, from the type. A source-level return type of `void` is a zero-size type, and the storage occupies zero cells.

— **Zone 2** — the source parameters. The source-level parameters follow, in declaration order. A parameter whose type is concrete passes through unchanged. A parameter whose type involves a type parameter is lowered to `%void`; a slice reference `&[T]` or `$[T]` is lowered to `&[void]` or `$[void]`.

— **Zone 3** — the descriptors and dependence parameters. Generic parameters from up to three levels — the `impl` block, the target type, and the subroutine itself — are emitted in that order. Within each level, parameters appear in declaration order. For each type parameter, the `type` descriptor reference is emitted as `%void`. For each bound element of the bound on a type parameter, one `%void` is emitted; the elements appear in declaration order. The structure each element designates is defined in the subclause on bound descriptor emission; an element that carries no structure designates a zero-size object. For each dependence parameter, one parameter of its type is emitted.

The return type of the lowered signature is `void`; the result is delivered through the zone 1 out-parameter.

The lowered signature is a single symbol composed of concrete types, `%void`s, and the types of dependence parameters. The resulting symbol is invocable across `#dyn` boundaries without source.

#### Examples (informative)

```
extern fn sort.[T: Ord](arr: $[T]) { ... }
// lowers to:
// fn sort(
//     out:    %void,   // zone 1
//     arr:    $[void], // zone 2
//     T_type: %void,   // zone 3: T'bound(type)
//     T_Ord:  %void,   // zone 3: T'bound(Ord)
// ) -> void

extern fn add.[T: numeric](a: T, b: T) -> T { ... }
// lowers to:
// fn add(
//     out:       %void, // zone 1
//     a:         %void, // zone 2
//     b:         %void, // zone 2
//     T_type:    %void, // zone 3: T'bound(type)
//     T_numeric: %void, // zone 3: T'bound(numeric)
// ) -> void

extern fn process.[T: Ord + Clone](x: &T) { ... }
// lowers to:
// fn process(
//     out:     %void,   // zone 1
//     x:       %void,   // zone 2
//     T_type:  %void,   // zone 3: T'bound(type)
//     T_Ord:   %void,   // zone 3: T'bound(Ord)
//     T_Clone: %void,   // zone 3: T'bound(Clone)
// ) -> void

extern fn merge.[
    T: Ord, U: Clone
](arr: $[T], default: U, count: si4) { ... }
// lowers to:
// fn merge(
//     out:     %void,   // zone 1
//     arr:     $[void], // zone 2
//     default: %void,   // zone 2
//     count:   si4,     // zone 2: concrete
//     T_type:  %void,   // zone 3: T'bound(type)
//     T_Ord:   %void,   // zone 3: T'bound(Ord)
//     U_type:  %void,   // zone 3: U'bound(type)
//     U_Clone: %void,   // zone 3: U'bound(Clone)
// ) -> void

extern fn fill.[
    T: numeric, let N: uaddr
](buf: $[T; N]) { ... }
// lowers to:
// fn fill(
//     out:       %void, // zone 1
//     buf:       %void, // zone 2
//     T_type:    %void, // zone 3: T'bound(type)
//     T_numeric: %void, // zone 3: T'bound(numeric)
//     N:         uaddr, // zone 3: dependence
// ) -> void

extern fn identity.[T](x: T) -> T { return x; }
// lowers to:
// fn identity(
//     out:    %void,    // zone 1
//     x:      %void,    // zone 2
//     T_type: %void,    // zone 3: T'bound(type)
// ) -> void
```

Usage through `#dyn`:

```
#dyn libsort {
    fn sort(out: %void, arr: $[void],
        t_type: %void, t_ord: %void);
}

pub fn sort.[T: Ord](arr: $[T]) {
    airside {
        let dummy: void;
        let t_type = contract T'bound(type) else trap();
        let t_ord  = contract T'bound(Ord)  else trap();

        libsort::sort(%dummy, %arr, t_type, t_ord);
    }
}

// At the invocation:
sort.[si4](my_array);
```

For `extern fn sort.[T: Ord](...)`, the implementation generates both the lowered symbol and the forwarding subroutine.

### 5.9.3 `#dyn` boundary constraint

#### Static semantics

The generic parameters of subroutines and types imported via `#add` are resolved by the importing translation unit. A generic subroutine declared `extern` is exempt from the restriction defined below. The lowered signature is composed entirely of concrete types and `%void`s.

#### Constraints

A generic subroutine without `extern` shall not be exposed across `#dyn` boundaries. A `#dyn` block shall not declare a subroutine with unresolved generic parameters.

## 5.10 Patterns and destructuring

A pattern decomposes a value into its constituent parts. Patterns appear in `let` declarations, `match` alternatives, and `if let` and `while let` conditions.

### Syntax

```
pattern        = literal_pat | ident_pat | ignore_pat | wild_pat
               | variant_pat | contract_pat | struct_pat | anon_pat
               | slice_pat | string_pat | range_pat
               | binding_pat | or_pat ;

literal_pat    = integer_literal | float_literal ;
ident_pat      = [ "mut", ws ], identifier ;
ignore_pat     = '?' ;
wild_pat       = "wild", [ ws, '(', ws, identifier, ws, ')' ] ;
variant_pat    = single_path, ws, '{', ws,
                 [ field_pat_list | unnamed_pat_list ], ws,
                 '}' | single_path ;
contract_pat   = single_path, ws, '(', ws, pattern, ws, ')' ;
struct_pat     = single_path, ws, '{', ws,
                 ( field_pat_list | unnamed_pat_list ), ws, '}' ;
anon_pat       = '.', ws, '{', ws, unnamed_pat_list, ws, '}' ;

field_pat_list = field_pat, ws, { ',', ws, field_pat, ws }, [ ',', ws ],
                 [ ws, '...' ] ;
field_pat      = [ "mut", ws ], [ identifier, ws, '=', ws ],
                 '.', ws, identifier,
                 [ ws, '@', ws, pattern ] ;

unnamed_pat_list = unnamed_pat, ws,
                   { ',', ws, unnamed_pat, ws }, [ ',', ws ] ;
unnamed_pat      = ident_pat, [ ws, '@', ws, pattern ] ;

slice_pat      = '[', ws,
                 [ element_pat, ws, { ',', ws, element_pat, ws },
                   [ ',', ws ] ], ']' ;
element_pat    = pattern | '...' ;
string_pat     = string_literal | raw_string_literal ;
range_pat      = literal_pat, ws, ( '..' | '..=' ), ws, literal_pat ;
binding_pat    = ident_pat, ws, '@', ws, pattern ;
or_pat         = pattern, ws, '|', ws, pattern ;
```

### 5.10.1 Pattern forms

#### Static semantics

— **Literal pattern** — matches a specific `numeric` value. This pattern is always refutable.

— **Identifier pattern** — an identifier, optionally preceded by `mut`, binds the matched value to a name at its original type. `mut` makes the binding a multi-assignment binding, as defined in the subclause on per-binding assignment. This pattern is irrefutable.

— **Ignore pattern** — matches every value of the matched type and introduces no binding. This pattern is irrefutable.

— **`wild` pattern** — matches a value that no declared variant of the matched type covers, and yields a reference to the cells of the matched object (`&[ui1]`). The bare form `wild` discards it. The form `wild(`*name*`)` binds it to *name*.

— **Variant pattern** — matches an enum variant. A unit variant is written as the path alone; a variant with payload is written with braces.

— **Contract variant pattern** — matches a variant of a contract type, as defined in the clause on statements and control flow, and decomposes its payload by the enclosed pattern. This pattern is refutable.

— **Struct pattern** — decomposes a struct value into its fields. The type name is mandatory. `...` at the end ignores remaining named fields; `...` is permitted only for named-field structs, not unnamed-field structs.

— **Anonymous struct pattern** (`.{ }`) — decomposes a tuple value into positional fields. Irrefutable when all sub-patterns are irrefutable.

— **Slice pattern** — matches a slice or array by element-wise comparison. The rules governing it are defined in the clause on statements and control flow.

— **String literal pattern** — syntactic shorthand for a fixed-length slice pattern whose elements are the `ui1` values of the string literal, as defined by the mapping in the clause on lexical structure. A raw string literal pattern follows the same rules. The implementation expands the pattern into its Γ sequence during translation. Refutable. (e.g. `"abc"` as a pattern is identical to `[0x61, 0x62, 0x63]`.)

— **Range pattern** — matches a value within a numeric range. `..=` is inclusive; `..` is exclusive. Refutable.

— **Binding pattern** (`@`) — `name @ sub_pattern` binds the matched value to `name` while testing against `sub_pattern`. Refutability follows from the sub-pattern.

— **Or-pattern** — `p | q` matches if either alternative matches. This pattern is refutable when both alternatives are refutable.

#### Constraints

The alternatives of an or-pattern shall bind the same names with the same types and the same binding kind.

A `wild` pattern that matches no value shall not appear.

A string literal pattern shall appear only when the matched type is `&[ui1]`, `&[ui1; N]`, or `[ui1; N]`. Using a string literal pattern on any other type shall not appear.

### 5.10.2 Struct destructuring

#### Static semantics

A struct pattern decomposes a value of a struct type or an enum variant with a struct payload. The type name, or the variant path, is mandatory.

In a **named-field destructuring**, a `field_pat` designates a field by `.field_name`. The form `.field_name` binds the field value to `field_name`. The form `binding_name = .field_name` binds it to `binding_name`. A following `@ sub_pattern` applies the sub-pattern to the field value.

`...` at the end of the field list causes fields not mentioned in the pattern to be ignored.

An **unnamed-field destructuring**, which applies to anonymous structs, unnamed-field structs, and unnamed-field variants, uses `unnamed_pat_list`. Fields are matched by position in declaration order. Each `unnamed_pat` introduces a binding or a sub-pattern for the field at its position.

#### Constraints

Every field of a named-field destructuring shall be mentioned unless the pattern ends with `...`.

The bindings of an unnamed-field destructuring shall equal the fields of the type declaration in number and in order.

A destructuring pattern shall not be applied to a value of a type satisfying `with destruct`, nor to a value of reference type. A destructuring pattern is one of: a struct pattern, an anonymous struct pattern (`.{ ... }`), or a variant pattern that destructures a payload.

#### Examples (informative)

```
// Named-field struct
struct point { x: si4, y: si4 }
let point { .x, .y } = get_point();  // all fields
let point { .x, ... } = get_point(); // y ignored
let point { origin = .x @ 0, .y } = get_point() else {
    return; // x bound to origin, constrained to 0
};

// Enum with named-field variant
enum event {
    KeyPress { key: ui4, modifiers: ui1 },
    Quit
}

match e {
    event::KeyPress { .key, ... } -> handle(key); // modifiers ignored
    event::Quit                   -> quit();
    wild                          -> ignore();
}

// Anonymous struct (tuple) destructuring
let .{ a, b } = get_pair();      // all fields, positional order
// let .{ a, ... } = get_pair();
// translation failure — ... not permitted

// Enum with unnamed-field variant
match result {
    verdict::Pass(val) -> use(val);
    verdict::Fail(err) -> handle(err);
}
```

### 5.10.3 Per-binding assignment

#### Static semantics

A pattern binding designates the matched component within the matched value. Where the binding carries `mut`, an assignment through it stores to that component.

A pattern introduces one binding for each identifier pattern and each field pattern it contains. A binding whose pattern element carries the `mut` modifier is a multi-assignment binding; a binding whose pattern element carries no `mut` modifier is a single-assignment binding. The kind of one binding is independent of the kind of every other binding the same pattern introduces.

The `mut` modifier carries this meaning in every pattern context — `let` declarations, `match` alternatives, `if let` conditions, and `while let` conditions.

#### Examples (informative)

```
let struct_t { .a, mut .b, .c } = get_structure();
// a and c are single-assignment; b is multi-assignment
b += 1; // OK — b is mut
// a += 1; — translation failure: a is single-assignment

let .{ x, mut y, z } = get_triple();
y += 1; // OK — y is mut

// Per-binding mut with refutable patterns
let verdict::Pass(.{ a, mut b }) = try_get_pair() else { return; };
b += 1; // OK — b is mut

// Every binding of a pattern carries its own mut
let verdict::Pass(.{ mut a, mut b }) = try_get_pair() else { return; };
a += 1; // OK
b += 1; // OK
```

### 5.10.4 Refutability

#### Static semantics

A pattern is **irrefutable** if it matches every possible value of the matched type. A pattern is **refutable** if there exists at least one value of the matched type that the pattern does not match.

Refutability determines whether a `let` declaration requires an `else` clause, as defined in the subclause on the `else` clause.

The following patterns are irrefutable for any type:

— An identifier pattern, with or without `mut`.

The following patterns are irrefutable when their sub-components are irrefutable:

— A struct pattern in which every field sub-pattern is irrefutable, whether or not the pattern ends with `...`.

— A binding pattern `name @ sub` where `sub` is irrefutable.

— An or-pattern `p | q` where at least one of `p` or `q` is irrefutable.

The following patterns are always refutable:

— Literal patterns.

— Range patterns.

— String literal patterns.

— Variable-length slice patterns containing `...` and at least one other element pattern — refutable due to minimum length or element mismatch.

A variant pattern is irrefutable where the variant covers every value of the matched type, and refutable otherwise.

A `wild` pattern is irrefutable where the matched type declares no variant, and refutable otherwise.

**Fixed-length slice patterns** contain no `...`. They are irrefutable when the matched type is an array of type `[T; N]` or a reference of type `&[T; N]`, `N` is determined at translation time, and the pattern length equals `N`. They are refutable otherwise.

Against a slice reference (`&[T]`), the sole irrefutable slice pattern is `[...]` — it matches every slice regardless of length or content.

## 5.11 `with` clauses

A `with` clause attaches behavioural properties to a declaration. It appears after the declaration’s core syntax and before the body where one is present.

### Syntax

```
with_single  = "with", ws, with_item ;
with_braced  = "with", ws, '{', ws, with_item, ws,
               { ',', ws, with_item, ws }, [ ',', ws ], '}' ;
with_item    = with_word, [ ws, with_body ] ;
with_word    = ? a keyword or contextual word defined in subsequent
                 clauses ? ;
with_body    = ? keyword-specific syntax, defined per keyword ? ;
```

### Static semantics

A `with` clause takes one of two forms:

— **Single-item form** (`with_single`) — `with word` or `with word(...)` or `with word { ... }`: attaches exactly one property. The form itself does not include a terminating semicolon. The enclosing declaration’s grammar determines whether a semicolon or body block follows.

— **Braced form** (`with_braced`) — `with { k1, k2, ... }`: attaches one or more properties in a single clause. A trailing comma is permitted. The closing brace terminates the clause.

The two forms are interchangeable when only one item is present. The braced form is required when two or more properties are attached to the same declaration.

`with` clauses are part of the declaration in which they appear and are evaluated at translation time. The syntax and semantics of each `with` word are defined in the clause where that word is introduced. The `with` words defined by this specification are:

— `destruct` — attaches a destructor block (clause on references and resource management).

— `inv` — declares the inverted pair of a contract type (clause on statements and control flow).

— `repr` — controls representation (clause on types).

— `discrim` — sets the discriminant type of an enum (clause on types).

— `align` — sets minimum alignment (clause on types).

— `variadic` — declares a variadic state type (clause on types).

### Constraints

A declaration shall carry at most one `with` clause; all properties are collected into it, using `with_braced` when more than one is needed. Within a braced clause, each word shall appear at most once. A `with` word shall appear only on the declaration kinds for which it is defined. `with destruct` shall appear only on `struct`, `enum`, and `contract` declarations.

### Examples (informative)

```
// with_single form
struct handle { fd: si4 } with destruct { close(self.fd); };

// with_braced form
struct packet {
    header: ui4,
    payload: &[ui1]
} with {
    repr(pack(1)),
    align(4)
}

// contract type with inverted pair
contract result.[T, F] {
    Pass(T) = 1,
    Fail(F) = wild(0)
} with {
    inv -> selftype.[F, T],
    discrim(ui1)
}
```

## 5.12 Visibility and name introduction

### 5.12.1 Visibility modifier

#### Syntax

```
visibility_modifier = "pub" ;
```

#### Static semantics

A declaration marked `pub` is visible to importers. A declaration without `pub` is private to its defining module.

The visibility of items inside an `impl` block is defined in the clause on protocols and implementations. The visibility of `#add` declarations and module members is defined in the clause on programme structure and translation.

### 5.12.2 Unqualified name introduction

#### Syntax

```
use_declaration = [ "pub", ws ], "use", ws, use_tree, ws, ';' ;
use_tree        = single_path, [ ws, "as", ws, identifier ]
                | single_path, ws, '::', ws, '*'
                | single_path, ws, '::', ws, '{', ws, use_tree, ws,
                  { ',', ws, use_tree, ws }, [ ',', ws ], '}' ;
```

#### Static semantics

Each `use_tree` selects one or more named items and introduces names for them into the enclosing scope. Resolution of an introduced name yields the selected item. The introduced name is visible from the `use` declaration to the end of the enclosing scope.

A `use_tree` consisting of a `single_path` selects the item denoted by the path. Its introduced name is the final identifier of the path. When an `as` clause is present, the identifier of the clause is its introduced name.

In a braced `use_tree`, the path preceding `::{` is prepended to the path of each enclosed `use_tree`. This rule applies recursively to each nested braced `use_tree`.

A `use_tree` ending in `::*` selects the accessible direct members of the namespace denoted by the preceding path.

The visibility modifier of a `use_declaration` applies to every name introduced by the declaration.

#### Constraints

— Each path selecting an item shall resolve to a named item.

— Each path preceding `::{` or `::*` shall resolve to a namespace.

— Each introduced identifier shall differ from every other identifier declared or introduced in the enclosing scope, subject to the duplicate-declaration rules defined in the subclause on duplicate declarations.

— Each item selected by a `pub use` declaration shall be visible to importers of the source unit containing its declaration.

#### Examples (informative)

```
use math::sqrt;
let r = sqrt(2.0); // unqualified access

use io::{ read, write, close }; // multi-import

use collections::map as dictionary;

#add "bool.kr" as booleans;
use booleans::*;

pub use root::{
    branch::leaf,
    nested::{
        item as renamed,
        children::*
    }
};
```

### 5.12.3 Named items

#### Static semantics

The named items of a `use_tree` include enum variants, associated constants, and associated subroutines. Enum variants include unit, unnamed-field, and named-field variants.

#### Examples (informative)

```
use colour::Red;
use colour::{ Green, Blue };
// Red, Green, Blue may be used without the colour:: prefix.

let c = Red; // equivalent to colour::Red

// Associated constant
use si4::MAX; // imports the associated constant si4::MAX
let m = MAX;  // equivalent to si4::MAX

// Associated subroutine
use vec::new;  // imports the associated subroutine vec::new
let v = new(); // equivalent to vec::new()
```

## 5.13 Top-level `asm`

A **top-level `asm` block** appears at source unit scope, outside any subroutine. It embeds execution environment instructions directly into the translation unit, defining symbols that participate in external resolution. Top-level `asm` is the declaration-level counterpart of inline `asm`, defined in the clause on expressions.

### Syntax

```
top_level_asm = "asm", ws, asm_body ;
```

### Static semantics

Top-level `asm` blocks are implicitly airside. The `asm_body` production, its two forms, and the rules that fix where the instruction text ends are defined in the clause on expressions.

The following restrictions distinguish top-level `asm` from inline `asm`:

— A `with` clause shall not appear.

— Only inline `xlat` expressions (`'(expr)`) may be used to inject translation-time values into the instruction text.

— Symbol definition — a top-level `asm` block may define external symbols via implementation-defined directives. The resulting symbols participate in external resolution in the same manner as symbols produced by `extern` declarations.

A top-level `asm` block is a σ operation.

### Constraints

A `'expr` expression within a top-level `asm` block shall be evaluable at translation time. Using an execution-time value shall not appear.

### Implementation defined

The syntax of instruction text, implementation-defined directives, and the set of supported execution environments for top-level `asm` are implementation defined. A conforming implementation shall document the supported syntax of instruction text for each execution environment.

### Examples (informative)

```
const STACK_SIZE: uaddr = 4096 * 4;

asm {
    .section .bss
    .align 16
    stack_bottom:
        .skip '( STACK_SIZE )
    stack_top:
}

asm {
    .global _start
    _start:
        call main
}
```

## 5.14 `#inline` and `#no_inline`

The `#inline` and `#no_inline` directives control whether the implementation substitutes a subroutine’s body at each invocation site.

### Syntax

```
inline_directive    = '#inline' ;
no_inline_directive = '#no_inline' ;
```

Either directive is written immediately before the `fn` keyword (or before `pub` or `airside`, if present) of the subroutine declaration to which it applies.

### Static semantics

Where `#inline` is applied, the implementation should replace each invocation of the annotated subroutine with a copy of its body at the invocation site. A conforming implementation shall not reject a programme solely because an `#inline` directive could not be honoured.

Where `#no_inline` is applied, the implementation shall not replace an invocation of the annotated subroutine with a copy of its body. The subroutine shall be emitted as a discrete invocable entity in the opaque code, and every invocation to it shall be emitted as an invocation instruction.

`#inline` and `#no_inline` may be applied to any subroutine declaration, including `airside fn`, methods within `impl` blocks, and protocol default methods.

### Constraints

`#inline` and `#no_inline` shall not both appear on the same subroutine declaration.

`#inline` and `#no_inline` shall not be applied to subroutine prototypes (declarations without a body), `static` declarations, `const` declarations, or type declarations.

### Examples (informative)

```
#inline
fn fast_abs(x: si4) -> si4 {
    return if x < 0 then -x else x;
}

#no_inline
fn cold_path(err: error_code) -> ! {
    log_error(err);
    trap();
}

// #no_inline on a hook point — external tools may patch this symbol
#no_inline
extern fn trace_entry(id: ui4) {
    // body may be empty; the symbol shall exist as an invocable entity
}

#inline
impl counter {
    pub fn get(&self) -> uaddr { return (*self).val; }
}
```

### Design rationale (informative)

The circumstances in which an implementation declines `#inline` include a recursive invocation at the site, an indirect invocation, a code-size constraint of the execution environment, and a body unavailable in the current translation unit.

`#inline` is a best-effort recommendation, whereas `#no_inline` is a requirement, because disregarding `#no_inline` can impair correctness. Failure to honour `#inline` affects performance alone. A programme can depend on a subroutine remaining a discrete symbol for interposition by external tooling, debugger breakpoints, or preservation of constant-time code. Disregarding `#no_inline` can therefore cause malfunction that no diagnostic can detect.

## 5.15 Symbol identification

The `#symbol` directive overrides the logical external name of a declaration with an identification string. A Kurt declaration is thereby identified, in the opaque code and at symbol resolution, by a name that differs from its Kurt identifier.

### Syntax

```
symbol_directive = '#symbol', ws, string_literal ;
```

The `#symbol` directive is written immediately before the declaration to which it applies. The string literal specifies the external identification; its content is opaque to this specification and is passed through without transformation.

### Static semantics

`#symbol` may be applied to any declaration that carries the `extern` prefix, and to any `dyn_item` (subroutine or static) declared inside a `#dyn` block. When `#symbol` is present, it overrides the logical external name that would otherwise be derived from the declaration’s identifier. The overridden name is the content of the string literal. The implementation shall use this overridden name — not the Kurt identifier — as the external identification.

Outside a `#dyn` block, `extern` provides the preservation and invocation interface semantics that `#symbol` supplements; inside a `#dyn` block, the block itself supplies external resolution and `extern` is not required. `#symbol` may be applied to subroutine declarations and `static` declarations.

### Constraints

`#symbol` applied to a declaration that carries neither `extern` nor membership in a `#dyn` block shall not appear.

`#symbol` shall not be applied to `let`, `const`, type declarations, or `impl` blocks.

A translation unit shall not define two external symbols bearing the same external name.

### Implementation defined

The interpretation of the string literal is implementation defined. A conforming implementation shall document how `#symbol` strings are interpreted for each supported environment.

### Examples (informative)

```
// The Kurt subroutine kurt_compress is exported as “compress”
#symbol "compress"
extern fn kurt_compress(src: &[ui1], dst: $[ui1])
    -> verdict.[uaddr, void] {
    ...
}

// The Kurt static is exported as “global_state”
#symbol "global_state"
extern static mut state: app_state = default();

// #symbol outside #dyn and without extern — translation failure
// #symbol "foo"
// fn bar() { } // translation failure: extern or #dyn required
```

## 5.16 Informative annotations

An annotation attaches implementation-specific metadata to a declaration. Annotations carry no normative force under this specification.

### Syntax

```
annotation         = '#[', annotation_content, ']#' ;
annotation_content = ? implementation defined ? ;
```

An annotation is written immediately before the declaration to which it applies. Multiple annotations may appear on the same declaration; they are processed in source order. The content between `#[` and `]#` is a sequence of tokens whose structure and interpretation are entirely implementation defined. This specification imposes no grammar on the annotation content. The annotation opening and closing tokens are defined in the clause on lexical structure.

### Static semantics

An annotation is opaque to this specification. A conforming implementation may assign implementation-defined meaning to specific annotations, including but not limited to: optimization hints, diagnostic control, documentation metadata, and static-analysis markers. The implementation shall document the set of annotations it recognizes and the semantics it assigns to each.

An annotation that the implementation does not recognize has no effect.

Annotations shall not alter the normative semantics of the programme as defined by this specification.

### Constraints

Annotations may be applied to subroutine declarations, type declarations (struct, enum, alias), `const` declarations, `static` declarations, and `impl` blocks. Applying an annotation to a `let` declaration, to a struct field, or to an enum variant shall not occur.

An unbalanced `#[` without a matching `]#` shall not appear.

### Examples (informative)

```
#[deprecated "use fast_foo instead"]#
pub fn slow_foo(x: si4) -> si4 { ... }

#[cfg target = "aarch64"]#
fn neon_memcpy(dst: %mut ui1, src: %ui1, len: uaddr) { ... }

#[test]#
fn test_addition() {
    let r = add(2, 3);
    assert(r == 5);
}
```

## 5.17 Duplicate declarations

This subclause governs the uniqueness of names within a scope and the interaction of declarations in nested scopes.

### Static semantics

A declaration in an inner scope **hides** a declaration of the same name in an outer scope. The inner declaration introduces a distinct named item; for the duration of the inner scope, the name denotes the inner item. After the inner scope exits, the outer declaration is visible.

For `impl` blocks, the uniqueness of protocol implementations and the resolution of item name overlap are defined in the clause on protocols and implementations.

### Constraints

Within a single scope, a name shall be declared at most once. This rule applies uniformly to all declaration forms: `fn`, `let`, `const`, `static`, `struct`, `enum`, `type` (alias), `protocol`, and `impl` associated items.

### Examples (informative)

```
// Hiding in an inner scope — distinct binding, may share a name
let x: si4 = 1;
{
    // hides outer x — distinct binding, different type
    let x: fe11s52 = 2.0;
    use_float(x); // x is fe11s52 here
}                 // inner x destroyed; outer x visible again
use_int(x);       // x is si4 here, value 1

// Duplicate in the same scope — translation failure
// let y = 1;
// let y = 2; // translation failure: y already declared in this scope
```
