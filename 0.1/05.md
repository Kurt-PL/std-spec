# 5. Types

This clause defines the built-in types of the Kurt programming language, the layout of composite types, and type inference.

## 5.1 Type classification

### Syntax

```
type = single_path
     | array_type
     | anon_struct_type
     | ref_type
     | slice_reference
     | subroutine_pointer_type
     | protocol_type
     | inferred_type ;
```

`single_path` is defined in §6.2.1. `ref_type` and `slice_reference` are defined in §8.1 and §8.2.5. `protocol_type` is defined in §9.6.

### Static semantics

Each type of the Kurt programming language is either a built-in type or a declared type.

**Built-in types** are the types that this specification defines.

**Declared types** are types introduced by `struct` (§4.7), `enum` (§4.8), and `contract` (§7.2) declarations in the programme.

### Constraints

A `single_path` that is a `type` shall denote a type.

### Implementation requirements

The implementation shall not realize a built-in type by introducing a declaration or any other source text into the programme.

## 5.2 Size and alignment

### Static semantics

The following values are parameters of a machine:

<table>
<thead><tr><th>Parameter</th><th>Meaning</th><th>Constraint</th></tr></thead>
<tbody>
<tr><td>Cell width</td><td>Bits per cell</td><td>&gt; 0</td></tr>
<tr><td>Address width</td><td>Bit width of <code>uaddr</code> and <code>saddr</code></td><td>Defined by the environment of the machine; &gt; 0</td></tr>
<tr><td>Reference width</td><td>Bit width of <code>%void</code> and of subroutine pointers</td><td>Defined by the environment of the machine; shall be at least the address width</td></tr>
</tbody>
</table>

For every type with non-zero size, `T'align` is a power of two and divides `T'size`. A type whose size is zero has alignment zero unless another rule of this clause fixes its alignment.

For a closed type (§4.10) satisfying `numeric`, a reference type other than a wide reference (§8.2.2), and a subroutine pointer type, `T'align == T'size`, and the size derives from the type’s **bit width** *W*<sub>t</sub>:

`T'size` = 2<sup><span class="ceil">⌈&thinsp;log<sub>2</sub> <span class="ceil">⌈&thinsp;*W*<sub>t</sub> / `cellbits`&thinsp;⌉</span>&thinsp;⌉</span></sup>

Where `T'size` × `cellbits` is greater than *W*<sub>t</sub>, the interpretation of the type takes each value from *W*<sub>t</sub> bits alone; which bits those are is implementation defined.

For a closed type satisfying `numeric`, *W*<sub>t</sub> is the width defined in §5.3 or §5.4. For a reference type other than a wide reference, and for a subroutine pointer type, *W*<sub>t</sub> is the reference width.

The number of cells of the τ of each machine is two raised to its address width.

### Constraints

For each type, where a construct analysed on a machine uses its layout, or has, on that machine, that type or a type in which it occurs, the size of that type on that machine, computed over the non-negative integers, shall belong to the value set (§2.2.3) of `uaddr` on that machine.

### Implementation requirements

The implementation shall document the values of all three parameters for each supported environment of the programme machine and of the translation machine. The reference width shall be sufficient for a subroutine pointer to designate each subroutine of the programme in that environment.

### Implementation defined

Where `T'size` × `cellbits` is greater than *W*<sub>t</sub>, the Γ sequence that a store places for a value, among those that represent it, is implementation defined.

### Design rationale (informative)

An alignment greater than a value requires is sound in every environment, and no environment requires more than the number of cells the value occupies. `T'align == T'size` is therefore sound without this specification stating the requirement of each environment. `pack(N)` gives up the resulting padding cells where the programme states its target’s requirement.

The suffix numeral of an integer type name denotes a power-of-two multiple of `cellbits`, and each floating radix point number type has a bit width that is a power of two, so <span class="ceil">⌈&thinsp;*W*<sub>t</sub> / `cellbits`&thinsp;⌉</span> is a power of two whenever `cellbits` divides *W*<sub>t</sub>. Rounding `T'size` up to a power of two keeps the alignment rule satisfied in every machine, including one whose cell width does not divide *W*<sub>t</sub>.

## 5.3 Integer types

### Static semantics

An **unsigned** integer type uses pure binary encoding. The value of a *W*<sub>t</sub>-bit unsigned integer with bits *b*<sub>*W*<sub>t</sub>&minus;1</sub>, …, *b*<sub>0</sub> is <span class="sum">∑<sub>*k*=0</sub><sup>*W*<sub>t</sub>&minus;1</sup></span> *b*<sub>*k*</sub> × 2<sup>*k*</sup>.

A **signed** integer type uses two’s complement encoding. The value of a *W*<sub>t</sub>-bit signed integer with bits *b*<sub>*W*<sub>t</sub>&minus;1</sub>, …, *b*<sub>0</sub> is &minus;*b*<sub>*W*<sub>t</sub>&minus;1</sub> × 2<sup>*W*<sub>t</sub>&minus;1</sup> + <span class="sum">∑<sub>*k*=0</sub><sup>*W*<sub>t</sub>&minus;2</sup></span> *b*<sub>*k*</sub> × 2<sup>*k*</sup>. Bit *W*<sub>t</sub>&minus;1 is the **sign bit**.

### 5.3.1 Cell width

#### Syntax

```
cellbits_expr = "cellbits",
                [ ws, '::', ws, ( 'prog' | "xlat" | "arbit" ) ] ;
```

#### Static semantics

Under the rules for type inference, synthesis of a `cellbits` expression is undetermined. Its default type is `uaddr`.

`cellbits` has three **qualified forms**.

`cellbits::prog` evaluates to the cell width (§2.2.1) of the programme machine, `cellbits::xlat` to that of the translation machine, and `cellbits::arbit` to that of the arbiter machine.

The unqualified `cellbits` evaluates to the cell width of the machine on which the evaluation takes place.

The value sets of the integer types other than `uaddr` and `saddr` in an evaluation are determined by the value to which the unqualified `cellbits` evaluates in that evaluation.

#### Constraints

The value of a `cellbits` expression shall fit in its type.

Where `cellbits == 8`, `ui1` is 8-bit and `ui4` is 32-bit. Where `cellbits == 16`, `ui1` is 16-bit and `ui4` is 64-bit.

## 5.4 Floating radix point number types

Arithmetic on a floating radix point number type conforms to ISO/IEC 60559:2020 where this clause does not state otherwise.

### Static semantics

A **floating radix point number type** divides its *W*<sub>t</sub> bits into three adjacent fields, from the position of greatest weight to the position of least weight: the sign bit, the **exponent field**, and the **significand field**. A value of such a type is a **floating radix point number**.

The floating radix point number types are those the following table names. In each identifier, the numeral after `fe` is the width of the exponent field and the numeral after `s` that of the significand field, and *W*<sub>t</sub> is one more than their sum.

#### Implementation defined

The following are implementation defined for each supported environment of the programme machine and of the translation machine:

&mdash; The rounding mode governing a floating radix point number operation.

&mdash; Whether a machine provides more than one such rounding mode.

&mdash; Where it does, the means by which one is chosen, the range over which a choice remains in effect, and the set of modes among which a choice can be made.

### 5.4.3 Comparison

#### Dynamic semantics

The comparison operators on a floating radix point number type compare by the order that the ISO/IEC 60559:2020 total order predicate defines. Each of the following holds if and only if the condition after it holds:

&mdash; `a > b` &mdash; `b` precedes `a` in this order.

&mdash; `a >= b` &mdash; `a > b` or `a == b`.

&mdash; `a == b` &mdash; `a` and `b` occupy the same position in this order.

&mdash; `a != b` &mdash; `a == b` does not hold.

&mdash; `a <= b` &mdash; `a < b` or `a == b`.

&mdash; `a < b` &mdash; `a` precedes `b`.

### 5.4.4 NaN propagation

#### Dynamic semantics

A signalling NaN operand of `+`, `-`, `*`, `/`, or `%` is treated as a quiet NaN with the same sign for the purpose of the rules below.

Where `+`, `-`, `*`, `/`, or `%` yields NaN, the result is a quiet NaN with residue 0. For `*`, `/`, and `%` its sign is the XOR of the operands’ signs. For `+` and `-` its sign is that of the leading operand, except where the following operand alone is NaN. There it is the sign of the following operand, negated where the operator is `-`.

#### Implementation requirements

The presence of a signalling NaN operand in an arithmetic operation, in a comparison, or in a conversion by `as` shall alter no control flow and shall not invoke the subroutine that `trap` names.

#### Implementation defined

The implementation’s behaviour upon a signalling NaN operand of an arithmetic operation, other than the arithmetic result and control flow, is implementation defined.

## 5.5 `void`

### Static semantics

`void` has size zero. It is in unit form (§4.6), and its sole value is written `void`.

## 5.6 Built-in contract type

### Static semantics

`verdict[T, F]` is the built-in contract type, generic over a success payload type (§7.2) `T` and a failure payload type `F`.

`verdict[T, F]` has exactly two variants, each in unnamed-field form with one field. `Pass`, the success variant, has a field of type `T` and takes the discriminant value 1. `Fail`, the failure variant, has a field of type `F`, covers every other discriminant value, and has the canonical value 0 (§4.8). The discriminant type is `ui1`. `verdict[T, F]` is a contract type with the inverted pair `verdict[F, T]` (§7.2).

### Examples (informative)

```
// The conventional truth-value vocabulary, declared in source
type bool = verdict[void, void];
const true:  bool = verdict::Pass.{ void };
const false: bool = verdict::Fail.{ void };
```

### Notes (informative)

The definition of `verdict[T, F]` is equivalent to the declaration:

```
contract verdict[T, F] {
    Pass { pub T } = 1,
    Fail { pub F } = wild(0)
} with {
    inv -> selftype[F, T],
    discrim(ui1),
    copyable
}
```

## 5.7 Array types

`[T; N]` is an **array type** of length `N`.

### Syntax

```
array_type = '[', ws, type, ws, ';', ws, ( expression | inferred_type ),
             ws, ']' ;
```

### Static semantics

`[T; N]'size == N * T'size`. `[T; N]` places each of its elements at the offset its position, counting from zero, multiplied by `T'size`. Where `N` is not zero, `[T; N]'align == T'align`.

§8.2.5 defines the decay of a reference to `[T; N]` to the corresponding slice reference. It also defines the built-in fields `.ptr` and `.len` that a `[T; N]` value and references to it expose.

## 5.8 Anonymous struct types

### Syntax

```
anon_struct_type = '.', ws, '{', ws, type, ws, { ',', ws, type, ws },
                   [ ',', ws ], '}' ;
```

### Static semantics

An **anonymous struct type** is a built-in type whose fields are named by their index, counting from zero in declaration order (§2.2.6).

## 5.9 References

### Static semantics

A reference type is composed from a tribe and a sequence of modifiers (§8.1).

The stored representation of a slice reference is defined in §8.2.5, and that of a reference to a protocol type in §9.6. For every other reference type the stored representation is one field of the reference width, and §5.2 gives the size and the alignment.

### Implementation defined

What the field of a reference carries besides the address is implementation defined.

## 5.10 Subroutine pointer types

### Syntax

```
subroutine_pointer_type = subroutine_ptr_header, ws,
                          subroutine_proto_param, subroutine_sig_tail ;

subroutine_ptr_header   = [ extern_clause, ws ], [ "variadic", ws ],
                          fn_head, [ ws, generic_clause ] ;
```

The `fn_head`, `subroutine_sig_tail`, and `extern_clause` productions are defined in §4.2.

### Static semantics

A subroutine pointer designates a subroutine. An expression that names a subroutine yields a value of the subroutine pointer type that agrees with that subroutine in each item of the list that defines when two subroutine pointer types are the same type. Where a generic argument list (§4.10) follows an expression that names a subroutine or has a subroutine pointer type, the two form an expression that has the type of the first less its `generic_clause`. Each argument of that list stands in that type in place of the generic parameter it corresponds to.

The permitted conversions involving subroutine pointers are defined in §6.9.7 and §6.9.8.

In a type, the `extern` clause names the invocation interface, the `variadic` keyword selects the variadic form of that interface, and the `airside` keyword states that the subroutine is declared `airside` or within an `#extern` block. The effects each of these has upon a declaration, and the invocation interface of a subroutine that carries no `extern` clause, are defined in §4.2.1, §4.2.2, and §4.2.3.

A subroutine pointer whose type has a `generic_clause` or a subject bound (§9.4.2) designates a subroutine whose signature is lowered as §4.10.2 defines.

A `routes` clause or `with` clause belongs to the outermost subroutine declaration or subroutine pointer type whose return type it follows.

Within a translation unit, two subroutine pointer types are the same type where they agree in each of the following:

&mdash; The routes.

&mdash; The invocation interface.

&mdash; The variadic status.

&mdash; The airside status.

&mdash; The generic parameters, and the bound elements of each, in order.

&mdash; The types of the fixed parameters (§4.2), in order.

&mdash; The return type or `!`.

&mdash; The subject bounds, in order.

In this comparison, the generic parameters of the two at the same position are taken to be the same generic parameter where both are type parameters or both are dependence parameters (§4.10) of the same type.

### Constraints

The `with` clause of a subroutine pointer type shall contain only subject bounds. A subroutine pointer type in a type position shall be a closed type. An expression that ends in a generic argument list after an expression that names a generic subroutine or has a subroutine pointer type shall appear only as the leading expression of a subroutine invocation. An expression that names an implanted subroutine whose lowered signature carries a `selftype` level or the generic parameters of an enclosing declaration shall also appear only there.

### Design rationale (informative)

The type of a subroutine pointer alone fixes how the designated subroutine is invoked, and a generic parameter occurring free in that type would leave the invocation varying with a type argument that the subroutine has no means to receive.

### Examples (informative)

```
fn(si4) -> si4                // native (implicit)
extern fn(si4) -> si4         // native (explicit, identifier omitted)
extern(native) fn(si4) -> si4 // native (explicit, identifier present)
```

## 5.11 Composite type representation

### Syntax

```
repr_clause    = 'repr', ws, '(', ws, repr_arg, ws, ')' ;
repr_arg       = pack_scheme | identifier ;
pack_scheme    = 'pack', ws, '(', ws, integer_literal, ws, ')' ;
discrim_clause = 'discrim', ws, '(', ws, single_path, ws, ')' ;
align_clause   = 'align', ws, '(', ws, integer_literal, ws, ')' ;
```

### Static semantics

`repr` determines the placement of the fields of a struct, and of the fields of each variant of a variant type (§4.6). The argument names a layout scheme:

&mdash; `pack(N)` &mdash; each field is placed at the alignment §5.11.3 gives it.

&mdash; `native` &mdash; on each machine, the layout that machine gives the type.

### Constraints

The `discrim` argument shall be a closed type satisfying `integer`, or `void`.

In `pack(N)`, `N` shall be a power of two greater than zero.

A `repr` identifier not among those the implementation documents shall not appear.

`discrim(void)` shall appear only on a variant type whose discriminant type would be `void` were the `with` clause absent.

Where the `discrim` argument satisfies `integer`, all discriminant values shall fit in that type.

### Implementation requirements

The implementation shall support the layout schemes `pack` and `native`.

### Implementation defined

The layout `repr(native)` gives, and any further `repr` identifier and the layout it names, are implementation defined.

### 5.11.1 Composite type layout

#### Static semantics

Unless a `repr` identifier gives the layout of a composite type, Kurt standard alignment (§2.2.5) gives it from a sequence of types. That sequence is:

&mdash; For a struct, the types of its fields in declaration order.

&mdash; For an anonymous struct type, the types of its fields in index order.

&mdash; For a variant type, its discriminant type, followed by its variant payload type (§5.11.2).

Where Kurt standard alignment gives the layout, a struct or an anonymous struct type places each of its fields, and a variant type its discriminant, at the offset Kurt standard alignment assigns the type at the same position in that sequence. For such a composite type `S`, `S'size` and `S'align` are the size and the alignment Kurt standard alignment assigns that sequence.

Where the interpretation of a composite type maps two Γ sequences to one value, the two have the same symbol at each padding cell (§2.2.5) of that value.

Two values of one composite type that differ only at their padding cells hold and carry the same values.

The layout of a type requires each of the following:

&mdash; The layouts of its constituents (§8.7), of the types of its `?` fields and, for an array type, of its element type (§4.10).

&mdash; What each of those layouts requires.

&mdash; The value of each of its dependence arguments, as written where the type is written.

The layout of a reference type or of a subroutine pointer type requires nothing. The value of an expression requires the layout of each type whose layout it, or a construct within it, uses (§4.1).

#### Constraints

The layout of a type shall not require the layout of that type. Where that type is the type a generic declaration introduces with its own generic parameters as the generic arguments, its layout shall not require the layout of another instantiation of that declaration.

#### Implementation requirements

The implementation shall set every bit of every padding cell to zero when a value of a composite type is constructed.

### 5.11.2 Automatic discriminant sizing

#### Static semantics

On each machine on which the declaration of a variant type is analysed, its **discriminant type** is determined by the first of the following that applies:

1. Where `with discrim(T)` is specified, the discriminant type is `T`.
2. Where the type declares zero or one variants and no variant has an explicit discriminant value, the discriminant type is `void`.
3. The unsigned integer type of least bit width whose value set includes all discriminant values under the cell width of that machine is selected. If any discriminant value is negative, the signed integer type of least bit width whose value set includes them is selected instead. Of two such types of equal bit width, the one other than `uaddr` or `saddr` is selected.

A variant type whose discriminant type is `void` has exactly one discriminant value, and that value is zero. The sole declared variant takes it where one is declared, and the implicit wild variant (§4.8) covers it where none is.

Where Kurt standard alignment gives the layout of a variant type, the variant type places the fields of each variant where a struct of the same fields and the same `repr` places them, advanced by the offset that Kurt standard alignment assigns the variant payload type of the variant type. The **variant payload type** of a variant type is the type whose alignment is the greatest of zero and the alignments of the structs that place the fields of its variants, and whose size is the greatest of zero and the sizes of those structs, rounded up to a multiple of that alignment.

#### Constraints

A variant type whose discriminant values no value set of an integer type includes under the cell width of a machine on which its declaration is analysed shall not appear.

#### Examples (informative)

These examples apply where `cellbits::prog == 8`.

```
// 1 variant → void discriminant
enum unit { only }
// 3 variants → ui1 discriminant
enum colour { red, green, blue }
// value 2006 → ui2 discriminant
enum year_tag { y2006 = 2006 }
// negative → si4 discriminant
enum offset { neg = -19700101 }
// forced to ui4
enum forced { lo, hi } with discrim(ui4);

// translation failure: -72 is outside the value set of ui1
// enum error { lo = -72 } with discrim(ui1);

// translation failure: discrim(void) with two variants
// enum bad { lo, hi } with discrim(void);
```

### 5.11.3 `with repr(pack(N))`

#### Static semantics

Under `with repr(pack(N))`, the alignment Kurt standard alignment uses for each field that `repr` places is the lesser of the field type’s alignment and `N`.

### 5.11.4 `with align(N)`

#### Static semantics

The alignment of a type that carries `align(N)` is the greater of `N` and the alignment the type would have were the clause absent, and the type’s size is rounded up to a multiple of the alignment.

#### Constraints

`N` shall be a power of two greater than zero.

#### Examples (informative)

```
struct packet {
    header: ui4,
    seq: ui4,
    payload: &[ui1]
} with {
    repr(pack(1)),
    align(4)
}
```

### 5.11.5 `with variadic`

#### Static semantics

A struct declared `with variadic` serves as the state object for variadic argument iteration, and the implementation supplies the destructor of the type.

#### Constraints

Where a construct uses the layout of a `with variadic` type on a machine, the size of that type on that machine shall equal the size of the native variadic state object of that machine.

#### Implementation defined

For each machine, the layout of the type of its native variadic state object, the means by which a `with variadic` type reaches the arguments it holds, and the conversions a variadic argument undergoes on it are implementation defined.

#### Examples (informative)

```
// AArch64 AAPCS64: type definition
struct va_list {
    pub airside __stack:   %void,
    pub airside __gr_top:  %void,
    pub airside __vr_top:  %void,
    pub airside __gr_offs: si4,
    pub airside __vr_offs: si4,
} with variadic;

// AArch64 AAPCS64: iteration impl
impl va_list {
    pub airside fn next_int[T: integer]($mut self) -> T {
        if self.__gr_offs < 0 {
            let offs = self.__gr_offs;
            self.__gr_offs = offs + 8;
            if offs + 8 <= 0 {
                let addr = self.__gr_top as uaddr + offs as uaddr;
                return *(addr as %ui8) as T;
            }
        }

        let addr = self.__stack;
        self.__stack = ((addr as uaddr) + 8) as %void;
        return *(addr as %T);
    }

    pub airside fn copy(&self) -> selftype {
        return *(self as %selftype);
    }
}
```

## 5.12 Type inference and the inferred type `?`

### Syntax

```
inferred_type = '?' ;
```

### Static semantics

An **inferred type** is an occurrence of `inferred_type`. Its meaning is given by the following, according to where it appears:

&mdash; The type annotation of a `let`, `const`, or `static` declaration, or of an implanted constant that appears directly in an `impl` block &mdash; that declaration is equivalent to the same declaration with the annotation omitted.

&mdash; An argument of an instantiation or of a generic argument list &mdash; it is an omitted argument.

&mdash; Any other inferred type that gives the type of an expression within which it lies &mdash; it is the type that the rules of this subclause determine for that expression.

A declaration with an initializer or expression and no type annotation has the type the rules of this subclause determine for that initializer or expression.

Where a `let` declaration has no initializer, the matched type (§4.11) of its pattern is its type annotation, where present. Otherwise it is the following:

&mdash; For a composite pattern &mdash; the type its path denotes, or the variant type that declares the variant its path denotes.

&mdash; For an anonymous struct pattern &mdash; the anonymous struct type whose element types are the matched types of its element patterns.

&mdash; For an identifier pattern &mdash; the type of its binding.

Where no enclosing pattern gives a binding a type, it **draws on** each such binding that an identifier expression names in the following operand of a simple assignment whose leading operand is an identifier expression naming it. It also draws on each binding that a binding it draws on draws on. It, together with each binding that both draws on it and is drawn on by it, forms its **group**. Its type is the common type of the following operands of the simple assignments whose leading operand is an identifier expression naming a binding of its group, other than those operands in which an identifier expression naming a binding of its group occurs. Where there is no such operand, synthesis of that type is undetermined, and its default type is `void`.

The type of a construct is determined by **synthesis** or by **checking**. Synthesis derives the type from the construct itself. Checking adopts an **expected type** that one of the following supplies:

&mdash; A type annotation.

&mdash; A type to which this specification requires the type of the construct to be assignable (§6.8).

&mdash; The type that an implanted constant a protocol `impl` block provides shall bear.

&mdash; An operation.

&mdash; A use site of the name that the construct’s declaration introduces.

&mdash; The expected type of an enclosing expression, or the type at a position within it, where this specification gives the type at that position within the type of that enclosing expression as the type of the construct or as the common type of a set of expressions that includes the construct.

Where more than one of these applies, checking determines the type on which those that determine one agree, and determines none where none of them determines one. Where those that determine a type do not all determine the same one, the construct shall not appear.

If synthesis determines a type and checking determines a type to which it is assignable, the construct has the type that checking determines. If exactly one determines a type, the construct has that type. If neither determines a type and the form of the construct defines a default type, the construct has that type. Otherwise, the construct shall not appear.

The **common type** of a set of expressions is the one type that each of them has, disregarding those that are jumps or diverging expressions (§7.11). Where the set is not empty and each of them is so disregarded, the requirement of a common type is satisfied, synthesis of that common type is undetermined, and its default type is `void`.

Where the rules of an operation, a cast included, admit exactly one type that an undetermined operand can have, given the types determined for its other operands and for its result, that type is the expected type of the operand.

A path that omits the generic arguments of a generic declaration, where this specification takes from it an instantiation of that declaration, stands for the same path with those arguments written. An invocation that omits the generic arguments called for by the `generic_clause` of the type of its leading expression, or of the method (§9.2) it resolves to, stands for the same invocation with those arguments written.

For the rules of this subclause, a local item that appears in a block, and each construct within it, lies within no construct other than one that is, or lies within, that item. The omitted arguments within one expression, `const` or `static` declaration, or implanted constant are found together, from the following pairs of types that arise within it:

1. For each expression whose expected type is or contains an omitted argument &mdash; that expected type and the synthesized type of the expression.

2. For each composite pattern whose path contains an omitted argument &mdash; the matched type and the type that the path denotes or whose variant it denotes.

3. For an omitted argument that items 1 and 2 leave unfound &mdash; for each expression that has an expected type and whose synthesized type is or contains that omitted argument, that expected type and the synthesized type with the arguments already found in place.

The two types of a pair correspond. Where two corresponding types are instantiations of one generic declaration, their arguments in the same place correspond as well. Two types or dependence arguments (§4.10) are the **same argument** where they are one of the following:

&mdash; Two instantiations of one generic declaration whose arguments in each place are the same argument.

&mdash; Two types that are the same type and are not both instantiations of one generic declaration.

&mdash; Two dependence arguments that have the same value in semantic analysis (§10.2).

&mdash; Two identifier expressions that name the same dependence parameter.

Of the types and arguments that correspond to an omitted argument within an expression, a `const` or `static` declaration, or an implanted constant, those that neither are nor contain an omitted argument not already found remain. The omitted argument is found where at least one remains and, with the arguments already found in place, all that remain are the same argument. The omitted argument is then that argument.

### Constraints

An inferred type shall appear only in a position listed above.

A declaration whose pattern has no matched type shall not appear.

Every omitted argument shall be found. With the found arguments in place, each type or argument that corresponds to an omitted argument shall be the same argument as the one found for it.

### Examples (informative)

```
let n      = 42; // neither synthesis nor checking: default saddr
let m: si4 = 42; // checking: literal takes si4

// T and F found from the expected type; 42 takes T
let v: verdict[si4, si4] = verdict::Pass.{ 42 };

// T found from the type of the argument, no explicit
// argument needed
let r = identity(m); // identity[T](x: T) -> T  →  T = si4

// T appears only in the return type: found from the
// expected type
let d: si4 = default_value();

// no expected type: explicit argument mandatory
let e = default_value[si4]();

// expected type propagates to both branches
let w: colour = if cond then colour::red else colour::green;

// operator operand: the unconstrained operand takes the type of
// the other operand
let big: uaddr = 4096;
let half = big / 2; // 2 takes uaddr

// the expected type reaches both operands of the shift
// through its result
let mask: ui4 = 1 << 5; // 1 and 5 both take ui4

// use-site resolution: i takes uaddr from a.len and a.ptr
fn f(a: &[ui1]) {
    let mut i = 0;          // default would be saddr
    while a.len > i {       // a.len is uaddr → i is uaddr
        consume(a.ptr + i); // i is uaddr here too
    } and then { i += 1; }
}
```
