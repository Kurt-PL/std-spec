# 5. Declarations

This clause defines the declarations of the Kurt programming language: subroutines, bindings, composite types, generics, patterns, `with` clauses, visibility, and the prefixes an item may carry.

## 5.1 Items

A **declaration** introduces a name into a scope. A **definition** does so and determines the contents of what it names.

### Syntax

```
item        = { item_prefix, ws }, ( global_item | local_item ) ;

item_prefix = annotation
            | symbol_directive
            | inline_directive
            | no_inline_directive ;

global_item = module_decl
            | impl_block
            | protocol_decl
            | global_instruct ;

local_item  = subroutine_def
            | const_decl
            | static_decl
            | struct_decl
            | enum_decl
            | contract_decl
            | type_alias_decl
            | use_decl
            | add_decl
            | path_decl
            | dyn_decl
            | trap_handler_decl ;
```

A **global item** appears in a source unit or in a module body. A **local item** appears in a source unit, in a module body, or in a block. The block is defined in the clause on statements and control flow, and the source unit and the module body in the clause on programme structure and translation.

An **item prefix** stands upon an item.

`module_decl`, `add_decl`, `path_decl`, and `dyn_decl` are defined in the clause on programme structure and translation. `impl_block` and `protocol_decl` are defined in the clause on protocols and implementations. `contract_decl` and `trap_handler_decl` are defined in the clause on statements and control flow. Every other item is defined in this clause.

### Constraints

An item prefix other than an annotation shall stand at most once upon what it prefixes. An annotation may stand upon what it prefixes any number of times.

A local item that appears in a block shall satisfy each of the following:

&mdash; It refers to no binding whose object is an automatic object and that is declared outside the item.

&mdash; No generic parameter, other than one of the item or of a construct within it, occurs free in a type or an expression that is, or lies within, it.

&mdash; It names no protocol item of an enclosing protocol, or of a protocol that the bound list of an enclosing protocol names, by its identifier alone other than as the method of a method invocation.

## 5.2 Subroutine declarations

### Syntax

```
(* Shared productions *)
extern_clause     = "extern", [ ws, '(', ws, identifier, ws, ')' ] ;
variadic_clause   = "variadic", ws, '(', ws, identifier, ws, ':', ws,
                    type, ws, ')' ;
subroutine_return = '->', ws, ( type | '!' ) ;

(* Headers *)
subroutine_def_header   = [ "pub", ws ], [ extern_clause, ws ],
                          [ variadic_clause, ws ], [ "airside", ws ],
                          "fn", ws, identifier, [ ws, generic_clause ] ;

subroutine_proto_header = [ "pub", ws ], [ extern_clause, ws ],
                          [ "variadic", ws ], [ "airside", ws ],
                          "fn", ws, identifier, [ ws, generic_clause ] ;

(* Parameter lists *)
subroutine_def_param   = '(', ws, [ parameter_list ], ws, ')' ;
subroutine_proto_param = '(', ws, [ proto_parameter_list ], ws, ')' ;

parameter_list = parameter, ws, { ',', ws, parameter, ws },
                 [ ',', ws ] ;
parameter      = [ "mut", ws ], identifier, ws, ':', ws, type ;

proto_parameter_list = proto_parameter, ws,
                       { ',', ws, proto_parameter, ws }, [ ',', ws ] ;
proto_parameter      = [ "mut", ws ], [ identifier, ws, ':', ws ],
                       type ;

(* Definition form: parameter names mandatory *)
subroutine_def = subroutine_def_header, ws, subroutine_def_param,
                 [ ws, subroutine_return ],
                 [ ws, routes_clause ],
                 [ ws, with_single | ws, with_curly ], ws, block ;
```

The `generic_clause` production is defined in the subclause on generic declarations.

### Static semantics

A subroutine definition introduces a named subroutine into the enclosing scope and supplies its operations. Every subroutine has an invocation interface. It is `native` unless an `extern` clause names another, as the subclause on external declaration defines.

A **subroutine prototype** states the name, the parameters, and the return type of a subroutine. It appears only in a `#dyn` block, as defined in the clause on programme structure and translation, or in a protocol body, as defined in the clause on protocols and implementations.

If `-> T` is omitted, the return type is `void`.

`mut` on a parameter governs the parameter binding alone.

### Dynamic semantics

When a subroutine is invoked, execution proceeds as follows:

1. Argument evaluation &mdash; each argument expression is evaluated in the order defined in the subclause on subroutine invocation.
2. Body evaluation &mdash; the body is evaluated.
3. Value return &mdash; the return value is copied or transferred to the invoker.
4. Local destruction &mdash; control exits, innermost first, each master and each scope of the invocation that it has not exited, as the clause on semantics defines.

### Constraints

Where a subroutine definition or the definition of an associated subroutine declares `-> !`, or declares a return type other than `void`, the programme point at the end of its body shall be unreachable. A subroutine declaring `-> !` shall not return control to its invoker. Such a violation, where not detected during translation, can cause indeterminate state.

### Examples (informative)

```
fn add(a: si4, b: si4) -> si4 { return a + b; }
fn diverge() -> ! { trap(); }
fn unit() { } // returns void

// mut parameter: the parameter binding is multi-assignment
fn zero_and_sum(mut buf: [si4; 4]) -> si4 {
    let mut total: si4 = 0;
    let mut i = 0;

    while i < 4 {
        total += *buf.at(i);
        *buf.at_xcl(i) = 0;
    } and then { i += 1; }

    return total;
}

// Direct recursion
fn factorial(n: uaddr) -> uaddr {
    return if n == 0 then 1 else n * factorial(n - 1);
}
```

### 5.2.1 `airside fn`

#### Static semantics

An invocation of an `airside fn`, or through a subroutine pointer whose type carries the `airside` keyword, requires airside.

### 5.2.2 External declaration

#### Static semantics

A declaration prefixed with `extern` is an **external declaration**. The prefix has the following effects upon the declaration:

&mdash; Name stability &mdash; the external name is the declaration’s identifier, and the implementation shall apply no name transformation to it.

&mdash; Invocation interface &mdash; for subroutine declarations, the parenthesized identifier selects the invocation interface. `native` denotes the native invocation interface of the machine on which an invocation of the subroutine takes place.

A declaration carries an **external name** where it carries `extern` or `#symbol`, or where it appears in a `#dyn` block.

The implementation shall retain in the opaque code an item that is analysed on the programme machine and that lies outside every `#dyn` namespace, in a form invocable or accessible from outside the translation unit, where any of the following holds:

&mdash; The declaration that introduces it carries an external name.

&mdash; The item is a subroutine and an expression names it other than to name the invoked subroutine of an invocation.

&mdash; A descriptor the implementation emits designates it.

A definition that carries neither `extern` nor `#symbol` has an implementation-defined name in the opaque code.

#### Constraints

A parenthesized invocation interface identifier shall not appear on an `extern static` declaration. An identifier not among the invocation interfaces the implementation documents shall not appear.

#### Implementation defined

How an external name is represented in the opaque code is implementation defined.

#### Examples (informative)

```
pub extern fn init() { ... }
pub extern(native) fn init2() { ... } // equivalent to above
pub extern(efi) fn efi_entry(handle: uaddr, table: %ui1)
    -> uaddr { ... }

// extern without pub: kept in opaque code, private to the module
extern fn internal_hook() { ... }

// internal: implementation-defined name
fn helper(x: si4) -> si4 { ... }

pub extern static version: ui4 = 1;
extern static mut hw_state: ui4 = 0; // preserved but private
```

### 5.2.3 Variadic subroutines

A variadic subroutine accepts a variable number of arguments after its fixed parameters.

#### Static semantics

A subroutine declared with a `variadic` clause uses the variadic variant of its invocation interface. The identifier names a binding whose type is the specified `with variadic` type.

#### Dynamic semantics

Upon entry, the implementation performs the argument capture that the variadic variant of the invocation interface requires, and initializes the binding’s object as the interface requires.

#### Constraints

The type named in the `variadic` clause shall satisfy `variadic`.

#### Examples (informative)

```
// Forwarding subroutine
variadic(args: va_list) fn my_printf(fmt: %ui1) -> si4 {
    return my_vprintf(fmt, args);
}

// Iteration within airside
variadic(args: va_list) fn sum_ints(count: si4) -> si4 {
    let mut total: si4 = 0;
    let mut i: si4 = 0;

    while i < count {
        airside { total += args.next_int[si4](); }
    } and then { i += 1; }

    return total;
}

// Indirect invocation through a variadic subroutine pointer
let f: extern variadic fn(%ui1) -> si4 = my_printf;
f(fmt, width, name);
```

## 5.3 Binding declarations

### Syntax

```
let_decl = "let", ws, pattern_body, [ ws, ':', ws, type ],
           [ ws, '=', ws, expression ],
           [ ws, else_bind, ws, block ], ws, ';' ;

else_bind = "else", [ ws, '.', ws, ident_pat ] ;
```

The pattern forms and their refutability are defined in the subclause on patterns and destructuring.

### Static semantics

The **`else` branch** of a construct that carries an `else_bind` is the construct that follows that `else_bind`, and the `ident_pat` of the `else_bind` introduces its name within that branch. In a `let` declaration, an `if let` expression, and a `while` expression of the `while let` form, the type of that name is the type of the expression whose value the pattern is applied to. In every other construct, it is the failure payload type of the expression whose value selects the `else` branch.

A binding is a **multi-assignment binding** where `mut`, other than as a `ref_modifier`, precedes the identifier or `self` by which it is introduced, with no identifier between them, or where a `variadic_clause` introduces it. Every other binding is a **single-assignment binding**. The object of a multi-assignment binding may be stored into through that binding any number of times.

Binding a value to a binding initializes its object. An initialization of a binding’s object that the construct introducing the binding performs is a store into the object through that binding, and so is one that the invocation performs for a parameter or a variadic binding. An initializer performs that initialization at the point of declaration. For a parameter or a variadic binding, it is performed at the first programme point of the subroutine body, and a trace from the declaration of the binding is one from that point.

A binding’s object is **definitely initialized** at a programme point where it is a permanent object, or where every trace from the declaration of the binding to that point contains a store into the object through that binding. It is **possibly initialized** there where it is a permanent object, or where some such trace does so.

### Constraints

The binding’s object shall be loaded, a managed reference to it created, and, through the binding, a constituent object of it stored into, only at a programme point at which it is definitely initialized. Such a violation through a reference, where not detected during translation, can cause indeterminate state.

The object of a single-assignment binding shall be stored into through that binding at most once.

An assignment expression whose leading operand names a binding whose object is an automatic object shall follow the declaration of that binding in the token sequence.

A declaration that omits both the type annotation and the initializer shall not appear.

### Examples (informative)

```
let x: si4 = 42;     // single-assignment, initialized at declaration
let y = x + 1;       // single-assignment, type inferred
let mut counter = 0; // multi-assignment, initialized at declaration
counter += 1;        // OK: counter is mut

// Deferred initialization: single-assignment
let result: si4;
if condition {
    result = compute_a();
} else {
    result = compute_b();
}
print(result); // OK: every trace to here assigns result
// result = 0; // translation failure: result is single-assignment

// Deferred initialization: multi-assignment
let mut buf: [ui1; 4096];
buf = [0; 4096];
airside { dma_fill(%buf, 4096); }
print(buf); // OK: buf was initialized by the assignment above

// Translation-time condition: no trace skips the if body
const always: verdict[void, void] = verdict::Pass.{ void };
let val: si4;
if always {
    val = 1;
}
print(val); // OK: no trace to here omits the assignment

// Diverging branch: its trace reaches no point after the if
let z: si4;
if runtime_condition {
    z = compute();
} else {
    trap();
}
print(z); // OK: the only trace to here assigns z

// translation failure: a trace omits the assignment
// let x: si4;
// if runtime_condition {
//     x = 1;
// }
// print(x); // the else trace reaches here and assigns nothing

// translation failure: managed reference to a binding
// that is not definitely initialized
// let a: si4;
// let r = &a;
```

### 5.3.1 The `else` clause on refutable patterns

#### Dynamic semantics

1. The initializer expression is evaluated.
2. The result is matched against the pattern.
3. If the pattern matches, the objects of the bindings the pattern introduces are initialized and execution continues after the declaration.
4. If the pattern does not match, the `else` branch is evaluated, and on entry to it, where the `else` clause names a binding, the value that failed to match is bound to that name.

#### Constraints

Where its pattern is refutable, a `let` declaration shall include an initializer and an `else` clause; otherwise it shall include no `else` clause.

The `else` branch shall be a control transfer or a diverging expression.

#### Examples (informative)

```
// Irrefutable patterns: else is forbidden
let .{ x, y } = get_point(); // OK
// translation failure: irrefutable
// let .{ x, y } = get_point() else { return; };

// Refutable patterns: else is mandatory
// OK: diverge
let verdict::Pass.{ x } = try_parse() else { return; };
// OK: diverge with binding
let verdict::Pass.{ x } = try_parse() else.fail {
    log(fail); return;
};

// translation failure: no else
// let verdict::Pass.{ x } = try_parse();
```

## 5.4 Translation-time constants

A `const` declaration introduces a translation-time constant.

### Syntax

```
const_decl = [ "pub", ws ], "const", ws, ( identifier | '?' ), ws,
             [ ':', ws, type, ws ], '=', ws, expression, ws, ';' ;
```

### Static semantics

The initializer expression is evaluated at translation time, as defined in the clause on expressions.

A `const` declared as `?` introduces no name, and its initializer is evaluated once, on the constant machine. `pub` upon it has no effect.

### Constraints

A store to a field of the value a `const` declaration introduces shall not appear, regardless of the field’s modifiers.

### Examples (informative)

```
const max_size: uaddr = 1024;
const tau: fe11s52 = 6.283185307179586476925286766559;
// type inferred from the initializer
const limit = 1024~ui4;
// subroutine invoked at translation time
const crc_table: [ui4; 256] = make_lut();
```

## 5.5 Global bindings

A `static` declaration introduces a permanent object, as defined in the clause on semantics, and, other than where declared as `?`, a binding whose object is that permanent object. The initializer is evaluated at translation time, once for each machine on which it would be analysed were it not an analysis root. The object holds the resulting value when execution begins, and, where the declaration has an initializer, a translation-time evaluation that loads from the object, or from a constituent object of it, obtains the resulting value of the initializer.

### Syntax

```
static_decl = [ "pub", ws ], [ "extern", ws ], "static", ws,
              [ "mut", ws ], ( identifier | '?' ), ws,
              [ ':', ws, type, ws ], '=', ws, expression, ws, ';' ;
```

### Static semantics

A `static` declared as `?` introduces no name. A `#symbol` directive upon it gives the name by which the opaque code and symbol resolution identify it. `pub` upon it has no effect.

An object expression designating the object of a single-assignment `static` binding is storable at no programme point.

### Constraints

An identifier expression or a path expression that names a `static mut` binding requires airside.

### Examples (informative)

```
static config: app_config = default_config();
static mut counter: uaddr = 0;
// type inferred from the initializer
static limit = 4096~uaddr;

fn increment() {
    airside { counter += 1; } // airside required for static mut access
}

// Per-field store permission via mut field
struct atomic_counter {
    mut value: ui4  // mut field: airside stores always permitted
}

static shared_counter: atomic_counter = atomic_counter.{ .value = 0 };
// shared_counter is `static` (not `static mut`), but the `mut` field
// permits airside stores through &shared_counter.
```

## 5.6 Composite types

A **composite type** is a type composed of zero or more fields.

A **variant type** is a composite type whose value holds one of a set of named variants and a discriminant that records which. An `enum` declaration introduces a variant type, and so does a `contract` declaration, as defined in the clause on statements and control flow.

### Syntax

```
composite_form   = '{', ws, ( anon_field_list | named_field_list ), ws,
                   '}' ;

anon_field_list  = anon_field, ws, { ',', ws, anon_field, ws },
                   [ ',', ws ] ;
anon_field       = field_modifiers, type, [ ws, '=', ws, expression ] ;

named_field_list = named_field, ws, { ',', ws, named_field, ws },
                   [ ',', ws ] ;
named_field      = field_modifiers, identifier, ws, ':', ws, type,
                   [ ws, '=', ws, expression ]
                 | '?', ws, ':', ws, type ;

field_modifiers  = { field_modifier, ws } ;
field_modifier   = "pub" | "airside" | "mut" ;
```

### Static semantics

A struct type, and each variant of a variant type, takes one of three forms:

&mdash; **Unit form** &mdash; it has no composite form.

&mdash; **Unnamed-field form** &mdash; its composite form matches `anon_field_list`.

&mdash; **Named-field form** &mdash; its composite form matches `named_field_list`.

An anonymous struct type is in unnamed-field form.

### Constraints

The path of a composite construction or of a composite pattern shall name a variant, or a type in unit form, unnamed-field form, or named-field form. Curly brackets shall follow that path only where the type or variant it names is in unnamed-field or named-field form. They shall enclose a `field_init_list` or a `field_pat_list` only where that type or variant is in named-field form, and an `expression_list` or an `unnamed_pat_list` only where it is in unnamed-field form.

A field name shall be unique within a named-field composite type. `?` fields are exempt from uniqueness.

A composite construction whose path names a type or variant with an `airside` field requires airside.

A field that the declaration of a composite type declares without `pub` shall be designated, other than by an ignore pattern, only within the namespace that declares the composite type.

### 5.6.1 Field modifiers

#### Static semantics

The field modifiers `airside` and `mut` have the following effects:

&mdash; `airside` requires airside of every load from and every store to the field, and of the creation of a reference to the field or to a constituent object of it.

&mdash; `mut` gives the field **per-field store permission**. The field may be stored to through a reference or a binding that itself permits no store. Such a store requires airside, and so does the creation of a store-permitting reference to the field or to a constituent object of it.

#### Constraints

A field declaration that repeats a modifier shall not appear.

### 5.6.2 `?` fields

#### Static semantics

A **`?` field** declares padding cells within a named-field composite type.

### 5.6.3 Default-value expressions

#### Static semantics

A field may carry a default-value expression of the form `= expr`. Where a composite construction omits the field, the field holds the value the expression yields.

## 5.7 Struct declarations

A struct declaration introduces a named composite type.

### Syntax

```
struct_decl = [ "pub", ws ], "struct", ws, identifier,
              [ ws, generic_clause ],
              ( [ ws, with_single ], ';'
              | ws, with_curly
              | ws, composite_form,
                [ ws, with_single, ';' | ws, with_curly ] ) ;
```

### Examples (informative)

```
// Unit form
struct empty_t;

struct point { x: si4, y: si4 }

struct origin_point {
    x: si4 = 0,
    y: si4 = 0
}

struct example {
    // private, the binding kind governs stores
    a: si4,
    // public,  the binding kind governs stores
    pub b: si4,
    // private, airside stores always permitted
    mut c: si4,
    // public,  airside stores
    pub mut d: si4,
    // private, airside-only access
    airside e: si4,
    // public,  airside-only
    pub airside f: si4,
    // private, airside-only, airside stores
    airside mut g: si4,
    // public,  airside-only, airside stores
    pub airside mut h: si4
}

struct network_header {
    version: ui1,
    ?: ui1,
    length: ui2,
    ?: [ui1; 4],
    payload_offset: ui4
}
```

## 5.8 Enum declarations

### Syntax

```
enum_decl = [ "pub", ws ], "enum", ws, identifier,
            [ ws, generic_clause ], ws, '{', ws,
            [ variant_list ], ws, '}',
            [ ws, with_single, ';' | ws, with_curly ] ;

variant_list  = variant, ws, { ',', ws, variant, ws }, [ ',', ws ] ;
variant       = identifier, [ ws, composite_form ],
                [ ws, '=', ws, variant_value ] ;

variant_value = discrim_value
              | "wild", [ ws, '(', ws, discrim_value, ws, ')' ] ;

discrim_value = [ sign, ws ], integer_literal ;
```

### Static semantics

`wild` declares that the designated variant covers all discriminant values not matched by any other variant.

A `discrim_value` denotes the digit value of the integer literal it carries, negated where a `-` precedes the literal. That literal takes no type from inference, and the value the `discrim_value` denotes is an integer.

`wild(V)` declares a **canonical value** for the wild variant, where `V` is a `discrim_value`. A construction of the wild variant stores `V` as the discriminant. (e.g. `verdict::Fail.{ payload }` stores `V` as the discriminant.) The canonical value also governs discriminant extraction via `as`, as defined in the clause on expressions.

Where `wild` is written without a canonical value, a construction of the wild variant stores as the discriminant the value the automatic discriminant assignment algorithm assigns that variant.

The rules of this subclause govern every variant type.

A variant type that declares no `wild` variant has an **implicit wild variant**. It is assigned no discriminant value of its own. It covers all discriminant values of the type’s discriminant type that no declared variant matches.

A value of a variant type that declares no `wild` variant may be constructed by the expression `TypeName::wild`, as defined in the subclause on wild construction in the clause on expressions.

When a variant is declared without an explicit discriminant value, the implementation assigns a discriminant automatically using the following algorithm:

1. Collect the occupied set *S*, the union of all explicitly specified discriminant values and all `wild(V)` canonical values the type declares.
2. Initialize a candidate counter *d* to zero.
3. Traverse the variants in declaration order. A `wild` variant without a canonical value counts as lacking an explicit discriminant value. For each variant that lacks one, advance *d* to the smallest value ≥ *d* that is not in *S*, assign *d* as the variant’s discriminant value, add *d* to *S*, and set *d* to *d* + 1.

### Constraints

A type shall have at most one `wild` variant.

Each explicitly specified discriminant value within a variant type, counting each `wild(V)` canonical value among them, shall be distinct from every other.

A variant type for which the automatic discriminant assignment algorithm, defined above, finds no representable candidate value shall not appear.

### Examples (informative)

```
// Variants in unit form only
enum colour { red, green, blue }

// Variant in unnamed-field form: single positional field
enum packet { data { &[ui1] }, ack, error = wild }

// Variants in unnamed-field form: multiple positional fields
enum shape {
    circle { fe11s52 },                 // radius: .0
    rect { fe11s52, fe11s52 },          // width: .0, height: .1
    triangle { fe8s23, fe8s23, fe8s23 } // sides: .0, .1, .2
}

// Variants in named-field form
enum event {
    key_press { key: ui4, modifiers: ui1 },
    mouse_move { x: si2, y: si2 },
    quit
}

// Mixed
enum message {
    ping,
    data { ui1, [ui1; 32] },          // positional: kind + payload
    error { code: ui4, msg: &[ui1] }, // named fields
    unknown = wild
}

// Accessing the fields of variants in unnamed-field form
let s: shape = shape::rect.{ 3.0, 4.0 };
match s {
    let shape::rect.{ w, h }        -> area(w, h);
    let shape::circle.{ r }         -> area_circle(r);
    let shape::triangle.{ a, b, c } -> area_triangle(a, b, c);
    wild                            -> 0.0;
}

// Accessing the fields of variants in named-field form
let e: event = event::key_press.{ .key = 65~ui4, .modifiers = 0~ui1 };
match e {
    let event::key_press.{ .key, .modifiers } ->
        handle_key(key, modifiers);
    let event::mouse_move.{ .x, .y }          -> handle_mouse(x, y);
    event::quit                              -> quit();
    wild                                     -> ignore();
}
```

## 5.9 Type aliases

A type alias introduces a new name for an existing type.

### Syntax

```
type_alias_decl = [ "pub", ws ], "type", ws, identifier,
                  [ ws, generic_clause ], ws, '=', ws, type, ws, ';' ;
```

### Static semantics

At every use site, a type alias is replaced by its aliased type, with the generic arguments supplied there substituted for the parameters it declares.

### Constraints

A type alias that is directly or indirectly recursive shall not appear. A generic alias that declares a generic parameter not appearing in the aliased type shall not appear.

### Examples (informative)

```
type byte        = ui1;
type index       = uaddr;
type pair[A, B]  = .{A, B};
type matrix[T]   = [[T; 4]; 4];

pub type seconds = ui4;

// No conversion at any use site
let b: byte = 42~ui1;
let c: ui1  = b;
fn takes_ui1(x: ui1) {}
takes_ui1(b);

// Protocol bounds resolve on the aliased type
fn show[T: fmt](x: T) { ... }
show(b); // OK: ui1 implements fmt

// Generic argument identity
let p1: pair[byte, si4] = .{ 1~ui1, 2 };
let p2: pair[ui1,  si4] = p1; // same type

// A struct declaration introduces a distinct type
struct seconds2 { val: ui4 }
```

## 5.10 Generic declarations

A generic declaration introduces a type, a subroutine, or a protocol parameterized over one or more generic parameters &mdash; type parameters or dependence parameters.

### Syntax

```
generic_clause   = '[', ws, generic_item, ws,
                   { ',', ws, generic_item, ws }, [ ',', ws ], ']' ;
generic_item     = type_param | dependence_param ;
type_param       = identifier, [ ws, ':', ws, bound ] ;
dependence_param = "const", ws, identifier, ws, ':', ws, type ;
bound            = bound_elem, ws, { '+', ws, bound_elem, ws } ;
bound_elem       = builtin_bound | single_path ;

generic_args     = '[', ws, generic_arg, ws,
                   { ',', ws, generic_arg, ws }, [ ',', ws ], ']' ;
generic_arg      = type | expression ;
```

A **generic argument list** follows the name of the generic type, subroutine, or protocol it instantiates, or an expression whose type is a subroutine pointer type with a `generic_clause`, where it instantiates the subroutine that the value of that expression designates. Its arguments correspond in order to the declared generic parameters. A type argument resolves a type parameter, and a dependence argument resolves a dependence parameter.

### Static semantics

Generic parameters are in scope for the entire declaration or subroutine pointer type that declares them. An `impl` block that names the type introduces its own generic parameters, as defined in the clause on protocols and implementations.

A generic parameter **occurs free** in a type or an expression where, other than within a part of that type or expression of which it is a generic parameter, it occurs there, or occurs free in a type that a `selftype` there stands for or in the type of an expression that is, or lies within, that type or expression. A type in which a generic parameter occurs free is an **open type**, and any other type is a **closed type**. **Instantiation** is the derivation, from a generic declaration, of a type, a subroutine, or a protocol by resolving each of its generic parameters to an argument.

A **type parameter** is, in semantic analysis, a distinct open type, and, in each evaluation, denotes its type argument. An **eligible resolution** of generic parameters is a resolution of each of them in which each type parameter resolves to a closed type that satisfies each built-in bound that the bound upon that type parameter names, and each that a protocol that bound names entails. An open type satisfies a built-in bound `X` if and only if, in every programme and every machine, it satisfies `X` under every eligible resolution of its generic parameters.

A **dependence parameter** declares a value upon which the types within the declaration may depend. The expression supplied for it is a **dependence argument**. A dependence parameter may appear wherever a value expression of the same type may appear. (e.g. an array length, or the type or expression of a subsequent parameter or field.)

Two instantiations of the same generic declaration are the same type if and only if all type arguments are the same types and all dependence arguments yield the same value.

Each of the following is an instantiation of a built-in generic declaration:

&mdash; An array type `[T; N]` &mdash; of one whose generic parameters are a type parameter for `T` and a dependence parameter of type `uaddr` for `N`, in that order.

&mdash; An anonymous struct type &mdash; of one with one type parameter per field, in field order.

&mdash; A slice reference &mdash; of one of its tribe and modifiers with one type parameter for its element type.

&mdash; Every other reference type &mdash; of another one of its tribe and modifiers with one type parameter for its referent type.

&mdash; A subroutine pointer type that carries no `generic_clause` &mdash; of one particular to that type, with one type parameter per parameter type, in order, followed by one for its return type where that is not `!`.

&mdash; `verdict[T, F]` &mdash; of one with a type parameter for `T` and one for `F`, in that order.

&mdash; A protocol type &mdash; of one particular to its protocol, with the generic parameters of that protocol.

A type satisfies a declared protocol `X` if and only if an implementation of `X` for it is witnessed, as the clause on protocols and implementations defines witnessed implementations.

### Constraints

A dependence argument shall be supplied explicitly.

Where a generic argument list is written, the number of arguments it supplies shall equal the number of parameters in the declaration, or, where it follows an expression whose type is a subroutine pointer type, in the `generic_clause` of that type. Where a generic parameter occurs free in a dependence argument or in the expression of an associated constant, that argument or expression shall be one of the expressions whose values are excepted by the definition, in the clause on semantics, of what an execution context can occupy. For this rule, that definition also excepts the value of a layout intrinsic, and of an identifier expression or a path expression that names a dependence parameter or an associated constant.

The path of a bound element shall name a protocol. Each type argument shall satisfy every bound element declared upon the parameter it resolves.

An inner parameter that hides an outer parameter of the same name shall not appear.

A field access whose receiver has, after reference transparency, a type parameter as its type shall not appear.

Each generic parameter that occurs free in an open type shall be a generic parameter of a declaration or subroutine pointer type within which the open type appears.

The type of a dependence parameter shall be a closed type, shall be copyable, and shall neither be a reference type nor contain one as a constituent.

An operation between two instantiations whose dependence arguments yield different values shall not appear. Such a violation, where not detected during translation, can cause indeterminate state.

### Examples (informative)

```
struct pair[A, B] {
    first:  A,
    second: B
}

contract option[T] {
    some { T },
    none { void } = wild
}

struct arc[T] {
    ptr: %T,
    mut ref_count: &atomic mut ui4
}

// Instantiation
let p: pair[si4, verdict[void, void]] =
    pair.{ .first = 42, .second = verdict::Pass.{ void } };
let x: option[si4] = option::some.{ 7 };

// Explicit generic arguments: required when type cannot be inferred
fn default_value[T: defaulted]() -> T {
    return (T as defaulted)::default();
}

let val = default_value[si4]();

// Inline bound
fn max[T: primitive](a: T, b: T) -> T {
    return if a > b then a else b;
}

// Dependence parameters
struct matrix[T, const rows: uaddr, const cols: uaddr] {
    data: [T; rows * cols]
}

let m: matrix[fe11s52, 3, 4] = ...;
```

### 5.10.1 Generic dispatch

#### Static semantics

A generic subroutine accesses type-specific properties through a bound descriptor passed to it at each invocation site, or through the generic argument vector of a type descriptor passed to it. A **bound descriptor** is a descriptor of a kind that `T'bound(X)` emits, as defined in the clause on expressions.

The invoker supplies a type descriptor for each type argument:

&mdash; Where the type argument is, in semantic analysis, a closed type, the descriptor `T'bound(type)` emits.

&mdash; Where it is otherwise a type parameter, the descriptor the invoker received for that type parameter, or the descriptor it reaches for that parameter through generic argument vectors from a type descriptor it received.

&mdash; Where it is otherwise an open type, a type descriptor the invoker assembles. Its size and alignment follow from the layout rules applied to its arguments, and its field 2 designates the same subroutine for every instantiation of the generic declaration the type instantiates. Each type descriptor so assembled, and the generic argument vector it designates, is a temporary object that the invocation produces.

An assembled type descriptor is supplied, or held in a generic argument vector, only for a type parameter whose bound names no declared protocol. For every other type parameter, and for the subject of every subject bound, the type descriptor that the invoker supplies, or that a generic argument vector holds, is the one that accompanies the protocol descriptor supplied for that parameter or subject. Those two descriptors are immortal objects. Each descriptor that an invocation receives exists until control leaves the body evaluation of that invocation.

### 5.10.2 Signature lowering

The signature of a generic subroutine is lowered to the programme machine’s invocation interface. The lowered signature is divided into three zones, in the following order.

The return type of the lowered signature is `void`. The result is delivered through the zone 1 parameter.

#### Zone 1

The first parameter is `%mut void`, designating storage the invoker reserves for the return value. The invoker determines the storage region by applying the layout rules of the clause on types to the source-level return type, taking the size and the alignment of each type parameter within it from that parameter’s type descriptor.

#### Zone 2

The source-level parameters follow, in declaration order. A parameter whose type is an open type is lowered to `%void`, and the argument is passed as an unmanaged reference to storage holding the source-level value. A parameter whose type is a closed type is lowered to that type.

#### Zone 3

The descriptors and dependence parameters stand in levels, in the following order:

1. `selftype`, where it is a type parameter of the signature as the clause on protocols and implementations defines.
2. The generic parameters of the subroutine itself.
3. The subject bounds of its `with` clause.
4. The generic parameters of the enclosing declaration.

The enclosing declaration is the `protocol` declaration for a subroutine that a protocol body declares or that a protocol implementation provides, and the `impl(...)` parameter list for a subroutine that an inherent implementation provides. Within each level, parameters and subject bounds appear in declaration order.

For each type parameter, the `type` descriptor reference is emitted as `%void`, followed by one `%void` for each bound element of its bound, in the order of its bound. For each subject bound, the `type` descriptor reference of its subject is emitted as `%void`, followed by the descriptor reference of its protocol as `%void`. The descriptor each element designates is defined in the subclause on bound descriptor emission. For each dependence parameter, one parameter of its type is emitted.

#### Dynamic semantics

An invocation whose zone 3 holds references that do not designate descriptors as the subclause on generic dispatch and zone 3 call for under an eligible resolution of the generic parameters its levels hold can cause indeterminate state.

#### Constraints

A `#dyn` block shall not declare a generic subroutine.

#### Design rationale (informative)

The lowered signature is a single symbol composed of closed types and `%void`s. The resulting symbol is invocable across `#dyn` boundaries without source.

#### Examples (informative)

```
extern fn process[T: ord + clone](x: &T) { ... }
// lowers to:
// fn process(
//     out:     %mut void,   // zone 1
//     x:       %void,       // zone 2
//     T_type:  %void,       // zone 3: T'bound(type)
//     T_ord:   %void,       // zone 3: T'bound(ord)
//     T_clone: %void        // zone 3: T'bound(clone)
// ) -> void

extern fn merge[
    T: ord, U: clone
](arr: $[T], default: U, count: si4) { ... }
// lowers to:
// fn merge(
//     out:     %mut void,   // zone 1
//     arr:     %void,       // zone 2
//     default: %void,       // zone 2
//     count:   si4,         // zone 2: closed
//     T_type:  %void,       // zone 3: T'bound(type)
//     T_ord:   %void,       // zone 3: T'bound(ord)
//     U_type:  %void,       // zone 3: U'bound(type)
//     U_clone: %void        // zone 3: U'bound(clone)
// ) -> void

extern fn fill[
    T: numeric, const N: uaddr
](buf: $[T; N]) { ... }
// lowers to:
// fn fill(
//     out:       %mut void, // zone 1
//     buf:       %void,     // zone 2
//     T_type:    %void,     // zone 3: T'bound(type)
//     T_numeric: %void,     // zone 3: T'bound(numeric)
//     N:         uaddr,     // zone 3: dependence
// ) -> void

extern fn identity[T](x: T) -> T { return x; }
// lowers to:
// fn identity(
//     out:    %mut void,   // zone 1
//     x:      %void,       // zone 2
//     T_type: %void,       // zone 3: T'bound(type)
// ) -> void
```

Usage through `#dyn`:

```
#dyn libsort {
    fn sort(out: %mut void, arr: %void,
        t_type: %void, t_ord: %void);
}

pub fn sort[T: ord](arr: $[T]) {
    airside {
        let mut dummy: void = void;
        let t_type = contract T'bound(type) else trap();
        let t_ord  = contract T'bound(ord)  else trap();

        libsort::sort(%mut dummy, %arr as! %void, t_type, t_ord);
    }
}

// At the invocation:
sort[si4](my_array);
```

## 5.11 Patterns and destructuring

Patterns appear in `let` declarations, `match` alternatives, and `if let` and `while let` conditions. The value a pattern is applied to is the **matched value**, its type is the **matched type**, and the object that holds it is the **matched object**.

### Syntax

```
pattern        = [ "let", ws ], pattern_body ;
pattern_body   = literal_pat | ident_pat | ignore_pat | wild_pat
               | composite_pat | anon_pat
               | slice_pat | string_pat | range_pat
               | binding_pat | or_pat ;

literal_pat    = [ sign, ws ], ( integer_literal | float_literal )
               | char_literal ;
ident_pat      = [ "mut", ws ], identifier ;
ignore_pat     = '?' ;
wild_pat       = "wild", [ ws, '(', ws, identifier, ws, ')' ] ;
composite_pat  = single_path,
                 [ ws, '.', ws, '{', ws,
                   [ field_pat_list | unnamed_pat_list ], ws,
                   '}' ] ;
anon_pat       = '.', ws, '{', ws, unnamed_pat_list, ws, '}' ;

field_pat_list = field_pat, ws, { ',', ws, field_pat, ws }, [ ',', ws ],
                 [ ws, '...' ] ;
field_pat      = [ "let", ws ], [ "mut", ws ],
                 [ identifier, ws, '=', ws ],
                 '.', ws, identifier,
                 [ ws, '@', ws, pattern ] ;

unnamed_pat_list = pattern, ws,
                   { ',', ws, pattern, ws }, [ ',', ws ] ;

slice_pat      = '[', ws,
                 [ element_pat, ws, { ',', ws, element_pat, ws },
                   [ ',', ws ] ], ']' ;
element_pat    = pattern | '...' ;
string_pat     = string_literal | raw_string_literal ;
range_pat      = literal_pat, ws, ( '..' | '..=' ), ws, literal_pat ;
binding_pat    = ident_pat, ws, '@', ws, pattern ;
or_pat         = pattern_body, ws, '|', ws, pattern_body ;
```

### 5.11.1 Pattern forms

#### Static semantics

Where a `literal_pat` carries a `sign`, that `sign` is a unary negation or a unary identity whose operand is the literal that follows it, and the `literal_pat` denotes the value that operation yields. Otherwise the `literal_pat` denotes the value of its literal. A literal within a pattern is yielded by each evaluation that tests the pattern.

&mdash; **Literal pattern** &mdash; `p` matches a value `v` where `v == p` holds.

&mdash; **Identifier pattern** &mdash; an identifier, optionally preceded by `mut`, binds the matched value to a name at its original type. Within a `pattern`, an identifier pattern that no `let` governs is a composite pattern.

&mdash; **Ignore pattern** &mdash; matches every value of the matched type and introduces no binding.

&mdash; **`wild` pattern** &mdash; matches a value that no declared variant of the matched type covers, and yields a reference to the cells of the matched object (`&[ui1]`, or `&volatile [ui1]` where the reference nearest the matched object carries `volatile`). For the rules of the clause on references and resource management, that reference is created as from an object expression that designates the matched object from the matched expression. The bare form `wild` discards it. The form `wild(`*name*`)` binds it to *name*.

&mdash; **Composite pattern** &mdash; matches a value of the type or variant its path names where each pattern it applies to a field of that value matches.

&mdash; **Anonymous struct pattern** (`.{ }`) &mdash; matches a value of an anonymous struct type where each pattern it lists matches the field at its position.

&mdash; **Slice pattern** &mdash; matches a slice or array by element-wise comparison. The rules governing it are defined in the clause on statements and control flow.

&mdash; **String literal pattern** &mdash; syntactic shorthand for a fixed-length slice pattern whose elements are the `ui1` values of the string literal, as defined by the mapping in the clause on lexical structure. A raw string literal pattern follows the same rules. (e.g. with an 8-bit cell and a literal encoding that assigns each character of the basic source character set the value that ISO/IEC 646:1991 (International Reference Version) assigns it, `"abc"` as a pattern is identical to `[0x61, 0x62, 0x63]`.)

&mdash; **Range pattern** &mdash; `a..=b` matches a value `v` where `a <= v` and `v <= b` hold, and `a..b` matches one where `a <= v` and `v < b` hold.

&mdash; **Binding pattern** (`@`) &mdash; `name @ sub_pattern` applies both `name` and `sub_pattern` to the matched value, and matches where both match.

&mdash; **Or-pattern** &mdash; `p | q` matches where either alternative matches.

A `let` **governs** the `pattern_body` or `field_pat` it precedes and every pattern and `field_pat` within it. An identifier pattern that a `let` governs binds, whether or not its identifier names a declaration in scope.

Where a `let`, or the `pattern` that follows an `@`, belongs, in different derivations of a source unit, to patterns of different extent, it belongs to the one of greatest extent.

Where the matched type of a literal, range, `wild`, composite, anonymous struct, slice, or string literal pattern is a reference type, the pattern applies reference transparency, as the clause on expressions defines it, to the matched value: the matched type of the pattern is instead the referent type, and its matched object the referent. The pattern matches a value of the reference type where it so matches the value the referent holds.

Matching that reaches a part through an unmanaged reference requires airside.

#### Dynamic semantics

A **part** is the matched object itself, a discriminant, a field, or an element, whether held by value or reached through a reference, or a reference through which reference transparency reaches a matched object. Matching loads a part of the matched object only where one of the following holds:

&mdash; The pattern compares that part.

&mdash; The pattern binds that part.

&mdash; The pattern matches the length that part holds.

&mdash; That part is a reference through which the pattern reaches another part.

A part reached through a reference is accessed through the value of that reference that the load of the part holding it yielded. A pattern compares its parts in leading-to-following order and stops at the first comparison that fails, except that the failure of an alternative of an or-pattern moves on to its next alternative. Within one evaluation of a `match` expression or a `let` declaration, or of the condition of an `if let` or a `while let`, the first comparison of a part, or the first reach of another part through it, loads it. Within that evaluation, every later comparison, reach, or binding of that part, in the same alternative or a later one, uses the value that load yielded. A part that the pattern binds and that is not so loaded is loaded after the pattern matches, at the programme point at which the objects of the bindings it introduces are initialized.

#### Constraints

The alternatives of an or-pattern shall bind the same names with the same types and the same binding kind.

An `ident_pat` or `field_pat` that carries `mut`, and a `field_pat` that carries an identifier before `=`, shall bind a name.

A pattern that matches no value of the matched type under any eligible resolution of the generic parameters that occur free in that type shall not appear.

The path of a composite pattern shall name the matched type or a variant of it.

A string literal pattern shall appear only where the element type of the matched type is `ui1`.

### 5.11.2 Struct destructuring

#### Static semantics

A **destructuring pattern** is a composite pattern other than its path alone, or an anonymous struct pattern (`.{ ... }`).

A **named-field destructuring** is a destructuring pattern whose path names a type or variant in named-field form. In it, a `field_pat` designates a field by `.field_name`. Where a `let` governs it, the form `.field_name` binds the field value to `field_name`, and the form `binding_name = .field_name` binds it to `binding_name`. A following `@ sub_pattern` applies the sub-pattern to the field value.

`...` at the end of the field list matches the fields the pattern does not mention, without binding them.

An **unnamed-field destructuring** is a destructuring pattern whose path names a type or variant in unnamed-field form, or an anonymous struct pattern. Each pattern its `unnamed_pat_list` lists designates the field at its position, counting in declaration order, and is applied to that field.

#### Constraints

Every field of a named-field destructuring, other than a `?` field, shall be mentioned unless the pattern ends with `...`.

The `unnamed_pat_list` of an unnamed-field destructuring shall list as many patterns as the matched type or variant has fields.

#### Examples (informative)

```
// Struct in named-field form
struct point { x: si4, y: si4 }
let point.{ .x, .y } = get_point();  // all fields
let point.{ .x, ... } = get_point(); // y ignored
let point.{ origin = .x @ 0, .y } = get_point() else {
    return; // x bound to origin, constrained to 0
};

// Enum with a variant in named-field form
match e {
    // fields other than key ignored
    let event::key_press.{ .key, ... } -> handle(key);
    event::quit                       -> quit();
    wild                              -> ignore();
}

// Anonymous struct destructuring
let .{ a, b } = get_pair();      // all fields, positional order
// let .{ a, ... } = get_pair();
// translation failure: ... not permitted
```

### 5.11.3 Pattern bindings

#### Static semantics

A pattern binding holds the value of the part its identifier pattern or `field_pat` binds, copied or transferred into it as the clause on references and resource management defines.

A pattern introduces one binding for each of the following that it contains, counting, of each or-pattern within it, the first alternative alone: an identifier pattern or `field_pat` that a `let` governs, and a `wild_pat` that carries an identifier. In each other alternative, each of these binds its name to the binding that name has in the first alternative.

#### Examples (informative)

```
let struct_t.{ .a, mut .b, .c } = get_structure();
// a and c are single-assignment, b is multi-assignment
b += 1; // OK: b is mut
// a += 1; // translation failure: a is single-assignment

let .{ x, mut y, z } = get_triple();
y += 1; // OK: y is mut

// Per-binding mut with refutable patterns
let verdict::Pass.{ .{ a, mut b } } = try_get_pair() else { return; };
b += 1; // OK: b is mut
```

### 5.11.4 Refutability

#### Static semantics

A pattern is **irrefutable** where it matches every value of the matched type, and **refutable** otherwise.

A slice pattern is irrefutable where each of its element patterns is irrefutable and the pattern matches every length that a value of the matched type can have under some eligible resolution of the generic parameters that occur free in that type, and refutable otherwise. A rest pattern is irrefutable. Which lengths a slice pattern matches is defined in the subclause on slice and string literal patterns.

## 5.12 `with` clauses

A `with` clause attaches properties to a declaration or to a subroutine pointer type.

### Syntax

```
with_single  = "with", ws, with_item ;
with_curly   = "with", ws, '{', ws, with_item, ws,
               { ',', ws, with_item, ws }, [ ',', ws ], '}' ;
with_item    = destruct_clause | inv_clause | repr_clause
             | discrim_clause | align_clause | "variadic" | "copyable"
             | subject_bound ;
```

### Static semantics

Each word is defined in the clause where it is introduced:

&mdash; `destruct` &mdash; supplies the destructor of the type (clause on references and resource management).

&mdash; `inv` &mdash; declares the inverted pair of a contract type (clause on statements and control flow).

&mdash; `repr` &mdash; controls representation (clause on types).

&mdash; `discrim` &mdash; sets the discriminant type of a variant type (clause on types).

&mdash; `align` &mdash; sets minimum alignment (clause on types).

&mdash; `variadic` &mdash; declares a variadic state type (clause on types).

&mdash; `copyable` &mdash; makes the type copyable where each of its constituents is (clause on references and resource management).

&mdash; `impl` &mdash; requires that a type implement a protocol (clause on protocols and implementations).

### Constraints

Within a clause enclosed by curly brackets, each word other than `impl` shall appear at most once. A `with` word shall appear only on the declaration kinds and type kinds for which it is defined.

A `with` clause shall not combine `variadic` with `repr`, `destruct`, or `copyable`, nor `copyable` with `destruct`.

### Examples (informative)

```
// with_single form
struct handle { fd: si4 } with destruct { close(self.fd); };

// with_curly form
struct packet {
    header: ui4,
    payload: &[ui1]
} with {
    repr(pack(1)),
    align(4)
}
```

## 5.13 Visibility and name introduction

### 5.13.1 Visibility modifier

#### Static semantics

A declaration marked `pub` is visible outside the namespace that declares it. A variant is visible wherever the type that declares it is visible. Where a declaration introduces a namespace identifier, `pub` upon it applies to every one it introduces, and the visibility of the declarations within the namespace is governed by `pub` upon those declarations independently. Namespaces, and the visibility a path requires at each of its segments, are defined in the clause on programme structure and translation.

### 5.13.2 Unqualified name introduction

#### Syntax

```
use_decl = [ "pub", ws ], "use", ws, use_tree, ws, ';' ;
use_tree = single_path, [ ws, "as", ws, identifier ]
         | single_path, ws, '::', ws, '*'
         | single_path, ws, '::', ws, '{', ws, use_tree, ws,
           { ',', ws, use_tree, ws }, [ ',', ws ], '}' ;
```

#### Static semantics

Each `use_tree` selects one or more named items and introduces names for them into the enclosing scope. Resolution of an introduced name yields the selected item.

A `use_tree` consisting of a `single_path` selects the item denoted by the path. Its introduced name is the final identifier of the path. When an `as` clause is present, the identifier of the clause is its introduced name.

In a `use_tree` enclosed by curly brackets, the path preceding `::{` is prepended to the path of each `use_tree` within.

A `use_tree` ending in `::*` selects the children of the namespace denoted by the preceding path that are visible where the `use_decl` appears.

The visibility modifier of a `use_decl` applies to every name introduced by the declaration.

#### Constraints

&mdash; Each path selecting an item shall resolve to a named item.

&mdash; Each path preceding `::{` or `::*` shall resolve to a namespace.

&mdash; A `use_tree` shall contain no generic argument list.

&mdash; Each item selected by a `pub use` declaration shall be visible outside the namespace that declares the `pub use` declaration.

#### Examples (informative)

```
use math::sqrt;
let r = sqrt(2.0); // unqualified access

use io::{ read, write, close }; // multi-import

use collections::map as dictionary;

#add "bool.kr" as booleans;
use booleans::*;

pub use root::{
    branch::leaf,
    nested::{
        item as renamed,
        children::*
    }
};
```

### 5.13.3 Named items

#### Static semantics

A **named item** is a variant, an associated constant, an associated subroutine, or a declaration that introduces a name.

#### Examples (informative)

```
use colour::red;
use colour::{ green, blue };
// red, green, blue can be used without the colour:: prefix.

let c = red; // equivalent to colour::red

// Associated constant
use si4::max; // imports the associated constant si4::max
let m = max;  // equivalent to si4::max

// Associated subroutine
use vec::new;  // imports the associated subroutine vec::new
let v = new(); // equivalent to vec::new()
```

## 5.14 Global `instruct` blocks

A **global `instruct` block** is an `instruct` block that is a `global_instruct`. It embeds instructions into the opaque code. Inline `instruct` blocks are defined in the clause on expressions.

### Syntax

```
global_instruct = "instruct", ws, instruct_body ;
```

### Static semantics

The `instruct_body` production is defined in the clause on expressions, and where an `instruct` block ends in the clause on lexical structure.

A global `instruct` block differs from an inline `instruct` block in the following:

&mdash; An inline expression (`'(expr)`) is the only form that injects a translation-time value into the instruction text.

&mdash; The block may define external symbols through implementation-defined directives. A symbol so defined is resolved in the same manner as a symbol produced by an `extern` declaration.

### Implementation defined

The set of supported environments of the programme machine for global `instruct` blocks is implementation defined.

### Examples (informative)

```
const stack_size: uaddr = 4096 * 4;

instruct {
    .section .bss
    .align 16
    stack_bottom:
        .skip '( stack_size )
    stack_top:
}

instruct {
    .global _start
    _start:
        call main
}
```

## 5.15 `#inline` and `#no_inline`

The `#inline` and `#no_inline` directives control whether the implementation substitutes a subroutine’s body at each invocation site.

### Syntax

```
inline_directive    = '#inline' ;
no_inline_directive = '#no_inline' ;
```

### Static semantics

Where `#inline` is applied, the implementation should replace each invocation of the annotated subroutine with a copy of its body at the invocation site.

Where `#no_inline` is applied, the implementation shall not replace an invocation of the annotated subroutine with a copy of its body. Each invocation of the subroutine on the programme machine shall be emitted as an invocation instruction, and a subroutine so invoked shall be emitted in the opaque code in a form invocable by those instructions. A subroutine that no invocation on the programme machine invokes is emitted where the subclause on external declaration retains it.

### Constraints

`#inline` and `#no_inline` shall stand only upon a subroutine definition or the definition of an associated subroutine, and shall not both stand upon the same one.

### Design rationale (informative)

Failure to honour `#inline` affects performance alone. A programme can depend on a subroutine remaining a discrete symbol in the opaque code, and on the instructions of its body being executed at one place. Disregarding `#no_inline` can therefore cause malfunction that no diagnostic can detect.

### Examples (informative)

```
#inline
fn fast_abs(x: si4) -> si4 {
    return if x < 0 then -x else x;
}

#no_inline
fn cold_path(err: error_code) -> ! {
    log_error(err);
    trap();
}

// #no_inline on a hook point: external tools may patch this symbol
#no_inline
extern fn trace_entry(id: ui4) {
    // body may be empty.
}

impl counter {
    #inline
    pub fn get(&self) -> uaddr { return self.val; }
}
```

## 5.16 Symbol identification

The `#symbol` directive overrides the external name of a declaration with an identification string.

### Syntax

```
symbol_directive = '#symbol', ws, string_literal ;
```

### Static semantics

Where `#symbol` is present, the implementation shall use the content of its string literal as the external name.

### Constraints

`#symbol` shall stand only upon a subroutine definition, the definition of an associated subroutine, a `static` declaration, or a `dyn_item`.

Distinct external symbols the opaque code of a translation unit contains shall bear distinct external names.

### Implementation defined

The interpretation of the string literal is implementation defined for each supported environment of the programme machine and of the translation machine.

### Examples (informative)

```
// The Kurt subroutine kurt_compress is exported as “compress”
#symbol "compress"
extern fn kurt_compress(src: &[ui1], dst: $[ui1])
    -> verdict[uaddr, void] {
    ...
}

// The Kurt static is exported as “global_state”
#symbol "global_state"
extern static mut state: app_state = default();

// A constant has no external name for #symbol to override
// #symbol "limit"
// const limit: ui4 = 64; // translation failure
```

## 5.17 Annotations

An annotation attaches implementation-specific information to an item.

### Syntax

```
annotation         = '#[', annotation_content, ']#' ;
annotation_content = ? implementation defined ? ;
```

### Static semantics

A conforming implementation may assign meaning to an annotation it recognizes. The meaning it assigns shall leave unchanged both the behaviour this specification defines for the programme and which source units the implementation rejects.

### Constraints

A `#[` without a matching `]#` shall not appear.

### Implementation defined

The structure and the interpretation of the content between `#[` and `]#` are implementation defined.

### Examples (informative)

```
#[hot]#
fn dispatch(op: ui1) -> si4 { ... }

#[cold]#
fn report_failure(code: si4) { ... }

#[section ".boot"]#
airside fn reset_vector() { ... }
```

## 5.18 Duplicate declarations

### Static semantics

A declaration in an inner scope **hides** a declaration of the same name in an outer scope. The inner declaration introduces a distinct named item. Throughout the inner scope, the name denotes the inner item.

For `impl` blocks, the uniqueness of protocol implementations and the resolution of item name overlap are defined in the clause on protocols and implementations.

### Constraints

Within a single scope, a name shall be declared at most once. The children of one namespace shall bear distinct names, and so shall the items of one `impl` block and the protocol items of one `protocol` body. A `#path` declaration introduces a prefix rather than a name, as the clause on programme structure and translation defines.

The parameters of one subroutine declaration or subroutine pointer type, its variadic binding included, shall bear distinct names, and so shall the generic parameters of one `generic_clause` or `impl(...)` parameter list.

### Examples (informative)

```
// Hiding in an inner scope: distinct binding, may share a name
let x: si4 = 1;
{
    // hides outer x: distinct binding, different type
    let x: fe11s52 = 2.0;
    use_float(x); // x is fe11s52 here
}                 // inner x destroyed, outer x visible again
use_int(x);       // x is si4 here, value 1

// Duplicate in the same scope: translation failure
// let y = 1;
// let y = 2; // translation failure: y already declared in this scope
```
