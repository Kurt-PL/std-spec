# 1. General

This clause constitutes the axioms, the Kurt machine, the scope, the conformance criteria, and the notation that the remainder of this specification uses.

## 1.1 Founding axioms

This specification is derived from two foundational axioms.

### Axiom 1 &mdash; the computer is a machine

A machine is caused to act by every condition, under one constant law. The computer is such a machine, and it calculates while powered.

### Axiom 2 &mdash; the language is self-contained

This specification is the sole definition of the Kurt programming language. An explicit delegation is part of the definition.

## 1.2 The Kurt machine

The **Kurt machine** is the formal structure from which all semantics in this specification are derived. It is a 5-tuple *K* = (*Q*, *Γ*, *Σ*, *δ*, *q*<sub>0</sub>), where:

&mdash; *Q* is a finite, non-empty set of states. A state is the whole of the machine apart from the boundary.

&mdash; *Γ* is the set of symbols storage can hold, the integers from zero to *n* for an integer *n* greater than zero. The cells of storage, the number of symbols of *Γ*, and the addressing of cells are defined in the clause on semantics.

&mdash; *Σ* is the set of values that pass across the boundary between the machine and its environment. A signal originates from the machine or from the environment. The symbol ε denotes the absence of a signal at the boundary.

&mdash; *δ* : *C* → *C* is the transition function, where *C* is the set of configurations. *δ* is total. It is fixed before *q*<sub>0</sub> and remains so.

&mdash; *q*<sub>0</sub> ∈ *Q* is the state the machine occupies when power is first applied.

The **environment** of a machine is what lies beyond its boundary and supplies the cells its storage comprises.

The following values are derived from the tuple.

&mdash; A **storage map** pairs every cell of storage with a symbol of *Γ*. *τ* is the storage of the machine. The storage map of *q*<sub>0</sub> is the machine’s initial storage.

&mdash; A **configuration** is a pair *c* = (*q*, *σ*): a state *q* ∈ *Q* and a signal *σ* ∈ *Σ* ∪ {ε}. The set of configurations is *C* = *Q* × (*Σ* ∪ {ε}).

&mdash; The machine passes through the sequence of configurations (*c*<sub>*s*</sub>) for *s* = 0, 1, 2, …, where the state of *c*<sub>0</sub> is *q*<sub>0</sub> and its signal is ε, and the state of *c*<sub>*s*+1</sub> is the state of *δ*(*c*<sub>*s*</sub>). The signal of *c*<sub>*s*+1</sub> is the one the environment supplies at the step where it supplies one, and the signal of *δ*(*c*<sub>*s*</sub>) otherwise. The sequence is infinite.

An implementation shall model programme execution as a Kurt machine, the **programme machine**. For each translation, it shall model two further Kurt machines, the **translation machine** and the **arbiter machine**. The clause on expressions defines the machine on which each evaluation takes place and, for a translation-time evaluation, the state in which it begins.

### Design rationale (informative)

The Kurt machine is a theory, and the computer is the phenomenon it accounts for. Each element of the tuple and each derived value corresponds to a property of the computer:

&mdash; *Q* &mdash; every part of the computer that holds a symbol.

&mdash; *Γ* &mdash; the symbols a cell of the computer can hold.

&mdash; *Σ* &mdash; interrupts, device commands, and all values exchanged through input and output.

&mdash; *δ* &mdash; the fixed interpreting logic realized as processor circuitry.

&mdash; *q*<sub>0</sub> &mdash; the computer as it stands at the instant the electric field first supplies it with enough energy to act.

&mdash; *τ* &mdash; the storage.

&mdash; *c* &mdash; the computer entire at one step, and whatever signal the boundary holds.

&mdash; (*c*<sub>*s*</sub>) &mdash; the computer advancing from that instant.

## 1.3 Scope

This specification defines the form of programmes written in the Kurt programming language and establishes the semantics of such programmes. The body comprises ten normative clauses:

&mdash; §1. General

&mdash; §2. Semantics

&mdash; §3. Lexical structure

&mdash; §4. Declarations

&mdash; §5. Types

&mdash; §6. Expressions

&mdash; §7. Statements and control flow

&mdash; §8. References and resource management

&mdash; §9. Protocols and implantations

&mdash; §10. Programme structure and translation

This specification does not specify any of the following:

&mdash; Any programme written in the language it defines.

&mdash; How source text is obtained.

&mdash; How the opaque code produced by translation is combined for execution.

&mdash; How a translated programme is invoked.

&mdash; The capacity limits of any data-processing system.

## 1.4 Conformance

A **programme** is Kurt source text composed of the constructs defined in this specification. A **conforming programme** is a programme whose translation incurs no translation failure. Source units and opaque code are defined in the clause on programme structure and translation.

An **extension** is the introduction of an element this specification does not define, other than where this specification declares it implementation defined. A **reduction** is the omission of an element this specification defines, other than where this specification permits the omission.

A **conforming implementation** is one that satisfies both of the following:

&mdash; It supports a mode in which every conforming programme is accepted and the implementation provides no extension and no reduction.

&mdash; Every execution the implementation exhibits of a programme is an admissible execution of the programme, as defined in the subclause on the ordering of τ.

An implementation need not exhibit every admissible execution of a programme.

## 1.5 Method of description and syntax notation

The syntax of the Kurt programming language is described using an Extended Backus-Naur Form (EBNF) based on ISO/IEC 14977:1996. It refines the notation in two respects: a meta-identifier may contain a low line, and a terminal string may contain an escape. `letter`, `digit`, and `character` are as defined in the clause on lexical structure. The notation uses the following conventions:

```
syntax               = syntax_rule, { syntax_rule } ;
syntax_rule          = meta_identifier, '=', definitions_list, ';' ;
definitions_list     = single_definition, { '|', single_definition } ;
single_definition    = syntactic_term, { ',', syntactic_term } ;
syntactic_term       = syntactic_factor, [ '-', syntactic_exception ] ;
syntactic_exception  = syntactic_factor
                       (* a syntactic factor containing no
                          meta-identifiers *) ;
syntactic_factor     = [ integer, '*' ], syntactic_primary ;
syntactic_primary    = optional_sequence
                     | repeated_sequence
                     | grouped_sequence
                     | meta_identifier
                     | terminal_string
                     | special_sequence
                     | empty_sequence ;

optional_sequence    = '[', definitions_list, ']' ;
repeated_sequence    = '{', definitions_list, '}' ;
grouped_sequence     = '(', definitions_list, ')' ;

terminal_string      = '\'', { terminal_char_single | escape }, '\''
                     | '\"', { terminal_char_double | escape }, '\"' ;
terminal_char_single = ? any character except apostrophe
                         or reverse solidus ? ;
terminal_char_double = ? any character except quotation mark
                         or reverse solidus ? ;
escape               = '\\', ( '\'' | '\"' | '\\' ) ;
meta_identifier      = letter, { letter | digit | '_' } ;
integer              = digit, { digit } ;
special_sequence     = '?', { character - '?' }, '?' ;
empty_sequence       = ;
```

The symbols of Extended BNF used in this specification are:

&mdash; `,` (comma) &mdash; concatenation: the items appear in sequence, lexically adjacent. Whitespace shall not appear between them unless the nonterminal `ws` is written at the concatenation point.

&mdash; `|` &mdash; alternation: separates alternative definitions.

&mdash; `=` &mdash; defining symbol: introduces a production rule.

&mdash; `;` &mdash; closing symbol: ends a production rule.

&mdash; `[ ... ]` &mdash; optional: the enclosed sequence may appear zero or one time.

&mdash; `{ ... }` &mdash; repetition: the enclosed sequence may appear zero or more times.

&mdash; `( ... )` &mdash; grouping: overrides precedence.

&mdash; `"..."` and `'...'` &mdash; terminal string: a fixed sequence of characters. The two quotation forms are equivalent. Within each form, the enclosing quotation mark, the other quotation mark, and `\` are each escaped with a preceding `\`.

&mdash; `(* ... *)` &mdash; comment: explanatory text, no formal effect.

&mdash; `-` &mdash; exception: the sequence defined by the first operand, excluding sequences defined by the second.

&mdash; `? ... ?` &mdash; special sequence: a construct that cannot be expressed in pure EBNF, its meaning defined by surrounding prose.

This specification encloses a keyword in quotation marks and every other terminal string in apostrophes.

Where the grammar derives a construct by more than one production, the construct is the one the static semantics of this specification permit. A construct they permit as more than one, with a different meaning under each, shall not appear.

The following terms carry the meanings defined here throughout the ten normative clauses of this specification.

&mdash; **shall** &mdash; a normative requirement. A conforming implementation always satisfies what it requires of the implementation, and violating it constitutes non-conformance. A violation of what it requires of a programme has the effect that the subclause on translation failure and the rule that states the requirement define.

&mdash; **shall not** &mdash; a normative prohibition. A conforming implementation always abstains from what it prohibits of the implementation, and violating it constitutes non-conformance. A violation of what it prohibits of a programme has the effect that the subclause on translation failure and the rule that states the prohibition define.

&mdash; **should** &mdash; a normative recommendation. An implementation or programme is encouraged to satisfy what it recommends. An implementation that violates it does not by itself fail to conform, and a programme that violates it does not by that violation incur a translation failure.

&mdash; **should not** &mdash; a normative discouragement. An implementation or programme is encouraged to refrain from what it discourages. An implementation that violates it does not by itself fail to conform, and a programme that violates it does not by that violation incur a translation failure.

&mdash; **may** &mdash; a permission. An implementation or programme is free to do what it permits, or not to.

&mdash; **need not** &mdash; the absence of a requirement.

&mdash; **can** / **cannot** &mdash; a statement of capability or of its absence. It is descriptive and imposes no requirement.

&mdash; **implementation defined** &mdash; a choice the implementation makes. The implementation shall document it.

&mdash; **translation time** &mdash; the period during which the implementation translates source units.

&mdash; **execution time** &mdash; the period during which the programme machine executes the opaque code.

Each subclause in this specification follows the heading structure defined in the annex on editorial rules. Informative text is marked as such and does not impose requirements on implementations or programmes.

An example shows only what it illustrates. Whatever else it requires &mdash; in particular the declaration of every name it uses but does not itself declare &mdash; the surrounding programme provides.
