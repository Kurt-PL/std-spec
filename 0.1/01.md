# §1. General

This clause fixes the axioms, the machine, the conformance criteria, and the notation that the remainder of this specification rests upon.

## 1.1 Founding axioms

This specification is derived from two foundational axioms.

### Axiom 1 — The computer is a machine

A machine is caused to act by every condition, and alike by the same. The computer is such a machine, and it calculates while powered.

### Axiom 2 — The language is self-contained

This specification is the sole definition of the Kurt programming language; an explicit delegation is part of the definition.

## 1.2 The Kurt machine

The **Kurt machine** is the formal object from which all semantic definitions in this specification are derived. It is a 5-tuple *K* = (*Q*, *Γ*, *Σ*, *δ*, *q*<sub>0</sub>), where:

— *Q* is a finite, non-empty set of states.

— *Γ* is the cell alphabet. It is the set of integers from zero to one less than the number of its members, and it has more than one member.

— *Σ* is the signal alphabet.

— *δ* is the transition function.

— *q*<sub>0</sub> ∈ *Q* is the initial state.

The elements of the tuple are characterized as follows.

— *Q* is the set of states the machine can occupy. A state is the whole of the machine apart from the boundary.

— *Γ* is the set of symbols storage can hold. The cells of storage, the number of symbols of *Γ*, and the addressing of cells are defined in the clause on semantics.

— *Σ* is the set of values that cross the boundary between the machine and its environment. A signal originates from the machine or from the environment. The symbol ε denotes the absence of a signal at the boundary.

— *δ* : *C* → *C*, where *C* is the set of configurations. *δ* is total and immutable: it is defined for every configuration, and it is fixed before *q*<sub>0</sub> and remains so throughout execution.

— *q*<sub>0</sub> is the state the machine occupies when power is first applied.

The **environment** of a machine is what lies beyond its boundary and supplies the cells its storage comprises.

The following values are derived from the tuple.

— A **storage map** pairs every cell of storage with a symbol of *Γ*. *T* is the set of storage maps. *τ* is the storage of the machine; the storage map of *q*<sub>0</sub> is the programme’s initial storage, and what *τ* holds at a cell thereafter is defined in the clause on semantics.

— A **configuration** is a pair *c* = (*q*, *σ*): a state *q* ∈ *Q* and a signal *σ* ∈ *Σ* ∪ {ε}. The set of configurations is *C* = *Q* × (*Σ* ∪ {ε}).

— The machine passes through the sequence of configurations (*c*<sub>*s*</sub>) for *s* = 0, 1, 2, …, where the state of *c*<sub>0</sub> is *q*<sub>0</sub> and the state of *c*<sub>*s*+1</sub> is the state of *δ*(*c*<sub>*s*</sub>). The signal of *c*<sub>*s*+1</sub> is the one the environment supplies at the step where it supplies one, and the signal of *δ*(*c*<sub>*s*</sub>) otherwise. The sequence is infinite.

A conforming implementation shall model programme execution as a Kurt machine.

### Design rationale (informative)

The Kurt machine is derived from the physical computer. Each element of the tuple and each derived value corresponds to a property of the physical machine:

— *Q* — every part of the physical machine that holds a symbol.

— *Γ* — the symbols a cell of the physical machine can hold.

— *Σ* — interrupts, device commands, and all values exchanged through input and output.

— *δ* — the fixed interpreting logic realized as processor circuitry.

— *q*<sub>0</sub> — the machine as it stands at the instant the first electrons reach *δ*.

— *T* — the set of all possible contents of the storage of the physical machine.

— *τ* — the contents of the storage at a given instant.

— *c* — the physical machine entire at one step, and whatever signal the boundary holds.

— (*c*<sub>*s*</sub>) — the machine advancing from the instant power is applied.

## 1.3 Scope

This specification defines the form of programmes written in the Kurt programming language and establishes the interpretation of such programmes. The body comprises ten normative clauses:

— §1. General — establishes the axiomatic foundation, the formal computational model, the conformance framework, and the syntax notation.

— §2. Semantics — defines the δ model, the τ model, reachability and indeterminacy, σ operations, the uniformity rule, the airside/landside boundary, and the classification of errors.

— §3. Lexical structure — defines the source encoding, tokens, identifiers, keywords, literals, comments, and punctuation.

— §4. Types — defines the built-in types and their representations, value sets, and storage layout rules.

— §5. Declarations — defines `fn`, `let`, `const`, `static`, composite types, `struct`, `enum`, `type` aliases, generics, variadic subroutines, patterns and destructuring, `with` clauses, visibility (`pub`, `use`), `asm`, `#inline`/`#no_inline`, `#symbol`, and `#[...]#` annotations.

— §6. Expressions — defines the expression hierarchy: primary, postfix, unary, binary, cast, and special forms; assignment and all operators and their semantics; `airside` and `xlat` blocks; the `xlat?` conditional; the evaluation-model semantics of translation-time evaluation; inline `asm`; type intrinsics (`'size`, `'align`, `'offset`, `'bound`); and the precedence table.

— §7. Statements and control flow — defines blocks and statements, contract types, `if`, `match`, `while`, `loop`, `return`, `break`, `continue`, `express`, labelled blocks, and `trap`.

— §8. References and resource management — defines reference families and modifiers, the derivation tree, object lifetime, atomic references and ordering fences, unmanaged references, compare-and-swap, copy and transfer semantics, assignment semantics, and destructors (`with destruct`, `destruct()`, `undestruct`).

— §9. Protocols and implementations — defines inherent `impl`, method declarations, protocol declarations, protocol `impl`, protocol objects (`dyn`), descriptors, and built-in bounds.

— §10. Programme structure and translation — defines source processing order, `#add`, `#dyn`, `#path`, `module`, the conditional translation directives (`#flag`, `#unflag`, `#flag_if`, `#flag_else_if`, `#flag_else`, `#flag_endif`), and translation units.

This specification does not specify any of the following:

— any programme written in the language it defines;

— the mechanism by which source text is obtained;

— the mechanism by which the opaque code produced by translation is combined for execution;

— the mechanism by which a translated programme is invoked;

— the capacity limits of any data-processing system.

## 1.4 Conformance

A **programme** is Kurt source text composed of the constructs defined in this specification. A **conforming programme** is a programme that the grammar of this specification admits and that satisfies every requirement this specification imposes on the programme. A source unit is the text submitted for translation at one time, and the opaque code is what a conforming implementation produces from it; both are defined in the clause on programme structure and translation.

A **conforming implementation** is one that satisfies all of the following:

— It supports a mode of operation in which every conforming programme is accepted.

— For every conforming programme, every execution the implementation exhibits of it is an execution the programme admits, as defined in the subclause on the ordering of τ. An implementation need not exhibit every such execution.

— It rejects every source unit that contains a translation failure, as defined in the clause on semantics, and issues a diagnostic that identifies the violated requirement.

— It documents every implementation-defined behaviour.

An implementation that is not a conforming implementation is **non-conforming**. A non-conforming implementation shall not claim conformance to this specification or certification against it.

A conforming implementation may provide extensions, provided they do not alter the behaviour of any conforming programme. An extension shall not assign special semantics to a subroutine, type, or namespace based on its name or path. The semantics of a declaration are determined by its syntactic form and its `with` clause.

## 1.5 Method of description and syntax notation

The syntax of the Kurt programming language is described using an Extended Backus-Naur Form (EBNF) based on ISO/IEC 14977:1996. It refines the notation in two respects: a meta-identifier may contain a low line, and a terminal string may contain an escape. *Letter*, *digit*, and *character* are as defined in the clause on lexical structure. *Type*, *expression*, and *declaration* each denote the forms the clause that defines them admits — the clauses on types, on expressions, and on declarations respectively. Every production fixes the placement of inter-token whitespace. The notation uses the following conventions:

```
syntax               = syntax_rule, { syntax_rule } ;
syntax_rule          = meta_identifier, '=', definitions_list, ';' ;
definitions_list     = single_definition, { '|', single_definition } ;
single_definition    = syntactic_term, { ',', syntactic_term } ;
syntactic_term       = syntactic_factor, [ '-', syntactic_exception ] ;
syntactic_exception  = syntactic_factor
                       (* a syntactic factor containing no
                          meta-identifiers *) ;
syntactic_factor     = [ integer, '*' ], syntactic_primary ;
syntactic_primary    = optional_sequence
                     | repeated_sequence
                     | grouped_sequence
                     | meta_identifier
                     | terminal_string
                     | special_sequence
                     | empty_sequence ;

optional_sequence    = '[', definitions_list, ']' ;
repeated_sequence    = '{', definitions_list, '}' ;
grouped_sequence     = '(', definitions_list, ')' ;

terminal_string      = '\'', { terminal_char_single | escape }, '\''
                     | '\"', { terminal_char_double | escape }, '\"' ;
terminal_char_single = ? any character except apostrophe
                         or reverse solidus ? ;
terminal_char_double = ? any character except quotation mark
                         or reverse solidus ? ;
escape               = '\\', ( '\'' | '\"' | '\\' ) ;
meta_identifier      = letter, { letter | digit | '_' } ;
integer              = digit, { digit } ;
special_sequence     = '?', { character - '?' }, '?' ;
empty_sequence       = ;
```

The symbols of Extended BNF used in this specification are:

— `,` (comma) — concatenation: the items appear in sequence, lexically adjacent. Whitespace shall not appear between them unless the nonterminal `ws` is written at the concatenation point.

— `|` — alternation: separates alternative definitions.

— `=` — defining symbol: introduces a production rule.

— `;` — terminator: ends a production rule.

— `[ ... ]` — optional: the enclosed sequence may appear zero or one time.

— `{ ... }` — repetition: the enclosed sequence may appear zero or more times.

— `( ... )` — grouping: overrides precedence.

— `"..."` and `'...'` — terminal string: a literal sequence of characters. The two quotation forms are equivalent; each permits the other quotation mark to appear without escaping. Within each form, the enclosing quotation mark is escaped with a preceding `\`, as is `\` itself.

— `(* ... *)` — comment: explanatory text, no formal effect.

— `-` — exception: the sequence defined by the first operand, excluding sequences defined by the second.

— `? ... ?` — special sequence: meaning defined by surrounding prose; used for constructs that cannot be expressed in pure EBNF.

This specification writes a keyword in the double-quoted form and every other terminal string in the single-quoted form. The keyword list in the clause on lexical structure, and not the quotation form, determines whether a terminal string is a keyword.

In addition, the following verbal forms are used throughout this specification with the meanings defined here:

— **shall** — a normative requirement. A conforming implementation or programme always satisfies it. Failing to satisfy it constitutes non-conformance.

— **shall not** — a normative prohibition. A conforming implementation or programme never exhibits the described behaviour. Exhibiting it constitutes non-conformance.

— **should** — a normative recommendation. A conforming implementation or programme is encouraged to follow it. Deviation does not by itself constitute non-conformance.

— **should not** — a normative discouragement. A conforming implementation or programme refrains from the described behaviour. Engaging in it does not by itself constitute non-conformance.

— **may** — a permission. A conforming implementation or programme is free to satisfy the described behaviour or to omit it; either choice conforms to this specification.

— **need not** — the absence of an obligation. A conforming implementation or programme may, but is not required to, satisfy the described behaviour.

— **can** / **cannot** — descriptive, not normative. They describe a capability or its absence within the framework of this specification, and impose no obligations.

— **implementation defined** — the implementation chooses the behaviour and shall document the choice.

— **translation environment** — the environment in which the implementation translates source units.

— **execution environment** — the environment in which the translated programme executes.

— **translation time** — the period during which the implementation translates source units.

— **execution time** — the period during which the translated programme executes.

Each subclause in this specification follows the heading structure defined in the annex on editorial rules, omitting each heading that has no applicable content. Informative text is marked as such and does not impose obligations on implementations or programmes.

An example shows only what it illustrates. Whatever else it requires — in particular the declaration of every name it uses but does not itself declare — the surrounding programme provides.
