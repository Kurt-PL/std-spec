# 6. Expressions

This clause defines the expressions of the Kurt programming language: their kinds and operators, assignment, casting, the `airside`, `xlat`, and `const` blocks, inline `instruct` blocks, the type intrinsics, and operator precedence.

## 6.1 Expression kinds

Every expression has a type. Every expression is either an **object expression**, which designates an object, or a **value expression**, which designates a computed value. Where an operation uses the value of an object expression, the expression yields its object’s current value.

An object expression is **storable** at a programme point where a store through it is permitted. A projection, as defined in the clause on references and resource management, is storable at no programme point.

The precedence and associativity of the operators defined in this clause are given in the subclause on operator precedence and associativity.

### Syntax

```
expression   = primary_expr | postfix_expr | unary_expr | binary_expr
             | cast_expr | special_expr | control_expr ;

primary_expr = identifier_expr | literal | paren_expr
             | composite_literal | contract_construct
             | wild_construction
             | array_literal | repeat_literal | tuple_literal
             | uninit_expression | cellbits_expr ;

postfix_expr = invocation_expr | instance_expr | field_access
             | method_invocation | propagation_expr ;

unary_expr   = negation_expr | identity_expr | not_expr | deref_expr
             | ref_shared_expr | ref_exclusive_expr
             | ref_unmanaged_expr ;

binary_expr  = arith_expr | bitwise_expr | comparison_expr
             | logical_expr | assignment_expr | compound_assign
             | cas_expr ;

special_expr = airside_block | xlat_block | const_block
             | eval_cond_block | eval_cond_expr | instruct_block
             | type_intrinsic | destruct_invocation | undestruct_expr
             | volatile_fence | guard_fence ;

control_expr = block | labelled_block
             | if_block | if_expr | if_let_block | if_let_expr
             | match_expression | while_block | while_expr
             | loop_expression | extraction_block | extraction_expr
             | return_expression | break_expression
             | continue_expression
             | express_expression | trap_invocation ;
```

`literal` and `cellbits_expr` are defined in the clause on lexical structure and in the clause on types. `contract_construct`, `logical_expr`, and every alternative of `control_expr` are defined in the clause on statements and control flow. `cas_expr`, `destruct_invocation`, `undestruct_expr`, `volatile_fence`, and `guard_fence` are defined in the clause on references and resource management. Every other alternative is defined in this clause.

## 6.2 Primary expressions

### 6.2.1 Identifier expression

#### Syntax

```
identifier_expr     = single_path | "self" ;
single_path         = path_root, { ws, '::', ws, path_segment } ;
path_root           = path_segment
                    | qualified_path_root ;
path_segment        = identifier, [ ws, generic_args ]
                    | "super" | "srcroot" ;
qualified_path_root = '(', ws, type, ws, "as", ws,
                      single_path, ws, ')' ;
```

The `generic_args` production is defined in the subclause on generic declarations.

#### Static semantics

An **identifier expression** resolves a name to its binding or to the named item it denotes. The name is looked up in the enclosing scope. Where it is not found there, the search proceeds outward through enclosing scopes until a matching declaration is found, a `module` is exhausted, or the source unit scope is exhausted. `self` names the binding the innermost enclosing self parameter or `with destruct` block introduces.

A **path expression** resolves a qualified name: a sequence of identifiers separated by `::`, optionally rooted at a **qualified path root** of the form `(T as Protocol)`. What the path denotes is defined in the clause on programme structure and translation.

A qualified path root `(T as Protocol)` selects the namespace of `Protocol` as implemented by `T`. The path that follows accesses an associated subroutine or an associated constant that `Protocol` declares.

An identifier expression is an object expression when it names a binding. It is a value expression when it names a `const` declaration, an associated constant, a dependence parameter, a subroutine, or an enum unit variant.

#### Dynamic semantics

An identifier expression that names a binding designates its object. Evaluating one that names a `const` declaration yields the resulting value of its initializer, which an evaluation on each machine that names it reaches once, at translation time. Evaluating one that names an associated constant yields the resulting value of its expression, as defined in the clause on protocols and implementations. Evaluating one that names a dependence parameter yields the value of the dependence argument. For subroutine names and enum unit variants, the expression yields the subroutine value or the variant value respectively.

#### Constraints

An identifier expression naming no matching declaration shall not appear.

A path that resolves to no declaration shall not appear. The final component of a path in expression position shall not name a namespace.

#### Examples (informative)

```
let x: si4 = 42;

// identifier expression — resolves to the binding x
x;

// path expression — resolves to the variant red of enum colour
colour::red;
// path expression — resolves to the associated constant max on si4
si4::max;
// path expression — resolves to the subroutine write in module io
io::write;

// Qualified path root — disambiguates protocol items

// associated constant from bounded impl on ui1
(ui1 as bounded)::min;
// associated subroutine from defaulted impl on si4
(si4 as defaulted)::default();
```

### 6.2.2 Literal expression

#### Static semantics

A literal expression is the syntactic occurrence of a literal value in source text. The forms of literals, and the rules that fix the type of each, are defined in the clause on lexical structure. Each literal form is a value expression.

### 6.2.3 Parenthesized expression

#### Syntax

```
paren_expr = '(', ws, expression, ws, ')' ;
```

#### Static semantics

A parenthesized expression binds as a single operand within the expression that encloses it, whatever the default precedence and associativity would give. The type of a parenthesized expression is that of the enclosed expression, and it is an object expression where the enclosed expression is one.

#### Examples (informative)

```
let x = (a + b) * c; // forces addition before multiplication
let y = -(a + b);    // negation applies to the sum
```

### 6.2.4 Composite literal

#### Syntax

```
composite_literal = single_path,
                    [ ws, '.', ws, '{', ws,
                      [ expression_list | field_init_list ], ws,
                      '}' ] ;

expression_list   = expression, ws, { ',', ws, expression, ws },
                    [ ',', ws ] ;
field_init_list   = field_init, ws, { ',', ws, field_init, ws },
                    [ ',', ws ] ;
field_init        = '.', identifier, ws, '=', ws, expression ;
```

#### Static semantics

A **composite literal** constructs a value of a composite type. The three forms correspond to the three composite type forms:

— **Unit literal** — the identifier alone. The expression yields the sole value of the type.

— **Unnamed-field literal** — the identifier followed by `.` and an expression list enclosed by curly brackets. Each expression corresponds to a field by position, in declaration order.

— **Named-field literal** — the identifier followed by `.` and a field initializer list enclosed by curly brackets. Each initializer names its target field.

The first initializer determines the form: if its token sequence matches `'.' identifier '='`, the body is a `field_init_list`; otherwise it is an `expression_list`.

A composite literal is a value expression.

#### Dynamic semantics

For a unit literal, no evaluation occurs.

For an unnamed-field literal, expressions are evaluated in source order, each evaluated before the next begins.

For a named-field literal, field initializers are evaluated in source order, each evaluated before the next begins. Default-value expressions for omitted fields are evaluated after all explicit initializers, in the declaration order of the omitted fields, each evaluated before the next begins.

#### Constraints

A path that names a type or a variant, written as an expression without a composite form, shall name one in unit form.

Every field that carries no default-value expression, other than a `?` field, shall be initialized exactly once in the literal. A field that carries one shall be initialized at most once. In an unnamed-field literal a field is initialized by the expression at its position, so the expressions shall fill a leading run of the fields.

A `?` field shall be initialized by no literal. It is initialized to zero at construction, as defined in the clause on types.

#### Examples (informative)

```
// Unit literal
struct empty_t;
let v = empty_t;

// Named-field literal
struct point { x: si4, y: si4 }
let p = point.{ .x = 1, .y = 2 };

// Unnamed-field literal
struct pair { si4, si4 }
let q = pair.{ 1, 2 };

// Enum variant literals
enum shape {
    circle { fe11s52 },
    rect { fe11s52, fe11s52 }
}

let s1 = shape::circle.{ 1.5 };
let s2 = shape::rect.{ 3.0, 4.0 };

// Defaults omitted
struct origin_point { x: si4 = 0, y: si4 = 0 }
let o = origin_point.{};

// Source-order evaluation — compute_y is invoked before compute_x
let r = point.{ .y = compute_y(), .x = compute_x() };
```

### 6.2.5 Wild construction

`EnumType::wild` yields a value that no declared variant of the enum covers.

#### Syntax

```
wild_construction = single_path, ws, '::', ws, "wild" ;
```

#### Static semantics

A wild construction is a value expression.

#### Constraints

A wild construction that yields no value shall not appear.

#### Implementation defined

The value a wild construction yields is implementation defined.

#### Examples (informative)

```
enum empty {}
let w1 = empty::wild;

enum colour { red, green, blue }
let w2 = colour::wild;
```

### 6.2.6 Array literal and repeat literal

#### Syntax

```
array_literal  = '[', ws, [ expression, ws, { ',', ws, expression, ws },
                 [ ',', ws ] ], ']' ;
repeat_literal = '[', ws, expression, ws, ';', ws, expression, ws, ']' ;
```

#### Static semantics

An **array literal** `[e1, e2, ..., eN]` is an expression of type `[T; N]`, where `T` is the common type of all element expressions and `N` is the number of elements. Where the literal has no element expression, `T` is determined by checking alone, as the clause on types defines checking.

A **repeat literal** `[expr; N]` is an expression of type `[T; N]`, where `T` is the type of `expr` and `N`, the length expression of that type, is an expression of type `uaddr`.

Both forms are value expressions.

#### Dynamic semantics

In an array literal, element expressions are evaluated in source order, each evaluated before the next begins.

In a repeat literal, `N` is evaluated before the initializer expression begins, and the initializer expression is evaluated once. The resulting value is stored into all `N` elements by copy.

#### Constraints

All elements of an array literal shall have a common type.

A repeat literal shall not appear where `T` is not copyable.

#### Examples (informative)

```
let arr = [10, 20, 30];             // [saddr; 3]
let zeros: [ui1; 4096] = [0; 4096]; // repeat literal
```

### 6.2.7 Tuple literal

#### Syntax

```
tuple_literal = '.', ws, '{', ws, expression, ws,
                { ',', ws, expression, ws }, [ ',', ws ], '}' ;
```

#### Static semantics

A tuple literal `.{ e1, e2, ..., eN }` is an expression of type `.{T1, T2, ..., TN}`, where each `Ti` is the type of the corresponding element expression.

A tuple literal is a value expression. Element expressions are evaluated in source order, each evaluated before the next begins.

#### Examples (informative)

```
// pair: .{saddr, verdict[void, void]}
let pair = .{ 42, verdict[void, void]::Pass(void) };
// triple: .{saddr, fe8s23, verdict[void, void]}
let triple = .{ 1, 2.0, verdict[void, void]::Fail(void) };
```

### 6.2.8 Uninitialized value introduction

#### Syntax

```
uninit_expression = "uninit" ;
```

#### Static semantics

`uninit` is a value expression whose result is an **uninitialized value**.

Its type is determined by checking alone, as the clause on types defines.

#### Dynamic semantics

An uninitialized value is in one of two states.

— **Contained** — a value `uninit` yields is contained.

— **Escaped** — a contained value becomes escaped where a reference that permits stores to an object holding it is passed as an argument to a subroutine imported via `#dyn` or appears as an operand of an `instruct` block.

Where the implementation defines no value for an `uninit` expression, a store performs no write of the value of such an expression where that expression is the one whose value the store stores, or is reached from that one through literals and parenthesized expressions alone. Each step of that reach passes to the enclosed expression of a parenthesized expression, to an element expression of a tuple literal or an array literal, to the initializer expression of a repeat literal, or to an expression that initializes a field of a composite literal. Where it defines none and the value of the expression is not so stored, the expression yields the value that a load yields from storage reserved for it, at which no write has been performed since its reservation. Where a reference that does not permit stores to an object holding an uninitialized value is passed or appears in the way that makes a contained value escaped, a load from that object occurs at that point.

An object ceases to hold an uninitialized value when a value other than `uninit` is stored into it, by direct assignment or through a reference that permits stores.

#### Constraints

An `uninit` expression requires airside.

#### Implementation requirements

The implementation shall issue an advisory diagnostic at the first operation upon a contained uninitialized value, and at the first managed-reference creation on an object holding one. It should do the same where the value is escaped, and may do so at any subsequent such operation or creation in either state.

#### Implementation defined

The value an `uninit` expression yields is implementation defined, and the implementation may define none.

#### Examples (informative)

```
// FFI out-parameter via unmanaged reference
let y = airside {
    let mut x: large_t = uninit; // contained
    // store-permitting reference to #dyn — contained → escaped
    foreign_init(%mut x);
    // first load in escaped — the implementation should issue an
    // advisory diagnostic
    express x;
};

// Local store exits the state
airside {
    let mut w: si4 = uninit; // contained
    // load-only reference to #dyn — load in contained — the
    // implementation shall issue an advisory diagnostic
    foreign_peek(%w);
    w = 0; // contained exited — no diagnostic
    express w;
}

// uninit in non-initializer assignment
airside {
    let mut x = 0; // normal
    x = uninit;    // contained
    // first load in contained — the implementation shall issue an
    // advisory diagnostic
    express x;
}

// argument position — the parameter type checks it
let random_seed = airside { express randgen(uninit); };

// translation failure — no annotation, and uninit supplies no type
// airside {
//     let mut z = uninit;
// }
```

## 6.3 Postfix expressions

A postfix expression is formed by appending an operator or operand list to the following side of a primary expression or another postfix expression.

### 6.3.1 Subroutine invocation

#### Syntax

```
invocation_expr = expression, ws, '(', ws, [ argument_list ], ws, ')' ;
argument_list   = expression, ws, { ',', ws, expression, ws },
                  [ ',', ws ] ;
instance_expr   = expression, ws, generic_args ;
```

#### Static semantics

A subroutine invocation expression invokes the subroutine designated by the leading expression.

The type of a subroutine invocation expression is the return type of the invoked subroutine. Where the invocation is a diverging expression, synthesis of its type is undetermined, and its default type is `void`. A subroutine invocation, and an expression that ends in a generic argument list after an expression, are value expressions.

#### Dynamic semantics

The leading expression is evaluated before the arguments. Arguments are evaluated in source order. Each argument is evaluated before the next begins. The resulting values are copied or transferred into the parameter bindings of the invoked subroutine. When the subroutine carries the `variadic` modifier, arguments beyond the fixed parameters are evaluated in source order after the last fixed argument. These values are passed through the variadic variant of the invoked subroutine’s invocation interface and are accessible through the variadic binding within the invoked subroutine.

After all arguments have been evaluated, control transfers to the subroutine body. When the subroutine returns, the return value is the value of the invocation expression.

#### Constraints

The leading expression of a subroutine invocation shall have a subroutine pointer type.

The number of arguments shall equal the number of parameters of the type of the leading expression, or, in a method invocation, of the declaration of the method it resolves to, other than its self parameter, unless that type carries the `variadic` keyword. Each argument shall be assignable to the corresponding parameter’s type.

An invocation of a subroutine carrying the `variadic` modifier shall provide at least the fixed parameters.

An invocation expression that invokes a variadic subroutine through a subroutine pointer shall use a subroutine pointer type that carries the `variadic` keyword, as defined in the clause on types.

#### Examples (informative)

```
// direct subroutine invocation
let sum = add(2, 3);
// generic subroutine invocation with explicit type argument
let val = get_default[si4]();

// subroutine pointer invocation
use ext::get_info;
let callback: fn(si2) -> result = get_info;
let r = callback(42);

// Source-order evaluation: a() is invoked first, then b(), then c()
foo(a(), b(), c());
```

### 6.3.2 Field access

#### Syntax

```
field_access = expression, ws, '.', ws, identifier
             | expression, ws, '.', ws, integer_literal ;
```

#### Static semantics

A field access expression `e.f` designates the field named `f` in the type of `e` after reference transparency. The expression `e` — to the leading side of the `.` token here and in a method invocation — is the **receiver**. The result type is the type of the field.

For struct types, `f` names a declared field. For tuple types and unnamed-field variant payloads, `f` is an index into the fields in declaration order.

A field access is an object expression when the receiver is an object expression or has a reference type; otherwise it is a value expression. A multi-assignment binding permits a store to its field, and a reference permits one where the store permission defined in the clause on references and resource management grants it. Where the receiver permits no store, the field is storable where the per-field store permission defined in the clause on declarations permits it.

The built-in fields of array types (`.ptr` and `.len`) are accessed by the same field access form. Their access rules are defined in the clause on references and resource management.

#### Constraints

For struct types, `f` shall be an identifier matching a declared field name. For tuple types and unnamed-field variant payloads, `f` shall be an integer literal in the range `[0, N)`, where `N` is the number of fields.

#### Examples (informative)

```
let p = point.{ .x = 1, .y = 2 };
p.x;     // field access on a value — yields si4

let pair = .{ 42, verdict[void, void]::Pass(void) };
pair.0;  // positional field access — yields saddr
pair.1;  // positional field access — yields verdict

let arr = [10, 20, 30];
arr.len; // built-in field — yields 3~uaddr (projection)
arr.ptr; // built-in field — yields %saddr (projection)
```

### 6.3.3 Method invocation

#### Syntax

```
method_invocation           = expression, ws, '.', ws, identifier,
                              [ ws, generic_args ], ws,
                              '(', ws, [ argument_list ], ws, ')'
                            | qualified_method_invocation ;
qualified_method_invocation = '(', ws, expression, ws, "as", ws,
                              single_path, ws, ')', ws, '.', ws,
                              identifier, [ ws, generic_args ], ws,
                              '(', ws, [ argument_list ], ws, ')' ;
```

#### Static semantics

A method invocation expression `e.m(args)` invokes the method named `m` on the receiver `e` after reference transparency. The resolution of `m` is defined in the subclause on name resolution in the clause on protocols and implementations.

A **qualified method invocation** `(e as Protocol).m(args)` invokes the method named `m` from an implementation of `Protocol`.

The type of a method invocation expression is the return type of the resolved method. Where the invocation is a diverging expression, synthesis of its type is undetermined, and its default type is `void`. A method invocation is a value expression.

#### Dynamic semantics

The receiver is evaluated before the arguments. The subclause on subroutine invocation governs the rest of the invocation.

#### Constraints

In a qualified method invocation, `Protocol` shall declare a method named `m`.

#### Examples (informative)

```
struct counter { pub val: uaddr }

impl counter {
    pub fn get(&self) -> uaddr { return (*self).val; }
    pub fn increment($self) { self.val += 1; }
}

let c_ref: &counter = &some_counter;
c_ref.get();   // OK — method invocation on &counter

// Qualified method invocation
// disambiguates inherent/protocol or protocol/protocol collision
(value as fmt).fmt(&buf);
// invokes the fmt method from the fmt impl
```

### 6.3.4 Contract propagation

#### Syntax

```
propagation_expr = expression, ws, '?' ;
```

#### Static semantics

The type of the `?` expression is the success payload type of the operand.

#### Dynamic semantics

1. The operand `e` is evaluated.
2. If the value is a success variant, the payload is extracted and becomes the result of the `?` expression.
3. If the value is a failure variant, the payload is extracted, and the enclosing subroutine performs an early return with a failure-variant value containing the extracted payload.

#### Constraints

The operand `e` shall have a contract type.

The enclosing subroutine’s return type shall be a contract type, and the failure payload type of the operand shall exactly match the failure payload type of the enclosing subroutine’s return type.

#### Examples (informative)

```
fn read_config(path: &[ui1]) -> verdict[config, io_error] {
    let file = open(path)?;     // propagates io_error on failure
    let data = read_all(file)?; // propagates io_error on failure
    return parse(data);
}
```

### 6.3.5 Reference transparency

#### Static semantics

When the expression to the leading side of `.` has a reference type, the field or method is looked up in the referent type `T`. This transparency applies exactly once.

An access to a discriminant, a field, an element, or a payload that the referent type places within its layout, directly or within another it so places, is performed through the reference the receiver yields. For unmanaged references, the access made through this transparency requires airside, as the dereference of an unmanaged reference does.

#### Examples (informative)

```
struct point { pub x: si4, pub y: si4 }
let p = point.{ .x = 1, .y = 2 };
let r: &point = &p;
r.x;     // OK — equivalent to (*r).x, yields 1

let rr: &&point = &r;
// rr.x; // translation failure — &point has no field named x
```

### 6.3.6 Automatic referencing

#### Static semantics

Where the receiver’s type does not match the method’s self parameter, the receiver is adjusted to the type the self parameter names. The adjustment is at most one reference creation or one reference cast, followed by the implicit casts the position of the self parameter requires, and the constraints upon that creation and upon each cast apply to it. A value is adjusted to an exclusive reference or to a shared reference, an exclusive reference is adjusted to a shared reference, and a reference carrying `mut` is adjusted to one that does not carry it. No other adjustment is permitted.

#### Examples (informative)

```
let mut m: counter = counter.{ .val = 0 };
m.increment();    // auto-ref: value → $counter to satisfy $self
m.get();          // auto-ref: value → &counter to satisfy &self

let r: &counter = &m;
r.get();          // OK — &self already satisfied
// r.increment(); // translation failure — &counter cannot satisfy $self
```

## 6.4 Unary expressions

### 6.4.1 Negation and identity

#### Syntax

```
negation_expr = '-', ws, expression ;
identity_expr = '+', ws, expression ;
```

#### Static semantics

Unary negation (`-expr`) and unary identity (`+expr`) require the operand to satisfy `numeric`. The result type is the operand’s type `T`. Each is a value expression.

Unary identity yields the value of its operand.

Unary negation yields the following.

— Signed integer types — the result is the arithmetic negation. When the operand is the minimum value of the type, the result wraps to that same value.

— Unsigned integer types — the result is the two’s complement negation. The value is 2<sup>*W*<sub>t</sub></sup> − *x* for non-zero `x`, and `0` for `x == 0`.

— Floating radix point number types — unary negation flips the sign bit. All other bits are preserved.

#### Examples (informative)

```
let a: si4 = -42;      // signed negation
let b: ui4 = -1~ui4;   // two’s complement: 0xFFFFFFFF
let c: fe11s52 = -0.0; // negative zero
```

### 6.4.2 Not

#### Syntax

```
not_expr = '!', ws, expression ;
```

#### Static semantics

The `!` operator has two meanings, determined by the type of the operand:

— Bitwise NOT — when the operand satisfies `integer`, `!x` yields the bitwise complement of `x`, the value whose bit at each position `k` is `1` if and only if the bit at position `k` in `x` is `0`. The result type is `T`.

— Contract polarity inversion — defined in the clause on statements and control flow.

A `!` expression is a value expression.

#### Constraints

A `!` expression whose operand neither satisfies `integer` nor is a contract type that declares `inv` shall not appear.

#### Examples (informative)

```
let a: ui4 = 0xFF00_FF00~ui4;
let b = !a; // 0x00FF_00FF~ui4 — bitwise NOT

let v: verdict[si4, si4] = verdict::Pass(42);
let w = !v; // verdict::Fail(42) — polarity inversion
```

### 6.4.3 Dereference

#### Syntax

```
deref_expr = '*', ws, expression ;
```

#### Static semantics

A dereference expression is an object expression. It designates the referent of its operand, and its type is the referent type. An access through it to the object it designates, or to a discriminant, a field, an element, or a payload the referent type places within its layout, directly or within another it so places, is performed through the reference its operand yields.

#### Constraints

The operand of `*` shall have a reference type. Its referent type shall be one the `type` production of the clause on types yields, and shall not be a protocol type.

A dereference of an unmanaged reference requires airside, other than the dereference a re-reference performs.

#### Examples (informative)

```
let x: si4 = 42;
let r: &si4 = &x;
let val = *r; // dereference — yields 42

let mut y: si4 = 0;
let e: $si4 = $y;
*e = 99; // store through exclusive reference

airside {
    let p = 0x4000_1000~uaddr as %volatile mut ui4;
    *p = 0xDEAD_BEEF; // volatile store through unmanaged reference
    let v = *p;       // volatile load through unmanaged reference
}
```

### 6.4.4 Reference creation

#### Syntax

```
ref_shared_expr    = '&', ws, [ modifier_list, ws ], expression ;
ref_exclusive_expr = '$', ws, [ modifier_list, ws ], expression ;
ref_unmanaged_expr = '%', ws, [ modifier_list, ws ], expression ;

modifier_list      = modifier, { ws, modifier } ;
modifier           = "volatile" | "mut" | "atomic" | "guard" ;
```

#### Static semantics

`&expr` creates a shared reference to the operand.

`$expr` creates an exclusive reference to the operand. An exclusive reference permits both loads and stores.

`%expr` creates an unmanaged reference to the operand.

`&expr`, `$expr`, and `%expr` are value expressions, and each yields a reference value.

Where the operand is a value expression, the reference designates the temporary object holding its value.

Modifiers may be placed between the tribe and the operand. The resulting reference type includes the specified modifiers. Where the operand reaches its object through a reference and is not the dereference of one, and the reference nearest the object carries `volatile`, the resulting reference type includes `volatile` as well.

The placement of modifiers, the set of valid tribe–modifier combinations, and their semantics are defined in the clause on references and resource management.

#### Constraints

The operand of `&expr`, of `$expr`, and of `%expr` shall not be a projection. Where that operand is the dereference of a reference, the subclause on reference casting governs what the expression creates. Otherwise, where the reference the expression creates permits stores, the operand shall be a storable object expression. Where the reference nearest the object that operand designates carries `atomic` or `guard`, the operand shall be the dereference of that reference.

#### Examples (informative)

```
let x: si4 = 42;

// shared reference
let r: &si4 = &x;
// shared volatile reference
let v: &volatile si4 = &volatile x;
// shared atomic reference
let at: &atomic si4 = &atomic x;

let mut y: si4 = 0;

// exclusive reference
let e: $si4 = $y;
// exclusive volatile reference
let ev: $volatile si4 = $volatile *e;

// Unmanaged reference
let p: %si4 = %x;
airside { let val = *p; }

// Shared references can coexist
let a: &si4 = &x;
let b: &si4 = &x; // OK — multiple shared references
```

## 6.5 Arithmetic operators

All arithmetic operators require both operands to satisfy the `numeric` bound. The operators `+` and `-` additionally accept a leading operand of unmanaged reference type with a following operand of type `uaddr`. The rules for this form are defined in the clause on references and resource management. Saturating and widening operators require the `integer` bound.

### Syntax

```
arith_expr = expression, ws, arith_op, ws, expression ;
arith_op   = '+' | '+|' | '+@'
           | '-' | '-|'
           | '*' | '*|' | '*@'
           | '/' | '/|'
           | '%' ;
```

### Constraints

The operands of any binary arithmetic operator shall be the same type `T`, or shall be an unmanaged reference and a `uaddr` in the form defined above.

### 6.5.1 Wrapping integer arithmetic

#### Static semantics

For operands of a type `T` satisfying `numeric`, the base and saturating arithmetic operators yield results of type `T`. For operands of an integer type, the base arithmetic operators yield results as follows.

— Addition — `a + b` yields (*a* + *b*) mod 2<sup>*W*<sub>t</sub></sup>, mapped to the value set of `T`.

— Subtraction — `a - b` yields (*a* − *b*) mod 2<sup>*W*<sub>t</sub></sup>, mapped to the value set of `T`.

— Multiplication — `a * b` yields (*a* × *b*) mod 2<sup>*W*<sub>t</sub></sup>, mapped to the value set of `T`.

— Division — `a / b` yields the integer quotient of `a` divided by `b`, truncated towards zero. When the mathematical quotient is not representable in `T` — which occurs only when `a` is the minimum value of a signed type and `b` is `-1` — the result wraps, and `a / b` yields `a`.

— Remainder — `a % b` yields *a* − *q* × *b*, where *q* is the quotient `a / b` yields. The sign of the result, when non-zero, is the sign of `a`. When division of the signed minimum by `-1` wraps, the remainder is `0`.

— Division by zero — `a / 0` yields `0`. `a % 0` yields `a`.

### 6.5.2 Saturating integer arithmetic

#### Static semantics

For operands of a type satisfying `integer`, let *MIN* and *MAX* denote the minimum and maximum values of the value set of `T`. The saturating operators `+|`, `-|` and `*|` yield *MAX* where the mathematical result exceeds *MAX*, *MIN* where it is less than *MIN*, and the mathematical result otherwise.

`a /| b` yields the truncated-towards-zero quotient when the result is representable. When the result is not representable (signed minimum divided by `-1`), the result is *MAX*. Where `b` is zero, `a /| 0` yields `0`.

### 6.5.3 Widening integer arithmetic

#### Static semantics

For operands of a type satisfying `integer`, the widening operators yield the full mathematical result as a pair of `T` values. The result type is the anonymous tuple `.{T, T}`.

`a +@ b` yields `.{low, high}`. The mathematical sum is represented as an unsigned 2*W*<sub>t</sub>-bit value for unsigned `T` and a two’s complement 2*W*<sub>t</sub>-bit value for signed `T`. `low` contains the *W*<sub>t</sub> bits of lesser weight, mapped to the value set of `T`. `high` contains the *W*<sub>t</sub> bits of greater weight, mapped to the value set of `T`. For unsigned types, `high` is the carry bit and has the value `0` or `1`. For signed types, `high` has the value `0` or `-1`.

`a *@ b` yields `.{low, high}`. The mathematical product is represented as an unsigned 2*W*<sub>t</sub>-bit value for unsigned `T` and a two’s complement 2*W*<sub>t</sub>-bit value for signed `T`. `low` contains the *W*<sub>t</sub> bits of lesser weight; `high` contains the *W*<sub>t</sub> bits of greater weight. Both are mapped to the value set of `T`.

#### Examples (informative)

```
let a: ui4 = 0xFFFF_FFFF~ui4;
let b: ui4 = 2~ui4;
let .{ low, high } = a +@ b;
// Mathematical sum: 0x1_0000_0001 (33 bits)
// low:  0x0000_0001~ui4
// high: 0x0000_0001~ui4 (carry)

let c: ui4 = 0x1_0000~ui4;
let d: ui4 = 0x1_0000~ui4;
let .{ lo, hi } = c *@ d;
// Mathematical product: 0x1_0000_0000 (4294967296)
// lo: 0x0000_0000~ui4
// hi: 0x0000_0001~ui4
```

### 6.5.4 Floating radix point number arithmetic

#### Static semantics

`a % b` yields the ISO/IEC 60559:2020 remainder: the value *a* − *n* × *b*, where *n* is the integer nearest to the exact quotient of *a* divided by *b* (ties to even). `a % 0.0` yields NaN.

#### Constraints

A saturating operator (`+|`, `-|`, `*|`, `/|`) or a widening operator (`+@`, `*@`) on a floating radix point number type shall not appear.

## 6.6 Bitwise and shift operators

The bitwise operators `&`, `|`, and `^` and the shift operators `<<` and `>>` require both operands to satisfy the `integer` bound. The result type is the type `T` of the operands.

### Syntax

```
bitwise_expr = expression, ws, bitwise_op, ws, expression ;
bitwise_op   = '&' | '|' | '^' | '<<' | '>>' ;
```

### Constraints

The operands of `&`, `|`, `^`, `<<`, or `>>` shall be the same type `T`.

### Examples (informative)

These examples apply where `cellbits::prog == 8`.

```
let a: ui4 = 0xFF00_FF00~ui4;
let b: ui4 = 0x00FF_FF00~ui4;

let and_r  = a & b;     // 0x0000_FF00~ui4
let or_r   = a | b;     // 0xFFFF_FF00~ui4
let xor_r  = a ^ b;     // 0xFFFF_0000~ui4

let x: si4 = -1~si4;    // all bits set (0xFFFFFFFF)
let shr    = x >> 4;    // -1~si4 (arithmetic shift)

let y: ui1 = 0x80~ui1;
let shl    = y << 1;    // 0x00~ui1 (0x100 mod 2^8 = 0)
let shr_u  = y >> 1;    // 0x40~ui1 (logical shift)

// Shift count >= bit width (ui4 has W = 32 when cellbits == 8)
let z: ui4 = 1~ui4;
let big    = z << 32;   // 0~ui4
let big2   = z << 100;  // 0~ui4
let neg: si4 = -1~si4;
let big3   = neg >> 32; // -1~si4 (sign bit replicated)

// Negative shift count — the shift is performed in the other
// direction.
let v: si4 = 64~si4;
let sh: si4 = -4~si4;
let other  = v << sh;   // descending shift of v by 4: 4~si4
```

### 6.6.1 Bitwise AND, OR, XOR

#### Static semantics

— Bitwise AND — `a & b` yields the value whose bit at each position *k* (counting from zero at the position of least weight) is `1` if and only if the bits at position *k* in both `a` and `b` are `1`.

— Bitwise OR — `a | b` yields the value whose bit at each position *k* is `1` if and only if the bit at position *k* in at least one of `a` or `b` is `1`.

— Bitwise XOR — `a ^ b` yields the value whose bit at each position *k* is `1` if and only if the bits at position *k* in `a` and `b` differ.

The operations are performed on the two’s complement representation.

### 6.6.2 Shift operators

#### Static semantics

An ascending shift `a << b` yields (*a* × 2<sup>*b*</sup>) mod 2<sup>*W*<sub>t</sub></sup>, mapped to the value set of `T`.

A descending shift `a >> b` yields a value determined by the signedness of `T`:

— Unsigned types — the result is the integer part of *a* ÷ 2<sup>*b*</sup>.

— Signed types — the result is *a* ÷ 2<sup>*b*</sup>, rounded towards negative infinity.

Where the value of `b` is negative, the result is that of the shift in the other direction by −*b* positions, where −*b* is computed over the integers.

If the value of `b` is greater than or equal to *W*<sub>t</sub>:

— For an ascending shift, the result is `0`.

— For an unsigned descending shift, the result is `0`.

— For a signed descending shift, the result is `0` where `a` is non-negative and `-1` where `a` is negative.

## 6.7 Comparison operators

The comparison operators have the result type `verdict[void, void]` and require both operands to satisfy the `numeric` bound.

### Syntax

```
comparison_expr = expression, ws, comparison_op, ws, expression ;
comparison_op   = '==' | '!=' | '<' | '>' | '<=' | '>=' ;
```

### Static semantics

— Integer comparison — `a < b`, `a <= b`, `a > b`, `a >= b`, `a == b`, and `a != b` yield `verdict::Pass(void)` where the value of `a` is respectively less than, less than or equal to, greater than, greater than or equal to, equal to, and not equal to the value of `b`, and `verdict::Fail(void)` otherwise.

— Floating radix point number comparison — the comparison operators on a floating radix point number type follow the rules defined in the clause on types.

### Constraints

Both operands of a comparison operator shall be the same type `T`.

### Examples (informative)

```
let a: si4 = -1~si4;
let b: si4 = 1~si4;
let r = a < b;   // Pass — signed comparison: -1 < 1

let x: ui4 = 0xFFFF_FFFF~ui4;
let y: ui4 = 1~ui4;
let s = x > y;   // Pass — unsigned comparison: 4294967295 > 1

let p: fe11s52 = 0.0 / 0.0;    // +0nanq — payload 0, XOR(+, +) = +
let q: fe11s52 = -(0.0 / 0.0); // -0nanq
let t = p == p;     // Pass — reflexive
let u = p == q;     // Fail — sign differs
let v = p > 1.0;    // Pass — +qNaN orders above every non-NaN value
let w = p == 0nanq; // Pass — bit-identical

let neg_zero: fe11s52 = -0.0;
let pos_zero: fe11s52 = 0.0;
let z1 = neg_zero == pos_zero; // Fail — sign distinguishes zero
let z2 = neg_zero < pos_zero;  // Pass

let n = 0nans < 0nanq; // Pass — +sNaN orders below +qNaN
```

## 6.8 Assignment

An assignment expression stores a value into the object its leading operand designates. Two forms exist: simple assignment and compound assignment.

### Syntax

```
assignment_expr = expression, ws, '=', ws, expression ;

compound_assign = expression, ws, compound_op, ws, expression ;
compound_op     = '+=' | '-=' | '*=' | '/=' | '%='
                | '+|=' | '-|=' | '*|=' | '/|='
                | '&=' | '|=' | '^=' | '<<=' | '>>=' ;
```

### Static semantics

Both forms are value expressions whose result type is `void`.

A type `S` is **assignable** to a type `T` where `S` and `T` are the same type, or where this specification defines an implicit cast from `S` to `T`.

### Dynamic semantics

A store of an uncopyable type, other than a store through an unmanaged reference, proceeds in two steps:

1. The existing value held by the target object is destroyed, if the object is initialized.
2. The new value is transferred into the target object.

### Constraints

The leading operand shall be a storable object expression, or an identifier expression that names a single-assignment binding whose object is not possibly initialized at the programme point of the assignment.

In a simple assignment, the type of the following operand shall be assignable to the type of the leading operand.

### Examples (informative)

```
let mut x: si4 = 0;
x = 42;

// Deferred initialization of a single-assignment binding
let y: si4;
y = compute();
```

### 6.8.1 Evaluation order

#### Dynamic semantics

In a simple assignment `a = b`:

1. The leading operand `a` is evaluated to determine its object.
2. The following operand `b` is evaluated.
3. The resulting value is stored into the object of `a`.

Each step is sequenced before the next.

In a compound assignment `a op= b`:

1. The leading operand `a` is evaluated to determine its object and to load the current value held by the object.
2. The following operand `b` is evaluated.
3. The binary operation `op` is performed on the current value of `a` and the value of `b`.
4. The result is stored into the object of `a`.

Each step is sequenced before the next.

### 6.8.2 Compound assignment operators

#### Constraints

The leading operand shall be a storable object expression.

The operands of a compound assignment shall satisfy what its binary operation requires of its operands.

#### Examples (informative)

```
let mut x: uaddr = 10;
x += 5;    // wrapping:   x is now 15
x -|= 100; // saturating: x is now 0

let mut flags: ui4 = 0xFF00;
flags &= 0x0F0F; // flags is now 0x0F00
flags ^= 0x00FF; // flags is now 0x0FFF
flags <<= 4;     // flags is now 0xFFF0
```

## 6.9 Type casting

### Syntax

```
cast_expr   = expression, ws, "as", [ ws, '!' ], ws, cast_target ;
cast_target = type ;
```

### Static semantics

Where the cast target is `?`, it is an inferred type, as defined in the clause on types, and the type it resolves to is the target of the conversion. The subclause that defines the conversion states the default type for the form where it defines one.

The `!` of a cast expression selects bitwise reinterpretation, as defined in the subclause on bitwise reinterpretation. A cast expression without it converts by the rules of the subclause that defines the conversion for the types of its operand and its target.

### 6.9.1 Conversion categories

#### Static semantics

— **Wrapping** — the value is reduced modulo 2 to the power of the bit width of the target type into the value set of the target type.

— **Zero-extension** — the source value is padded with zero bits in the positions of greater weight.

— **Sign-extension** — the source value is padded by replicating the sign bit in the positions of greater weight.

— **Reinterpretation** — the Γ sequence is preserved and only the type interpretation changes.

— **Rounding** — rounding and overflow follow the ISO/IEC 60559:2020 conversion under the rounding mode.

— **Truncation towards zero** — the fractional part is discarded.

— **Saturation** — out-of-range values are clamped to the nearest boundary of the target type.

### 6.9.2 Integer → integer

#### Static semantics

<table>
<thead><tr><th></th><th>Target wider</th><th>Target same width</th><th>Target narrower</th></tr></thead>
<tbody>
<tr><td>Unsigned → Unsigned</td><td>Zero-extension</td><td>Reinterpretation</td><td>Wrapping</td></tr>
<tr><td>Unsigned → Signed</td><td>Zero-extension</td><td>Reinterpretation</td><td>Wrapping</td></tr>
<tr><td>Signed → Unsigned</td><td>Sign-extension then reinterpretation</td><td>Reinterpretation</td><td>Wrapping</td></tr>
<tr><td>Signed → Signed</td><td>Sign-extension</td><td>Reinterpretation</td><td>Wrapping</td></tr>
</tbody>
</table>

#### Examples (informative)

```
// wrapping: low 8 bits → 255~ui1
255~si4 as ui1
// reinterpretation: 0xFF → 255~ui1
-1~si1 as ui1
// zero-extension: 42~si4
42~ui1 as si4
// sign-extension: -1~si4
-1~si1 as si4
// sign-extension, then reinterpretation: 0xFFFFFFFF → 4294967295~ui4
-1~si1 as ui4
// reinterpretation: 0x80 → -128~si1
128~ui1 as si1
```

### 6.9.3 Integer → floating radix point number

#### Static semantics

The integer value is converted by rounding.

#### Static semantics

```
-2.9~fe11s52 as si4  // -2~si4 (towards zero)
1e20~fe11s52 as si4  // si4 max (saturating)
-1e20~fe11s52 as ui4 // 0~ui4 (unsigned min, saturating)

// 0~si4 (NaN → zero)
(0.0~fe11s52 / 0.0~fe11s52) as si4
// 0~si4 (NaN → zero, regardless of sign)
-(0.0~fe11s52 / 0.0~fe11s52) as si4
```

### 6.9.5 Floating radix point format conversions

#### Static semantics

<table>
<thead><tr><th>Condition</th><th>Semantics</th></tr></thead>

<tr><td>Exactly representable</td><td>Exact</td></tr>
<tr><td>Not exact</td><td>Rounding</td></tr>

For a NaN operand, the sign bit and the kind are preserved. When the target format’s payload field is wider than the source’s, the payload is zero-extended. When the target format’s payload field is narrower than the source’s, a payload that fits within the target width is preserved; a payload that does not fit is saturated to the target’s maximum payload, as defined in the clause on types.

#### Examples (informative)

```
// fe5s10’s payload is 9 bits. 0x3FFFFF overflows and saturates.
0nanq'0x3FFFFF as fe5s10   // → 0nanq'0x1FF
0nanq'1        as fe5s10   // fits → preserved
0nanq'1        as fe19s236 // wider field → zero-extended
```

### 6.9.6 Variant type → discriminant

#### Static semantics

`e as ?` extracts the discriminant. The default type for this form is the **discriminant type** of the variant type, which automatic discriminant sizing or `with discrim(T)` determines. Where the discriminant type is `void`, the form yields `void`.

`e as T` where `T` satisfies `integer` extracts the discriminant and then converts it to `T` using the integer-to-integer conversion rules. Where the discriminant type is `void`, the conversion yields zero.

The extracted value depends on the variant the value currently holds:

— For a variant other than the wild variant, the extracted value is the variant’s discriminant.

— For a wild variant with a canonical value (`wild(V)`), the extracted value is `V`.

— For a wild variant without a canonical value, the extracted value is the discriminant value stored.

#### Constraints

An `as` conversion whose source is a variant type shall have `?` or a type satisfying `integer` as its target.

#### Examples (informative)

```
enum colour { red, green, blue }
let c = colour::green;
let d = c as ?;     // d: ui1, value 1
let e = c as ui4;   // e: ui4, value 1
                    // (discriminant extracted, then zero-extended)

let b = verdict[void, void]::Pass(void);
let n = b as ?;     // n: ui1, value 1
let m = b as uaddr; // m: uaddr, value 1

let v: verdict[si4, si4] = verdict::Pass(42);
let r = v as ?;     // r: ui1, value 1 (payload 42 is discarded)
```

### 6.9.7 Reference conversions

The rules for reference casting are defined in the clause on references and resource management.

#### Examples (informative)

```
// permitted on landside
// $T → &T
let shared = exclusive as &T;
// &T → %T
let uman = shared as %T;
// %T → uaddr
let addr = uman as uaddr;
// &mut T → &T
let plain = mut_ref as &T;
// &atomic T → &guard T
let guarded = atomic_ref as &guard T;
// uaddr → %T
let uman2 = addr as %T;

// %T → &T: airside
let managed = airside { express uman2 as &T; };
// %T → $T: airside
let exclusive = airside { express uman2 as $T; };

// translation failures
// addr as &T;       — uaddr → &T
// shared as $T;     — &T → $T
// shared as &mut T; — &T → &mut T

// atomic_ref as &T; — &atomic T → &T
```

### 6.9.8 Subroutine pointer conversions

#### Static semantics

Conversion between `%void` and a subroutine pointer type, or between two subroutine pointer types that are not the same type, is permitted via `as!`.

#### Examples (informative)

```
airside {
    let uman_ptr: %void = 0x4000_1000~uaddr as %void;
    let f: fn() -> void = uman_ptr as! fn() -> void;
    let g: fn(si4) -> si4 = f as! fn(si4) -> si4;
    let back: %void = g as! %void;
}
```

### 6.9.9 Other disallowed conversions

#### Constraints

The following conversions shall not appear in a cast expression without `!`:

— Any source type that is not `numeric`, a variant type, or a reference.

— Any target type that is neither `numeric`, nor a reference, nor `?`.

— Reference conversions not permitted by the rules defined in the clause on references and resource management.

— Conversions between a reference type and a type that is neither `uaddr` nor a reference type.

### 6.9.10 Bitwise reinterpretation

`as!` performs a reinterpretation.

#### Dynamic semantics

The source value is not destroyed.

#### Constraints

A cast with `as!` requires airside.

A `Source'size`/`Target'size` mismatch shall not appear. `as!` on a reference to a protocol type shall not appear.

#### Examples (informative)

```
airside {
    // ISO/IEC 60559:2020 bits as integer
    let bits: ui4    = some_float as! ui4;
    // integer bits as ISO/IEC 60559:2020
    let back: fe8s23 = bits as! fe8s23;
}
```

## 6.10 `airside` blocks

An `airside` block is an expression whose block is an airside region, as the clause on semantics defines airside.

### Syntax

```
airside_block = "airside", ws, block ;
```

### Static semantics

The type and value of an `airside` block follow the rules for express blocks defined in the clause on statements and control flow.

### Implementation requirements

The implementation shall not use the presence of an `airside` block to eliminate or reorder an operation outside the block.

### Examples (informative)

```
let raw_val = airside {
    let ptr = 0x4000_1000~uaddr as %volatile atomic mut ui4;
    express *ptr;
};

// airside fn — the entire body is implicitly airside
airside fn read_mmio(addr: uaddr) -> ui4 {
    let ptr = addr as %volatile atomic ui4;
    return *ptr;
}
```

## 6.11 `xlat` blocks, `const` blocks, and the `xlat?` and `const?` conditionals

A `xlat` block and a `const` block are expressions evaluated at translation time. A `xlat?` or `const?` conditional selects one of two branches according to the machine on which its evaluation takes place.

### Syntax

```
xlat_block      = "xlat", ws, block ;
const_block     = "const", ws, block ;
eval_lead       = block | "then", ws, expression ;
eval_cond_block = ( "xlat" | "const" ), ws, '?', ws, eval_lead, ws,
                  "else", ws, block ;
eval_cond_expr  = ( "xlat" | "const" ), ws, '?', ws, eval_lead, ws,
                  "else", ws, plain_expression ;
```

### Static semantics

The type and value of a `xlat` block or a `const` block follow the rules for express blocks defined in the clause on statements and control flow. Each `xlat` block, `const` block, and operation on a symbol declared in a `#dyn xlat` namespace is evaluated once each time an evaluation on the translation machine or the constant machine reaches it, and, where the construct that immediately encloses it is analysed on the programme machine, once more. The resulting value of that further evaluation serves every evaluation on the programme machine that reaches it. What these contribute to the opaque code is defined in the subclause on opaque code exclusion.

Any operation valid at execution time is valid within a `xlat` block, subject to the rule governing `trap` in translation-time evaluation, defined in the clause on statements and control flow.

The **analysis roots** of the translation machine are the `xlat` blocks, the `#dyn xlat` namespaces, and the operations on symbols declared in a `#dyn xlat` namespace, as defined in the clause on programme structure and translation. Of those operations, one that lies within a leading branch of a `xlat?` conditional, and within no analysis root that lies within that branch, is not an analysis root.

The analysis roots of the constant machine are the `const` blocks and the following:

— The initializers of `const` declarations and of `static` bindings.

— The expressions of associated constants.

— The `T'bound(X)` expressions where, in semantic analysis, `T` is a closed type and no generic parameter occurs free in a generic argument of `X`.

— The expressions of inline expression operands of `instruct` blocks.

— The length expressions of array types and the dependence arguments that require no value of a dependence parameter.

Each of these, other than one that is a `xlat` block or a `const` block, and each construct of which it is the innermost analysis root, is analysed also on each machine on which the construct that immediately encloses it is analysed.

The analysis roots of the programme machine are the global `instruct` blocks and, outside every `#dyn` namespace, the `static` declarations and the declarations that carry an external name. An evaluation of an analysis root of the translation machine or the constant machine, and each evaluation it reaches, is a **translation-time evaluation**, on whichever machine it takes place.

A construct is **analysed on** the translation machine where the innermost analysis root that contains it is one of that machine, on the constant machine where that root is one of the constant machine and not of the translation machine, and on the programme machine where that root is one of the programme machine alone. A construct that the sentence above places on no machine or on the programme machine alone is analysed also on each machine on which a construct analysed on that machine names a type whose declaration, or an `impl` block for which, contains it. Such a construct is analysed also on each machine on which a construct analysed on that machine has a type in which such a type occurs. Such a construct is analysed also on each machine on which a construct analysed on that machine names a subroutine, a `const` declaration, a `static` binding, or an associated constant whose declaration contains it. A construct that the rules above place on no machine, other than a `const` declaration or an associated constant, is analysed on the programme machine. A construct shall satisfy the static semantics and the constraints of this specification under each machine on which it is analysed.

An evaluation of an analysis root of the translation machine takes place on that machine, and one of a `const` block on the constant machine. Every other evaluation takes place on the machine of the evaluation that reaches it or of the analysis of a type that requires its value, or, where there is neither, on the programme machine.

#### The `xlat?` and `const?` conditionals

A `xlat?` conditional selects its leading branch in an evaluation on the translation machine, and a `const?` conditional in one on the constant machine. Each selects its `else` branch in every other evaluation.

A construct within a branch of a `xlat?` or `const?` conditional, and within no analysis root that lies within that branch, is analysed, in place of the machines on which it would otherwise be, on each machine on which the conditional is analysed and on which an evaluation of it selects that branch, and also on the following machine:

— For the leading branch of a `xlat?` conditional — the translation machine.

— For the leading branch of a `const?` conditional — the constant machine.

— For the `else` branch of either — the programme machine.

At an evaluation, the branch the conditional does not select is discarded. The opaque code contains nothing of a leading branch.

The type of a `xlat?` or `const?` conditional is the common type of its branches.

### Dynamic semantics

Where the value of an analysis root of the translation machine or the constant machine contains a managed reference, the referent, and each object of which the referent is a constituent object or a run of elements, acquires the permanent object lifetime. This applies transitively to managed references contained within those objects.

### Constraints

The translation machine, the constant machine, and the programme machine are ordered in that sequence. An analysis root of a machine shall refer to no binding whose object has the automatic object lifetime, that is declared outside the root, and whose declaration is analysed on a machine later in that sequence than the machine of the root.

A translation-time evaluation of an `instruct` block shall take place on the translation machine.

A `const` declaration, a `static` binding, or an associated constant shall not appear where an evaluation of its initializer or expression on the translation machine or the programme machine yields a value that differs from every value that the initializer or expression can yield on the constant machine with the same generic arguments.

For this rule, each analysis root of the translation machine and each `const` block that the initializer or expression reaches on the constant machine yields there, at each reach, a value it yields in that evaluation on the translation machine or the programme machine. References and subroutine pointers are compared as follows:

— An unmanaged reference — the same address and the same further information.

— A managed reference — referents that hold the same values. A pair of referents met again within its own comparison compares as the same. Where the referent type is a protocol type, the referents are the objects that `.ptr` designates, and they hold the same values only where their erased types are the same.

— A subroutine pointer — the same subroutine.

An evaluation on the translation machine shall not access, or create a reference to, the object of a `static` binding declared outside every `#dyn xlat` namespace, or a constituent object of that object. A `xlat` block, a `const` block, the expression of an inline expression operand, and a length expression or dependence argument that is an analysis root shall satisfy the constraint the clause on declarations places upon a local item that appears in a block. So shall an operation on a symbol declared in a `#dyn xlat` namespace where the construct that immediately encloses it is analysed on the programme machine.

A translation-time evaluation shall not store into the object of a `static` binding declared outside every `#dyn xlat` namespace, or into a constituent object of that object.

The evaluation of a default-value expression, of the initializer of a `const` declaration or of a `static` binding, or of the expression of an associated constant shall not require, directly or indirectly, the evaluation of that same expression. For this rule:

— An expression requires what its constituent expressions require.

— Naming a `const` declaration, a `static` binding, or an associated constant requires the evaluation of its initializer or expression, except where the name of a `static` binding, alone or followed by field accesses, is the operand of an expression that creates a reference or the receiver of a `.ptr` or `.len` projection.

— A load from the object of a `static` binding, or from a constituent object of that object, requires the evaluation of the initializer of that binding.

— A composite literal requires the default-value expressions of the fields it omits.

— Naming a subroutine requires what its body requires.

— A `T'bound(X)` expression requires nothing.

Neither a value that a translation-time evaluation incorporates into the opaque code nor an object that value designates, transitively, shall be or hold a subroutine pointer to a subroutine whose definition lies within an expression of which only the resulting value is incorporated into the opaque code, or within a leading branch of a `xlat?` or `const?` conditional.

The branches of a `xlat?` or `const?` conditional shall have a common type.

### Examples (informative)

```
const buffer_size: uaddr = xlat {
    express 4096 * page_count();
};

fn platform_init() {
    xlat? {
        init_at_translation();
    } else {
        init_at_execution();
    }
}

// The `else` branch is empty
xlat? {
    calibrate();
} else {}

// Expression form
let width: uaddr = xlat? then translation_simd_width() else 16;

// `instruct` in the leading branch of xlat?
const seed: ui4 = xlat {
    express xlat? then airside {
        let mut r: ui4;
        instruct { rdtsc } with { out(eax) -> r; };
        express r;
    } else 0;
};

// Nesting other conditions inside the leading branch
xlat? {
    #flag_if(aarch64) aarch64_init(); ##
} else {}
```

### 6.11.1 Translation-machine evaluation

#### Static semantics

An evaluation on the translation machine takes the cell width, the address width, the reference width, the rounding mode, the atomicity set, the transactionality set, the literal encoding, and the unqualified type intrinsics from that machine.

#### Examples (informative)

```
const build_version: &[ui1] = xlat {
    #add std::"posix.kr" as posix;
    use posix::env;
    express env::get("build_version");
};

const font_data: &[ui1] = xlat {
    #add std::"posix.kr" as posix;
    use posix::fs;
    express fs::read_raw("font.ttf");
};
```

### 6.11.2 Programme-machine and constant-machine evaluation

#### Static semantics

The cell width, the address width, and the reference width of the constant machine are each the greater of those of the translation machine and the programme machine, and its atomicity set and transactionality set hold every pair of a size and an alignment. Its environment is one that the environment of the translation machine provides. An evaluation on the programme machine takes the properties the subclause on translation-machine evaluation lists from the programme machine. An evaluation on the constant machine takes the rounding mode and the literal encoding from the programme machine, and the rest of those properties from the constant machine.

#### Examples (informative)

```
// make_lut is invoked on the translation machine
const crc_table: [ui4; 256] = xlat { express make_lut(); };

// Here it is invoked on each machine that uses exec_table
const exec_table: [ui4; 256] = make_lut();

// static with complex initializer
static greeting: &[ui1] = build_greeting("world");
```

### 6.11.3 Reproducibility

#### Implementation requirements

Given the same implementation, the same environment of the programme machine, and the same environment of the translation machine, a programme’s translation-time evaluations take place in the same relative order on every translation.

### 6.11.4 Opaque code exclusion

#### Implementation requirements

Of an expression that is an analysis root of the translation machine or the constant machine, only the resulting value is incorporated into the opaque code, as if it were a literal of the same type.

#### `xlat` in `#dyn` interface sources

Where a conforming implementation produces an interface source, `xlat` blocks shall be replaced by their evaluated result values.

### 6.11.5 Cross-machine value validity

A value yielded by an evaluation on the translation machine crosses where it becomes the result of that evaluation within an enclosing evaluation on the programme machine or the constant machine, and where it is the value with which a `static` binding is initialized. A value that an evaluation of a `const` block yields crosses where it becomes the result of that evaluation within an enclosing evaluation on the translation machine or the programme machine, and where it is the value with which a `static` binding is initialized.

#### Static semantics

The type of a value that crosses is analysed on the machine to which it crosses.

— Values of `void` and of any floating radix point number type cross unchanged.

— Values of integer types cross unchanged. A crossed value shall belong to the value set, as defined in the clause on types, of its type determined under the cell width of the machine to which it crosses. For `uaddr` and `saddr`, the crossed value shall belong to the value set determined under the address width of that machine.

— Values of reference types cross by their tribe. The address of an unmanaged reference crosses unchanged, and its referent does not cross. A managed reference crosses together with its referent. Where the referent type is `[U]`, the referent that crosses is an array of `.len` elements of type `U`. Where it is neither `[U]` nor a protocol type, the referent that crosses is an object of the referent type. Within one crossing, each referent crosses once, by the rules of this subclause, and its crossed counterpart is an object of the permanent object lifetime. A referent that is a constituent object of another referent in the same crossing, or a run of elements of an array that is another referent in that crossing, crosses as the corresponding constituent object, or run of elements, of the crossed counterpart of that referent. Where runs of elements of one array are referents in one crossing and overlap, directly or through further such runs, the least run of that array that contains them all is a referent in that crossing. A crossed managed reference designates the crossed counterpart of the referent of the original, and bears the tribe and the modifiers of the original. The address of an unmanaged reference, and the length of a slice reference, shall belong to the value set of `uaddr` determined under the address width of the machine to which the reference crosses, and the length of a managed slice reference, multiplied by `U'size`, shall not exceed the number of cells of the τ of that machine. The length of a slice reference crosses unchanged, the `.tyd` and `.prd` fields of a wide reference to a protocol type cross as the corresponding descriptors of the machine to which they cross, and the `.ptr` of a managed one crosses together with the erased value it designates.

— A subroutine pointer crosses as a subroutine pointer that designates the same subroutine. The subroutine shall not be one declared in a `#dyn xlat` namespace. It is analysed on the machine to which the pointer crosses, and so is each subroutine that a descriptor designates where a reference crosses as that descriptor.

— A value of any other type crosses by composition. Each value it holds crosses by the rules of this subclause, as the clause on references and resource management defines the constituents of a type. The discriminant of a variant type crosses as a value of the discriminant type. The value is reconstructed under the layout rules of its type, as defined in the clause on types.

#### Constraints

A crossing that violates any rule of the static semantics above shall not appear.

#### Implementation requirements

The diagnostic for a crossing that violates a rule of the static semantics above shall identify the value to which that rule applies, and its type.

#### Design rationale (informative)

Crossed referents acquire the permanent object lifetime because the value can be incorporated into the opaque code, and storage incorporated into the opaque code is reserved for the entire execution of the programme.

## 6.12 Inline `instruct` blocks

An inline `instruct` block is an expression that embeds instructions. Global `instruct` blocks are defined in the clause on declarations.

### Syntax

```
instruct_block = "instruct", ws, instruct_body,
                 [ ws, constraint_clause ] ;

constraint_clause = "with", ws, '{', ws,
                    { instruct_constraint, ';', ws }, '}' ;

instruct_body  = { '#' }, '{', { ? instruction text line ? }, '}',
                 { '#' } ;

instruct_constraint
    = 'in',      ws, '(', ws, operand_target, ws, ')', ws,
                 '=', ws, expression
    | 'out',     ws, '(', ws, operand_target, ws, ')', ws,
                 '->', ws, identifier
    | 'io',      ws, '(', ws, operand_target, ws, ')', ws,
                 '=', ws, expression, ws, '->', ws,
                 identifier
    | 'clobber', ws, '(', ws, ? mill identifier ?, ws,
                 { ',', ws, ? mill identifier ?, ws },
                 ')' ;

operand_target = [ '\'', identifier | '\'?'
                 | '\'', digit, { digit }
                 | ? mill identifier ? ] ;
```

### Static semantics

Where an `instruct` block ends is defined in the clause on lexical structure.

Any character sequence beginning with `'` that follows a character other than a character permitted within an identifier is a Kurt operand; all other text is **instruction text**.

A Kurt operand has four forms:

— Named operand (`'name`) — references a named constraint declared in the constraint clause.

— Positional operand (`'0`, `'1`, …) — references a constraint by its index in the constraint clause, counting from zero.

— Sequential operand (`'?`) — takes the next unmatched positional constraint in declaration order.

— Inline expression (`'(expr)`) — the expression is evaluated at translation time and inserted as an immediate value.

Three operand-targeting modes are defined, `clobber` exempt. In each, the constraint clause declares the target and the instruction text references it:

— Named — the clause writes `in('name) = expr`, and the text writes `'name`.

— Positional — the clause writes `in('1) = expr` to declare an explicit index, or `in() = expr` to take the next available one, and the text writes an index or `'?`. Explicit indices and `'?` may coexist, and the text may reference one index more than once.

— Mill — the clause writes `in(rax) = expr`, and the text writes the bare mill identifier.

The Kurt comment syntax defined in the clause on lexical structure applies to the delimiting tokens of an `instruct` block. Apart from the operands above and from what ends the instruction text, the text within the block is opaque to the lexical rules of Kurt and is **delivered** verbatim to the environment the block targets. The block targets the environment of the programme machine where it is a global `instruct` block, and the environment of the translation machine or of the programme machine where it is analysed on that machine and an execution context of that machine can occupy a succession of programme points that contains its first programme point.

#### Constraint keywords

— `in(target) = expr` — places the value of `expr` in `target` before the instructions of the `instruct` block are executed.

— `out(target) -> var` — captures the value of `target` into the `mut` binding `var` after the instructions of the `instruct` block are executed.

— `io(target) = expr -> var` — places the value of `expr` in `target` before the instructions are executed; captures `target` into `var` after they are executed.

— `clobber(r1, r2, ...)` — declares that the parts of the mill the listed mill identifiers name may be modified. The implementation shall save and restore their values across the `instruct` block.

### Dynamic semantics

The expressions of the constraints are evaluated in constraint-clause order.

### Constraints

An inline `instruct` block requires airside.

Where the opening delimiter of an `instruct` block carries no `#` character, the curly brackets of its instruction text shall balance.

The number of `#` characters in the opening and closing delimiters of an `instruct` block shall be equal.

The instruction text of an `instruct` block shall follow the syntax of instruction text of the environment to which it is delivered, and this specification constrains it in no other way.

A `'` token that does not match one of the four Kurt operand forms shall not appear.

The three operand-targeting modes shall not be mixed in a single constraint clause (`clobber` exempt).

Each `'name` shall match exactly one named constraint of the constraint clause. Each `'N` shall be a valid index, counting from zero. `'?` past the last unmatched positional shall not appear. Duplicate mill identifiers among operand targets and overlap between operand targets and `clobber` entries shall not appear.

### Implementation defined

The **mill** of a machine is the part of its state other than its storage. A **mill identifier** names a part of the mill. The mill identifiers a machine supports and the syntax of instruction text are implementation defined. A conforming implementation shall document the list of the mill identifiers, and the syntax of instruction text, for each supported environment of the programme machine and of the translation machine.

### Examples (informative)

```
// No constraints
airside { instruct { msr daifclr, #2 }; }

// Mill mode
airside {
    let mut n: saddr;

    instruct { svc #0 } with {
        in(x8) = 64; in(x0) = 1; in(x1) = buf;
        in(x2) = len; out(x0) -> n;
        clobber(x16, x17);
    }
}

// Named mode
airside {
    let mut r: ui4;

    instruct {
        mrs 'c, sctlr_el1
        orr 'c, 'c, '(1 << 2)
        msr sctlr_el1, 'c
    } with { io('c) = v -> r; }
}

// Positional — anonymous, '? sequential
airside {
    instruct {
        mov x0, '?
        mov x1, '?
    } with {
        in() = 1;
        in() = 2;
    }
}

// Positional — reordered via explicit index
airside {
    instruct {
        mov x0, '? // 2
        mov x1, '? // 1
    } with {
        in('1) = 1;
        in('0) = 2;
    }
}

// Positional — same operand referenced twice
airside {
    instruct {
        mov x0, '0 // both 1
        mov x1, '0
    } with {
        in() = 1;
    }
}

// -> !
fn halt() -> ! {
    loop { airside { instruct { wfi } } }
}

// Instruction text is constrained only upon delivery — the
// discarded branch may hold instruction text of another environment
airside {
    let mut t: ui8;

    xlat? {
        instruct { rdtsc } with { out(eax) -> t; }
    } else {
        instruct { mrs '0, cntvct_el0 } with { out() -> t; }
    }
}

// The `instruct` block lies in the leading branch of xlat?, so it is
// delivered to the environment of the translation machine alone.
fn include_bytes(path: &[ui1]) -> &[ui1] {
    xlat? {
        let mut r: &[ui1];
        airside {
            instruct { /* translation-machine I/O */ }
                with { out() -> r; }
        }
        return r;
    } else {
        trap();
    }
}
```

## 6.13 Type intrinsic expressions

A type intrinsic expression queries a property of a type.

### Syntax

```
type_intrinsic    = type, ws, type_intrinsic_op ;
type_intrinsic_op = '\'', ws,
                    ( 'size' | 'align'
                    | 'offset', ws, '(', ws, identifier, ws, ')'
                    | 'bound',  ws, '(', ws, bound_argument, ws, ')' ),
                    [ ws, '::', ws, ( 'prog' | "xlat" | "const" ) ] ;
bound_argument    = bound_elem | "type" ;
```

### 6.13.1 Layout intrinsics

#### Static semantics

`T'size` yields the size of the type `T` in cells. The result is a `uaddr` value.

`T'align` yields the alignment requirement of the type `T` in cells. The result is a `uaddr` value.

`T'offset(field)` yields the cell offset of the named field within the struct type `T`. The result is a `uaddr` value. The offset is computed according to the layout rules defined in the clause on types.

Each layout intrinsic permits the three qualified forms defined in the clause on types, written after it. The form qualified with `::prog` yields its value under the layout of `T` in the programme machine, the form qualified with `::xlat` under that in the translation machine, and the form qualified with `::const` under that in the constant machine.

#### Constraints

`T'offset(field)` on a type that is not a struct, or when `field` does not name a declared field of `T`, shall not appear.

#### Examples (informative)

```
const sz: uaddr  = my_struct'size;
const al: uaddr  = my_struct'align;
const off: uaddr = my_struct'offset(field_name);
```

### 6.13.2 Bound descriptor emission

#### Static semantics

`T'bound(X)` queries whether the type `T` satisfies the bound `X` and emits a descriptor for `T`. The result type is `verdict[%void, void]`. When `T` satisfies `X`, the result is `verdict::Pass(ptr)` where `ptr` is an unmanaged reference to that descriptor. When `T` does not satisfy `X`, the result is `verdict::Fail(void)`. Where, in semantic analysis, `T` is an open type or a generic parameter occurs free in a generic argument of `X`, whether `T` satisfies `X` is decided in semantic analysis. In that case, `T'bound(X)` yields, for a declared protocol `X`, the descriptor of an implementation of `X` witnessed for `T`, and for `type`, `numeric`, `integer`, or `primitive` that `T` satisfies, the descriptor of that kind for the type `T` denotes in each evaluation, and for any other bound `T` satisfies, a reference to an object of size zero. In that case, it yields `verdict::Fail(void)` where there is none.

A descriptor belongs to a machine. Its contents are the layout of `T` and the addresses of its subroutines in that machine. `T'bound(X)::prog` yields the descriptor of the programme machine, `T'bound(X)::xlat` that of the translation machine, and `T'bound(X)::const` that of the constant machine.

When the result is `verdict::Pass(ref)`, the reference permits no store. Where, in semantic analysis, `T` is a closed type and no generic parameter occurs free in a generic argument of `X`, it refers to an object of permanent object lifetime. In that case, within one translation unit, multiple evaluations of `T'bound(X)` that yield the descriptor of one machine, for the same `(T, X)` pair where `T` satisfies `X`, yield the same reference value.

The descriptor the expression yields depends on the kind of bound:

<table>
<thead><tr><th>Bound kind</th><th>Descriptor</th></tr></thead>
<tbody>
<tr><td><code>type</code></td><td>A type descriptor as defined in the subclause on descriptors</td></tr>
<tr><td>Declared protocol</td><td>A protocol descriptor with the three-zone layout defined in the subclause on descriptors</td></tr>
<tr><td><code>numeric</code>, <code>integer</code>, or <code>primitive</code></td><td>An arithmetic descriptor defined in the subclause on descriptors</td></tr>
<tr><td>Any other bound</td><td>A reference to an object of size zero</td></tr>
</tbody>
</table>

`T'bound(type)` yields `verdict::Pass` for every type.

The `.tyd` and `.prd` fields of a wide reference to a protocol type are the `verdict::Pass` payloads of `T'bound(type)` and `T'bound(Protocol)` for the erased type `T`.

#### Constraints

The type `T` of a `T'bound(X)` expression shall be a closed type, a type parameter, or, within an associated subroutine that a protocol `impl` block provides, `selftype` or the target type of that block. Where the expression takes a qualified form, `T` shall be, in semantic analysis, a closed type and no generic parameter shall occur free in a generic argument of `X`.

#### Design rationale (informative)

Returning `verdict[%void, void]` lets bound satisfaction be tested as an ordinary contract value: a programme asserts satisfaction by trapping on the `verdict::Fail` path, and the `verdict::Pass` payload is the descriptor reference that the formation of a reference to a protocol type consumes.

#### Examples (informative)

```
// Declared protocol — yields protocol descriptor
const si4_ord: %void = contract si4'bound(ord) else trap();

// Built-in bound
const si4_num: verdict[%void, void] = si4'bound(numeric);
```

### Static semantics

**Leading-to-following associativity** means `a op b op c` is parsed as `(a op b) op c`. **Following-to-leading associativity** means `a op b op c` is parsed as `a op (b op c)`. A form whose associativity the table gives as `—` does not associate, and an expression in which such a form supplies an operand of the same form shall not appear. (e.g. `a < b < c` shall not appear.)

— Type intrinsics bind less tightly than dereference and reference creation and more tightly than the unary operators of precedence 7. (e.g. `&T'size` is parsed as `(&T)'size`, the size of a reference to `T`. `!T'size` is parsed as `!(T'size)`.)

— `and`, `or`, and `xor` are defined in the clause on statements and control flow, which gives the order in which their operands are evaluated.

— The table assigns precedence to compare-and-swap (`>.<`), to the value forms taking `else`, and to contract extraction as whole forms. The semantics of `>.<` are defined in the clause on references and resource management.
