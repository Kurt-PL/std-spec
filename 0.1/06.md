# §6. Expressions

This clause defines the expressions of the Kurt programming language: their kinds and operators, assignment, casting, the `airside` and `xlat` blocks, inline `asm`, the type intrinsics, and operator precedence.

## 6.1 Expression kinds

An expression is a sequence of operators and operands that computes a value. Every expression has a type. Every expression is either an **object expression**, which designates an object, or a **value expression**, which designates a computed value. An object expression may appear on either side of an assignment; a value expression may appear only where a value is expected.

An object expression is **storable** at a programme point where a store through it is permitted there. A projection, as defined in the clause on references and resource management, is storable at no programme point.

The complete precedence table is defined in the subclause on operator precedence and associativity.

### Syntax

```
expression   = primary_expr | postfix_expr | unary_expr | binary_expr
             | cast_expr | special_expr | control_expr ;

primary_expr = identifier_expr | literal | paren_expr
             | composite_literal | contract_construct | wild_construction
             | array_literal | repeat_literal | tuple_literal
             | uninit_expression | cellbits_expr ;

postfix_expr = invocation_expr | field_access | method_invocation
             | propagation_expr ;

unary_expr   = negation_expr | not_expr | deref_expr
             | ref_shared_expr | ref_exclusive_expr | ref_unmanaged_expr ;

binary_expr  = arith_expr | bitwise_expr | comparison_expr | logical_expr
             | assignment_expr | compound_assign | cas_expr ;

special_expr = airside_block | xlat_block
             | xlat_cond_block | xlat_cond_expr | asm_block
             | type_intrinsic | destruct_invocation | undestruct_expr
             | volatile_fence | guard_fence ;

control_expr = block | labelled_block
             | if_block | if_expr | if_let_block | if_let_expr
             | match_expression | while_block | while_expr
             | loop_expression | extraction_block | extraction_expr
             | return_expression | break_expression | continue_expression
             | express_expression | trap_invocation ;
```

`literal` and `cellbits_expr` are defined in the clause on lexical structure and in the clause on types. `contract_construct`, `logical_expr`, and every alternative of `control_expr` are defined in the clause on statements and control flow; `cas_expr`, `destruct_invocation`, `undestruct_expr`, `volatile_fence`, and `guard_fence` in the clause on references and resource management. Every other alternative is defined in this clause.

## 6.2 Primary expressions

### 6.2.1 Identifier expression

#### Syntax

```
identifier_expr     = single_path ;
single_path         = path_root, { ws, '::', ws, path_segment } ;
path_root           = path_segment
                    | qualified_path_root ;
path_segment        = identifier, [ ws, generic_args ]
                    | "super" | "srcroot" ;
qualified_path_root = '(', ws, type, ws, "as", ws,
                      single_path, ws, ')' ;
```

The `generic_args` production is defined in the subclause on generic declarations.

#### Static semantics

An **identifier expression** resolves a name to its binding or to the named item it denotes. The name is looked up in the enclosing scope. Where it is not found there, the search proceeds outward through enclosing scopes until a matching declaration is found or the source unit scope is exhausted.

A **path expression** resolves a qualified name: a sequence of identifiers separated by `::`, optionally rooted at a **qualified path root** of the form `(T as Protocol)`. What the path denotes is defined in the clause on programme structure and translation.

A qualified path root `(T as Protocol)` selects the namespace of `Protocol` as implemented by `T`. The path that follows accesses an associated subroutine, an associated constant, or any other associated item that the implementation of `Protocol` for `T` provides. The form resolves a name that an inherent item and a protocol item, or two protocol items, share on the same type.

An identifier expression is an object expression when it names a `let`, `static`, or `static mut` binding. It is a value expression when it names a `const` declaration, a subroutine, or an enum unit variant.

#### Dynamic semantics

Evaluating an identifier expression yields the value held by the object of the named binding (for object expressions) or the translation-time value of the named constant (for `const` declarations). For subroutine names and enum unit variants, the expression yields the subroutine value or the variant value respectively.

#### Constraints

An identifier expression naming no matching declaration shall not appear.

A path that resolves to no declaration shall not appear. The final component of a path in expression position shall not name a namespace.

In a qualified path root `(T as Protocol)`, `T` shall be a type that implements `Protocol`.

#### Examples (informative)

```
let x: si4 = 42;

// identifier expression — resolves to the binding x
x;

// path expression — resolves to the variant red of enum colour
colour::red;
// path expression — resolves to the associated constant max on si4
si4::max;
// path expression — resolves to the subroutine write in module io
io::write;

// Qualified path root — disambiguates items of a protocol

// associated constant from bounded impl on ui1
(ui1 as bounded)::min;
// associated subroutine from defaulted impl on si4
(si4 as defaulted)::default();
```

### 6.2.2 Literal expression

#### Static semantics

A literal expression is the syntactic occurrence of a literal value in source text. The forms of literals — integer, floating radix point number, character, string, and raw string — and the rules that fix the type of each are defined in the clause on lexical structure. Each literal form is a value expression.

### 6.2.3 Parenthesized expression

#### Syntax

```
paren_expr = '(', ws, expression, ws, ')' ;
```

#### Static semantics

A parenthesized expression binds as a single operand within the expression that encloses it, whatever the default precedence and associativity would give. The type of a parenthesized expression is that of the enclosed expression, and it is an object expression where the enclosed expression is one.

#### Examples (informative)

```
let x = (a + b) * c; // forces addition before multiplication
let y = -(a + b);    // negation applies to the sum
```

### 6.2.4 Composite literal

#### Syntax

```
composite_literal = single_path,
                    [ ws, '.', ws, '{', ws,
                      [ expression_list | field_init_list ], ws,
                      '}' ] ;

expression_list   = expression, ws, { ',', ws, expression, ws },
                    [ ',', ws ] ;
field_init_list   = field_init, ws, { ',', ws, field_init, ws },
                    [ ',', ws ] ;
field_init        = '.', identifier, ws, '=', ws, expression ;
```

#### Static semantics

A **composite literal** constructs a value of a composite type. The three forms correspond to the three composite type forms:

— **Unit literal** — the identifier alone. The expression yields the sole value of the type.

— **Unnamed-field literal** — the identifier followed by `.` and an expression list enclosed by curly brackets. Each expression corresponds to a field by position, in declaration order.

— **Named-field literal** — the identifier followed by `.` and a field initializer list enclosed by curly brackets. Each initializer names its target field.

The first initializer determines the form: if its token sequence matches `'.' identifier '='`, the body is a `field_init_list`; otherwise it is an `expression_list`.

A composite literal is always a value expression.

#### Dynamic semantics

For a unit literal, no evaluation occurs.

For an unnamed-field literal, expressions are evaluated in source order, each fully evaluated before the next begins.

For a named-field literal, field initializers are evaluated in source order, each fully evaluated before the next begins. Default-value expressions for omitted fields are evaluated after all explicit initializers, in the declaration order of the omitted fields, each fully evaluated before the next begins.

#### Constraints

A composite literal written as an identifier alone shall name a type in unit form.

Every field that carries no default-value expression, other than a `?` field, shall be initialized exactly once in the literal. A field that carries one shall be initialized at most once. In an unnamed-field literal a field is initialized by the expression at its position, so the expressions shall fill a leading run of the fields.

A `?` field shall be initialized by no literal. It is initialized to zero at construction, as defined in the clause on declarations.

#### Examples (informative)

```
// Unit literal
struct empty_t;
let v = empty_t;

// Named-field literal
struct point { x: si4, y: si4 }
let p = point.{ .x = 1, .y = 2 };

// Unnamed-field literal
struct pair { si4, si4 }
let q = pair.{ 1, 2 };

// Enum variant literals
enum shape {
    circle { fe11s52 },
    rect { fe11s52, fe11s52 }
}

let s1 = shape::circle.{ 1.5 };
let s2 = shape::rect.{ 3.0, 4.0 };

// Defaults omitted
struct origin_point { x: si4 = 0, y: si4 = 0 }
let o = origin_point.{};

// Source-order evaluation — compute_y runs before compute_x
let r = point.{ .y = compute_y(), .x = compute_x() };
```

### 6.2.5 Wild construction

`EnumType::wild` yields a value that no declared variant of the enum covers. Which such value it yields is implementation defined.

#### Syntax

```
wild_construction = single_path, ws, '::', ws, "wild" ;
```

#### Static semantics

A wild construction is always a value expression.

#### Constraints

A wild construction that yields no value shall not appear.

#### Examples (informative)

```
enum empty {}
let w1 = empty::wild;

enum colour { red, green, blue }
let w2 = colour::wild;
```

### 6.2.6 Array literal and repeat literal

#### Syntax

```
array_literal  = '[', ws, expression, ws, { ',', ws, expression, ws },
                 [ ',', ws ], ']' ;
repeat_literal = '[', ws, expression, ws, ';', ws, expression, ws, ']' ;
```

#### Static semantics

An **array literal** `[e1, e2, ..., eN]` is an expression of type `[T; N]`, where `T` is the common type of all element expressions and `N` is the number of elements.

A **repeat literal** `[expr; N]` is an expression of type `[T; N]`, where `T` is the type of `expr` and `N` is an expression of type `uaddr`. The expression `expr` is evaluated once and the result is copied `N` times.

Both forms are value expressions.

#### Dynamic semantics

In an array literal, element expressions are evaluated in source order, each fully evaluated before the next begins.

In a repeat literal, `N` is fully evaluated before the initializer expression begins, and the initializer expression is evaluated once. The resulting value is stored into all `N` elements by copy.

#### Constraints

All elements of an array literal shall have a common type.

A repeat literal shall not appear where `T` is not copyable.

#### Examples (informative)

```
let arr = [10, 20, 30];             // [si4; 3]
let zeros: [ui1; 4096] = [0; 4096]; // repeat literal
```

### 6.2.7 Tuple literal

#### Syntax

```
tuple_literal = '.', ws, '{', ws, expression, ws,
                { ',', ws, expression, ws }, [ ',', ws ], '}' ;
```

#### Static semantics

A tuple literal `.{ e1, e2, ..., eN }` is an expression of type `.{T1, T2, ..., TN}`, where each `Ti` is the type of the corresponding element expression. The elements need not share a type.

A tuple literal is a value expression. Element expressions are evaluated in source order.

#### Examples (informative)

```
// pair: .{saddr, verdict.[void, void]}
let pair = .{ 42, verdict.[void, void]::Pass(void) };
// triple: .{saddr, fe8s23, verdict.[void, void]}
let triple = .{ 1, 2.0, verdict.[void, void]::Fail(void) };
```

### 6.2.8 Uninitialized value introduction

#### Syntax

```
uninit_expression = "uninit" ;
```

#### Static semantics

`uninit` is a value expression whose result is an **uninitialized value**.

Its type is determined by checking alone, as the clause on types defines. Where it is the value of an assignment to a binding’s object, that assignment counts as an assignment to the object in determining definite initialization, as defined in the clause on declarations.

#### Dynamic semantics

An uninitialized value is in one of two states.

— **Contained** — a value `uninit` yields is contained.

— **Escaped** — a contained value becomes escaped where a reference that permits stores to an object holding it is passed as an argument to a subroutine imported via `#dyn` or appears as an operand of an `asm` block.

An operation upon an uninitialized value yields a value of the operation’s type. Where a reference that does not permit stores to an object holding one is so passed or so appears, a load from that object occurs at that point.

An object ceases to hold an uninitialized value when a value other than `uninit` is stored into it, by direct assignment or through a reference that permits stores.

#### Constraints

An `uninit` expression requires airside.

#### Implementation requirements

The implementation shall issue an advisory diagnostic at the first operation upon a contained uninitialized value, and at the first managed-reference creation on an object holding one. The implementation should issue an advisory diagnostic at the first such operation upon an escaped value. The implementation may issue an advisory diagnostic at any subsequent such operation in either state.

A conforming implementation that determines the value an operation upon an uninitialized value yields shall document the mechanism and shall apply it uniformly to every such operation.

#### Examples (informative)

```
// FFI out-parameter via unmanaged reference
let y = airside {
    let mut x: large_t = uninit; // contained
    // store-permitting reference to #dyn — contained → escaped
    foreign_init(%mut x);
    // first load in escaped — the implementation should issue an
    // advisory diagnostic
    express x;
};

// Local store exits the state
airside {
    let mut w: si4 = uninit; // contained
    // load-only reference to #dyn — load in contained — the
    // implementation shall issue an advisory diagnostic
    foreign_peek(%w);
    w = 0; // contained exited — no diagnostic
    express w;
}

// uninit in non-initializer assignment
airside {
    let mut x = 0; // normal
    x = uninit;    // contained
    // first load in contained — the implementation shall issue an
    // advisory diagnostic
    express x;
}

// argument position — the parameter type checks it
let random_seed = airside { express randgen(uninit); };

// translation failure — no annotation, and uninit supplies no type
// airside {
//     let mut z = uninit;
// }
```

## 6.3 Postfix expressions

A postfix expression is formed by appending an operator or operand list to the following side of a primary expression or another postfix expression. The binding strength of each postfix operator is defined in the subclause on operator precedence and associativity.

### 6.3.1 Subroutine invocation

#### Syntax

```
invocation_expr = expression, ws, '(', ws, [ argument_list ], ws, ')' ;
argument_list   = expression, ws, { ',', ws, expression, ws },
                  [ ',', ws ] ;
```

#### Static semantics

A subroutine invocation expression invokes the subroutine designated by the leading expression.

The type of a subroutine invocation expression is the return type of the invoked subroutine. A subroutine invocation is always a value expression.

The number and types of variadic arguments are not verified during translation.

#### Dynamic semantics

The leading expression is evaluated before the arguments. Arguments are evaluated in declaration order. Each argument is fully evaluated before the next begins. The resulting values are copied or transferred into the parameter bindings of the invoked subroutine. When the subroutine carries the `variadic` modifier, arguments beyond the fixed parameters are evaluated in source order after the last fixed argument. These values are passed through the variadic invocation interface of the environment that evaluates the invocation and are accessible through the variadic binding within the invoked subroutine.

After all arguments have been evaluated, control transfers to the subroutine body. When the subroutine returns, the return value is made available as the result of the invocation expression.

#### Constraints

The leading expression of a subroutine invocation shall evaluate to a subroutine or a subroutine pointer.

The number of arguments shall equal the number of parameters in the subroutine’s declaration, unless the subroutine carries the `variadic` modifier. Each argument shall be assignable to the corresponding parameter’s type.

An invocation of a subroutine carrying the `variadic` modifier shall provide at least the fixed parameters.

An invocation expression that invokes a variadic subroutine through a subroutine pointer shall use a subroutine pointer type that carries the `variadic` keyword, as defined in the clause on types.

#### Examples (informative)

```
// direct subroutine invocation
let sum = add(2, 3);
// generic subroutine invocation with explicit type argument
let val = get_default.[si4]();

// subroutine pointer invocation
use ext::get_info;
let callback: fn(si2) -> result = get_info;
let r = callback(42);

// Declaration-order evaluation: a() runs first, then b(), then c()
foo(a(), b(), c());
```

### 6.3.2 Field access

#### Syntax

```
field_access = expression, ws, '.', ws, identifier
             | expression, ws, '.', ws, integer_literal ;
```

#### Static semantics

A field access expression `e.f` yields the value of the field named `f` in the type of `e` after reference transparency. The expression `e` — to the leading side of the `.` token here and in a method invocation — is the **receiver**. The result type is the type of the field.

For struct types, `f` names a declared field. For tuple types and unnamed-field variant payloads, `f` is an index into the fields in declaration order.

A field access is an object expression when the receiver is an object expression; otherwise it is a value expression. A multi-assignment binding permits a store to its field, and a reference permits one where the store permission defined in the clause on references and resource management grants it. Where the receiver permits no store, the field is storable where the per-field store permission defined in the clause on declarations permits it.

The modifier semantics (`pub`, `airside`, `mut`) and their interaction with the kind of the enclosing binding are defined in the clause on declarations.

The built-in fields of array types (`.ptr` and `.len`) are accessed by the same field access form. Their specific access rules — the distinction between projection and stored access, storability, and modifier propagation — are defined in the clause on references and resource management.

#### Constraints

For struct types, `f` shall be an identifier matching a declared field name. For tuple types and unnamed-field variant payloads, `f` shall be an integer literal in the range `[0, N)`.

A non-`pub` field shall be accessed only within the module that declares the containing type. An access to an `airside` field requires airside.

#### Examples (informative)

```
let p = point.{ .x = 1, .y = 2 };
p.x;     // field access on a value — yields si4

let pair = .{ 42, verdict.[void, void]::Pass(void) };
pair.0;  // positional field access — yields si4
pair.1;  // positional field access — yields verdict

let arr = [10, 20, 30];
arr.len; // built-in field — yields 3~uaddr (projection)
arr.ptr; // built-in field — yields %si4 (projection)
```

### 6.3.3 Method invocation

#### Syntax

```
method_invocation           = expression, ws, '.', ws, identifier, ws,
                              '(', ws, [ argument_list ], ws, ')'
                            | qualified_method_invocation ;
qualified_method_invocation = '(', ws, expression, ws, "as", ws,
                              single_path, ws, ')', ws, '.', ws,
                              identifier, ws, '(', ws,
                              [ argument_list ], ws, ')' ;
```

#### Static semantics

A method invocation expression `e.m(args)` invokes the method named `m` on the receiver `e` after reference transparency. The resolution of `m` is defined in the subclause on method name resolution in the clause on protocols and implementations.

A **qualified method invocation** `(e as Protocol).m(args)` invokes the method named `m` from the implementation of `Protocol` for the type of `e`, regardless of any inherent method or other protocol method of the same name on the type.

The type of a method invocation expression is the return type of the resolved method. A method invocation is always a value expression.

#### Dynamic semantics

The receiver is evaluated before the arguments. The subclause on subroutine invocation governs the rest of the invocation.

#### Constraints

In a qualified method invocation, the type of `e` shall implement `Protocol`, and the implementation shall provide a method named `m`.

#### Examples (informative)

```
struct counter { pub val: uaddr }

impl counter {
    pub fn get(&self) -> uaddr { return (*self).val; }
    pub fn increment($self) { self.val += 1; }
}

let c_ref: &counter = &some_counter;
c_ref.get();   // OK — method invocation on &counter

let mut m: counter = counter.{ .val = 0 };
m.increment(); // OK — auto-ref: $self applied to mut value
m.get();       // OK — auto-ref: &self applied to value

// Qualified method invocation
// disambiguates inherent/protocol or protocol/protocol collision
(value as fmt).fmt(&buf);
// invokes the fmt method from the fmt impl
```

### 6.3.4 Contract propagation

#### Syntax

```
propagation_expr = expression, ws, '?' ;
```

#### Static semantics

The `?` operator is a postfix operator that extracts the success value from an expression of a contract type, or propagates the failure value to the enclosing subroutine by causing an early return.

The type of the `?` expression is the success type `T` of the contract pair.

#### Dynamic semantics

1. The operand `e` is evaluated.
2. The resulting value is tested against the contract’s success variant.
3. If the value is a success variant, the payload is extracted and becomes the result of the `?` expression. Execution continues normally.
4. If the value is a failure variant, the payload is extracted, and the enclosing subroutine performs an early return with a failure-variant value containing the extracted payload.

#### Constraints

The operand `e` shall have a contract type.

The enclosing subroutine’s return type shall itself be a contract type, and the failure payload type of the operand shall exactly match the failure payload type of the enclosing subroutine’s return type.

#### Examples (informative)

```
fn read_config(path: &[ui1]) -> verdict.[config, io_error] {
    let file = open(path)?;     // propagates io_error on failure
    let data = read_all(file)?; // propagates io_error on failure
    return parse(data);
}
```

### 6.3.5 Reference transparency

#### Static semantics

When the expression to the leading side of `.` has a reference type, the field or method is looked up in the referent type `T`, not in the reference type. This transparency applies exactly once.

For unmanaged references, the access made through this transparency requires airside, as the dereference of an unmanaged reference does.

#### Examples (informative)

```
struct point { pub x: si4, pub y: si4 }
let p = point.{ .x = 1, .y = 2 };
let r: &point = &p;
r.x;     // OK — equivalent to (*r).x, yields 1

let rr: &&point = &r;
// rr.x; // translation failure — &point has no field named x
```

### 6.3.6 Automatic referencing

#### Static semantics

Where the receiver’s type does not match the method’s self parameter, the receiver is adjusted to the type the self parameter names. The adjustment is one reference creation or one reference cast, and the constraints upon that creation or cast apply to it. A value is adjusted to an exclusive reference or to a shared reference, and an exclusive reference is adjusted to a shared reference. No other adjustment is permitted.

#### Examples (informative)

```
let mut m: counter = counter.{ .val = 0 };
m.increment();    // auto-ref: value → $counter to satisfy $self
m.get();          // auto-ref: value → &counter to satisfy &self

let r: &counter = &m;
r.get();          // OK — &self already satisfied
// r.increment(); // translation failure — &counter cannot satisfy $self
```

## 6.4 Unary expressions

A unary expression is formed by prefixing an operator to a primary or postfix expression. The binding strength of each unary operator is defined in the subclause on operator precedence and associativity.

### 6.4.1 Negation

#### Syntax

```
negation_expr = '-', ws, expression ;
```

#### Static semantics

Unary negation (`-expr`) requires the operand to satisfy `numeric`. The result type is the operand’s type `T`. A unary negation expression is always a value expression.

— Signed integer types (`siN`, `saddr`) — the result is the arithmetic negation. When the operand is the minimum value of the type, the result wraps to that same value.

— Unsigned integer types (`uiN`, `uaddr`) — the result is the two’s complement negation. The value is 2<sup>*W*<sub>t</sub></sup> − *x* for non-zero `x`, and `0` for `x == 0`, where *W*<sub>t</sub> is the bit width of `T`.

— Floating radix point number types — unary negation flips the sign bit. All other bits are preserved.

#### Examples (informative)

```
let a: si4 = -42;      // signed negation
let b: ui4 = -1~ui4;   // two’s complement: 0xFFFFFFFF
let c: fe11s52 = -0.0; // negative zero
```

### 6.4.2 Not

#### Syntax

```
not_expr = '!', ws, expression ;
```

#### Static semantics

The `!` operator has two distinct meanings, determined by the type of the operand:

— Bitwise NOT — when the operand satisfies `integer`, `!x` yields the bitwise complement of `x`, the value whose bit at each position `k` is `1` if and only if the bit at position `k` in `x` is `0`. The result type is `T`.

— Contract polarity inversion — when the operand has a contract type that declares `inv -> U`, `!x` yields a value of type `U`, with the success and failure variants exchanged. Contract polarity inversion is defined in the clause on statements and control flow.

A `!` expression is always a value expression.

#### Constraints

A `!` expression whose operand neither satisfies `integer` nor is a contract type that declares `inv` shall not appear.

#### Examples (informative)

```
let a: ui4 = 0xFF00_FF00~ui4;
let b = !a; // 0x00FF_00FF~ui4 — bitwise NOT

let v: verdict.[si4, si4] = verdict::Pass(42);
let w = !v; // verdict::Fail(42) — polarity inversion
```

### 6.4.3 Dereference

#### Syntax

```
deref_expr = '*', ws, expression ;
```

#### Static semantics

The dereference operator `*` accesses the object designated by a reference. The operand has a reference type, with any combination of modifiers. The result type is the referent type.

A dereference expression is an object expression. It designates the referent. Assigning to `*r` stores to the referent, subject to the kind of the binding and the reference’s family.

Dereference through a managed reference is permitted in landside code, under the rules defined in the clause on references and resource management.

#### Dynamic semantics

Evaluating `*r` loads from or stores to the object identified by the reference `r`. For `volatile`-modified references, each dereference is a σ operation.

#### Constraints

The operand of `*` shall have a reference type. Its referent type shall be one the `type` production of the clause on types yields, and shall not be a protocol object type.

A dereference of an unmanaged reference requires airside.

#### Examples (informative)

```
let x: si4 = 42;
let r: &si4 = &x;
let val = *r; // dereference — yields 42

let mut y: si4 = 0;
let e: $si4 = $y;
*e = 99; // store through exclusive reference

airside {
    let p = 0x4000_1000~uaddr as %volatile mut ui4;
    *p = 0xDEAD_BEEF; // volatile store through unmanaged reference
    let v = *p;       // volatile load through unmanaged reference
}
```

### 6.4.4 Reference creation

#### Syntax

```
ref_shared_expr    = '&', ws, [ modifier_list, ws ], expression ;
ref_exclusive_expr = '$', ws, [ modifier_list, ws ], expression ;
ref_unmanaged_expr = '%', ws, [ modifier_list, ws ], expression ;

modifier_list      = modifier, { ws, modifier } ;
modifier           = "volatile" | "mut" | "atomic" | "guard" ;
```

#### Static semantics

`&expr` creates a shared reference to the operand. A shared reference permits loading from the referent, and permits storing through it where it carries `mut`. Multiple shared references to the same object may coexist.

`$expr` creates an exclusive reference to the operand. An exclusive reference permits both loads and stores.

`%expr` creates an unmanaged reference to the operand.

`&expr`, `$expr`, and `%expr` are value expressions, and each yields a reference value.

Modifiers may be placed between the family and the operand to create a reference with the specified modifier directly, without a subsequent `as` cast. The placement rules for modifiers are defined in the clause on references and resource management. The resulting reference type includes the specified modifiers.

The set of valid family–modifier combinations and their semantics are defined in the clause on references and resource management. That clause fixes which combinations require airside, which shall not appear, and how modifiers interact with the derivation tree.

#### Constraints

The operand of `&expr`, of `$expr`, and of `%expr` shall be an object expression, and shall not be a projection. Where that operand is the dereference of a reference, the subclause on reference casting governs what the expression creates. Otherwise, where the reference the expression creates permits stores, the operand shall be a storable object expression.

The exclusivity an exclusive reference asserts is defined in the clause on references and resource management.

#### Examples (informative)

```
let x: si4 = 42;

// shared reference
let r: &si4 = &x;
// shared volatile reference
let v: &volatile si4 = &volatile x;
// shared atomic reference
let a: &atomic si4 = &atomic x;

let mut y: si4 = 0;

// exclusive reference
let e: $si4 = $y;
// exclusive volatile reference
let ev: $volatile si4 = $volatile *e;

// Unmanaged reference
let p: %si4 = %x;
airside { let val = *p; }

// Shared references can coexist
let a: &si4 = &x;
let b: &si4 = &x; // OK — multiple shared references
```

## 6.5 Arithmetic operators

All arithmetic operators require both operands to satisfy the `numeric` bound. The operators `+` and `-` additionally accept a leading operand of unmanaged reference type with a following operand of type `uaddr`. The rules for this form are defined in the clause on references and resource management. Saturating and widening operators require the `integer` bound.

Throughout this subclause, the bit width of a type `T`, denoted *W*<sub>t</sub>, and the value set of an integer type are as the clause on types defines them.

### Syntax

```
arith_expr = expression, ws, arith_op, ws, expression ;
arith_op   = '+' | '+|' | '+@'
           | '-' | '-|'
           | '*' | '*|' | '*@'
           | '/' | '/|'
           | '%' ;
```

### Constraints

The operands of any binary arithmetic operator shall be the same type `T`, or shall be an unmanaged reference and a `uaddr` in the form defined above.

### 6.5.1 Wrapping integer arithmetic

#### Static semantics

For operands of a type satisfying `integer`, the base arithmetic operators yield results as follows. All results are of type `T`.

— Addition — `a + b` yields (*a* + *b*) mod 2<sup>*W*<sub>t</sub></sup>, mapped to the value set of `T`. For signed types, the modular result is mapped by interpreting the low *W*<sub>t</sub> bits as a two’s complement representation.

— Subtraction — `a - b` yields (*a* − *b*) mod 2<sup>*W*<sub>t</sub></sup>, mapped to the value set of `T` by the same rule.

— Multiplication — `a * b` yields (*a* × *b*) mod 2<sup>*W*<sub>t</sub></sup>, mapped to the value set of `T` by the same rule.

— Division — `a / b` yields the integer quotient of `a` divided by `b`, truncated towards zero. The absolute value of the quotient equals the quotient of the absolute values (|*a* / *b*| = |*a*| / |*b*|), and the sign is negative if and only if the operands have different signs. When the mathematical quotient is not representable in `T` — which occurs only when `a` is the minimum value of a signed type and `b` is `-1` — the result wraps, and `a / b` yields `a`.

— Remainder — `a % b` yields *a* − *q* × *b*, where *q* is the quotient `a / b` yields. The sign of the result, when non-zero, is the sign of `a`. When division of the signed minimum by `-1` wraps, the remainder is `0`.

— Division by zero — `a / 0` yields `0`. `a % 0` yields `a`.

### 6.5.2 Saturating integer arithmetic

#### Static semantics

For operands of a type satisfying `integer`, the saturating operators `+|`, `-|` and `*|` clamp the mathematical result to the value range of `T`. Let *MIN* and *MAX* denote the minimum and maximum values of the value set of `T`. Such an operator yields *MAX* where the mathematical result exceeds *MAX*, *MIN* where it is less than *MIN*, and the mathematical result otherwise.

`a /| b` yields the truncated-towards-zero quotient when the result is representable. When the result is not representable (signed minimum divided by `-1`), the result is *MAX*. Where `b` is zero, `a /| 0` yields `0`.

### 6.5.3 Widening integer arithmetic

#### Static semantics

For operands of a type satisfying `integer`, the widening operators yield the full mathematical result as a pair of `T` values. The return type is the anonymous tuple `.{T, T}`.

`a +@ b` yields `.{low, high}`. The mathematical sum is represented as an unsigned 2*W*<sub>t</sub>-bit value for unsigned `T` and a two’s complement 2*W*<sub>t</sub>-bit value for signed `T`. `low` contains the *W*<sub>t</sub> bits of lesser weight, mapped to the value set of `T`. `high` contains the *W*<sub>t</sub> bits of greater weight, mapped to the value set of `T`. For unsigned types, `high` is the carry bit and has the value `0` or `1`. For signed types, `high` is the sign extension of the low half and has the value `0` or `-1`.

`a *@ b` yields `.{low, high}`. The mathematical product is represented as a 2*W*<sub>t</sub>-bit value. `low` contains the *W*<sub>t</sub> bits of lesser weight; `high` contains the *W*<sub>t</sub> bits of greater weight. Both are mapped to the value set of `T`.

#### Examples (informative)

```
let a: ui4 = 0xFFFF_FFFF~ui4;
let b: ui4 = 2~ui4;
let .{ low, high } = a +@ b;
// Mathematical sum: 0x1_0000_0001 (33 bits)
// low:  0x0000_0001~ui4
// high: 0x0000_0001~ui4 (carry)

let c: ui4 = 0x1_0000~ui4;
let d: ui4 = 0x1_0000~ui4;
let .{ lo, hi } = c *@ d;
// Mathematical product: 0x1_0000_0000 (4294967296)
// lo: 0x0000_0000~ui4
// hi: 0x0000_0001~ui4
```

### 6.5.4 Floating radix point number arithmetic

#### Static semantics

For operands of a floating radix point number type, the base arithmetic operators `+`, `-`, `*`, `/`, `%` yield results of type `T`. The rounding mode, NaN propagation, and the results of operations involving infinity and zero are defined in the clause on types.

The remainder operator `a % b` is defined for a floating radix point number type. The result is the ISO/IEC 60559:2020 remainder: the value *a* − *n* × *b*, where *n* is the integer nearest to the exact quotient of *a* divided by *b* (ties to even). `a % 0.0` yields NaN.

#### Constraints

A saturating operator (`+|`, `-|`, `*|`, `/|`) or a widening operator (`+@`, `*@`) on a floating radix point number type shall not appear.

### 6.5.5 Unary negation

Unary negation (`-expr`) is defined in the subclause on unary expressions.

## 6.6 Bitwise and shift operators

The bitwise operators `&`, `|`, and `^` require both operands to satisfy the `integer` bound. The shift operators `<<` and `>>` require both operands to satisfy the `integer` bound. The result type is the type of the leading operand. Let *W*<sub>t</sub> denote the bit width of the leading operand’s type.

### Syntax

```
bitwise_expr = expression, ws, bitwise_op, ws, expression ;
bitwise_op   = '&' | '|' | '^' | '<<' | '>>' ;
```

### Constraints

The operands of `&`, `|`, or `^` shall be the same type `T`.

### Examples (informative)

These examples apply where `cellbits::exec == 8`.

```
let a: ui4 = 0xFF00_FF00~ui4;
let b: ui4 = 0x00FF_FF00~ui4;

let and_r  = a & b;     // 0x0000_FF00~ui4
let or_r   = a | b;     // 0xFFFF_FF00~ui4
let xor_r  = a ^ b;     // 0xFFFF_0000~ui4
let not_a  = !a;        // 0x00FF_00FF~ui4

let x: si4 = -1~si4;    // all bits set (0xFFFFFFFF)
let not_x  = !x;        // 0~si4 (0x00000000)
let shr    = x >> 4;    // -1~si4 (arithmetic shift)

let y: ui1 = 0x80~ui1;
let shl    = y << 1;    // 0x00~ui1 (0x100 mod 2^8 = 0)
let shr_u  = y >> 1;    // 0x40~ui1 (logical shift)

// Shift count >= bit width (ui4 has W = 32 when cellbits == 8)
let z: ui4 = 1~ui4;
let big    = z << 32;   // 0~ui4
let big2   = z << 100;  // 0~ui4
let neg: si4 = -1~si4;
let big3   = neg >> 32; // -1~si4 (sign bit replicated)

// Negative shift count — the shift is performed in the other
// direction. The operands need not share a type.
let sh: si4 = -4~si4;
let other  = z << sh;   // descending shift of z by 4
```

### 6.6.1 Bitwise AND, OR, XOR

#### Static semantics

— Bitwise AND — `a & b` yields the value whose bit at each position *k* (counting from zero at the position of least weight) is `1` if and only if the bits at position *k* in both `a` and `b` are `1`.

— Bitwise OR — `a | b` yields the value whose bit at each position *k* is `1` if and only if the bit at position *k* in at least one of `a` or `b` is `1`.

— Bitwise XOR — `a ^ b` yields the value whose bit at each position *k* is `1` if and only if the bits at position *k* in `a` and `b` differ.

These definitions apply uniformly to signed and unsigned integer types. The operations are performed on the two’s complement representation. The result is interpreted according to the value set of `T`.

### 6.6.2 Shift operators

#### Static semantics

An ascending shift `a << b` yields (*a* × 2<sup>*b*</sup>) mod 2<sup>*W*<sub>t</sub></sup>, mapped to the value set of `T`. The bit representation of `a` is shifted towards positions of greater weight by `b` positions. Vacated positions of lesser weight are filled with zeros.

A descending shift `a >> b` yields a value determined by the signedness of `T`:

— Unsigned types — the result is the integer part of *a* ÷ 2<sup>*b*</sup>. Vacated positions of greater weight are filled with zeros (logical shift).

— Signed types — the result is the integer part of *a* ÷ 2<sup>*b*</sup>, rounded towards negative infinity. Vacated positions of greater weight are filled with copies of the sign bit (arithmetic shift).

Where the value of `b` is negative, the shift is performed in the other direction by −*b* positions, taken as an exact operation over the integers: `a << b` yields the descending shift of `a` by −*b*, and `a >> b` yields the ascending shift of `a` by −*b*.

If the value of `b` is greater than or equal to *W*<sub>t</sub>:

— For an ascending shift, the result is `0`.

— For an unsigned descending shift, the result is `0`.

— For a signed descending shift, the result is `0` where `a` is non-negative and `-1` where `a` is negative.

### 6.6.3 Bitwise NOT

#### Static semantics

`!` on an operand satisfying `integer` is defined in the subclause on unary expressions.

## 6.7 Comparison operators

The comparison operators return `verdict.[void, void]` and require both operands to satisfy the `numeric` bound.

### Syntax

```
comparison_expr = expression, ws, comparison_op, ws, expression ;
comparison_op   = '==' | '!=' | '<' | '>' | '<=' | '>=' ;
```

### Static semantics

The result type of a comparison is `verdict.[void, void]`.

— Integer comparison — for unsigned integer types, `a < b` yields `verdict::Pass(void)` if and only if the value of `a` is strictly less than the value of `b` in the natural order on the value set [0, 2<sup>*W*<sub>t</sub></sup> − 1]. For signed integer types, the comparison follows the natural order on the value set [−2<sup>*W*<sub>t</sub>−1</sup>, 2<sup>*W*<sub>t</sub>−1</sup> − 1]: the values are compared as mathematical integers, not as the Γ sequences that represent them.

— Floating radix point number comparison — the comparison operators on a floating radix point number type follow the rules defined in the clause on types.

### Constraints

Both operands of a comparison operator shall be the same type `T`.

### Examples (informative)

```
let a: si4 = -1~si4;
let b: si4 = 1~si4;
let r = a < b;   // Pass — signed comparison: -1 < 1

let x: ui4 = 0xFFFF_FFFF~ui4;
let y: ui4 = 1~ui4;
let s = x > y;   // Pass — unsigned comparison: 4294967295 > 1

let p: fe11s52 = 0.0 / 0.0;    // +0nanq — payload 0, XOR(+, +) = +
let q: fe11s52 = -(0.0 / 0.0); // -0nanq
let t = p == p;     // Pass — reflexive
let u = p == q;     // Fail — sign differs
let v = p > 1.0;    // Pass — +qNaN orders above every non-NaN value
let w = p == 0nanq; // Pass — bit-identical

let neg_zero: fe11s52 = -0.0;
let pos_zero: fe11s52 = 0.0;
let z1 = neg_zero == pos_zero; // Fail — sign distinguishes zero
let z2 = neg_zero < pos_zero;  // Pass

let n = 0nans < 0nanq; // Pass — +sNaN orders below +qNaN
```

## 6.8 Assignment

An assignment expression stores a value into an object expression. Two forms exist: simple assignment and compound assignment.

### Syntax

```
assignment_expr = expression, ws, '=', ws, expression ;

compound_assign = expression, ws, compound_op, ws, expression ;
compound_op     = '+=' | '-=' | '*=' | '/=' | '%='
                | '+|=' | '-|=' | '*|=' | '/|='
                | '&=' | '|=' | '^=' | '<<=' | '>>=' ;
```

### Static semantics

Both forms are value expressions whose result type is `void`.

A type `S` is **assignable** to a type `T` where `S` and `T` are the same type, or where this specification defines an implicit conversion from `S` to `T`.

### Dynamic semantics

A store of an uncopyable type proceeds in two steps:

1. The existing value held by the target object is destroyed, if the object is initialized there.
2. The new value is transferred into the target object.

### Constraints

The leading operand shall be a storable object expression, or an object expression designating the object of a single-assignment binding that is not definitely initialized at the programme point.

The type of the following operand shall be assignable to the type of the leading operand.

### Examples (informative)

```
let mut x: si4 = 0;
x = 42;

// Deferred initialization of a single-assignment binding
let y: si4;
y = compute();
```

### 6.8.1 Evaluation order

#### Dynamic semantics

In a simple assignment `a = b`:

1. The leading operand `a` is evaluated to determine its object.
2. The following operand `b` is evaluated.
3. The resulting value is stored into the object of `a`.

Each step is sequenced before the next.

In a compound assignment `a op= b`:

1. The leading operand `a` is evaluated to determine its object and to load the current value held by the object.
2. The following operand `b` is evaluated.
3. The binary operation `op` is performed on the current value of `a` and the value of `b`.
4. The result is stored into the object of `a`.

Each step is sequenced before the next.

### 6.8.2 Compound assignment operators

A compound assignment operator combines a binary operation with a store to the leading operand.

#### Static semantics

**Arithmetic compound assignments** — `+=`, `-=`, `*=`, `/=`, `%=` — follow wrapping semantics. `+=` and `-=` accept a leading operand of unmanaged reference type with a following operand of type `uaddr`, as defined in the clause on references and resource management.

**Saturating compound assignments** — `+|=`, `-|=`, `*|=`, `/|=` — follow saturating semantics.

**Bitwise compound assignments** — `&=`, `|=`, `^=` — follow the bitwise semantics defined in this clause. **Shift compound assignments** — `<<=`, `>>=` — follow the shift semantics defined in this clause.

#### Constraints

The leading operand shall be a storable object expression.

The operands of an arithmetic compound assignment shall satisfy `numeric`, or shall be an unmanaged reference and a `uaddr` in the form defined above. The operands of a saturating compound assignment shall satisfy `integer`. The operands of a bitwise compound assignment shall satisfy `integer` and shall be the same type `T`. The operands of a shift compound assignment shall satisfy `integer`.

#### Examples (informative)

```
let mut x: uaddr = 10;
x += 5;    // wrapping:   x is now 15
x -|= 100; // saturating: x is now 0

let mut flags: ui4 = 0xFF00;
flags &= 0x0F0F; // flags is now 0x0F00
flags ^= 0x00FF; // flags is now 0x0FFF
flags <<= 4;     // flags is now 0xFFF0
```

## 6.9 Type casting

`as` performs explicit type conversion between types.

### Syntax

```
cast_expr   = expression, ws, "as", [ ws, '!' ], ws, cast_target ;
cast_target = type ;
```

### Static semantics

Where the cast target is `?`, it is an inferred type, as defined in the clause on types, and the type it resolves to is the target of the conversion. The subclause that defines the conversion states the default type for the form where it defines one.

The `!` of a cast expression selects bitwise reinterpretation, as defined in the subclause on bitwise reinterpretation. A cast expression without it converts by the rules of the subclause that defines the conversion for the types of its operand and its target.

### 6.9.1 Conversion categories

#### Static semantics

The following terms describe the operations that `as` can perform. Each conversion is classified by one of these terms throughout this subclause.

— **Truncation** — the value is reduced modulo 2<sup>target_bits</sup>. Bits of greater weight are discarded.

— **Zero-extension** — the source value is padded with zero bits in the positions of greater weight.

— **Sign-extension** — the source value is padded by replicating the sign bit in the positions of greater weight.

— **Reinterpretation** — the Γ sequence is preserved unchanged and only the type interpretation changes.

— **Rounding** — the value is converted to the nearest representable value, using round-to-nearest, ties-to-even.

— **Truncation towards zero** — the fractional part is discarded.

— **Saturation** — out-of-range values are clamped to the nearest boundary of the target type.

### 6.9.2 Integer → Integer

#### Static semantics

<table>
<thead><tr><th></th><th>Target wider</th><th>Target same width</th><th>Target narrower</th></tr></thead>
<tbody>
<tr><td>Unsigned → Unsigned</td><td>Zero-extension</td><td>Reinterpretation</td><td>Truncation</td></tr>
<tr><td>Unsigned → Signed</td><td>Zero-extension</td><td>Reinterpretation</td><td>Truncation</td></tr>
<tr><td>Signed → Unsigned</td><td>Sign-extension then reinterpretation</td><td>Reinterpretation</td><td>Truncation</td></tr>
<tr><td>Signed → Signed</td><td>Sign-extension</td><td>Reinterpretation</td><td>Truncation</td></tr>
</tbody>
</table>

#### Examples (informative)

```
// truncation: low 8 bits → 255~ui1
255~si4 as ui1
// reinterpretation: 0xFF → 255~ui1
-1~si1 as ui1
// zero-extension: 42~si4
42~ui1 as si4
// sign-extension: -1~si4
-1~si1 as si4
// sign-extension, then reinterpretation: 0xFFFFFFFF → 4294967295~ui4
-1~si1 as ui4
// reinterpretation: 0x80 → -128~si1
128~ui1 as si1
```

### 6.9.3 Integer → Floating radix point number

#### Static semantics

The integer value is converted to the nearest representable floating radix point number. If the value is not exactly representable, it is rounded (round-to-nearest, ties-to-even).

### 6.9.4 Floating radix point number → Integer

#### Static semantics

The conversion truncates towards zero, then saturates for out-of-range values.

<table>
<thead><tr><th>Condition</th><th>Semantics</th></tr></thead>
<tbody>
<tr><td>Finite, in range</td><td>Truncation towards zero</td></tr>
<tr><td>Finite, above target max</td><td>Saturation to target type maximum</td></tr>
<tr><td>Finite, below target min</td><td>Saturation to target type minimum</td></tr>
<tr><td>Positive infinity</td><td>Target type maximum</td></tr>
<tr><td>Negative infinity</td><td>Target type minimum</td></tr>
<tr><td>NaN</td><td>Zero</td></tr>
</tbody>
</table>

#### Examples (informative)

```
3.7~fe8s23 as si4    // 3~si4 (towards zero)
-2.9~fe11s52 as si4  // -2~si4 (towards zero)
1e20~fe11s52 as si4  // si4 max (saturating)
-1e20~fe11s52 as ui4 // 0~ui4 (unsigned min, saturating)

// 0~si4 (NaN → zero)
(0.0~fe11s52 / 0.0~fe11s52) as si4
// 0~si4 (NaN → zero, regardless of sign)
-(0.0~fe11s52 / 0.0~fe11s52) as si4
```

### 6.9.5 Floating radix point format conversions

#### Static semantics

<table>
<thead><tr><th>Condition</th><th>Semantics</th></tr></thead>
<tbody>
<tr><td>Exactly representable</td><td>Exact</td></tr>
<tr><td>In range, not exact</td><td>Rounding</td></tr>
<tr><td>Overflow</td><td>Positive or negative infinity, preserving sign</td></tr>
<tr><td>NaN</td><td>NaN</td></tr>
<tr><td>Positive or negative infinity</td><td>The same infinity</td></tr>
</tbody>
</table>

For a NaN operand, the sign bit and the quiet/signalling bit are preserved. When the target format’s payload field is wider than the source’s, the payload is zero-extended. When the target format’s payload field is narrower than the source’s, a payload that fits within the target width is preserved; a payload that does not fit is saturated to the target’s maximum payload, as defined in the clause on types.

#### Examples (informative)

```
// fe5s10’s payload is 9 bits. 0x3FFFFF overflows and saturates.
0nanq'0x3FFFFF as fe5s10   // → 0nanq'0x1FF
0nanq'1        as fe5s10   // fits → preserved
0nanq'1        as fe19s236 // wider field → zero-extended
```

### 6.9.6 Address-width conversions

#### Static semantics

`uaddr` and `saddr` follow the same integer-to-integer conversion rules as other integer types of equivalent width. `uaddr` is treated as unsigned; `saddr` is treated as signed.

### 6.9.7 Variant type → discriminant

#### Static semantics

A value of a variant type may be cast to its discriminant value using `as`. Variant types are defined in the clause on declarations.

`e as ?` extracts the discriminant. The default type for this form is the **discriminant type** of the variant type, which automatic discriminant sizing or `with discrim(T)` determines. Where the discriminant type is `void`, the form yields `void`.

`e as T` where `T` satisfies `integer` extracts the discriminant and then converts it to `T` using the standard integer-to-integer conversion rules. Where the discriminant type is `void`, the conversion yields zero.

The extracted value depends on the variant the value currently holds:

— For an **explicit variant** (non-wild), the extracted value is the variant’s discriminant.

— For a **wild variant with a canonical value** (`wild(V)`), the extracted value is `V` — the canonical value, regardless of the discriminant value stored.

— For a **wild variant without a canonical value** (`wild` alone), the extracted value is the discriminant value stored.

#### Constraints

An `as` conversion whose source is a variant type shall have `?` or a type satisfying `integer` as its target.

#### Examples (informative)

```
enum colour { red, green, blue }
let c = colour::green;
let d = c as ?;     // d: ui1, value 1
let e = c as ui4;   // e: ui4, value 1
                    // (discriminant extracted, then zero-extended)

let b = verdict.[void, void]::Pass(void);
let n = b as ?;     // n: ui1, value 1
let m = b as uaddr; // m: uaddr, value 1

let v: verdict.[si4, si4] = verdict::Pass(42);
let r = v as ?;     // r: ui1, value 1 (payload 42 is discarded)
```

### 6.9.8 Reference conversions

#### Static semantics

`as` is extended to permit conversions between reference types that share the same referent type `T`. A reference cast changes the family (`$`, `&`, `%`), the modifiers (`volatile`, `mut`, `atomic`, `guard`), or both. The referent type `T` is unchanged. Changing `T` requires `as!` in an `airside` block.

The rules for reference casting — the permitted conversions, the distinction between landside and airside casts, and the prohibitions — are defined in the clause on references and resource management.

#### Examples (informative)

```
// $T → &T: landside
let shared = exclusive as &T;
// &T → %T: landside
let uman = shared as %T;
// %T → uaddr: landside
let addr = uman as uaddr;
// &mut T → &T: landside
let plain = mut_ref as &T;

// &atomic T → &guard T: landside
let guarded = atomic_ref as &guard T;
// uaddr → %T: landside
let uman2 = addr as %T;

// %T → &T: airside
let managed = airside { express uman2 as &T; };
// %T → $T: airside
let exclusive = airside { express uman2 as $T; };

// translation failures
// addr as &T;       — uaddr → &T
// shared as $T;     — &T → $T
// shared as &mut T; — &T → &mut T

// atomic_ref as &T; — &atomic T → &T
```

### 6.9.9 Subroutine pointer conversions

#### Static semantics

Conversion between `%void` and a subroutine pointer type, or between two subroutine pointer types with different signatures, is permitted via `as!`, which requires airside.

#### Examples (informative)

```
airside {
    let uman_ptr: %void = 0x4000_1000~uaddr as %void;
    let f: fn() -> void = uman_ptr as! fn() -> void;
    let g: fn(si4) -> si4 = f as! fn(si4) -> si4;
    let back: %void = g as! %void;
}
```

### 6.9.10 Other disallowed conversions

#### Constraints

The following conversions shall not appear when attempted with `as`:

— Any source type that is not `numeric`, a variant type, or a reference (structs, tuples, `void`, subroutine pointers).

— Any target type that is neither `numeric`, nor a reference, nor `?`.

— Reference conversions not permitted by the rules defined in the clause on references and resource management.

### 6.9.11 Bitwise reinterpretation

`as!` performs a reinterpretation of a value from one type to another.

#### Dynamic semantics

`as!` transfers the source value, as the clause on references and resource management defines transfer.

The source value’s destructor is not invoked, and the destruction obligation of the source type is extinguished. If the target type has `with destruct`, the reinterpreted value acquires the target type’s destruction obligation.

#### Constraints

A cast with `as!` requires airside.

A `Source'size`/`Target'size` mismatch shall not appear. `as!` on `dyn Protocol` shall not appear.

#### Examples (informative)

```
airside {
    // ISO/IEC 60559:2020 bits as integer
    let bits: ui4    = some_float as! ui4;
    // integer bits as ISO/IEC 60559:2020
    let back: fe8s23 = bits as! fe8s23;
}
```

## 6.10 `airside` blocks

An `airside` block is an expression whose block is an airside region, as the clause on semantics defines airside.

### Syntax

```
airside_block = "airside", ws, block ;
```

### Static semantics

An `airside` block is an expression. Its type and value follow the rules for express blocks defined in the clause on statements and control flow.

`airside` blocks may be nested.

### Implementation requirements

The implementation shall not use the presence of an `airside` block to justify transformations on code outside the block, as defined in the clause on semantics.

### Examples (informative)

```
let raw_val = airside {
    let ptr = 0x4000_1000~uaddr as %volatile mut ui4;
    express *ptr;
};

// airside fn — the entire body is implicitly airside
airside fn read_mmio(addr: uaddr) -> ui4 {
    let ptr = addr as %volatile ui4;
    return *ptr;
}
```

## 6.11 `xlat` blocks and the `xlat?` conditional

A `xlat` block is an expression that is evaluated at translation time. A `xlat?` conditional selects one of two branches according to its evaluation context.

### Syntax

```
xlat_block = "xlat", ws, block ;
xlat_lead       = block | "then", ws, expression ;
xlat_cond_block = "xlat", ws, '?', ws, xlat_lead, ws, "else", ws, block ;
xlat_cond_expr  = "xlat", ws, '?', ws, xlat_lead, ws,
                  "else", ws, plain_expression ;
```

### Static semantics

A `xlat` block is an expression. Its type and value follow the rules for express blocks defined in the clause on statements and control flow. The implementation shall evaluate the block during translation. The resulting value is a translation-time constant and may be used wherever a translation-time constant is required. What the block contributes to the opaque code is defined in the subclause on opaque code exclusion.

Any operation valid at execution time is valid within a `xlat` block, subject to the rule governing `trap` in a `xlat` block, defined in the clause on statements and control flow.

Every evaluation takes place in one of two **evaluation contexts**. It takes place in translation-time evaluation where it is the evaluation of an expression within a `xlat` block, of an operation on a symbol declared in a `#dyn xlat` namespace as defined in the clause on programme structure and translation, of a `T'bound(X)` operation, or of the initializer of a `const` or `static` binding. Every other evaluation takes place in execution-time evaluation.

Every evaluation observes one of two **evaluation environments**. It observes the translation environment where it is the evaluation of an expression within a `xlat` block or of an operation on a symbol declared in a `#dyn xlat` namespace, whatever else encloses it. Every other evaluation observes the execution environment.

The body of a subroutine is evaluated in the context and the environment of its invocation. A body its programme invokes from both environments shall satisfy the static semantics of this specification under each.

An expression is **evaluable at translation time** when every value it requires is itself determined at translation time. An expression whose evaluation reaches an execution-environment `asm` block is not evaluable at translation time.

An expression is a **translation-time constant** where this specification requires the implementation to determine its value during translation. Which forms it requires so is stated at each form.

Recursion within `xlat` blocks is permitted but bounded by an implementation-defined evaluation limit.

#### The `xlat?` conditional

A `xlat?` conditional selects its leading branch where its evaluation context is translation-time evaluation, and its `else` branch where its evaluation context is execution-time evaluation.

Both branches are subject to the full static semantics of this specification at every point where the conditional appears. The leading branch is checked under the evaluation environment the conditional observes, and the `else` branch under the execution environment. The branch that is not selected is **discarded**. A discarded branch is not evaluated, and nothing it contains reaches the opaque code.

The type of a `xlat?` conditional is the common type of its branches.

### Dynamic semantics

When a value evaluated at translation time and incorporated into the opaque code contains a reference, the implementation shall produce opaque code in which the referent occupies its storage region, as defined in the subclause on objects in the clause on semantics. That referent acquires the permanent object lifetime. This applies transitively to references contained within the referent.

### Constraints

An expression that is not evaluable at translation time shall not appear where the evaluation context is translation-time evaluation.

A `xlat` block shall not refer to a binding declared outside the enclosing `xlat` block unless the binding is introduced by a `const` declaration.

Unbounded recursion during translation-time evaluation shall not appear.

The branches of a `xlat?` conditional shall have a common type.

### Examples (informative)

```
const buffer_size: uaddr = xlat {
    express 4096 * page_count();
};

fn platform_init() {
    xlat? {
        init_at_translation();
    } else {
        init_at_execution();
    }
}

// Only one branch — the execution branch is empty
xlat? {
    calibrate();
} else {}

// Expression form
let width: uaddr = xlat? then translation_simd_width() else 16;

// asm inside xlat? — instruction emitted in the leading branch
const seed: ui4 = xlat {
    express xlat? then airside {
        let mut r: ui4;
        asm { rdtsc } with { out(eax) -> r; };
        express r;
    } else 0;
};

// Nesting other conditions inside the leading branch
xlat? {
    #flag_if(aarch64) aarch64_init(); #
} else {}
```

### Design rationale (informative)

A `xlat` block mandates evaluation during translation, so an expression within it whose inputs are not determined at translation time cannot appear.

### 6.11.1 Translation-environment evaluation

#### Static semantics

An evaluation that observes the translation environment takes place in an environment whose cell width is the greater of *B*<sub>e</sub> and *B*<sub>x</sub>, carried out by the translation environment. Such an evaluation takes `cellbits`, the address width, the reference width, the rounding mode governing a floating radix point number operation, and the unqualified layout intrinsics from that environment.

`cellbits` evaluates to the cell width of that environment, and the value sets of the `uiN` and `siN` types are determined by it. The value sets of `uaddr` and `saddr` are determined by the address width of the translation environment.

The qualified forms of the layout intrinsics, defined in the subclause on type intrinsic expressions, name an environment whatever evaluation they stand in.

An `asm` block in such an evaluation is a **translation-environment `asm` block**. An `asm` block in an evaluation that observes the execution environment is an **execution-environment `asm` block**. A translation-environment `asm` block targets the translation environment. The `cellbits` of the translation environment and the `cellbits` governing the enclosing evaluation may differ. The rules governing the boundary between a translation-environment `asm` block and the enclosing `xlat` Kurt code are defined in the subclause on inline `asm` in `xlat`.

### 6.11.2 Execution-environment evaluation

#### Static semantics

An evaluation that observes the execution environment takes `cellbits`, the address width, the reference width, the rounding mode governing a floating radix point number operation, and the unqualified layout intrinsics from the execution environment. The initializer expression of a `const` or `static` declaration is such an evaluation, and takes place at translation time.

#### Examples (informative)

```
// make_lut observes the translation environment
const crc_table: [ui4; 256] = xlat { express make_lut(); };

// The same subroutine observes the execution environment here
const exec_table: [ui4; 256] = make_lut();

// static with complex initializer
static greeting: &[ui1] = build_greeting("world");
```

### 6.11.3 Translation-environment access

#### Static semantics

External subroutines of the translation environment are declared in `#dyn xlat` namespaces, as defined in the clause on programme structure and translation.

#### Examples (informative)

```
const build_version: &[ui1] = xlat {
    #add std::"posix" as posix;
    use posix::env;
    express env::get("build_version");
};

const font_data: &[ui1] = xlat {
    #add std::"posix" as posix;
    use posix::fs;
    express fs::read_raw("font.ttf");
};
```

### 6.11.4 Reproducibility

#### Implementation requirements

Given the same implementation, the same execution environment, and the same translation environment, a programme’s `xlat` blocks are evaluated in the same relative order on every translation.

### 6.11.5 Opaque code exclusion

#### Implementation requirements

A `xlat` block, a `const` initializer, and a `static` initializer are each evaluated at translation time. Of each, only the resulting value is incorporated into the opaque code, as if it were a literal of the same type.

— No executable code originating from the body of such an expression shall be present in the opaque code.

— No data for which storage was reserved in evaluating it, other than the result value, shall be present.

— No symbol references to subroutines or bindings used only in evaluating it shall be present.

Where a subroutine is invoked both in evaluations that observe the translation environment and at execution time, the implementation shall keep its code present for the execution-time invocation sites. The former sites do not contribute to the opaque code.

#### `xlat` in `#dyn` interface sources

When a conforming implementation produces an interface source as a side effect of translation, `xlat` blocks shall be replaced by their evaluated result values. The interface source shall not contain a `xlat` block.

### 6.11.6 Cross-environment value validity

A value yielded by an evaluation that observes the translation environment crosses to the execution environment where it becomes the result of that evaluation within an enclosing evaluation that observes the execution environment, and where it is an argument of an invocation whose body observes the execution environment. The crossing is governed by the rules below, applied recursively to the structure of the value.

#### Static semantics

— Values of `void` and of any floating radix point number type cross unchanged.

— Values of integer types cross by value. A crossed value shall belong to the value set, as defined in the clause on types, of its type evaluated under the `cellbits` of the execution environment. For `uaddr` and `saddr`, the crossed value shall belong to the value set evaluated under the address width of the execution environment.

— Values of reference types cross together with their referents. Each referent crosses by the rules of this subclause and occupies storage in the execution environment as an object of permanent object lifetime. A reference to that object is established with family and modifiers equivalent to the original. Shared referents remain shared after crossing. A cyclic reference graph crosses by its closure, with every reference established again to refer to the crossed counterpart of its original referent. A reference that a qualified form of `T'bound` yields instead crosses unchanged. The `.tyd` and `.prd` fields of a protocol object wide reference cross as the corresponding descriptors of the execution environment, and its `.ptr` crosses together with the erased value it designates.

— Subroutine pointers cross by reference to the subroutine they identify. The subroutine shall be one whose definition lies outside every `xlat` block.

— A value of any other type crosses by composition. Each value it holds crosses by the rules of this subclause, as the clause on references and resource management defines the constituents of a type. The discriminant of a variant type crosses as a value of the discriminant type. It is reconstructed in the execution environment under the layout rules of its type, as defined in the clause on types. The implementation shall perform whatever rearrangement of cells the reconstruction requires.

A value crosses in the other direction where an invocation yields it to an evaluation that observes the translation environment. It crosses by the rules above, reading the environment entered for the execution environment. A reference so crossing designates the object it designated before, and the rules the clause on references and resource management gives that object govern it unchanged.

#### Constraints

A crossing that violates any rule of the static semantics above shall not appear. The diagnostic shall identify the offending leaf value, its type, and the parameter of the execution environment under which the value cannot be represented.

#### Design rationale (informative)

Crossed referents acquire the permanent object lifetime because the value is incorporated into the opaque code, and storage incorporated into the opaque code is reserved for the entire execution of the programme.

Where an evaluation observes the translation environment, the `cellbits` governing `uiN` and `siN` types is the greater of the two environments’ values, so the crossing from `xlat` to the execution environment narrows or preserves the width of an integer type derived from the cell width. The address width within `xlat` is that of the translation environment, so the crossing for `uaddr` and `saddr` can be narrowing or widening depending on the relative address widths.

## 6.12 Inline `asm`

An inline `asm` block embeds execution environment instructions within a subroutine body. Global `asm` is defined in the clause on declarations.

### Syntax

```
asm_block = "asm", ws, asm_body, [ ws, constraint_clause ] ;

constraint_clause = "with", ws, '{', ws,
                    { asm_constraint, ';', ws }, '}' ;

asm_body  = '{', { ? instruction text line ? }, '}'
          | { '#' }, '{', { ? instruction text line ? }, '}',
            { '#' } ;

asm_constraint = 'in',      ws, '(', ws, operand_target, ws, ')', ws,
                            '=', ws, expression
               | 'out',     ws, '(', ws, operand_target, ws, ')', ws,
                            '->', ws, identifier
               | 'io',      ws, '(', ws, operand_target, ws, ')', ws,
                            '=', ws, expression, ws, '->', ws,
                            identifier
               | 'clobber', ws, '(', ws, ? resource identifier ?, ws,
                            { ',', ws, ? resource identifier ?, ws },
                            ')' ;

operand_target = [ '\'', identifier | '\'?'
                 | '\'', digit, { digit }
                 | ? resource identifier ? ] ;
```

### Static semantics

An `asm` block is written in one of two forms. In the **curly bracket form**, the instruction text ends at the closing curly bracket that matches the opening one, and the curly brackets within the instruction text are counted for the match. In the **extended form**, the opening delimiter is one or more `#` characters followed by `{`, and the instruction text ends at the first `}` followed by the same number of `#` characters. No character of the instruction text bears upon where it ends.

Any character sequence beginning with `'` that follows a character other than a character permitted within an identifier is a Kurt operand; all other text is **instruction text**. The syntax of instruction text is implementation defined.

A Kurt operand has four forms:

— Named operand (`'name`) — references a named constraint declared in the constraint clause.

— Positional operand (`'0`, `'1`, …) — references a constraint by its index in the constraint clause, counting from zero.

— Sequential operand (`'?`) — takes the next unmatched positional constraint in declaration order.

— Inline expression (`'(expr)`) — the expression is evaluated at translation time and inserted as an immediate value.

Three operand-targeting modes are defined (`clobber` exempt):

— Named — `in('name) = expr` in the constraint clause; `'name` in the instruction text.

— Positional — constraints may declare an explicit index (`in('1) = expr`) to reorder, or omit the target (`in() = expr`) to take the next available index. The instruction text references by index (`'0`, `'1`) or by `'?`. `'?` and explicit indices may coexist. A single index may be referenced multiple times in the instruction text.

— Resource — `in(rax) = expr` in the constraint clause; bare resource identifier in the instruction text.

The constraint clause is optional. Without it, a `'` reference shall not appear.

The Kurt comment syntax defined in the clause on lexical structure applies to the delimiting tokens of an `asm` block. Apart from the operands above and from what ends the instruction text, the text within the block is opaque to the lexical rules of Kurt and is **delivered** verbatim to the environment the block targets: to the translation environment where translation-time evaluation reaches the block, and to the execution environment where the block is incorporated into the opaque code.

#### Constraint keywords

— `in(target) = expr` — places the value of `expr` in `target` before the `asm` block executes.

— `out(target) -> var` — captures the value of `target` into the `mut` binding `var` after the `asm` block executes.

— `io(target) = expr -> var` — initializes `target` from `expr` before execution; captures `target` into `var` after execution.

— `clobber(r1, r2, ...)` — declares that the listed resources may be modified. The implementation shall save and restore the values of the listed resources across the `asm` block. Resource identifiers are implementation defined.

### Dynamic semantics

Constraints are evaluated in constraint-clause order. Inputs bind before execution. Outputs capture after it. An inline `asm` block is a σ operation.

### Constraints

Inline `asm` requires airside.

The number of `#` characters in the opening and closing delimiters of the extended form shall be equal. In the curly bracket form, the curly brackets of the instruction text shall balance. Instruction text whose curly brackets do not balance shall be written in the extended form.

The instruction text of an `asm` block shall follow the syntax of instruction text of the environment to which it is delivered, and this specification constrains it in no other way.

A `'` token that does not match one of the four Kurt operand forms shall not appear.

The three operand-targeting modes shall not be mixed in a single constraint clause (`clobber` exempt).

Each `'name` shall match exactly one `with`-clause declaration. Each `'N` shall be a valid index, counting from zero. `'?` past the last unmatched positional shall not appear. Duplicate resource targets and overlap between operand targets and `clobber` entries shall not appear.

### Implementation defined

An execution environment resource is an execution-environment-specific binding target that the `asm` block addresses. (e.g. a named storage location.) Resource identifiers, resource classes, and the syntax of instruction text are implementation defined. A conforming implementation shall document these for each supported execution environment.

### Examples (informative)

```
// No constraints
airside { asm { msr daifclr, #2 }; }

// Resource mode
airside {
    let mut n: saddr;

    asm { svc #0 } with {
        in(x8) = 64; in(x0) = 1; in(x1) = buf;
        in(x2) = len; out(x0) -> n;
        clobber(x16, x17);
    }
}

// Named mode
airside {
    let mut r: ui4;

    asm {
        mrs 'c, sctlr_el1
        orr 'c, 'c, '(1 << 2)
        msr sctlr_el1, 'c
    } with { io('c) = v -> r; }
}

// Positional — anonymous, '? sequential
airside {
    asm {
        mov x0, '?
        mov x1, '?
    } with {
        in() = 1;
        in() = 2;
    }
}

// Positional — reordered via explicit index
airside {
    asm {
        mov x0, '? // 2
        mov x1, '? // 1
    } with {
        in('1) = 1;
        in('0) = 2;
    }
}

// Positional — same operand referenced twice
airside {
    asm {
        mov x0, '0 // both 1
        mov x1, '0
    } with {
        in() = 1;
    }
}

// -> !
fn halt() -> ! {
    loop { airside { asm { wfi } } }
}

// Instruction text is constrained only upon delivery — the
// discarded branch may hold instruction text of another environment
airside {
    let mut t: ui8;

    xlat? {
        asm { rdtsc } with { out(eax) -> t; }
    } else {
        asm { mrs '0, cntvct_el0 } with { out() -> t; }
    }
}

// A subroutine invoked only within xlat blocks is never incorporated
// into the opaque code. Its asm targets the translation environment,
// whatever the execution environment is.
fn include_bytes(path: &[ui1]) -> &[ui1] {
    airside { asm { /* translation-environment I/O */ } }
}
```

### 6.12.1 `asm` in `xlat`

#### Static semantics

An `asm` block in an evaluation that observes the translation environment targets that environment.

Where an evaluation observes the translation environment, `cellbits` takes the greater of *B*<sub>e</sub> and *B*<sub>x</sub>. Where *B*<sub>x</sub> differs from that value, a value that crosses the boundary of a translation-environment `asm` block is converted according to the type of the value.

Passing from the enclosing Kurt code — an `in` constraint or an argument — a value of an integer type derived from the cell width is narrowed by truncation.

Passing to the enclosing Kurt code — an `out` constraint or a returned value — a value of an integer type derived from the cell width is widened. A value of a type satisfying `primitive` is widened by zero-extension, and a value of a type satisfying `integer` but not `primitive` by sign-extension. Both conversion categories are defined in the subclause on type casting.

For an `io` constraint, the first of the two rules applies to the initial value and the second to the captured value.

Values of `uaddr`, `saddr`, and reference types cross unchanged.

Values of a floating radix point number type cross unchanged.

Values of `void` cross unchanged.

A value whose type has constituents is converted by recursive application of the above rules to each value it holds.

#### Implementation defined

The dialect of instruction text of the translation environment accepted in such an `asm` block is implementation defined. The implementation shall document the dialect for each supported translation environment.

## 6.13 Type intrinsic expressions

A type intrinsic expression queries a property of a type. The type operand appears on the leading side, and a type intrinsic from the set `'size`, `'align`, `'offset`, `'bound` appears on the following side.

### Syntax

```
type_intrinsic    = type, ws, type_intrinsic_op ;
type_intrinsic_op = '\'', ws,
                    ( 'size' | 'align'
                    | 'offset', ws, '(', ws, identifier, ws, ')'
                    | 'bound',  ws, '(', ws, bound_argument, ws, ')' ),
                    [ ws, '::', ws, ( 'exec' | "xlat" ) ] ;
bound_argument    = bound_elem | "type" ;
```

### 6.13.1 Layout intrinsics

#### Static semantics

`T'size` yields the size of the type `T` in cells. The result is a `uaddr` value.

`T'align` yields the alignment requirement of the type `T` in cells. The result is a `uaddr` value.

`T'offset(field)` yields the cell offset of the named field within the struct type `T`. The result is a `uaddr` value. The offset is computed according to the layout rules defined in the clause on types.

Each layout intrinsic permits the two qualified forms defined in the clause on types, written after the type intrinsic. `T'size::exec` yields the layout of `T` in the execution environment, and `T'size::xlat` yields its layout in the translation environment. `T'align` and `T'offset(field)` permit the same two forms. Each qualified form yields the same value wherever it is evaluated. The value of the unqualified form is that of the evaluation environment the evaluation observes, as defined in the subclause on `xlat` blocks and the `xlat?` conditional.

#### Constraints

`T'offset(field)` on a type that is not a struct, or when `field` does not name a declared field of `T`, shall not appear.

#### Examples (informative)

```
const sz: uaddr  = my_struct'size;
const al: uaddr  = my_struct'align;
const off: uaddr = my_struct'offset(field_name);
```

### 6.13.2 Bound descriptor emission

#### Static semantics

`T'bound(X)` queries whether the concrete type `T` satisfies the bound `X` and emits a descriptor for `T`. The result type is `verdict.[%void, void]`. When `T` satisfies `X`, the result is `verdict::Pass(ptr)` where `ptr` is an unmanaged reference to that descriptor. When `T` does not satisfy `X`, the result is `verdict::Fail(void)`.

A descriptor belongs to an environment. Its contents are the layout of `T` and the addresses of its subroutines in that environment. The unqualified form yields the descriptor of the environment the evaluation observes. `T'bound(X)::exec` yields the descriptor of the execution environment and `T'bound(X)::xlat` that of the translation environment. Each qualified form yields the same reference wherever it is evaluated.

When the result is `verdict::Pass(ref)`, the reference permits no store and refers to an object of permanent object lifetime. Within one translation unit, multiple evaluations of `T'bound(X)` for the same `(T, X)` pair where `T` satisfies `X` yield the same reference value.

A bound that constrains which types a type parameter can be resolved to, without licensing any operation the erased body performs upon a value of `T`, carries no fields. The descriptor the expression returns depends on the kind of bound:

<table>
<thead><tr><th>Bound kind</th><th>Returned descriptor</th></tr></thead>
<tbody>
<tr><td><code>type</code></td><td>A type descriptor (size, alignment, destructor) as defined in the subclause on descriptors</td></tr>
<tr><td>Declared protocol</td><td>A protocol descriptor with the three-zone layout defined in the subclause on descriptors</td></tr>
<tr><td><code>numeric</code>, <code>integer</code>, or <code>primitive</code></td><td>An arithmetic descriptor defined in the subclause on descriptors</td></tr>
<tr><td>Any other bound</td><td>A reference to an object of size zero</td></tr>
</tbody>
</table>

`T'bound(type)` yields `verdict::Pass` for every type. The payload is a reference to the type descriptor for `T`.

#### `T'bound` and protocol objects

The `.tyd` and `.prd` fields of a protocol object wide reference, in every family and modifier form, are the `verdict::Pass` payloads of `T'bound(type)` and `T'bound(Protocol)` for the erased concrete type `T`.

#### Examples (informative)

```
// Declared protocol — returns protocol descriptor
const si4_ord: %void = contract si4'bound(ord) else trap();

// Built-in bound
const si4_num: verdict.[%void, void] = si4'bound(numeric);
```

#### Design rationale (informative)

Returning `verdict.[%void, void]` lets bound satisfaction be tested as an ordinary contract value: a programme asserts satisfaction by trapping on the `verdict::Fail` path, and the `verdict::Pass` payload is the descriptor reference that `&dyn Protocol` formation consumes. Since the operation is evaluated during translation, the implementation resolves the verdict there.

### Static semantics

**Leading-to-following associativity** means `a op b op c` is parsed as `(a op b) op c`. **Following-to-leading associativity** means `a op b op c` is parsed as `a op (b op c)`. A form whose associativity the table gives as `—` **does not associate**, and an expression in which such a form supplies an operand of the same form shall not appear. (e.g. `a < b < c` shall not appear.)

— Unary operators are prefix-form and bind more tightly than any binary operator, and less tightly than the postfix operators of precedences 2 to 4. (e.g. `*&x` is parsed as `*(&x)`. `-a + b` is parsed as `(-a) + b`.)

— Type intrinsics bind less tightly than dereference and reference creation and more tightly than negation and not. (e.g. `&T'size` is parsed as `(&T)'size`, the size of a reference to `T`. `!T'size` is parsed as `!(T'size)`.)

— A cast expression binds more tightly than any arithmetic or bitwise operator, and casts are processed in leading-to-following order. (e.g. `x as ui4 + y` is parsed as `(x as ui4) + y`. `a as! B as C` is parsed as `(a as! B) as C`.)

— `and`, `or`, and `xor` are defined in the clause on statements and control flow, which gives the order in which their operands are evaluated.

— The table assigns precedence to compare-and-swap (`>.<`), to the value forms taking `else`, and to contract extraction as whole forms. The semantics of `>.<` are defined in the clause on references and resource management.
