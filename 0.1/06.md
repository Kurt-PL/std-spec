# 6. Expressions

This clause defines the expressions of the Kurt programming language: their kinds and operators, assignment, casts and reinterpretations, the `airside` and `const` blocks, the `xlat?` and `arbit?` conditionals, translation-time evaluation, inline `instruct` blocks, the type intrinsics, and operator precedence.

## 6.1 Expression kinds

Every expression other than a jump has a type. Every expression is either an **object expression**, which designates an object, or a **value expression**, which designates a computed value. An expression that this specification does not make an object expression is a value expression. Where an operation uses the value of an expression, the expression yields the current value of the object that it designates or that holds its value.

An object expression is **storable** at a programme point where a store through it is permitted.

Expressions evaluated in an order are each evaluated before the next begins.

### Syntax

```
expression   = primary_expr | postfix_expr | unary_expr | binary_expr
             | cast_expr | special_expr | control_expr ;

primary_expr = identifier_expr | literal | paren_expr
             | composite_construction | wild_construction
             | array_construction | repeat_construction
             | anon_struct_construction
             | uninit_expression | cellbits_expr ;

postfix_expr = invocation_expr | instance_expr | field_expr
             | method_invocation | propagation_expr ;

unary_expr   = negation_expr | identity_expr | not_expr | deref_expr
             | ref_shared_expr | ref_exclusive_expr
             | ref_unmanaged_expr ;

binary_expr  = arith_expr | bitwise_expr | comparison_expr
             | logical_expr | assignment_expr | compound_assign
             | cas_expr ;

special_expr = airside_block | const_block
             | eval_cond_block | eval_cond_expr | instruct_block
             | type_intrinsic | volatile_fence | guard_fence ;

control_expr = block | labelled_block
             | if_block | if_expr | if_let_block | if_let_expr
             | match_expression | while_block | while_expr
             | loop_expression | extraction_block | extraction_expr
             | return_expression | break_expression
             | continue_expression
             | express_expression ;
```

`literal` and `cellbits_expr` are defined in the clause on lexical structure and in the clause on types. `logical_expr` and each form the `control_expr` production lists are defined in the clause on statements and control flow. `cas_expr`, `volatile_fence`, and `guard_fence` are defined in the clause on references and resource management. Every other form that a production of this subclause lists is defined in this clause.

## 6.2 Primary expressions

### 6.2.1 Identifier expression

#### Syntax

```
identifier_expr   = single_path | "self" | "trap" ;
path_prefix       = { ( path_segment | qualified_segment ), ws, '::',
                      ws } ;
single_path       = path_prefix, path_segment ;
path_segment      = identifier, [ ws, generic_args ]
                  | "super" | "srcroot"
                  | "selftype", [ ws, generic_args ] ;
qualified_segment = '(', ws, type, ws, "impl", ws, single_path, ws,
                    ')' ;
```

The `generic_args` production is defined in the subclause on generic declarations.

#### Static semantics

An **identifier expression** resolves a name to its binding or to the named item it denotes. `self` and an `identifier` that is the first segment of a path are resolved as the clause on declarations defines, and a path as the clause on programme structure and translation defines. What `trap` names is defined in the subclause on `trap`.

A **path expression** is an identifier expression whose `single_path` contains `::`. What the path denotes is defined in the clause on programme structure and translation.

An identifier expression is an object expression when it names a binding.

#### Dynamic semantics

An identifier expression that names a binding designates its object. Evaluating one that names a `const` declaration yields the value of the initializer block of that declaration. Evaluating one that names an implanted constant yields the value of its expression, as defined in the clause on protocols and implantations. Evaluating one that names a dependence parameter yields the value of the dependence argument. Evaluating one that names a subroutine yields that subroutine.

#### Constraints

The final segment of a path in expression position shall not reach a namespace other than a type.

In a qualified segment, the `single_path` shall denote a protocol.

#### Examples (informative)

```
let x: si4 = 42;

// identifier expression: resolves to the binding x
x;

// path expression: resolves to the implanted constant max through si4
si4::max;
// path expression: resolves to the subroutine write in module io
io::write;

// Qualified segment: disambiguates protocol items

// implanted constant of the implantation of bounded for ui1
(ui1 impl bounded)::min;
// implanted subroutine of the implantation of defaulted for si4
(si4 impl defaulted)::default();
```

### 6.2.2 Parenthesized expression

#### Syntax

```
paren_expr = '(', ws, expression, ws, ')' ;
```

#### Static semantics

A parenthesized expression binds as a single operand within the expression that encloses it, whatever the default precedence and associativity would give. The type of a parenthesized expression is that of the enclosed expression, and it is an object expression where the enclosed expression is one.

#### Examples (informative)

```
let x = (a + b) * c; // forces addition before multiplication
let y = -(a + b);    // negation applies to the sum
```

### 6.2.3 Composite construction

#### Syntax

```
composite_construction = single_path,
                         [ ws, '.', ws, '{', ws,
                           [ expression_list | field_init_list ], ws,
                           '}' ] ;

expression_list        = expression, ws, { ',', ws, expression, ws },
                         [ ',', ws ] ;
field_init_list        = field_init, ws, { ',', ws, field_init, ws },
                         [ ',', ws ] ;
field_init             = '.', ws, identifier, ws, '=', ws, expression ;
```

#### Static semantics

A **composite construction** constructs a value of the type its path denotes, or, where its path denotes a variant, of the type whose variant it denotes. One whose curly brackets enclose nothing takes the form of the type or variant its path denotes. The forms of a composite construction are:

&mdash; **Unit construction** &mdash; the path alone. Where the type or variant its path denotes is not in unit form, it is equivalent to the path followed by `.{}`.

&mdash; **Unnamed-field construction** &mdash; the path followed by `.` and an expression list enclosed by curly brackets. The position of each expression designates a field, counting in declaration order.

&mdash; **Named-field construction** &mdash; the path followed by `.` and a field initializer list enclosed by curly brackets. Each initializer designates its target field by name.

A path that denotes a type or a variant, written as an expression, is a composite construction.

#### Dynamic semantics

The expressions of a composite construction are evaluated in source order, and then the default-value expressions of the fields it omits, in declaration order. Each expression of a composite construction initializes the field that its position or its field initializer designates.

#### Constraints

Every field that carries no default-value expression, other than a `?` field, shall be initialized exactly once in the construction. A field that carries one shall be initialized at most once. In an unnamed-field construction, the expressions shall fill a leading run of the fields.

#### Examples (informative)

```
// Unit construction
let v = empty_t;

// Named-field construction
let p = point.{ .x = 1, .y = 2 };

// Unnamed-field construction
struct pair { si4, si4 }
let q = pair.{ 1, 2 };

// Enum variant constructions
enum shape {
    circle { fe11s52 },
    rect { fe11s52, fe11s52 }
}

let s1 = shape::circle.{ 1.5 };
let s2 = shape::rect.{ 3.0, 4.0 };

// Defaults omitted
struct origin_point { x: si4 = 0, y: si4 = 0 }
let o = origin_point.{};

// Source-order evaluation: compute_y is invoked before compute_x
let r = point.{ .y = compute_y(), .x = compute_x() };
```

### 6.2.4 Wild construction

A wild construction yields a value that no declared variant of the variant type its path denotes covers.

#### Syntax

```
wild_construction = single_path, ws, '::', ws, "wild" ;
```

#### Constraints

A wild construction that yields no value shall not appear.

#### Implementation defined

The value a wild construction yields is implementation defined.

#### Examples (informative)

```
enum empty {}
let w1 = empty::wild;

enum colour { red, green, blue }
let w2 = colour::wild;
```

### 6.2.5 Array construction and repeat construction

#### Syntax

```
array_construction  = '[', ws,
                      [ expression, ws, { ',', ws, expression, ws },
                        [ ',', ws ] ], ']' ;
repeat_construction = '[', ws, expression, ws, ';', ws, expression,
                      ws, ']' ;
```

#### Static semantics

An **array construction** `[e1, e2, ..., eN]` is an expression of type `[T; N]`, where `T` is the common type of all element expressions and `N` is the number of elements. Where the construction has no element expression, `T` is determined by checking alone, as the clause on types defines checking.

A **repeat construction** `[expr; N]` is an expression of type `[T; N]`, where `T` is the type of `expr`.

#### Dynamic semantics

In an array construction, element expressions are evaluated in source order.

In a repeat construction, `N` is evaluated before the initializer expression begins, and the initializer expression is evaluated once. The value of the initializer expression is stored into all `N` elements by copy.

#### Constraints

All elements of an array construction shall have a common type.

A repeat construction shall appear only where `T` is copyable.

#### Examples (informative)

```
let arr = [10, 20, 30];             // [saddr; 3]
let zeros: [ui1; 4096] = [0; 4096]; // repeat construction
```

### 6.2.6 Anonymous struct construction

#### Syntax

```
anon_struct_construction = '.', ws, '{', ws, expression, ws,
                           { ',', ws, expression, ws }, [ ',', ws ],
                           '}' ;
```

#### Static semantics

An anonymous struct construction `.{ e1, e2, ..., eN }` is an expression of type `.{T1, T2, ..., TN}`, where each `Ti` is the type of the corresponding element expression.

#### Dynamic semantics

Element expressions are evaluated in source order.

#### Examples (informative)

```
// pair: .{saddr, verdict[void, void]}
let pair = .{ 42, verdict[void, void]::Pass.{ void } };
// triple: .{saddr, fe8s23, verdict[void, void]}
let triple = .{ 1, 2.0, verdict[void, void]::Fail.{ void } };
```

### 6.2.7 Uninitialized value introduction

#### Syntax

```
uninit_expression = "uninit" ;
```

#### Static semantics

`uninit` yields an **uninitialized value**.

Its type is determined by checking alone, as the clause on types defines.

#### Dynamic semantics

An uninitialized value is in one of two states.

&mdash; **Contained** &mdash; a value `uninit` yields is contained.

&mdash; **Escaped** &mdash; a contained value becomes escaped where a reference that permits stores to an object holding it is passed as an argument to a subroutine imported via `#dyn` or appears as an operand of an `instruct` block.

Where the implementation defines no value for an `uninit` expression, a store performs no write at the cells at which it would place the value of that expression. This applies where that expression is the one whose value the store stores, or is reached from that one by a succession of the following steps:

&mdash; To the enclosed expression of a parenthesized expression.

&mdash; To an element expression of an anonymous struct construction or an array construction.

&mdash; To the initializer expression of a repeat construction.

&mdash; To an expression that initializes a field of a composite construction.

Where the implementation defines none and the value of such an expression is not so stored, the expression yields the value that a load yields from storage reserved for it, at which no write has been performed since its reservation.

Where a reference that does not permit stores to an object holding an uninitialized value is passed or appears in the way that makes a contained value escaped, a load from that object occurs at that programme point.

An object ceases to hold an uninitialized value when a value other than `uninit` is stored into it.

#### Constraints

An `uninit` expression requires airside.

#### Implementation requirements

The implementation shall issue an advisory diagnostic at the first operation upon a contained uninitialized value, and at the first managed-reference creation on an object holding one. It should do the same where the value is escaped, and may do so at any subsequent such operation or creation in either state.

#### Implementation defined

The value an `uninit` expression yields is implementation defined, and the implementation may define none.

#### Examples (informative)

```
// FFI out-parameter via unmanaged reference
let y = airside {
    let mut x: large_t = uninit; // contained
    // store-permitting reference to #dyn: contained → escaped
    foreign_init(%mut x);
    // first load in escaped: the implementation should issue an
    // advisory diagnostic
    express x;
};

// Local store exits the state
airside {
    let mut w: si4 = uninit; // contained
    // load-only reference to #dyn, load in contained: the
    // implementation shall issue an advisory diagnostic
    foreign_peek(%w);
    w = 0; // contained exited: no diagnostic
    express w;
}

// uninit in non-initializer assignment
airside {
    let mut x = 0; // normal
    x = uninit;    // contained
    // first load in contained: the implementation shall issue an
    // advisory diagnostic
    express x;
}

// argument position: the parameter type checks it
let random_seed = airside { express randgen(uninit); };

// translation failure: no annotation, and uninit supplies no type
// airside {
//     let mut z = uninit;
// }
```

## 6.3 Postfix expressions

### 6.3.1 Subroutine invocation

#### Syntax

```
invocation_expr = expression, ws, '(', ws, [ argument_list ], ws, ')' ;
argument_list   = expression, ws, { ',', ws, expression, ws },
                  [ ',', ws ] ;
instance_expr   = expression, ws, generic_args ;
```

#### Static semantics

A subroutine invocation expression invokes the subroutine designated by the leading expression. A subroutine invocation is performed through the invocation interface of the type of its leading expression, or, in a method invocation, of the method the invocation resolves to.

In a method invocation, the first argument is the receiver, or, where the subclause on automatic referencing adjusts the receiver, the reference that the adjustment creates. The expressions of the argument list follow it.

The type of a subroutine invocation expression is the return type of the invoked subroutine. Where the leading expression has a subroutine pointer type whose return is `!`, or the invocation is a method invocation of a method that returns `!`, synthesis of the type of the invocation is undetermined, and its default type is `void`.

#### Dynamic semantics

An invocation evaluates the leading expression and then the arguments, in source order.

The arguments correspond in order to the fixed parameters of the type of the leading expression, or, in a method invocation, to those of the declaration of the method the invocation resolves to. Each fixed parameter of the invoked subroutine has an object of the type its declaration gives it. Where the invoked subroutine has a binding for a parameter, the object of that parameter is the object of that binding. The invocation stores the value of each argument that corresponds to a parameter, through the type of that parameter, into the object of the invoked subroutine’s fixed parameter at the position of that parameter.

Where the invoked subroutine uses the variadic variant of its invocation interface, the values of the arguments beyond the fixed parameters are passed through that variant.

When the subroutine returns, the return value is the value of the invocation expression.

#### Constraints

The leading expression of a subroutine invocation that is not a method invocation shall have a subroutine pointer type.

A subroutine invocation analysed on a machine shall be performed through an invocation interface that the implementation documents for that machine.

The number of arguments shall be at least the number of fixed parameters of the type of the leading expression, or, in a method invocation, of the declaration of the method the invocation resolves to. Where that type carries no `variadic` keyword, or, in a method invocation, the declaration of the method does not use the variadic variant of its invocation interface, the number of arguments shall equal that number.

An invocation expression that invokes, through a subroutine pointer, a subroutine that uses the variadic variant of its invocation interface shall use a subroutine pointer type that carries the `variadic` keyword, as defined in the clause on types.

#### Examples (informative)

```
// direct subroutine invocation
let sum = add(2, 3);
// generic subroutine invocation with explicit type argument
let val = get_default[si4]();

// subroutine pointer invocation
use ext::get_info;
let callback: fn(si2) -> result = get_info;
let r = callback(42);

// Source-order evaluation: a() is invoked first, then b(), then c()
foo(a(), b(), c());
```

### 6.3.2 Field expression

#### Syntax

```
field_expr = expression, ws, '.', ws, identifier
           | expression, ws, '.', ws, integer_literal ;
```

#### Static semantics

In a field expression and in a method invocation, the expression before the `.` token is the **receiver**. A field expression `e.f` is an object expression where the type of the object that `e` designates after reference transparency, or of the object that holds the value of `e`, places within that object an object as the field that `f` names. The field expression then designates the object so placed. An identifier `f` names the field of that name, and an integer literal `f` the field at that position, counting from zero in declaration order. The result type is the type of the field.

A multi-assignment binding permits a store to its field, and a reference permits one where the store permission defined in the clause on references and resource management grants it. Where the receiver permits no store, the field is storable where the field mutability defined in the clause on declarations permits it.

#### Constraints

In a field expression, `f` shall name a field of the type of its receiver after reference transparency. Where `f` is an integer literal, the type of the receiver after reference transparency shall be a type in unnamed-field form, and `f` shall be in the range `[0, N)`, where `N` is the number of its fields. A field expression whose receiver has, after reference transparency, a variant type shall not appear.

#### Examples (informative)

```
let p = point.{ .x = 1, .y = 2 };
p.x;     // field expression on a value: yields si4

let pair = .{ 42, verdict[void, void]::Pass.{ void } };
pair.0;  // positional field expression: yields saddr
pair.1;  // positional field expression: yields verdict

let arr = [10, 20, 30];
arr.len; // built-in field: yields 3~uaddr (projection)
arr.ptr; // built-in field: yields %saddr (projection)
```

### 6.3.3 Method invocation

#### Syntax

```
method_invocation           = expression, ws, '.', ws, identifier,
                              [ ws, generic_args ], ws,
                              '(', ws, [ argument_list ], ws, ')'
                            | qualified_method_invocation ;
qualified_method_invocation = '(', ws, expression, ws, "impl", ws,
                              single_path, ws, ')', ws, '.', ws,
                              identifier, [ ws, generic_args ], ws,
                              '(', ws, [ argument_list ], ws, ')' ;
```

#### Static semantics

A method invocation expression `e.m(args)` invokes the method named `m` on the receiver `e` after reference transparency. The resolution of `m` is defined in the subclause on name resolution in the clause on protocols and implantations.

Where the `identifier` after a `.` belongs, in different derivations of a source unit, to a method invocation and to a field expression, it belongs to the method invocation.

A **qualified method invocation** `(e impl Protocol).m(args)` invokes the method named `m` of `Protocol` on the receiver `e` after reference transparency.

The type of a method invocation expression is the return type of the resolved method. Where the resolved method is declared `-> !`, synthesis of the type of the invocation is undetermined, and its default type is `void`.

#### Dynamic semantics

The dynamic semantics of the invocation are those the subclause on subroutine invocation defines.

#### Constraints

In a qualified method invocation, `Protocol` shall declare a method named `m`.

#### Examples (informative)

```
struct counter { pub val: uaddr }

impl counter {
    pub fn get(&self) -> uaddr { return self.val; }
    pub fn increment($self) { self.val += 1; }
}

let c_ref: &counter = &some_counter;
c_ref.get(); // OK: method invocation on &counter

// Qualified method invocation
// disambiguates inherent/protocol or protocol/protocol collision
(value impl fmt).fmt(&buf);
// invokes fmt of the implantation of fmt
```

### 6.3.4 Contract propagation

#### Syntax

```
propagation_expr = expression, ws, '?' ;
```

#### Static semantics

The type of the `?` expression is the success payload type of the operand.

#### Dynamic semantics

1. The operand `e` is evaluated.
2. The value is matched, as the subclause on patterns and destructuring defines.
3. If the value is a success variant, its success payload is the value of the `?` expression.
4. If the value is a failure variant, the enclosing subroutine returns a failure-variant value that holds the failure payload of that value.

#### Constraints

The operand `e` shall have a contract type.

The enclosing subroutine’s return type shall be a contract type, and the failure payload type of the operand shall exactly match the failure payload type of the enclosing subroutine’s return type.

#### Examples (informative)

```
fn read_config(path: &[ui1]) -> verdict[config, io_error] {
    let file = open(path)?;     // propagates io_error on failure
    let data = read_all(file)?; // propagates io_error on failure
    return parse(data);
}
```

### 6.3.5 Reference transparency

#### Static semantics

A construct that applies **reference transparency** to a value of a reference type takes the referent in place of that value, and the referent type in place of that reference type. It performs each access to the referent, or to an inner object of it, through that reference, and an access it so performs through an unmanaged reference requires airside. Reference transparency applies once to a construct.

A field expression or a method invocation whose receiver has a reference type applies reference transparency to the value of the receiver, other than to access, by name, a field that the representation of that reference type holds. The field or the method is then looked up in the referent type.

#### Examples (informative)

```
struct point { pub x: si4, pub y: si4 }
let p = point.{ .x = 1, .y = 2 };
let r: &point = &p;
r.x;     // OK: equivalent to (*r).x, yields 1

let rr: &&point = &r;
// rr.x; // translation failure: &point has no field named x
```

### 6.3.6 Automatic referencing

#### Static semantics

In a method invocation where the method the invocation resolves to does not take `self` by value, the receiver is adjusted by one creation of a reference to the receiver. The tribe and modifiers of that reference are those of the type of the self parameter. The creation is a re-reference where reference transparency applies, and the constraints upon reference creation apply to it.

#### Constraints

The type of the reference that the adjustment creates shall be assignable to the type of the self parameter.

#### Examples (informative)

```
let mut m: counter = counter.{ .val = 0 };
m.increment(); // auto-ref: value → $counter to satisfy $self
m.get();       // auto-ref: value → &counter to satisfy &self

let r: &counter = &m;
r.get();       // OK: re-reference &*r satisfies &self
// translation failure: &counter cannot satisfy $self:
// r.increment();
```

## 6.4 Unary expressions

### 6.4.1 Negation and identity

#### Syntax

```
negation_expr = '-', ws, expression ;
identity_expr = '+', ws, expression ;
```

#### Static semantics

Unary negation (`-expr`) and unary identity (`+expr`) require the operand to satisfy `numeric`. The result type is the operand’s type `T`.

Unary identity yields the value of its operand.

Unary negation yields the following.

&mdash; Integer types &mdash; the result is (&minus;*x*) mod 2<sup>*W*<sub>t</sub></sup>, mapped to the value set of `T`, where *x* is the value of the operand.

&mdash; Floating radix point number types &mdash; unary negation flips the sign bit. All other bits are preserved.

#### Examples (informative)

These examples apply where `cellbits::prog == 8`.

```
let a: si4 = -42;      // signed negation
let b: ui4 = -1~ui4;   // two’s complement: 0xFFFFFFFF
let c: fe11s52 = -0.0; // negative zero
```

### 6.4.2 Not

#### Syntax

```
not_expr = '!', ws, expression ;
```

#### Static semantics

The `!` operator has two meanings, determined by the type of the operand:

&mdash; Bitwise NOT &mdash; when the operand satisfies `integer`, `!x` yields (&minus;*x* &minus; 1) mod 2<sup>*W*<sub>t</sub></sup>, mapped to the value set of the operand’s type. The result type is the type of the operand.

&mdash; Contract polarity inversion &mdash; defined in the clause on statements and control flow.

#### Constraints

The operand of `!` shall satisfy `integer` or be of a contract type that declares `inv`.

#### Examples (informative)

These examples apply where `cellbits::prog == 8`.

```
let a: ui4 = 0xFF00_FF00~ui4;
let b = !a; // 0x00FF_00FF~ui4: bitwise NOT

let v: verdict[si4, si4] = verdict::Pass.{ 42 };
let w = !v; // verdict::Fail.{ 42 }: polarity inversion
```

### 6.4.3 Dereference

#### Syntax

```
deref_expr = '*', ws, expression ;
```

#### Static semantics

A dereference expression is an object expression. It designates the referent of its operand, and its type is the referent type. An access through it to the object it designates, or to an inner object of that object, is performed through the reference its operand yields. An object expression reaches its object through a reference where an access through it to the object it designates is performed through that reference, and that reference is the reference nearest the object.

#### Constraints

A dereference of an unmanaged reference requires airside, other than one that is the operand of a re-reference.

#### Examples (informative)

```
let x: si4 = 42;
let r: &si4 = &x;
let val = *r; // dereference: yields 42

let mut y: si4 = 0;
let e: $si4 = $y;
*e = 99; // store through exclusive reference

airside {
    let p = 0x4000_1000 as %volatile mut ui4;
    *p = 0xDEAD_BEEF; // volatile store through unmanaged reference
    let v = *p;       // volatile load through unmanaged reference
}
```

### 6.4.4 Reference creation

#### Syntax

```
ref_shared_expr    = '&', ws, [ modifier_list, ws ], expression ;
ref_exclusive_expr = '$', ws, [ modifier_list, ws ], expression ;
ref_unmanaged_expr = '%', ws, [ modifier_list, ws ], expression ;

modifier_list      = modifier, { ws, modifier } ;
modifier           = "volatile" | "mut" | "atomic" | "guard" ;
```

#### Static semantics

`&expr` creates a shared reference to the operand.

`$expr` creates an exclusive reference to the operand.

`%expr` creates an unmanaged reference to the operand.

Where the operand is a value expression, the reference designates the temporary object holding its value.

The resulting reference type includes the specified modifiers. Where the operand reaches its object through a reference and is not the dereference of one, and the reference nearest the object carries `volatile`, the resulting reference type includes `volatile` as well.

The placement of modifiers, the set of valid tribe&ndash;modifier combinations, and their semantics are defined in the clause on references and resource management.

#### Constraints

Where the operand of `&expr`, of `$expr`, or of `%expr` is the dereference of a reference, the subclause on reference casting defines what the expression creates. Where the operand is not the dereference of a reference:

&mdash; `&expr` and `$expr` require airside where the operand reaches its object through an unmanaged reference.

&mdash; Where the reference that `&expr` or `$expr` creates permits stores, the operand shall be a storable object expression.

&mdash; Where the reference that `%expr` creates permits stores, the operand shall be a storable object expression or a value expression.

Where the reference nearest the object that the operand designates carries `atomic` or `guard`, the operand shall be the dereference of that reference.

#### Examples (informative)

```
let x: si4 = 42;

// shared reference
let r: &si4 = &x;
// shared volatile reference
let v: &volatile si4 = &volatile x;
// shared atomic reference
let at: &atomic si4 = &atomic x;

let mut y: si4 = 0;

// exclusive reference
let e: $si4 = $y;
// exclusive volatile reference
let ev: $volatile si4 = $volatile *e;

// Unmanaged reference
let p: %si4 = %x;
airside { let val = *p; }

// Shared references can coexist
let a: &si4 = &x;
let b: &si4 = &x; // OK: multiple shared references
```

## 6.5 Arithmetic operators

### Syntax

```
arith_expr = expression, ws, arith_op, ws, expression ;
arith_op   = '+' | '+|' | '+@'
           | '-' | '-|'
           | '*' | '*|' | '*@'
           | '/' | '/|'
           | '%' ;
```

### Static semantics

For operands of a type `T` satisfying `numeric`, the operators `+`, `-`, `*`, `/`, and `%`, and the saturating operators, yield results of type `T`. The subclause on unmanaged reference arithmetic defines the results of `+` and `-` for a leading operand of unmanaged reference type.

### Constraints

The operands of an arithmetic operator shall be of one type, which satisfies the `numeric` bound, or, for `+` and `-`, shall be a leading operand of unmanaged reference type and a following operand of type `uaddr`. Saturating and widening operators require the `integer` bound.

### 6.5.1 Wrapping integer arithmetic

#### Static semantics

For operands of an integer type `T`, the operators `+`, `-`, `*`, `/`, and `%` yield results as follows.

&mdash; Addition &mdash; `a + b` yields (*a* + *b*) mod 2<sup>*W*<sub>t</sub></sup>, mapped to the value set of `T`.

&mdash; Subtraction &mdash; `a - b` yields (*a* &minus; *b*) mod 2<sup>*W*<sub>t</sub></sup>, mapped to the value set of `T`.

&mdash; Multiplication &mdash; `a * b` yields (*a* × *b*) mod 2<sup>*W*<sub>t</sub></sup>, mapped to the value set of `T`.

&mdash; Division &mdash; `a / b` yields the integer quotient of `a` divided by `b`, truncated towards zero. When the mathematical quotient does not belong to the value set of `T`, `a / b` yields `a`.

&mdash; Remainder &mdash; `a % b` yields (*a* &minus; *q* × *b*) mod 2<sup>*W*<sub>t</sub></sup>, mapped to the value set of `T`, where *q* is the quotient `a / b` yields.

&mdash; Division by zero &mdash; `a / 0` yields `0`.

### 6.5.2 Saturating integer arithmetic

#### Static semantics

For operands of a type `T` satisfying `integer`, let *MIN* and *MAX* denote the minimum and maximum values of the value set of `T`. The saturating operators `+|`, `-|` and `*|` yield *MAX* where the mathematical result exceeds *MAX*, *MIN* where it is less than *MIN*, and the mathematical result otherwise.

`a /| b` yields the truncated-towards-zero quotient when the result belongs to the value set of `T`. When it does not, the result is *MAX*. Where `b` is zero, `a /| 0` yields `0`.

### 6.5.3 Widening integer arithmetic

#### Static semantics

For operands of a type `T` satisfying `integer`, the widening operators yield the full mathematical result as a pair of `T` values. The result type is the anonymous struct type `.{T, T}`.

`a +@ b` and `a *@ b` yield `.{low, high}` for the mathematical sum and the mathematical result of the multiplication respectively. Each is represented as an unsigned 2*W*<sub>t</sub>-bit value for unsigned `T` and a two’s complement 2*W*<sub>t</sub>-bit value for signed `T`. `low` contains the *W*<sub>t</sub> bits of lesser weight and `high` those of greater weight, each mapped to the value set of `T`.

#### Examples (informative)

These examples apply where `cellbits::prog == 8`.

```
let a: ui4 = 0xFFFF_FFFF~ui4;
let b: ui4 = 2~ui4;
let .{ low, high } = a +@ b;
// Mathematical sum: 0x1_0000_0001 (33 bits)
// low:  0x0000_0001~ui4
// high: 0x0000_0001~ui4 (carry)

let c: ui4 = 0x1_0000~ui4;
let d: ui4 = 0x1_0000~ui4;
let .{ lo, hi } = c *@ d;
// Mathematical result of the multiplication: 0x1_0000_0000 (4294967296)
// lo: 0x0000_0000~ui4
// hi: 0x0000_0001~ui4
```

### 6.5.4 Floating radix point number arithmetic

#### Static semantics

`a % b` yields the ISO/IEC 60559:2020 remainder: the value *a* &minus; *n* × *b*, where *n* is the integer nearest to the exact quotient of *a* divided by *b* (ties to even). `a % 0.0` yields NaN.

## 6.6 Bitwise and shift operators

### Syntax

```
bitwise_expr = expression, ws, bitwise_op, ws, expression ;
bitwise_op   = '&' | '|' | '^' | '<<' | '>>' ;
```

### Static semantics

The result type of a bitwise or shift operator is the type `T` of the operands.

### Constraints

The bitwise operators `&`, `|`, and `^` and the shift operators `<<` and `>>` require both operands to satisfy the `integer` bound.

The operands of `&`, `|`, `^`, `<<`, or `>>` shall be the same type `T`.

### Examples (informative)

These examples apply where `cellbits::prog == 8`.

```
let a: ui4 = 0xFF00_FF00~ui4;
let b: ui4 = 0x00FF_FF00~ui4;

let and_r  = a & b;     // 0x0000_FF00~ui4
let or_r   = a | b;     // 0xFFFF_FF00~ui4
let xor_r  = a ^ b;     // 0xFFFF_0000~ui4

let x: si4 = -1~si4;    // all bits set (0xFFFFFFFF)
let shr    = x >> 4;    // -1~si4 (arithmetic shift)

let y: ui1 = 0x80~ui1;
let shl    = y << 1;    // 0x00~ui1 (0x100 mod 2^8 = 0)
let shr_u  = y >> 1;    // 0x40~ui1 (logical shift)

// Shift count >= bit width (ui4 has W = 32 when cellbits == 8)
let z: ui4 = 1~ui4;
let big    = z << 32;   // 0~ui4
let big2   = z << 100;  // 0~ui4
let neg: si4 = -1~si4;
let big3   = neg >> 32; // -1~si4 (sign bit replicated)

// Negative shift count: the shift is performed in the other
// direction.
let v: si4 = 64~si4;
let sh: si4 = -4~si4;
let other  = v << sh;   // descending shift of v by 4: 4~si4
```

### 6.6.1 Bitwise AND, OR, XOR

#### Static semantics

&mdash; Bitwise AND &mdash; `a & b` yields the value whose bit at each position *k* is `1` if and only if the bits at position *k* in both `a` and `b` are `1`.

&mdash; Bitwise OR &mdash; `a | b` yields the value whose bit at each position *k* is `1` if and only if the bit at position *k* in at least one of `a` or `b` is `1`.

&mdash; Bitwise XOR &mdash; `a ^ b` yields the value whose bit at each position *k* is `1` if and only if the bits at position *k* in `a` and `b` differ.

The bits of each operand are those of its value mod 2<sup>*W*<sub>t</sub></sup>, and the value yielded is mapped to the value set of `T`.

### 6.6.2 Shift operators

#### Static semantics

An ascending shift `a << b` yields (*a* × 2<sup>*b*</sup>) mod 2<sup>*W*<sub>t</sub></sup>, mapped to the value set of `T`.

A descending shift `a >> b` yields a value determined by the signedness of `T`:

&mdash; Unsigned types &mdash; the result is the integer part of *a* ÷ 2<sup>*b*</sup>.

&mdash; Signed types &mdash; the result is *a* ÷ 2<sup>*b*</sup>, rounded towards negative infinity.

Where the value of `b` is negative, the result is that of the shift in the other direction by &minus;*b* positions, where &minus;*b* is computed over the integers.

#### Design rationale (informative)

For a shift by *W*<sub>t</sub> or more positions, the rules above give `0` for an ascending shift and for an unsigned descending shift, and, for a signed descending shift, `0` where `a` is non-negative and `-1` where `a` is negative.

## 6.7 Comparison operators

### Syntax

```
comparison_expr = expression, ws, comparison_op, ws, expression ;
comparison_op   = '==' | '!=' | '<' | '>' | '<=' | '>=' ;
```

### Static semantics

The comparison operators have the result type `verdict[void, void]`.

&mdash; Integer comparison &mdash; `a < b`, `a <= b`, `a > b`, `a >= b`, `a == b`, and `a != b` yield `verdict::Pass.{ void }` where the value of `a` is respectively less than, less than or equal to, greater than, greater than or equal to, equal to, and not equal to the value of `b`, and `verdict::Fail.{ void }` otherwise.

&mdash; Floating radix point number comparison &mdash; the comparison operators on a floating radix point number type follow the rules defined in the clause on types.

### Constraints

The comparison operators require both operands to satisfy the `numeric` bound.

Both operands of a comparison operator shall be the same type `T`.

### Examples (informative)

```
let a: si4 = -1~si4;
let b: si4 = 1~si4;
let r = a < b;      // Pass (signed comparison: -1 < 1)

let x: ui4 = 0xFFFF_FFFF~ui4;
let y: ui4 = 1~ui4;
let s = x > y;      // Pass (unsigned comparison: 4294967295 > 1)

let p: fe11s52 = 0.0 / 0.0;    // +0nanq: residue 0, XOR(+, +) = +
let q: fe11s52 = -(0.0 / 0.0); // -0nanq

let t = p == p;     // Pass: reflexive
let u = p == q;     // Fail: sign differs
let v = p > 1.0;    // Pass: +qNaN orders above every non-NaN value
let w = p == 0nanq; // Pass: bit-identical

let neg_zero: fe11s52 = -0.0;
let pos_zero: fe11s52 = 0.0;
let z1 = neg_zero == pos_zero; // Fail: sign distinguishes zero
let z2 = neg_zero < pos_zero;  // Pass

let n = 0nans < 0nanq;         // Pass: +sNaN orders below +qNaN
```

## 6.8 Assignment

An assignment expression stores a value into the object its leading operand designates, as the clause on semantics defines a store. Two forms exist: simple assignment and compound assignment.

### Syntax

```
assignment_expr = expression, ws, '=', ws, expression ;

compound_assign = expression, ws, compound_op, ws, expression ;
compound_op     = '+=' | '-=' | '*=' | '/=' | '%='
                | '+|=' | '-|=' | '*|=' | '/|='
                | '&=' | '|=' | '^=' | '<<=' | '>>=' ;
```

### Static semantics

Both forms have the result type `void`.

A type `S` is **assignable** to a type `T` where `S` and `T` are the same type, or where this specification states that `S` **decays** to `T`. Where `S` decays to `U`, `U` decays to `T`, and `T` is not `S`, `S` decays to `T`. That decay yields what the decay to `U` followed by the decay to `T` yields. A decay takes place exactly where this specification relates a type to another by assignability.

### Constraints

Where a construct stores the value of an expression, the type of the expression shall be assignable to the type through which the store is performed.

The leading operand shall be a storable object expression, or an identifier expression that names a single-assignment binding whose object is an automatic object.

### Examples (informative)

```
let mut x: si4 = 0;
x = 42;
```

### 6.8.1 Evaluation order

#### Dynamic semantics

In a simple assignment `a = b`:

1. The leading operand `a` is evaluated to determine its object.
2. The following operand `b` is evaluated.
3. The value of `b` is stored into the object of `a`.

In a compound assignment `a op= b`:

1. The leading operand `a` is evaluated to determine its object and to load the current value held by the object.
2. The following operand `b` is evaluated.
3. The binary operation `op` is performed on the current value of `a` and the value of `b`.
4. The result is stored into the object of `a`.

In both forms, each step is earlier in programme order than the next.

### 6.8.2 Compound assignment operators

#### Constraints

The operands of a compound assignment shall satisfy what its binary operation requires of its operands.

#### Examples (informative)

```
let mut x: uaddr = 10;
x += 5;    // wrapping:   x is now 15
x -|= 100; // saturating: x is now 0

let mut flags: ui4 = 0xFF00;
flags &= 0x0F0F; // flags is now 0x0F00
flags ^= 0x00FF; // flags is now 0x0FFF
flags <<= 4;     // flags is now 0xFFF0
```

## 6.9 Casts and reinterpretations

### Syntax

```
cast_expr   = expression, ws, "as", [ ws, '!' ], ws, cast_target ;
cast_target = type ;
```

### Static semantics

A `cast_expr` without `!` is a **cast**, and one with `!` is a **reinterpretation**.

### 6.9.1 Conversion categories

#### Static semantics

&mdash; **Wrapping** &mdash; the value is reduced modulo 2<sup>*W*<sub>t</sub></sup>, where *W*<sub>t</sub> is the bit width of the target type, into the value set of the target type.

&mdash; **Rounding** &mdash; rounding and overflow follow the ISO/IEC 60559:2020 conversion under the rounding mode.

&mdash; **Truncation towards zero** &mdash; the fractional part is discarded.

&mdash; **Saturation** &mdash; out-of-range values are clamped to the nearest boundary of the target type.

### 6.9.2 Integer → integer

#### Static semantics

The integer value is converted by wrapping.

#### Examples (informative)

These examples apply where `cellbits::prog == 8`.

```
// wrapping: low 8 bits → 255~ui1
255~si4 as ui1
// wrapping: 0xFF → 255~ui1
-1~si1 as ui1
// wrapping: 42~si4
42~ui1 as si4
// wrapping: -1~si4
-1~si1 as si4
// wrapping: 0xFFFFFFFF → 4294967295~ui4
-1~si1 as ui4
// wrapping: 0x80 → -128~si1
128~ui1 as si1
```

### 6.9.3 Integer → floating radix point number

#### Static semantics

The integer value is converted by rounding.

### 6.9.4 Floating radix point number → integer

#### Static semantics

<table>
<thead><tr><th>Condition</th><th>Semantics</th></tr></thead>
<tbody>
<tr><td>Finite, in range</td><td>Truncation towards zero</td></tr>
<tr><td>Finite, above target max</td><td>Saturation to target type maximum</td></tr>
<tr><td>Finite, below target min</td><td>Saturation to target type minimum</td></tr>
<tr><td>Positive infinity</td><td>Target type maximum</td></tr>
<tr><td>Negative infinity</td><td>Target type minimum</td></tr>
<tr><td>NaN</td><td>Zero</td></tr>
</tbody>
</table>

#### Examples (informative)

```
3.7~fe8s23 as si4    // 3~si4 (towards zero)
-2.9~fe11s52 as si4  // -2~si4 (towards zero)
1e20~fe11s52 as si4  // si4 max (saturating)
-1e20~fe11s52 as ui4 // 0~ui4 (unsigned min, saturating)

// 0~si4 (NaN → zero)
(0.0~fe11s52 / 0.0~fe11s52) as si4
// 0~si4 (NaN → zero, regardless of sign)
-(0.0~fe11s52 / 0.0~fe11s52) as si4
```

### 6.9.5 Floating radix point format conversions

#### Static semantics

<table>
<thead><tr><th>Condition</th><th>Semantics</th></tr></thead>
<tbody>
<tr><td>Exactly representable</td><td>Exact</td></tr>
<tr><td>Not exact</td><td>Rounding</td></tr>
<tr><td>NaN</td><td>NaN</td></tr>
<tr><td>Positive or negative infinity</td><td>The same infinity</td></tr>
</tbody>
</table>

For a NaN operand, the sign bit and the kind are preserved. When the target format’s residue field is wider than the source’s, the residue is zero-extended. When the target format’s residue field is narrower than the source’s, a residue that fits within the target width is preserved; a residue that does not fit is saturated to the target’s maximum residue, as defined in the clause on types.

#### Examples (informative)

```
// fe5s10’s residue is 9 bits. 0x3FFFFF overflows and saturates.
0nanq'0x3FFFFF as fe5s10   // → 0nanq'0x1FF
0nanq'1        as fe5s10   // fits → preserved
0nanq'1        as fe19s236 // wider field → zero-extended
```

### 6.9.6 Variant type → discriminant

#### Static semantics

`e as ?` extracts the discriminant. The default type for this form is the discriminant type of the variant type.

`e as T` where `T` satisfies `integer` extracts the discriminant and then converts it to `T` using the integer-to-integer conversion rules. Where the discriminant type is `void`, the conversion yields zero.

The extracted value depends on the variant the value holds:

&mdash; For a variant other than a wild variant, the extracted value is the variant’s discriminant.

&mdash; For a wild variant with a canonical value (`wild(V)`), the extracted value is `V`.

&mdash; For a wild variant without a canonical value, the extracted value is the discriminant value stored.

#### Dynamic semantics

Where a cast extracts the discriminant, it uses, of the value of `e`, only the discriminant, and loads that discriminant from the object that holds that value.

#### Constraints

A cast whose source is a variant type shall have as its target a type that satisfies `integer` or is the discriminant type of the source.

#### Examples (informative)

```
enum colour { red, green, blue } with copyable;
let c = colour::green;
let d = c as ?;     // d: ui1, value 1
let e = c as ui4;   // e: ui4, value 1
                    // (discriminant extracted, then wrapped)

let b = verdict[void, void]::Pass.{ void };
let n = b as ?;     // n: ui1, value 1
let m = b as uaddr; // m: uaddr, value 1

let v: verdict[si4, si4] = verdict::Pass.{ 42 };
let r = v as ?;     // r: ui1, value 1 (payload 42 is discarded)
```

### 6.9.7 Cast operand and target types

#### Constraints

The type of the operand of a cast shall satisfy `numeric` or be a variant type or a reference type. Where the operand is not of a variant type, its target shall satisfy `numeric` or be a reference type. Where one of the two is a reference type, the other shall be `uaddr` or a reference type.

### 6.9.8 Bitwise reinterpretation

#### Dynamic semantics

A reinterpretation preserves the Γ sequence of the value of its operand and changes only the interpretation applied to it.

#### Constraints

A reinterpretation requires airside.

The type of the operand of a reinterpretation and its target shall have the same size under every eligible resolution of the generic parameters that occur free in them.

#### Examples (informative)

These examples apply where `cellbits::prog == 8`.

```
airside {
    // ISO/IEC 60559:2020 bits as integer
    let bits: ui4    = some_float as! ui4;
    // integer bits as ISO/IEC 60559:2020
    let back: fe8s23 = bits as! fe8s23;
}

// subroutine pointers
airside {
    let unmanaged_ptr: %void = 0x4000_1000 as %void;
    let f: fn() -> void = unmanaged_ptr as! fn() -> void;
    let g: fn(si4) -> si4 = f as! fn(si4) -> si4;
    let back: %void = g as! %void;
}
```

## 6.10 `airside` blocks

### Syntax

```
airside_block = "airside", ws, block ;
```

### Static semantics

The type and value of an `airside` block follow the rules for express blocks defined in the clause on statements and control flow.

### Implementation requirements

The implementation shall not use the presence of an `airside` block to eliminate or reorder an operation outside the block.

### Examples (informative)

```
let raw_val = airside {
    let ptr = 0x4000_1000 as %volatile atomic mut ui4;
    express *ptr;
};

// airside fn: the body is implicitly airside
airside fn read_mmio(addr: uaddr) -> ui4 {
    let ptr = addr as %volatile atomic ui4;
    return *ptr;
}
```

## 6.11 `const` blocks and the `xlat?` and `arbit?` conditionals

A `const` block is an expression evaluated at translation time. A `xlat?` or `arbit?` conditional selects one of two branches according to the machine on which its evaluation takes place.

### Syntax

```
const_block     = "const",
                  [ ws, '::', ws, ( 'prog' | "xlat" | "arbit" ) ],
                  ws, block ;
eval_cond_block = ( "xlat" | "arbit" ), ws, '?', ws, block
                | ( "xlat" | "arbit" ), ws, '?', ws, if_lead, ws,
                  "else", ws, block ;
eval_cond_expr  = ( "xlat" | "arbit" ), ws, '?', ws, if_lead, ws,
                  "else", ws, plain_expression ;
```

The `if_lead` production is defined in the clause on statements and control flow.

### Static semantics

The type and value of a `const` block follow the rules for express blocks defined in the clause on statements and control flow. A `const::xlat`, `const::arbit`, or `const::prog` block names the translation machine, the arbiter machine, or the programme machine, respectively.

Unless this specification states otherwise, any operation valid at execution time is valid within a `const` block.

The **leading branch** is:

&mdash; Of a `xlat?` or `arbit?` conditional, the `block` or the `expression` of its `if_lead`, or, where it has none, the `block` after its `?`.

&mdash; Of an `if` expression, the `block` or the `expression` of its `if_lead`, or, where it has none, the `block` after its `if_head` or `if_let_head`, as the clause on statements and control flow defines those productions.

The **analysis roots** of the translation machine are the `#dyn xlat` namespaces and the operations on symbols declared in a `#dyn xlat` namespace, as defined in the clause on programme structure and translation. Of those operations, one that is, or lies within, a leading branch of a `xlat?` conditional, and lies within no analysis root that is, or lies within, that branch, is not an analysis root.

The analysis roots of the programme machine are the global `instruct` blocks, the `trap` handlers, and, outside every `#dyn` namespace, the `static` declarations and the declarations that carry an external name.

A **constant expression** is the expression of an implanted constant in which no generic parameter occurs free, or a `const` block.

The initializer of a `const` or `static` declaration is evaluated as the operand of `express` in a `const` block written in its place. That block is the **initializer block** of the declaration.

The **evaluation roots**, which are also analysis roots, are the constant expressions and the following:

&mdash; The `T'bound(X)` expressions where, in semantic analysis, `T` is a closed type and no generic parameter occurs free in a generic argument of `X`.

&mdash; The expressions of inline expression operands of `instruct` blocks.

&mdash; The dependence arguments in which no generic parameter occurs free.

An evaluation root is analysed also on each machine for which it is evaluated.

The evaluations that an evaluation performs, directly or through invocations, are its **nested evaluations**. An evaluation of an evaluation root or of an analysis root of the translation machine, and each of its nested evaluations, is a **translation-time evaluation**, on whichever machine it takes place.

A local item that appears in a block, and each construct that lies within it, lies within no analysis root, and within no branch of a `xlat?` or `arbit?` conditional, other than one that is, or lies within, that item.

The clause on types defines what the layout of a type requires.

A construct analysed on a machine uses on that machine what the clause on declarations defines it to use, except as follows:

&mdash; It uses the layout of the type in a qualified form on the machine that the form names.

&mdash; On the machine that a qualified form names, it uses what it uses through a descriptor that the form emits.

A construct is **analysed on** the machines of the innermost analysis root within which it lies: each machine for which that root is evaluated, where it is an evaluation root, and otherwise the machine of which it is an analysis root. A construct that lies within no evaluation root, and within no analysis root other than one of the programme machine, is analysed also on each machine on which a construct does one of the following:

&mdash; Uses, on that machine, the declaration of a type whose declaration, or an `impl` block on that type, contains it.

&mdash; Uses, on that machine, the layout of a type whose layout requires the value of a dependence argument that is, or contains, it.

&mdash; Is analysed on that machine and has a type that is, or in which occurs, a type whose declaration, or an `impl` block on that type, contains it.

&mdash; Uses through a descriptor, on that machine, the body of a subroutine whose declaration contains it.

&mdash; Uses, on that machine, the declaration of a subroutine, a `const` declaration, a `static` binding, or an implanted constant whose declaration contains it.

The machines on which constructs are analysed, and for which evaluation roots are evaluated, form the **machine placement**. The machine placement is the least, by inclusion, that satisfies the rules of this specification. Where a rule tests its condition in the machine placement without some of those rules, that placement is the least that satisfies the rest.

A construct that is analysed on no machine in the machine placement without this rule, other than an implanted constant or its expression, is analysed on the programme machine. This rule is the **programme default**.

A construct shall satisfy the static semantics and the constraints of this specification under each machine on which it is analysed.

Each evaluation **takes place on** one machine. An evaluation of an analysis root of the translation machine takes place on that machine. The evaluation of an evaluation root for a machine takes place on that machine. Every other evaluation takes place on the machine of the innermost evaluation of which it is a nested evaluation, or of the analysis of a type whose layout requires its value, or, where there is neither, on the programme machine.

#### The `xlat?` and `arbit?` conditionals

Where a `xlat?` or `arbit?` conditional omits its `else` branch, the conditional is equivalent to one whose `else` branch is an empty block.

A `xlat?` conditional selects its leading branch in an evaluation on the translation machine, and an `arbit?` conditional in one on the arbiter machine. Each selects its `else` branch in every other evaluation.

A construct that is, or lies within, a branch of a `xlat?` or `arbit?` conditional is analysed, in place of the machines on which it would otherwise be, on each machine for which it is evaluated and on the following machines, unless it lies within an analysis root that is, or lies within, that branch:

&mdash; Each machine on which the conditional is analysed and on which an evaluation of the conditional selects that branch.

&mdash; Where that branch is an `else` branch and, in the machine placement without this entry, no such machine exists, each machine on which the conditional is analysed. This entry is the **`else` fallback**.

&mdash; For the leading branch of a `xlat?` conditional, the translation machine.

&mdash; For the leading branch of an `arbit?` conditional, the arbiter machine.

In the machine placement without one of the programme default and the `else` fallback, the other tests its condition in the machine placement without both.

An evaluation of the conditional evaluates the branch it selects.

The type of a `xlat?` or `arbit?` conditional is the common type of its branches.

#### Await collection

The **layout types** of a type are that type and each type whose layout the layout of that type requires, as the clause on types defines that relation.

The **crossing types** of a type are the least set of types that contains the layout types of that type and, for each managed reference type in the set, the layout types of its referent type.

A branch of a `xlat?` or `arbit?` conditional is **unselected** on a machine when the conditional selects its other branch there, as defined above.

The **inner constructs** of a construct or type on a machine are the constructs within it, except the following:

&mdash; Each local item that appears in a block, and each construct within one.

&mdash; Each branch unselected on that machine, and each construct within one.

&mdash; Each construct within an evaluation root that lies within that construct or type.

An evaluation root paired with a machine **draws in** each crossing type of the type of its value, paired with that machine. A construct or type that is not an evaluation root, paired with a machine, draws in the following, each paired with that machine except where the entry states otherwise:

&mdash; Its inner constructs.

&mdash; The type, if any, that a declaration it uses gives to what that declaration declares.

&mdash; Each evaluation root whose value the layout of a type that it uses requires, paired with that machine, or, where it uses that layout through a qualified form, with the machine that the form names.

&mdash; Each part of a definition that it uses.

&mdash; On every machine, what it uses through a descriptor.

&mdash; On every machine, for each type that one of its descriptors describes, each evaluation root whose value the layout of a crossing type of that type requires.

&mdash; On every machine, the body of each subroutine that it names other than as a method invocation or as the leading expression of a subroutine invocation.

The **await collection** of an evaluation of an evaluation root is the least set that contains the following:

&mdash; What the root, paired with the machine on which the evaluation takes place, would draw in were it not an evaluation root.

&mdash; What each member of the set draws in.

Each member carries the generic arguments under which it is drawn in.

Each type in an await collection is the type as written at the place from which it is drawn in. That place is one of the following:

&mdash; The declaration that gives it.

&mdash; The evaluation root whose value has it.

&mdash; The construct that uses its layout.

&mdash; The construct one of whose descriptors describes it.

&mdash; The type whose layout requires it, or the declaration of that type.

&mdash; The managed reference type whose referent type it is.

Where that place omits the type, the type counts as written there in full.

Where a construct or type draws in another construct or type that has generic parameters, and supplies generic arguments for them, the member so drawn in has those arguments for those parameters. A pair drawn in under different generic arguments is a different member.

The generic parameters of an implanted item to which a path resolves, and of the subroutine that an implantation provides for it, are determined by the clause on protocols and implantations.

An evaluation of an evaluation root **directly awaits**, for each evaluation root paired with a machine in its await collection, the evaluation of that root performed for that machine, where there is one. It **awaits** each evaluation in the least set that contains each evaluation that it directly awaits and each evaluation that an evaluation in the set directly awaits.

An evaluation root **is evaluated for** the machines of the place where it is written, as follows:

&mdash; A `const` block that names a machine is evaluated for that machine.

&mdash; The initializer block of a `const` or `static` declaration, and each evaluation root that lies within the type that the declaration states, are evaluated for the programme machine.

&mdash; Any other evaluation root that lies within a subroutine body, an evaluation root, a `#dyn xlat` namespace, or a local item that appears in a block is evaluated for each machine on which it is analysed and, where it is the expression of an implanted constant, for each machine for which a protocol descriptor with a field for that implanted constant is emitted.

&mdash; Any other evaluation root is evaluated for the programme machine.

Where a construct uses the layout of a type on a machine, each evaluation root whose value the layout of that type requires, and which is written at that use, is evaluated also for that machine.

Each evaluation root has one evaluation for each machine for which it is evaluated. An evaluation of an evaluation root on the translation machine takes place exactly once. This specification does not fix the number of times an evaluation of an evaluation root on another machine takes place.

An evaluation root has an evaluation **performed for** each of the following machines:

&mdash; Each machine on which the root is analysed.

&mdash; Each machine on which a construct analysed there yields the value of the root.

&mdash; The machine of each protocol descriptor that holds the value of an implanted constant whose expression is the root.

The evaluation performed for a machine is the evaluation of the root for that machine, or, where there is none, its only evaluation.

### Dynamic semantics

The value of an evaluation of an evaluation root **crosses** to each machine for which that evaluation is performed, by the rules of the subclause on cross-machine value validity. The value crossing to one machine, together with each referent that crosses with it under those rules, is one **crossing**.

The value, and each referent that crosses with it, cross as they stand once the evaluation determines the value, and before control, in leaving the block or expression, destroys any object or releases any storage.

On each machine for which an evaluation of an evaluation root is performed, the root yields the value of that evaluation crossed to that machine.

The **products** of an evaluation of an evaluation root are the objects for which it, or one of its nested evaluations, reserves storage, and, where the root is the initializer block of a `static` declaration, the permanent object that the declaration introduces.

Each cell of each machine has a **starting value** for each translation. It is the same in every translation-time evaluation on that machine, and no translation-time evaluation, and no result of one, affects it.

For each machine for which an evaluation of an evaluation root is performed, its **completed result state** on that machine consists of the value that crosses to that machine and the values of the cells of the crossed counterparts of the referents that cross with it. Where the root is the initializer block of a `static` declaration, the state also includes the values of the cells of the permanent object that the declaration introduces on that machine, which hold that value. Each such state is fixed for the translation.

At each τ point of an execution context on the translation machine, the **translation environment** consists of the cells of the objects declared in a `#dyn xlat` namespace and the cells that the environment of the translation machine holds as its own.

For a given implementation, the inputs of an evaluation of an evaluation root are the following:

&mdash; The programme.

&mdash; The properties of each machine.

&mdash; The starting values of the cells of its machine.

&mdash; The completed result states on its machine of the evaluations that complete before it begins.

&mdash; The completed result state of each evaluation it directly awaits, on each machine with which its await collection pairs the root of that evaluation.

&mdash; On the translation machine, the signals it receives from the environment of that machine and the values it loads from the translation environment.

The evaluation begins with each cell of its machine that one of those completed result states describes holding the value of that state, and with each other cell outside the translation environment holding its starting value. The rules upon execution contexts and the ordering of τ apply within the evaluation alone, to the operations that it and its nested evaluations perform. Its operations, the addresses and values they determine, and whether it completes, diverges, or causes a translation failure depend only on its inputs.

On the translation machine, translation-time evaluations share the environment of that machine and the translation environment. The signals each exchanges with that environment, and the accesses each performs to the translation environment, take effect for the others in the relative order of those evaluations. The translation environment holds only the values that the environment of the translation machine and those interactions give it.

At each cell that a completed result state on the programme machine describes, the initial storage of the programme machine holds the value of that state.

An evaluation of an analysis root of the translation machine that takes place outside every evaluation of an evaluation root satisfies the requirements above upon an evaluation of an evaluation root, with the value of that analysis root in place of the value of the evaluation root.

### Constraints

The translation machine, the arbiter machine, and the programme machine are ordered in that sequence. An analysis root of a machine shall refer to no binding that is introduced outside the root by a construct analysed on a machine later in that sequence than each machine on which the root is analysed, and whose object is an automatic object.

A translation-time evaluation of an `instruct` block shall take place on the translation machine.

An evaluation on the translation machine or on the arbiter machine shall not access, or create a reference to, the object of a `static` binding declared outside every `#dyn xlat` namespace, or a constituent object of that object.

A `const` block, the expression of an inline expression operand, and a dependence argument that is an evaluation root shall satisfy the constraints the clause on declarations places upon a local item that appears in a block.

An operation that is an analysis root and is on a symbol declared in a `#dyn xlat` namespace shall be one that, were it not an analysis root, would be analysed on the translation machine alone.

An evaluation of an evaluation root shall not await itself.

A construct shall yield the value of an evaluation of an evaluation root only after that evaluation has completed. Within an evaluation of an evaluation root, a construct shall access a product of another evaluation of an evaluation root only after that other evaluation has completed. A violation of either requirement, where not detected during translation, can cause indeterminate state.

The branches of a `xlat?` or `arbit?` conditional shall have a common type.

### Design rationale (informative)

An evaluation can enter code that is paired with no machine in its await collection or in the await collection of an evaluation that it awaits: at an address converted from an integer, through an `instruct` block, or through a pointer, crossed to another machine, to a subroutine declared in a `#dyn xlat` namespace.

Only translation-time evaluations on the translation machine can act on an environment, so only their number of times is observable. An evaluation of an evaluation root on another machine depends only on its inputs, and each time it takes place it yields the same result.

### Examples (informative)

```
const buffer_size: uaddr = const::xlat {
    express 4096 * page_count();
};

fn platform_init() {
    xlat? {
        init_at_translation();
    } else {
        init_at_execution();
    }
}

// Without an `else` branch
xlat? {
    calibrate();
}

// Expression form

// `instruct` in the leading branch of xlat?

    express xlat? then airside {

```

### 6.11.1 Translation-machine evaluation

#### Static semantics

An evaluation on the translation machine takes the cell width, the address width, the reference width, the rounding mode, the atomicity set, the transactionality set, the literal encoding, and the unqualified type intrinsics from that machine.

#### Examples (informative)

```
const build_version: &[ui1] = const::xlat {
    #add std::"posix.kr" as posix;
    use posix::env;
    express env::get("build_version");
};

const font_data: &[ui1] = const::xlat {
    #add std::"posix.kr" as posix;
    use posix::fs;
    express fs::read_raw("font.ttf");
};
```

### 6.11.2 Programme-machine and arbiter-machine evaluation

#### Static semantics

The cell width, the address width, and the reference width of the arbiter machine are each the greater of those of the translation machine and the programme machine. The atomicity set and the transactionality set of the arbiter machine hold every pair of a size and an alignment. Its environment is one that the environment of the translation machine provides.

An evaluation on the programme machine takes the properties the subclause on translation-machine evaluation lists from the programme machine. An evaluation on the arbiter machine takes the rounding mode and the literal encoding from the programme machine, and the rest of those properties from the arbiter machine.

#### Examples (informative)

```
// make_lut is invoked on the translation machine
const crc_table: [ui4; 256] = const::xlat { express make_lut(); };

// Here it is invoked on the programme machine, and exec_table
// crosses to each machine for which that evaluation is performed
const exec_table: [ui4; 256] = make_lut();

// static with complex initializer
static greeting: &[ui1] = build_greeting("world");
```

### 6.11.3 Reproducibility

#### Implementation requirements

Given the same implementation, the same environment of the programme machine, and the same environment of the translation machine, a programme’s translation-time evaluations take place in the same relative order on every translation.

An evaluation of an evaluation root shall begin after every evaluation that it awaits has completed.

#### Implementation defined

The relative order in which a programme’s translation-time evaluations take place is implementation defined.

### 6.11.4 Opaque code exclusion

#### Implementation requirements

The opaque code shall contain nothing that lies within an evaluation root, within an analysis root of the translation machine, or within a leading branch of a `xlat?` or `arbit?` conditional.

### 6.11.5 Cross-machine value validity

#### Static semantics

The type of a value that crosses is analysed on the machine to which it crosses. A value crosses according to its type:

&mdash; Values of `void`, of an integer type, and of a floating radix point number type cross unchanged.

&mdash; Values of reference types cross by their tribe, as below.

&mdash; A subroutine pointer to a subroutine not declared in a `#dyn xlat` namespace crosses as one that designates the same subroutine, which is analysed on the machine to which the pointer crosses. A pointer to a subroutine declared in a `#dyn xlat` namespace crosses to the translation machine as one that designates the same subroutine, and to each other machine as a value that this specification does not fix.

&mdash; A value of any other type crosses by composition. Each value it holds, as the clause on references and resource management defines holding, crosses. The crossed value is laid out under the layout rules of its type, as defined in the clause on types.

The address of an unmanaged reference crosses unchanged, and its referent does not cross.

A managed reference crosses together with its referent, except where it crosses to the programme machine and its referent is the object of a `static` binding declared outside every `#dyn xlat` namespace, a constituent object of that object, or a run of elements of an array that is either.

Within one crossing, each referent that crosses does so once, and its crossed counterpart is a resident object or a constituent object of one. Where one referent in a crossing is a constituent object of another, or a run of elements of an array that is another, it crosses as the corresponding constituent object, or run of elements, of the crossed counterpart of that other referent.

Where runs of elements of one array are referents in one crossing and overlap, directly or through further such runs, the least run of that array that contains them all is a referent in that crossing.

A crossed managed reference designates the crossed counterpart of the referent of the original, or that referent where it does not cross, and bears the tribe and the modifiers of the original.

The length of a slice reference crosses unchanged. The `.tyd` and `.prd` fields of a reference to a protocol type cross as the corresponding descriptors of the machine to which they cross, and each subroutine that those descriptors designate is analysed on that machine. The erased type of a reference to a protocol type is analysed on the machine to which the reference crosses.

#### Constraints

&mdash; A crossed value, each value it holds, and the value held by the crossed counterpart of each referent that crosses with it shall each belong to the value set of its type as analysed on the machine to which the crossed value crosses.

&mdash; Each referent that crosses shall be of a copyable type.

&mdash; The address of an unmanaged reference, and the length of a slice reference, shall belong to the value set of `uaddr` determined under the address width of the machine to which the reference crosses.

&mdash; The length of a managed slice reference, multiplied by the size of the element type of its referent type on the machine to which it crosses, computed over the non-negative integers without wrapping, shall belong to the value set of `uaddr` on that machine.

#### Implementation requirements

The diagnostic for a crossing that violates a constraint above shall identify the value to which that constraint applies, and its type.

#### Design rationale (informative)

The crossed counterparts of referents are immortal objects because the initial storage of the programme machine can hold the value that crosses, and execution can then use that value at any of its τ points.

## 6.12 Inline `instruct` blocks

An inline `instruct` block is an expression that embeds instructions.

### Syntax

```
instruct_block = "instruct", ws, instruct_body,
                 [ ws, constraint_clause ] ;

constraint_clause = "with", ws, '{', ws,
                    { instruct_constraint, ws, ';', ws }, '}' ;

instruct_body  = '{', { ? instruction text line ? }, '}' ;

instruct_constraint
    = 'in',      ws, '(', ws, operand_target, ws, ')', ws,
                 '=', ws, expression
    | 'out',     ws, '(', ws, operand_target, ws, ')', ws,
                 '->', ws, identifier
    | 'io',      ws, '(', ws, operand_target, ws, ')', ws,
                 '=', ws, expression, ws, '->', ws,
                 identifier
    | 'clobber', ws, '(', ws, ? mill identifier ?, ws,
                 { ',', ws, ? mill identifier ?, ws },
                 ')' ;

operand_target = [ '\'', identifier | '\'?'
                 | '\'', digit, { digit }
                 | ? mill identifier ? ] ;
```

### Static semantics

The **mill** of a machine is the part of its state other than its storage. A **mill identifier** names a part of the mill.

Within the curly brackets of an `instruct_body`, a `\` that lies within no Kurt operand and is not the second character of an instruction text escape begins an **instruction text escape**, which consists of that `\` and the character that follows it. A `'` begins a Kurt operand where it lies within no Kurt operand begun before it, is not part of an instruction text escape, and follows a character other than one permitted within an identifier. The Kurt operand extends over the longest sequence of characters beginning with that `'` that matches a Kurt operand form. All other text, instruction text escapes included, is **instruction text**.

A Kurt operand has four forms:

&mdash; Named operand (`'name`) &mdash; names a named constraint declared in the constraint clause.

&mdash; Positional operand (`'0`, `'1`, …) &mdash; selects a constraint by its index in the constraint clause, counting from zero.

&mdash; Sequential operand (`'?`) &mdash; takes the next unmatched positional constraint in index order.

&mdash; Inline expression operand (`'(expr)`) &mdash; the expression is evaluated at translation time and its value is placed within the instruction text.

In each operand-targeting mode, the constraint clause declares the target and the instruction text names it:

&mdash; Named &mdash; the clause writes `in('name) = expr`, and the text writes `'name`.

&mdash; Positional &mdash; the clause writes `in('1) = expr` to declare an explicit index, or `in() = expr` to take the next available one, and the text writes an index or `'?`.

&mdash; Mill &mdash; the clause writes `in(rax) = expr`, and the text writes the bare mill identifier.

The Kurt comment syntax defined in the clause on lexical structure applies to the delimiting tokens of an `instruct` block. Apart from the operands above and from what ends the instruction text, the text within the block is opaque to the lexical rules of Kurt.

The instruction text of the block, with each instruction text escape replaced by the character that follows its `\`, is **delivered** to the environment the block targets.

The block targets the environment of the programme machine where it is a global `instruct` block. It targets the environment of the translation machine or of the programme machine where it is analysed on that machine and an execution context of that machine can occupy a succession of programme points that contains its first programme point.

#### Constraint clauses

&mdash; `in(target) = expr` &mdash; places the value of `expr` in `target` before the instructions of the `instruct` block are executed.

&mdash; `out(target) -> var` &mdash; stores the value of `target` into the object of `var`, through `var`, after the instructions of the `instruct` block are executed.

&mdash; `io(target) = expr -> var` &mdash; places the value of `expr` in `target` before the instructions are executed; stores the value of `target` into the object of `var`, through `var`, after they are executed.

&mdash; `clobber(r1, r2, ...)` &mdash; declares that the instructions of the block may modify the parts of the mill the listed mill identifiers name.

### Dynamic semantics

The expressions of the constraints are evaluated in constraint-clause order.

### Constraints

An inline `instruct` block requires airside.

The curly brackets of the instruction text of an `instruct` block, other than those of instruction text escapes, shall balance.

The instruction text of an `instruct` block shall follow the syntax of instruction text of the environment to which it is delivered.

Each `'` that begins a Kurt operand shall begin a sequence of characters that matches one of the four Kurt operand forms. Each instruction text escape shall be `\\`, `\'`, `\{`, or `\}`.

The entries of a single constraint clause, other than its `clobber` entries, shall all use one operand-targeting mode.

Each `'name` shall match exactly one named constraint of the constraint clause. Each `'N` shall be the index of a positional constraint of the constraint clause. `'?` past the last unmatched positional shall not appear. Duplicate mill identifiers among operand targets and overlap between operand targets and `clobber` entries shall not appear.

The `var` of an `out` or `io` constraint shall name a multi-assignment binding.

### Implementation requirements

After an `instruct` block, each part of the mill that its `clobber` entries name shall hold the value that it held before the block.

### Implementation defined

The mill identifiers a machine supports, the syntax of instruction text, and the form in which the value of the expression of an inline expression operand is placed within it are implementation defined for each supported environment of each machine.

### Examples (informative)

```
// No constraints
airside { instruct { msr daifclr, #2 }; }

// Mill mode
airside {
    let mut n: saddr;

    instruct { svc #0 } with {
        in(x8) = 64; io(x0) = 1 -> n; in(x1) = buf;
        in(x2) = len;
        clobber(x16, x17);
    }
}

// Named mode
airside {
    let mut r: ui4;

    instruct {
        mrs 'c, sctlr_el1
        orr 'c, 'c, '(1 << 2)
        msr sctlr_el1, 'c
    } with { io('c) = v -> r; }
}

// Positional: anonymous, '? sequential
airside {
    instruct {
        mov x0, '?
        mov x1, '?
    } with {
        in() = 1;
        in() = 2;
    }
}

// Positional: reordered via explicit index
airside {
    instruct {
        mov x0, '? // 2
        mov x1, '? // 1
    } with {
        in('1) = 1;
        in('0) = 2;
    }
}

// Positional: same operand referenced twice
airside {
    instruct {
        mov x0, '0 // both 1
        mov x1, '0
    } with {
        in() = 1;
    }
}

// -> !
fn halt() -> ! {
    loop { airside { instruct { wfi } } }
}

// Instruction text is constrained only upon delivery: the
// discarded branch may hold instruction text of another environment
airside {
    let mut t: ui8;

    xlat? {
        instruct { rdtsc } with { out(eax) -> t; }
    } else {
        instruct { mrs '0, cntvct_el0 } with { out() -> t; }
    }
}

// The `instruct` block lies in the leading branch of xlat?, so it is
// delivered to the environment of the translation machine alone.
fn include_bytes(path: &[ui1]) -> &[ui1] {
    xlat? {
        let mut r: &[ui1];
        airside {
            instruct { /* translation-machine I/O */ }
                with { out() -> r; }
        }
        return r;
    } else {
        trap();
    }
}
```

## 6.13 Type intrinsic expressions

A type intrinsic expression queries a property of a type.

### Syntax

```
type_intrinsic    = type, ws, type_intrinsic_op ;
type_intrinsic_op = '\'', ws,
                    ( 'size' | 'align'
                    | 'offset', ws, '(', ws, offset_field, ws, ')'
                    | 'bound',  ws, '(', ws, bound_argument, ws, ')' ),
                    [ ws, '::', ws, ( 'prog' | "xlat" | "arbit" ) ] ;
bound_argument    = bound_elem | "type" ;
offset_field      = [ identifier, ws ], '.', ws,
                    ( identifier | integer_literal ) ;
```

### 6.13.1 Layout intrinsics

#### Static semantics

`T'size` yields the size of the type `T` in cells.

`T'align` yields the alignment of the type `T` in cells.

`T'offset(f)` yields the cell offset of the field that `f` designates, from the first cell of the representation of a value of `T`. Where an identifier precedes the `.` of `f`, `f` designates a field of the variant of `T` that identifier names, and otherwise a field of `T`. An identifier after the `.` names that field, and an integer literal after it gives its position, counting from zero in declaration order.

Each layout intrinsic yields a `uaddr` value. Each layout intrinsic permits the three qualified forms defined in the clause on types, written after it. The form qualified with `::prog` yields its value under the layout of `T` on the programme machine, the form qualified with `::xlat` under that on the translation machine, and the form qualified with `::arbit` under that on the arbiter machine.

#### Constraints

`T'offset(f)` shall appear only where `f` designates a field that `T` places. An integer literal in `f` shall appear only where that field belongs to a type or variant in unnamed-field form. Where a layout intrinsic takes a qualified form, `T` shall be, in semantic analysis, a closed type. The value of a layout intrinsic shall belong to the value set of its type.

#### Examples (informative)

```
const sz: uaddr  = my_struct'size;
const al: uaddr  = my_struct'align;
const off: uaddr = my_struct'offset(.field_name);
```

### 6.13.2 Bound descriptor emission

#### Static semantics

`T'bound(X)` queries whether the type `T` satisfies the bound `X` and emits a descriptor for `T`. The result type is `verdict[%void, void]`. When `T` satisfies `X`, the result is `verdict::Pass.{ ptr }` where `ptr` is an unmanaged reference to that descriptor. When `T` does not satisfy `X`, the result is `verdict::Fail.{ void }`.

Where, in semantic analysis, `T` is an open type or a generic parameter occurs free in a generic argument of `X`, whether `T` satisfies `X` is decided in semantic analysis, and the descriptor `T'bound(X)` emits is as follows:

&mdash; A declared protocol &mdash; the descriptor the table below gives for `X`, of an implantation of `X` witnessed for `T`. `T'bound(X)` yields `verdict::Fail.{ void }` where no such implantation is witnessed.

&mdash; A bound other than a declared protocol &mdash; the descriptor the table gives for `X`, of the type that `T` denotes in each evaluation.

A descriptor belongs to a machine: every address and value it holds, and every object it designates, is that of that machine. `T'bound(X)::prog` emits the descriptor of the programme machine, `T'bound(X)::xlat` that of the translation machine, and `T'bound(X)::arbit` that of the arbiter machine.

When the result is `verdict::Pass.{ ptr }`, `ptr` permits no store and designates a descriptor that exists before the evaluation. Where, in semantic analysis, `T` is a closed type and no generic parameter occurs free in a generic argument of `X`, the following hold:

&mdash; That descriptor is an immortal object.

&mdash; Within one translation unit, multiple evaluations of `T'bound(X)` that emit the descriptor of one machine, for the same `(T, X)` pair where `T` satisfies `X`, yield the same reference value.

The descriptor the expression emits depends on the kind of bound:

<table>
<thead><tr><th>Bound kind</th><th>Descriptor</th></tr></thead>
<tbody>
<tr><td><code>type</code></td><td>A type descriptor as defined in the subclause on descriptors</td></tr>
<tr><td>Declared protocol</td><td>A protocol descriptor as defined in the subclause on descriptors</td></tr>
<tr><td><code>numeric</code>, <code>integer</code>, or <code>primitive</code></td><td>An arithmetic descriptor as defined in the subclause on descriptors</td></tr>
<tr><td>Any other bound</td><td>An immortal object of size zero</td></tr>
</tbody>
</table>

`T'bound(type)` yields a value of the `Pass` variant for every type.

#### Constraints

The type `T` of a `T'bound(X)` expression shall be a closed type, a type parameter, or, within an implanted subroutine that a protocol `impl` block provides, `selftype` or the target type of that block. Where the expression takes a qualified form, `T` shall be, in semantic analysis, a closed type and no generic parameter shall occur free in a generic argument of `X`.

#### Design rationale (informative)

Returning `verdict[%void, void]` lets bound satisfaction be tested as an ordinary contract value: a programme that requires satisfaction traps on the `verdict::Fail` path, and the `verdict::Pass` payload is the descriptor reference that the formation of a reference to a protocol type consumes.

#### Examples (informative)

```
// Declared protocol: yields protocol descriptor
const si4_ord: %void = contract si4'bound(ord)::prog else trap();

// Built-in bound
const si4_num: verdict[%void, void] = si4'bound(numeric)::prog;
```

### Static semantics

**Leading-to-following associativity** means `a op b op c` is parsed as `(a op b) op c`. **Following-to-leading associativity** means `a op b op c` is parsed as `a op (b op c)`. A form whose associativity the table gives as a dash does not associate, and an expression in which such a form supplies an operand of the same form shall not appear. (e.g. `a < b < c` shall not appear.)

The table assigns precedence to compare-and-swap (`>.<`), to the value forms taking `else`, and to contract extraction as whole forms.
