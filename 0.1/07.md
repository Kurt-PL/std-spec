# 7. Statements and control flow

This clause defines the statements and the control flow of the Kurt programming language: blocks, contract types, branching, pattern matching, loops, control transfers, and the divergence primitive.

## 7.1 Blocks and statements

### Syntax

```
block            = '{', ws, { block_item, ws }, '}' ;
block_item       = ( { item_prefix, ws }, local_item )
                 | let_decl | statement ;

statement        = block_expression
                 | [ plain_expression ], ws, ';' ;

block_expression = block | labelled_block | if_block | if_let_block
                 | match_expression | while_block | loop_expression
                 | extraction_block | airside_block | xlat_block
                 | const_block | eval_cond_block | instruct_block ;
plain_expression = ? an expression that is not a block_expression ? ;
```

### Static semantics

A **block** is a sequence of block items delimited by curly brackets. The statements and `let` declarations of a block are evaluated in order, and the programme point at the end of the block is occupied after the last of them, or at once where the block has none.

For the rules of scope, object lifetime, and automatic object layout, an expression that has branches, alternatives, a loop body, or a continuation is a block, and so is each of its branches, alternatives, loop bodies, and continuations, whether or not curly brackets delimit it.

A **block expression** is an expression of one of the forms the `block_expression` production lists. Every other expression is a **plain expression**.

A statement that is a plain expression evaluates the expression. A statement whose expression is omitted performs no operations.

Where a block expression stands as a statement, it constitutes the whole of that statement, and what follows it begins a new statement.

Where an `else` clause or an `and then` clause belongs, in different derivations of a source unit, to different constructs, it belongs to the innermost of them.

## 7.2 Contract types

A **contract type** partitions its values into a success side and a failure side. A declared type is a contract type only where a `contract` declaration introduces it. The built-in `verdict[T, F]` is a contract type as defined in the clause on types.

### Syntax

```
contract_decl = [ "pub", ws ], "contract", [ ws, '!' ], ws,
                identifier, [ ws, generic_clause ], ws,
                '{', ws, variant, ws, ',', ws, variant, ws,
                [ ',', ws ], '}',
                [ ws, with_single, ';' | ws, with_curly ] ;

inv_clause    = 'inv', ws, '->', ws, type ;
```

The `inv` clause appears as a `with` item on a `contract` declaration.

### Static semantics

A `contract` declaration introduces a contract type of two variants. The payload of a value of a contract type is the value the field of its variant holds. The **success payload type** and the **failure payload type** of a contract type are the types of the fields of its success variant and of its failure variant. A construct that obtains a payload from a value of a contract type, or places a payload in one, designates by position the field that holds that payload.

In a `contract` declaration, the `wild` variant is the failure side and the other variant the success side. In a `contract!` declaration, the `wild` variant is the success side and the other variant the failure side.

A contract type and the type its `inv` clause names form an **inverted pair**.

### Constraints

Each variant of a `contract` declaration shall be in unnamed-field form with exactly one field.

Exactly one variant of a `contract` declaration shall bear a `wild` discriminant.

An `inv` clause naming a type that does not declare `inv` back to the declaring type shall not appear.

The success payload type of the type the `inv` clause names shall equal the failure payload type of the declaring type, and vice versa.

### Examples (informative)

```
// 1. contract without inverted pair
//    wild = failure. No ! operator.
contract toggle {
    on { void },
    off { void } = wild
}

// 2. contract! without inverted pair
//    Polarity inverted: wild = success.
contract! http_result {
    ok { response } = wild,
    error { http_error } = 404
}

// 3. contract ↔ contract inverted pair
//    Polarity is inverted by placing wild on a different variant
//    in each declaration.
contract switch[T] {
    on { T }, off { void } = wild
} with inv -> switch_inv[T];

contract switch_inv[T] {
    on { T } = wild, off { void }
} with inv -> switch[T];

// 4. contract ↔ contract! inverted pair
//    Both declarations have identical structure. Polarity is
//    inverted by contract! rather than by rearranging wild.
contract acquired[T] {
    have { T },
    missing { void } = wild
} with inv -> lost[T];

contract! lost[T] {
    have { T },
    missing { void } = wild
} with inv -> acquired[T];

// 5a. Self-inverse (generic)
//     The inverted pair is the type itself with type arguments
//     swapped. !result[T, F] yields result[F, T].
contract result[T, F] {
    pass { T } = 1,
    fail { F } = wild(0)
} with {
    inv -> selftype[F, T],
    discrim(ui1)
}

// 5b. Self-inverse (non-generic)
//     inv -> truthy_bool names the type itself directly.
//     Only the explicit variant is the failure side.
//     All other discriminant values are the success side.
contract! truthy_bool {
    true { void } = wild(1),
    false { void } = 0
} with {
    inv -> truthy_bool,
    discrim(ui1)
}
```

### 7.2.1 Polarity inversion

#### Static semantics

`!expr`, where `expr` has a contract type `T` and `T` declares `inv -> U`, yields a value of type `U`.

#### Dynamic semantics

Where `!expr` is evaluated, the yielded value takes the variant of `U` on the side other than the one on which the variant of the value of `expr` lies, and holds the payload of that value.

The discriminant of the yielded value is the one the clause on declarations gives the variant it takes.

#### Examples (informative)

```
// For verdict[void, void], verdict has
//   with inv -> selftype[F, T],
// so !verdict[void, void] yields verdict[void, void].
let x = !verdict[void, void]::Pass.{ void }; // x = Fail.{ void }
let y = !verdict[void, void]::Fail.{ void }; // y = Pass.{ void }

// Inverted pair
let s:    switch[si4]     = switch::on.{ 1 };
let inv:  switch_inv[si4] = !s;   // result type is switch_inv[si4]
let s2:   switch[si4]     = !inv; // result type is switch[si4]

// verdict: inverted pair is selftype[F, T]
// !verdict[T, F] yields verdict[F, T]
let r:     verdict[si4, &[ui1]] = verdict::Pass.{ 42 };
let inv_r: verdict[&[ui1], si4] = !r;

// polarity inversion in control-flow position
if !result -> err { handle(err); }
let err = contract !result else.val { recover(val); return; };
```

### 7.2.2 Logical operators

#### Syntax

```
logical_expr = expression, ws, logical_op, ws, expression ;
logical_op   = "and" | "or" | "xor" ;
```

#### Static semantics

The result type of `and`, `or`, and `xor` is `verdict[void, void]`.

#### Dynamic semantics

`a and b` &mdash; if `a` is the failure variant, the result is `verdict::Fail.{ void }` and `b` is not evaluated. Otherwise, the result is `verdict::Pass.{ void }` if `b` is the success variant and `verdict::Fail.{ void }` if `b` is the failure variant.

`a or b` &mdash; if `a` is the success variant, the result is `verdict::Pass.{ void }` and `b` is not evaluated. Otherwise, the result is `verdict::Pass.{ void }` if `b` is the success variant and `verdict::Fail.{ void }` if `b` is the failure variant.

`a xor b` &mdash; both operands are evaluated. The result is `verdict::Pass.{ void }` if exactly one operand is the success variant and `verdict::Fail.{ void }` otherwise.

#### Constraints

Each operand shall be of a contract type.

#### Examples (informative)

```
let ok  = a > 0 and b > 0;
let any = x == 1 or y == 1;
let one = x == 1 xor y == 1;
```

### 7.2.3 Contract extraction

#### Syntax

```
extraction_block = "contract", ws, expression, ws, else_bind,
                   ws, block ;
extraction_expr  = "contract", ws, expression, ws, else_bind,
                   ws, plain_expression ;
```

#### Static semantics

The type of `contract expr else …` is the success payload type of `expr`.

#### Dynamic semantics

When `contract expr else [.id] …` is evaluated:

1. `expr` is evaluated.
2. If the result is the success variant, its payload is the result of the whole expression.
3. If the result is the failure variant, the `else` branch is evaluated, and on entry to it, where `else` names a binding (`else.id`), the failure variant’s payload is bound to `id`. The value of the `else` branch is the result of the whole expression.

#### Constraints

The type of `expr` shall be a contract type.

The `else` branch shall be a control transfer or a diverging expression, or its type shall be assignable to the success payload type of `expr`.

#### Examples (informative)

```
// Diverging else branch
let v = contract compute() else { return; };
let v = contract compute() else.err { return err; };

// Value-yielding else branch
let v = contract compute() else default;
let v = contract compute() else.err recover(err);
let v = contract compute() else.err { log(err); express recover(err); };

// Destructuring the success payload
let .{ x, y } = contract get_point() else { return; };

// Assignment to an existing object
let mut result: si4;
result = contract compute() else { return; };

// Polarity inversion
let e = contract !contract_value else.v { recover(v); return; };
```

## 7.3 Branching upon a contract

### Syntax

```
if_head     = [ label, ws ], "if", ws, expression,
              [ ws, '->', ws, ident_pat ] ;
if_lead     = block | "then", ws, expression ;

if_block    = if_head, ws, block
            | if_head, ws, if_lead, ws, else_branch ;
if_expr     = if_head, ws, if_lead, ws, else_value ;

else_branch = else_bind, ws, ( block | if_block | if_let_block ) ;
else_value  = else_bind, ws, plain_expression ;
```

### Static semantics

The type of an `if` expression that no `express` targets is the common type of its branches.

The **leading branch** of an `if` expression is the `block` or the `expression` of its `if_lead`, or, where it has none, the `block` after its `if_head`.

`-> v` introduces `v` within the leading branch.

Where an `if` expression omits its `else` branch, the expression is equivalent to one whose `else` branch is an empty block.

### Dynamic semantics

In an `if` expression other than `if let`:

1. The condition expression is evaluated.
2. Where the result is the success variant, the leading branch is evaluated, and on entry to it the success payload is bound to `v` where `-> v` is present.
3. Where the result is the failure variant, the `else` branch is evaluated, and on entry to it the failure payload is bound to `e` where `else.e` is present.

The value of an `if` expression is the value of the branch that is evaluated.

### Constraints

The condition expression of an `if` expression other than `if let` shall have a contract type.

Where an `if` expression carries an `else`, the two branches shall have a common type.

### Examples (informative)

```
// else-if chain
if parse(input) -> val {
    accept(val);
} else.err if check(err) -> recovered {
    accept(recovered);
} else.err2 {
    handle(err2);
}

// then / else value form
let y = if a > b then a else b;
let z = if find(x) -> v then v * 2 else 0;
let w = if find(x) -> v then v * 2 else.e { log(e); express 0; };
```

### 7.3.1 Pattern branching

#### Syntax

```
if_let_head  = [ label, ws ], "if", ws, "let", ws, pattern_body, ws,
               '=', ws, expression ;

if_let_block = if_let_head, ws, block
             | if_let_head, ws, if_lead, ws, else_branch ;
if_let_expr  = if_let_head, ws, if_lead, ws, else_value ;
```

#### Static semantics

An `if let` expression is an `if` expression that tests a pattern against an expression. The pattern introduces its names within the leading branch.

#### Dynamic semantics

1. The expression after `=` is evaluated.
2. The result is matched against the pattern.
3. If the pattern matches, the leading branch is evaluated, and on entry to it the objects of the bindings the pattern introduces are initialized.
4. If the pattern does not match, the `else` branch is evaluated, and on entry to it, where the `else` clause names a binding, the value that the pattern did not match is bound to that name.

#### Examples (informative)

```
if let verdict::Pass.{ config } = load_config(path) {
    apply(config);
} else {
    use_defaults();
}

// Binding the value that did not match
if let verdict::Pass.{ config } = load_config(path) {
    apply(config);
} else.bad {
    report(bad);
}

// Value-yielding
let result = if let verdict::Pass.{ v } = compute() then v * 2 else 0;

// Chaining
if let packet::data.{ payload } = pkt {
    process(payload);
} else if let packet::ack = pkt {
    acknowledge();
} else {
    reject();
}
```

## 7.4 Pattern matching

Each `match_alternative` of a `match` expression is an **alternative**.

### Syntax

```
match_expression  = [ label, ws ], "match", ws, expression, ws, '{',
                    { ws, match_alternative }, ws, '}' ;
match_alternative = pattern, [ ws, "if", ws, expression ], ws, '->',
                    ws, expression, ws, ';' ;
```

### Static semantics

The type of a `match` expression that no `express` targets is the common type of its alternatives.

The pattern of an alternative introduces its names within that alternative. The `if` and the expression that follow the pattern of an alternative are its **filter clause**. Within a filter clause, a name that a `wild` pattern introduces yields the reference the pattern yields, and every other name the pattern introduces designates the part the pattern binds to the name. An object expression that designates, through such a name, that part or a constituent object of it is storable at no programme point. For the rules of the clause on references and resource management, such a name is taken to be an object expression that designates that part from the matched expression.

### Dynamic semantics

The expression after `match` is evaluated, and the pattern of each alternative tested is applied to its result. Alternatives are tested in the order they appear in the token sequence. The first alternative whose pattern matches and whose filter clause, when present, yields the success variant is selected. Where the pattern of an alternative does not match, or its filter clause does not yield the success variant, control leaves the block of that alternative before the next alternative is tested. The objects of the bindings that the pattern of the selected alternative introduces are then initialized from the parts they bind, and the corresponding expression is evaluated; its value is the value of the `match` expression.

### Constraints

All alternatives shall have a common type.

The expression of a filter clause shall have a contract type.

Neither the evaluation of a filter clause nor an evaluation it reaches shall store into, or invalidate, a part of the matched object of its alternative, a constituent object of such a part, or an object of which such a part is a constituent object. Such a violation, where not detected during translation, can cause indeterminate state.

### 7.4.1 Exhaustiveness

#### Static semantics

An alternative that bears no filter clause covers the values its pattern matches. An alternative that bears a filter clause covers no value. A `match` expression is **exhaustive** where every value of the matched type is covered by at least one of its alternatives.

#### Constraints

A `match` expression shall be exhaustive.

Every alternative shall match a value that no preceding alternative covers.

#### Examples (informative)

```
// Range patterns
match ch {
    0x41..=0x5A -> upper();
    0x61..0x7B  -> lower();
    wild        -> other();
}

// Filter clause
match val {
    let x @ 0..=100 if x % 2 == 0 -> even_in_range(x);
    let x -> other(x);
}
```

### 7.4.2 Slice and string literal patterns

The `slice_pat`, `element_pat`, and `string_pat` productions are defined in the subclause on patterns and destructuring.

#### Static semantics

The **rest pattern** `...` within a slice pattern matches zero or more elements without binding them. The element patterns before it correspond in order to the first elements of the value, and those after it in order to its last elements. In a slice pattern without `...`, the element patterns correspond in order to the elements of the value.

A slice pattern without `...` is a **fixed-length slice pattern**, and matches only a value whose length equals the number of its element patterns. A slice pattern with `...` is a **variable-length slice pattern**, and matches only a value whose length is not less than the number of its element patterns other than the `...`.

The matched type of each element pattern is the element type of the matched type.

#### Dynamic semantics

Where the length of the value is one the slice pattern matches, each element of the value is compared against the corresponding element pattern, and the slice pattern matches where every element pattern matches. Where the length is not one the slice pattern matches, no element is compared.

#### Constraints

A slice pattern shall appear only where the matched type is an array type or a referent type `[U]`.

At most one `...` shall appear in a single slice pattern.

#### Examples (informative)

```
// String literal matching: HTTP method dispatch
match method {
    "GET"   -> handle_get();
    "POST"  -> handle_post();
    "PUT"   -> handle_put();
    // identifier pattern: type-preserving, cmd: &[ui1]
    let cmd -> unknown_method(cmd);
}

// Element-level patterns with ranges and bindings
match header {
    let [0x00, len @ 0x01..=0xFF] -> read_payload(len);
    [0x01, ?]                     -> keepalive();
    ?                             -> reject();
}

// Array matching
let packet: [ui1; 4] = receive();
match packet {
    let [0xDE, 0xAD, hi, lo] -> process(hi, lo);
    ?                        -> discard();
}

// Rest pattern: prefix matching
match binary {
    // ELF magic, any length ≥ 4
    [0x7F, 0x45, 0x4C, 0x46, ...] -> elf_binary();
    // MZ header
    [0x4D, 0x5A, ...]             -> pe_binary();
    ?                             -> unknown_format();
}

// wild on a non-ui1 slice: type-destroying
match signals { // signals: &[si4]
    [0, 0, 0]    -> idle();
    // identifier pattern: type-preserving, other: &[si4]
    let other    -> active(other);
    // alternatively, wild: type-destroying, raw: &[ui1]
    // wild(raw) -> dump(raw);
}

// Or-pattern within elements
match tag {
    [0x00 | 0x01, ?] -> version_zero_or_one();
    ?                -> other();
}

// Filter clause
match data {
    "OK" if status == 200 -> success();
    let resp              -> reject(resp);
}

// Refutable slice pattern in let: else required
let frame: &[ui1] = receive_frame();
let [magic, version, ...] = frame else { return; };

// Combining slice pattern in if let
if let [magic, version] = frame {
    if magic == 0xFE { process(version); }
} else {
    reject();
}
```

## 7.5 Loops

### 7.5.1 `while`

#### Syntax

```
while_head  = [ label, ws ], "while", ws,
              ( expression, [ ws, '->', ws, ident_pat ]
              | "let", ws, pattern_body, ws, '=', ws, expression ) ;
while_body  = block, [ ws, "and", ws, "then", ws, block ] ;
while_then  = "then", ws, expression,
              [ ws, "and", ws, "then", ws, expression ] ;
while_lead  = while_body | while_then ;

while_block = while_head, ws, while_body, [ ws, else_bind, ws, block ]
            | while_head, ws, while_then, ws, else_bind, ws, block ;
while_expr  = while_head, ws, while_lead, ws, else_value ;
```

#### Static semantics

The expression a `while` expression evaluates before each iteration is its **conditional initializer**.

The **loop body** of a `while` expression is the first `block` of its `while_body` or the first `expression` of its `while_then`, and its **continuation** is the second `block` or `expression` of that production, where one is present.

`-> v` introduces `v` within the loop body.

The `while let` form tests a pattern against an expression. The pattern introduces its names within the loop body.

#### Dynamic semantics

For the first form:

1. The conditional initializer is evaluated.
2. If the result is the failure variant, the loop exits after evaluating an `else` branch where one is present, and on entry to that branch the failure payload is bound to `e` where `else.e` is present.
3. The loop body is evaluated, and on entry to it the success payload is bound to `v` where `-> v` is present.
4. After the body completes or a `continue` within it that targets the `while` expression is evaluated, the continuation is evaluated where one is present.
5. Control returns to step 1.

For the `while let` form:

1. The conditional initializer is evaluated.
2. The result is matched against the pattern.
3. If the pattern does not match, the loop exits after evaluating an `else` branch where one is present, and on entry to that branch, where the `else` clause names a binding, the value that the pattern did not match is bound to that name.
4. The loop body is evaluated, and on entry to it the objects of the bindings the pattern introduces are initialized.
5. After the body completes or a `continue` within it that targets the `while` expression is evaluated, the continuation is evaluated where one is present.
6. Control returns to step 1.

A `continue` within the continuation that targets the `while` expression ends the continuation, and the conditional initializer is evaluated again.

Each evaluation of the conditional initializer begins a **round** of the evaluation of the `while` expression that performs it. The round ends where the continuation begins, where the conditional initializer is next evaluated, or where control leaves the `while` expression.

#### Constraints

The conditional initializer of a `while` expression in the first form shall be an expression of a contract type.

Where a `while` expression omits its `else` branch, every `break` that targets it shall supply `void`.

A `break` or a `continue` within the `else` branch or the conditional initializer of a `while` expression shall not target that `while` expression.

#### Examples (informative)

```
while running { body; }

// Counted iteration with a continuation
let mut i = 0;
while i < 10 {
    visit(i);
} and then {
    i += 1;
}

// Multiple step statements
let mut i = 0;
let mut j = 10;
while i < j {
    visit(i, j);
} and then {
    i += 1;
    j -= 1;
}

// after continue, the continuation is evaluated before the
// conditional initializer
let mut i = 0;
let mut skipped = 0;
while i < 10 {
    if i == 5 {
        skipped += 1;
        continue; // the continuation (i += 1) is still evaluated
    }
    visit(i);
} and then { i += 1; }

// Contract payload binding
while read_line(file) -> line {
    process(line);
}

// while let: contract type iteration
let mut iter = collection.iter();
while let verdict::Pass.{ x } = iter.next() {
    i#use(x);
}

// while let: anonymous struct destructuring
while let verdict::Pass.{ .{ key, value } } = map_iter.next_pair() {
    process(key, value);
}

// Combining while let with a continuation
let mut count = 0;
while let verdict::Pass.{ x } = iter.next() {
    process(x);
} and then {
    count += 1;
}

// Expression form
let mut k = 0;
let last = while k < 10 then visit(k) and then k += 1 else k;

// To retain the failure payload, assign it in the body before breaking:
let mut last_err: io_error = io_error::none;
loop {
    let line = contract read_line(file) else.err {
        last_err = err;
        break;
    };
    process(line);
}
log(last_err);

// translation-time condition: evaluated at translation; the point
// after it is unreachable when it yields the success variant
while xlat { express feature; } {
    poll();
}
```

### 7.5.2 `loop`

#### Syntax

```
loop_expression = [ label, ws ], "loop", ws, block ;
```

#### Static semantics

The **loop body** of a `loop` expression is its `block`.

#### Dynamic semantics

A `loop` expression evaluates its loop body repeatedly. It exits only by a control transfer that leaves it.

## 7.6 `return`

### Syntax

```
return_expression = "return", [ ws, expression ] ;
```

### Static semantics

In `return expr;`, the value of `expr` is the return value.

### Dynamic semantics

When `return` is evaluated:

1. If present, the return expression is evaluated.
2. Control returns to the invoker.

### Constraints

The type of `expr` in `return expr;` shall be assignable to the return type of the enclosing subroutine.

Bare `return;` shall not appear where the enclosing subroutine has a non-`void` return type.

A `return` expression shall not appear where the enclosing subroutine is declared `-> !`.

## 7.7 `break` and `continue`

### Syntax

```
break_expression    = "break", [ ws, '.', ws, identifier ],
                      [ ws, expression ] ;
continue_expression = "continue", [ ws, '.', ws, identifier ] ;
```

### Static semantics

A `break` or a `continue` without a label targets the innermost loop whose loop body or continuation encloses it. One with a label (`break.label`, `continue.label`) targets the loop that label names.

A `break` reachable from the loop it targets supplies to that loop the value of its expression, or `void` where it carries none. An `else` branch supplies to its loop the value it yields. The type of a loop is the common type of its `else` branch and of the expressions that the `break` expressions supplying values to it carry. The type is `void` where a `break` without an expression supplies to it, or where neither an `else` branch nor a `break` that carries an expression supplies to it.

### Dynamic semantics

A `break` evaluates its expression where it carries one, and terminates the loop it targets. A `continue` ends the current iteration of the loop it targets.

Where the value of the conditional initializer of a `while` expression ends the loop, the value of the loop is `void` where it has no `else` branch.

### Constraints

`break` without a label shall appear only within a loop body or the continuation of a `while` expression. `break` with a label shall name the label of a loop that encloses it.

The values a `break` supplies to the loop it targets, and the value of an `else` branch, shall have a common type.

`continue` shall appear only within a loop body or the continuation of a `while` expression. `continue` with a label shall name the label of a loop that encloses it.

### Examples (informative)

```
// break exits the loop
loop {
    if done { break; }
    work();
}

// Labelled continue in nested loops
outer: while outer_cond() -> a {
    while inner_cond() -> b {
        if reject(a, b) { continue.outer; }
        i#use(a, b);
    }
}
```

## 7.8 Express blocks

### Syntax

```
express_expression = "express", [ ws, '.', ws, identifier ], ws,
                     expression ;
```

### Static semantics

`express` targets a block or a labelled construct.

When no label is provided, the target is the innermost block containing the `express` expression. When a label is provided (`express.label value;`), the target is the enclosing labelled construct of the name.

A block whose value is yielded by `express` is an **express block**. An `express` reachable from the construct it targets supplies to that construct the value of its expression. The type of a construct targeted by `express` is the common type of the values supplied to it and of the value the construct yields of itself at a programme point reachable from it. A block that no `express` targets has type `void`. When control reaches the end of a block, the value the block yields there is `void`.

### Dynamic semantics

When an `express` expression is evaluated, its expression is evaluated, control exits the construct it targets, and the value of that construct is the value of that expression.

### Constraints

`express` without a label whose immediately enclosing block is a subroutine body shall not appear. `express.label` shall name a labelled construct, other than a loop, that encloses the `express` expression.

The values the `express` expressions targeting one construct supply shall have a common type. Where the construct yields a value of itself at a programme point reachable from it, that value shall have that type also.

## 7.9 Labelled constructs

A **labelled construct** is a block, an `if` expression, a `match` expression, or a loop, prefixed with a **label** of the form `name:`.

### Syntax

```
label           = identifier, ws, ':' ;
labelled_block  = label, ws, block ;
```

### Static semantics

A label is visible only within the construct it prefixes, and only `break`, `continue`, and `express` name it, to target that construct.

An inner label hides an outer label of the same name throughout the inner scope.

### Examples (informative)

```
let result = outer: {
    let x = compute();
    if x < 0 { express.outer 0; }
    express x * 2;
};

let mut iterator = collection.iter();
search: while iterator.next() -> item {
    let mut subs = item.children().iter();
    while subs.next() -> sub {
        if sub.matches(query) {
            result = sub;
            break.search;
        }
    }
}
```

## 7.10 Divergence primitive

`trap()` invokes a subroutine that the implementation provides, of type `fn() -> !`.

### Syntax

```
trap_invocation   = "trap", ws, '(', ws, ')' ;
trap_handler_decl = "trap", ws, block ;
```

### Dynamic semantics

When `trap()` is evaluated:

&mdash; If a `trap` handler is declared in the translation unit of the invocation, that handler is invoked.

&mdash; If no handler is declared there, the default behaviour is performed.

### Implementation requirements

The default behaviour shall diverge.

### Implementation defined

The default behaviour is implementation defined.

### 7.10.1 `trap` handler

#### Constraints

The handler shall be a diverging expression.

Multiple handlers within one translation unit shall not appear.

#### Examples (informative)

```
trap {
    gpio_led_on(led_red);

    loop {
        airside { *$volatile gpio_led ^= 1; }
        spin_delay(500000);
    }
}

// Re-entry guard
static mut entered: ui1 = 0;

trap {
    airside {
        if *&atomic entered != 0 { loop {} }
        *&atomic mut entered = 1;
    }

    cleanup();
    loop {}
}
```

### 7.10.2 `trap` in translation-time evaluation

#### Dynamic semantics

A `trap` expression reached during translation-time evaluation is a translation failure. The translation failure supersedes any execution-time trap handler that the translation unit declares.

#### Examples (informative)

```
// Translation-time check: aborts translation on an unsupported
// programme machine
xlat {
    if cellbits::prog != 8 {
        trap(); // translation failure: unsupported cell width
    }
};

// `trap` on the verdict::Fail path of a contract test within xlat
const ?: void = xlat {
    match key'bound(ord) {
        verdict::Pass -> { };
        verdict::Fail -> { trap(); };
        // translation failure when key does not satisfy ord
    }
};

// `trap` in the `else` branch of a `xlat?` conditional
fn platform_init() {
    xlat? {
        init_at_translation();
    } else {
        // not selected in an evaluation on the translation machine
        trap();
    }
}
```

## 7.11 Control transfers and diverging expressions

### Static semantics

An expression is a **control transfer** where it is of one of the following forms:

&mdash; `return`, with or without a value.

&mdash; `break`, with or without a label or value.

&mdash; `continue`, with or without a label.

&mdash; `express`.

Each of the following is itself a control transfer where it is not a diverging expression:

&mdash; A block, the programme point at the end of which is not reachable from the block, and within which no control transfer reachable from the block targets it.

&mdash; An `if` or `match` expression every branch or alternative of which is a diverging expression or a control transfer, and within which no control transfer reachable from the expression targets it.

&mdash; An `airside` block whose body is a control transfer or a diverging expression.

&mdash; A `loop` expression, or a `while` expression whose `else` branch is a control transfer or a diverging expression, from which no `break` targeting it is reachable.

An expression is a **diverging expression** where it is of one of the following forms:

&mdash; An invocation of `trap`.

&mdash; A `loop` expression from which none of the following is reachable: a `return`, a `?` expression, a `break` targeting it or an enclosing loop, a `continue` targeting an enclosing loop, or an `express` targeting an enclosing block or labelled construct.

&mdash; An invocation whose leading expression has a subroutine pointer type whose return is `!`, or a method invocation that resolves to a method declared `-> !`.

&mdash; A block, the programme point at the end of which is not reachable from the block, and from which no `return` and no `?` expression is reachable, and within which every `break`, `continue`, or `express` reachable from the block targets a construct within it.

&mdash; An `airside` block whose body is a diverging expression.

A control transfer and a diverging expression each yield no value. In any context that requires an expression of type `T`, either is accepted in place of an expression of type `T`.

A construct whose type is the common type of a set of expressions, as the clause on types defines the common type, is itself a diverging expression where all of the following hold:

&mdash; That set is not empty, and every expression of it is a diverging expression.

&mdash; No `return` and no `?` expression is reachable from the construct.

&mdash; Every `break` and every `express` reachable from the construct targets a construct within it.

&mdash; Every `continue` reachable from the construct targets it or a construct within it.

&mdash; The construct yields no value of itself at a programme point reachable from it.

### Constraints

A `break`, a `continue`, or an `express` shall target a construct that is, or lies within, the innermost of the following that encloses it:

&mdash; A subroutine body.

&mdash; A `trap` handler.

&mdash; A `xlat` block.

&mdash; A `const` block.

&mdash; The initializer of a `const` declaration or of a `static` declaration.

&mdash; A default-value expression.

&mdash; The expression of an associated constant.

&mdash; The expression of an inline expression operand of an `instruct` block.

&mdash; A dependence argument.

A `return` or a `?` expression shall appear only where the innermost of those constructs that encloses it is a subroutine body.

### Implementation requirements

The implementation shall place an implicit `trap` expression so that an execution context that continues after the evaluation of a diverging expression evaluates it next. No implicit `trap` is placed for an implicit `trap`. The implicit `trap` is subject to the rules defined in the subclause on the divergence primitive.

Where the leading expression of an invocation expression has a subroutine pointer type whose return is `!`, and either that leading expression names no subroutine or the invocation is an external subroutine invocation, as defined in the subclause on σ operations, the implementation shall preserve the invocation as an invocation instruction in the opaque code. It shall replace that instruction neither with a copy of the invoked body nor with a jump that discards the return site. The implicit `trap` defined above shall be placed immediately following that instruction in the opaque code.

### Examples (informative)

```
const true:  verdict[void, void] = verdict::Pass.{ void };
const false: verdict[void, void] = verdict::Fail.{ void };

// A diverging branch contributes no type. The common type is si4.
let x: si4 = if cond then 42 else trap();

// `-> !` invocation is diverging.
fn fail(msg: &[ui1]) -> ! { trap(); }

let y: si4 = match parse(input) {
    let verdict::Pass.{ val } -> val;
    verdict::Fail             -> fail("parse failed");
};

// The end of this block is unreachable and no control transfer
// leaves it, so the block is diverging.
let z: si4 = {
    log("diverging");
    trap();
};

// Nothing reachable from this `loop` leaves it, so it is diverging.
airside fn halt() -> ! {
    loop { instruct { wfi } }
}

// A `break` excluded by a const condition is unreachable.
fn spin() -> ! {
    while true {
        if false { break; }
        airside { instruct { wfi } }
    }
}

// A `break` reachable by an execution-time condition denies
// divergence, and the point after it is reachable.
while true {
    if shutdown() { break; }
    poll();
}
cleanup();
```
