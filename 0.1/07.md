# §7. Statements and control flow

This clause defines the statements and the control flow of the Kurt programming language: blocks, contract types, branching, pattern matching, loops, control transfers, and the divergence primitive.

Every branching construct of this clause that branches upon a value requires the condition or operand to have a contract type. The forms that branch upon a pattern, `if let` and `while let`, accept an expression of any type. Control transfers and diverging expressions are defined in the subclause on control transfers and diverging expressions.

## 7.1 Blocks and statements

### Syntax

```
block            = '{', ws, { block_item, ws }, '}' ;
block_item       = ( { item_prefix, ws }, local_item )
                 | let_decl | statement ;

statement        = block_expression
                 | [ plain_expression ], ';' ;

block_expression = block | labelled_block | if_block | if_let_block
                 | match_expression | while_block | loop_expression
                 | extraction_block | airside_block | xlat_block
                 | xlat_cond_block | asm_block ;
plain_expression = ? an expression that is not a block_expression ? ;
```

### Static semantics

A **block** is a sequence of block items delimited by curly brackets. The items of a block are carried out in order. A declaration among them takes effect throughout the block, as defined in the clause on declarations.

A statement specifies an action to be performed. Except as indicated, statements are executed in sequence. The production of each declaration and of each statement fixes whether a semicolon (`;`) terminates it. A statement does not yield a value unless it contains `express` or is part of a value-yielding construct.

A **block expression** is an expression of one of the forms the `block_expression` production lists. Every other expression is a **plain expression**.

A statement that is a plain expression evaluates the expression and discards the result. A statement whose expression is omitted performs no operations.

Where a block expression stands as a statement, it constitutes the whole of that statement, and what follows it begins a new statement.

## 7.2 Contract types

A **contract type** partitions its values into a success side and a failure side. Each side may carry a payload. A declared type is a contract type only where a `contract` declaration introduces it. The built-in `verdict.[T, F]` is a contract type as defined in the clause on types. The `?` operator propagates a contract value, and may be combined with `!` for polarity inversion. It is defined in the clause on expressions.

### Syntax

```
contract_decl      = [ "pub", ws ], "contract", [ ws, '!' ], ws,
                     identifier, [ ws, generic_clause ], ws,
                     '{', ws, contract_variant, ws, ',',
                     ws, contract_variant, ws, [ ',', ws ], '}',
                     ( [ ws, with_single ], ';' | ws, with_curly ) ;

contract_variant   = identifier, ws, '(', ws, type, ws, ')',
                     [ ws, '=', ws, variant_value ] ;

contract_construct = single_path, ws, '(', ws, expression, ws, ')' ;
inv_clause         = 'inv', ws, '->', ws, type ;
```

The `inv` clause appears as a `with` item on a `contract` declaration.

### Static semantics

A `contract` declaration introduces a contract type of two variants, each holding a payload of the type its declaration parenthesizes. The payload of a contract variant is public. A contract type is a variant type, as defined in the clause on declarations.

In a `contract` declaration, the `wild` variant is the failure (falsy) side and the other variant the success (truthy) side. In a `contract!` declaration, the polarity is inverted.

A **contract construction** yields a value of the variant that its path names, holding the value of the enclosed expression as the payload. A contract variant is matched by the contract variant pattern defined in the clause on declarations.

#### Inverted pairs

A contract type may declare an **inverted pair** using the `inv` clause, whereupon `!` applied to a value of the declaring type yields a value of the named type. Where `A` declares `with inv -> B`, `B` declares `with inv -> A`.

Both types may be declared `contract`, both `contract!`, or one of each.

### Constraints

Exactly one variant of a `contract` declaration shall bear a `wild` discriminant.

An `inv` declaration without the symmetric back-declaration on the named type shall not appear.

A contract type shall not satisfy any arithmetic bound.

The success payload type named by the `inv` clause shall equal the failure payload type of the declaring type, and vice versa.

### Examples (informative)

```
// 1. contract without inverted pair
//    wild = failure. No ! operator.
contract toggle {
    on(void),
    off(void) = wild
};

// 2. contract! without inverted pair
//    Polarity inverted: wild = success.
contract! http_result {
    ok(response) = wild,
    error(http_error) = 404
};

// 3. contract ↔ contract inverted pair
//    Polarity is inverted by placing wild on a different variant
//    in each declaration.
contract switch.[T] {
    on(T), off(void) = wild
} with inv -> switch_inv.[T];

contract switch_inv.[T] {
    on(T) = wild, off(void)
} with inv -> switch.[T];

// 4. contract ↔ contract! inverted pair
//    Both declarations have identical structure. Polarity is
//    inverted by contract! rather than by rearranging wild.
contract acquired.[T] {
    have(T),
    missing(void) = wild
} with inv -> lost.[T];

contract! lost.[T] {
    have(T),
    missing(void) = wild
} with inv -> acquired.[T];

// 5a. Self-inverse (generic)
//     The inverted pair is the type itself with type arguments
//     swapped. !result.[T, F] yields result.[F, T].
contract result.[T, F] {
    pass(T) = 1,
    fail(F) = wild(0)
} with {
    inv -> selftype.[F, T],
    discrim(ui1)
}

// 5b. Self-inverse (non-generic)
//     inv -> truthy_bool names the type itself directly.
//     Falsy-by-declaration: only the explicit variant is falsy.
//     All other discriminant values are truthy.
contract! truthy_bool {
    true(void) = wild(1),
    false(void) = 0
} with {
    inv -> truthy_bool,
    discrim(ui1)
}
```

### Notes (informative)

In pattern 2, the discriminant value `404` matches the `error` variant (failure/falsy). All other discriminant values are covered by `wild` — the `ok` variant (success/truthy). When used with `if`, `?`, and contract extraction, the success and failure sides are determined by the `contract!` polarity.

Patterns 3 and 4 achieve the same result — polarity inversion via `!` — through different structural means. In pattern 3, the two declarations have different structures (`wild` is on different variants), so both are declared `contract`. In pattern 4, the two declarations have identical structures, so one is declared `contract!` to invert the interpretation.

Pattern 5a is the self-inverse case. `inv -> selftype.[F, T]` permutes the generic arguments. Where `T == F`, `!` becomes a value-level toggle. The built-in `verdict.[T, F]` uses this pattern. Pattern 5b is the non-generic variant: `inv -> truthy_bool` names the type directly, and `contract!` makes `wild` the success side.

Where `!v` has a type, so does `!!v`, by the symmetry the `inv` clause requires. `!!v` yields the original variant with the original payload and a canonical discriminant.

### 7.2.1 Polarity inversion

#### Static semantics

`!expr`, where `expr` has a contract type `T` and `T` declares `inv -> U`, yields a value of type `U`: the success and failure variants are exchanged, and the payload is preserved unchanged.

The discriminant of the yielded value is the declared discriminant of the variant it takes, where that variant is explicit. Where the variant is `wild(V)`, the discriminant is `V`. Where the variant is `wild` without a canonical value, the discriminant is the value the automatic discriminant assignment algorithm assigns, as defined in the clause on declarations.

#### Examples (informative)

```
// For verdict.[void, void], verdict has
//   with inv -> selftype.[F, T],
// so !verdict.[void, void] yields verdict.[void, void].
let x = !verdict.[void, void]::Pass(void); // x = Fail(void)
let y = !verdict.[void, void]::Fail(void); // y = Pass(void)

// Inverted pair
contract switch.[T] {
    on(T), off(void) = wild
} with inv -> switch_inv.[T];

contract switch_inv.[T] {
    on(T) = wild, off(void)
} with inv -> switch.[T];

let s:    switch.[si4]     = switch::on(1);
let inv:  switch_inv.[si4] = !s;   // result type is switch_inv.[si4]
let s2:   switch.[si4]     = !inv; // result type is switch.[si4]

// Inverted pair — mixed polarity
contract acquired.[T] {
    have(T), missing(void) = wild
} with inv -> lost.[T];

contract! lost.[T] {
    have(T), missing(void) = wild
} with inv -> acquired.[T];

// verdict: inverted pair is selftype.[F, T]
// !verdict.[T, F] yields verdict.[F, T]
let r:     verdict.[si4, &[ui1]] = verdict::Pass(42);
let inv_r: verdict.[&[ui1], si4] = !r;

// polarity inversion in control-flow position
if !result -> err { handle(err); }
let err = contract !result else.val { recover(val); };
```

### 7.2.2 Logical operators

`and` (short-circuit AND), `or` (short-circuit OR), and `xor` (XOR) combine values of contract types. The result type is `verdict.[void, void]`.

#### Syntax

```
logical_expr = expression, ws, logical_op, ws, expression ;
logical_op   = "and" | "or" | "xor" ;
```

#### Static semantics

`a and b` — if `a` is the failure variant, the result is `verdict::Fail(void)` and `b` is not evaluated. Otherwise, the result is `verdict::Pass(void)` if `b` is the success variant and `verdict::Fail(void)` if `b` is the failure variant.

`a or b` — if `a` is the success variant, the result is `verdict::Pass(void)` and `b` is not evaluated. Otherwise, the result is `verdict::Pass(void)` if `b` is the success variant and `verdict::Fail(void)` if `b` is the failure variant.

`a xor b` — both operands are evaluated. The result is `verdict::Pass(void)` if exactly one operand is the success variant and `verdict::Fail(void)` otherwise.

#### Constraints

Each operand shall be of a contract type.

#### Examples (informative)

```
// The result of and, or, and xor is verdict.[void, void].
let ok  = a > 0 and b > 0;
let any = x == 1 or y == 1;
let one = x == 1 xor y == 1;

contract toggle { on(void), off(void) = wild };
let both        = t1 and t2; // toggle and toggle → verdict
let either      = t1 or  t2; // toggle or  toggle → verdict
let exactly_one = t1 xor t2; // toggle xor toggle → verdict

contract result { ok(si4), err(void) = wild(0) };
let valid  = compute() and bounds_check();
let any_ok = primary() or  backup();
// result and verdict → verdict
// result or  result  → verdict
```

### 7.2.3 Contract extraction

#### Syntax

```
extraction_block = "contract", ws, expression, ws, else_bind, ws, block ;
extraction_expr  = "contract", ws, expression, ws, else_bind,
                   ws, plain_expression ;
```

#### Static semantics

`contract expr else fallback` is an expression. Its type is the success payload type of `expr`.

#### Dynamic semantics

When `contract expr else [.id] fallback` is evaluated:

1. `expr` is evaluated.
2. If the result is the success variant, its payload is the result of the whole expression. `fallback` is not evaluated.
3. If the result is the failure variant: when `else` names a binding (`else.id`), the failure variant’s payload is bound to `id`, in scope only within `fallback`. `fallback` is evaluated. Its value is the result of the whole expression.

#### Constraints

The type of `expr` shall be a contract type.

`fallback` shall be a control transfer or a diverging expression, or its type shall be the success payload type of `expr` or a type for which this specification defines an implicit cast to it. Control transfers and diverging expressions are defined in the subclause on control transfers and diverging expressions.

#### Examples (informative)

```
// Diverging fallback
let v = contract compute() else { return; };
let v = contract compute() else.err { return err; };

// Value fallback
let v = contract compute() else default;
let v = contract compute() else.err recover(err);
let v = contract compute() else.err { log(err); express recover(err); };

// Destructuring the success payload
let .{ x, y } = contract get_point() else { return; };

// Assignment to an existing object
let mut result: si4;
result = contract compute() else { return; };

// Deferred initialization
let value: si4;
value = contract compute() else fallback;

// Polarity inversion
let e = contract !contract_value else.v { recover(v); return; };
```

## 7.3 Branching upon a contract

An `if` expression other than `if let` takes a value of a contract type.

### Syntax

```
if_head     = [ label, ws ], "if", ws, expression,
              [ ws, '->', ws, identifier ] ;
if_lead     = block | "then", ws, expression ;

if_block    = if_head, ws, block
            | if_head, ws, if_lead, ws, else_branch ;
if_expr     = if_head, ws, if_lead, ws, else_value ;

else_branch = else_bind, ws, ( block | if_block | if_let_block ) ;
else_value  = else_bind, ws, plain_expression ;
```

### Static semantics

The condition expression is evaluated. Where the result is the success variant, the `if` block executes; where it is the failure variant, the `else` branch executes. The value of an `if` expression is the value of the branch that executes, and its type is the common type of its branches.

`-> v` binds the success payload to `v` and introduces `v` within the `if` block.

`else.e` binds the failure payload to `e` and introduces `e` within the `else` branch.

Where the `else` branch is omitted, the expression is equivalent to one whose `else` branch is an empty block.

### Constraints

The condition expression of an `if` expression other than `if let` shall have a contract type.

Where an `if` expression or an `if let` expression carries an `else`, the two branches shall have a common type, whether each branch is a block or an expression.

A name introduced by `->` shall be referred to only within the block or expression that follows it.

### 7.3.1 `else if` chains

#### Static semantics

An `if` expression, together with the expressions chained to it by `else`, is a **chain**. A chain is one scope, extending from its leading `if` to the end of its final branch.

#### Examples (informative)

```
if parse(input) -> val {
    accept(val);
} else.err if check(err) -> recovered {
    accept(recovered);
} else.err2 {
    handle(err2);
}
```

### 7.3.2 `then` / `else` value form

#### Static semantics

`then` / `else` is a conditional expression in which each branch is a single expression that yields a value.

#### Examples (informative)

```
let y = if a > b then a else b;
let z = if find(x) -> v then v * 2 else 0;
let w = if find(x) -> v then v * 2 else.e { log(e); express 0; };
```

### 7.3.3 Refutable pattern branching

#### Syntax

```
if_let_head  = [ label, ws ], "if", ws, "let", ws, pattern, ws,
               '=', ws, expression ;

if_let_block = if_let_head, ws, block
             | if_let_head, ws, if_lead, ws, else_branch ;
if_let_expr  = if_let_head, ws, if_lead, ws, else_value ;
```

#### Static semantics

`if let` tests a refutable pattern against an expression. Where the pattern matches, the bound names are available in the `if` block. Where the pattern does not match, the `else` branch executes. Where the `else` branch is omitted, the expression is equivalent to one whose `else` branch is an empty block. The value of an `if let` expression is the value of the branch that executes, and its type is the common type of its branches. Where the `else` clause names a binding (`else.e`), the value that the pattern did not match is bound to the name within the branch.

#### Dynamic semantics

1. The initializer expression is evaluated.
2. The result is matched against the pattern.
3. If the pattern matches, all bound names are initialized and the `if` block executes.
4. If the pattern does not match, the `else` branch executes. No name introduced by the pattern is bound.

#### Constraints

A name introduced by the pattern shall be referred to only within the block or expression that follows the initializer expression.

#### Examples (informative)

```
if let verdict::Pass(config) = load_config(path) {
    apply(config);
} else {
    use_defaults();
}

// Binding the value that did not match
if let verdict::Pass(config) = load_config(path) {
    apply(config);
} else.bad {
    report(bad);
}

// Value-yielding
let result = if let verdict::Pass(v) = compute() then v * 2 else 0;

// Chaining
if let packet::data.{ payload } = packet {
    process(payload);
} else if let packet::ack = packet {
    acknowledge();
} else {
    reject();
}
```

## 7.4 Pattern matching

`match` performs exhaustive pattern matching on a value. The expression following the `match` keyword is the **matched expression**. Each pattern–expression pair within the curly brackets is an **alternative**.

### Syntax

```
match_expression  = [ label, ws ], "match", ws, expression, ws, '{',
                    { ws, match_alternative }, ws, '}' ;
match_alternative = pattern, [ ws, "if", ws, expression ], ws, '->',
                    ws, expression, ws, ';' ;
```

### Static semantics

A `match` expression is a value expression, and its type is the common type of its alternatives. The pattern forms, their syntax, their destructuring rules, and their refutability are defined in the clause on declarations.

A **guard clause** — `if` followed by an expression, after the pattern — restricts matching. The alternative is selected only when the pattern matches and the guard yields the success variant. Guard expressions may reference bindings introduced by the pattern.

### Dynamic semantics

Alternatives are tested in the order they appear in the token sequence. The first alternative whose pattern matches and whose guard, when present, yields the success variant is selected. The corresponding expression is evaluated and its value is the value of the `match` expression.

### Constraints

All alternatives shall have a common type.

The expression of a guard clause shall have a contract type.

### 7.4.1 Exhaustiveness

#### Static semantics

An alternative that bears no guard clause covers the values its pattern matches. An alternative that bears a guard clause covers no value. A `match` expression is **exhaustive** where every value of the matched type is covered by at least one of its alternatives.

#### Constraints

A `match` expression shall be exhaustive.

Every alternative shall match a value that no preceding alternative covers.

#### Examples (informative)

```
// Enum variant
match r {
    let verdict::Pass(val) -> accept(val);
    let verdict::Fail(err) -> handle(err);
}

// Struct destructuring with field ignore
match config {
    let config.{ .timeout, ... } -> timeout;
}

// Range patterns
match ch {
    0x41..=0x5A -> upper();
    0x61..0x7B  -> lower();
    wild        -> other();
}

// Binding pattern with @
match status_code {
    let code @ 400..=499 -> log_client_error(code);
    let code @ 500..=599 -> log_server_error(code);
    wild                 -> ok();
}

// Struct field sub-patterns
match point {
    let point.{ .x @ 0..=100, .y }     -> plot(x, y);
    let point.{ a = .x @ 0..=100, .y } -> plot(a, y);
    wild                               -> fallback();
}

// Identifier pattern
match colour {
    colour::red  -> warm();
    let rest     -> cool(rest);
}

// Or-pattern
match colour {
    colour::red | colour::green | colour::blue -> primary();
    wild                                       -> non_primary();
}

// Nested patterns
match r {
    let verdict::Pass(res::yes.{ v }) -> accept(v);
    verdict::Pass(res::no)            -> handle_absent();
    verdict::Pass(wild)               -> handle_unknown();
    let verdict::Fail(e)              -> handle_err(e);
}

// Guard clause
match val {
    let x @ 0..=100 if x % 2 == 0 -> even_in_range(x);
    let x -> other(x);
}
```

### 7.4.2 Slice and string literal patterns

#### Syntax

The `slice_pat`, `element_pat`, and `string_pat` productions are defined in the subclause on patterns and destructuring.

#### Static semantics

A slice pattern matches a value of type `&[T]`, `&[T; N]`, or `[T; N]` by comparing the elements of the value against the element patterns.

The **rest pattern** `...` within a slice pattern matches zero or more elements without binding them. It may appear at the beginning, the end, or between element patterns:

— `[p0, p1, ...]` — matches a slice whose first two elements match `p0` and `p1`, ignoring the remaining elements.

— `[..., p0, p1]` — matches a slice whose last two elements match `p0` and `p1`, ignoring the preceding elements.

— `[p0, ..., p1]` — matches a slice whose first element matches `p0` and whose last element matches `p1`, ignoring the elements in between.

A slice pattern without `...` is a **fixed-length slice pattern**, and matches only a value whose length equals the number of its element patterns. A slice pattern with `...` is a **variable-length slice pattern**, and matches only a value whose length is not less than the number of its element patterns other than the `...`.

#### Dynamic semantics

Where the length of the value is one the slice pattern matches, each element of the value is compared against the corresponding element pattern in leading-to-following order, and the slice pattern matches where every element pattern matches. Where the length is not one the slice pattern matches, no element is compared.

Once an element pattern fails, subsequent elements need not be tested.

#### Constraints

— A slice pattern shall appear only when the matched type is a slice reference (`&[T]`), a reference to an array (`&[T; N]`), or an array value (`[T; N]`).

— Each element pattern within a slice pattern shall be valid for the element type `T`.

— At most one `...` shall appear in a single slice pattern.

#### Examples (informative)

```
// String literal matching — HTTP method dispatch
match method {
    "GET"   -> handle_get();
    "POST"  -> handle_post();
    "PUT"   -> handle_put();
    // identifier pattern: type-preserving, cmd: &[ui1]
    let cmd -> unknown_method(cmd);
}

// Equivalent explicit cell pattern
match method {
    [0x47, 0x45, 0x54] -> handle_get(); // “GET”
    let cmd            -> unknown_method(cmd);
}

// Element-level patterns with ranges and bindings
match header {
    let [0x00, len @ 0x01..=0xFF] -> read_payload(len);
    [0x01, ?]                     -> keepalive();
    ?                             -> reject();
}

// Array matching
let packet: [ui1; 4] = receive();
match packet {
    let [0xDE, 0xAD, hi, lo] -> process(hi, lo);
    ?                        -> discard();
}

// Rest pattern — prefix matching
match binary {
    // ELF magic, any length ≥ 4
    [0x7F, 0x45, 0x4C, 0x46, ...] -> elf_binary();
    // MZ header
    [0x4D, 0x5A, ...]             -> pe_binary();
    ?                             -> unknown_format();
}

// Rest pattern — suffix matching
match path {
    [..., 0x2F] -> directory(); // ends with ‘/’
    ?           -> file();
}

// Rest pattern — both ends
match frame {
    [0x7E, ..., 0x7E] -> valid_frame(); // HDLC-like framing
    ?                 -> invalid_frame();
}

// wild on a non-ui1 slice — type-destroying
match signals { // signals: &[si4]
    [0, 0, 0]    -> idle();
    // identifier pattern: type-preserving, other: &[si4]
    let other    -> active(other);
    // alternatively, wild: type-destroying, raw: &[ui1]
    // wild(raw) -> dump(raw)
}

// Or-pattern within elements
match tag {
    [0x00 | 0x01, ?] -> version_zero_or_one();
    ?                -> other();
}

// Guard clause
match data {
    "OK" if status == 200 -> success();
    let resp              -> fallback(resp);
}

// Refutable slice pattern in let — else required
let [magic, version, ...] = packet else { return; };

// Combining slice pattern in if let
if let [magic, version] = packet {
    if magic == 0xFE { process(version); }
} else {
    reject();
}
```

## 7.5 Loops

### 7.5.1 `while`

#### Syntax

```
while_head  = [ label, ws ], "while", ws,
              ( expression, [ ws, '->', ws, identifier ]
              | "let", ws, pattern, ws, '=', ws, expression ) ;
while_body  = block, [ ws, "then", ws, block ] ;

while_block = while_head, ws, while_body, [ ws, else_bind, ws, block ] ;
while_expr  = while_head, ws, while_body, ws, else_value ;
```

#### Static semantics

The expression a `while` expression evaluates before each iteration is its **conditional initializer**: in the first form it yields a value of a contract type and may bind the success payload, and in the `while let` form it yields a value matched against a pattern that may bind names. In the first form, if it yields the success variant the body executes, and if it yields the failure variant the loop exits.

`while cond { body }` is a diverging expression in the cases defined in the subclause on control transfers and diverging expressions. The optional `else` branch of a `while` expression is evaluated where the conditional initializer yields the failure variant, and supplies the value of the expression upon the exit. Where the branch is omitted, the expression is equivalent to one whose `else` branch is an empty block. Where the `else` clause names a binding (`else.e`), the value that ended the loop is bound to the name within the branch: in the first form the failure payload of the conditional initializer, and in the `while let` form the value that the pattern did not match.

The `then` block is part of the iteration. A `break` within it targets the loop, and the value of the block itself is discarded. A `break` within the `else` branch targets the nearest loop enclosing the `while` expression, and the value the branch yields is the value of the `while` expression upon the exit. Where the branch is a block, an `express` that targets it supplies that value; where it is a plain expression, its own value is supplied.

Where it is not a diverging expression, its type is the common type of the values supplied to it, as defined in the subclause on `break` and `continue`.

The optional `-> v` clause binds the success payload to `v` within the body block for the iteration. The binding is established again on each iteration from the most recent evaluation of the conditional initializer.

The `while let` form tests a refutable pattern against an expression on each iteration. When the pattern matches, the bound names are available in the loop body, established again each iteration from that iteration’s match. When the pattern does not match, the loop exits.

#### Dynamic semantics

For the contract condition form:

1. The conditional initializer is evaluated.
2. If the result is the failure variant, the loop exits after evaluating an `else` branch where one is present. The `then` block does not execute.
3. If `-> v` is present, the payload is bound to `v`. The body executes.
4. After the body completes or `continue` is executed, the `then` block executes where one is present.
5. Control returns to step 1.

For the `while let` form:

1. The conditional initializer is evaluated.
2. The result is matched against the pattern.
3. If the pattern does not match, the loop exits after evaluating an `else` branch where one is present, and no names are bound.
4. All bound names are initialized and the loop body executes.
5. After the body completes or `continue` is executed, the `then` block executes where one is present.
6. Control returns to step 1.

#### Constraints

The conditional initializer of a `while` expression in the first form shall be an expression of a contract type.

#### Examples (informative)

```
while running { body; }

// Counted iteration with then block
let mut i = 0;
while i < 10 {
    visit(i);
} then {
    i += 1;
}

// Multiple step statements
let mut i = 0;
let mut j = 10;
while i < j {
    visit(i, j);
} then {
    i += 1;
    j -= 1;
}

// Contract payload binding
while read_line(file) -> line {
    process(line);
}

// while let — contract type iteration
let mut iter = collection.iter();
while let verdict::Pass(x) = iter.next() {
    i#use(x);
}

// while let — tuple destructuring
while let verdict::Pass(.{ key, value }) = map_iter.next_pair() {
    process(key, value);
}

// while let — nested pattern
while let verdict::Pass(.{ id, data }) = stream.read_packet() {
    dispatch(id, data);
}

// Combining while let with then
let mut count = 0;
while let verdict::Pass(x) = iter.next() {
    process(x);
} then {
    count += 1;
}

// To retain the failure payload, assign it in the body before breaking:
let mut last_err: io_error = io_error::none;
loop {
    let line = contract read_line(file) else.err {
        last_err = err;
        break;
    };
    process(line);
}
log(last_err);

// const binding as condition — the loop is a diverging expression;
// the point after it is unreachable
const enabled: verdict.[void, void] = verdict::Pass(void);
while enabled {
    poll();
}

// translation-time condition — evaluated at translation, diverges
// when it yields the success variant
while xlat { express feature; } {
    poll();
}

// execution-time condition — not a diverging expression by virtue of
// its condition, whatever value the condition takes at execution time
while running {
    poll();
}
```

### 7.5.2 `loop`

#### Syntax

```
loop_expression = [ label, ws ], "loop", ws, block ;
```

#### Static semantics

`loop` with a given block carries out that block repeatedly, as `while verdict.[void, void]::Pass(void)` with the block does. A `loop` block is a diverging expression in the cases defined in the subclause on control transfers and diverging expressions. Where it is not a diverging expression, its type is the common type of the values supplied to it, as defined in the subclause on `break` and `continue`.

#### Dynamic semantics

Control leaves the loop through a `break` or a `return` that targets it or encloses it, or through a diverging expression.

### 7.5.3 `then` block

#### Static semantics

The optional `then` block on a `while` expression is evaluated after each iteration of the body, before the condition is evaluated again. On a `while` expression the `then` keyword shall be followed by a block.

#### Dynamic semantics

A `while` expression with a `then` block is defined by the following structural equivalence:

```
while <cond> { <body> } then { <step> }

// is equivalent to:

while <cond> {
    { <body> } // continue exits this inner block
    <step>
}
```

The inner block around `<body>` is the target of an unlabelled `continue`. A `continue` exits that inner block, and the step statements then execute before the condition is evaluated again. A `break` exits the entire loop, and the step statements do not execute.

#### Examples (informative)

```
// continue executes the then block before re-checking the condition
let mut i = 0;
let mut skipped = 0;
while i < 10 {
    if i == 5 {
        skipped += 1;
        continue; // then block (i += 1) still runs
    }
    visit(i);
} then { i += 1; }
```

## 7.6 `return`

A `return` expression terminates execution of the enclosing subroutine and yields its return value.

### Syntax

```
return_expression = "return", [ ws, expression ] ;
```

### Static semantics

`return expr;` evaluates `expr` and terminates the enclosing subroutine. The value of `expr` is the return value of the subroutine invocation expression at the invocation site.

A `return` expression is a control transfer.

### Dynamic semantics

When `return` is executed:

1. If present, the return expression is evaluated.
2. The automatic objects whose scope is between the `return` site and the subroutine boundary are destroyed in reverse declaration order, as defined in the clause on semantics.
3. Control returns to the invoker. The return value is made available as the result of the invocation expression.

Parameter bindings are destroyed after all local bindings, in reverse declaration order, as defined in the clause on semantics.

### Constraints

The type of `expr` in `return expr;` shall be assignable to the subroutine’s declared return type.

Bare `return;` in a subroutine with a non-`void` return type shall not appear.

A subroutine declared `-> !` shall not contain a `return` expression.

## 7.7 `break` and `continue`

### Syntax

```
break_expression    = "break", [ ws, '.', ws, identifier ],
                      [ ws, expression ] ;
continue_expression = "continue", [ ws, '.', ws, identifier ] ;
```

### Static semantics

`break` terminates execution of the innermost enclosing loop. If a label is provided (`break.label`), the named loop is terminated instead. If an expression is provided (`break expr` or `break.label expr`), the expression is evaluated and its value becomes the value of the terminated loop.

`continue` ends the current iteration of the innermost enclosing loop and begins the next. If a label is provided (`continue.label`), the named loop is continued instead.

Both `break` and `continue` are control transfers. A `break` supplies to the loop it targets the value of its expression, or `void` where it carries none, and an `else` branch supplies to its loop the value it yields. A loop that is supplied no value has type `void`.

### Dynamic semantics

When `break` or `continue` is executed, the automatic objects whose scope is between the `break`/`continue` site and the target label, or the enclosing loop boundary, are destroyed in reverse declaration order before control transfers, as defined in the clause on semantics.

### Constraints

`break` without a label shall appear only within a loop body. `break` with a label shall name a loop label that is in scope. Labelled constructs are defined in the subclause on labelled constructs.

The values a `break` supplies to the loop it targets, and the value of the `else` branch where the loop carries one, shall have a common type.

`continue` shall appear only within a loop body. `continue` with a label shall name a loop label that is in scope.

### Examples (informative)

```
// break exits the loop
loop {
    if done { break; }
    work();
}

// value from a labelled block via express
let result = search: {
    let mut iterator = collection.iter();
    while iterator.next() -> item {
        if item.matches(query) { express.search item; }
    }

    express default_item;
};

// continue skips to the next iteration (via then block)
let mut i = 0;
while i < 10 {
    if skip(i) { continue; } // then block still runs
    process(i);
} then { i += 1; }

// Labelled continue in nested loops
outer: while outer_cond() -> a {
    while inner_cond() -> b {
        if reject(a, b) { continue.outer; }
        i#use(a, b);
    }
}
```

## 7.8 Express blocks

`express` yields a value from a block and exits the block.

### Syntax

```
express_expression = "express", [ ws, '.', ws, identifier ], ws,
                     expression ;
```

### Static semantics

`express` targets a block or a labelled construct. When `express value;` is evaluated, `value` is evaluated, control exits the targeted construct, and that construct’s value is `value`. `express` may appear anywhere within the construct, not only at the end. When `express` is executed, what remains of the targeted construct is not executed.

When no label is provided, the target is the immediately enclosing block. When a label is provided (`express.label value;`), the target is the enclosing labelled construct of the name. The target can enclose the `express` expression through any number of intervening constructs, including loops.

The immediately enclosing block is the innermost block containing the `express` expression, whether or not the block carries a label.

A block whose value is yielded by `express` is an **express block**. The type of a construct targeted by `express` is the common type of the values supplied to it and of the value the construct yields of itself. A block that no `express` targets has type `void`. When control reaches the end of a block, the value the block yields there is `void`.

`express` is a control transfer. It yields no value at the `express` site, and supplies the value of its operand to the construct it targets.

### Dynamic semantics

The automatic objects whose scope is between the `express` site and the boundary of the target are destroyed in reverse declaration order before the target exits, as defined in the clause on semantics.

### Constraints

`express` without a label whose immediately enclosing block is a subroutine body shall not appear. `express.label` shall name a labelled construct that encloses the `express` expression. A label that names no enclosing labelled construct, or that names a loop, shall not appear.

The values the `express` expressions targeting one construct supply shall have a common type. Where control can reach the end of the construct, the value it yields there shall have that type also.

### Examples (informative)

```
let x = { let a = 10; express a * 2; };
// x = 20

let y = {
    let a = compute();
    if a < 0 { express 0; } // early exit
    let b = transform(a);
    express b;
};
```

## 7.9 Labelled constructs

A **labelled construct** is a block, an `if` expression, an `if let` expression, a `match` expression, or a loop, prefixed with a **label** of the form `name:`.

### Syntax

```
label           = identifier, ws, ':' ;
labelled_block  = label, ws, block ;
```

### Static semantics

A label supplies a name by which `break`, `continue`, and `express` may target the construct it prefixes. Which of them may target which labelled construct, and what each does upon reaching it, are defined in the subclauses on those expressions.

A labelled construct is an expression.

Label names follow identifier rules. An inner label hides an outer label of the same name for the duration of the inner scope.

### Dynamic semantics

The automatic objects whose scope is between the `express`, `break`, or `continue` site and the target label are destroyed in reverse declaration order before control transfers, as defined in the clause on semantics.

### Examples (informative)

```
let result = outer: {
    let x = compute();
    if x < 0 { express.outer 0; }
    express x * 2;
};

let mut iterator = collection.iter();
search: while iterator.next() -> item {
    while item.children().iter().next() -> sub {
        if sub.matches(query) {
            result = sub;
            break.search;
        }
    }
}
```

## 7.10 Divergence primitive

`trap` names a subroutine that the implementation provides, of type `fn() -> !`. An invocation of it is a diverging expression.

### Syntax

```
trap_invocation   = "trap", ws, '(', ws, ')' ;
trap_handler_decl = "trap", ws, block ;
```

### Dynamic semantics

When `trap()` is evaluated:

— If a `trap` handler is declared in the translation unit of the invocation, that handler executes.

— If no handler is declared there, the default behaviour is implementation defined. The default shall diverge.

### 7.10.1 `trap` handler

#### Static semantics

A `trap` handler replaces the default behaviour with the block the handler declares. A handler may appear wherever a declaration may appear, in any source unit of the translation unit.

The handler takes no arguments.

#### Dynamic semantics

Where `trap()` is evaluated inside the handler, the handler is invoked again.

#### Constraints

The handler shall be a diverging expression.

The handler shall not refer to a binding whose object has the automatic object lifetime.

Multiple handlers within one translation unit shall not appear.

#### Examples (informative)

```
trap {
    gpio_led_on(led_red);

    loop {
        airside { *$volatile gpio_led ^= 1; }
        spin_delay(500000);
    }
}

// Re-entry guard
static mut entered: ui1 = 0;

trap {
    airside {
        if *&atomic entered != 0 { loop {} }
        *&atomic mut entered = 1;
    }

    cleanup();
    loop {}
}
```

### 7.10.2 `trap` in `xlat`

#### Static semantics

A `trap` expression evaluated within a `xlat` block is a translation failure. The translation fails at the point where the `trap` is reached during translation-time evaluation. The translation failure supersedes any execution-time trap handler that the translation unit declares.

The translation failure is scoped to the translation-time evaluation that reached the `trap` and to the source unit translation that depends on it. Other translation-time evaluations within the same translation unit — each `xlat` block, each `const` and `static` initializer — are independent. Whether they reach `trap` is determined separately for each.

Within a `xlat?` conditional, the branch that translation-time evaluation does not select is not evaluated — as defined in the subclause on `xlat` blocks and the `xlat?` conditional. A `trap` expression appearing in the branch produces no translation failure.

#### Examples (informative)

```
// Translation-time environment check — aborts translation on
// unsupported execution environments
xlat {
    if cellbits::exec != 8 {
        trap(); // translation failure: unsupported cell width
    }
};

// `trap` on the verdict::Fail path of a contract test within xlat
const ?: void = xlat {
    match T'bound(ord) {
        verdict::Pass(?) -> { };
        verdict::Fail(?) -> { trap(); };
        // translation failure when T does not satisfy ord
    }
};

// `trap` in the execution branch of a `xlat?` conditional —
// not a translation failure
fn platform_init() {
    xlat? {
        init_at_translation();
    } else {
        // not a translation failure
        // translation-time evaluation does not select this branch
        trap();
    }
}
```

### 7.10.3 `trap` and `#dyn` boundaries

#### Static semantics

Opaque codes bound via `#dyn` are separate translation units, each with its own `trap` handler. A `trap` reached within a subroutine imported through `#dyn` invokes the handler of the translation unit that defines the subroutine. It does not reach the handler of the invoking translation unit.

## 7.11 Control transfers and diverging expressions

This subclause classifies expressions by where their evaluation continues execution.

### Static semantics

An expression is a **control transfer** if its evaluation continues execution at a point this specification determines, other than the point that follows it in programme order. The control transfers are:

— `return`, with or without a value, which continues at the invocation site.

— `break`, with or without a label or value, which continues after the loop it targets.

— `continue`, with or without a label, which continues at the next iteration of the loop it targets.

— `express`, which continues after the block it targets.

Each of the following is itself a control transfer where it is not a diverging expression:

— a block every path through which ends in a diverging expression or in a control transfer that does not target it.

— an `if`, `if let`, or `match` expression every branch or alternative of which is a diverging expression or a control transfer that does not target it.

— an `airside` block whose body is a control transfer or a diverging expression.

An expression is a **diverging expression** if its evaluation continues execution at no point of the programme. The following expression forms are diverging:

— an invocation of `trap`.

— a `loop` block, and a `while` block whose condition is evaluable at translation time and evaluates to the success variant, where none of the following is reachable: a `break` targeting the block or an enclosing loop, a `continue` targeting an enclosing loop, a `return`, or an `express` targeting an enclosing block.

— an invocation of a subroutine declared `-> !`.

— a block where every path through the block ends in a diverging expression.

— an `if` expression where every branch is a diverging expression.

— a `match` expression where every alternative is a diverging expression.

— an `if let` expression where every branch is a diverging expression.

— an `airside` block whose body is a diverging expression.

A control transfer and a diverging expression each yield no value. In any context that requires an expression of type `T`, either is accepted in place of an expression of type `T`.

A construct whose type is the common type of a set of expressions, as the clause on types defines the common type, is itself a diverging expression where every expression of that set is a diverging expression.

### Implementation requirements

The implementation shall place an implicit `trap` expression at the point that follows each diverging expression of the programme in programme order. No implicit `trap` is placed after an implicit `trap`. The inserted `trap` is subject to all rules defined in the subclause on the divergence primitive.

Where an invocation expression invokes a subroutine declared `-> !`, and where either

— the invocation is through a subroutine pointer obtained by `as!` reinterpretation, or

— the invocation is an external subroutine invocation, as defined in the subclause on σ operations,

the implementation shall preserve the invocation as an invocation instruction in the opaque code, and shall replace it neither with a copy of the invoked body nor with a jump that discards the return site. The implicit `trap` defined above shall be placed immediately following the instruction in programme order.

If an external subroutine invocation returns control to the invoker, the implicit `trap` is reached and the programme transitions according to the subclause on the divergence primitive.

### Examples (informative)

```
const true:  verdict.[void, void] = verdict::Pass(void);
const false: verdict.[void, void] = verdict::Fail(void);

// A diverging branch contributes no type. The common type is si4.
let x: si4 = if cond then 42 else trap();

// `-> !` invocation is diverging.
fn fail(msg: &[ui1]) -> ! { trap(); }

let y: si4 = match parse(input) {
    let verdict::Pass(val) -> val;
    verdict::Fail(?)       -> fail("parse failed");
};

// A block where every path diverges is itself diverging.
let z: si4 = {
    log("diverging");
    trap();
};

// A `loop` without reachable `break` is diverging.
airside fn halt() -> ! {
    loop { asm { wfi } }
}

// A `break` excluded by a const condition is unreachable.
fn spin() -> ! {
    while true {
        // The condition is const: the break is unreachable.
        if false { break; }
        airside { asm { wfi } }
    }
}

// A `break` reachable by an execution-time condition denies
// divergence, and the point after it is reachable.
while true {
    // execution-time condition: the break is reachable
    if shutdown() { break; }
    poll();
}
cleanup();
```
