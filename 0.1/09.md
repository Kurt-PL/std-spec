# §9. Protocols and implementations

This clause defines the mechanisms by which types acquire behaviour: the attachment of items to a single type, the items themselves, and the abstraction by which multiple types share an interface.

The subroutine declaration grammar is defined in the clause on declarations. The reference and derivation model is defined in the clause on references and resource management. The built-in types and their bound classifications are defined in the clause on types.

## 9.1 Inherent implementations

An inherent `impl` block introduces methods, associated subroutines, and associated constants into a type’s own namespace.

### Syntax

```
impl_block = "impl", [ ws, impl_generic_params ], ws, type,
             [ ws, generic_args ],
             [ ws, ( with_single | with_braced ) ],
             ws, '{', ws, { inherent_item, ws }, '}' ;

impl_generic_params = '(', ws, impl_generic_item, ws,
                      { ',', ws, impl_generic_item, ws }, [ ',', ws ],
                      ')' ;

impl_generic_item = identifier, [ ws, ':', ws, bound ]
                  | "const", ws, identifier, ws, ':', ws, type ;

inherent_item = method_declaration
              | associated_fn
              | associated_const_def ;

associated_fn = [ "pub", ws ], [ "airside", ws ], "fn", ws,
                identifier, [ ws, generic_clause ], ws, '(', ws,
                [ parameter_list ], ws, ')', [ ws, '->', ws, type ],
                [ ws, ( with_single | with_braced ) ], ws, block ;

associated_const_def = [ "pub", ws ], "const", ws, identifier, ws,
                       [ ':', ws, type, ws ], '=', ws, expression,
                       ';' ;
```

### Static semantics

An inherent `impl` block may contain three kinds of items:

— Methods — subroutines whose first parameter is a self parameter (`&self`, `$self`, `self`, `mut self`). A method is invoked through the `.` operator. The self parameter determines how the receiver is accessed — by shared reference, by exclusive reference, or by transfer.

— Associated subroutines — subroutines without a self parameter. An associated subroutine has no receiver; it is invoked through a qualified path.

— **Associated constants** — translation-time constants scoped to the type’s namespace. An associated constant is accessed via `Type::NAME`. The value expression is evaluated at translation time. The rule for an omitted type annotation is defined in the subclause on binding declarations. The type may refer to `selftype` — within an `impl T` block, `selftype` is an alias for `T`.

Each item shall individually be marked `pub` to be visible to importers; items without `pub` are private to the module that declares the `impl` block.

An inherent `impl` block may be generic. Generic parameters are introduced by an `impl(...)` parameter list immediately after the `impl` keyword and before the target type. The declared parameters are in scope from the point of declaration through the end of the block. The `impl` block’s generic parameters and any generic parameters of the type are independent; the `impl` block introduces its own parameter list.

Multiple inherent `impl` blocks for the same type are permitted, provided no item name collisions occur. Items from different `impl` blocks on the same type are merged into a single namespace.

### Constraints

The value expression of an associated constant shall be evaluable at translation time.

A name collision between items from different inherent `impl` blocks on the same type shall not appear.

A `type` declaration inside an inherent `impl` block shall not appear.

The resolution of name overlap between an inherent `impl` item and a protocol `impl` item on the same type is defined in the subclause on method name resolution.

An identifier declared in an `impl(...)` parameter list shall not share its name with any declaration visible in the enclosing scope at the point of the `impl` block.

### Examples (informative)

```
impl(T) stack.[T] {
    // Associated subroutine — constructor, invoked via stack::new()
    pub fn new() -> selftype {
        return stack { .data = [], .len = 0 };
    }

    // Associated subroutine — factory with capacity
    pub fn with_capacity(cap: uaddr) -> selftype { ... }

    // Methods — invoked via value.method()
    pub fn push($self, val: T) { ... }
    pub fn pop($self) -> verdict.[T, void] { ... }
    pub fn len(&self) -> uaddr { return (*self).len; }
    pub fn is_empty(&self) -> verdict.[void, void] {
        return (*self).len == 0;
    }
}

impl si4 {
    // Associated constants — accessed via si4::MIN, si4::MAX
    pub const MIN: si4 = -2147483648;
    pub const MAX: si4 = 2147483647;
    // type inferred from the initializer
    pub const ZERO = 0~si4;
}

// Usage
let s = stack.[si4]::new(); // associated subroutine
s.push(42);                 // method
let m = si4::MAX;           // associated constant
```

## 9.2 Method declarations

Methods are subroutines that appear inside `impl` blocks or protocol bodies and receive a self parameter as their first parameter. The self parameter determines how the implementing type’s value is accessed. Automatic referencing, by which a receiver is adjusted to the self parameter, is defined in the clause on expressions.

### Syntax

```
method_declaration  = [ "pub", ws ], [ "airside", ws ], "fn", ws,
                      identifier, [ ws, generic_clause ], ws, '(', ws,
                      method_params, ws, ')', [ ws, '->', ws, type ],
                      [ ws, ( with_single | with_braced ) ], ws,
                      block ;

method_prototype    = [ "pub", ws ], [ "airside", ws ], "fn", ws,
                      identifier, [ ws, generic_clause ], ws, '(', ws,
                      method_proto_params, ws, ')',
                      [ ws, '->', ws, type ],
                      [ ws, ( with_single | with_braced ) ], ws,
                      ';' ;

method_params       = self_param, [ ws, ',', ws, parameter_list ],
                      [ ws, ',' ]
                    | [ parameter_list ], [ ws, ',' ] ;

method_proto_params = self_param,
                      [ ws, ',', ws, proto_parameter_list ], [ ws, ',' ]
                    | [ proto_parameter_list ], [ ws, ',' ] ;

self_param          = [ ( ( '&' | '$' ), ws,
                      { ref_modifier, ws } )
                      | ( "mut", ws ) ],
                      ( "self" | '[', ws, "self", ws, ']' ) ;
```

The prototype-elision rule from the clause on declarations applies: when a `method_prototype` is in scope for the same name, the corresponding `method_declaration` may omit any clause already fixed by it. Parameter-name optionality in `method_prototype` follows the same rule as in a subroutine prototype, defined in the clause on declarations.

### Static semantics

A self parameter makes the subroutine a **method**, invoked through the `.` operator. The `self_param` production fixes `self` as the first parameter.

`selftype` is a keyword that stands, in a type position, for a type the enclosing declaration fixes.

Within an `impl` declaration, `selftype` stands for the type the declaration implements upon, from the point where the type is written to the end of the declaration. Within a `protocol` declaration, `selftype` stands for the type of an eventual implementer, throughout the declaration, subject to the constraint on protocol item signatures below.

The self parameter forms are:

— `&self` — shared reference of the receiver. Equivalent to `self: &selftype`; the load and store permissions follow from the reference family, as defined in the clause on references and resource management.

— `$self` — exclusive reference of the receiver. Equivalent to `self: $selftype`; the method may load from and store to the receiver, and the exclusivity guarantee follows from the reference family.

— `self` — transfer, single-assignment binding. The value is transferred into the parameter and the invoker’s binding is invalidated.

— `mut self` — transfer, multi-assignment binding. Same as `self` but the method may reassign `self` within its body.

Modifiers follow the family directly.

The `self` keyword enclosed in a bracket pair — `[self]` — on a receiver whose family is `&` or `$`, makes the receiver a slice reference to the implementing type. Writing `X[self]`, where `X` is any admissible combination of family and modifiers, is equivalent to `self: X[selftype]` — the slice reference of the form with element type `selftype`.

A subroutine in an `impl` block or protocol body with no self parameter is an **associated subroutine**, not a method. It is invoked through a qualified path. In a generic context where the implementing type is ambiguous, the qualified path root defined in the clause on expressions disambiguates.

### Constraints

`self` is a keyword in the parameter position and shall not be used as an ordinary parameter name elsewhere in the parameter list.

`&self` and `$self` do not accept the `mut` modifier on the binding — whether the referent is storable is determined by the reference family (`&` vs `$`). `mut &self` and `mut $self` shall not appear.

A bracketed receiver without a preceding family — `[self]` — shall not appear. `mut [self]` shall not appear.

The receiver family is `&` or `$`. `%` in any form, including `%[self]`, shall not appear as a receiver family.

### Examples (informative)

```
impl(T) T {
    fn at(&[self], idx: uaddr) -> &selftype {
        // self: &[T]
        ...
    }

    fn at_xcl($[self], idx: uaddr) -> $selftype {
        // self: $[T]
        ...
    }
}
```

### Design rationale (informative)

A slice appears only as the referent of a reference; the bracketed forms therefore require the `&` or `$` family.

`%` is excluded because method dispatch through `.` resolves a receiver without an enclosing `airside` block, while access through an unmanaged reference requires one. Admitting `%self` would conceal unmanaged access behind `.` or impose a receiver-dependent `airside` requirement at the invocation site. An associated subroutine taking `%self` provides the same operation through ordinary invocation syntax inside an `airside` block.

### 9.2.1 Method name resolution

#### Static semantics

A method invocation `e.m(args)` is resolved by the following procedure, applied to the type of `e` after reference transparency:

1. If an inherent `impl` block on the type provides a method named `m`, the invocation resolves to the method.
2. Otherwise, the implementation collects every protocol `impl` block on the type whose implementation provides a method named `m`:

a. If exactly one such protocol `impl` exists, the invocation resolves to its method.

b. If two or more such protocol `impl` blocks exist, the invocation is ambiguous.

c. If no such protocol `impl` exists, the invocation resolves to no method.

A qualified method invocation, defined in the clause on expressions, resolves to the implementation of the named protocol for the type of the receiver.

The same resolution procedure applies to associated subroutines and associated constants accessed through qualified path syntax (`Type::item`): an inherent item takes priority; in its absence, exactly one protocol item is required. The qualified-path form `(Type as Protocol)::item` invokes the item from the implementation of `Protocol` for `Type`.

#### Constraints

Collisions of method or associated item names between a protocol `impl` block and an inherent `impl` block, or between two protocol `impl` blocks, are resolved at each invocation or access site by the procedure above.

An invocation or access that resolves to two or more protocol methods, or to no method, shall not appear. An access to an associated subroutine or associated constant through qualified path syntax that resolves to two or more protocol items of the same name shall not appear. Protocol items are defined in the subclause on protocol declarations.

Duplicate implementations of a protocol on a type are a translation failure, as defined in the subclause on duplicate detection.

#### Examples (informative)

```
// Inherent method takes priority over protocol method
struct counter { val: ui4 }

impl counter {
    pub fn get(&self) -> ui4 { return self.val; }
}

protocol Get {
    fn get(&self) -> ui4;
}

impl counter as Get {
    fn get(&self) -> ui4 { return self.val * 2; }
}

let c = counter { .val = 5 };
c.get();          // resolves to inherent — yields 5
(c as Get).get(); // resolves to Get impl — yields 10

// Single protocol method, no inherent
struct widget {}

impl widget as Drawable {
    fn draw(&self) { ... }
}

let w = widget {};
w.draw();         // resolves to Drawable::draw

// Two protocol methods, no inherent
protocol Render { fn draw(&self); }
protocol Paint  { fn draw(&self); }

impl widget as Render { fn draw(&self) { ... } }
impl widget as Paint  { fn draw(&self) { ... } }

w.draw();             // translation failure — ambiguous
(w as Render).draw(); // OK
(w as Paint).draw();  // OK
```

## 9.3 Protocol declarations

A protocol declares a named interface: a set of method prototypes, associated constants, and default methods that implementing types shall provide.

### Syntax

```
protocol_declaration = [ "pub", ws ], "protocol", ws, identifier,
                       [ ws, generic_clause ],
                       [ ws, ':', ws, bound ],
                       [ ws, ( with_single | with_braced ) ],
                       ws, '{', ws, { protocol_item, ws }, '}' ;

protocol_item = method_prototype
              | default_method
              | associated_const ;

default_method   = method_declaration ;
associated_const = "const", ws, identifier, ws, ':', ws, type,
                   [ ws, '=', ws, expression ], ws, ';' ;
```

### Static semantics

A protocol introduces a name into the enclosing scope. The name may be used as a bound on generic parameters (`.[ T: Protocol ]`), as the target of an `impl` block (`impl T as Protocol`), and as the referent of a protocol object type (`&dyn Protocol`), as defined in the subclause on protocol objects.

A protocol body contains zero or more **protocol items**. The three kinds of protocol item are:

— Method prototypes — a subroutine signature without a body; a protocol `impl` block provides it, as defined in the subclause on protocol implementations. A method prototype without a self parameter declares an associated subroutine — it is invoked through a qualified path. Method prototypes in protocols follow the same self-parameter grammar defined in the subclause on method declarations.

— Default methods — a method declaration standing in the protocol body, defined in the subclause on default methods. A default method has full access to `selftype`, to the other methods of the protocol, and to the protocol’s associated constants. A default method may invoke other methods of the same protocol on `self`, including those declared by a method prototype.

— Associated constants — a constant member declared with `const NAME: Type;` inside the protocol body; a protocol `impl` block provides a value unless the protocol provides a default expression, as defined in the subclause on protocol implementations. These follow the same rules as associated constants in inherent `impl` blocks, with the addition that the value expression may refer to `selftype`.

#### Visibility

`pub protocol` is visible to importers; `protocol` without `pub` is private to the declaring source unit. Methods within a protocol body follow the same visibility model as subroutines: each method shall individually be marked `pub` to be visible to importers.

### Constraints

A protocol name shall be unique within its scope. A protocol may be generic; the generic parameter rules defined in the clause on declarations apply.

In the signature of a protocol item, `selftype` shall appear only within the type of a self parameter.

### 9.3.1 Associated constants in protocols

#### Static semantics

An associated constant in a protocol follows the same access rules as in an inherent `impl` — `Type::NAME` or `(Type as Protocol)::NAME` — with the additional constraint that the value is determined by the implementing type.

An associated constant is not accessible through a reference to a protocol object.

#### Examples (informative)

```
pub protocol Bounded.[T] {
    const MIN: T;
    const MAX: T;
}

impl ui1 as Bounded.[selftype] {
    const MIN: ui1 = 0;
    const MAX: ui1 = 255~ui1;
}

fn clamp.[T: Bounded.[T] + primitive](val: T) -> T {
    let lo = (T as Bounded.[T])::MIN;
    let hi = (T as Bounded.[T])::MAX;
    return if val < lo then lo else if val > hi then hi else val;
}
```

### 9.3.2 Superprotocol bounds

#### Static semantics

A protocol may require that implementing types also implement other protocols. The requirement is expressed by a bound upon the protocol name. Superprotocol methods are available within the protocol’s default methods without additional qualification.

#### Constraints

A type that implements a protocol with superprotocol bounds shall also implement all required superprotocols.

#### Examples (informative)

```
pub protocol Printable: Fmt + Clone {
    fn print(&self) { println("{}", &[self as &dyn Fmt]); }
}
```

### 9.3.3 Default methods

#### Static semantics

A **default method** is a protocol item that is a method declaration rather than a method prototype: the declaration stands in the protocol body with its body present. Where an `impl` block for a type does not provide the item, that body is used. Where the `impl` block provides it, the provided body replaces the default entirely. A default method declared without a self parameter is an associated subroutine, and the same rules govern it.

#### Examples (informative)

```
pub protocol Summary {
    fn title(&self) -> &[ui1];

    fn summary(&self) -> &[ui1] {
        return self.title(); // invokes the method prototype
    }
}
```

## 9.4 Protocol implementations

A protocol `impl` block provides the concrete methods and associated constants for a protocol on a specific type.

### Syntax

```
protocol_impl = "impl", [ ws, impl_generic_params ], ws, type,
                [ ws, generic_args ], ws, "as", ws, single_path, ws,
                '{', ws,
                { protocol_impl_item, ws }, '}' ;

protocol_impl_item = method_declaration
                   | associated_const_def ;
```

### Static semantics

A protocol `impl` block provides the concrete definitions that the protocol requires. The effect of omitting or overriding a default method is defined in the subclause on default methods.

A protocol `impl` block may be generic, by the `impl(...)` parameter list. The protocol’s type arguments may reference the declared parameters. The `impl` block’s generic parameters and any generic parameters of the type are independent.

### Constraints

All non-default methods declared in the protocol shall be provided; missing methods are a translation failure. Associated constants shall be specified unless the protocol provides a default value.

The protocol `impl` block shall satisfy all bounds declared on the protocol — including superprotocol bounds and bounds on the protocol’s generic parameters.

### Examples (informative)

```
impl si4 as Ord.[selftype] {
    fn cmp(&self, other: &selftype) -> ordering {
        return if *self > *other then ordering::Greater
        else if *self < *other then ordering::Less
        else ordering::Equal;
    }
}

impl(T) vec.[T] as Iterator.[T] {
    fn next($self) -> verdict.[T, void] {
        if self.pos < self.len {
            let val = self.data.at(self.pos);
            self.pos += 1;
            return verdict::Pass(val);
        } else {
            return verdict::Fail(void);
        }
    }
}
```

### 9.4.1 Implementation locality

#### Constraints

A protocol implementation is permitted only if at least one of the following is declared in the current translation unit: the protocol declaration, or the implementing type declaration.

### 9.4.2 Duplicate detection

#### Constraints

A type shall implement a given protocol instantiation at most once within the same translation unit. Instantiations that resolve the protocol’s generic parameters differently are distinct. If two source units within the same translation unit provide `impl T as Protocol` for the same type and the same instantiation, this shall not appear. The diagnostic shall identify both conflicting implementations and a source unit from which both are reached in the `#add` dependency graph — a **collision source**.

## 9.5 Descriptors

A **descriptor** is a structure the implementation emits for a concrete type. Type-erased code loads from a descriptor to obtain the properties of the type upon which it operates. As defined in the clause on declarations, every type parameter carries the type descriptor, and each bound upon it carries a further descriptor. The type of a reference to a descriptor is `%void`.

### Notes (informative)

A method added to a protocol takes the next field of Zone B, so every descriptor of the protocol is laid out afresh. Opaque code that was translated against the earlier layout indexes the wrong field.

### 9.5.4 Protocol descriptor

A **protocol descriptor** is divided into two zones, always in the following order.

#### Zone A — superprotocol descriptor references

Zone A contains one `%void` field per direct superprotocol of the protocol. The fields appear in the order the superprotocols are declared in the protocol’s bound list. Each field designates a complete, self-contained protocol descriptor for that superprotocol. A superprotocol’s protocol descriptor follows the same two-zone structure; transitive superprotocols are reached by following the reference chain through successive Zone A fields.

A protocol with no superprotocols has an empty Zone A (zero fields).

#### Zone B — protocol method fields

Zone B contains one subroutine pointer field per method declared in the protocol body, in declaration order. Default methods occupy a field regardless of whether the implementing type overrides them: if the implementation provides an override, the override’s subroutine pointer occupies the field; otherwise, the default body’s subroutine pointer occupies it.

#### Field indexing

Zone B begins at field `S`, where `S` is the number of direct superprotocols. The `k`-th method declared in the protocol body (zero-indexed) occupies field `S + k`.

The total number of fields in a protocol descriptor for a protocol with `S` direct superprotocols and `M` methods is `S + M`.

### 9.5.5 Descriptor field signatures

A method of a protocol is a generic subroutine whose sole type parameter is the implementing type, bounded by the protocol. The type of the descriptor field the method occupies is the lowered signature of that generic subroutine, as defined in the subclause on signature lowering. Applied to a protocol method, that lowering yields the following.

— Zone 1 is the out-parameter, `%void`.

— Zone 2 is the source parameters in declaration order. The self parameter is the parameter whose type is the type parameter, and lowers to `%void`. A parameter whose type is, or involves, a generic parameter of the protocol lowers likewise, whatever the `impl` block resolves the parameter to. A parameter whose type mentions no generic parameter of the protocol is concrete and passes through unchanged.

— Zone 3 is two `%void` parameters: the type descriptor of the implementing type, and the descriptor of the protocol that bounds it. The type parameter is one, and the bound upon it has one element, so a protocol method admits no further descriptor here. The superprotocol descriptors of a protocol are reached through Zone A of the protocol’s own descriptor.

The return type of the lowered signature is `void`.

One field type therefore serves every implementation of the protocol, which is what an invocation through a protocol object requires: the invoker knows the field type without knowing the implementing type. Protocol objects are defined in the subclause on protocol objects.

The descriptor references that a generic invocation supplies as its trailing arguments are, for an invocation through a protocol object, the `.tyd` and `.prd` fields the reference carries.

### 9.5.6 Protocol descriptor examples (informative)

A protocol with no superprotocols:

```
protocol Ord.[T] {
    fn cmp(&self, other: &T) -> ordering;            // field 0
    fn lt(&self, other: &T) -> verdict.[void, void]; // field 1
    fn gt(&self, other: &T) -> verdict.[void, void]; // field 2
}

// Type descriptor for si4 (T'bound(type)):
// [0] = 4                (si4'size)
// [1] = 4                (si4'align)
// [2] = &null_destructor (si4 has no with destruct)

// Protocol descriptor for si4 as Ord.[selftype]:
// [0] = &si4_cmp : fn(%void, %void, %void, %void, %void) -> void
// [1] = &si4_lt  : fn(%void, %void, %void, %void, %void) -> void
// [2] = &si4_gt  : fn(%void, %void, %void, %void, %void) -> void
//                     ^out   ^self  ^other ^tyd   ^prd
```

A protocol with superprotocols:

```
protocol Foo: Bar + Baz {
    fn do_foo(&self) -> si4;
}

// Protocol descriptor layout for Foo:
// [0] = %void → Bar protocol descriptor (zone A)
// [1] = %void → Baz protocol descriptor (zone A)
// [2] = &do_foo : fn(%void, %void, %void, %void) -> void (zone B)
//                    ^out   ^self  ^tyd   ^prd
// Bar and Baz add no descriptor parameter: the bound upon the
// implementing type is Foo alone.
```

A protocol whose result type is a generic parameter of the protocol:

```
protocol Clone.[T] {
    fn clone(&self) -> T;
}

// Type descriptor for widget (T'bound(type)):
// [0] = widget'size
// [1] = widget'align
// [2] = &widget_destructor

// Protocol descriptor for widget as Clone.[selftype]:
// [0] = &widget_clone : fn(%void, %void, %void, %void) -> void
//                          ^out   ^self  ^tyd   ^prd
// The invoker allocates the out-storage from the type
// descriptor, as the signature lowering requires.
```

## 9.6 Protocol objects

A **protocol object** is a type whose concrete identity is erased. A value of type `dyn Protocol` is accessed only through a reference; the reference carries a reference to the value, a reference to a type descriptor, and a reference to a protocol descriptor.

### Syntax

```
protocol_object_type = "dyn", ws, single_path ;
```

The layout rules give no size for a `dyn Protocol` value; the value is accessed only through a reference. A reference to `dyn Protocol` is sized regardless of family.

### Static semantics

A reference to a protocol object is a wide reference. Its stored representation contains three fields:

<table>
<thead><tr><th>Offset</th><th>Field</th><th>Content</th></tr></thead>
<tbody>
<tr><td>0</td><td><code>ptr</code></td><td>reference to the value</td></tr>
<tr><td><code>(%void)'size</code></td><td><code>tyd</code></td><td><code>%void</code> — type descriptor</td></tr>
<tr><td>2 × <code>(%void)'size</code></td><td><code>prd</code></td><td><code>%void</code> — protocol descriptor</td></tr>
</tbody>
</table>

The total size is 3 × `(%void)'size`. The values the type descriptor reference and the protocol descriptor reference carry are defined in the clause on expressions, and the normative layout of both in the subclause on descriptors.

The type of `.ptr` is derived from the enclosing reference by the rule governing wide-reference-view fields, defined in the subclause on slice references. Because the concrete type is erased, the referent type is `void`. `.tyd` and `.prd` are `%void` under every family and modifier combination.

When a concrete value is implicitly cast to a protocol object reference, the implementation constructs a protocol descriptor containing references to the concrete type’s method implementations. A managed reference is implicitly cast to a reference to `dyn Protocol` of the same family and the same modifiers when its referent type implements `Protocol`.

### Dynamic semantics

Method invocations on protocol objects are dynamically dispatched. The implementation loads the method’s subroutine pointer from the protocol descriptor at the method’s fixed offset and performs an indirect invocation.

### Constraints

`dyn Protocol` shall not appear in any of the following positions:

— the type of a `let`, `const`, or `static` declaration;

— a subroutine parameter type or a return type, other than as the referent of a reference;

— a struct field type, an array element type, or a tuple field type.

A protocol used as the referent of a protocol object reference, in every family and modifier form, shall satisfy all of the following:

— All methods shall take `self` by reference (`&self` or `$self`), not by value.

— No method shall have generic parameters.

— The protocol shall not carry a built-in bound other than `copyable` or `variadic`.

Violating any of the above shall not appear.

### Examples (informative)

```
fn print_value(val: &dyn Fmt) {
    println("{}", &[val]);
}

let x: si4 = 42;
let b = verdict.[void, void]::Pass(void);
print_value(&x); // implicit cast: &si4 → &dyn Fmt
print_value(&b); // &verdict.[void, void] → &dyn Fmt

// Heterogeneous collection
let items: [&dyn Fmt; 2] = [&x, &b];
let mut iter = items.iter();
while iter.next() -> item {
    println("value: {}", &[item]);
}
```

### Design rationale (informative)

The inheritance of `mut` by `.ptr` keeps the store permission of `.ptr` equal to that of the reference it is derived from: `&dyn Protocol` yields a `.ptr` of `%void`, and `&mut dyn Protocol` and `$dyn Protocol` yield `%mut void`. Type-erased code therefore stores through `.ptr` in the cases in which the receiver reference permits a store, and in no other.

## 9.7 Built-in bounds

### Syntax

```
builtin_bound = "numeric" | "integer" | "primitive"
              | "copyable" | "variadic" | "atomic" ;
```

Kurt has six built-in bounds. The implementation resolves them by type identity. The three arithmetic bounds form a strict hierarchy: `primitive` ⊂ `integer` ⊂ `numeric`.

### 9.7.1 `numeric`

#### Static semantics

A type satisfies `numeric` if and only if it is an integer type or a floating radix point number type.

#### Constraints

A type satisfying `numeric` shall not declare `with destruct`.

#### Notes (informative)

The operations that require `numeric` are the arithmetic operators, unary negation, and the comparison operators, as defined in the clause on expressions.

### 9.7.2 `integer`

#### Static semantics

A type satisfies `integer` if and only if it is an integer type. `integer` is a strict subset of `numeric`.

#### Constraints

A type satisfying `integer` shall not declare `with destruct`.

#### Notes (informative)

Beyond those that require `numeric`, the operations that require `integer` are the bitwise operators, the shift operators, bitwise NOT, saturating arithmetic, and widening arithmetic, as defined in the clause on expressions, and the `discrim` argument on an enum, as defined in the clause on types.

### 9.7.3 `primitive`

#### Static semantics

A type satisfies `primitive` if and only if it is an unsigned integer type. `primitive` is a strict subset of `integer`.

#### Constraints

A type satisfying `primitive` shall not declare `with destruct`.

### 9.7.4 `copyable`

#### Static semantics

The copyable and uncopyable classification of types is defined in the clause on references and resource management.

A type satisfies `copyable` if and only if it is not uncopyable. A type parameter declared without `copyable` accepts both copyable and uncopyable types, and its bindings within the declaration body follow transfer semantics.

#### Examples (informative)

```
fn duplicate.[T: copyable](val: T) -> .{T, T} {
    return .{val, val}; // T is copyable
}

fn store.[T](slot: $T, val: T) {
    *slot = val;
    // T follows transfer semantics; val is not accessed after
}
```

### 9.7.5 `variadic`

#### Static semantics

A type satisfies `variadic` if and only if it is a struct declared `with variadic`. The type serves as the state object for variadic parameter capture within a subroutine declared with the `variadic` modifier. The `with variadic` declaration and the properties it grants are defined in the clause on types.

### 9.7.6 `atomic`

#### Static semantics

A type satisfies `atomic` if and only if `T'size` is a size for which the execution environment provides atomic operations, `T'align` is not less than `T'size`, and `T` is copyable.

A declared type satisfies `atomic` where it meets the conditions above; `with align(N)`, defined in the clause on types, raises a type’s alignment to meet the second condition.

#### Implementation defined

The set of sizes for which the execution environment provides atomic operations is implementation defined. A size belongs to the set where an arbitrary transformation of an object of the size can be applied atomically, using only the operations the execution environment provides and no storage beyond the object. The set can be empty. A conforming implementation shall document the set for each supported execution environment.

#### Notes (informative)

The operations that require `atomic` are the creation of atomic references, atomic load, atomic store, atomic compound assignment, and compare-and-swap, as defined in the clause on references and resource management.
