# §9. Protocols and implementations

This clause defines the mechanisms by which types acquire behaviour: the attachment of items to a single type, the items themselves, and the abstraction by which multiple types share an interface.

## 9.1 Inherent implementations

An `impl` block introduces methods, associated subroutines, and associated constants for a type. An `impl` block without an `as` clause is an **inherent implementation**, and introduces them into the type’s own namespace. One with an `as` clause is a **protocol implementation**, defined in the subclause on protocol implementations. An `impl(...)` parameter list introduces generic parameters whose scope is the whole `impl` block, the target type and the `as` clause included.

### Syntax

```
impl_block = "impl", [ ws, impl_generic_params ], ws, type,
             [ ws, generic_args ],
             [ ws, "as", ws, single_path ],
             ws, '{', ws, { impl_item, ws }, '}' ;

impl_generic_params = '(', ws, impl_generic_item, ws,
                      { ',', ws, impl_generic_item, ws }, [ ',', ws ],
                      ')' ;

impl_generic_item = identifier, [ ws, ':', ws, bound ]
                  | "const", ws, identifier, ws, ':', ws, type ;

impl_item = { item_prefix, ws },
            ( method_def | associated_fn | associated_const_def ) ;

associated_fn = [ "pub", ws ], [ "airside", ws ], "fn", ws,
                identifier, [ ws, generic_clause ], ws, '(', ws,
                [ parameter_list ], ws, ')', [ ws, '->', ws, type ],
                ws, block ;

associated_const_def = [ "pub", ws ], "const", ws, identifier, ws,
                       [ ':', ws, type, ws ], '=', ws, expression,
                       ';' ;
```

### Static semantics

An inherent `impl` block may contain three kinds of items:

— Methods — subroutines whose first parameter is a self parameter (`&self`, `$self`, `self`, `mut self`). A method is invoked through the `.` operator. The self parameter determines how the receiver is accessed — by shared reference, by exclusive reference, or by transfer.

— Associated subroutines — subroutines without a self parameter. An associated subroutine has no receiver.

— Associated constants — translation-time constants scoped to the type’s namespace. An associated constant is accessed via `Type::NAME`. The value expression is evaluated at translation time. The rule for an omitted type annotation is defined in the subclause on binding declarations. The type may refer to `selftype`, as the subclause on method declarations defines it.

For the visibility modifier, defined in the clause on declarations, the namespace that declares an item of an `impl` block is the one that encloses the block.

An inherent `impl` block may be generic, by the `impl(...)` parameter list. The target type may reference the declared parameters.

Multiple inherent `impl` blocks for the same type are permitted, provided no item name collisions occur. Items from different `impl` blocks on the same type are merged into a single namespace.

### Constraints

The value expression of an associated constant shall be evaluable at translation time.

A name collision between items from different inherent `impl` blocks on the same type shall not appear.

A `type` declaration inside an inherent `impl` block shall not appear.

The resolution of name overlap between an inherent `impl` item and a protocol `impl` item on the same type is defined in the subclause on method name resolution.

An identifier declared in an `impl(...)` parameter list shall not share its name with any declaration visible in the enclosing scope at the point of the `impl` block.

### Examples (informative)

```
impl(T) stack.[T] {
    // Associated subroutine — constructor, invoked via stack::new()
    pub fn new() -> selftype { ... }

    // Associated subroutine — factory with capacity
    pub fn with_capacity(cap: uaddr) -> selftype { ... }

    // Methods — invoked via value.method()
    pub fn push($self, val: T) { ... }
    pub fn pop($self) -> verdict.[T, void] { ... }
    pub fn len(&self) -> uaddr { return (*self).len; }
    pub fn is_empty(&self) -> verdict.[void, void] {
        return (*self).len == 0;
    }
}

impl si4 {
    // Associated constants — accessed via si4::min, si4::max
    pub const min: si4 = -2147483648;
    pub const max: si4 = 2147483647;
    // type inferred from the initializer
    pub const zero = 0~si4;
}

// Usage
let mut s = stack.[si4]::new(); // associated subroutine
s.push(42);                     // method
let m = si4::max;               // associated constant
```

## 9.2 Method declarations

Methods are subroutines that appear inside `impl` blocks or protocol bodies and receive a self parameter as their first parameter. The self parameter determines how the implementing type’s value is accessed. Automatic referencing, by which a receiver is adjusted to the self parameter, is defined in the clause on expressions.

### Syntax

```
method_def          = [ "pub", ws ], [ "airside", ws ], "fn", ws,
                      identifier, [ ws, generic_clause ], ws, '(', ws,
                      method_params, ws, ')', [ ws, '->', ws, type ], ws,
                      block ;

method_proto        = [ "pub", ws ], [ "airside", ws ], "fn", ws,
                      identifier, [ ws, generic_clause ], ws, '(', ws,
                      method_proto_params, ws, ')',
                      [ ws, '->', ws, type ], ws,
                      ';' ;

method_params       = self_param, [ ws, ',', ws, parameter_list ],
                      [ ws, ',' ]
                    | [ parameter_list ], [ ws, ',' ] ;

method_proto_params = self_param,
                      [ ws, ',', ws, proto_parameter_list ], [ ws, ',' ]
                    | [ proto_parameter_list ], [ ws, ',' ] ;

self_param          = [ ( ( '&' | '$' ), ws,
                      { ref_modifier, ws } )
                      | ( "mut", ws ) ],
                      ( "self" | '[', ws, "self", ws, ']' ) ;
```

A `method_def` that implements a `method_proto` shall state the generic clause, the self parameter, each parameter type, and the return type as the `method_proto` states them. Its parameter names may differ. Parameter names are optional in a `method_proto`, as they are in a subroutine prototype, defined in the clause on declarations.

### Static semantics

A self parameter makes the subroutine a **method**, invoked through the `.` operator. The `self_param` production fixes `self` as the first parameter.

`selftype` is a keyword that stands, in a type position, for a type the enclosing declaration fixes.

Within an `impl` declaration, `selftype` stands for the type the declaration implements upon, from the point where the type is written to the end of the declaration. Within a `protocol` declaration, `selftype` stands for the type of an eventual implementer, throughout the declaration, and is a type parameter of every item the protocol declares. It precedes every type parameter the item declares, and the bound upon it is the protocol that declares the item.

The self parameter forms are:

— `&self` — shared reference of the receiver. Equivalent to `self: &selftype`. The load and store permissions follow from the reference family, as defined in the clause on references and resource management.

— `$self` — exclusive reference of the receiver. Equivalent to `self: $selftype`. The method may load from and store to the receiver, and the exclusivity guarantee follows from the reference family.

— `self` — transfer, single-assignment binding. The value is transferred into the parameter and the invoker’s binding is invalidated.

— `mut self` — transfer, multi-assignment binding. Same as `self` but the method may reassign `self` within its body.

Modifiers follow the family directly.

Where `X` combines the family `&` or `$` with any permitted modifiers, the receiver `X[self]` is equivalent to `self: X[selftype]`, a slice reference with element type `selftype`.

A subroutine in an `impl` block or protocol body with no self parameter is an **associated subroutine**. It is invoked through a qualified path. In a generic context where the implementing type is ambiguous, the qualified path root defined in the clause on expressions disambiguates.

### Constraints

`self` shall appear in a parameter list only as the self parameter.

`mut &self` and `mut $self` shall not appear.

A bracketed receiver without a preceding family — `[self]` — shall not appear. `mut [self]` shall not appear.

The receiver family is `&` or `$`. `%` in any form, including `%[self]`, shall not appear as a receiver family.

### Examples (informative)

```
impl(T) T {
    fn at(&[self], idx: uaddr) -> &selftype {
        // self: &[T]
        ...
    }

    fn at_xcl($[self], idx: uaddr) -> $selftype {
        // self: $[T]
        ...
    }
}
```

### Design rationale (informative)

A slice appears only as the referent of a reference. The bracketed forms therefore require the `&` or `$` family.

`%` is excluded because method dispatch through `.` resolves a receiver without an enclosing `airside` block, while access through an unmanaged reference requires one. Permitting `%self` would conceal unmanaged access behind `.` or impose a receiver-dependent `airside` requirement at the invocation site. An associated subroutine taking `%self` provides the same operation through ordinary invocation syntax inside an `airside` block.

### 9.2.1 Method name resolution

#### Static semantics

Where the type of `e` after reference transparency is a protocol object type, the invocation resolves to the method named `m` that the protocol declares. Where the protocol declares no method of that name, the search proceeds through the protocols its bound list names, in declaration order, each searched by this same rule. Where the searched protocols declare one such method between them, the invocation resolves to it, and the resolution reaches it by the first path the search takes. Where they declare two or more, the invocation is ambiguous. Where they declare none, the invocation resolves to no method.

A method whose signature mentions `selftype` other than as the type of its self parameter is not so resolved.

Where that type is `[U]`, the invocation resolves by the procedure below applied to `U`, and only a method whose self parameter is bracketed resolves. The subclause on method declarations defines the bracketed receiver.

For every other type, a method invocation `e.m(args)` is resolved by the following procedure, applied to that type:

1. If an inherent `impl` block on the type provides a method named `m`, the invocation resolves to the method.
2. Otherwise, the implementation collects every protocol `impl` block on the type whose implementation provides a method named `m`:

— Where exactly one such protocol `impl` exists, the invocation resolves to its method.

— Where two or more such protocol `impl` blocks exist, the invocation is ambiguous.

— Where no such protocol `impl` exists, the invocation resolves to no method.

A qualified method invocation, defined in the clause on expressions, resolves to the implementation of the named protocol for the type of the receiver.

The same resolution procedure applies to associated subroutines and associated constants accessed through a path (`Type::item`). A path whose qualified path root is `(Type as Protocol)` reaches the item from the implementation of `Protocol` for `Type`.

#### Constraints

An invocation or access that resolves to two or more protocol methods, or to no method, shall not appear. An access to an associated subroutine or associated constant through a path that resolves to two or more protocol items of the same name shall not appear. Protocol items are defined in the subclause on protocol declarations.

Duplicate implementations of a protocol on a type are a translation failure, as defined in the subclause on duplicate detection.

#### Examples (informative)

```
// Inherent method takes priority over protocol method
struct counter { val: ui4 }

impl counter {
    pub fn get(&self) -> ui4 { return self.val; }
}

protocol readable {
    fn get(&self) -> ui4;
}

impl counter as readable {
    fn get(&self) -> ui4 { return self.val * 2; }
}

let c = counter.{ .val = 5 };
c.get();          // resolves to inherent — yields 5
(c as readable).get(); // resolves to readable impl — yields 10

// Single protocol method, no inherent
struct widget {}

impl widget as drawable {
    fn draw(&self) { ... }
}

let w = widget.{};
w.draw();         // resolves to drawable::draw

// Two protocol methods, no inherent
protocol render { fn draw(&self); }
protocol paint  { fn draw(&self); }

impl widget as render { fn draw(&self) { ... } }
impl widget as paint  { fn draw(&self) { ... } }

// w.draw();          // translation failure — ambiguous
(w as render).draw(); // OK
(w as paint).draw();  // OK
```

## 9.3 Protocol declarations

A protocol declares a named interface. Its items are method prototypes, associated constants, and default methods.

### Syntax

```
protocol_decl = [ "pub", ws ], "protocol", ws, identifier,
                [ ws, generic_clause ],
                [ ws, ':', ws, bound ],
                ws, '{', ws, { protocol_item, ws }, '}' ;

protocol_item = { item_prefix, ws },
                ( method_proto | default_method | associated_const ) ;

default_method   = method_def ;
associated_const = "const", ws, identifier, ws, ':', ws, type,
                   [ ws, '=', ws, expression ], ws, ';' ;
```

### Static semantics

A protocol introduces a name into the enclosing scope. The name may be used as a bound on generic parameters (`.[ T: Protocol ]`), as the target of an `impl` block (`impl T as Protocol`), and as the referent of a protocol object type (`&dyn Protocol`), as defined in the subclause on protocol objects.

A protocol body contains zero or more **protocol items**. The three kinds of protocol item are:

— Method prototypes — a subroutine signature without a body. A protocol `impl` block provides it, as defined in the subclause on protocol implementations. A method prototype without a self parameter declares an associated subroutine. Method prototypes in protocols follow the same self-parameter grammar defined in the subclause on method declarations.

— Default methods — a method declaration standing in the protocol body, defined in the subclause on default methods. A default method has full access to `selftype`, to the other methods of the protocol, and to the protocol’s associated constants. A default method may invoke other methods of the same protocol on `self`, including those declared by a method prototype.

— Associated constants — a constant member declared with `const NAME: Type;` inside the protocol body. A protocol `impl` block provides a value unless the protocol provides a default expression, as defined in the subclause on protocol implementations.

#### Protocol identity

One protocol declaration is **congruent** with another where all of the following hold.

— The two declare the same number of bound elements, and corresponding elements agree, in declaration order. Two elements naming declared protocols agree where those declarations are congruent. Two elements naming built-in bounds agree where they name the same bound.

— The two declare the same number of methods, and corresponding methods bear the same parameter types in order and the same return type, in declaration order.

— The two declare the same number of associated constants, and corresponding constants bear the same type, in declaration order.

A descriptor emitted under one declaration describes every declaration congruent with it.

A descriptor reaches a translation unit other than the one that emitted it, as `#dyn` permits. The lowered symbol of a generic subroutine carries `%void` for a type parameter a protocol bounds, as the subclause on signature lowering defines. Where the declaration the receiving unit reads is not congruent with the declaration the emitting unit reads, an access through the descriptor can cause indeterminate state.

For the visibility modifier, defined in the clause on declarations, the namespace that declares an item of a `protocol` body is the one that encloses the `protocol` declaration.

### Constraints

A protocol name shall be unique within its scope. A protocol may be generic. The generic parameter rules defined in the clause on declarations apply.

### 9.3.1 Associated constants in protocols

#### Static semantics

An associated constant in a protocol follows the same access rules as in an inherent `impl` — `Type::NAME` or `(Type as Protocol)::NAME` — with the additional constraint that the value is determined by the implementing type.

An associated constant is not accessible through a reference to a protocol object.

#### Examples (informative)

```
pub protocol bounded {
    const min: selftype;
    const max: selftype;
}

impl ui1 as bounded {
    const min: ui1 = 0;
    const max: ui1 = 255~ui1;
}

fn clamp.[T: bounded + primitive](val: T) -> T {
    let lo = (T as bounded)::min;
    let hi = (T as bounded)::max;
    return if val < lo then lo else if val > hi then hi else val;
}
```

### 9.3.2 The bound upon a protocol

#### Static semantics

A protocol may require that implementing types satisfy further bounds. The requirement is expressed by a bound upon the protocol name. The items of a protocol the bound list names are available within the protocol’s default methods without additional qualification.

#### Examples (informative)

```
pub protocol printable: fmt + clone {
    fn print(&self) { println("{}", &[self as &dyn fmt]); }
}
```

### 9.3.3 Default methods

#### Static semantics

A **default method** is a protocol item whose declaration stands in the protocol body with its body present. Where an `impl` block for a type does not provide the item, that body is used. Where the `impl` block provides it, the provided body replaces the default entirely. A default method declared without a self parameter is an associated subroutine, and the same rules govern it.

#### Examples (informative)

```
pub protocol encodable {
    fn name(&self) -> &[ui1];

    fn encode(&self, out: $[ui1]) -> verdict.[uaddr, &[ui1]] {
        // invokes the method prototype
        return verdict::Fail(self.name());
    }
}
```

## 9.4 Protocol implementations

A protocol `impl` block provides the concrete methods, associated subroutines, and associated constants for a protocol on a specific type. The `impl_block` production is given in the subclause on inherent implementations.

### Static semantics

The effect of omitting or overriding a default method is defined in the subclause on default methods.

A protocol `impl` block may be generic, by the `impl(...)` parameter list. The target type and the protocol’s type arguments may reference the declared parameters.

### Constraints

All non-default methods declared in the protocol shall be provided. Associated constants shall be specified unless the protocol provides a default value.

The implementing type shall satisfy all bounds declared on the protocol.

### Examples (informative)

```
impl si4 as ord {
    fn cmp(&self, other: &selftype) -> ordering {
        return if *self > *other then ordering::greater
        else if *self < *other then ordering::less
        else ordering::equal;
    }
}

impl(T) vec.[T] as iterator.[T] {
    fn next($self) -> verdict.[T, void] {
        if self.pos < self.len {
            let val = self.data.at(self.pos);
            self.pos += 1;
            return verdict::Pass(val);
        } else {
            return verdict::Fail(void);
        }
    }
}
```

### 9.4.1 Duplicate detection

#### Static semantics

The implementation emits one protocol descriptor for each protocol instantiation a type implements. Its Zone B fields designate the bodies the emitting translation unit reads. Where two translation units each implement the same instantiation upon the same type, each emits its own descriptor, and an operation upon a descriptor reaches the bodies of the unit that emitted it.

#### Constraints

A type shall implement a given protocol instantiation at most once within the same translation unit. Instantiations that resolve the protocol’s generic parameters differently are distinct. The diagnostic shall identify both colliding implementations and a source unit from which both are reached in the `#add` dependency graph — a **collision source**.

## 9.5 Descriptors

A **descriptor** is an object of permanent object lifetime that the implementation emits for a concrete type. Code that does not name the concrete type loads from a descriptor to obtain the properties of the type upon which it operates. As defined in the clause on declarations, every type parameter carries the type descriptor, and each bound upon it carries a further descriptor. The type of a reference to a descriptor is `%void`.

Each subclause below gives the fields of one kind of descriptor, in order. Kurt standard alignment, applied to that sequence of field types, gives the offset of each field and the size and the alignment of the descriptor. A descriptor belongs to an environment, as the clause on expressions defines. A field type whose width derives from the cell width takes the cell width of that environment.

An item of a protocol is reached through a descriptor in two stages. **Resolution** takes a name to the item it denotes, within the declaration the translation unit reads, as the subclause on method name resolution defines. **Selection** takes that item to the field it occupies, by the index its declaration order assigns it.

### 9.5.3 Protocol descriptor

A **protocol descriptor** is divided into three zones, always in the following order.

#### Zone A — descriptor references

Zone A contains one `%void` field per bound element of the protocol’s bound list, in the order the elements are declared. Each field designates the descriptor that the element designates for the implementing type, as the subclause on bound descriptor emission defines. The field of a declared protocol designates a protocol descriptor of the same three zones, and the bounds of that protocol are reached through its own Zone A.

A protocol with no bound list has an empty Zone A.

#### Zone B — protocol method fields

Zone B contains one subroutine pointer field per method declared in the protocol body, in declaration order. Default methods occupy a field regardless of whether the implementing type overrides them. Where the implementation provides an override, the override’s subroutine pointer occupies the field, and otherwise the default body’s subroutine pointer occupies it.

#### Zone C — associated constant fields

Zone C contains one `%void` field per associated constant declared in the protocol body, in declaration order. Each field designates the object the implementing type gives the constant. That object permits no store and has permanent object lifetime.

#### Field indexing

A protocol descriptor holds the fields the three zones give it and no other. A method prototype and a default method each occupy a Zone B field, whether or not the declaration carries a self parameter.

Zone B begins at field `S`, where `S` is the number of bound elements. The `k`-th method declared in the protocol body, counting from zero, occupies field `S + k`. Zone C begins at field `S + M`, where `M` is the number of methods. The `k`-th associated constant declared in the protocol body occupies field `S + M + k`.

### 9.5.4 Descriptor field signatures

The type of the descriptor field a method occupies is the lowered signature of that method, as defined in the subclause on signature lowering.

The self parameter is the leading source parameter, and its type is the one the subclause on method declarations gives the receiver form it bears.
The type of a Zone C field is `%void`, whatever the declared type of the associated constant. A load of the constant reads the designated object under that declared type.

For an invocation through a protocol object, the descriptor references of `selftype` are the ones the subclause on protocol objects gives. The invocation supplies the descriptor references of every type parameter the method itself declares, determined from the type arguments the invocation gives, as it does for any generic invocation.

### 9.5.5 Protocol descriptor examples (informative)

A protocol with no bound list:

```
protocol ord {
    fn cmp(&self, other: &selftype) -> ordering;            // field 0
    fn lt(&self, other: &selftype) -> verdict.[void, void]; // field 1
    fn gt(&self, other: &selftype) -> verdict.[void, void]; // field 2
}

// Type descriptor for si4 (selftype'bound(type)):
// [0] = 4                (si4'size)
// [1] = 4                (si4'align)
// [2] = &null_destructor (si4 has no with destruct)

// Protocol descriptor for si4 as ord:
// [0] = &si4_cmp : fn(%mut void, %void, %void, %void, %void) -> void
// [1] = &si4_lt  : fn(%mut void, %void, %void, %void, %void) -> void
// [2] = &si4_gt  : fn(%mut void, %void, %void, %void, %void) -> void
//                     ^out       ^self  ^other ^tyd   ^prd
```

A protocol with a bound list:

```
protocol packet: measurable + clone {
    fn cksum(&self) -> si4;
}

// Protocol descriptor layout for packet:
// [0] = %void → measurable protocol descriptor (zone A)
// [1] = %void → clone protocol descriptor (zone A)
// [2] = &cksum : fn(%mut void, %void, %void, %void) -> void (zone B)
//                   ^out       ^self  ^tyd   ^prd
// measurable and clone add no descriptor parameter: the bound
// upon the implementing type is packet alone.
```

A bound list that names a built-in bound:

```
protocol scaled: measurable + numeric {
    fn scale(&self, by: selftype) -> selftype;
}

// Protocol descriptor layout for scaled:
// [0] = %void → measurable protocol descriptor (zone A)
// [1] = %void → arithmetic descriptor           (zone A)
// [2] = &scale : fn(%mut void, %void, %void, %void, %void) -> void
//                   ^out       ^self  ^by    ^tyd   ^prd  (zone B)
// The numeric field designates an arithmetic descriptor, not a
// protocol descriptor, and dispatch does not follow it.
```

A protocol whose result type is `selftype`:

```
protocol clone {
    fn clone(&self) -> selftype;
}

// Type descriptor for widget (selftype'bound(type)):
// [0] = widget'size
// [1] = widget'align
// [2] = &widget_destructor

// Protocol descriptor for widget as clone:
// [0] = &widget_clone : fn(%mut void, %void, %void, %void) -> void
//                          ^out       ^self  ^tyd   ^prd
// The invoker reserves the out-storage from the type
// descriptor, as the signature lowering requires.
```

## 9.6 Protocol objects

A **protocol object** is a type whose concrete identity is erased. `dyn Protocol` has size zero and alignment zero, and no object of the type is reserved. What the type erases is reached through a reference to `dyn Protocol`, which is sized under every family and modifier combination.

### Syntax

```
protocol_object_type = "dyn", ws, single_path ;
```

### Static semantics

A reference to a protocol object is a wide reference. Its stored representation contains three fields:

<table>
<thead><tr><th>Offset</th><th>Field</th><th>Content</th></tr></thead>
<tbody>
<tr><td>0</td><td><code>ptr</code></td><td>reference to the value</td></tr>
<tr><td><code>(%void)'size</code></td><td><code>tyd</code></td><td><code>%void</code> — type descriptor</td></tr>
<tr><td>2 × <code>(%void)'size</code></td><td><code>prd</code></td><td><code>%void</code> — protocol descriptor</td></tr>
</tbody>
</table>

The total size is 3 × `(%void)'size`, and the alignment is `(%void)'align`. The values the type descriptor reference and the protocol descriptor reference carry are defined in the clause on expressions, and the normative layout of both in the subclause on descriptors.

The type of `.ptr` is derived from the enclosing reference by the rule governing the fields of a wide reference view, defined in the subclause on slice references. The referent type is `void`. `.tyd` and `.prd` are `%void` under every family and modifier combination.

A managed reference is implicitly cast to a reference to `dyn Protocol` of the same family and the same modifiers when its referent type implements `Protocol`. The cast constructs a wide reference whose fields are those the subclause on bound descriptor emission gives.

### Dynamic semantics

Method invocations on protocol objects are dynamically dispatched, in the two stages the subclause on descriptors defines.

Resolution yields the method the invocation names, the protocol that declares it, and the protocols through which it reached that protocol, as the subclause on method name resolution defines.

Selection begins at the descriptor `.prd` carries. For each protocol through which the resolution reached the declaring protocol, in that order, it follows the Zone A field at the index that protocol’s bound element occupies, and so reaches the descriptor of the protocol that declares the method. It takes the field at the index that declaration assigns the method.

The implementation then loads the subroutine pointer from that field and performs an indirect invocation. The receiver is the object `.ptr` designates, and the self argument is the one the subclause on signature lowering requires for the self parameter the method bears. The type descriptor argument is `.tyd`, and the protocol descriptor argument is the descriptor selection reached.

An invocation of a method that takes `self` by value transfers the receiver into the self parameter, as the subclause on transfer defines transfer. The size and the alignment of the receiver are those `.tyd` gives.

### Constraints

`dyn Protocol` shall not appear in any of the following positions, other than as the referent of a reference:

— the type of a `let`, `const`, or `static` declaration.

— a subroutine parameter type or a return type.

— a struct field type, an array element type, a slice element type, or a tuple field type.

A method that takes `self` by value shall be invoked through a protocol object reference only where the `.ptr` field of that reference permits stores.

### Examples (informative)

```
fn print_value(val: &dyn fmt) {
    println("{}", &[val]);
}

let x: si4 = 42;
let b = verdict.[void, void]::Pass(void);
print_value(&x); // implicit cast: &si4 → &dyn fmt
print_value(&b); // &verdict.[void, void] → &dyn fmt

// Heterogeneous collection
let items: [&dyn fmt; 2] = [&x, &b];
let mut iter = items.iter();
while iter.next() -> item {
    println("value: {}", &[item]);
}
```

### Design rationale (informative)

The inheritance of `mut` by `.ptr` keeps the store permission of `.ptr` equal to that of the reference it is derived from: `&dyn Protocol` yields a `.ptr` of `%void`, and `&mut dyn Protocol` and `$dyn Protocol` yield `%mut void`. Code that does not name the concrete type therefore stores through `.ptr` in the cases in which the receiver reference permits a store, and in no other.

## 9.7 Built-in bounds

### Syntax

```
builtin_bound = "numeric" | "integer" | "primitive"
              | "copyable" | "variadic" | "atomic" ;
```

The implementation resolves the built-in bounds by type identity. The three arithmetic bounds form a strict hierarchy: `primitive` ⊂ `integer` ⊂ `numeric`.

### 9.7.1 `numeric`

#### Static semantics

A type satisfies `numeric` if and only if it is an integer type or a floating radix point number type.

#### Constraints

A type satisfying `numeric` shall not declare `with destruct`.

#### Notes (informative)

The operations that require `numeric` are the arithmetic operators, unary negation, and the comparison operators, as defined in the clause on expressions.

### 9.7.2 `integer`

#### Static semantics

A type satisfies `integer` if and only if it is an integer type.

#### Notes (informative)

Beyond those that require `numeric`, the operations that require `integer` are the bitwise operators, the shift operators, bitwise NOT, saturating arithmetic, and widening arithmetic, as defined in the clause on expressions, and the `discrim` argument on a variant type, as defined in the clause on types.

### 9.7.3 `primitive`

#### Static semantics

A type satisfies `primitive` if and only if it is an unsigned integer type.

### 9.7.4 `copyable`

#### Static semantics

The copyable and uncopyable classification of types is defined in the clause on references and resource management.

A type satisfies `copyable` if and only if it is not uncopyable. A type parameter declared without `copyable` accepts both copyable and uncopyable types, and its bindings within the declaration body follow transfer semantics.

#### Examples (informative)

```
fn duplicate.[T: copyable](val: T) -> .{T, T} {
    return .{val, val}; // T is copyable
}

fn store.[T](slot: $T, val: T) {
    *slot = val;
    // T follows transfer semantics, and val is not accessed after
}
```

### 9.7.5 `variadic`

#### Static semantics

A type satisfies `variadic` if and only if it is a struct declared `with variadic`. The type serves as the state object for variadic parameter capture within a subroutine declared with the `variadic` modifier. The `with variadic` declaration and the properties it grants are defined in the clause on types.

### 9.7.6 `atomic`

#### Static semantics

A type `T` satisfies `atomic` if and only if `T'size` is a size for which the execution environment provides atomic operations, `T'align` is not less than `T'size`, and `T` is copyable.

#### Implementation defined

The set of sizes for which the execution environment provides atomic operations is implementation defined. The implementation shall include a size in the set only where an arbitrary transformation of an object of that size can be applied atomically, using only the operations the execution environment provides and no storage beyond the object. The set can be empty. A conforming implementation shall document the set for each supported execution environment.

#### Notes (informative)

The operations that require `atomic` are the creation of atomic references, atomic load, atomic store, atomic compound assignment, and compare-and-swap, as defined in the clause on references and resource management.
