# §9. Protocols and implementations

This clause defines the mechanisms by which types acquire behaviour: the attachment of items to a single type, the items themselves, and the abstraction by which multiple types share an interface.

## 9.1 Inherent implementations

An `impl` block introduces associated subroutines and associated constants for a type. An `impl` block without an `as` clause is an **inherent implementation**, and introduces them into the type’s own namespace. One with an `as` clause is a **protocol implementation**, defined in the subclause on protocol implementations. An `impl(...)` parameter list introduces generic parameters whose scope is the whole `impl` block, the target type and the `as` clause included.

### Syntax

```
impl_block = "impl", [ ws, impl_generic_params ], ws, type,
             [ ws, "as", ws, single_path ],
             ws, '{', ws, { impl_item, ws }, '}' ;

impl_generic_params = '(', ws, generic_item, ws,
                      { ',', ws, generic_item, ws }, [ ',', ws ],
                      ')' ;

impl_item = { item_prefix, ws },
            ( method_def | associated_const_def ) ;

associated_const_def = [ "pub", ws ], "const", ws, identifier, ws,
                       [ ':', ws, type, ws ], '=', ws, expression,
                       ';' ;
```

### Static semantics

An **associated constant** is a translation-time constant scoped to the type’s namespace, accessed via `Type::NAME`. Its expression, or the default expression of the protocol where the `impl` block gives none, is evaluated at translation time once for each set of arguments to which an access to the constant, or the emission of a protocol descriptor with a field for the constant, resolves the generic parameters of the `impl(...)` parameter list, and once where the `impl` block carries no such list. The rule for an omitted type annotation is defined in the subclause on binding declarations. Its type may refer to `selftype`, as the subclause on associated subroutine declarations defines it.

For the visibility modifier, defined in the clause on declarations, the namespace that declares an item of an `impl` block is the one that encloses the block.

Multiple inherent `impl` blocks for the same type are permitted. Items from different `impl` blocks on the same type are merged into a single namespace.

The resolution of name overlap between an inherent `impl` item and a protocol `impl` item on the same type is defined in the subclause on name resolution.

A **parameter anchor** of a parameter of an `impl(...)` parameter list is the target type where the target type is the parameter itself, or a type argument or dependence argument, of the target type or of the protocol the `as` clause names and at any depth of nesting, that is the parameter itself. The bound of the parameter is the bound the list places upon it, followed by the bound elements that each generic declaration places on the generic parameter a parameter anchor of it resolves, with the arguments of that declaration substituted and in its declaration order, the parameter anchors taken in the order they appear in the target type and then in the `as` clause. An element already in the bound is not repeated.

### Constraints

A name collision between items from different inherent `impl` blocks on the same type shall not appear.

Each parameter of an `impl(...)` parameter list shall have a parameter anchor. In a protocol implementation, the `impl(...)` parameter list shall place no bound upon a parameter.

A `type` declaration inside an inherent `impl` block shall not appear.

An identifier declared in an `impl(...)` parameter list shall not share its name with any declaration visible in the enclosing scope at the point of the `impl` block.

### Examples (informative)

```
impl(T) stack.[T] {
    // Associated subroutine — constructor, invoked via stack::new()
    pub fn new() -> selftype { ... }

    // Associated subroutine — factory with capacity
    pub fn with_capacity(cap: uaddr) -> selftype { ... }

    // Methods — invoked via value.method()
    pub fn push($self, val: T) { ... }
    pub fn pop($self) -> verdict.[T, void] { ... }
    pub fn len(&self) -> uaddr { return (*self).len; }
    pub fn is_empty(&self) -> verdict.[void, void] {
        return (*self).len == 0;
    }
}

impl si4 {
    // Associated constants — accessed via si4::min, si4::max
    pub const min: si4 = -2147483648;
    pub const max: si4 = 2147483647;
    // type inferred from the initializer
    pub const zero = 0~si4;
}

// Usage
let mut s = stack.[si4]::new(); // associated subroutine
s.push(42);                     // method
let m = si4::max;               // associated constant
```

## 9.2 Associated subroutine declarations

### Syntax

```
method_def          = [ "pub", ws ], [ "airside", ws ], "fn", ws,
                      identifier, [ ws, generic_clause ], ws, '(', ws,
                      method_params, ws, ')', [ ws, '->', ws, type ],
                      [ ws, with_single | ws, with_curly ], ws, block ;

subroutine_proto    = [ "pub", ws ], [ "airside", ws ], "fn", ws,
                      identifier, [ ws, generic_clause ], ws, '(', ws,
                      subroutine_proto_params, ws, ')',
                      [ ws, '->', ws, type ],
                      [ ws, with_single | ws, with_curly ], ws, ';' ;

method_params       = self_param, [ ws, ',', ws, parameter_list ],
                      [ ws, ',' ]
                    | [ parameter_list ], [ ws, ',' ] ;

subroutine_proto_params = self_param,
                      [ ws, ',', ws, proto_parameter_list ], [ ws, ',' ]
                    | [ proto_parameter_list ], [ ws, ',' ] ;

self_param          = [ ( ( '&' | '$' ), ws,
                      { ref_modifier, ws } )
                      | ( "mut", ws ) ],
                      ( "self" | '[', ws, "self", ws, ']' ) ;
```

### Static semantics

A subroutine in an `impl` block or protocol body is an **associated subroutine**. It is invoked through a qualified path. An associated subroutine that carries a self parameter is a **method**, and is invoked through the `.` operator as well.

`selftype` is a keyword that stands, in a type position, for a type the enclosing declaration fixes.

Within an `impl` declaration, `selftype` stands for the type the declaration implements upon, from the point where the type is written to the end of the declaration. Where the declaration carries an `as` clause, `selftype` is, for signature lowering alone, a type parameter of every subroutine the declaration provides, and the bound upon it there is the protocol the `as` clause names. Within a `protocol` declaration, `selftype` stands for the type of an eventual implementer, throughout the declaration, and is a type parameter of every item the protocol declares. It precedes every type parameter the item declares, and the bound upon it is the protocol that declares the item. Within a `struct`, `enum`, or `contract` declaration, `selftype` stands for the declaration, and takes generic arguments as the declaration’s name does.

The self parameter forms are:

— `self` — the receiver by value, single-assignment binding. Equivalent to `self: selftype`.

— `mut self` — the receiver by value, multi-assignment binding. Equivalent to `mut self: selftype`.

— `X self` and `X[self]`, where `X` combines the tribe `&` or `$` with any permitted modifiers — equivalent respectively to `self: X selftype` and to `self: X[selftype]`, the latter a slice reference with element type `selftype`.

### Constraints

`self` shall appear in a parameter list only as the self parameter.

`mut &self` and `mut $self` shall not appear.

A bracketed receiver without a preceding tribe — `[self]` — shall not appear. `mut [self]` shall not appear.

The receiver tribe is `&` or `$`.

### Design rationale (informative)

A slice appears only as the referent of a reference. The bracketed forms therefore require the `&` or `$` tribe.

`%` is excluded because method dispatch through `.` resolves a receiver without an enclosing `airside` block, while access through an unmanaged reference requires one. Permitting `%self` would conceal unmanaged access behind `.` or impose a receiver-dependent `airside` requirement at the invocation site. A subroutine with no self parameter, taking `%selftype` as its leading parameter, provides the same operation through ordinary invocation syntax inside an `airside` block.

### Examples (informative)

```
impl(T) T {
    fn at(&[self], idx: uaddr) -> &selftype {
        // self: &[T]
        ...
    }

    fn at_xcl($[self], idx: uaddr) -> $selftype {
        // self: $[T]
        ...
    }
}
```

### 9.2.1 Name resolution

#### Static semantics

Where the type of `e` after reference transparency is a protocol object type, the invocation resolves to the method named `m` that the protocol declares. Where the protocol declares no method of that name, the search proceeds through the protocols its bound list names, in declaration order, each searched by this same rule. Where the search reaches methods named `m` of exactly one protocol instantiation, the invocation resolves to the method named `m` of that instantiation, by the first path the search takes. Where it reaches methods named `m` of two or more protocol instantiations, the invocation is ambiguous. Where it reaches none, the invocation resolves to no method.

Where the search for a protocol object type reaches a method whose self parameter is bracketed, or whose signature mentions `selftype` other than as the type of its self parameter, the invocation resolves to no method.

Where the type of `e` after reference transparency is a type parameter, each protocol its bound names is searched as the first paragraph of this subclause searches a protocol, in the order the bound names them. Where the searches reach methods named `m` of exactly one protocol instantiation between them, the invocation resolves to the method named `m` of that instantiation, by the first path the searches take. Where they reach methods named `m` of two or more protocol instantiations, the invocation is ambiguous. Where they reach none, the invocation resolves to no method.

Where that type is `[U]`, the invocation resolves by the procedures of this subclause applied to `U`, and only a method whose self parameter is bracketed resolves.

For every other type, a method invocation `e.m(args)` is resolved by the following procedure, applied to that type:

1. If an inherent `impl` block on the type provides a method named `m`, the invocation resolves to the method.
2. Otherwise, the protocols of the implementations witnessed for the type, as the subclause on `with impl` defines witnessed implementations, are searched, each as the first paragraph of this subclause searches a protocol:

— Where the searches reach methods named `m` of exactly one implementation between them, the invocation resolves to the method named `m` of that implementation, by the first path the searches take.

— Where they reach methods named `m` of two or more implementations, the invocation is ambiguous.

— Where they reach none, the invocation resolves to no method.

A qualified method invocation, defined in the clause on expressions, resolves to the implementation of the named protocol for the type of the receiver that is witnessed, as the subclause on `with impl` defines witnessed implementations.

The same resolution procedure applies to associated subroutines and associated constants accessed through a path (`Type::item`). A path whose qualified path root is `(Type as Protocol)` reaches the item from the implementation of `Protocol` for `Type`, determined as for a qualified method invocation.

#### Constraints

An invocation or access that resolves to two or more protocol methods, or to no method, shall not appear. An access to an associated subroutine or associated constant through a path that resolves to two or more protocol items of the same name shall not appear. Protocol items are defined in the subclause on protocol declarations.

#### Examples (informative)

```
// Inherent method takes priority over protocol method
struct counter { val: ui4 }

impl counter {
    pub fn get(&self) -> ui4 { return self.val; }
}

protocol readable {
    fn get(&self) -> ui4;
}

impl counter as readable {
    fn get(&self) -> ui4 { return self.val * 2; }
}

let c = counter.{ .val = 5 };
c.get();          // resolves to inherent — yields 5
(c as readable).get(); // resolves to readable impl — yields 10

// Single protocol method, no inherent
struct widget {}

impl widget as drawable {
    fn draw(&self) { ... }
}

let w = widget.{};
w.draw();         // resolves to drawable::draw

// Two protocol methods, no inherent
protocol render { fn draw(&self); }
protocol paint  { fn draw(&self); }

impl widget as render { fn draw(&self) { ... } }
impl widget as paint  { fn draw(&self) { ... } }

// w.draw();          // translation failure — ambiguous
(w as render).draw(); // OK
(w as paint).draw();  // OK
```

## 9.3 Protocol declarations

A protocol declares a named interface.

### Syntax

```
protocol_decl = [ "pub", ws ], "protocol", ws, identifier,
                [ ws, generic_clause ],
                [ ws, ':', ws, bound ],
                ws, '{', ws, { protocol_item, ws }, '}' ;

protocol_item = { item_prefix, ws },
                ( subroutine_proto | default_subroutine | associated_const ) ;

default_subroutine = method_def ;
associated_const = "const", ws, identifier, ws, ':', ws, type,
                   [ ws, '=', ws, expression ], ws, ';' ;
```

### Static semantics

A protocol introduces a name into the enclosing scope. The name may be used as a bound on generic parameters (`.[ T: Protocol ]`), as the target of an `impl` block (`impl T as Protocol`), and as the referent of a protocol object type (`&dyn Protocol`), as defined in the subclause on protocol objects.

A protocol body contains zero or more **protocol items**. The three kinds of protocol item are:

— Subroutine prototypes — an associated subroutine signature without a body. A subroutine prototype in a protocol follows the same self-parameter grammar defined in the subclause on associated subroutine declarations.

— Default protocol subroutines — an associated subroutine declaration standing in the protocol body with its body present, defined in the subclause on default protocol subroutines. A default protocol subroutine may name `selftype` and every other item of the protocol.

— Associated constants — a constant member declared with `const NAME: Type;` inside the protocol body.

#### Protocol identity

One protocol declaration is **congruent** with another where all of the following hold. In each item, a generic parameter of one declaration and the corresponding generic parameter of the other are taken to be the same generic parameter, and the `selftype` of the one and that of the other the same type.

— The two declare the same number of generic parameters, and corresponding parameters, in declaration order, are of the same kind. Corresponding dependence parameters bear the same type. Corresponding type parameters bear the same number of bound elements, and their corresponding elements, in the order of the bound, agree as the next item defines agreement.

— The two declare the same number of bound elements, and corresponding elements agree, in declaration order. Two elements naming declared protocols agree where those declarations are congruent and their generic arguments are the same. Two elements naming built-in bounds agree where they name the same bound.

— The two declare the same number of associated subroutines, and corresponding subroutines, in declaration order, bear the same airside status, generic clauses whose parameters correspond as the first item requires, the same parameter types in order, the same return type, and the same number of subject bounds, corresponding subject bounds agreeing in order. Two subject bounds agree where their subjects are the same and their protocols agree as the second item defines agreement.

— The two declare the same number of associated constants, and corresponding constants bear the same type, in declaration order.

A descriptor emitted under one declaration describes every declaration congruent with it.

A descriptor reaches a translation unit other than the one that emitted it, as `#dyn` permits. The lowered symbol of a generic subroutine carries `%void` for a type parameter a protocol bounds, as the subclause on signature lowering defines. Where the declaration the receiving unit reads is not congruent with the declaration the emitting unit reads, an access through the descriptor can cause indeterminate state.

For the visibility modifier, defined in the clause on declarations, the namespace that declares an item of a `protocol` body is the one that encloses the `protocol` declaration.

### Constraints

A protocol name shall be unique within its scope. A protocol may be generic. The generic parameter rules defined in the clause on declarations apply.

### 9.3.1 Associated constants in protocols

#### Static semantics

An associated constant is not accessible through a reference to a protocol object.

#### Examples (informative)

```
pub protocol bounded {
    const min: selftype;
    const max: selftype;
}

impl ui1 as bounded {
    const min: ui1 = 0;
    const max: ui1 = 255~ui1;
}

fn clamp.[T: bounded + primitive](val: T) -> T {
    let lo = (T as bounded)::min;
    let hi = (T as bounded)::max;
    return if val < lo then lo else if val > hi then hi else val;
}
```

### 9.3.2 The bound upon a protocol

#### Static semantics

A protocol may require that implementing types satisfy further bounds. The requirement is expressed by a bound upon the protocol name. The items of a protocol the bound list names may be named within the default protocol subroutines of the protocol without additional qualification.

#### Constraints

A protocol shall not name itself in its bound list, directly or through the bound lists of the protocols that list names.

#### Examples (informative)

```
pub protocol printable: fmt + clone {
    fn print(&self) { println("{}", &[self as &dyn fmt]); }
}
```

### 9.3.3 Default protocol subroutines

#### Static semantics

A **default protocol subroutine** is a protocol item whose declaration stands in the protocol body with its body present. Where an `impl` block for a type does not provide the item, that body is used. Where the `impl` block provides it, the provided body replaces the default entirely.

#### Examples (informative)

```
pub protocol encodable {
    fn name(&self) -> &[ui1];

    fn encode(&self, out: $[ui1]) -> verdict.[uaddr, &[ui1]] {
        // invokes the subroutine prototype
        return verdict::Fail(self.name());
    }
}
```

## 9.4 Protocol implementations

A protocol `impl` block provides the associated subroutines and associated constants for a protocol on a specific type. The `impl_block` production is given in the subclause on inherent implementations.

### Constraints

Every subroutine prototype declared in the protocol shall be provided. An associated constant shall be provided unless the protocol provides a default expression for it. A protocol `impl` block shall provide only items the protocol declares.

An associated subroutine a protocol `impl` block provides shall state the `airside` modifier, the generic clause, the self parameter, each parameter type, the return type, and the subject bounds as the protocol declares them, in the same order, with the generic arguments of the `as` clause substituted for the protocol’s generic parameters and the target type for `selftype`. A receiver by value may differ from the one the protocol declares in `mut` alone. An associated constant it provides shall bear the type the protocol declares for it.

The implementing type shall satisfy all bounds declared on the protocol.

### Examples (informative)

```
impl si4 as ord {
    fn cmp(&self, other: &selftype) -> ordering {
        return if *self > *other then ordering::greater
        else if *self < *other then ordering::less
        else ordering::equal;
    }
}

impl(T) vec.[T] as iterator.[T] {
    fn next($self) -> verdict.[T, void] {
        if self.pos < self.len {
            let val = self.data.at(self.pos);
            self.pos += 1;
            return verdict::Pass(val);
        } else {
            return verdict::Fail(void);
        }
    }
}
```

### 9.4.1 Duplicate detection

#### Static semantics

The implementation emits one protocol descriptor for each protocol instantiation a type implements. Its Zone B fields designate the bodies the emitting translation unit reads. Where two translation units each implement the same instantiation upon the same type, each emits its own descriptor, and an operation upon a descriptor reaches the bodies of the unit that emitted it.

#### Constraints

A type shall implement a given protocol instantiation at most once within the same translation unit. Instantiations that resolve the protocol’s generic parameters differently are distinct. The diagnostic shall identify both colliding implementations and a source unit from which both are reached in the `#add` dependency graph.

### 9.4.2 `with impl`

A `with impl` item requires that a type implement a protocol, and makes that implementation witnessed within the subroutine that carries it.

#### Syntax

```
subject_bound = "impl", ws, type, ws, "as", ws, single_path ;
```

#### Static semantics

A `with impl` item is a **subject bound**. It stands in the `with` clause of a subroutine definition, of a subroutine prototype, or of a subroutine pointer type. The type it names before `as` is its **subject**, and the protocol its `single_path` names is its protocol.

An implementation of a protocol for a type is reached only where it is **witnessed**, and a protocol descriptor is formed only for a witnessed implementation. Where neither the type nor the generic arguments of the protocol involve a generic parameter, every implementation of the protocol for the type is witnessed. Otherwise, the implementations witnessed are the following.

— The implementations a bound on a type parameter names for that type parameter.

— The implementations the subject bounds of the subroutine name for their subjects.

— Within a protocol `impl` block, the implementation the block provides for its target type.

— For each implementation witnessed, the implementations for the same type of the protocols the bound list of its protocol names, with the generic arguments of its protocol substituted.

At each invocation of the subroutine, the invoker supplies, for each subject bound with the argument each of its generic parameters resolves to at the invocation substituted, an implementation of the protocol for the subject that is witnessed within the invoker.

#### Constraints

Except within the signature of an associated subroutine that a protocol `impl` block provides, a subject bound shall involve a generic parameter in its subject or in a generic argument of its protocol, its subject shall not be a type parameter, and no other subject bound of the same declaration shall bear the same subject and the same protocol instantiation. The subject of a subject bound of an associated subroutine that a protocol body declares, and the generic arguments of its protocol, shall not involve `selftype`.

An invocation whose invoker cannot supply a witnessed implementation for a subject bound, or for a bound element of a type parameter that names a declared protocol, shall not appear.

## 9.5 Descriptors

A **descriptor** is an object that the implementation emits for a type. As defined in the clause on declarations, every type parameter carries the type descriptor, and each bound upon it carries a further descriptor. The type of a reference to a descriptor is `%void`.

Each subclause below gives the fields of one kind of descriptor, in order. Kurt standard alignment, applied to that sequence of field types, gives the offset of each field and the size and the alignment of the descriptor. A descriptor belongs to an environment, as the clause on expressions defines. A field type whose width derives from the cell width takes the cell width of that environment.

An item of a protocol is reached through a descriptor in two stages. **Resolution** takes a name to the item it denotes, within the declaration the translation unit reads, as the subclause on name resolution defines. **Selection** takes that item to the field it occupies, by the index its declaration order assigns it.

### 9.5.3 Protocol descriptor

A **protocol descriptor** is divided into three zones, always in the following order.

#### Zone A — descriptor references

Zone A contains one `%void` field per bound element of the protocol’s bound list, in the order the elements are declared. Each field designates the descriptor that the element designates for the implementing type, as the subclause on bound descriptor emission defines. The field of a declared protocol designates a protocol descriptor of the same three zones, and the bounds of that protocol are reached through its own Zone A.

A protocol with no bound list has an empty Zone A.

#### Zone B — protocol subroutine fields

Zone B contains one subroutine pointer field per associated subroutine declared in the protocol body, in declaration order. Where the protocol `impl` block provides the associated subroutine, the subroutine pointer of the body it provides occupies the field, and otherwise the default body’s subroutine pointer occupies it.

#### Zone C — associated constant fields

Zone C contains one `%void` field per associated constant declared in the protocol body, in declaration order. Each field designates the object the implementing type gives the constant, and where the implementing type gives none, the object the protocol’s default expression yields with the generic arguments of the `as` clause substituted for the protocol’s generic parameters and the implementing type for `selftype`. That object permits no store and has permanent object lifetime.

#### Field indexing

A protocol descriptor holds the fields the three zones give it and no other.

Zone B begins at field `S`, where `S` is the number of bound elements. The `k`-th associated subroutine declared in the protocol body, counting from zero, occupies field `S + k`. Zone C begins at field `S + M`, where `M` is the number of associated subroutines. The `k`-th associated constant declared in the protocol body occupies field `S + M + k`.

### 9.5.4 Descriptor field signatures

The type of the descriptor field an associated subroutine occupies is the lowered signature of the subroutine as the protocol declares it, as defined in the subclause on signature lowering. A generic parameter of the protocol remains a generic parameter in that lowering, whatever the `impl` block resolves it to. An associated subroutine that a protocol `impl` block provides has that lowered signature.

The self parameter is the leading source parameter, and its type is the one the subclause on associated subroutine declarations gives the receiver form it bears.

The type of a Zone C field is `%void`, whatever the declared type of the associated constant. A load of the constant reads the designated object under that declared type.

For an invocation through a protocol object, the descriptor references of `selftype` are the ones the subclause on protocol objects gives. The invocation supplies the descriptor references and dependence arguments of every generic parameter the protocol and the subroutine declare, and of every subject bound the subroutine carries, determined from the generic arguments the protocol object type and the invocation give, as it does for any generic invocation.

#### Examples (informative)

```
// protocol ord, impl si4 as ord
// Source: fn cmp(&self, other: &selftype) -> ordering
// Field:  fn(%mut void, %void, %void, %void, %void) -> void
//            ^out       ^self  ^other ^tyd   ^prd

// protocol measurable, impl si4 as measurable
// Source: fn width(&self) -> uaddr
// Field:  fn(%mut void, %void, %void, %void) -> void
//            ^out       ^self  ^tyd   ^prd

// protocol clone, impl widget as clone
// Source: fn clone(&self) -> selftype
// Field:  fn(%mut void, %void, %void, %void) -> void
//            ^out       ^self  ^tyd   ^prd

// protocol keyed.[K], impl widget as keyed.[ui4]
// Source: fn at(&self, key: K) -> uaddr
// Field:  fn(%mut void, %void, %void, %void, %void, %void) -> void
//            ^out       ^self  ^key   ^tyd   ^prd   ^K

// protocol seekable — a parameter naming no protocol parameter
// Source: fn skip(&self, n: uaddr) -> uaddr
// Field:  fn(%mut void, %void, uaddr, %void, %void) -> void
//            ^out       ^self  ^n     ^tyd   ^prd
```

A protocol with no bound list:

```
protocol ord {
    fn cmp(&self, other: &selftype) -> ordering;            // field 0
    fn lt(&self, other: &selftype) -> verdict.[void, void]; // field 1
    fn gt(&self, other: &selftype) -> verdict.[void, void]; // field 2
}

// Type descriptor for si4 (selftype'bound(type)):
// [0] = 4                (si4'size)
// [1] = 4                (si4'align)
// [2] = &null_destructor (si4 has no with destruct)
// [3] = &empty           (si4 is not a generic instantiation)

// Protocol descriptor for si4 as ord:
// [0] = &si4_cmp : fn(%mut void, %void, %void, %void, %void) -> void
// [1] = &si4_lt  : fn(%mut void, %void, %void, %void, %void) -> void
// [2] = &si4_gt  : fn(%mut void, %void, %void, %void, %void) -> void
//                     ^out       ^self  ^other ^tyd   ^prd
```

A protocol with a bound list:

```
protocol packet: measurable + clone {
    fn cksum(&self) -> si4;
}

// Protocol descriptor layout for packet:
// [0] = %void → measurable protocol descriptor (zone A)
// [1] = %void → clone protocol descriptor (zone A)
// [2] = &cksum : fn(%mut void, %void, %void, %void) -> void (zone B)
//                   ^out       ^self  ^tyd   ^prd
// measurable and clone add no descriptor parameter: the bound
// upon the implementing type is packet alone.
```

A bound list that names a built-in bound:

```
protocol scaled: measurable + numeric {
    fn scale(&self, by: selftype) -> selftype;
}

// Protocol descriptor layout for scaled:
// [0] = %void → measurable protocol descriptor (zone A)
// [1] = %void → arithmetic descriptor           (zone A)
// [2] = &scale : fn(%mut void, %void, %void, %void, %void) -> void
//                   ^out       ^self  ^by    ^tyd   ^prd  (zone B)
// The numeric field designates an arithmetic descriptor, not a
// protocol descriptor, and dispatch does not follow it.
```

A protocol whose result type is `selftype`:

```
protocol clone {
    fn clone(&self) -> selftype;
}

// Type descriptor for widget (selftype'bound(type)):
// [0] = widget'size
// [1] = widget'align
// [2] = &widget_destructor
// [3] = &empty (widget is not a generic instantiation)

// Protocol descriptor for widget as clone:
// [0] = &widget_clone : fn(%mut void, %void, %void, %void) -> void
//                          ^out       ^self  ^tyd   ^prd
// The invoker reserves the out-storage from the type
// descriptor, as the signature lowering requires.
```

## 9.6 Protocol objects

A **protocol object** is a type whose concrete identity is erased. `dyn Protocol` has size zero and alignment zero, and no object of the type is reserved.

### Syntax

```
protocol_object_type = "dyn", ws, single_path ;
```

### Static semantics

A reference to a protocol object is a wide reference. Its stored representation contains three fields:

<table>
<thead><tr><th>Offset</th><th>Field</th><th>Content</th></tr></thead>
<tbody>
<tr><td>0</td><td><code>ptr</code></td><td>reference to the value</td></tr>
<tr><td><code>(%void)'size</code></td><td><code>tyd</code></td><td><code>%void</code> — type descriptor</td></tr>
<tr><td>2 × <code>(%void)'size</code></td><td><code>prd</code></td><td><code>%void</code> — protocol descriptor</td></tr>
</tbody>
</table>

The total size is 3 × `(%void)'size`, and the alignment is `(%void)'align`. The values the type descriptor reference and the protocol descriptor reference carry are defined in the clause on expressions, and the normative layout of both in the subclause on descriptors.

The type of `.ptr` is the one the subclause on slice references gives `.ptr` of a slice reference of the same tribe and modifiers. The referent type is `void`. `.tyd` and `.prd` are `%void` under every tribe and modifier combination.

A managed reference is implicitly cast to a reference to `dyn Protocol` of the same tribe and the same modifiers when an implementation of `Protocol` for its referent type is witnessed, as the subclause on `with impl` defines witnessed implementations. The cast constructs a wide reference whose fields are those the subclause on bound descriptor emission gives.

### Dynamic semantics

A method invocation on a protocol object is performed in the two stages the subclause on descriptors defines.

Resolution yields the method the invocation names, the protocol that declares it, and the protocols through which it reached that protocol, as the subclause on name resolution defines.

Selection begins at the descriptor `.prd` carries. For each protocol through which the resolution reached the declaring protocol, in that order, it follows the Zone A field at the index that protocol’s bound element occupies, and so reaches the descriptor of the protocol that declares the method. It takes the field at the index that declaration assigns the method.

The implementation then loads the subroutine pointer from that field and performs an indirect invocation. The receiver is the object `.ptr` designates, and the self argument is the one the subclause on signature lowering requires for the self parameter the method bears. The type descriptor argument is `.tyd`, and the protocol descriptor argument is the descriptor selection reached.

An invocation of a method that takes `self` by value transfers the receiver into the self parameter, as the subclause on transfer defines transfer. The size and the alignment of the receiver are those `.tyd` gives.

### Constraints

`dyn Protocol` shall not appear in any of the following positions, other than as the referent of a reference:

— the type of a `let`, `const`, or `static` declaration.

— a subroutine parameter type or a return type.

— a struct field type, an array element type, a slice element type, or a tuple field type.

A method that takes `self` by value shall be invoked through a protocol object reference only where the `.ptr` field of that reference permits stores.

### Design rationale (informative)

The inheritance of `mut` by `.ptr` keeps the store permission of `.ptr` equal to that of the reference it is derived from: `&dyn Protocol` yields a `.ptr` of `%void`, and `&mut dyn Protocol` and `$dyn Protocol` yield `%mut void`. Code that does not name the concrete type therefore stores through `.ptr` in the cases in which the receiver reference permits a store, and in no other.

### Examples (informative)

```
fn print_value(val: &dyn fmt) {
    println("{}", &[val]);
}

let x: si4 = 42;
let b = verdict.[void, void]::Pass(void);
print_value(&x); // implicit cast: &si4 → &dyn fmt
print_value(&b); // &verdict.[void, void] → &dyn fmt

// Heterogeneous collection
let items: [&dyn fmt; 2] = [&x, &b];
let mut iter = items.iter();
while iter.next() -> item {
    println("value: {}", &[item]);
}
```

## 9.7 Built-in bounds

### Syntax

```
builtin_bound = "numeric" | "integer" | "primitive"
              | "copyable" | "variadic" | "atomic" ;
```

### 9.7.1 `numeric`

#### Static semantics

A type satisfies `numeric` if and only if it is an integer type or a floating radix point number type.

#### Constraints

A type satisfying `numeric` shall not declare `with destruct`.

### 9.7.2 `integer`

#### Static semantics

A type satisfies `integer` if and only if it is an integer type.

### 9.7.3 `primitive`

#### Static semantics

A type satisfies `primitive` if and only if it is an unsigned integer type.

### 9.7.4 `copyable`

#### Static semantics

The copyable and uncopyable classification of types is defined in the clause on references and resource management.

A type satisfies `copyable` if and only if it is not uncopyable. A type parameter declared without `copyable` accepts both copyable and uncopyable types, and its bindings within the declaration body follow transfer semantics.

#### Examples (informative)

```
fn duplicate.[T: copyable](val: T) -> .{T, T} {
    return .{val, val}; // T is copyable
}

fn store.[T](slot: $T, val: T) {
    *slot = val;
    // T follows transfer semantics, and val is not accessed after
}
```

### 9.7.5 `variadic`

#### Static semantics

A type satisfies `variadic` if and only if it is a struct declared `with variadic`. The type serves as the state object for variadic parameter capture within a subroutine declared with the `variadic` modifier. The `with variadic` declaration and the properties it grants are defined in the clause on types.

### 9.7.6 `atomic`

#### Static semantics

A type `T` satisfies `atomic` if and only if `T'size` is a size for which the execution environment provides atomic operations, `T'align` is not less than `T'size`, and `T` is copyable.

#### Implementation defined

The set of sizes for which the execution environment provides atomic operations is implementation defined. The implementation shall include a size in the set only where an arbitrary transformation of an object of that size can be applied atomically, using only the operations the execution environment provides and no storage beyond the object. The set can be empty. A conforming implementation shall document the set for each supported execution environment.
